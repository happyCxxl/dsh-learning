## 0. 怎么读这一课（先看这段）

### 0.1 这一课是什么、不是什么

**是**：**一次分发到底发生了什么**——五种模式各自的"要不要等""谁能让它停""返回值归谁"。
**不是**：事件全景账（哪些事件属于哪个域、谁生产谁消费）——那是 `3.2` 与 `4.4`；也不是作用域过滤的实现（`2.5`）。

### 0.2 现在只要记住这 5 件事

1. 五种模式 = `emit` / `waterfall` / `parallel` / `serial` / `bail`，**名字就是方法名**：`ctx.emit(...)`、`ctx.waterfall(...)`……
2. **只有 `waterfall` 有 `next()`**；也只有"不调 `next()`"这一种短路方式会**连内建行为一起跳过**。
3. `serial` / `bail` 的提前停止看**返回值**（非 `null`/非 `false`/非 `undefined` 就停），与 `next` 无关；`emit` / `parallel` **谁都不能停**。
4. 五种方法**共用一个前半段** `dispatch()`：它负责"从参数里取出事件名"和"按作用域过滤出监听器名单"。**顺序永远等于注册顺序**（除非用 `prepend`）。
5. **`emit` 不是安全的广播**：它用 `Array.map` 调监听器，一次同步抛出会**饿死后面的监听器**，返回的 Promise 也没人持有。DSH 因此有三个包各自重写了"逐个容错"的 emit。

### 0.3 明确授权：这些词现在不用管

`Fiber`、`Service`、`inject`、`realm`、`isolate`、`shadowing`、`prepend` 的完整语义、`internal/update` 的配置拦截——**本课一个都不需要你弄懂**。
判断标准只有一条：**只要你能回答"这个词在分发流程的哪一步出现"，就够了**；其余等对应课展开（见附录 B）。

### 0.4 如果你是第一次读，跳过附录 A 的 Q3、Q4

## 1. 最小词汇表（本课新增的 7 个词）

前几课已定义过的词只有 `plugin` / `ctx` / `service`（`1.1`）。下面这 7 个是本课新用的，**只用大白话 + 上面那 3 个词解释**。

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **listener 监听器** | 一段"有这件事发生时请调用我"的函数。它被登记在某个事件名下 | `ctx.on('事件名', listener)` |
| **dispatch 分发** | "把这件事通知出去"这个动作本身 | `ctx.emit(...)` / `ctx.waterfall(...)` / `ctx.serial(...)` / `ctx.parallel(...)` / `ctx.bail(...)` |
| **mode 模式** | 一个事件被通知出去的**方式**；同一个事件只能用一种方式通知 | `DispatchMode`，五种取值 |
| **thisArg 载体** | 可选的第一实参：告诉框架"我是代表谁在发这件事"，用于作用域过滤 | `ctx.waterfall(carrier, 'agent/pre-step', …)` 里的 `carrier` |
| **next** | `waterfall` 交给监听器的一个动作：**调用它 = 继续问下一个人** | 监听器参数表最后那个 `next: () => …` |
| **inner 内建行为** | 调用方提供的"没人拦截时默认该做的事"；它就是 `next` 链的最后一环 | `args.pop()` 取出来的那个值 |
| **bail 值** | `serial`/`bail` 眼里的"我要就此打住"的返回值 | `isBailed(value)` 为真 |

> ⚠️ 这 7 个词都属于 **Cordis（第二编的主题）**。本课只用上面这个程度：为什么 `ctx` 能"点"出这些方法、载体怎么参与作用域过滤，`2.1`/`2.5` 才答。

## 2. 先建立画面

### 2.1 静态结构：一个事件名背后有什么

```
事件名（例如 'agent/pre-step'）
  └─ EventsService._hooks[name] : Hook[]        ← 按【注册顺序】排的监听器名单
       │                                            （prepend: true 会插到最前）
       ├─ Hook₁ { ctx, callback, global?, prepend? }
       ├─ Hook₂
       └─ Hook₃

五种公开方法（emit / parallel / serial / bail / waterfall）
  └─ 第一步都相同：this.dispatch(type, args)
       ① 若首个实参是 object/function → 当作 thisArg（载体）取走
       ② 取走事件名
       ③ 事件名不以 'internal/' 开头 → 先发一条 internal/dispatch 诊断事件
       ④ 按 thisArg 上的 Context.filter 过滤名单，并把 callback 绑到 thisArg 上
  └─ 第二步各不相同：各自的循环 / 等待 / 短路规则
```

### 2.2 动态过程：一次 `waterfall` 是怎么下探的

```
调用方：ctx.waterfall(carrier, 'x/wf', payload, inner)      ← inner = 内建行为
        │
        ▼
dispatch('waterfall', args) ──► cbs = [cb₁, cb₂]            ← 注册顺序；args 被剥到只剩 [payload, inner]
        │
        ▼  inner = args.pop()；args.push(next)
   cb₁(payload, next)              ← 最外层监听器【最先】执行
        │ 调 next()
        ▼
   cb₂(payload, next)              ← 下一层
        │ 调 next()
        ▼
   inner(payload)                  ← 内建行为（调用方提供的兜底）
        │ 返回值
        ▼
   返回值由内向外逐层返回；cb₁ 可以在返回前包装它
   ★ 任何一层【不调 next()】→ 剩下的 cbs 与 inner 全都不会执行（= 否决）
```

> **精确性说明**：`next` 不是"把 payload 换成新值传给下游"。它复用**同一个** `args` 数组重新调用下一个人，所以"改变下游看到的东西"必须靠**就地改共享对象**（§4.5 有源码与实测）。

### 2.3 大白话版：一次"通知"的五种叫法

**完全不用上面的术语**，先建立画面（来源：`docs/cordis-primer.zh.md` 第 19–29 行的模式表 + `vendor/cordis/src/events.ts` 第 183–243 行的实现；这里只做白话转述）。

1. 某段代码想说"有件事发生了"，于是按**事件名**喊一声。
2. 框架先找出"谁在听这件事"：一张按事件名分组的名单，**顺序就是当初登记的先后**。
3. 名单里的人可能有范围限制：只在特定范围内才被叫到（这就是"载体"的作用）。
4. 叫法有五种，区别只在**三件事**：要不要等对方把异步活干完、要不要收对方的返回值、谁能中途喊停。
5. **不留回执、不等**：挨个叫一遍就走，对方后面才完成的活不管，返回值丢掉（`emit`）。
6. **留回执、不等**：挨个叫，谁先给出"打住"的值就停（`bail`）。
7. **留回执、等**：一个个等对方干完再叫下一个，谁给出"打住"的值就停（`serial`）。
8. **一起叫、等全部**：同时叫所有人，等全部结束；最后如果有人失败，汇总成一次报错（`parallel`）。
9. **中间件式**：把"继续叫下一个人"做成一个可以调用的动作交给对方；对方调了才继续，不调**就地结束**——连"最后那个默认动作"也一起跳过（`waterfall`）。

## 3. 结论先行（12 条，全部带出处）

1. 五种模式 = `emit` / `waterfall` / `parallel` / `serial` / `bail`，它们是 Cordis 事件服务的**全部**分发入口：`export type DispatchMode = 'emit' | 'parallel' | 'serial' | 'bail' | 'waterfall'`（`vendor/cordis/src/events.ts` 第 32 行），实现集中在第 183–243 行。
2. 每句话版本（权威表在 `docs/cordis-primer.zh.md` 第 21–27 行）：
   - `emit`：不 await，按注册顺序，返回 void，返回值被丢掉。
   - `waterfall`：不 await，按注册顺序，倒数第一个参数是 `next`，返回值是**最外层监听器的返回值**。
   - `parallel`：await 全部，并行，返回 `Promise<void>`，只能最后以 `AggregateError` 失败。
   - `serial`：await，按顺序，遇到第一个 bail 值就停，返回那个值。
   - `bail`：同步版 serial，遇到第一个 bail 值就停。
3. **只有 `waterfall` 有 `next()`，也只有"不调 `next()`"这种短路方式**：不调用 `next()` 就返回，会让下游监听器**和内建行为**全部不执行（`vendor/cordis/src/events.ts` 第 227–229 行注释、第 234–243 行实现）。`serial`/`bail` 的提前停止看**返回值**，与 `next` 无关；`emit`/`parallel` 无法短路。
4. "bail 值"的判据不是布尔：`isBailed(value)` = `value !== null && value !== false && value !== undefined`（`vendor/cordis/src/events.ts` 第 13–15 行）。所以 `0`、`''`、`'x'` 都会停，`null`/`false`/`undefined` 都不会停（§6.2 实测 I 组）。
5. DSH 自己的 81 个事件里：**emit 59 / waterfall 17 / parallel 3 / serial 2 / bail 0**（§5 逐行重数；与 `3.2-事件全景.md` §9.2 记的 `emit 56` **不一致**，判定见 §5 的口径说明）。
6. **`emit` 不是安全的广播**：它用 `Array.map` 调用监听器，一个同步抛出会**饿死后续监听器**，返回的 Promise 被直接丢弃（可能变成未处理拒绝）。DSH 有三个包各自重写了"逐监听器容错"的 emit：agent（`packages/core/agent/src/dispatch.ts` 第 120–137 行）、session（`packages/core/session/src/index.ts` 第 398–416 行）、llm（`packages/llm/llm/src/index.ts` 第 354–365 行）。
7. `parallel` 的**返回值处理是"全跑完才报错"**：`Promise.allSettled` + `AggregateError`（`vendor/cordis/src/events.ts` 第 183–187 行）。监听器之间不能互相否决，失败是事后汇聚的。
8. 一个容易踩的诊断坑：`parallel` 向 `internal/dispatch` 上报的模式字符串是 **`'emit'`**，不是 `'parallel'`（`vendor/cordis/src/events.ts` 第 184 行 `this.dispatch('emit', args)`），§6.2 实测 H 组复现了这一点。
9. **能力事件与会话事件的分发方式不同**：能力事件（`fs/*`、`tools/*`、`llm/*`）以 `waterfall` 做拦截/决策、`emit` 做观察；会话事件（`session/*`）**只有 emit ×3 + parallel ×1，没有 waterfall/serial/bail**，且必须经 SessionStore 的单入口分发（`packages/core/session/src/index.ts` 第 43–82 行、第 1177–1207 行）。
10. **`waterfall` 的 `next()` 不接受实参**：`next('HACKED')` 会被忽略，下游看到的仍是原值（`vendor/cordis/src/events.ts` 第 237–240 行；§6.2 实测 G 组）。
11. **`@mode` 标签与签名互为镜像，且由生成器强制**：缺 `@mode` 报错；带尾部 `next` 却不是 `waterfall` 报错；标了 `waterfall` 却没有 `next` 也报错（`packages/typert/generator/src/cordis-catalog.ts` 第 200–211 行）。
12. **一处必须更正的旧说法**：上一轮记录说"本 checkout 不能 `import '@deepseek-ai/cordis'`，因为 `vendor/cordis/lib/` 下没有 `lib/index.js`"。实测：① `vendor/cordis/lib/index.js` **存在**（构建产物，60361 字节）；② 真正的原因是 `node_modules/@deepseek-ai/cordis` **没有安装**，所以裸包名在**纯 node** 下报 `ERR_MODULE_NOT_FOUND`；③ 但在 `node --import tsx/esm` 下**可以**成功——`tsconfig.base.json` 第 82–83 行把 `@deepseek-ai/cordis` → `vendor/cordis/src`、`@deepseek-ai/cosmokit` → `vendor/cosmokit/src` 做了路径映射（§6.4 有对照实测）。

**五种模式一张表**（判据与出处）

| 模式 | await？ | 顺序 | 谁来停 | 返回值处理 | 实现 |
|---|---|---|---|---|---|
| `emit` | 否 | 注册顺序 | **没人能停**（同步抛出会饿死后续） | 返回 `void`；监听器返回值**被丢弃**，返回的 Promise 也无人持有 | 第 194–196 行；声明第 53 行 |
| `waterfall` | 否（是否 await 由监听器自己决定） | 注册顺序，最外层先执行 | **不调 `next()` 就地返回** | 返回**最外层监听器的返回值**；中间层用 `await next()` 取下游结果再包装 | 第 234–243 行；声明第 86 行、注释第 76–85 行 |
| `parallel` | 是（`Promise.allSettled`） | 并行启动 | **没人能停** | 返回 `Promise<void>`；任一失败 → 全部结算后抛 `AggregateError` | 第 183–187 行；声明第 44 行 |
| `serial` | 是（逐个 await） | 注册顺序 | 第一个 `isBailed()` 为真的返回值 | 返回**首个 bail 值**，没有则 `undefined` | 第 204–209 行；声明第 63 行 |
| `bail` | 否（同步） | 注册顺序 | 同 serial | 返回**首个 bail 值** | 第 217–222 行；声明第 73 行 |

## 4. 机制：每个知识点旁边的源码（R11）

> 本节的每块源码都**真读过**（写作时逐行核对行号）。块号与 §8.2 末尾的「源码块清单」一一对应。

### 4.1 块 1：五种方法共用的前半段

`vendor/cordis/src/events.ts` 第 158–175 行

```ts
  /**
   * Resolve listeners for one dispatch and apply context filtering.
   *
   * @param type — the dispatch mode, reported on `internal/dispatch`.
   * @param args — the raw dispatch arguments; consumed up to the event name.
   * @returns the matching listener callbacks, bound to the dispatch `this`.
   */
  dispatch(type: string, args: any[]) {
    const thisArg = typeof args[0] === 'object' || typeof args[0] === 'function' ? args.shift() : null
    const name: string = args.shift()
    if (!name.startsWith('internal/')) {
      this.emit('internal/dispatch', type, name, args, thisArg)
    }
    const filter = thisArg?.[Context.filter]
    return (this._hooks[name] || [])
      .filter(hook => hook.global || !filter || filter.call(thisArg, hook.ctx))
      .map(hook => hook.callback.bind(thisArg))
  }
```

**做什么**：把"可能带载体的实参列表"解析成**一组已绑定 `this` 的回调**。它是 `emit` / `parallel` / `serial` / `bail` / `waterfall` 五个方法的公共第一步。

**依赖的变量从哪来**

- `args`：调用方 `emit(...args)` 等直接用 `...` 收进来的**同一个数组**。注意 `args.shift()` 是**就地消费**——两次 `shift` 之后，`args` 里只剩"给监听器的实参"。
- `this._hooks`：类字段，在第 132 行声明为 `_hooks: Record<keyof any, Hook[]> = {}`，就是 §2.1 那张"按事件名分组的监听器名单"。
- `Context.filter`：不是字符串，是 symbol，定义在 `vendor/cordis/src/context.ts` 第 45–46 行（`static readonly filter: unique symbol = symbols.filter`，注释原文 *"Symbol key for a context's listener filter, consulted on every event dispatch."*）。

**相邻的守卫**：`if (!name.startsWith('internal/'))` —— **内建事件自己不再上报**，否则 `internal/dispatch` 每次分发都再发一条 `internal/dispatch`，自我递归；`hook.global || !filter || filter.call(...)` —— 三个分支依次是"声明了 global 的监听器不受过滤""没有载体就没有过滤可言""有载体就按载体的规则裁决"。

**与哪个知识点相关**：结论 1（公共前半段）、结论 8（`parallel` 上报 `'emit'` 就发生在**调用方传进来的 `type`** 上，这个函数原样转发）。

**为什么这么写**：作者的两句 JSDoc 直接回答了参数含义——第 161 行 *"the dispatch mode, reported on `internal/dispatch`"*、第 162 行 *"the raw dispatch arguments; consumed up to the event name"*。**"consumed"就是说参数数组会被吃掉两层**，这也是"首个实参是对象/函数就当载体"这一约定能成立的前提。

### 4.2 块 2：`bail` 判据与五种模式的类型

`vendor/cordis/src/events.ts` 第 7–15 行与第 24–32 行

```ts
// （第 16–23 行：三个类型工具 Parameters / ReturnType / ThisType，
//   只服务于下面的类型声明，与本知识点无关，此处省略。）
/**
 * Return whether an event result should stop a bail-style dispatch.
 *
 * @param value — a listener's return value.
 * @returns `true` unless `value` is `null`, `false`, or `undefined`.
 */
export function isBailed(value: any) {
  return value !== null && value !== false && value !== undefined
}

/**
 * Event dispatch strategy used by the event service.
 *
 * `emit` runs synchronous listeners without awaiting them, `parallel` awaits
 * all listeners together, `serial` awaits them in order until one bails,
 * `bail` stops on the first synchronous bail value, and `waterfall` composes
 * listeners around a final `next` callback.
 */
export type DispatchMode = 'emit' | 'parallel' | 'serial' | 'bail' | 'waterfall'
```

**做什么**：`isBailed` 定义"什么算打住"；`DispatchMode` 把五种模式的**名字**固定成一个联合类型（于是 `dispatch(type, …)` 里那个字符串是被类型约束的）。

**依赖的变量从哪来**：`isBailed` 只吃一个监听器返回值，没有外部依赖；它是 `serial`（第 207 行）与 `bail`（第 220 行）**共用的唯一判据**。

**相邻的守卫**：这里没有 `if` 守卫——它本身就是守卫函数。真正的"守卫"在调用方：`if (isBailed(result)) return result`。

**与哪个知识点相关**：结论 3、结论 4。**判据不是布尔**：`0`、`''` 都算"打住"，`null`/`false`/`undefined` 都算"没意见"（实测 I 组）。

**为什么这么写**：作者只在 JSDoc 里写了结论（*"`true` unless `value` is `null`, `false`, or `undefined`"*），**没有写为什么选这三种做例外**。合理动机（**标注为推断**）：`serial` 的典型用法是"返回一个替代结果就接管"，而 `undefined`=没返回、`null`/`false`=调用方眼里的"空"，都被当成"不表态"；反过来 `0`/`''` 是可能合法出现的"真值结果"（例如长度 0 的列表），不能默默被当成不表态。

### 4.3 块 3：`parallel` 与 `emit`

`vendor/cordis/src/events.ts` 第 177–196 行

```ts
  /**
   * Run listeners concurrently and wait for all of them.
   *
   * @param args — optional `this`, the event name, then listener arguments.
   * @returns a promise resolving once every listener has settled.
   */
  async parallel(...args: any[]) {
    const results = await Promise.allSettled(this.dispatch('emit', args).map(async cb => cb(...args)))
    const errors = results.filter((result): result is PromiseRejectedResult => result.status === 'rejected')
    if (errors.length) throw new AggregateError(errors.map(error => error.reason))
  }

  /**
   * Run listeners synchronously without waiting for returned promises.
   *
   * @param args — optional `this`, the event name, then listener arguments.
   */
  emit(...args: any[]) {
    this.dispatch('emit', args).map(cb => cb(...args))
  }
```

**做什么**：两个"广播"入口。`parallel` = 全部启动 → `allSettled` 等全部结算 → 有失败才抛；`emit` = 同步挨个调用，不信返回值也不等 Promise。

**依赖的变量从哪来**：`args` 由调用方 `...` 传入（方法体内先交给 `dispatch`，被剥掉载体与事件名两层）；`this.dispatch` 就是块 1。`Promise.allSettled` / `PromiseRejectedResult` / `AggregateError` 都是 JS 内建。

**相邻的守卫**：`if (errors.length)` —— **只有真有人失败才构造 `AggregateError`**；`results.filter((result): result is PromiseRejectedResult => …)` 是类型谓词，作用是把 `status !== 'rejected'` 的成员在类型层面剔掉。

**与哪个知识点相关**：结论 7（`allSettled` + `AggregateError`，失败只能事后汇聚）、结论 6（`emit` 用 `.map`，同步抛出会中断整条 map）、结论 8（**第一行把 `'emit'` 当成 type 传给了 `dispatch`**，所以诊断事件里看到的是 `emit => x/parallel`）。

**为什么这么写**：JSDoc 第 180 行 *"Run listeners concurrently and wait for all of them."*、第 190 行 *"Run listeners synchronously without waiting for returned promises."*。`emit` 声明处（第 48 行）写得更直白：*"Dispatch an event synchronously, ignoring listener return values."* —— **返回值被忽略是设计，不是疏漏**；而 `.map` 而不是 `for` 的后果（同步抛出饿死后续）DSH 在 `packages/core/agent/src/dispatch.ts` 第 121–124 行用注释写成了明文理由（块 7）。

### 4.4 块 4：`serial` 与 `bail`

`vendor/cordis/src/events.ts` 第 198–222 行

```ts
  /**
   * Run listeners in order, awaiting each, until one returns a bail value.
   *
   * @param args — optional `this`, the event name, then listener arguments.
   * @returns the first bail value (see {@link isBailed}), if any.
   */
  async serial(...args: any[]) {
    for (const cb of this.dispatch('serial', args)) {
      const result = await cb(...args)
      if (isBailed(result)) return result
    }
  }

  /**
   * Run listeners synchronously until one returns a bail value.
   *
   * @param args — optional `this`, the event name, then listener arguments.
   * @returns the first bail value (see {@link isBailed}), if any.
   */
  bail(...args: any[]) {
    for (const cb of this.dispatch('bail', args)) {
      const result = cb(...args)
      if (isBailed(result)) return result
    }
  }
```

**做什么**：两个"逐个来、可以中途停"的入口。`serial` 每步 `await`；`bail` 同步。两者都**没有 `next`**。

**依赖的变量从哪来**：`isBailed` 来自块 2（同文件第 13–15 行）；`this.dispatch('serial'|'bail', args)` 来自块 1，各自上报的模式字符串是**自己的名字**（与 `parallel` 上报 `'emit'` 形成对照，实测 H 组）。

**相邻的守卫**：`if (isBailed(result)) return result` —— 这就是"停"的全部实现：**返回值一表态就 `return`，后面的 `for` 迭代不再发生**。

**与哪个知识点相关**：结论 2、结论 3（停止看返回值，不看 `next`）、结论 4。DSH 用 `serial` 做初始化的关键是"await 完才开始用"（附录 A Q3）。

**为什么这么写**：JSDoc 第 199 行 *"Run listeners in order, awaiting each, until one returns a bail value."*、第 212 行同步版同义。声明处第 61/71 行把返回值写成 *"the first bail value (non-null, non-false, non-undefined), if any."* —— 与 `isBailed` 的实现逐字对应。

### 4.5 块 5：`waterfall`（本课最容易误解的一段）

`vendor/cordis/src/events.ts` 第 224–243 行

```ts
  /**
   * Compose listeners around the final `next` callback.
   *
   * The last dispatch argument is treated as the innermost `next`. Listeners
   * run outermost-first; a listener that does not call `next()` vetoes the
   * rest of the chain, including the built-in behavior.
   *
   * @param args — optional `this`, the event name, listener arguments, then `next`.
   * @returns the outermost listener's return value.
   */
  waterfall(...args: any[]) {
    const cbs = this.dispatch('waterfall', args)
    const inner = args.pop()
    const next = () => {
      const cb = cbs.shift() ?? inner
      return cb(...args)
    }
    args.push(next)
    return next()
  }
```

**做什么**：把监听器串成一条由 `next` 手工驱动的链，最后一环是**调用方提供的 `inner`（内建行为）**。

**依赖的变量从哪来**

- `cbs`：块 1 的返回值——过滤+绑定后的监听器数组，**注册顺序**。
- `inner`：`args.pop()`，即**调用方传的最后一个实参**（见下面的真实调用点表）。**调用方必须提供它**，否则 `next` 链的末端是 `undefined`，一调就抛。
- `next`：闭包。它读的是**同一个 `args` 数组**（`args.push(next)` 把 `next` 放在共享数组末尾），所以每条监听器收到的 `next` 是同一个动作。

**相邻的守卫**：这里没有 `if`。**"不调 `next()`"本身就是守卫**——`cbs` 里剩下的回调与 `inner` 唯一的进入方式就是当前监听器调用 `next()`。作者在 JSDoc 第 227–229 行写死了这条：*"a listener that does not call `next()` vetoes the rest of the chain, including the built-in behavior."*

**与哪个知识点相关**：结论 2、结论 3、结论 10（`next` 忽略实参：闭包里是 `cb(...args)`，`args` 是共享的，你传什么都进不去）。

**为什么这么写**：JSDoc 首句 *"Compose listeners around the final `next` callback."* 说明了它是**环绕式中间件**；`@returns` 一句 *"the outermost listener's return value"* 解释了为什么最外层能拿到内层结果再包装。

**内建行为从哪来（五个真实调用点，逐个打开确认过）**

### 4.6 块 6：注册入口 `on()` 自己也是 `bail` 的用户

### 4.7 块 7–9：DSH 对 `emit` 的三次"加固改写"

#### 块 7：`agent` —— 最完整的一遍（连 `serial`/`waterfall` 一起封装）

`packages/core/agent/src/dispatch.ts` 第 107–137 行

```ts

//   此处只保留函数头之后的实现。）
export function agentEvents(ctx: Context, agent: Agent, carrier: Scoped<Agent> = agentCarrier(agent)): AgentEventDispatch {
  // The ordinary dispatch methods forward through Cordis' variadic mixins. The
  // fused (carrier, name, payload, ...rest) tuple is provably a valid argument
  // list for the matching thisArg overload, but TypeScript cannot relate the
  // generic Tail<K> spread back to that overload's conditional parameter
  // tuple — hence one contained, shape-preserving cast per method.
  const fused = <K extends AgentSubjectEvent>(payload: PayloadRest<K>): PayloadOf<K> =>
    // The dispatcher owns the subject injection; callers pass PayloadRest, so
    // the fused record is exactly the declared payload. The spread comes
    // first, so a structurally acceptable payload that happens to carry an
    // `agent` field can never override the injected subject.
    ({ ...payload, agent } as PayloadOf<K>)
  return {
    emit(name, payload) {
      // Cordis emit invokes callbacks through Array.map: one synchronous throw
      // starves later listeners, and returned promises are discarded. Agent
      // notifications are non-vetoing, so resolve the same filtered callback
      // set ourselves and contain both failure modes independently.
      const args: unknown[] = [carrier, name, fused(payload)]
      const callbacks = ctx.events.dispatch('emit', args)
      for (const callback of callbacks) {
        try {
          const returned: unknown = callback(...args)
          void Promise.resolve(returned).catch((error: unknown) => {
            ctx.logger.warn(`agent event "${name}" listener rejected: ${String(error)}`)
          })
        } catch (error: unknown) {
          ctx.logger.warn(`agent event "${name}" listener threw: ${String(error)}`)
        }
      }
    },
```

### 4.8 块 10：`emit` 的"故意不容错"对照面 —— `session/created`

`packages/core/session/src/index.ts` 第 1136–1164 行

```ts

//   此处从函数头之后开始。）
  announce(session: Session): void {
    const entry = this.liveEntryFor(session)
    if (entry.announced || entry.announcing) {
      throw new Error(`session "${entry.id}" was already announced`)
    }
    // Mark before emit: Cordis emit may deliver to earlier listeners and then
    // throw. Rollback must still pair that partial creation with disposal, and
    // a listener cannot recursively create a second lifecycle edge.
    entry.announced = true
    const callbackArgs: unknown[] = [session]
    entry.announcing = true
    try {
      const callbacks = collectSessionCallbacks(this.ctx, [entry.carrier, 'session/created', session])
      for (const callback of callbacks) {
        // Synchronous throws intentionally propagate and veto publication; the
        // yielded detach then emits the paired disposal edge. An async function
        // is nevertheless assignable to a void listener, so observe its returned
        // promise: rejection is too late to roll back and must be logged instead
        // of becoming unhandled.
        const returned: unknown = callback(...callbackArgs)
        void Promise.resolve(returned).catch((error: unknown) => {
          this.ctx.logger.warn(`session "${entry.id}": session/created listener rejected: ${String(error)}`)
        })
      }
    } finally {
      entry.announcing = false
      if (entry.detachRequested && !entry.appending) entry.detach()
    }
  }
```

```ts
   * rather than dispatch a raw `ctx.parallel('session/flush', …)` — one owner
   * and one spelling.
   * @param session - the session whose buffered events must reach durable storage.
   * @returns whether at least one durability listener participated, after every
   *   listener has settled successfully.
   * @throws the first registered listener failure after every listener settles.
   */
  async flush(session: Session): Promise<boolean> {
    const { carrier } = this.liveEntryFor(session)
    const callbackArgs: unknown[] = [session]
    const callbacks = collectSessionCallbacks(this.ctx, [carrier, 'session/flush', session])
    const results = await Promise.allSettled(callbacks.map((callback) => {
      try {
        return callback(...callbackArgs)
      } catch (error: unknown) {
        // Preserve the listener's exact rejection value; flush is a caller-owned
        // failure boundary, and Cordis listeners may throw arbitrary values.
        // oxlint-disable-next-line typescript/prefer-promise-reject-errors
        return Promise.reject(error)
      }
    }))
    const failure = results.find((result): result is PromiseRejectedResult => result.status === 'rejected')
    if (failure !== undefined) throw failure.reason
    return callbacks.length > 0
  }
```

**做什么**：`session/flush` 是 `parallel` 事件，但**不让调用方直接 `ctx.parallel`**：统一走这个 `flush()`。它自己做 `allSettled`、自己挑第一个失败抛出，并返回"是否至少有监听器参与"。

**依赖的变量从哪来**：`carrier` 来自 `liveEntryFor(session)` 解构——JSDoc 明写"载体在 `enter` 时捕获"，所以调用方**提供不了**载体，这才有"单入口"的必要；`collectSessionCallbacks` 来自块 8。

**相邻的守卫**：`try { return callback(...) } catch (error) { return Promise.reject(error) }` —— **同步抛出被转成 rejected promise**，于是它照样进入 `allSettled`、**不会饿死后面的监听器**（这正是 `parallel` 与 `emit` 的差别在 DSH 侧的补救）；`if (failure !== undefined) throw failure.reason` —— 只抛第一个失败，但**在所有监听器结算之后**。

**与哪个知识点相关**：结论 7（全跑完才报错）、结论 9（会话事件的单入口分发与失败边界）。可执行证据在 `packages/core/session/tests/scoped.spec.ts`：第 122–127 行 *"propagates a rejecting flush listener (the caller owns the failure policy)"*、第 129–138 行 *"does not let a synchronous flush failure starve later listeners"*、第 140–157 行 *"waits for slower flush listeners before reporting another listener failure"*。

**为什么这么写**：JSDoc 的原话给出两条理由——*"THE flush entry point: the store owns the carrier, so callers … must come through here rather than dispatch a raw `ctx.parallel('session/flush', …)` — one owner and one spelling."*，以及 *"@throws the first registered listener failure after every listener settles."* 另有一个真实的调用方按 `AggregateError` 收尾的例子（`ctx.parallel` 直接使用时）：`packages/workspace/workspace/src/index.ts` 第 480–491 行，注释原文 *"ctx.parallel settles every listener and rejects with one AggregateError."*

### 4.10 块 12：`@mode` 标签与签名为什么必须对得上

## 附录 A 关键问题与答案

### Q1 `emit` / `waterfall` / `parallel` / `serial` / `bail` 各自的语义与返回值处理方式？

**答：语义与返回值处理见 §3 末尾那张表**（实现行号全部在 `vendor/cordis/src/events.ts`）。要点重述：

- `emit` 不 await、不返回、返回值与 Promise 全丢弃；**没人能停**（同步抛出会饿死后续）。
- `waterfall` 把 `next` 交给监听器，**不调 `next()` 即否决**（连内建行为一起跳过）；返回**最外层监听器的返回值**，中间层用 `await next()` 取下游结果再包装。
- `parallel` 并行启动、`allSettled` 等全部结算，任一失败则抛 `AggregateError`；**没人能停**。
- `serial` 逐个 await，遇到第一个 `isBailed()` 为真的返回值就返回它。
- `bail` 是 `serial` 的同步版，判据相同。

补充两条容易漏的返回值规则：

1. `waterfall` 的 `next()` **不接受实参**——它用共享的 `args` 数组重新调用下游（第 237–240 行），所以"传值给下游"必须改成"就地改共享对象"（同结论见 `.agents/notes/implemented/architecture/2026-07-07-tool-call-timeout-policy.zh.md` 第 57 行；实测 G 组）。
2. `serial`/`bail` 的"停"用的是同一个判据 `isBailed`（第 13–15 行），与 `async`/同步无关；`parallel` 没有这个判据，只有 `AggregateError`。

### Q2 哪个不调 `next()` 会短路？为什么？

**答：只有 `waterfall`。**

原因是实现形态：`waterfall` 把每条监听器串成一条由 `next` 手工驱动的链——

```ts
const next = () => { const cb = cbs.shift() ?? inner; return cb(...args) }
```

（`vendor/cordis/src/events.ts` 第 237–240 行）

- 下游监听器（以及最后那个**内建行为** `inner`）唯一的进入方式，是当前监听器调用 `next()`。不调用，`cbs` 里剩余的回调与 `inner` 都不会被执行。
- 官方注释把它写成 *"a listener that does not call next() vetoes the rest of the chain, including the built-in behavior"*（第 227–229 行）。
- 语义上这是**有意的**：`docs/cordis-primer.zh.md` 第 39 行"对于单决策事件，短路是设计意图。策略监听器在拥有决策权时可以不调用 `next()` 直接返回，而仅做标注或观察的监听器则必须委托"。
- 注意：**"不调 `next()`"的短路与返回值无关**——返回 `undefined` 也照样短路（实测 F 组返回 `'vetoed'`，但只返回 `undefined` 效果相同，因为内建根本没跑）。这与 `serial`/`bail`"必须返回非空值才停"正好相反。

对照：`emit`/`parallel` 没有 `next` 参数，结构上不存在这种否决；`serial` 没有 `next`（`docs/architecture.zh.md` 第 113 行）。

### Q4 能力事件与会话事件在分发方式上有什么差别？

> ⚠️ **第一次读请跳过本题**：它需要先有"事件域"的概念（`1.1` §8 只点了名，`3.2` 才展开）。

**答：能力事件以 `waterfall` 承担"拦截/决策"，会话事件只有 `emit`/`parallel` 承担"广播/等待"，且会话事件被强制走 SessionStore 的单入口分发。**

| 维度 | 能力事件（`fs/*`、`tools/*`、`llm/*`） | 会话事件（`session/*`） |
|---|---|---|
| 定位 | "无需导入循环即可向某个 seam 附加策略和适配器"（`docs/architecture.zh.md` 第 80 行） | "追加到日志并通过 `session/event` 广播的持久事实"（同文件第 78 行） |
| 模式集合 | 决策型全用 waterfall：`fs/write-intent`、`fs/edit-intent`、`tools/pre-execute`、`tools/execute`、`tools/post-execute`、`tools/ptc-dispatch-log`、`llm/stream`；观察型用 emit：`fs/observed`、`tools/result`、`tools/change`、`llm/adapters-updated`（声明见 `packages/fs/fs/src/index.ts` 第 57–77 行、`packages/core/tools/src/index.ts` 第 151–208 行、`packages/llm/llm/src/types.ts` 第 21–23 行与 `packages/llm/llm/src/index.ts` 第 73–75 行） | **只有 emit ×3 + parallel ×1，没有 waterfall / serial / bail**：`session/created`（emit）、`session/disposed`（emit）、`session/event`（emit）、`session/flush`（parallel）（`packages/core/session/src/index.ts` 第 52/61/72/80 行，签名 54/63/74/82 行） |
| 能否改变结果 | 能。不调 `next()` 即否决，或返回替代决策（如工具拒绝、超时替换、fs 写入意图）（`packages/core/tools/src/index.ts` 第 144–148、155–159 行；`packages/fs/fs/src/index.ts` 第 51–54 行） | **不能改写事实**。唯一的否决是 `session/created` 的**同步抛出**，而且那是 emit 的同步抛出语义，不是 waterfall：*"Synchronous throws intentionally propagate and veto publication"*（同文件第 1150–1152 行）；`session/disposed`、`session/event` 的观察者失败一律被容错为 `logger.warn`（第 398–416 行） |
| 分发入口 | 由拥有 seam 的包直接调 `ctx.waterfall(...)` / `ctx.emit(...)`（如 `packages/core/tools/src/index.ts` 第 1505–1506、1703–1704、835 行；`packages/fs/tool-fs/src/read.ts` 第 163 行） | **必须经 SessionStore**：`collectSessionCallbacks()` → `ctx.events.dispatch('emit', args)` 取一次快照（第 393–396 行），再 `invokeContainedSessionObservers`（第 398–416 行）或 `Promise.allSettled`（第 1194–1203 行）跑；`flush` 的文档明写调用方"must come through here rather than dispatch a raw `ctx.parallel('session/flush', …)` — one owner and one spelling"（第 1177–1184 行） |
| 失败语义 | waterfall：内建行为被跳过 / 返回替代值；emit 观察者：失败被容错（三个包各自重写，见 §4.7） | `session/flush` 是"调用方拥有的失败边界"：全部结算后抛第一个监听器失败（第 1204–1206 行），测试见 `packages/core/session/tests/scoped.spec.ts` 第 122–138 行 |
| 域判据（同源） | "实时拦截或瞬态/活对象信号"用 Cordis 事件（`.agents/notes/implemented/architecture/2026-06-30-event-domain-semantics.zh.md` 第 27 行） | 持久事实是 `SessionEvent`；而 `session/*` 这四个是**总线事件**，本身不进日志（同文件第 23 行） |

**一句话记法**：**能力事件用 waterfall 争"这次怎么办"，会话事件用 emit/parallel 报"已经发生了什么"，并且会话事件的广播权归 SessionStore 一家。**
