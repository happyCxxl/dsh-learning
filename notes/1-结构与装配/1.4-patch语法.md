## 0. 怎么读这一课（阅读许可）

### 0.1 这一课是什么、不是什么

**是**：这两个文件的**方言**——顶层形状、允许的键、每种操作的确切语义、`!!js` 能写在哪、什么时候被求值。
**不是**：这些层是谁、按什么顺序叠上去的（那是 `1.2`）；`id` 在多层之间怎么覆盖最稳妥（那是 `1.3`）；`group` / `isolate` / preset 的运行时语义（那是第二、三编）。

### 0.2 现在只要记住这 4 件事

1. **两个文件是同一门方言**：顶层必须是数组，数组元素是"条目"或"patch 条目"，两者共用同一套元数据键。
2. **`cordis.yml`（根）的内容是写死的空数组 `[]`**，每次启动都被重写回去——**手改它没有意义**，要改就改 `cordis.patch.yml`。
3. **一条 patch 只有两种行为**：`insert`（加行）与按 `id` 覆盖（**逐键浅赋值**，`config` 是整体替换，没有深合并）。
4. **`!!js` 只能写在两处**：`config` 内的任意深度、以及 `disabled` 的**自身节点**；dump 系列命令从不求值它。

### 0.3 明确授权：这些现在**不用管**

本课会出现 `tree carrier`、`interpolate`、`internal/config` 瀑布、`isolate` / `intercept`、realm、preset、schema 投影、volatile 等词。**它们都是我在别处学的，现在不需要你懂。**

判断标准只有一条：**只要你能说出"这条语句属于上面 4 件事里的哪一件"，就够了。**
其余内容在附录 C 里留着备查，**第一次读请跳过它**。

### 0.4 本课复用的词汇

`profile` / `bundle` / `patch` / 条目 entry / 层 layer（`1.1`），`override` / `insert` / 层边界（`1.2`）——本课不重复定义。
`patch` 是源码里的正名（中文文档里偶见"补丁"，指的是同一个东西）；下文只用 `patch`。

## 1. 最小词汇表（本课新增 6 个词）

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **方言（entry-list YAML dialect）** | 这两个文件共用的那套写法：顶层一个数组，元素是行 | `entryListSchema`（= `yaml.JSON_SCHEMA.extend(JsExpr)`） |
| **表达式节点** | 一行"现在不算、等挂载时再算"的值，在文件里是一个不存在的 YAML 标签 | YAML 写 `!!js <表达式>`；读进来后是 `{ __jsExpr: '<表达式>' }` |
| **tree carrier** | 一种特殊条目：它的 `config` 里装的是**别人的行清单**，而不是给自己的配置 | 插件上写 `static readonly [EntryGroup.key] = true` |
| **锚点（anchor）** | 一个真实存在、用来定位"相对路径与输出来源"的文件 | 根 include 的 `path`；dump 也锚同一个文件 |
| **schema dump** | 不启动、不求值，只把"这颗树的结构"打印成 JSON Schema | `--dump-config-schema` |
| **探针（probe）** | 为了观察某个语义而临时写的一份最小 patch 文件，用 `--patch` 传进去 | `<repo>\.learning\notes\1-结构与装配\1.4-probes\*.patch.yml` |

> ⚠️ 这 6 个词里，`tree carrier` 与 `表达式节点` 的**运行机制**属于第二编（插件内核）；本课只用到上表这个程度——它们是什么形状、在哪一行被用到，就够了。

## 2. 先建立画面

### 2.1 静态结构：两个文件、一门方言

```
$DSH_HOME\profiles\<名字>\
├─ cordis.yml          根文件：内容写死为 []（空数组）        ← 锚点，永远不该手改
└─ cordis.patch.yml    用户 patch 层：顶层数组，元素是 patch 条目
        │
        │  同一门方言（entryListSchema）
        ▼
   顶层数组的元素只有两种
   ├─ 条目（entry）      { id?, name, config?, group?, disabled?, … }
   │                    ↑ 只能出现在根文件里，或 insert: 的数组里
   └─ patch 条目         { id?, insert?, config?, … }        ← 与条目共用元数据键
                        ↑ 出现在 patch 层文件里
```

> 精确性说明：**根文件也允许出现条目**（它就是一个条目列表），只是 DSH 每次启动都会把它重写回 `[]`，所以实际内容永远是空的。真正"装内容"的地方是各层的 `insert`。

### 2.2 动态过程：从文件到"运行中的条目列表"

顺序取自 `vendor\include\src\index.ts` 第 245–263 行的 `Service.init`（源码块见 §4.5）：

```
① yaml.load(文件内容, { schema: entryListSchema })     ← 用方言解析
        │
② 断言顶层是数组，否则当场抛 TypeError                  ← 只认数组
        │
③ applyEntryPatches(读到的数组, 所有层的 patch 扁平列表)  ← 唯一的 patch 算法
        │   中途：按 id 建索引 → 逐条 patch → insert 的行也登记进索引
        ▼
④ root.update(结果)                                     ← 到这一步才真正挂载插件
```

**要点**：patch **不是**逐层各跑一遍算法、也不是把文件合并成一份新文件；而是把各层的 patch 条目**压成一份扁平列表**，对着"根数组"跑**一次**算法（`packages\boot\app-boot\src\index.ts` 第 401–405 行的文档注释原文：*apply every layer's patches as ONE flattened list through the include's own patch algorithm*）。

### 2.3 大白话版：一份清单是怎么被改出来的

**完全不用上面的术语**（来源：`vendor\include\src\index.ts` 第 57–127 行 `applyEntryPatches` 与第 245–263 行 `Service.init` 的执行顺序，白话转述；细节见 §4）：

1. 启动时，程序先去找一个"清单文件"（根文件）。
2. 它把文件读成一串"行"。
3. 如果文件里不是"一串行"这种形状，它当场报错停下。
4. 然后它拿出一叠"改动说明"，一份一份按顺序看。
5. 每条说明要么是"在某处加几行"，要么是"把某一行里的某个字段换掉"。
6. 加行时，如果说明写了"加到哪一行里面"，它会先确认那一行**存在**、并且是个**能装行的容器**；不满足就只发一句警告，跳过这一条。
7. 换字段时，它按名字找那一行；找不到也只发警告、跳过，**不中断**。
8. 全部看完，它把结果交给下一步去真正挂载。
9. 整个过程里，那些写着"运行时再算"的值**一个字都没被算**——只是被原样搬过去。

## 4. 机制与源码对照（13 块）

> 每块都标了 `文件路径 第 A–B 行`；省略处一定写明省了哪些行、为什么省。路径用仓库内的相对路径，以 `<repo>` 为根。

### 4.1 方言从哪来：`!!js` 标签与 `entryListSchema`

**`vendor\include\src\index.ts` 第 9–23 行**

```ts
const JsExpr = new yaml.Type('tag:yaml.org,2002:js', {
  kind: 'scalar',
  resolve: (data) => typeof data === 'string',
  construct: (data) => ({ __jsExpr: data }),
  predicate: isJsExpr,
  represent: (data) => data['__jsExpr'],
})

/**
 * The entry-list YAML dialect: `!!js` scalars round-trip as expression nodes
 * the Loader evaluates at entry activation. Exported so config tooling
 * (`dsh --dump-config`) parses and prints exactly the dialect this include
 * mounts.
 */
export const entryListSchema = yaml.JSON_SCHEMA.extend(JsExpr)
```

按块讲解：

- **做什么**：`!!js` **不是 YAML 标准标签**，是这里注册的一个自定义 tag（`tag:yaml.org,2002:js`，kind 为 `scalar`）。`construct` 把标量文本包成 `{ __jsExpr: data }`；`represent` 把它还原回 `!!js` 标量。
- **与哪个知识点相关**：结论 1、6、7。这就是"两个文件是同一门方言"的**实现**：读进来是表达式节点，写回去还是 `!!js`。
- **为什么这么写**：这段 JSDoc 原文说得很直白——把它**导出**，是为了让配置工具（`dsh --dump-config`）"解析和打印的正是这个 include 挂载的那门方言"，于是 **dump 永不与真实启动漂移**。
- **用到它的几处**：include 自己 `yaml.load` 时用它（同文件第 218 行）；app-boot 解析 patch 文件（`packages\boot\app-boot\src\index.ts` 第 376 行）与打印 dump（同文件第 445、507 行）也用它。

- **与哪个知识点相关**：结论 2。所谓"根文件是空的"不是约定，是**代码写死的**。

### 4.3 根文件：为什么"不要编辑它"（三条互相独立的理由）

**`apps\cli\src\profile-boot.ts` 第 152–173 行**（省略第 162–166 行：`userLayer` / `fromDefaultProfile` 两个参数说明，与本知识点无关）

```ts
/**
 * Load a resolved profile for `name` and (re)write the empty root config. The
 * root is always rewritten: the whole composition is patch layers, and the
 * vendored Loader's tree write-back (a plugin self-disposing persists the
 * current tree) can bake composed rows into this file — which would duplicate
 * every bundle insert on the next boot. The file exists on disk only because
 * the Loader needs a real include root to anchor `baseUrl` at the profile
 * directory (the config dump anchors on the same file, so both compose over
 * the identical base).
 * @param name - the profile name.
 * …（第 162–166 行：`userLayer` / `fromDefaultProfile` / `@returns` / `@throws`，与本知识点无关，此处省略）
 */
export function prepareProfile(name: string, userLayer = true, fromDefaultProfile?: string): Profile {
  if (fromDefaultProfile !== undefined) initializeProfileFromDefault(name, fromDefaultProfile)
  const profile = loadProfile(NAME, name, INSTALL_ANCHOR, undefined, { userLayer })
  reportSkippedBundles(NAME, profile)
  writeFileSync(join(profile.dir, PROFILE_ROOT_FILENAME), PROFILE_ROOT_CONFIG)
  return profile
}
```

按块讲解：

- **做什么**：`prepareProfile` 在 `loadProfile` 之后**无条件**调用 `writeFileSync`，把根文件覆盖成常量。`--dump-config` 也走这个函数（`apps\cli\src\dump-config.ts` 第 38 行）；桌面端走 `composeProfile` 的同名写入（`apps\cli\src\profile-boot.ts` 第 204 行）。
- **与哪个知识点相关**：结论 2。**第一条理由：手改根文件在下次启动就被抹掉。**
- **为什么这么写（作者的原始理由在 JSDoc 里）**：**第二条理由——不重写会更糟**。Loader 有"写回"行为：插件自我 dispose 时，它把**当前**树持久化。链路是可追的：`Include.write()` 写的是 `this.root.data`（`vendor\include\src\index.ts` 第 336–340 行），而 `root.data` 已经被 `EntryGroup.update` 换成了 **patch 之后**的数组（`vendor\loader\src\config\group.ts` 第 48–50 行）；触发点例如"fiber 被 loader 行为 dispose → `options.disabled = true` → `tree.write()`"（`vendor\loader\src\index.ts` 第 158–166 行）。落盘由 `Include._writeFile` 完成（`vendor\include\src\index.ts` 第 289–308 行），只有在 `checkAccess` 判定文件只读时才抛 `cannot overwrite readonly config`（同文件第 204–211、290–292 行）。如果把这些"已经组合好的行"烤进根文件，**下次启动就会重复每一层的 insert**。
- **第三条理由——它是锚点**：JSDoc 后半句说明这个文件"存在"的意义是给 Loader 一个真实的 include 根，用来锚 `baseUrl`；`--dump-config` 锚的是同一个文件（`apps\cli\src\dump-config.ts` 第 40–41 行），所以 dump 与真实启动对着**同一份起点**组合。因此这个文件**必须存在、且必须是数组**：boot 传给 Include 的配置里**没有** `initial`（`packages\boot\app-boot\src\index.ts` 第 571–574 行只给 `path` 与 `patches`），文件缺失不会被自动补出来，而是直接报 `config file not found`（`vendor\include\src\index.ts` 第 252–258 行）。

### 4.4 读 patch 文件：三道校验，全部 fail loud

**`packages\boot\app-boot\src\index.ts` 第 371–389 行**

```ts
function parsePatchList(
  binName: string, file: string, content: string, label: string,
): PatchOptions[] {
  let parsed: unknown
  try {
    parsed = yaml.load(content, { schema: userPatchesSchema })
  } catch (error) {
    throw new Error(`${binName}: failed to parse ${label} ${file}: ${String(error)}`)
  }
  if (!Array.isArray(parsed)) {
    throw new Error(`${binName}: ${label} ${file} must be a top-level YAML array of loader patch entries`)
  }
  parsed.forEach((entry, index) => {
    if (typeof entry !== 'object' || entry === null || Array.isArray(entry)) {
      throw new Error(`${binName}: ${label} entry ${index + 1} in ${file} must be a mapping (a loader patch entry)`)
    }
  })
  return anchorInsertedPluginNames(parsed as PatchOptions[], file)
}
```

按块讲解：

- **做什么**：patch 文件的**唯一**解析入口（bundle 的 `cordis.patch.yml`、profile 的、`--patch` 的都走它）。三道门：YAML 必须能解析 → 顶层必须是数组 → 每个元素必须是 mapping（不是标量、不是数组）。
- **变量从哪来**：`userPatchesSchema` 来自同文件第 265 行（`const userPatchesSchema = entryListSchema`），第 260–264 行的注释说明**特意从 include 导入**，好让"patch 解析与 dump 打印永不漂移"；`label` 只是报错时用哪个词称呼这份列表（`patches` / `overlay`）。
- **与哪个知识点相关**：结论 1；以及 `1.2` 里"缺目标只告警、文件本身坏了才抛错"的分界——**文件级错误一律抛，单条 patch 打不到目标只告警**（同文件第 358–364 行的 JSDoc：*a single patch whose target row is absent stays a per-entry Loader warning, so one overlay shared across surfaces does not have to match every tree*）。
- **为什么这么写**：还能看到两个调用者的差别——`loadOptionalPatches`（第 305–325 行）把"文件不存在（ENOENT）"解释成"**没有这一层**"，其余读失败仍抛；`loadOverlayPatches`（第 327–344 行）则**文件缺失也抛**，因为调用者点名了这个文件。

### 4.5 唯一的 patch 算法：入口、克隆、索引、拆键

**`vendor\include\src\index.ts` 第 57–77 行**

```ts
export function applyEntryPatches(
  data: EntryOptions[],
  patches: PatchOptions[] | undefined,
  warn: (message: string, ...args: any[]) => void,
): EntryOptions[] {
  if (!patches?.length) return [...data]
  data = structuredClone(data)

  const entryMap = new Map<string, EntryOptions>()
  const buildMap = (entries: EntryOptions[]) => {
    for (const entry of entries) {
      if (entry.id) entryMap.set(entry.id, entry)
      if (entry.group && Array.isArray(entry.config)) {
        buildMap(entry.config)
      }
    }
  }
  buildMap(data)

  for (const patch of patches) {
    const { id, insert, name, ...overrides } = patch
```

按块讲解：

- **做什么**：这是**全部 patch 语义的所在地**。同一份函数被多处调用：include 挂载时（同文件第 240 行）、离线 `--dump-config`（`packages\boot\app-boot\src\index.ts` 第 465 行）、以及"先算一遍树来判定遥测开关"（`packages\boot\app-boot\src\profile.ts` 第 808–815 行的 `composeEntries`，被 `profile-context.ts` 第 72 行调用）。所以**dump 与真实启动用的是同一段代码**。
- **输入不可变**：`if (!patches?.length) return [...data]`（无 patch 时返回浅拷贝）与 `data = structuredClone(data)`（有 patch 时深拷贝）。JSDoc（第 43–56 行）给的原始理由：*patching shared entry objects would bake earlier patch values into the cached parse, so repeated application (config hot-reloads) could never revert a removed or changed patch*。
- **建索引**：`entryMap` 登记所有**带 `id`** 的条目；遇到 `entry.group && Array.isArray(entry.config)` 时**递归登记其子条目**。→ patch 既能定位顶层条目，也能定位 `group` 的子条目。
- **拆键**：`const { id, insert, name, ...overrides } = patch` —— `name` 与 `insert` 被**解构出去**，所以 `name` **永远不会被写到目标上**（它只会用于身份校验，见 §4.7）。
- **变量从哪来**：`data` 是"读到的根数组"（§2.2 第 ①–③ 步之间）；`patches` 是各层 patch 压成的扁平列表；`warn` 是调用者给的告警出口（include 挂载时接 Loader logger，dump 时接 stderr）。

### 4.6 `insert` 分支：加行，以及"新加的行马上可寻址"

**`vendor\include\src\index.ts` 第 79–102 行**

```ts

      if (id) {
        const target = entryMap.get(id)
        if (!target) {
          warn('patch insert: entry %C not found', id)
          continue
        }
        if (!target.group) {
          warn('patch insert: entry %C is not a group', id)
          continue
        }
        if (!Array.isArray(target.config)) target.config = []
        target.config.push(...insert)
      } else {
        data.push(...insert)
      }
      // Index what this patch added so a LATER patch in the same list can
      // target it. Patch lists compose one layer per source (each bundle
      // layer, then the user's, then `--patch` overlays), and a layer must be
      // able to configure or disable a row an earlier layer inserted; without
      // this, inserted rows were silently unpatchable.
      buildMap(insert)
      continue
    }
```

按块讲解：

- **做什么（两种形态）**：**不带 `id`** → `data.push(...insert)`，追加到**顶层末尾**（bundle 就是这么把自己那一堆条目推进空根的）；**带 `id`** → 目标必须存在（否则 `patch insert: entry %C not found`）且必须是 group（否则 `patch insert: entry %C is not a group`），然后 `target.config.push(...insert)`。`target.config` 不是数组时先补 `[]`。
- **两条守卫**：两个 `if (!…) { warn(…); continue }` —— **只告警、只跳过这一条**，不中断启动。这正是 `1.2` 里"`patch: entry ... not found` 只是 warning"的落点。
- **与哪个知识点相关**：结论 4；以及 §4.12 的"`group` 决定能不能作为落点"（判据是行上的 `group` 字段，**不是包名**）。
- **为什么这么写（作者原文就在块内）**：`buildMap(insert)` 前的三段注释说明——patch 列表是"一个来源一层"，**后一层必须能改到前一层刚插入的行**；不这么做，"inserted rows were silently unpatchable"。
- **分支末尾的 `continue` 很关键**：`insert` 分支一进去就 `continue`，所以**同一条 patch 上除 `id` / `insert` / `name` 外的键会被忽略**（想"插入并顺便覆盖"是做不到的）。

### 4.8 tree carrier：为什么 `group` / `include` 的 `config` 不求值

**`vendor\loader\src\index.ts` 第 104–121 行**

```ts
    ctx.on('internal/config', function (this: Fiber, _config, next) {
      const config = next()
      if (!this.entry || this.parent.fiber?.entry === this.entry) return config
      // Tree carriers (Group, Include) keep their configs literal: their
      // entry and patch lists hold other rows' configs, whose `!!js`
      // expressions belong to those rows' own fibers.
      const plugin = this.runtime?.callback as Record<PropertyKey, unknown> | undefined
      if (plugin?.[EntryGroup.key]) return config
      return interpolate(this.ctx, config)
    }, { global: true })

    ctx.on('internal/update', function (config, noSave, next) {
      if (!this.entry || noSave || this.parent.fiber?.entry === this.entry) return next()
      const unparse = this.runtime?.Config?.['simplify']
      this.entry.options.config = unparse ? unparse.call(this.runtime!.Config, config) : config
      this.entry.parent.tree.write()
      return next()
    }, { global: true, prepend: true })
```

按块讲解：

- **做什么（第一个钩子）**：`internal/config` 是"配置在挂载前最后一道加工"的瀑布。普通条目走到最后一行 `interpolate(this.ctx, config)` —— **在这里递归求值 `!!js`**。而如果插件自己带 `EntryGroup.key` 标记（即 tree carrier：`Group`、`Include`），就 `return config` 原样返回，**一个字都不求值**。

- **第二个钩子（`internal/update`）**：把"插件实例上的新配置"写回 `entry.options.config` 并触发 `tree.write()` —— 这是 §4.3 那条"Loader 会写回、所以根文件必须被重写"链条上的第一环（`tree.write()` → `Include.write()` → 落盘）。
- **标记在哪声明**：`vendor\include\src\index.ts` 第 159–168 行（`Include`）与 `vendor\loader\src\config\group.ts` 第 77 行（`Group`）都写着 `static readonly [EntryGroup.key] = true`；`EntryGroup.key` 的符号定义在 `group.ts` 第 7 行。

### 4.9 `!!js` 的实现：`evaluate` 与 `interpolate`

**`vendor\loader\src\config\utils.ts` 第 3–22 行**

```ts
// eslint-disable-next-line no-new-func
/** Evaluate a JavaScript expression against a loader context scope. */
export const evaluate = new Function('ctx', 'expr', `
  with (ctx) {
    return eval(expr)
  }
`) as ((ctx: object, expr: string) => any)

/** Recursively replace YAML `!!js` expression nodes with evaluated values. */
export function interpolate(ctx: object, value: any) {
  if (isJsExpr(value)) {
    return evaluate(ctx, value.__jsExpr)
  } else if (!value || typeof value !== 'object') {
    return value
  } else if (Array.isArray(value)) {
    return value.map(item => interpolate(ctx, item))
  } else {
    return valueMap(value, item => interpolate(ctx, item))
  }
}
```

按块讲解：

- **做什么**：`evaluate` 就是 `new Function('ctx', 'expr', 'with (ctx) { return eval(expr) }')`；`interpolate` 递归走遍对象 / 数组，遇到表达式节点就求值。
- **与哪个知识点相关**：结论 6 的"`config` 内任意深度"。
- **求值作用域（这条解释了两条实践惯例）**：表达式的自由变量是**全局**（`process`、`JSON`…）加上条目自己的 `ctx` 属性（`with (ctx)` 提供）。所以：查服务要用安全的 `ctx.get('...')`；取注入后的值直接写 `ctx.<service>.<field>`。仓库里的真实写法就是这两类——`packages\bundle\base\cordis.patch.yml` 第 22、30、99、103 行全是 `!!js "!ctx.get('profileContext')"`，而 `packages\bundle\web-app\cordis.patch.yml` 第 182–183 行是 `!!js ctx.webStartup.host ?? '127.0.0.1'`（该行所在条目第 180 行声明了 `inject: [webStartup]`，见 §4.13 的时机说明）。
- **配套**：`isJsExpr` 在 `vendor\loader\src\config\utils.ts` 第 24–27 行（判据是对象里有没有 `__jsExpr` 键），表达式节点的类型 `JsExpr` 在第 29–32 行。

### 4.10 `disabled`：唯一被求值的元数据字段

**`vendor\loader\src\config\entry.ts` 第 75–95 行**

```ts

  get disabled() {
    // group is always enabled
    if (this.options.group) return false
    let entry: Entry | undefined = this
    do {
      if (this.disabledOf(entry.options)) return true
      entry = entry.parent.ctx.fiber.entry
    } while (entry)
    return false
  }

  /**
   * Effective disabled state: a `!!js` expression evaluates against the loader
   * context. The raw node stays in the options, so write-back keeps the form.
   */

    return isJsExpr(options.disabled)
      ? Boolean(this.evaluate(options.disabled.__jsExpr))
      : Boolean(options.disabled)
  }
```

按块讲解：

- **做什么**：`disabled` 是一个 **getter**。它沿"自己 → 各级父条目"逐级问 `disabledOf`；`group` 行**永远不算禁用**（注释原文 `group is always enabled`）。`disabledOf` 只对 `disabled` **这个节点本身**判断是不是表达式节点：是就求值，不是就 `Boolean()` 强转。
- **与哪个知识点相关**：结论 6。两个推论都在这几行里：
  1. **`Boolean(...)` 强转** → Loader 把"其他真值"也当禁用（生成的 schema 因此只接受布尔 / null / 表达式，并在描述里写明它会拒绝其他真值：`config-schema\document.ts` 第 17 行）。
  2. **JSDoc 原文**：`The raw node stays in the options, so write-back keeps the form.` —— 求值结果**不写回** options，所以文件回写时 `!!js` 形态不丢（有测试钉住：`packages\boot\app-boot\tests\user-patches.spec.ts` 第 290–304 行断言 `options.disabled` 仍是 `{ __jsExpr: … }`，而 `entry.disabled` 是布尔）。
- **什么时候被求值**：`Entry.update` 第 136 行（`if (this.disabled) { this.fiber?.dispose(); return }`）与 `Entry.refresh` 第 113 行（`if (this.disabled) return`）——也就是**每次挂载决策**。所以表达式只能引用**那一刻已经可见**的值：真实 patch 里只用 `process.platform`、`process.env.*`、`ctx.get('profileContext')`（见 `packages\bundle\base\cordis.patch.yml` 第 22、30、99、103 行；`packages\bundle\web-app\cordis.patch.yml` 第 47、293 行）。
- **换掉表达式会怎样**：`entry.update({ disabled: <新表达式> })` 会**重新求值并挂载 / 卸载**（`packages\boot\app-boot\tests\user-patches.spec.ts` 第 306–330 行）。
- **`config` 的求值时机不同**（别混）：`config` 表达式在 **fiber 激活时、注入就绪之后**才求值。`Fiber._refresh` 只要有一个 `inject` 服务没就位，就把 epoch 置 `INACTIVE`（`vendor\cordis\src\fiber.ts` 第 611–623 行）；epoch 从 `INACTIVE` 变成就绪才 `_reload()`（第 646–673 行，第 655 行解析 config）→ `_resolveConfig()`（第 641–644 行）→ `internal/config` 瀑布 → `interpolate`。`fiber.update` 里还专门写了注释：*Config resolution may access injected services, so defer it until the fiber can activate*（第 740–741 行）。这就是 web-app patch 里 `inject: [webStartup]` + `host: !!js ctx.webStartup.host ?? '127.0.0.1'` 能工作的原因（`packages\bundle\web-app\cordis.patch.yml` 第 178–186 行）。
- **dump / schema dump 完全不求值**：`renderConfigDump` 的文档注释明确写 *`!!js` expressions print verbatim, unevaluated*，并说明这样输出仍是**一份可加载的 YAML**（`packages\boot\app-boot\src\index.ts` 第 406–407 行）；YAML 侧靠 §4.1 的 `represent` 还原标签。schema 侧同样只做结构校验：测试拿 `throw new Error("do-not-evaluate")` 当表达式，断言它既没执行、也没被打印进结果（`packages\boot\app-boot\tests\config-schema.spec.ts` 第 131–146 行）。

- `$defs.patch.properties` = `insert`（其余键来自 `allOf: [$defs.entryMetadata]`，见 `config-schema\document.ts` 第 24–30、152 行）
- `$defs.entry.required` = `['name']`（第 133 行）；`$defs.patch` 里 **`name` 不是 required**，只在出现时被约束为 `''` 或目标真实 `name`（第 141–147 行）

| 键 | 语义 | 出处 |
|---|---|---|
| `id` | 条目在树内的身份；patch 全靠它寻址。条目侧可省略时 Loader 会随机生成一个 id（见下），所以**补丁插入的行必须自带 id**，否则后续层永远打不到 | `config-schema\document.ts` 第 13 行；`vendor\loader\src\config\tree.ts` 第 51–58 行 |
| `name` | 要加载什么（包名或子路径导出）；插入的行必需，覆盖行可选（给了就是**身份断言**） | `document.ts` 第 14 行、第 29 行、第 133、141–147 行 |
| `insert` | 条目数组；不带 `id` 追加顶层，带 `id` 推进目标的 `config` 数组 | `vendor\include\src\index.ts` 第 79–101 行 |
| `config` | 传给插件的配置；patch 时**整体替换、无深合并** | `document.ts` 第 15、29 行；`vendor\include\src\index.ts` 第 120–123 行 |
| `group` | "允许被 patch 索引、允许作为可插入的条目列表容器"——**它不选择插件实现** | `document.ts` 第 16 行 |
| `disabled` | 布尔或 `!!js` 表达式；Loader 把**其他真值**也当禁用，schema 只接受布尔 / null / 表达式（其余真值会被 schema 拒） | `document.ts` 第 17 行；`vendor\loader\src\config\entry.ts` 第 91–95 行 |
| `inject` | 该行依赖的服务（数组或对象形式） | `document.ts` 第 18 行；`vendor\loader\src\index.ts` 第 129–135 行 |
| `intercept` | 拦截配置字典，挂到 `ctx[Context.intercept]` 上 | `vendor\loader\src\config\isolate.ts` 第 5–9、126 行 |
| `isolate` | 按名字隔离服务实现（`true` = 该条目私有 realm，字符串 = 同名条目共享的全局 realm） | `isolate.ts` 第 5–9、75–89 行 |
| 其他任意键 | 语法上允许（`PatchOptions` 有索引签名，赋值循环会照抄），但**没有语义** | `vendor\include\src\index.ts` 第 120–123、140 行 |

**两条补充**：

1. **随机 id 长什么样**：`EntryTree.ensureId` 用 `Math.random().toString(16).slice(2, 10)` 生成，并循环到不与已有 id 冲突为止（`vendor\loader\src\config\tree.ts` 第 51–58 行）。所以"没写 id 的行"在两次启动之间 id 是不同的——**要能被后续层改，就必须自己写 `id`**。
2. **`intercept` / `isolate` 不在 `EntryOptions` 的原始声明里**，是 loader 通过**模块增强**补上的（`vendor\loader\src\config\isolate.ts` 第 5–9 行的 `declare module './entry.ts'`）。真实用例就是 preset 里的 group 行：`isolate: { planMode: true }`（`packages\bundle\web-app\presets\standard.patch.yml` 第 46–51 行）。它们的**语义**属于第三编，第一次读请跳过（见附录 C）。

**索引可见性的边界**（本课最容易被忽略的一条，`1.2` 只讲了"后一层能改前一层插入的行"）：

- `buildMap` 只递归 `group && Array.isArray(config)`（`vendor\include\src\index.ts` 第 69–72 行）。所以：
  - 同一份扁平 patch 列表里，**后一条 patch 能看到前一条插入的行**（第 95–101 行的 `buildMap(insert)`）；
  - 但**看不到**"普通覆盖把 `config` 整体换掉时新引入的子行"——因为索引只在开头的 `buildMap(data)` 和每次 `insert` 后重建，**覆盖路径不重建**。仓库专门用测试钉住了这个语义：层 a 用 `config:` 换掉 group 的 `config` 引入 `child`，层 b 的 `- id: child` 报 `not found`，与实际 boot 一致（`packages\boot\app-boot\tests\config-dump.spec.ts` 第 118–150 行）。
  - 另外，像 `@deepseek-ai/dsh-agent-preset` 那样**自己管理子列表**（子行在 `config.plugins` 而非 `config` 数组、行上没有 `group: true`）的插件，其子行**不在 patch 索引里**；schema 收集器甚至会报 `unrecognized Loader tree carrier; use cordis:group or cordis:include for native child collection`（`packages\boot\app-boot\src\config-schema\collect.ts` 第 94–115 行，报错在 114 行）；实测中该 web profile 有 4 行这样的 preset 行，正好对应 4 条同类诊断（见 §5.2）。

## 附录 A 关键问题与答案

> 本课五个问题都属本课范围（patch 语法），**都要读**。其中涉及后续编运行语义的小段已单独标注"第一次读请跳过"。

### ① `cordis.yml` 与 `cordis.patch.yml` 各自的角色？为什么根文件是空数组、且注释说不要编辑它？

**角色**：两者是同一门 YAML 方言（`entryListSchema`）的两种用法（`vendor\include\src\index.ts` 第 9–23 行）。
`cordis.yml` 是 Loader include 的**锚点**（`baseUrl` 锚 + dump 锚），内容是常量 `PROFILE_ROOT_CONFIG` 的空数组；`cordis.patch.yml` 是**用户 patch 层**，顶层数组的元素是 patch 条目，运行时作为 Include 的 `config.patches` 传入，**在挂载前一次性应用到根数组上**（`packages\boot\app-boot\src\index.ts` 第 570–579 行；`vendor\include\src\index.ts` 第 245–263 行）。
层级顺序：bundle 层 → profile 层 → home 层（`$DSH_HOME\cordis.patch.yml`）→ `--patch` 层 → 遥测补丁（`packages\boot\app-boot\src\profile-context.ts` 第 65–73 行）。

**为什么是空数组**：因为没有"原始内容"这回事——整棵树全部由各层的 `insert` 推入，base bundle 就是"一个 insert 覆盖空根"（`packages\bundle\base\cordis.patch.yml` 第 1–4 行）。

**为什么不要编辑它**（三条独立理由）：
1. **改了也会没**：`prepareProfile` / `composeProfile` 每次启动都无条件重写它（`apps\cli\src\profile-boot.ts` 第 167–173、197–209 行）；实测 dump 前后 `LastWriteTime` 变了（§5.2）。
2. **就算不被重写也不能放行**：Loader 的写回会把**已组合**的 `root.data` 落盘（`vendor\include\src\index.ts` 第 336–340、289–308 行 + `vendor\loader\src\config\group.ts` 第 48–50 行 + `vendor\loader\src\index.ts` 第 158–166 行），下次启动就会**重复每一层的 insert**；头注释写明这份重写就是为了拆掉这个坑（`apps\cli\src\profile-boot.ts` 第 152–160 行）。
3. **它是锚点**：Loader 需要一个真实 include 根来锚 `baseUrl`，dump 也锚同一文件（`apps\cli\src\profile-boot.ts` 第 157–160 行；`apps\cli\src\dump-config.ts` 第 40–41 行），所以文件必须存在且是数组；boot 传的配置没有 `initial`，文件缺失直接报 `config file not found`（`packages\boot\app-boot\src\index.ts` 第 571–574 行；`vendor\include\src\index.ts` 第 252–258 行）。

### ② 一条 patch 条目允许哪些键？各自语义？

**9 个键**：`id`、`name`、`insert`、`config`、`group`、`disabled`、`inject`、`intercept`、`isolate`（`PatchOptions` 见 `vendor\include\src\index.ts` 第 129–141 行；生成 schema 实测 `$defs.entryMetadata.properties` + `$defs.patch.properties = {insert}`，见 §5.2 与 §4.14）。

语义与落点（逐键）：

- `id`：寻址键。非 `insert` 且无 `id` → 告警跳过；`id` 不存在 → 告警跳过。条目侧可省略（Loader 用 `Math.random().toString(16).slice(2, 10)` 随机生成，见 `vendor\loader\src\config\tree.ts` 第 51–58 行），但**补丁插入的行必须自带 `id`** 才能被后续层打到（`buildMap` 只登记真值 `id`）。
- `name`：要加载什么。**对覆盖行是"身份断言"而不是改名**——`name` 被解构出去、永不写到目标上；不符则整条跳过（`vendor\include\src\index.ts` 第 77、115–118 行）。
- `insert`：条目数组。不带 `id` → 追加顶层；带 `id` → 目标必须存在且是 group，子行推进 `target.config`。**`insert` 与覆盖键同时出现时，覆盖键被忽略**（分支里 `continue`，第 79–102 行）。
- `config`：插件配置。patch 时**整体替换、无深合并**（第 120–123 行；`config-schema\document.ts` 第 29 行）——所以要改一个字段必须重述整块 `config`（见 §4.7 的示意与 bundle 侧实例）。
- `group`：标记该行 `config` 是**可插入的条目列表容器**，并让它进入 patch 索引；**不选择插件实现**（`document.ts` 第 16 行）——实现由 `name` 决定，例如 `cordis:group`。
- `disabled`：布尔或 `!!js`；Loader 把其他真值也当禁用（`document.ts` 第 17 行；`entry.ts` 第 91–95 行）。
- `inject`：该行依赖的服务；插入行上的真实用法是 `inject: [webStartup]`（`packages\bundle\web-app\cordis.patch.yml` 第 180、201、231 行）。
- `intercept` / `isolate`：作用域手段，经模块增强加进 `EntryOptions`（`vendor\loader\src\config\isolate.ts` 第 5–9 行）；真实例子 `isolate: { planMode: true }`、`isolate: { compaction: true, toolResultPruner: true }`（`packages\bundle\web-app\presets\standard.patch.yml` 第 49–50、70–72、87–88 行）。**其运行语义属第三编——第一次读请跳过本节这一项**（详见附录 C）。
- 其他任意键：类型上允许（索引签名），赋值循环会照抄到目标上，但没有任何语义（第 120–123、140 行）。

### ③ `!!js` 能写在哪些位置、什么时候求值？（结合 `--dump-config` 原样打印不求值这个事实）

**能写的位置**（三处，且有一个例外）：

1. **`config` 内任意深度** —— 非 tree carrier 的条目在 `internal/config` 瀑布里被递归插值（`vendor\loader\src\index.ts` 第 104–113 行；`utils.ts` 第 11–22 行）。
2. **`disabled` 的自身节点** —— 每次挂载决策由 `Entry.disabled` getter 求值（`entry.ts` 第 76–95、113、136 行）。
3. **例外**：Group / Include 这类 tree carrier 的 `config` 保持字面量（它的 `config` 装的是别人的行清单，里面的 `!!js` 属于那一行自己的 fiber）——patch 文件 `insert:` 出来的行正属于这种形态。

**明确不能写的位置**：`id`、`name`、`group`、`inject`、`intercept`、`isolate` 六个元数据字段（含其下嵌套）——仓库门禁报 `!!js is not interpolated here`；`disabled` **下面**再嵌套的表达式同样不求值（`scripts\verify-cordis-config.ts` 第 41、517–539 行）。`docs\cordis-tutorial\05-config.zh.md` 第 107 行的说法与此一致。

**求值时机**（三个时间点）：

- `config`：**fiber 激活时、且 `inject` 就绪之后**。注入未齐 → epoch `INACTIVE`，不加载（`vendor\cordis\src\fiber.ts` 第 611–623 行）；就绪后 `_reload` → `_resolveConfig` → `internal/config`（第 641–673 行）。`fiber.update` 的注释直接说明"配置解析可能访问注入服务，所以延后到可激活时"（第 740–741 行）。
- `disabled`：**每次挂载决策**（条目 update / refresh 时，`entry.ts` 第 113、136 行）；换表达式会重新求值并挂载 / 卸载（`packages\boot\app-boot\tests\user-patches.spec.ts` 第 306–330 行）。
- **dump / schema dump：从不求值**。`renderConfigDump` 的注释写明 `!!js` 原样打印（`packages\boot\app-boot\src\index.ts` 第 406–407 行），靠 YAML `represent` 还原标签（`vendor\include\src\index.ts` 第 14 行）；实测 web dump 的 39 行 `!!js` **全部原样**，多行表达式以 `!!js >-` 块形式出现（§5.2）。schema 侧同样只做结构校验（`packages\boot\app-boot\tests\config-schema.spec.ts` 第 131–146 行）。

**一个容易忽略的推论**：正因为 `disabled` 的表达式节点**留在 options 里**而不写回求值结果，文件回写才能保住 `!!js` 形态（`entry.ts` 第 87–90 行的注释 + `user-patches.spec.ts` 第 290–304 行）。

### ④ patch 里的 `name` 是可选还是必需？给出真实例子。

**覆盖行（非 `insert`）：可选。** 省略时只按 `id` 命中；写上时作为**身份断言**，与目标真实 `name` 不符就整条跳过并告警（`vendor\include\src\index.ts` 第 115–118 行）。生成 schema 的写法是"`name` 不是 required，出现时其值必须是 `''` 或目标的真实 `name`"（`config-schema\document.ts` 第 141–147 行）。实测：
- 省略的真实例子：`- id: tool-bash` / `  disabled: true`（`packages\bundle\web-app\cordis.patch.yml` 第 465–472 行，同处还有 `tool-plugin-manager`、`tool-pwsh`）。
- 写上的真实例子（仓库内）：测试 fixture 里就有"覆盖行 + `name` 身份断言"的原文——`packages\boot\plugin-manager\tests\patch.spec.ts` 第 52 行的 `- id: tool` + `  name: another-package` + `  disabled: false`，以及同文件第 67 行那组 `- id: tool` / `  name: package` / `  config: …` / `  disabled: true # availability`。语义就是"我确认这个 `id` 现在还是这个包"。**注意**：仓库里 bundle 自己的 patch 覆盖行普遍**不写** `name`（例：`packages\bundle\web-app\cordis.patch.yml` 第 465–472 行只写 `id` + `disabled`）；用户层写不写都行（结构示意见 §4.7）。
- 不匹配的实测后果：探针 D → `patch: name mismatch for "ui-chat" (expected "@deepseek-ai/dsh-client-ui-chat", got "…"), skipping`，该条 `config` 未生效。

**插入行（`insert` 里的元素）：必需。** 生成 schema 的 `$defs.entry.required` 实测就是 `['name']`（`config-schema\document.ts` 第 132–135 行），运行时 `Entry._init` 会拿它去 `tree.import(this.options.name)`（`vendor\loader\src\config\entry.ts` 第 226 行），没有 `name` 就无从加载。`docs\cordis-tutorial\05-config.zh.md` 第 36–42 行给的最小条目也是"`name` 必需、`config` 可选"。

### ⑤ `group` 条目与 `insert` 的关系是什么？`insert` 带 `id` 与不带 `id` 有何区别？

**`group` 与 `insert` 的关系**：`group: true` 让该行的 `config` 成为**条目列表**，从而（a）它自身可被 patch 索引到，（b）它可以作为 `insert` 的落点。生成 schema 的原话：*"Allows patch indexing and insertion into an entry-list config; does not select the plugin implementation."*（`config-schema\document.ts` 第 16 行）。算法侧的条件是 `entry.group && Array.isArray(entry.config)`（递归登记子条目，`vendor\include\src\index.ts` 第 69–72 行）；运行时由 `Group` 插件装载这份子列表（`vendor\loader\src\config\group.ts` 第 74–89 行），builtin 名 `cordis:group`（`packages\boot\app-boot\src\index.ts` 第 564 行；`vendor\loader\src\config\tree.ts` 第 111–115 行）。真实 group 行写法：`packages\bundle\web-app\presets\standard.patch.yml` 第 46–51 行。

**两种 `insert` 的区别**（`vendor\include\src\index.ts` 第 79–102 行）：

| | 不带 `id` | 带 `id` |
|---|---|---|
| 行为 | `data.push(...insert)`，追加到**顶层末尾** | 目标必须存在**且 `group` 为真**，`target.config.push(...insert)` |
| 失败模式 | 无 | 目标不存在 → `patch insert: entry %C not found`；目标不是 group → `patch insert: entry %C is not a group`；**两者都只告警并跳过，不中断启动** |
| 谁能这么做 | 任何层（bundle 用它在空根上建树） | 任何层，只要目标行声明了 `group: true` |
| 实测 | 探针 A：新行落在 dump 末尾、无告警 | 探针 B（目标 `ui-chat` 不是 group）：`is not a group`；探针 G：`probe-child-added` 被推进 `probe-group.config` |
| 索引效应 | 插入后立即 `buildMap(insert)`，同层后续 patch 可继续打这些新行 | 同上 |

**一个必须记住的边界**：带 `id` 的 `insert` 要求目标是 **group**，而"group"由行上的 `group: true` 决定，**不由包名决定**。所以四类行打不到：目标行不存在、目标行不是 group、目标行是"用 `config:` 覆盖引入子行的普通行"（索引不重建，`packages\boot\app-boot\tests\config-dump.spec.ts` 第 118–150 行）、目标行是插件自管子列表（如 preset 的 `config.plugins`，`packages\boot\app-boot\src\config-schema\collect.ts` 第 94–115 行 + 探针 I）。
