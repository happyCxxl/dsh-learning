## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：cordis 内核里**四个核心对象**（Context / Registry / Fiber / Service）各自是什么、谁创建谁、一次 `ctx.plugin()` 在代码里究竟走了哪几步。

**不是**：依赖注入的**用法**（那是 2.2）、副作用的**顺序纪律**（2.3）、事件分发（2.4）、作用域（2.5）。本课只在链条上点到它们的位置，不展开它们的规则。

### 0.2 现在只要记住这 4 件事

1. **`ctx` 是一个 `Proxy`**，不是普通对象：属性读取走服务解析器（`ctx.x` 能取到服务，是因为代理的 `get` trap 去查了"登记表"）。
2. **四个对象是一条链上的四个角色**：root `Context` 造出 `Registry` 与 root `Fiber` → `ctx.plugin()` 让 `Registry` 建一条 **runtime** 记录并 `new Fiber` → `Fiber` 用 `parent.extend()` 造出**插件自己的**子 `ctx` → `Service` 子类在构造函数里 `super(ctx, name)` 把服务**登记**进 `reflect.store`。
3. **Fiber 是"一次插件应用"，不是"一个插件"**：同一个函数 `ctx.plugin()` 两次 → 登记表里仍是 1 条记录，但有 2 个 fiber（§7 的实测第 2b 段有数字）。
4. **服务的可见范围由 `fiber.store` 决定**：提供方自己的 fiber 会写入自己提供的服务（reflect.ts 第 293 行），依赖方靠 `inject` 在就绪时把实现写进自己的 store——所以"谁能读到"是有确定规则的，不是运气。

### 0.3 明确授权：这些现在**不用管**

- `effect` / disposer 的**逆序释放纪律**、`ctx.effect()` 的返回形状 → **2.3**；
- `inject` 的**写法与可选依赖** → **2.2**；五种事件分发 → **2.4**；
- `isolate` / `intercept` / 作用域遮蔽（shadow）→ **2.5**；`Config` schema 校验与组合 → **2.6**；
- Loader 如何把 YAML 变成 `ctx.plugin()` 调用 → **2.9**（本课只在 §7.3 用到它的一个事件监听点）。

判断标准只有一条：**能说清"这个对象在 §2.1 那张链上站在哪一环、谁创建它"**，就够了。

### 0.4 如果你是第一次读，跳过附录 A 的 Q5–Q9

附录 A 的 **Q5–Q9 涉及 2.2–2.5 才展开的细节**（`strict` 读取、inject 门控、卸载后残留、isolate 作用域）。第一次读只看 **Q1–Q4**（四个对象是什么、登记在哪、Fiber 代表什么、它们之间的关系）。

## 1. 最小词汇表（本课新增的 8 个词）

这 8 个词是本课的地基。**先用大白话建立直觉**，不要追问它们的实现——实现就是 §5–§9 的内容。

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **fiber** | **一次"把某个插件装上"的账本**：它记着这次装载的身份编号、状态、配置、依赖快照、以及卸载时要撤销的全部动作 | `class Fiber`（fiber.ts 第 184 行） |
| **runtime** | **按插件身份存的那一条记录**：一个插件只有一条 runtime，但它可以有多次装载（多个 fiber） | `Plugin.Runtime`（registry.ts 第 136–145 行），存在 `registry._internal` |
| **callback** | 归一之后**真正被调用的那个函数**——它同时也是"这个插件是谁"的**身份键** | `Plugin.Runtime.callback`（registry.ts 第 142 行） |
| **inject** | 插件事先声明的**"我要用哪些服务"清单**；清单没齐就不启动 | `ctx.inject([...], cb)` / `static inject = [...]` |
| **effect / disposer** | **副作用**与它配套的**撤销函数**：装的时候把"怎么卸"一起交出来 | `ctx.effect(() => { …; return () => {…} })`（细节在 2.3） |
| **uid** | fiber 的**身份编号**：root 是 `0`，其余每建一个自增；卸载后置 `null` | `fiber.uid`（fiber.ts 第 185–186 行） |
| **isolate（隔离键）** | 同一个服务名的**多个互不干扰的实现**之间的分组标签；默认全应用共用一个 | `ctx[symbols.isolate][name]`（context.ts 第 122–124 行；语义在 2.5） |
| **Proxy trap（代理钩子）** | 给对象装的"拦截器"：读属性、写属性、判存在都会先经过它 | `new Proxy(target, { get, set, has })`（reflect.ts 第 135–206 行） |

> ⚠️ `effect` 与 `isolate` 的**规则**属于 2.3 / 2.5；本课只用到"它存在、它挂在哪个对象上"这个程度。本课其余出现过的词（`Service` 基类、`reflect.store`、`registry._internal`、`epoch`）都在 §5–§9 就地定义。

### 2.2 动态过程：一次装载的先后顺序

用实测的事件序列画（来源：§7 第 3 段脚本的真实输出；每行的产生处都标了源码行）：

```
t0  new Context()                       root Fiber: uid=0 state=ACTIVE
t1  ctx.inject(['lateSvc'], cb)         先建一个 fiber（callback 还没跑）
        └─ 依赖 lateSvc 不存在 ⇒ 停在 PENDING        fiber.ts:611-623（_refresh → _setEpoch(INACTIVE)）
t2  ctx.plugin(LateSvc)                 runtime 新建 + new Fiber
        └─ emit internal/plugin  uid=2              fiber.ts:302
        └─ 无依赖 ⇒ epoch 从 INACTIVE 变有效
               internal/status  uid=2 PENDING->LOADING   fiber.ts:630-633
               callback 跑完
               internal/status  uid=2 LOADING->ACTIVE    fiber.ts:665-667
                        └─ _updateState 通知依赖方        fiber.ts:588-594 → reflect.ts:314-336
t3  依赖方被唤起
        internal/status  uid=1 PENDING->LOADING      ← 此刻它的 callback 才跑
        consumer.apply RAN, lateSvc=object
        internal/status  uid=1 LOADING->ACTIVE
```

**两条纪律**（§8 会给源码）：

- **"提供方先 ACTIVE，依赖方才 LOADING"**——通知由提供方 fiber 的**状态跃迁**触发，不是靠"谁先登记"。
- **插件 callback 运行时，自己的 fiber 还在 LOADING**（实测 `ranAt=LOADING`）：`ACTIVE` 是 callback 跑完之后的结论。

> 图上没有未定义的词：`callback` / `inject` / `uid` / `isolate` / `runtime` 都在 §1 定义过；`epoch` 在 §8 就地定义。
> 精确性说明：t2 的两条 `internal/status` 之间还夹着 `_execute`，图里省略了它——见 §7.2 与 §8.2。

## 3. 大白话版：写下一个插件之后，机器里发生了什么

**完全不用上面的术语**（来源：§5–§9 的源码因果链。步骤 1–2 对应 §5，3–5 对应 §6，6–9 对应 §8，10–11 对应 §9.1 / §9.2，12 对应 §9.3）：

1. 程序启动时，先造一个"总登记处"对象；这个对象把自己包了一层壳，之后所有人拿到的都是这层壳。
2. 同一时刻造一个"总账本"，编号为 0，状态直接算作"已激活"；再把四个自带工具（反射层、登记表、事件总线、日志）直接挂在总登记处身上。
3. 你调用"装一个插件"，登记表先判断你给的是什么：**函数**、**带 apply 的对象**、**类**——三种都换算成同**一个函数**（这个函数就是插件的身份）。
4. 登记表按这个函数去查有没有旧的记录：有就复用（说明这个插件之前装过），没有就新建一条并记下它的名字。
5. 登记表为这次装载**新开一本账本**（编号自增），账本里放一个**只属于本次装载的子登记处**，并把"怎么把这次装载撤销干净"登记到父账本上。
6. 账本翻出插件声明的"我要用哪些服务"清单，逐个去查：**缺一个就停在"等待中"**，一个也不缺才继续。
7. 继续的动作是：先把配置过一遍校验、再执行插件的那个函数，并把执行过程中产生的所有"怎么撤销"都收进账本。
8. 函数跑完、状态改成"已激活"的那一刻，通知所有"清单里点了我提供的服务名"的账本，让它们重新去查一遍。
9. 那些账本之前停在"等待中"，现在清单齐了，于是它们也走一遍第 7 步——**服务的就绪顺序就是这样一层层滚出来的**。
10. 插件想在子登记处上提供一项服务，做法通常是**继承一个基类**并在构造函数里调一次 `super(子登记处, '服务名')`——这一次调用就完成了登记。
11. 服务不是"塞进一个字典"就完事：登记时顺手把它包装成"一次性副作用"（撤销函数也一起登记），所以**账本被卸载时它自动消失**。
12. 之后别人写"子登记处.服务名"时，那个壳会拦截这次读取，按"隔离键 + 沿父账本上溯"找到实现；**找不到就抛错**——只有在"那个壳属于根账本"时才会安静地给你 `undefined`（实测见 §9.3 末尾）。

## 4. 结论先行：四个角色一览

四个对象不是四个并列名词，而是**一条链上的四个角色**。这张表是本课的总纲，每个来源都在 §5–§9 有对应的源码块。

| 对象 | 一句话 | 实例住哪 | 谁创建 | 身份 |
|---|---|---|---|---|
| **Context** | 插件之间的**依赖容器 + 代理对象**；所有服务 / 事件 / 生命周期 API 都从它进出 | 就是 `ctx` 本身（root 一个，每个 fiber 一个） | `new Context()`（context.ts 第 71 行）、`parent.extend()`（第 99 行） | 自身**没有 id**；要靠 `ctx.fiber.uid` 定位（出处：`.agents/notes/archived/architecture/2026-08-24-cordis-runtime-tree-inspection.zh.md` 第 40 行） |
| **Registry**（`RegistryService`） | **插件登记表**：把三种插件形态归一成一个 callback，为每个 callback 建一条 runtime 记录，并在当前 context 下启动 fiber | `ctx.registry` | 根 Context 构造函数（context.ts 第 79 行） | `Map<callback, Plugin.Runtime>`（registry.ts 第 197 行） |
| **Fiber** | **一次插件应用的生命周期实例**：状态机 + 配置 + 依赖快照 + 全部 disposer | `ctx.fiber` | `RegistryService.plugin()` 里 `new Fiber(...)`（registry.ts 第 330 行） | `uid`：root 为 `0`，其余自增（registry.ts 第 207–209 行、fiber.ts 第 235 行） |
| **Service** | 服务的**基类**：子类 `super(ctx, name)` 这一步就把自己注册进 ctx | 插件自己 new 出来的实例 | 插件作者（`class X extends Service`） | 服务名字符串 + isolate 作用域 symbol（reflect.ts 第 286–288 行） |

**三条硬结论**（前两条的依据在 §9.3，第三条在 §9.2）：

1. **`ctx` 是 `Proxy`。** 属性读取走 `ReflectService.handler.get`（reflect.ts 第 135–171 行），不是普通字段查找；文档 `docs/cordis-api/context.zh.md` 第 12 行原文也是这么写的：「上下文是一个代理：普通属性读取通过服务解析器进行」。
2. **Fiber 是"一次应用"，不是"一个插件"。** 同一个 callback 在 registry 里只有一条 runtime，但可以有多个 fiber（实测 §7 第 2b 段：同一函数 `ctx.plugin()` 两次 → `registry.size=1`、`fibers.length=2`）。
3. **Service 不是 cordis 的运行时对象，而是一个基类约定。** 它对内核的唯一要求是"构造完调用 `ctx.reflect.provide()`"，而 `provide` 把它包成一个 effect（reflect.ts 第 277–305 行），因此服务天然随 fiber 卸载而消失。

## 5. Context：构造函数做了四件事（源码对照）

`vendor/cordis/src/context.ts` 第 35–41、71–84、86–88 行（**三段接续**：类头与其 JSDoc——"为什么上下文是代理"这句权威表述就在这里；构造函数本身；构造函数之后紧邻的 `inspect` 自定义方法。中间第 43–70 行是四个静态 symbol 键与 `Context.is`，见 §5.3，此处不重复）：

```ts
/**
 * Root and child dependency containers for Cordis plugins.
 *
 * A context is a proxy: normal property reads go through the service resolver,
 * while `extend()`, `isolate()`, and `intercept()` create scoped child
 * contexts without mutating their parent.
 */
export class Context {                                         // ← 类头（第 42 行）
  // …（第 43–70 行：四个静态 symbol 键与 `Context.is`，见 §5.3，此处省略）
  /** Create the root context and install the built-in services. */

    const self = new Proxy<this>(this, ReflectService.handler)   // ② 代理在这里诞生
    this.root = self                                             // ③ root 指向代理自己
    this.baseUrl = undefined
    this.fiber = new Fiber(self, {}, Object.create(null), null, () => [])   // ③ root fiber，runtime 传 null
    this.reflect = new ReflectService(self)                      // ④ 四个内置服务
    this.registry = new RegistryService(self)                    //    直接挂成【自有属性】
    this.events = new EventsService(self)
    this.logger = new LoggerService(self)
    this.fiber._disposables.clear()
    return self                                                  // ⑤ 拿到的已经是代理
  }
  // …（第 85 行：一个空行，此处省略）
  [Symbol.for('nodejs.util.inspect.custom')]() {                 // ← 第 86 行：`console.log(ctx)` 显示成什么
    return `Context <${this.fiber.name}>`
  }
```

按块讲解：

- **类 JSDoc 的第二段**就是"ctx 是代理"这句结论的**作者原文**（英文 *A context is a proxy: normal property reads go through the service resolver*），与 `docs/cordis-api/context.zh.md` 第 12 行的中文译文对应——**§4 第 1 条硬结论直接引它，不是我的转述。**

- **① 两张表都用 `Object.create(null)`**：原型为 `null`，于是服务名不会撞上 `toString`、`constructor` 这类继承来的键——这是"服务名可以随便起"的前提。
- **② `new Proxy<this>(this, ReflectService.handler)`**：整个内核的地基。`handler` 就是 §9.3 要讲的那三个 trap。
- **③ `this.root = self`，随后 `new Fiber(self, {}, Object.create(null), null, () => [])`**：注意第 4 个参数 **`runtime` 传 `null`**——这是 root fiber 与普通 fiber 的分水岭（`{}` 是空 config、`Object.create(null)` 是空 inject、`() => []` 是空栈）。
- **④ 四个服务挂成自有属性**：所以 `ctx.registry` / `ctx.events` / `ctx.logger` 在**任何**插件的 ctx 里都读得到——它们不在服务表里，而在原型链上（§7 实测第 1 段、§9.3 第 ③ 条）。
- **⑤ `return self`**：构造函数返回了**代理**，所以 `new Context()` 的返回值是代理，`this` 才是裸对象。这也解释了为什么后面 `parent.extend({ fiber: this })` 正常工作——`this` 已经是代理，子对象的原型链直接接在它上面。

### 5.1 root fiber 为什么和普通 fiber 不同（源码）

`vendor/cordis/src/fiber.ts` 第 222–234 行 + 第 320–332 行（**两段接续**：前半是构造函数的头四行参数与分水岭 `if (runtime)`，后半是 `else` 分支的完整实现；中间第 235–319 行是普通 fiber 的整段装配逻辑，属 §7，此处省略）：

```ts
  constructor(
    public parent: Context,                                  // 谁装的我
    config: any,
    public inject: Dict<any>,                                // 归一后的依赖清单
    public runtime: Plugin.Runtime | null,                    // ← null 就是 root fiber
    getOuterStack: () => string[],
  ) {
    this._config = config
    const collect = (dispose: Disposable) => {                // 收集 disposer 的闭包
      this._disposables.push(dispose)
    }

    if (runtime) {
      // …（第 235–319 行：uid / 子 ctx / intercept / _runner / dispose / 广播 / 依赖检查，
      //   全文见 §7.1–§7.3；此处省略的理由是它属于"普通 fiber 的装配"这一知识点）
    } else {                                                  // ← runtime 为 null 才走这里
      this.uid = 0                                            // ① root 的编号固定是 0
      this.ctx = this.context = parent                        // ② root 的 ctx 就是它自己，不再 extend
      this.state = FiberState.ACTIVE                          // ③ 一出生就是"已激活"
      this.store = Object.create(null)                        // ④ 空的服务快照
      this._runner = {
        epoch: '',
        getOuterStack,
        execute: () => {},                                    // ⑤ root 没有插件代码可执行
        collect,
      }
      this.dispose = () => this.restart()                     // ⑥ root 不能真的被卸载，只能重启
    }
  }
```

- **上下文（谁调用它）**：这一支由 context.ts 第 77 行那句 `new Fiber(self, {}, Object.create(null), null, () => [])` 触发；普通 fiber 由 registry.ts 第 330 行触发（§6.2）。
- **①⑤⑥ 三处的意义**：`uid=0` 让 root 在编号上可识别；`execute` 是空函数 = root 不跑任何插件代码；`dispose` 指向 `restart()` = **root 无法被卸载**。
- **③ 一出生就是 ACTIVE**：后面 §6.1 与 §8.1 会用到——`_getImpl(name, true)` 只在提供方 fiber 是 `ACTIVE` 时才返回实现，root 提前满足这个条件；这也是 §9.3 第 ⑥ 条（root 读服务不需要 inject）能成立的前提。
- **④ `store` 是空表而不是 `undefined`**：普通 fiber 在装载前 `store` 是 `undefined`（fiber.ts 第 198 行），root 从一开始就有表——所以 `ctx.reflect.store` 与 `fiber.store` 的读法在 root 上不会踩空。

### 5.2 三个"复制自己"的方法（源码）

`vendor/cordis/src/context.ts` 第 90–107、121–125、141–145 行（**三段接续**：`extend` 连它的 JSDoc 一起给，`isolate` / `intercept` 只给函数体；省略的是第 109–120、127–138 行两段 JSDoc，理由是它们与 `extend` 的 JSDoc 同构）：

```ts
  /**
   * Create a child context with extra metadata on top of the current scope.
   *
   * The child prototypally inherits every property of this context; own
   * properties of `meta` shadow the inherited ones. The parent is not mutated.
   *
   * @param meta — own properties (including symbol keys) to define on the child.
   * @returns a child context inheriting from this one.
   */
  extend(meta = {}): this {                                                  // ← 函数头
    const shadow = Reflect.getOwnPropertyDescriptor(this, symbols.shadow)?.value
    const self = Object.create(getTraceable(this, this))                     // ① 原型链，不是拷贝
    for (const prop of Reflect.ownKeys(meta)) {
      Object.defineProperty(self, prop, Reflect.getOwnPropertyDescriptor(meta, prop)!)   // ② meta 的自有描述符原样搬
    }
    if (!shadow) return self
    return Object.assign(Object.create(self), { [symbols.shadow]: shadow })  // ③ shadow 存在时再套一层
  }
  // …（第 109–120 行：isolate 的 JSDoc，此处省略）
  isolate(name: string, label?: symbol) {                                    // ← 函数头
    const shadow = Object.create(this[symbols.isolate])                      // ④ 基于父表建子表
    shadow[name] = label ?? Symbol(name)                                     // ⑤ 同一个 label = 同一个 scope
    return this.extend({ [symbols.isolate]: shadow })
  }
  // …（第 127–138 行：intercept 的 JSDoc，此处省略）
  intercept(name: string, config: any) {                                     // ← 函数头
    const intercept = Object.create(this[symbols.intercept])
    intercept[name] = config                                                 // ⑥ 同理，基于父拦截表
    return this.extend({ [symbols.intercept]: intercept })
  }
```

- **① 是 `Object.create`，不是复制**：子 ctx 通过原型链继承父 ctx 的一切，**父对象不变**。`getTraceable(this, this)` 只是把"追踪信息"再包一层。
- **② 用 `Reflect.ownKeys` + 描述符**：symbol 键与不可枚举键也会被搬过去，且 getter/setter 保持原样——所以 `{ fiber: this }` 这类 symbol 键元数据不会丢。
- **③ shadow 分支**：`symbols.shadow` 是 `getTraceable` 机制用的标记（utils.ts 第 153 行），只有经过追踪包装的 ctx 才会走到这里。**细节属 2.3 / 2.5，本课不展开。**
- **④⑤ 隔离键的套路**：基于父表建子表，只改自己那一个键；源码第 115 行的 JSDoc 原文写着 `Passing the same label to two isolate() calls joins their scopes`——这就是"同一个 label = 同一个作用域"的权威表述（完整用法在 2.5）。
- **⑥ `intercept` 与 `isolate` 是同一个套路**：都是"基于父表建子表，再 `extend` 出去"，保证父级不受影响。**两者都不是拷贝整张表**，只多一个键。

### 5.3 `Context.is()` 为什么不依赖 `instanceof`（源码）

`vendor/cordis/src/context.ts` 第 42–68 行（类的开头：四个静态 symbol 键 + `is()` + 静态初始化块。省略的是第 52–60 行 `is()` 的 JSDoc，理由同上）：

```ts
export class Context {                                           // ← 类头
  /** Symbol key under which a disposer exposes its EffectMeta diagnostics tree. */
  static readonly effect: unique symbol = symbols.effect
  /** Symbol key for a context's listener filter, consulted on every event dispatch. */
  static readonly filter: unique symbol = symbols.filter
  /** Symbol key of the isolation map (see the `Context[symbols.isolate]` property). */
  static readonly isolate: unique symbol = symbols.isolate
  /** Symbol key of the intercept map (see the `Context[symbols.intercept]` property). */
  static readonly intercept: unique symbol = symbols.intercept
  // …（第 52–60 行：is() 的 JSDoc，此处省略）
  static is(value: any): value is Context {
    return !!value?.[Context.is as any]                                  // ① 读的是品牌属性
  }

  static {                                                               // ② 类静态初始化块
    Context.is[Symbol.toPrimitive] = () => Symbol.for('cordis.is')       // ③ 品牌 = 全局 symbol
    Context.prototype[Context.is as any] = true                          // ④ 原型上打品牌
  }
```

- **①③ 的技巧**：`Context.is` 是个函数，函数不能直接当属性键用，于是给它一个 `Symbol.toPrimitive`——被当作键时**返回全局 symbol** `Symbol.for('cordis.is')`。所以 `value?.[Context.is]` 实际读的是 `value[Symbol.for('cordis.is')]`。
- **④ 品牌挂在原型上**：`Context.prototype` 以及所有 `Object.create` 出来的子 ctx 都能读到，所以对子 ctx 也返回 `true`。
- **四个静态 symbol 键**（`effect` / `filter` / `isolate` / `intercept`）与 `utils.ts` 第 60–63 行的全局 symbol 一一对应，是"框架内部键不会撞上服务名"的第一道保障（第二道是 §9.3 的 `isSpecialProperty`）。
- **跨 realm / 跨多份 cordis 副本都成立**的原因：`Symbol.for` 走的是**全局注册表**，不依赖同一个 `Context` 类对象。**（标注为推断：源码注释只写了 "Works across realms and across multiple copies of cordis"，"两份打包产物互相识别"是我据 `Symbol.for` 语义推得的，未实跑跨副本场景。）**

### 6.1 归一：三种形态 → 一个 callback

### 6.2 入口：守卫 + runtime 复用 + 启动 fiber

`vendor/cordis/src/registry.ts` 第 316–336 行（`plugin()` 全函数，未删节）：

```ts
  plugin(plugin: Plugin, config?: any, getOuterStack = buildOuterStack()) {   // ← 函数头
```

### 7.1 构造函数前半：编号、子 ctx、intercept 层

`vendor/cordis/src/fiber.ts` 第 222–245 行（保留了构造函数头与三个必需参数的来源）：

- **③ 与 ⑦ 是同一个事件名**：`'internal/plugin'`（声明在 events.ts 第 331 行）。**创建时发一次、卸载时也发一次**，监听方要靠 `fiber.uid === null` 判断方向。Loader 正是听这个事件来给 fiber 补 `entry`、合并行上的 `inject`（`vendor/loader/src/index.ts` 第 129–135 行）。

## 8. 依赖 epoch：一个插件什么时候才算"可用"（源码对照）

**先说两个词**（本节新增，只在本节用到）：

- **epoch（纪元）**：一条**字符串指纹**，由"每个依赖的实现方 fiber 的 uid"拼成（`_refresh`）。指纹变了 = 依赖换人了 = 需要重装。
- **`INACTIVE` 哨兵**：fiber.ts 第 176 行的常量 `'__INACTIVE__'`，表示"依赖不齐"。

### 8.1 查依赖、算指纹、决定装或卸

`vendor/cordis/src/fiber.ts` 第 597–609 行（`_checkImpl` 全函数，未删节）：

```ts
  // 本块说明：这是 §8.1 上半块，只有 10 行——它本身没有可省的循环，把 ②③④ 三个
  // `return delete` 分支拿掉任何一个，读者就断在"缺依赖时到底删不删快照"上，所以整块照录。
  _checkImpl(name: string) {                                   // ← 函数头
    const impl = this.ctx.reflect._getImpl(name, true)         // ① strict=true：提供方必须 ACTIVE
    if (!impl) return delete this._store[name]                 // ② 没有 → 从快照里删掉
    try {
      if (impl.check && !impl.check.call(getTraceable(this.ctx, impl.value))) {
        return delete this._store[name]                        // ③ check() 说不可用 → 也删掉
      }
    } catch (error) {
      impl.fiber.ctx.logger.error(error)
      return delete this._store[name]                          // ④ check() 抛错 → 当作不可用
    }
    this._store[name] = impl                                   // ⑤ 就绪 → 写进【自己的】快照
  }
```

- **① `strict=true` 的含义**：`_getImpl` 在 strict 下要求**提供方 fiber 的 `state === ACTIVE`**（reflect.ts 第 237–243 行）。**所以"服务已登记但提供方还没激活"不算就绪。**
- **②③④ 三种"不可用"**：不存在 / `check()` 返回假 / `check()` 抛错——**都只是把名字从快照里删掉**，不抛错、不中断。`check` 是 `ctx.provide(name, value, check)` 的第三个参数（reflect.ts 第 277 行）。
- **⑤ `this._store` 是"我依赖的实现快照"**：`_reload` 时被复制成公开的 `this.store`（第 647 行）。**注意区分两张 store**：`fiber._store` / `fiber.store`（依赖方看别人）与 `reflect.store`（全局服务表，挂在 root 上）。
- **谁调用它**：fiber 构造函数末尾（§7.3 ⑩）逐个依赖调一次；`provide` 之后由 `notify` 调（reflect.ts 第 323 行）。

**接着算指纹、决定装或卸** —— `vendor/cordis/src/fiber.ts` 第 611–639 行（`_refresh` / `_setEpoch`，未删节）：

```ts
  _refresh() {                                                 // ← 函数头（第 611 行）
    // 读之前先知道两个输入的来源：this.inject = 插件声明的依赖清单（构造函数的 public 参数，
    // 来自 registry.ts 第 330 行的 Inject.resolve(plugin.inject)）；
    // this._store = 上一步 _checkImpl 逐个写进去的"已就绪依赖"快照（§8.1 上半块）。
    let epoch: string | boolean = false
    epoch = ''
    for (const name of Object.keys(this.inject)) {             // ⑥ 遍历自己声明的依赖
      const impl = this._store[name]
      if (!impl) {
        epoch = INACTIVE                                       // ⑦ 任一缺失 → 整体回退"不可用"
        break
      }
      epoch += ':' + impl.fiber.uid                            // ⑧ 指纹 = 各提供方的 uid 串
    }
    this._setEpoch(epoch)
  }

  private _setEpoch(epoch: string) {                           // ← 函数头
    const oldEpoch = this._runner.epoch
    if (epoch === oldEpoch) return                             // ⑨ 指纹没变 → 什么都不做
    this._runner.epoch = epoch
    if (this.inertia) return                                   // ⑩ 有装载/卸载在路上 → 交给它收尾
    this._updateState(() => {
      if (epoch !== INACTIVE && oldEpoch === INACTIVE) {
        this.inertia = this._reload()                          // ⑪ 从"不齐"到"齐" → 装载
        return FiberState.LOADING
      } else {
        this.inertia = this._unload()                          // ⑫ 反向（含换人）→ 卸载后重装
        return FiberState.UNLOADING
      }
    })
  }
```

- **⑧ 指纹为什么用 uid 而不是值**：uid 能表达"**换人了**"——同一个服务名改由另一个 fiber 提供时 uid 变了，指纹就变了，于是依赖方**自动重装**（⑫）。这也是 DSH 客户端热替换依赖级联的原理：`.agents/notes/implemented/architecture/2026-07-23-client-plugin-loading-model.zh.md` 第 95 行原文「fiber 的激活纪元串接着它各服务提供方的 uid，因此替换 connection 等基础 provider 的 fiber 时，每个依赖方都会经 cordis 本身重新装载」。
- **⑨⑩ 两个提前返回**：指纹没变不做事；有 `inertia` 在路上就不插手（由它自己收尾，见 §8.2 末尾与 §8.3 末尾）。
- **⑪⑫ 是唯一的状态跃迁入口**：`LOADING` 与 `UNLOADING` 只在这里产生。

### 8.2 装载：让出一次微任务，再跑插件代码

`vendor/cordis/src/fiber.ts` 第 42–49 行 + 第 641–673 行（**两段接续**：先给 `resolveConfig` 这个模块级函数的文档注释，再给 `_resolveConfig` 与 `_reload` 的完整实现——② 调用的就是前者，缺了它读者不知道 ② 在做什么）：

```ts
// （下面是 ② 所调用函数 resolveConfig 的契约，摘自它自己的 JSDoc（同文件第 42–49 行）：
//   无 schema 时原样返回，校验不过抛 ValidationError；`@param` 行已省）
  private _resolveConfig(config: any) {                        // ← 函数头
    config = this.context.waterfall(this, 'internal/config', config, () => config)   // ① 配置瀑布
    return this.runtime ? resolveConfig(this.runtime, config) : config              // ② schema 校验
  }

  private async _reload() {                                    // ← 函数头
    this.store = { ...this._store }                            // ③ 把依赖快照公开出去
    const oldEpoch = this._runner.epoch
    try {
      await Promise.resolve()                                  // ④ 让出一次微任务
      // A disposer queued before this checkpoint may already have invalidated
      // the load. Do not run plugin code for a stale epoch; the state update
      // below will drain any effects collected while the fiber was PENDING.
      if (this._runner.epoch === oldEpoch) {                   // ⑤ 复查：指纹没被作废
        this.config = this._resolveConfig(this._config)         // ⑥ 解析 + 校验配置
        await this._execute(this._runner)                       // ⑦ 真正跑插件（§7.2 那套分流）
        this._error = undefined
      }
    } catch (reason) {
      // impl guarantees that the error is non-null (?)
      this.ctx.logger.error(reason)                             // ⑧ 出错：记日志 + 记错误 + 纪元失效
      this._error = reason
      this._runner.epoch = INACTIVE
    }
    this._updateState(() => {
      if (this._runner.epoch === oldEpoch) {
        this.inertia = undefined                                // ⑨ 装载成功：状态将由 _getState() 算出 ACTIVE
      } else {
        this.inertia = this._unload()                           // ⑩ 期间被作废：立刻卸载
        return FiberState.UNLOADING
      }
    })
  }
```

- **① `internal/config` 是一个 waterfall 事件**（声明在 events.ts 第 339 行）：监听方可以**改写**这一次的配置。**HMR / 配置组合走的就是这个口子（2.6 / 2.7）。**
- **② `resolveConfig`**：`runtime.Config` 存在就跑 standard-schema 校验，失败抛 `ValidationError`（fiber.ts 第 50–62 行、第 19–36 行）。**root fiber 没有 runtime，所以跳过校验。**
- **④ `await Promise.resolve()` 不是装饰**：它把"开始跑插件代码"推迟一个微任务；作者注释（第 651–653 行）说明理由是"在这之前排队的 disposer 可能已经把这个装载作废了"——**所以第 ⑤ 行的复查是必须的，不能省。**
- **⑧ 出错不等于崩溃**：错误记进 `_error`（`await()` 时会重抛，见 §6.2 ⑥⑦），fiber 随后被算作 `FAILED`（`_getState()` 第 576 行）。
- **⑨ 状态是怎么变成 ACTIVE 的**：`_updateState(callback)` 里若 callback 没返回状态，就调 `_getState()`（第 574–579 行）：`uid===null → DISPOSED`、有 `_error → FAILED`、`epoch !== INACTIVE → ACTIVE`、否则 `PENDING`。**所以 ACTIVE = "依赖指纹有效且没出错"**，不是某个布尔开关。

### 8.3 卸载：逆序、逐个兜错

`vendor/cordis/src/fiber.ts` 第 675–696 行 + 第 712–717 行（**两段接续**：`_unload` 函数体未删节；另摘 `restart()` 的 JSDoc，因为它写明了这条路径的契约——`_unload` 自身没有文档注释）：

```ts
  /**
   * Dispose and immediately reload this plugin with its current config.
   *
   * @returns a promise resolving once the reload settled.
   * @throws {CordisError} `INACTIVE_EFFECT` when the fiber is already disposed.
   */
  // （上面 6 行来自同文件第 712–717 行，是 _unload 的公开入口 restart() 的 JSDoc；
  //   _unload 自身没有文档注释，贴它是为了让读者知道"卸载 + 立即重装"这条路径的契约）
  private async _unload() {                                    // ← 函数头
    await Promise.all(this._disposables.clear().map(async (dispose) => {   // ① clear() 返回【逆序】的副本
      try {
        await composeError(async (info) => {
          await Promise.resolve()
          info.error = new Error()
          await runDisposable(dispose)                          // ② 跑一个 disposer
        }, this._runner.getOuterStack)
      } catch (reason) {
        this.ctx.logger.error(reason)                          // ③ 谁抛错谁自己进日志
      }
    }))
    this.store = undefined
    this._updateState(() => {
      if (this._runner.epoch === INACTIVE) {
        this.inertia = undefined                               // ④ 卸载完成
      } else {
        this.inertia = this._reload()                          // ⑤ 期间又被激活 → 重新装载
        return FiberState.LOADING
      }
    })
  }
```

- **① "逆序"的确切来源是 `DisposableList.clear()`**：utils.ts 第 27–31 行——先取出全部值、清空表、再 `values.reverse()`。**所以"后注册的先撤销"这条纪律在数据结构这一层就保证了**（顺序语义的完整讲解在 2.3）。
- **③ 一个 disposer 抛错不会阻断其余卸载**：每个 disposer 都包在独立 `try/catch` 里，错误只进 logger——**所以卸载是"尽力而为"的，不能靠它做事务**（标注为推断：源码只保证"继续卸载"，没有回滚机制）。
- **④⑤ 与 §8.2 的 ⑨⑩ 呼应**：装载与卸载互为对方收尾路径的兜底——`_setEpoch` 遇到 `inertia` 会提前返回（§8.1 ⑩），把"接下来该装还是该卸"交给这里。

### 8.4 状态跃迁时通知谁

`vendor/cordis/src/fiber.ts` 第 574–595 行（`_getState` 与 `_updateState` 两个私有方法连读，未删节——状态是**算出来的**，所以必须把 `_getState` 一起读）：

```ts
  private _getState() {                                        // ← 函数头（第 574 行）
    if (this.uid === null) return FiberState.DISPOSED          // ① 编号被清 → 已卸载
    if (this._error) return FiberState.FAILED                  // ② 有错 → 失败
    if (this._runner.epoch !== INACTIVE) return FiberState.ACTIVE   // ③ 指纹有效 → 已激活
    return FiberState.PENDING                                  // ④ 否则：等依赖
  }

  private _updateState(callback: () => void | FiberState) {    // ← 函数头（第 581 行）
    const oldState = this.state
    this.state = callback() ?? this._getState()                // ⑤ callback 没返回状态就用 _getState() 算
    if (oldState === this.state) return                        // ⑥ 状态没变：安静返回
    // FIXME internal/fiber-info
    this.context.emit('internal/status', this, oldState)        // ⑦ 广播状态变化（events.ts 第 333 行）

    // only notify changes between ACTIVE and NON-ACTIVE states
    if (oldState !== FiberState.ACTIVE && this.state !== FiberState.ACTIVE) return   // ⑧ 只在跨越 ACTIVE 时通知
    for (const key of Reflect.ownKeys(this.ctx.reflect.store)) {
      const impl = this.ctx.reflect.store[key as symbol]
      if (impl.fiber !== this) continue                         // ⑨ 只看【我提供的】服务
      this.ctx.reflect.notify([impl.name])                      // ⑩ 通知依赖这些服务的 fiber
    }
  }
```

- **①–④ 是"状态是算出来的"这句结论的落点**：`DISPOSED` / `FAILED` / `ACTIVE` / `PENDING` 四个状态**没有一个是布尔开关**，全由 `uid`、`_error`、`epoch` 三个事实推出。所以 §8.1 的 ⑪⑫ 只负责"发起装载/卸载"，最终状态由这里决定。
- **⑧ 是"提供方先 ACTIVE、依赖方才 LOADING"的机制**：只有**跨入或跨出** `ACTIVE` 才触发通知；`PENDING→LOADING` 这种中间跃迁只广播事件（⑦）、不打扰任何人。
- **⑨⑩ 通知的粒度是"服务名"**：`notify`（reflect.ts 第 314–336 行）遍历 registry 里**所有** fiber，命中 `name in fiber.inject` 的才重新 `_checkImpl` + `_refresh`——**所以通知的代价与已登记的 fiber 总数成正比**（"插件越多，一次激活越慢"是**标注为推断**：源码只说明遍历范围，未做性能实测）。
- **② 与 §7.3 ⑦ 是同一族事件**：`internal/plugin`（登记/注销）+ `internal/status`（状态）——Loader 与 inspector 都挂在这两个事件上。

### 9.2 `provide` 内部：登记 + 撤销

`vendor/cordis/src/reflect.ts` 第 277–305 行（`provide` 全函数，未删节）：

```ts
  provide(name: string, value?: any, check?: () => boolean) {  // ← 函数头
    return this.ctx.fiber.effect(() => {                       // ① 整个登记被包成一个 effect
      if (!this.props[name]) {
        this.props[name] ??= { type: 'service' }                // ② 声明属性类型
      } else if (this.props[name].type !== 'service') {
        throw new Error(`property "${name}" is already declared as ${this.props[name].type}`)
      }
      this.props[name] = { type: 'service' }

      this.ctx.root[symbols.isolate][name] ??= Symbol(name)     // ③ 隔离键在 root 上分配【一次】
      const key = this.ctx[symbols.isolate][name]
      const impl: Impl = { name, value, fiber: this.ctx.fiber, check }
      if (this.store[key]) {
        throw new Error(`service "${name}" has been registered at <${this.store[key].fiber.name}>`)   // ④ 撞名即抛
      }
      this.store[key] = impl                                   // ⑤ 写全局服务表
      this.ctx.fiber.store![name] = impl                       // ⑥ 同时写【自己】 fiber 的快照
      if (this.ctx.fiber.state === FiberState.ACTIVE) {
        this.notify([name])                                    // ⑦ 自己已激活 → 立刻通知依赖方
      }
      return async () => {                                     // ← disposer
        delete this.store[key]                                 // ⑧ 只删全局表
        const fibers = this.notify([name])
        await Promise.allSettled(fibers.map(fiber => fiber.await()))
        // ensure self access before dependencies cleanup
        delete this.ctx.fiber.store![name]                     // ⑨ 最后才删自己的快照
      }
    }, `ctx.provide(${JSON.stringify(name)})`)                 // ⑩ 诊断标签
  }
```

- **① 服务是"副作用"不是"字段"**：整段登记被 `fiber.effect()` 包住，返回的 `async () => {...}` 就是撤销函数，被收进该 fiber 的 `_disposables`。**所以"服务随 fiber 卸载而消失"不需要额外代码。**
- **② 属性类型声明与撞名检查**：`reflect.props` 里一条属性要么是 `service` 要么是 `accessor`；已被声明成 `accessor` 时这里直接抛错（§9.3 ⑤ 讲 accessor 从哪来）。
- **③ `??=` 出现在 `ctx.root` 上**：隔离键是**整个应用分配一次**的，子 ctx 只是在自己的隔离表里指向同一个 symbol（这就是 §5.2 ④ 那张"原型链上的子表"的用途）。
- **④ 撞名抛错的粒度是"同一个隔离键下"**：不同 isolate scope 可以同名（2.5 的主题）。
- **⑥ 就是 §0.2 第 4 件事**：提供方**立刻**把服务写进自己的 store，所以提供方自己的 ctx 一定读得到（实测 §7 第 1 段 A1 项）。
- **⑧⑨ 的顺序有注释**：`ensure self access before dependencies cleanup`——**先撤销别人对它的访问，再撤销自己的**，避免卸载过程中有人读到半死的服务。
- **⑩ 标签出现在 `ctx.getEffects()` 的诊断树里**（fiber.ts 第 568–572 行）。

### 9.3 `ctx.x` 为什么能直接拿到服务

`vendor/cordis/src/reflect.ts` 第 133–171 行（**两段接续**：先给类头与 `handler` 的第一行，再给 `get` trap 全段，未删节；同一 `handler` 里的 `set`（第 173–197 行）与 `has`（第 199–205 行）是"写"与"判存在"，与本节无关，此处不摘）：

```ts
export class ReflectService {                                  // ← 类头（第 133 行）
  /** Proxy traps implementing service resolution for every context object. */
  static handler: ProxyHandler<Context> = {                    // ← 块开头
    get: (target, prop, ctx: Context) => {                     // ① 三个参数：裸对象 / 属性名 / 代理
      if (isSpecialProperty(prop)) {
        return Reflect.get(target, prop, ctx)                  // ② 特殊键直通
      }
      if (Reflect.has(target, prop)) {
        return getTraceable(ctx, Reflect.get(target, prop, ctx))   // ③ 自有/继承属性优先
      }

      const error = new Error(`cannot get property "${prop}" without inject`)   // ④ 预备错误

      try {
        const def = target.reflect.props[prop]
        if (def?.type === 'accessor') {
          return def.get.call(ctx, ctx[symbols.receiver], error)        // ⑤ accessor：mixin 出来的方法
        }

        if (!ctx.fiber.runtime) return ctx.reflect.get(prop, false)     // ⑥ root ctx：宽松读取
        return ctx.events.waterfall('internal/get', ctx, prop, error, () => {
          const key = target[symbols.isolate][prop]                     // ⑦ 本层的隔离键
          let fiber = (ctx[symbols.shadow] as Context ?? ctx).fiber
          while (true) {                                                // ⑧ 沿 fiber 父链上溯
            const impl = fiber.store?.[prop]
            if (impl) return getTraceable(ctx, impl.value)               // ⑨ 命中：返回实现
            if (prop in fiber.inject) {
              error.message = `cannot get required service "${prop}" in inactive context`
              throw error                                                // ⑩ 声明了依赖但没就绪 → 抛
            }
            if (!fiber.runtime) throw error                              // ⑪ 上溯到 root 仍没有 → 抛
            if (fiber.parent[symbols.isolate][prop] !== key) throw error  // ⑫ 隔离键变了 → 抛
            fiber = fiber.parent.fiber                                   // ⑬ 继续往上
          }
        })
      } catch (e: any) {
        throw e === error ? enhanceError(e) : e                          // ⑭ 只给"自己的"错误补调用栈
      }
    },
```

- **② 什么算"特殊键"**：定义在本文件第 80–91 行的 `isSpecialProperty`——**symbol 键、`prototype` / `then` 两个保留字、纯数字串、`_` 开头**。**理由：这些名字不会被当作服务名**（框架自身的 symbol 与 `then` 的 Promise 协议必须直通）。
- **③ `Reflect.has` 会沿原型链找**：所以四个内置服务（root 的自有属性）在任何子 ctx 上都读得到——**实测第 1 段**：子 ctx 读 `ctx.registry/events/logger` 都成功，`Object.hasOwn(Object.getPrototypeOf(childCtx), 'registry') === true`。
- **⑤ accessor 分支**：`ctx.on`、`ctx.plugin`、`ctx.effect`、`ctx.get` 这些**不是服务**，而是 mixin 装的 accessor——ReflectService 构造函数第 219–222 行把 `reflect/fiber/registry/events` 的若干键 mixin 出来，accessor 本体的实现是第 364–390 行的 `mixin()`。实测：`Object.hasOwn(ctx,'on') === false`、`'on' in ctx === true`、`ctx.reflect.props.on === {"type":"accessor"}`。
- **⑥ 这是"root 无需 inject"的源码原因**：root fiber 的 `runtime` 是 `null`（§5.1），于是直接走 `ctx.reflect.get(prop, false)`——`strict=false` 表示**不要求提供方 ACTIVE**（reflect.ts 第 233–243 行）。
- **⑦⑧⑫⑬ 查找规则**：先取**本层**的隔离键，然后沿父链逐级查 `fiber.store`；一旦某一级父级的隔离键与起点不同就**停止**（不跨隔离作用域误读）。这就是 §3 第 12 步"按隔离键 + 沿父账本上溯"。
- **⑨ 与 ⑩ 的区别很关键**：`fiber.store` 是"**我依赖的实现快照**"，它有两个写入者——`_checkImpl` 按 `inject` 写入（§8.1 ⑤），`provide` 写入**自己提供**的服务（§9.2 ⑥）。因此"提供方自己的 ctx 读自己提供的服务"走的是 ⑥ 之外的正常路径并**必定成功**（实测 A1）；而"清单里没有这个名字、父链上也没有"则走 ⑪ 抛出 `cannot get property ... without inject`。
- **⑭ `enhanceError`**：只对"本 trap 自己造的那条 `error`"改写调用栈（reflect.ts 第 73–78 行），别人的错误原样抛。

**实测：三种"读不到"的确切行为**（脚本直接加载 `vendor/cordis/src/index.ts`，跑法与 §7 相同）

```
R1 root ctx 读一个从未被提供过的名字        -> undefined
P2 PENDING fiber 读"清单里有、但没就绪"      -> THROWS: cannot get required service "neverSvc" in inactive context
P3 子 ctx 读"清单里没有"的未知名字           -> THROWS: cannot get property "other" without inject
```

→ 所以 §3 第 12 步那句"找不到就抛错"有一个**确切前提**：**只有 root ctx 会安静地返回 `undefined`**（第 ⑥ 行的宽松分支）。插件自己的 ctx 一定抛错，只是错误文案分两种：**清单里有 → `cannot get required service ... in inactive context`；清单里没有 → `cannot get property ... without inject`**。

> **另一个必须记住的边界**（实测 §7 第 6 段）：`provide` 的 disposer 只删 `reflect.store[key]`（第 ⑧ 行），**不删 `reflect.props[name]`**；而 `has` trap 判的是 `props`（第 199–205 行）。后果：**卸载后 `'服务名' in ctx` 仍为 `true`，但读出来是 `undefined`**。→ 做存在性判断要**读值**，不要只读 `in`。

### Q1 `ctx` 是什么？

→ 它是 `Context` 实例的 **`Proxy`**：`new Context()` 内部执行 `const self = new Proxy(this, ReflectService.handler)` 并 `return self`（context.ts 第 74、83 行）；每个插件拿到的是 `parent.extend({ fiber })` 造出的**子 context**（fiber.ts 第 236 行）。所以"ctx"同时是三种东西：**依赖容器**（服务名 → 实现的解析器，§9.3）、**效果宿主**（`effect`/`on`/`plugin` 都挂在当前 fiber 上）、**事件入口**（`emit`/`waterfall`/…）。`docs/cordis-api/context.zh.md` 第 12 行的定位与源码一致。

|---|---|---|---|
| 插件登记表 | `ctx.registry._internal`（registry.ts 第 197 行） | 归一后的 **callback** / `Plugin.Runtime` | "这个插件装了吗？有几个 fiber？" |
| 服务登记表 | `ctx.reflect.store`（reflect.ts 第 209 行） | **isolate symbol** / `Impl { name, fiber, value, check }`（第 116–125 行） | "这个服务名现在由谁实现？" |

→ 写入点分别是 `plugin()` 里的 `this._internal.set(callback, runtime)`（registry.ts 第 327 行）与 `provide()` 里的 `this.store[key] = impl`（reflect.ts 第 292 行）。

### Q3 `Fiber` 代表什么？

→ 代表**一次插件应用**（一次 `ctx.plugin()` 调用），**不是插件本身**：同一插件可有多个 fiber，共享同一条 runtime（`Runtime.fibers` 是 `DisposableList<Fiber>`，registry.ts 第 140 行；实测 `registry.size=1 / fibers.length=2`，见 §7 第 2b 段）。它承载：状态机（fiber.ts 第 147–154 行）、已校验的 config、依赖实现快照 `store`、以及全部 disposer；`uid` 是它在 registry 内的唯一编号——root 为 `0`，每次读取 `registry.counter` 自增（第 206–209 行），dispose 后置 `null`（第 268 行）。

### Q4 四个对象各自是什么？它们之间是什么关系？

→ **Context** 是依赖容器兼代理对象（context.ts 第 42–84 行）；**Registry** 是插件登记表，把三种形态归一成 callback 并为每个 callback 存一条 runtime（registry.ts 第 195–197、222–228 行）；**Fiber** 是一次插件应用的生命周期实例（fiber.ts 第 184–210 行）；**Service** 是服务基类，`super(ctx, name)` 即 `ctx.reflect.provide`（service.ts 第 42–59 行）。
→ 关系是**单向链路**（§2.1 图）：root `Context` 构造时装好 `registry` 与 root `Fiber` → `ctx.plugin()` 时 Registry 建 runtime 并 `new Fiber` → Fiber 用 `parent.extend({ fiber })` 得到自己的子 Context 并执行插件 → 插件（Service 子类）在 callback 里调 `provide` 把服务挂到 `reflect.store` → 状态转 ACTIVE 时通知依赖方。**Context 不会自己创建 Fiber，Fiber 也不登记插件**：两者各由上一层负责（`registry.plugin` 与 `Service` 构造函数）。

### Q5 `ctx` 用属性访问直接拿服务，中间用了什么语言机制？

→ 四条，全部在 §9.3 那块源码里：

1. **`Proxy` trap 拦截属性读**：`new Proxy(this, ReflectService.handler)`（context.ts 第 74 行），实现在 reflect.ts 第 135–171 行；
2. **服务名 → 实现**存在 `reflect.store`，键是 `ctx.root[symbols.isolate][name] ??= Symbol(name)`（reflect.ts 第 286 行）——**用 symbol 作键**，避免撞名；
3. **查找沿原型链 + fiber 父链**：子 ctx 由 `Object.create` 造出（context.ts 第 101 行），trap 里 `while (true)` 沿 `fiber.parent.fiber` 上溯查 `fiber.store`（reflect.ts 第 155–166 行），并用隔离键做"不跨作用域"的门禁；
4. **读到的值再包一层 `Proxy`**：`getTraceable` → `createTraceable`（utils.ts 第 117–125、165–218 行），把方法调用里的 `this.ctx` 重绑到**调用方**。

→ 附带两条：`ctx.on` / `ctx.plugin` / `ctx.effect` 这类**不是服务**而是 `mixin` 装的 accessor（reflect.ts 第 219–222 行与第 364–390 行，`has` trap 判 `props`）；root ctx 因为 root fiber 的 `runtime === null` 而走 `strict=false` 分支（reflect.ts 第 152 行），所以不 inject 也能读。

### Q6 一个插件从被登记到可用，中间发生了什么？

→ 七步（与 §2.2 动态图一一对应）：

1. Loader 动态 `import` 模块并 `unwrapExports` 归一 ESM/CJS/default（loader `config/entry.ts` 第 226–233 行、`index.ts` 第 200–208 行）；
2. `registry.plugin()` 用 `resolve` 归一 callback，按 callback 复用或新建 runtime（registry.ts 第 316–328 行）；
3. `new Fiber`：分 uid、`parent.extend({fiber})`、把 dispose 注册成父 fiber 的 effect、发 `internal/plugin`（fiber.ts 第 235–302 行）；
4. 依赖判定 `_checkImpl` / `_refresh`，缺依赖则停在 `PENDING`（fiber.ts 第 597–623 行）；
5. 全部就绪 → `_setEpoch` → `_reload()`：让出一次微任务、复查 epoch、`internal/config` waterfall + schema 校验、执行 callback（fiber.ts 第 625–673 行；校验在第 50–62 行）；
6. 进入 `ACTIVE` 时 `_updateState` → `reflect.notify` 遍历所有 fiber，把 `name in fiber.inject` 的依赖方唤起（fiber.ts 第 588–594 行、reflect.ts 第 314–336 行）；
7. 此后服务可用、disposer 已挂在父 fiber 上；卸载时逆序释放、`uid` 置 `null`、runtime 空了就 `registry.delete`（fiber.ts 第 265–297、675–696 行）。

→ 实测事件序列正是这个顺序（§7 第 3 段），且实测到**依赖方 callback 运行时自己的状态还是 `LOADING`**，跑完才 `ACTIVE`。

### Q7 三种插件形态分别怎么被处理？

→ 全部在 `RegistryService.resolve()` 归一（registry.ts 第 222–228 行）：函数（含 class）等价于自身；`{apply}` 等价于 `plugin.apply`；其余 `undefined` → `plugin()` 抛错。之后只有两处分叉：

| 形态 | 归一成的 callback | 执行方式 | runtime.name |
|---|---|---|---|
| 函数 `apply(ctx, config)`（含 ESM 命名空间） | 函数自身 | `runtime.callback(ctx, config)`（fiber.ts 第 259 行） | `plugin.name`（具名导出/具名函数可得） |
| `{ apply }` 对象 | `plugin.apply` | 同上 | 方法名就是 `'apply'` → 置 `undefined`（registry.ts 第 324–325 行），除非显式写 `name` |
| `Service` 子类 / 任意 class | 构造函数自身 | `isConstructor` 为真 → `new callback(ctx, config)`，再跑 `[symbols.initHooks]`、`[symbols.init]`（fiber.ts 第 251–257 行） | 类名 |

→ **模块命名空间对象也走对象那一支**：它有 `apply` 命名导出就被 `isApplicable` 命中（registry.ts 第 8–10 行），有 `name` 命名导出就成了 `runtime.name`。**Service 子类不额外走特殊路径**：它的"提供服务"是构造函数里 `super()` 调 `provide()` 的副作用（service.ts 第 57 行）；`static inject` / `static Config` 只是被 registry / fiber 当普通字段读（registry.ts 第 326、330 行）。
→ 元数据读取位置：`plugin.inject`（`Inject.resolve`，registry.ts 第 71–88 行 + 第 330 行）、`plugin.Config`（第 326 行 → fiber.ts 第 50–62 行校验）、`plugin.provide`（service.ts 第 43 行）、`plugin.intercept`（`Plugin.Base`，registry.ts 第 110 行）。

### Q8 服务卸载后为什么 `'name' in ctx` 还是 `true`？

→ 因为 `provide` 的 disposer 只删了 `reflect.store[key]`（reflect.ts 第 298 行），**没有删 `reflect.props[name]`**（它在第 279–284 行被写死）；而 `has` trap 判的是 `props`（第 199–205 行）。实测：dispose 后 `props.tmpSvc` 仍是 `{"type":"service"}`、`ctx.get('tmpSvc')` 变成 `undefined`、`'tmpSvc' in ctx` 仍为 `true`。
→ **判据要用值，不要用 `in`。**

### Q9 为什么 root ctx 读服务不需要 inject，插件 ctx 就需要？

→ 因为 get trap 里有一句 `if (!ctx.fiber.runtime) return ctx.reflect.get(prop, false)`（reflect.ts 第 152 行）：root fiber 的 `runtime` 是 `null`（context.ts 第 77 行 + fiber.ts 第 320 行），走"宽松读取"（`strict=false`）；普通 fiber 有 runtime，就必须在 `fiber.store` 里命中，否则按情况抛两种错之一（第 155–166 行，实测见 §9.3 末尾）。`strict` 的差别在 `_getImpl`：`strict=true` 要求提供方 fiber 处于 `ACTIVE`（reflect.ts 第 237–243 行）。
→ 另一条容易误解的：**root ctx 读"不存在的服务名"也走宽松路径**，所以它安静地返回 `undefined` 而不抛错——这是 `ctx.get(...)` 与插件 ctx 的直接属性读取在行为上的真实差别。
