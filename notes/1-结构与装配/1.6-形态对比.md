## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：把"DSH 有几种产品形态、它们之间差什么"讲死——**每个形态层加了哪些行、相对 base 少了什么、这些差异写在哪里**。
**不是**：patch 的完整语法（那是 `1.4`）、组合顺序的完整推导（那是 `1.2`）、preset 与 realm 的机制（那是 `2.5` 与第三编）。

### 0.2 现在只要记住这 4 件事

1. **六个 bundle 分成两类**：`dsh-base` 是"共享第一层"，其余五个是"形态层"；四个形态层（web-app / headless / sdk-app / acp-app）**只做两件事**——按 `id` 改写 base 的行、插入自己形态专有的行。唯一例外是 `sdk-minimal`：它**不叠 base**，自己就是完整配置树。
2. **"相对 base 少了什么"几乎都是 `disabled: true`**，而不是删行。base 是共享的，删行会在组合顺序变化时**悄悄复现**；禁用是显式且可审查的。
3. **同一内核长出多形态的机制只有三个变量**：`profile`（选出 bundle 列表）→ `bundle`（声明有序的 patch 文件列表）→ `patch`（按 `id` 覆盖 / insert）。**内核本身没有"形态"这个概念**，形态全部存在于 patch 文档里。
4. **桌面不是第六个 template**。`PROFILE_TEMPLATES` 只有 5 个键（acp / web / headless / sdk / sdk-minimal）；Desktop 复用 **web 的 bundle 列表**，靠 `profileContext.name === 'desktop'` 之类的表达式差异长成另一个形态。

### 0.3 明确授权：这些现在不用管

- **preset / isolate / realm** —— 它们决定"每个会话挂哪套 agent 平面"，属 `2.5` 与第三编。本课只在 §4.5 与附录 C 点一下"Web 把 agent 平面让给了 preset"这个**事实**，不解释 preset 怎么工作；
- **`!!js` 表达式什么时候求值** —— 属 `2.6`。本课只用到"它是写在 YAML 里的表达式，能把环境变量与 `ctx` 读进来"这个程度；
- **HMR（热重载）** —— 属 `2.7`。本课只记"headless / sdk / acp 显式禁用它，sdk-minimal 根本不含它"；
- **兼容性预检**（为什么某些 bundle 被跳过）—— 属 `2.9` / `4.5`。

判断标准只有一条：**只要你能说清"这一行是 base 给的、还是某个形态层加的/改的"，就够了。**

### 0.4 本课依赖 1.1 / 1.2 的词汇

`profile` / `bundle` / `patch` / 条目 `entry` / 层 `layer` 已由 `notes\1-结构与装配\1.1-名词与分层.md` 定义；`override`（覆盖）与 `insert`（插入）的完整语义由 `notes\1-结构与装配\1.2-装配顺序.md` 给出。**本课不重复这两篇的内容**，只点它们在本课里的用法。

## 1. 最小词汇表（本课新增的 6 个词）

| 词 | 大白话 | 在源码/配置里的样子 |
|---|---|---|
| **形态 / surface** | 一个**对用户可见的产品外形**（CLI 一次性任务、浏览器 GUI、桌面应用、SDK、ACP）。它是"叠了哪些层"的结果，不是代码里的一个类型 | 文档里说"表层"；源码里没有 `surface` 这个键，只有 profile 名与 bundle 列表 |
| **形态层** | 只负责"在一个共享底座上长出某个形态"的那一层 patch | `dsh-web-app` / `dsh-headless` / `dsh-sdk-app` / `dsh-acp-app` 四个包 |
| **`disabled: true`** | 一条**显式的禁用覆盖**：不改行、不删行，只把那一行关掉 | 顶层 `- id: xxx` + `disabled: true`（**没有** `name`、**没有** `config`） |
| **平台门控** | 同一件事按操作系统挂不同实现：一行在 Windows 上禁用、它的孪生行在非 Windows 上禁用 | `disabled: !!js process.platform === 'win32'` 与取反的孪生行 |
| **`!!js` 表达式** | 写在 YAML 里的**表达式**，在条目激活时求值，因此能读环境变量与 `ctx` | `!!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'` |
| （复用）**`id`** | 一行的**稳定身份**，也是 patch 唯一的定位手段 | `- id: tool-bash`；改写 base 的行必须写对 `id` |

> ⚠️ 表里的 `preset` **没有**收进来——它属于 `2.5` 与第三编，本课只在 §4.5 与附录 C 提到它的"存在"，不当作定义的一部分（R1）。

## 2. 先建立画面

### 2.1 从属关系图（静态：谁是谁的一部分）

```
profile（= $DSH_HOME\profiles\<名字>\package.json 里的 dsh.profile.bundles）
│
├─ 第 1 层：dsh-base 的 patch            ← 共享第一层，只有一个 insert、94 行
│     · 模型适配器、工具、持久化、沙箱与审批、设置、凭据、遥测
│     · 它给每一行都起了稳定的 id（patch 就是靠 id 找到这些行的）
│
└─ 第 2 层：某一个形态层的 patch          ← 只做两件事
      ├─ 按 id 覆盖 base 的行（override）  → 改值、改 persona、禁用它
      └─ insert 自己专有的行               → 宿主行 / 协议服务器行 / 浏览器行
          │
          ▼
      组装结果 = 一棵插件树 = 一个产品形态

例外（第 5 个 template）：
sdk-minimal 的列表里**只有它自己**      → 它的那一个 insert 就是完整树（27 行），没有 base 层
桌面（不是 template）：               → 用 web 的列表，靠表达式差异长出另一个形态
```

### 2.2 组装链（动态：先后顺序）

```
空条目列表（profile 目录里的 cordis.yml = []）
   │
   ▼  ① 各 bundle 的 patch，按 dsh.profile.bundles 的书写顺序
       base 的 insert（94 行）          ← 形态层能按 id 改它，就是因为它先叠
       ▼
       形态层的 patch（覆盖 + insert）
   │
   ▼  ② profile 自己的 cordis.patch.yml
   ▼  ③ home 级 patch（$DSH_HOME\cordis.patch.yml，不存在则跳过）
   ▼  ④ 各 --patch overlay（按命令行顺序）
   │
   ▼
最终条目列表 → 挂载 → 运行时插件树
```

> ①→④ 的权威表述与逐层源码在 `1.2`；本课只用到"**base 在前、形态层在后**"这一条。

### 2.3 大白话版：同一份底座怎么长出六种产品

**完全不用上面的术语**（来源：`docs\architecture.zh.md` 第 25–29 行 + 六个 patch 文件的头注释；这里只做白话转述）：

1. 有一份"人人都要的东西"清单：怎么连模型、有哪些工具、会话记在哪、写文件要不要问一声。这份清单被写成一张**很大的插入表**（94 行），它就是 `dsh-base`。
2. 每个产品形态**不重写这份清单**，而是拿它当起点。
3. 想要"跑一次就退出、不开端口、不要浏览器"的产品，就把其中"模型自我介绍那几句话"改成自己的一版、把"临时工具呈现模式"改成同一个开关，再加两行：一个负责读命令行、一个负责跑任务。这就是 headless，一共加了 2 行、改了 3 行。
4. 想要"只给自动化程序用、走 stdio 协议"的产品，做法一样：加两行（一个启动器、一个协议服务器），并且**关掉"让模型自动起标题"那一行**——因为这个协议根本没有地方显示标题，不该多花一次模型请求。ACP 与 SDK 都是这个套路。
5. 想要浏览器界面的产品，动作最大：加 87 行（Web 宿主行 + 一串浏览器插件名册 + 一个 preset 注册表），同时**把 24 行"作用在单个 agent 上的工具行"关掉**，交给"每个会话各挂一套"的机制去提供。
6. 还想要一个"什么额外东西都不要"的极简 SDK：这个产品**不拿第一份清单当起点**，而是自己从头写一份只有 27 行的完整清单——不需要的东西不是"被关掉"，而是**从头到尾没写**。
7. 还有一类特殊需求：桌面应用。它没有自己的第六份清单，而是**复用浏览器那份的两行列表**，只在几个地方写"如果是桌面，就打开这个、否则关掉"。
8. 所以"DSH 有几种形态"的答案是：**形态的数量 = profile 列表的组合数，不是代码里的分支数。**

## 3. 结论先行（本课的骨架结论，逐条带出处）

1. **六个 bundle 分成两类**：`dsh-base` 是"共享第一层"，其余五个是"形态层"。四个形态层（web-app、headless、sdk-app、acp-app）**只做两件事**——按 `id` 改写 base 的行、插入自己形态专有的行；唯一例外是 `sdk-minimal`，它**不叠 base**，自己就是完整配置树。
   出处（文档）：`docs\architecture.zh.md` 第 25 行；`packages\bundle\README.zh.md` 第 12 行。

   出处（作者原文）：`packages\bundle\web-app\cordis.patch.yml` 第 455–457 行（源码见 §4.3 块 9）。

这一节是本课的重心：每个机制类知识点旁边就给出源码，粒度以"能自解释"为准。
**每块上方的 `文件路径 第 A–B 行` 就是定位坐标**；块内凡有省略，都用注释写明省了哪些行、为什么省。

### 4.1 bundle 是怎么声明"我有哪几个 patch 文件"的

`bundle` 与 `patch` 的对应关系不是约定，而是**包自己的 `package.json` 里写死的字段**。多数 bundle 只有一个 patch 文件，`dsh-web-app` 有五个——五个文件都是**一个 bundle 的一层**，不是一个 bundle 的五个层。

**块 1：一个 bundle 声明五个 patch 文件**

`packages\bundle\web-app\package.json` 第 30–52 行

```json
  "files": [
    "lib/index.js",
    "lib/startup.js",
    "cordis.patch.yml",
    "presets/standard.patch.yml",
    "presets/ptc.patch.yml",
    "presets/minimal.patch.yml",
    "presets/cordis.patch.yml",
    "lib/public-url-*.js",
    "lib/types/**/*.d.ts"
  ],
  "license": "MIT",
  "dsh": {
    "bundle": {
      "patch": [
        "./cordis.patch.yml",
        "./presets/standard.patch.yml",
        "./presets/ptc.patch.yml",
        "./presets/minimal.patch.yml",
        "./presets/cordis.patch.yml"
      ]
    }
  },
  // （第 53 行起是 "dependencies"：与本知识点无关，此处省略）
```

按块讲解：

- **做什么**：声明"这个 bundle 由哪些 patch 文件组成"。`files` 是 npm 打包白名单（**发布时**要带上这些文件），`dsh.bundle.patch` 是 **DSH 自己的字段**（npm 不认识它），两者列的是同一批文件，但职责不同——前者管分发，后者管组装。
- **与哪个知识点相关**：§3 结论 3 的中间那个变量——`bundle` 决定"贡献哪些 patch 文件、按什么顺序"。
- **为什么这么写**：四个 `presets\*.patch.yml` **各自是一条 preset 声明**（附录 C），它们必须排在主 patch **之后**——因为主 patch 的最后一段（第 579–583 行）插入了 `agent-preset-registry`，而 preset 声明要插进这个注册表管辖的范围里。**数组顺序就是应用顺序**，这一点与 `1.2` §3.2 的 `flatMap` 一致。
- **其余五个 bundle 怎么写**：`base` / `headless` / `sdk-app` / `acp-app` / `sdk-minimal` 的 `dsh.bundle.patch` 都是**一个字符串**（`"./cordis.patch.yml"`），位置分别在 `packages\bundle\base\package.json` 第 31–35 行、`headless\package.json` 第 37–41 行、`sdk-app\package.json` 第 31–35 行、`acp-app\package.json` 第 31–35 行、`sdk-minimal\package.json` 第 31–35 行。

**块 2：字符串与数组被统一成同一种形状**

上一条里"有的写字符串、有的写数组"，之所以不成为特例，是因为读取它的函数先做了一次归一化：

`packages\boot\app-boot\src\profile.ts` 第 51–75 行

```ts
/**
 * The patch files a bundle declares, as written: one file for a string
 * `patch`, the listed files in order for an array.
 * @param bundle - the bundle's `dsh.bundle` declaration, as read from package.json.
 * @returns the package-relative patch file paths in application order.
 * @throws {Error} when `patch` is neither a string nor a list of strings.
 */
export function bundlePatchFiles(bundle: DshBundleManifest): string[] {
  const declared = typeof bundle.patch === 'string' ? [bundle.patch] : bundle.patch
  if (!Array.isArray(declared) || !declared.every(file => typeof file === 'string')) {
    throw new Error('dsh.bundle.patch must be a file path or a list of file paths')
  }
  return declared
}

/**
 * Resolve a bundle declaration to its ordered absolute patch files.
 * @param packageDir - absolute directory of the bundle package.
 * @param bundle - the bundle's `dsh.bundle` declaration, as read from package.json.
 * @returns the absolute patch file paths in application order.
 * @throws {Error} when `patch` is neither a string nor a list of strings.
 */
export function bundlePatchPaths(packageDir: string, bundle: DshBundleManifest): string[] {
  return bundlePatchFiles(bundle).map(file => join(packageDir, file))
}
```

按块讲解：

- **做什么**：`bundlePatchFiles` 把"字符串"包成单元素数组，于是**一个文件**与**一串文件**在后续代码里是同一种东西；不是字符串也不是字符串数组 → 直接抛错；`bundlePatchPaths` 再把包内相对路径接到包目录上。
- **依赖的变量从哪来**：`bundle` 参数是**调用方**传进来的 `bundleManifest.dsh?.bundle`——即该 bundle 包 `package.json` 里的 `dsh.bundle` 对象（块 1 里那个 `{ patch: [...] }`）。`DshBundleManifest` 与 `join` 都是本文件顶部 import 的类型与函数。
- **为什么这么写**：`@returns the package-relative patch file paths in application order`——注释直接点明返回值**带顺序**。这条顺序就是 §3 结论 3 里 "bundle → 有序 patch 文件列表" 的落点。

### 4.2 profile 决定叠哪些 bundle（五个 template + 一个例外）

**块 3：随发行版交付的五个 profile 模板**

- **为什么这么写**：`sdk-minimal` 那一项**不是笔误**——它表达的就是 §3 结论 1 的例外（README 与设计笔记的理由见 §4.4）。`INSTALLATION_OWNED_PROFILE_TUPLES` 是另一件事：早期安装把 `headless` 写成三元组，这份表把它**规范化回模板**（第 198–200 行）。
- **桌面不在这里**：`Record<string, ProfileTemplate>` 只有 5 个键，没有 `desktop`——§4.6 讲它怎么来的。
- **这里没有 `DEFAULT_PROFILE_BUNDLES`**：它在本文件第 213 行（`['@deepseek-ai/dsh-base']`），只用于"没有模板的自定义 profile 初始化"。

**块 4：bundle 层按清单顺序逐层读出，失败者不中断**

`packages\boot\app-boot\src\profile.ts` 第 732–766 行

```ts
// （第 719–731 行是函数文档注释：说明本函数用于"应用方自有的、已初始化的 profile 目录"，
//   以及"退役 bundle 会先被移出清单""读不出来的 bundle 只记录不中断"，此处省略全文）
export function loadProfileDirectory(       // ← 函数头：三个输入 = 诊断前缀、profile 目录、安装锚点
  binName: string,
  dir: string,
  installAnchor: string,
  options: { userLayer?: boolean } = {},
): Profile {
  const manifest = dropRetiredBundles(dir, readProfileManifest(binName, dir))   // ① 读清单
  const bundles = manifest.dsh?.profile?.bundles ?? []                          // ② 顺序的唯一来源
  const layers: ProfileLayer[] = []
  const skippedBundles: SkippedBundle[] = []
  const exemptions = bundles.length === 0 ? {} : readProfileVersionExemptions(dir)
  for (const packageName of bundles) {                                          // ③ 按书写顺序遍历
    try {
      const packageDir = resolveBundleDir(binName, packageName, installAnchor, dir)
      const bundleManifest = readProfileManifest(binName, packageDir)
      const bundle = bundleManifest.dsh?.bundle
      if (bundle === undefined) {
        throw new Error(`${binName}: profile bundle ${JSON.stringify(packageName)} declares no dsh.bundle in its package.json`)
      }
      // A bundle is not a plugin row, so row admission never reads its own peers.
      const issue = evaluatePluginCompatibility(bundleManifest, exemptions)
      if (issue !== undefined && !issue.exempted) throw new Error(pluginCompatibilityWarning(issue))
      const patchPaths = bundlePatchPaths(packageDir, bundle)                    // ④ 块 2 那个函数
      const patches = patchPaths.flatMap(patchPath => loadOverlayPatches(binName, patchPath))
      layers.push({ packageName, packageDir, patchPaths, patches })              // ⑤ 顺序 = 数组顺序
    } catch (error) {
      skippedBundles.push({ packageName, reason: String(error) })                // ⑥ 失败只记录
    }
  }
  const patchPath = join(dir, PROFILE_PATCH_FILENAME)
  const patches = options.userLayer !== false && existsSync(patchPath)
    ? loadOverlayPatches(binName, patchPath)
    : []
  return { name: basename(dir), dir, layers, patchPath, patches, skippedBundles }
}
```

按块讲解：

- **做什么**：把 profile 目录读成 `Profile`——**bundle 层的顺序就是清单里的顺序**，profile 自己的 patch 层单独读。
- **依赖的变量从哪来**：`manifest` = profile 目录 `package.json` 的内容（经 `dropRetiredBundles` 剔除已下线 bundle）；`bundles` = 其中的 `dsh.profile.bundles`，`?? []` 让"没写 bundles"的 profile 得到空数组；`installAnchor` 由调用方传入（本文件的 `loadProfile` 与桌面应用各传自己的）。`PROFILE_PATCH_FILENAME` 是第 40 行的常量，值就是字符串 `'cordis.patch.yml'`。
- **相邻的守卫**：第 748–750 行——bundle 没声明 `dsh.bundle` → **抛错**（被 catch 接住）；第 752–753 行——兼容性预检不通过且未被豁免 → **抛错**，同样进 `skippedBundles`。
- **为什么这么写**：`for … of` 直接遍历数组，**没有排序、没有去重**——所以 §3 结论 3 里"顺序由 `dsh.profile.bundles` 决定"是字面事实；⑥ 让"某个 bundle 装坏了"只损失那一个形态层，其余照常（`reportSkippedBundles` 之后把这些原因打到 stderr）。
- **这就是"形态层叠在 base 之上"的实现**：base 排在 `bundles[0]`，形态层排在 `bundles[1]`，`layers` 数组的顺序就是**应用顺序**。

**块 5：层序的权威表述（含 home 层与 `--patch`）**

`apps\cli\src\profile-boot.ts` 第 184–209 行

```ts
/**
 * Load `name` and compose its effective patch stack: bundle layers in
 * `dsh.profile.bundles` order (a base-backed profile gets the base bundle's
 * platform-gated shell rows), the profile's user layer, the home-level user
 * layer (`$DSH_HOME/cordis.patch.yml` — machine-local preferences that apply
 * to every profile, so it outranks the per-profile layer), `--patch` overlays,
 * then the telemetry switch.
 * @param name - the profile name.
 * @param patchFiles - `--patch` overlay paths, in argv order.
 * @param fromDefaultProfile - shipped template for a missing named profile.
 * @param resolvedProfile - application-owned profile and installation.
 * @returns the profile and its patch layers.
 */
async function composeProfile(
  name: string,
  patchFiles: readonly string[],
  fromDefaultProfile?: string,
  resolvedProfile?: ResolvedProfileRuntime,
): Promise<ComposedProfile> {
  const profile = resolvedProfile?.profile ?? prepareProfile(name, true, fromDefaultProfile)
  if (resolvedProfile !== undefined) writeFileSync(join(profile.dir, PROFILE_ROOT_FILENAME), PROFILE_ROOT_CONFIG)
  const resolutionOptions = { installAnchor: resolvedProfile?.installAnchor ?? INSTALL_ANCHOR, profile }
  const resolution = await createRuntimeResolution(resolutionOptions)
  const overlays = patchFiles.flatMap(file => loadOverlayPatches(NAME, resolve(file)))
  return { profile, resolution, overlays }
}
```

按块讲解：

- **做什么**：一次启动把 profile 与它的 patch 栈装好：读 profile（必要时用模板初始化）、算运行期解析、把 `--patch` 读成 overlay 列表。
- **依赖的变量从哪来**：`resolvedProfile` 由**桌面应用**这类"自己拥有 profile"的调用方传入（此时不走 `$DSH_HOME` 解析）；缺失则退回 `prepareProfile(name, true, fromDefaultProfile)`——即 `1.2` §6 讲的官方路径。`NAME` / `INSTALL_ANCHOR` 是本模块的常量。
- **为什么这么写（本课最相关的一句）**：JSDoc 第一句里的 **`bundle layers in dsh.profile.bundles order`** 就是 §3 结论 3 的第一段；括号里那句 *"a base-backed profile gets the base bundle's platform-gated shell rows"* 则是本课的形态学前提——**base 先叠，形态层才改得到它**。
- **本课不重复 `1.2` 的推导**：完整层序（含 profile → home → argv，以及"dump 与启动同序"）在 `1.2` §3；这里只摘"顺序从哪来"。

export function createRuntimeProjectMetadata(projectDir: string, release: DesktopRelease): void {
  mkdirSync(projectDir, { recursive: true, mode: 0o700 })
  const packageSet = verifyDesktopCorePackageSet(projectDir, release.version)
  const manifest = {

}

- **为什么这么写**：Desktop 的 profile 目录**由应用自己拥有**并提供给共享的 CLI runner（`docs\architecture.zh.md` 第 53 行原文：*"并拥有保留的 `$DSH_HOME/profiles/desktop`"*），因此它不必进入 `PROFILE_TEMPLATES`——模板表的用途是"首次使用时自动初始化"，而 Desktop 由应用自己初始化。

## 6. 一条实用命令：把某个形态的配置树打印出来

```powershell
# 通用形式（从源码仓库跑，cwd = <repo> 根目录）
pnpm dsh --profile <名字> --dump-default-config > <临时目录>\tree.yml
```

| 你需要知道的 | 说明 |
|---|---|
| **在哪个目录跑** | 用 `pnpm dsh` 时必须**在 `<repo>` 根目录**（脚本定义在根 `package.json` 第 198 行：`node --import tsx/esm apps/cli/src/bin.ts`）。profile 本身从 `$DSH_HOME` 解析，与 cwd 无关；**唯一例外**是 `--patch <相对路径>` 按 cwd 解析 |
| **可执行文件怎么找到** | 三种办法：① 源码方式 `pnpm dsh …`（改代码时用）；② 安装版 `& '<安装目录>\resources\runtime\cli\bin\dsh.cmd' …`（`dsh` 通常不在 PATH 上，路径带引号时 PowerShell 必须加 `&`）；③ 把 launcher 目录临时加进 PATH |
| **输出落在哪** | 加了 `> …\tree.yml` 就写进你指定的文件（建议落到**临时目录**；在仓库里跑会留下未跟踪文件） |
| **副作用** | dump 只打印、不启动。唯一次要副作用：它会**重写该 profile 目录里的 `cordis.yml`**（`apps\cli\src\profile-boot.ts` 第 171 行无条件写入那个固定空表，第 204 行在应用方自有 profile 的路径上同样写一次），文件内容无害、但修改时间会变 |
| **本 checkout 的一个前提** | `apps\cli\lib\`（构建产物）在本 checkout 里**不存在**，所以 `node apps\cli\lib\bin.js …` 这种写法在这里跑不起来；要用 `pnpm dsh`（源码直跑）或安装版 launcher。**未找到** `apps\cli\lib\bin.js` 文件（`glob` 结果为空） |
| **典型报错** | ① 名字不存在且不在模板表里 → `profile "xxx" does not exist; create it with 'dsh plugin --profile xxx add <package>'`（模板名 `acp`/`web`/`headless`/`sdk`/`sdk-minimal` 会自动初始化，源码 §4.2 块 3）；② 由桌面应用独占管理的 profile → 拒绝操作；③ `--dump-default-config` 不能与 `--patch` 同用（`apps\cli\src\args.ts` 第 133 行报 `--dump-default-config prints the bundle layers and takes no --patch`） |
| **一个坑（实测）** | 别用 `... | Select-Object -First N` 截断它的输出——管道提前关闭会掐死子进程，退出码变成 `-1`（输出本身是对的，属假象）。要截断就**先重定向到文件，再读文件前 N 行** |

**`--dump-default-config` 与 `--dump-config` 的差别**：前者只输出**bundle 层**（profile 层、home 层、argv 层既不渲染、也不读文件），所以它是"profile 的 patch 写坏了也能出结果"的诊断手段（`apps\cli\src\dump-config.ts` 第 26–28、47 行；展开见 `1.2` §6）。

### Q1 从 base 到 Web 产品，中间加了什么？

→ **加了 87 行插入、27 行覆盖**（`packages\bundle\web-app\cordis.patch.yml`，静态复核见 §7.2）。插入分三段：① **Web 宿主行**（`webserver`、`web-runtime`、`web-startup`、各 `*-controller`、`session-stats`、`session-turn-outline`、`directory-picker`、`plugin-inventory`、`schedule`…）；② **浏览器插件名册**（`modules`、`connection`、`ui-*` 60 余行，这些行的名字里大多带 `dsh-client-`）；③ **preset 注册表**（最后一段 `insert`，`agent-preset-registry`，`default: standard`）。覆盖分两类：**表层专有值**（`system-prompt` 的 persona 前缀与后缀、`session-query-sqlite`、`tools` 的 `DSH_TOOLS_MODE`）与**把 agent 平面让给 preset**（`tool-bash`、`tool-pwsh`、`tool-fs`、`tool-subagent*`、`tool-todo`、`tool-web` 等 24 行全部 `disabled: true`）。
出处：本文 §4.5 块 15、块 16；`packages\bundle\web-app\cordis.patch.yml` 第 14–38、44–583 行；`docs\architecture.zh.md` 第 29 行。

### Q2 `dsh-sdk-minimal` 为什么刻意不带 `dsh-base`？它的配置树有什么特点？

→ **理由（设计笔记原文）**：把"极简"表达成完整 SDK profile 的 overlay 时，base 的每个服务**仍然挂载**，"排除"只能靠散落在不相关插件里的过滤器与 disable 项；而且 base 后续新增的行会改变运行时行为，即使模型可见工具被过滤掉也一样（`.agents\notes\archived\architecture\2026-08-24-standalone-sdk-minimal-profile.md` 第 10 行原文：*"leaves every `dsh-base` service mounted and makes exclusion depend on filters and disable entries spread across unrelated plugins"*）。所以要的是**组合级排除**，而不是过滤。同一份笔记第 12 行还说明了另一条约束：调用方**自带的**完整 Cordis 树被否决（那会绕开 profile 初始化、bundle 解析、持久插件管理、home 与调用 patch 层以及 `dsh` 自己的进程生命周期）。源码里的原话见 §4.4 块 13 引的作者注释：*"this profile owns each service row and omits every optional producer it does not use."*

**特点**：
1. 一个 `insert` 就是全部 **27 行**，无任何覆盖（`cordis.patch.yml` 第 1–3 行；源码见 §4.4 块 11）。
2. 静态复核 27 个插入行、0 个覆盖行；dump 出的顶层行数也是 27、`patched by` 标记为 0（§7.1 证据 A、§7.2）——**实测与静态计数一致**。
3. 安全默认值刻意最宽：`sandbox-policy.mode: danger-full-access`（第 41–45 行），而 base 是 `DSH_PERMISSION_MODE ?? 'workspace-write'`；该策略允许 shell 改动进程可访问的任何路径，故只能配隔离 workspace 使用（`packages\bundle\sdk-minimal\README.zh.md` 第 12 行；源码见 §4.4 块 12）。
4. 关掉 harness 身份与运行时上下文：`includeHarnessIdentity: false`、`includeRuntimeContext: false`（第 84–89 行；开关效果见 §4.4 块 14）。
5. `maxTokensAsSuccess: false`（第 15 行）与完整 SDK 的默认 `true` **相反**（源码见 §4.4 块 11）。
6. settings、credentials、遥测、web 工具、subagent、skills、compaction、goal、文件系统工具等**根本不存在**（不是"被禁用"）。
7. 模型可见工具只有**一个**按平台选择的持久 shell（README 第 81 行）。
8. 它**仍然处在正常层序里**：文件头注释第 3 行 *"User profile, home, and invocation patches still apply above it."*——自定义照样通过 profile 的 `cordis.patch.yml`、home 层与 `--patch` 生效（设计笔记第 32 行）。

### Q3 同一内核如何长出 CLI / Web / 桌面 / SDK / ACP 多种形态？

→ 机制是 **profile → bundle → patch** 三级：

1. **profile** 的 `dsh.profile.bundles` 决定叠哪些 bundle。例如 `web` = `['@deepseek-ai/dsh-base','@deepseek-ai/dsh-web-app']`、`sdk-minimal` = `['@deepseek-ai/dsh-sdk-minimal']`（`packages\boot\app-boot\src\profile.ts` 第 179–195 行，源码见 §4.2 块 3）。
2. **bundle** 用 `dsh.bundle.patch` 声明一个**有序 patch 文件列表**（`bundlePatchFiles` / `bundlePatchPaths`，第 58–75 行，源码见 §4.1 块 2），例如 web-app 的 5 个文件。
3. **patch** 文档按 `id` 替换整行 `config` / 禁用 / 插入新行；层序是 bundle 层 → profile patch → home patch → `--patch`（`apps\cli\src\profile-boot.ts` 第 184–196 行，源码见 §4.2 块 5）。

**内核（cordis 树）不含形态概念**：形态差异 100% 由 patch 文档表达。Web 靠插入 87 行宿主/浏览器行 + 禁用 24 行 agent 平面行；Headless 靠插入一个 runner 行；SDK / ACP 靠插入一个协议服务器行。桌面则是"**web 的 bundle 列表 + `profileContext.name === 'desktop'` 表达式**"（`apps\desktop\src\project-manager.ts` 第 32、142 行；`packages\bundle\web-app\cordis.patch.yml` 第 45–62 行），不是独立 template。
