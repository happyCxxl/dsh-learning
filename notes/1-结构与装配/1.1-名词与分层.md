## 0. 怎么读这一课（先看这段，能省你一小时）

### 0.1 这一课是什么、不是什么

**是**：术语坐标系。目标是"看到这些词知道指什么、知道该去哪个文件查"。
**不是**：机制讲解。**本课不解释任何东西是怎么实现的**，机制在第二编（插件内核）与第三编（运行内核）。

### 0.2 现在只要记住这 5 件事

1. **DSH 跑起来时，本质上是"一棵插件树"**——连 agent loop、会话日志、工具注册表都是树上的插件。
2. **这棵树不是写出来的，是"叠"出来的**：`profile` 按顺序点名若干 `bundle`，每个 `bundle` 带一份 `patch`，`patch` 里按 `id` 增改"条目"，最后再叠你自己的 patch。
3. **插件之间共享一个上下文 `ctx`**，靠 `ctx.<名字>` 互相取用能力（这些能力叫"服务"）。
4. **一次会话里，事件分三类**：持久的会话事件、进程内的 agent 事件、挂在能力接缝上的能力事件。
5. **循环有三个层级词**：`turn`（轮次）⊃ `step`（步骤）⊃ 一次模型请求 + 它引发的工具执行。

### 0.3 明确授权：其余 30 多个词，现在**不用管**

本课会出现大量你暂时不懂的词（cordis、seam、preset、scope、realm、settlement、inbox、projection、lineage、Ralph…）。**这些都是我在别处学的，现在不需要你懂。**

判断标准只有一条：**只要你能回答"这个词属于上面 5 件事里的哪一件"，就够了**。剩下的等对应编展开（见附录 B 的术语索引，标注了每个词在第几课展开）。

### 0.4 如果你是第一次读，跳过附录 A

**附录 A 的四题解答属于第二、三编的内容**（preset / scope / realm / pre-step / settlement）。第一次读**跳过它**，否则会被四个没解释的重概念砸晕。

## 1. 最小词汇表（5 个词，大白话，先不碰 cordis 内部）

这 5 个词是理解后面一切的地基。**先用大白话建立直觉，不要追问它们的实现。**

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **plugin 插件** | 一段**可以被装上、也可以被卸下**的代码。卸下时它做的事要能全部撤销 | 最小形态是一个导出 `apply(ctx)` 的函数<br>（`apply(ctx)`＝"装你的时候会调用这个函数，并把 `ctx` 交给你"） |
| **ctx（context）** | 所有插件**共享的一个"登记处"**。插件往里面登记自己的东西，也从里面取别人的东西 | `ctx.sessions`、`ctx.tools`、`ctx.llm`… |
| **service 服务** | 登记处里**一项有名字的能力**。名字就是那个键（`sessions`、`tools`…） | `ctx.` 后面那一节 |
| **entry 条目** | 配置里的**一行**：`id`（这行的身份）+ `name`（要加载什么）+ 可选的 `config` / `disabled` / `inject` | YAML 里的<br>`- id: xxx`<br>`  name: yyy` |
| **layer 层** | **一次叠上去的一批条目**。本课里"一层"通常就是"一个 patch 文件" | 一个 bundle 可带一个或多个 patch 文件；每个文件就是一层 |

> ⚠️ **这 5 个词都属于 cordis 的词汇体系，而 cordis 本身是第二编的主题。** 本课只用到上面这个程度——为什么 `ctx` 能"点"出服务、`apply` 什么时候被调用、卸下时怎么撤销，**这里不答**，第二编答。

## 2. 从属关系图（谁是谁的一部分）

原文的五节是**并列**的，容易让人不知道层级。下面是它们真正的关系。

### 2.1 产品组装链（静态结构）

```
$DSH_HOME                      通常是 ~/.dsh
└─ profiles\<名字>\             ← profile：一个目录 + 一份清单
   ├─ package.json              · dsh.profile.bundles = [bundle₁, bundle₂, …]（按序）
   ├─ cordis.yml                · 空的根条目表（起点，别改它）
   ├─ cordis.patch.yml          · 你自己的 patch 层
   └─ node_modules\             · 你自己装的第三方 bundle
        │
        │  启动时按顺序叠加（后者覆盖前者）
        ▼
   bundle₁ 的 patch ┐
   bundle₂ 的 patch ┤  每份 patch = 一串「条目 entry」
   profile 的 patch ┤  条目 = { id, name, config?, disabled?, inject? }
   home 级 patch    ┤  操作 = 按 id 覆盖 config / 禁用 / 插入新的
   --patch overlay  ┘
        │
        ▼  组装结果
   插件树（运行时）── 每个条目 ⇒ 一个被加载的插件 ⇒ 往 ctx 上登记服务/工具/监听器
```

### 2.2 循环层级（动态过程）

```
会话 session（一次完整对话的真源，只追加）
└─ turn 轮次        一次"把已接纳的输入处理干净"的过程
   └─ step 步骤     一次模型请求 + 它引发的工具执行
        └─ 事件      执行过程中被记下来/被广播的东西
                     ├─ 会话事件（持久，写进日志）
                     ├─ agent 事件（实时，进程内）
                     └─ 能力事件（挂在能力接缝上）
Round（外层策略迭代，如 Goal Round）在 turn 之外，由策略自己计数
```

> 严格说事件不是"装在 step 里"，而是**在 turn/step 的过程中产生**，并可按 turn/step 归类。这里用包含关系画图只是为了让你知道谁大谁小。

## 3. 大白话版：用户敲一句话，机器里发生了什么

**完全不用上面的术语**，先建立画面（来源：`docs\architecture.zh.md` 第 92–111 行的轮次流程伪代码；这里只做白话转述，细节留到第三编）。

1. 用户的话被收进一个"待处理队列"。
2. 有个循环把它取走，开始一个**轮次**。
3. 循环先把"要给模型看的东西"拼起来：系统提示词 + 历史消息 + 可用工具的说明书。
4. 然后发一次模型请求——这就是一个**步骤**的开始。
5. 模型流式吐字，界面上字一个个出现。
6. 如果模型说"我要用某个工具"，循环就去执行那个工具；执行前后都有检查点（权限、审批、守卫）。
7. 工具结果再喂回模型，模型继续；可能重复好几轮——**同一个轮次里可以有多个步骤**。
8. 模型不再要工具、队列也空了，轮次结束。
9. 全程"值得留下的事实"被追加进会话日志；"过程中的瞬时数据"只走实时事件，不进日志。

## 4. 第一层世界观：一切皆插件

> 出处（文档）：`docs\architecture.zh.md` 第 9–13 行（Cordis 一节）

运行中的 `dsh` **就是一棵插件树**。原文：

> 产品的每一部分都是插件，包括模型适配器、工具注册表、会话日志，以及 agent loop 本身，因此每个都可以从配置替换。
> 不存在需要打补丁的特权内核：扩展 dsh 的方式是把插件挂载到其他插件旁边，而各项注册都是副作用，会在其插件卸载时撤销。

### 4.1 它解决什么问题（这一段是"为什么"，原文没写）

- 传统做法里，总有一层"核心"是别人改不了的：想定制只能 fork、打补丁，或者求作者开一个配置后门。
- DSH 的选择是**把核心也做成插件**，于是"定制"这件事统一成了"在上面再叠一层 patch"——**不需要改任何包的代码，就能改变产品行为**。
  - 仓库里现成的例子：Web 形态用 patch 把 `dsh-base` 带来的 `tool-bash`、`tool-pwsh` 直接置为 `disabled: true`（出处：`packages\bundle\web-app\cordis.patch.yml` 第 468–472 行）。
- **代价**（标注为推断）：生效顺序变成了必须理解的规则——同一份配置，叠的先后不同结果就不同。所以本课后面那串"组合顺序"不是细节，是核心。

### 4.2 三个关键词

| 术语 | 指什么 |
|---|---|
| **plugin 插件** | 一个可挂载、可卸载的单元；最小形态是导出 `apply(ctx)` 的函数 |
| **ctx（上下文）** | 插件之间共享的登记处。插件通过它**登记**东西、**取用**别人的东西 |
| **service 服务** | 插件向 `ctx` 贡献的**具名能力**，用 `ctx.<键>` 取用 |

**`ctx.sessions` / `ctx.tools` 这类写法的语义**：从共享登记处取名为 `sessions` / `tools` 的那项服务。
→ 进一步的问题（谁登记进去的？什么时候登记？卸下时怎么撤销？）**属于第二编**。

## 5. 第二层：这棵树是怎么叠出来的

### 5.1 三个词：各自到底是什么

| 名词 | 是什么（一句话） | **不是什么** | 在哪 | 怎么被声明 |
|---|---|---|---|---|
| **profile** | 一套**具名组装**：一个目录 + 一份清单，说明"这个产品形态由哪些 bundle 叠成、用户自己改了什么" | 不是程序，不是可执行文件 | `$DSH_HOME\profiles\<名字>\` | 该目录里 `package.json` 的 `dsh.profile` 字段 |
| **bundle** | 一个**可分发单元**，内容是"一份 patch + 挂载代码" | 不是插件本身（它挂载的条目才是插件）；一个 bundle 可以挂多个条目 | 作为 npm 包分发（`@deepseek-ai/dsh-base` 等官方包，也可以是第三方包） | 包自己的 `package.json` 里 `dsh.bundle.patch` 字段，指向它的 patch 文件（可为一个文件，也可为**有序文件列表**） |
| **patch** | 一份**对插件树的修改指令清单**：按 `id` 定位条目，然后覆盖 `config` / 禁用 / 插入新条目 | **不是** git 的 diff 补丁 | bundle 内部一份；profile 里也有一份（你自己的那份） | 顶层 YAML 数组；profile 的那份固定叫 `cordis.patch.yml` |

> **术语统一说明**：本笔记之后只用英文名 `profile` / `bundle` / `patch`（源码里就是这三个词）。中文"组合包"只在需要读中文文档时对照一下——它指的就是 `bundle`。

**一句话关系**：`profile` 按顺序点名若干 `bundle` → 每个 `bundle` 自带一份 `patch` → `patch` 按 `id` 改或加条目 → 最后叠加**你自己的 patch**。跑起来的结果就是那棵插件树。

另外：`cordis.yml` 是**空的根条目表**（起点，别改它），整棵树全靠 patch 叠出来。

### 5.2 三个结构示意（说明这三样东西各长什么样）

> 以下都是**结构示意**，字段形态取自仓库内公开文件；取值是示例，不代表任何实际部署。

**① profile 的清单** —— `<profile 目录>\package.json`
```json
{ "name": "dsh-profile-<名字>", "private": true,
  "dsh": { "profile": {
      "bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app", "<第三方 bundle 包名>"] } },
  "dependencies": { "<第三方 bundle 包名>": "^1.0.0" } }
```
注意第三项：**第三方包也可以作为 bundle 被点名**，通常同时出现在 `dependencies` 里。

**② 一个 bundle 自带的 patch** —— 简单的 bundle 可能只有几行：
```yaml
# <某个 bundle>/cordis.patch.yml
- insert:
    - id: <该 bundle 的条目 id>
      name: '<该 bundle 的包名>'
```

**这个字段是怎么被读的（源码）** —— `packages\boot\app-boot\src\profile.ts` 第 58–64 行：

```ts
export function bundlePatchFiles(bundle: DshBundleManifest): string[] {
  const declared = typeof bundle.patch === 'string' ? [bundle.patch] : bundle.patch
  if (!Array.isArray(declared) || !declared.every(file => typeof file === 'string')) {
    throw new Error('dsh.bundle.patch must be a file path or a list of file paths')
  }
  return declared
}
```

按块讲解：

- **第 59 行**：`patch` 是**字符串**就包成单元素数组——"一个文件"和"一串文件"因此被统一成同一种形状。
- **第 60–62 行**：既不是字符串、也不是字符串数组 → **直接抛错**，错误信息就是那句 `dsh.bundle.patch must be a file path or a list of file paths`。
- **第 63 行**：返回数组的**顺序就是应用顺序**——这是"多个 patch 文件按序叠加"的落点。仓库里的实例是 `dsh-web-app`（在自己的 `package.json` 里声明了 5 个文件）。

**③ 用户自己的 patch 层** —— `$DSH_HOME\profiles\<名字>\cordis.patch.yml`。
它的文件头注释会写明自己是 "applied after every bundle layer"，形式是按 `id` 覆盖某些行的 `config`：
```yaml
- id: <某个条目的 id>
  name: "<该条目的包名>"
  config:
    <该条目拥有的全部配置键>: <值>
```
更完整的真实写法可以看仓库里的 `packages\bundle\web-app\cordis.patch.yml`（既覆盖 base 的行，也 `insert` 自己的行）。

**④ 看组装结果**：把配置树打印出来（`--dump-config` 只打印、不启动）：
```powershell
dsh --profile <名字> --dump-config > tree.yml
```
输出里层边界用 `# ==` 注释标出。执行时要注意四件事：

1. **在哪个目录执行都可以** —— profile 从 `$DSH_HOME` 解析，与当前目录无关。
   （唯一例外：`--patch <相对路径>` 里的相对路径是**按当前目录**解析的。）
2. **`dsh` 通常不在 PATH 上**，所以要显式给路径，三种办法：
   ```powershell
   # 一、用完整路径调 launcher（路径带引号时 PowerShell 必须加 &）
   & '<安装目录>\resources\runtime\cli\bin\dsh.cmd' --profile <名字> --dump-config > tree.yml
   # 二、临时加进 PATH（只对当前终端会话生效）
   $env:PATH += ';<安装目录>\resources\runtime\cli\bin'
   dsh --profile <名字> --dump-config
   # 三、从源码仓库跑（改代码时用；在 <repo> 根目录）
   pnpm dsh --profile <名字> --dump-config
   ```
3. **`<名字>` 是什么**：它必须是 `$DSH_HOME\profiles\` 下的一个**目录名**（单个路径段——不含 `/`、`\`，且不能是 `.`、`..`、`node_modules`）。行为分三种：
   - **命中发行版模板名**（`acp` / `web` / `headless` / `sdk` / `sdk-minimal`）而目录尚不存在 → **自动初始化**它（`packages\boot\app-boot\src\profile.ts` 第 786–794 行：目录里没有 `package.json` 且名字在 `PROFILE_TEMPLATES`（第 179–195 行）里，就 `initProfile`）。
   - **不在模板名单**且目录不存在 → **直接报错**，并告诉你创建方式：
     `profile "xxx" does not exist; create it with 'dsh plugin --profile xxx add <package>'`
   - **由桌面应用独占管理的 profile** → CLI 拒绝操作。
   另一个真实副作用：**每次 dump 都会重写该 profile 目录里的 `cordis.yml`**（`apps\cli\src\profile-boot.ts` 第 171 行无条件写入那个固定的空条目表）。内容无害，但该文件的修改时间会变化。
4. **不是所有 profile 都能这样 dump**：由桌面应用独占管理的 profile 会被拒绝（报 `profile "xxx" is managed exclusively by the Electron application`）。另外 **stderr 可能带警告**（例如某个不兼容的第三方 bundle 被跳过），建议把 stdout 重定向到文件再看。

### 5.3 profile 的 patch 层为什么是"真源"

bundle 作者写下的只是**默认值**；产品实际行为的差异，最终都体现在"谁在后面叠了什么"：

- bundle 的 patch 提供默认；
- profile 的 patch 覆盖默认；
- home 级 patch 与 `--patch` 再往上叠。

所以想搞清楚"这个产品的某个行为从哪来"，`--dump-config` 输出里的 `# ==` 注释就是答案——它标明了"哪一层贡献了这一行""哪一层改过它"。

### 5.4 三个最容易混的点

1. **profile 不是程序**：跑起来的是插件树，profile 只是"配方"。
2. **bundle 不是插件**：bundle 是"配置 + 挂载代码"的分发格式，它挂载的条目才是插件。
3. **patch 不是 git 补丁**：它是 YAML 数组形式的修改指令，按 `id` 定位而不是按行号。

> 辅助类比（一句话，仅作参照，**机制完全不同**）：bundle 大致相当于 Spring Boot starter（一个依赖带来一串自动配置），profile 相当于一套启动配置。

### 5.5 组合顺序（背下来）

```
空条目列表（cordis.yml 里的 []）
  → 各 bundle 的 patch，按 profile 中列出的顺序依次叠加
  → profile 自己的 cordis.patch.yml
  → home 级的那份 patch（$DSH_HOME\cordis.patch.yml，不存在则跳过）
  → 任意 --patch overlay（按命令行顺序）
```

这条顺序有两处源码依据：
- `apps\cli\src\dump-config.ts` 第 44–75 行：注释原文 "bundle, profile, home, then argv order"。
- `packages\boot\app-boot\src\profile-context.ts` 第 63–74 行（热重载路径）：同样是 bundle → profile → home → overlays。

**源码：顺序就是这一段定的** —— `apps\cli\src\dump-config.ts` 第 44–75 行（整个函数，连它的文档注释）：

```ts
/**
 * Read dump layers in bundle, profile, home, then argv order without composing them.
 * @param loaded - prepared profile and parsed bundle and profile patches.
 * @param defaultOnly - omit profile, home, and argv layers without reading their files.
 * @param patches - overlay paths relative to the invoking directory, in argv order.
 * @returns the labeled layers shared by YAML and schema dumps.
 */
export function collectConfigDumpLayers(
  loaded: Profile,
  defaultOnly: boolean,
  patches: readonly string[],
): ConfigDumpLayer[] {
  const layers: ConfigDumpLayer[] = loaded.layers.map(layer => ({   // ① 各 bundle 的层
    label: layer.packageName,
    patches: layer.patches,
  }))
  if (!defaultOnly) {
    if (existsSync(loaded.patchPath)) {                             // ② profile 自己的 patch
      layers.push({ label: loaded.patchPath, patches: loaded.patches })
    }
    const homePatchFile = homePatchPath()                           // ③ home 级 patch
    const homePatches = loadOptionalPatches(NAME, homePatchFile)
    if (homePatches !== undefined) {
      layers.push({ label: homePatchFile, patches: homePatches })
    }
    for (const file of patches) {                                   // ④ --patch 覆盖层
      const absolute = resolve(file)
      layers.push({ label: absolute, patches: loadOverlayPatches(NAME, absolute) })
    }
  }
  return layers
}
```

按块讲解：

- **JSDoc 第一句**就是这个顺序的权威表述（英文原文 "bundle, profile, home, then argv order"）——§5.5 的结论直接来自它。
- **①** `loaded.layers` 是**各 bundle 的层**，其顺序由 `dsh.profile.bundles` 决定：`loadProfileDirectory` 就是按那个数组 `for` 遍历的（`packages\boot\app-boot\src\profile.ts` 第 738–743 行）。
- **②** profile 自己的 patch：**存在才 push**（`existsSync` 先判一次）。
- **③** home 级 patch：走 `loadOptionalPatches`，返回 `undefined` 就不 push —— 这就是"缺失时不贡献层、也不报错"的落点。
- **④** `--patch` 覆盖层：在 `for` 里**按 argv 顺序**依次 push；相对路径在这里被 `resolve(file)` 成绝对路径（所以它按当前目录解析）。
- **数组顺序 = 应用顺序**：返回的 `layers` 会被交给同一套 patch 算法依次应用，因此**后出现的覆盖先出现的**。
- **顺带解释了 `--dump-default-config`**：`if (!defaultOnly)` 把 ②③④ 整段跳过——**连文件都不读**。

**声明落点**：profile 与 bundle 都在**各自的 `package.json`** 里用 `dsh` 字段声明身份——
`dsh.profile`（列出 bundle）／`dsh.bundle.patch`（指向 patch 文件）。
（`dsh.*` 是 **DSH 自定义字段**，npm 不认识它。）

### 5.6 bundle 分工（"产品是被拼出来的"最好例证）

| bundle | 加了什么 |
|---|---|
| `dsh-base` | `web`/`headless`/`sdk`/`acp` 的**共享第一层**：模型适配器、工具、持久化、沙箱与审批策略、设置、凭据、遥测 |
| `dsh-web-app` | 浏览器应用 |
| `dsh-headless` | 不带服务器的一次性运行器 |
| `dsh-sdk-app` | SDK 的 JSON-RPC 服务器 |
| `dsh-acp-app` | 仅用于自动化的 ACP 服务器 |
| `dsh-sdk-minimal` | **刻意保留的例外**：自带完整显式 SDK 配置树，**不应用 `dsh-base`** |

→ "DSH 有几种产品形态"的答案：**同一棵树，换几层 patch。**

## 6. 第三层：core 的包与它们的 `ctx` 键（表一）

> 出处（文档）：`docs\architecture.zh.md` 第 61–70 行；`packages\core\README.zh.md` 第 25–36 行

| 包 | 职责 | `ctx` 键 |
|---|---|---|
| `core/session` | 仅追加的 `SessionEvent` 日志和内存存储 | `ctx.sessions` |
| `core/system-prompt` | 提示词片段与工具 schema 的组装 | `ctx.systemPrompt` |
| `core/tools` | 作用域化的工具注册表和带把关的执行流水线 | `ctx.tools` |
| `core/agent` | `Agent` 接口、活跃 agent 注册表和 `agent/*` 事件 | `ctx.agents` |
| `core/agent-loop` | 实现该接口的**默认**驱动器 | `ctx.agentLoop` |
| `core/scope` | 按 agent 划分作用域的注册原语 | **库，无 ctx 键** |
| `llm/llm` | 消息与流式词汇表，以及适配器 seam | `ctx.llm` |
| `webhook/webhook` | 已认证 delivery 的分派和 Session 创建 | `ctx.webhookRuntime` |

**怎么读这张表的第三列**：`ctx` 键 = **这个包在共享登记处占用的名字**。有名字 = 别的插件能取用它（"贡献能力"）；没名字 = 它只提供函数给别人调用（"提供原语"）。

**源码：`ctx.sessions` 这个键是怎么来的** —— `packages\core\session\src\index.ts` 第 914–949 行（类体内部省略）：

```ts
/**
 * In-memory session store (`ctx.sessions`).
 *
 * Persistence is intentionally not implemented here — the agent lifecycle
 * attaches a session-log writer to each published session's write handle;
 * a session published outside that lifecycle persists nothing.
 */
export class SessionStore extends Service {
  // …（第 922–946 行：内部 store、projections 字段与注册接口，此处省略）

  constructor(ctx: Context) {
    super(ctx, 'sessions')            // ← 这一句决定了它的 ctx 键叫 sessions
    // …（第 950 行起：注入 typert、注册查询等）
  }
}
```

按块讲解：

- **`extends Service`**：一个包要"贡献一项具名能力"，做法就是定义一个继承 `Service` 的类。
- **`super(ctx, 'sessions')`**：**表里那一列的 `ctx.sessions` 不是文档起的名字，而是代码里写死的字符串**——想知道某个 `ctx.<键>` 是谁提供的，就搜这个字符串。
- **JSDoc 第 917–919 行**顺带点明一个边界：这个内存存储**自己不做持久化**，"持久化"是 agent 生命周期挂上去的写入器（细节属第三编）。
- **反过来看 `core/scope`**：它没有这样的 `Service` 声明，所以表里写"库，无 ctx 键"。
- 该类构造里的 `ctx.inject(['typert'], …)` 属第二编的依赖注入，此处跳过。

**两处要停下来的地方**

1. **`scope` 没有 ctx 键**，文档写"库，不使用 ctx key"→ 分界线是：**贡献能力 vs 提供原语**。
2. **`agent` 与 `agent-loop` 是两个包**：`agent` 定义**接口与约定**，`agent-loop` 是**默认实现**。
   所以扩展插件只依赖 `agent`，**驱动器本身可替换**——这是"无特权内核"最直接的证据。

## 7. 第四层：循环的三个词

> 出处（文档）：`docs\glossary.zh.md` 第 35–39 行（循环层级）；`docs\architecture.zh.md` 第 90 行

| 术语 | 定义 | 白话 |
|---|---|---|
| **step 步骤** | 一次**模型请求**，以及由模型响应引发的**工具执行** | "问一次模型，并把它要的工具跑完" |
| **turn 轮次** | 会话中一次对已接纳输入的**排空过程**；在领首条输入之前打开，在不再欠任何工作时关闭。**一个轮次包含零个或多个步骤** | "把手头的活干到没事可干" |
| **Round** | 承载一个轮次的**外层策略迭代**（如 Goal Round、Ralph Round）。计数器归该策略所有，**不统计会话里的每个轮次** | "某个策略层面的第几轮"，和会话里的 turn 不是一回事 |

## 8. 第五层：三个事件域

> 出处（文档）：`docs\architecture.zh.md` 第 74–84 行

原文：**"事件就是扩展点，而选对事件域是大多数改动的第一个决定。"**

| 事件域 | 性质 | 典型事件 | 何时使用 |
|---|---|---|---|
| **会话事件** | **持久**、追加到日志、经 `session/event` 广播 | `turn/*`、`step/*`、`system/message`、`user/message`、`assistant/message`、`assistant/attempt`、`tool/*` | 某个事实必须**在重新加载后仍然存在** |
| **agent 事件** | **实时**、进程本地 | `agent/*`：inbox、步骤、状态、请求、验证、续跑 | 要**观察或拦截进行中的工作** |
| **能力事件** | 挂在能力接缝（seam）上的策略与适配器 | `fs/*`、`tools/*`、`telemetry/*` | 不引入循环依赖就想挂策略 |

**写作约定说明**：`turn/*` 这种写法里的 `*` **不是代码语法**，是文档里表示"这一类事件"的简写（`turn/start`、`turn/end` 都算）。

## 附录 A 四题解答

> ⚠️ **第一次读请跳过本节。** 它涉及 preset / scope / realm / `agent/pre-step` / settlement 等**第二、三编才展开**的概念。留着是为了将来回查。

### Q1 想让**某一个会话**拥有与其他会话不同的能力集合，该用哪个机制？

**答案：组装一个 agent preset；其中需要隔离的服务行使用 `isolate` realm。**
出处（文档）：`docs\architecture.zh.md` 第 151 行「目标 → 机制」表。

底层原语（出处：`docs\glossary.zh.md` 第 11–21 行的 `agent-scope` 一节）：

- `scope` 只有**两层且扁平**：一项贡献要么是*全局的*（对所有 agent 可见），要么归属于**恰好一个** scope key。
- 在 `agent.ctx` 上做的注册**只对该 agent 生效**，且其生命周期绑定该 scope。
- **shadowing**：带作用域的同名条目只在自身 scope 内**替换全局对应项**——这是"按 agent 定制 persona / 工具变体"的机制。
- **restriction**（`tools.restrict`）：为单个 scope **过滤全局工具集合**，多个 restriction 取**交集**。被滤掉的工具既不出现在提示词中，也**拒绝执行**，与"这个工具不存在"无法区分。
- ⚠️ 带作用域的注册**不会向下继承**给 subagent；子树行为靠 lineage 数据表达。
- 展开时机：第三编（scope / preset）。

### Q2 `dsh-sdk-minimal` 与 `dsh-base` 是什么关系？为什么这个例外值得保留？

**答案：`dsh-sdk-minimal` 是一个不应用 `dsh-base` 的独立 bundle**——它不站在共享底座上，而是自带一份**完整且显式**的 SDK 配置树。而 `dsh-base` 是 `web`/`headless`/`sdk`/`acp` 的**共享第一层**。
出处（文档）：`docs\architecture.zh.md` 第 25 行；`packages\core\README.zh.md` 称其为"完整、独立且功能集经过刻意精简的组合"。

文档给出的保留理由：

1. 它证明**同一 launcher 之后可以不放 base**——组合完全由 profile 与有序 patch 表达（第 45 行）。
2. 它提供**零隐式继承**的参照物：SDK 嵌入场景需要显式、可审计的配置树。
3. Python SDK 的极简示例就选择随附的 `sdk-minimal` profile（第 49 行）。

> 标注为**推断**：它同时充当"最小可运行性"的回归证据——若哪天出现"base 之外也必需"的东西，它会最先坏掉。

### Q3 一个 turn 里有 0 个 step，说明发生了什么？

**答案：一次被拒绝、或被改写为空的轮次——没有发出任何模型请求就关闭了。**
出处（文档）：`docs\architecture.zh.md` 第 97 行 `reject, or a first enter rewritten empty -> close the turn with no step`；第 117 行"首次领取被拒绝或为空时，关闭不含步骤的持久轮次。"
机制：`agent/pre-step` 决定接纳哪些输入，**监听器可以改写或拒绝已领取的消息**。

### Q4 会话事件与 agent 事件，哪一个在进程重启后还在？为什么分两个域？

**答案：重启后仍在的是会话事件；agent 事件是进程本地的实时事件。**
出处（文档）：`docs\architecture.zh.md` 第 74–80、113、127 行。

| 域 | 性质 | 使用判据 |
|---|---|---|
| **会话事件** | 追加到日志、经 `session/event` 广播的**持久事实** | "当某个事实**必须在重新加载后仍然存在**时，使用它" |
| **agent 事件** | 携带**活跃 Agent**：inbox、步骤、状态、请求、验证、续跑 | "要**观察或拦截进行中的工作**时，使用它" |
| **能力事件** | `fs/*`、`tools/*`、`telemetry/*` | 不引入循环依赖就想挂策略与适配器时 |

**为什么必须分域**：实时流式帧**高频、瞬态**（`agent/assistant-stream` 发布进程本地的 start、瞬态 chunk、end frame），逐个写日志会爆炸。所以把**过程**与**事实**分离：收尾时把完整紧凑 stream **一次性**提交为 `assistant/message`（或仅日志的 `assistant/attempt`）。提交后 fork、恢复、transcript、遥测、持久化都从这些持久 settlement 派生；实时 UI 增量则来自 `agent/assistant-stream`。边界情形：进程在 settlement 之前**硬中断**，**不会**留下持久 attempt stream。
