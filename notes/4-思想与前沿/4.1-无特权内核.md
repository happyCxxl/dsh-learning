## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：把「无特权内核」这句话拆成**可检验的机制**——它由哪几件事共同构成、每件事在源码里落在哪个类/哪一行、以及它换来了什么、要付出什么。
**不是**：profile / bundle / patch 的组装顺序（那是 `1.2`）、能力 seam 的完整清单与三角色逐条对照（那是 `4.4`）。

### 0.2 现在只要记住 3 件事

1. **不存在「必须改它才能扩展」的模块**。扩展的方式是把插件挂到别的插件旁边；注册是**副作用**，插件卸载时自动撤销。
2. **「可替换」的落地单位是配置行**。任何出现在 `--dump-config` 输出里的条目都有 `id`，也就都能被你自己写的 patch 替换。
3. **唯一的具象实现也可以被换掉**。agent loop 是「唯一的具体循环插件」，但它自己就是一行配置——**唯一性来自配置选择，不来自代码特权**。

### 0.3 明确授权：这些现在不用管

- **seam 的三角色逐条对照、16 个不可直接加载的 seam 包清单**——属于 `4.4`；本课在 §3.2 / §4.2 只用到「Definition 不是 TypeScript `interface`」「提供方缺席必须显式失败」这两条结论；
- **patch 的语法与覆盖语义（浅赋值、`insert` 的两种形态）**——属于 `1.2`，本课只在 §3.3 描述叠加顺序时点名，不重讲；
- **`!!js` 表达式什么时候求值**——属于 `2.6`；本课 §5.4 的配置里会出现它，只要知道「它在 dump 里原样打印、在条目激活时求值」就够；
- **事件域 `agent/*` 的完整清单**——属于第三编；本课只把它当成「分包之后留下的稳定面」这一个事实用。
- 判断标准：只要你能说清本课提到的每个词**属于上面哪一件事**，就够了。

### 0.4 本课复用的词汇（不在这里重新定义）

`profile` / `bundle` / `patch` / 条目 `entry` / 层 `layer` 五个词已由 `1.1` 定义，叠加顺序由 `1.2` 定死；本课不重复。

## 1. 最小词汇表（本课新增的 6 个词）

| 词 | 大白话 | 在源码里的样子 |
|---|---|---|
| **插件树** | 启动时被叠出来的那棵东西，产品的每一部分都挂在它上面 | 运行中的 `dsh` 就是它；由 `cordis.yml` + 各层 patch 组合 |
| **驱动** | 真正「跑」一个 agent 的东西：发模型请求、跑工具、再重复 | `@deepseek-ai/dsh-agent-loop`，服务键 `ctx.agentLoop` |
| **工厂** | 一个「按需造 agent」的对象，驱动把自己注册成它 | `AgentFactory` 接口（`createAgent` / `resume` 两个方法） |
| **`ctx.<键>`** | 插件向共享上下文贡献出来的服务，别人用键取 | `ctx.agents`、`ctx.tools`、`ctx.llm` |
| **注册 = 副作用** | 挂上去的动作本身会产生效果，卸载时**成对撤销** | `ctx.effect(() => ctx.agents.setFactory(this), …)` |
| **显式失败** | 该在场的东西不在场，就报错，不偷偷给个默认实现 | `throw new Error('no agent factory registered (load an agent-loop plugin)')` |

> 表里前四个词属于「插件树／服务」这套体系；`4.4` 会把服务再细分成核心主干、可替换 seam、组合包与独立服务四类角色。

## 2. 先建立画面

### 2.1 静态结构：谁挂在谁旁边（不是谁写在谁里面）

```
                      空根 cordis.yml（内容只有 []）
                              │  各层 patch 依次 insert
                              ▼
   ┌──────────────────────── 插件树（一份配置清单）────────────────────────┐
   │  ctx.agents      = dsh-agent         ← 只有「接口 + 注册表」，不造 agent │
   │        ▲                                                              │
   │        │ ctx.effect(() => ctx.agents.setFactory(this))  ← 反向注册      │
   │        │                                                              │
   │  ctx.agentLoop   = dsh-agent-loop    ← 唯一的具体驱动，也是一行配置     │
   │                                                                       │
   │  ctx.llm / ctx.tools / ctx.shell / ctx.fs / …  ← 各是一条配置行          │
   └───────────────────────────────────────────────────────────────────────┘
```

**图上一处精确性说明**：箭头方向是「**驱动把自己的工厂塞进注册表**」，不是「注册表包含驱动的实现」。`dsh-agent` 里没有任何一行 import `dsh-agent-loop`（§4.1 第 4 块用依赖清单证明这一点），所以这条边只在**运行时**存在。

### 2.2 动态过程：一次「加一个模型适配器」要动哪些文件

```
       ① 写一个新包（实现适配器）        ← 唯一被改的东西
              │
              ▼
       ② 在配置里加一行（或改一行的提供方包名）
              │
              ▼
       ③ 重新启动 → 插件树重建 → 新提供方注册到 ctx.llm
              │
              ▼
       ④ 卸载或改回去 → 注册随 ctx.effect 一起撤销 → 不留残留
```

**全程没有第 ⑤ 步「改内核源码」。** 判据（反问式）：如果你能列出「必须改某个核心文件才能加的扩展点」，这个设计就被推翻了——文档的「新行为的归属位置」表把 20 类新行为**全部**指向「注册服务」或「监听事件」，**没有一类**指向「改内核」（`docs/architecture.zh.md` 第 147–168 行）。

### 2.3 大白话：用户敲一句话之前，机器里先发生了什么

来源标注：以下序列改写自 `docs/architecture.zh.md` 第 92–111 行的轮次流程伪代码（**是本笔记对它的白话转述**，不是原文照抄）；这一段**完全不用术语**，先建立画面。

1. 进程启动，先把一份「空表」铺在桌上。
2. 按顺序往上贴一张张「增补单」：先贴发行版自带的（共享那一份、界面那一份……），再贴你自己写的那份，最后贴命令行上临时指定的那份。
3. 每次贴完，桌上那张表就变一个样子；被后贴的条目点名的东西，会覆盖先贴的同名条目。
4. 贴完之后，这张表就是这次运行的**全部内容**：谁提供「跟模型说话」的能力、谁提供「跑命令」的能力、谁负责把 agent 转起来——每一样都在表上占一行。
5. 你敲进一句话之后：模型请求出发 → 回来的工具调用被派发出去 → 工具自己再决定要不要读文件、跑命令。
6. 这条链子上的每一环——模型适配器、工具、执行器、连「转起来」那个循环本身——**都是表上的一行**。
7. 所以想换掉任何一环，需要改的是**表**，不是**代码**。
8. 反过来说，如果某一环不在表上，它就不可能在这次运行里存在——这也是为什么「少配一行」等于「少一项能力」。

## 3. 结论先行

**一句话**：DSH 里不存在「必须打补丁才能扩展」的内核——产品的每一部分都是插件，包括 agent loop 本身，因此都可以从配置替换（`docs/architecture.zh.md` 第 11 行）。「无特权」描述的是**扩展权限的分布**：没有任何一个模块握有「只有改我才能加东西」的地位（`docs/architecture.zh.md` 第 13 行）。

三条可检验的推论：

| # | 推论 | 出处 |
|---|---|---|
| 1 | 扩展方式是「把插件挂载到其他插件旁边」，而不是修改内核源码 | `docs/architecture.zh.md` 第 13 行 |
| 2 | 各项注册是**副作用**，会在插件卸载时撤销——无特权同时意味着**无残留** | `docs/architecture.zh.md` 第 13 行 |
| 3 | 可替换性由 **seam**（Service Definition / Service Provider / Consumer 三角色）落地；替换一个提供方就能改变整个产品 | `docs/architecture.zh.md` 第 137、139 行 |

**两个必须知道的边界**（否则会把「无特权内核」理解错）：

- 它**不等于「没有核心服务」**。`ctx.sessions`、`ctx.tools`、`ctx.systemPrompt`、`ctx.agents` 这些主干服务真实存在，在能力 seam 表中的角色列标为 `core`（`docs/capability-seams.zh.md` 第 635 行；`ctx.sessions` 在第 591 行、`ctx.tools` 在第 627 行、`ctx.systemPrompt` 在第 626 行）。关键在于：这些主干**也是配置行**，照样可以被自己的 patch 替换。判据是文档原话——`--dump-config`「打印出的任何条目，都可以由你自己的 patch 替换」（`docs/architecture.zh.md` 第 39 行）。
- 它**与「权限／能力安全」无关**。DSH 里 `capability` 有两个互不相干的含义；设计笔记明确警告不要把「可替换实现」与权限／沙箱安全服务混淆（`.agents/notes/implemented/architecture/2026-06-13-capability-seams.zh.md` 第 34 行）。

**反问式判据**：如果能列出「必须改某个核心文件才能加的扩展点」，这个设计就被推翻了。文档的「新行为的归属位置」表把 **20 类新行为全部**指向注册服务或监听事件，没有一类指向「改内核」（`docs/architecture.zh.md` 第 147–168 行）。

## 4. 机制与源码对照

本节的规则：每个机制类知识点**就地**给源码块。每块上方标 `文件路径 第 A–B 行`；块内 `// …` 注释写明省了哪些行、为什么省；块下按「做什么 / 与哪个知识点相关 / 为什么这么写」讲。

### 4.1 agent 与 agent-loop 为什么要分包（本课最核心的一幕）

**先看结论，再看代码。** 四层证据，逐层收紧：

1. **设计理念（自述）**：公开的 `Agent` 接口与注册表在 `dsh-agent`，构造与驱动在循环包，并通过**已注册工厂**提供；「消费方因此依赖 `dsh-agent` 而不依赖 `dsh-agent-loop`，从而保持驱动器可替换」（`packages/core/agent/README.zh.md` 第 81 行）。
2. **注册方向**：循环包在 `ctx.agents` 上把自身注册为 `AgentFactory`，「因此消费方从不导入本包」（`packages/core/agent-loop/README.zh.md` 第 89 行）。
3. **惰性装配**：没有驱动器注册工厂之前，`ctx.agents` 保持惰性——随附驱动器是 `dsh-agent-loop`，「最小的可用组合需要同时加载两者」（`packages/core/agent/README.zh.md` 第 28 行）。
4. **依赖方向（可实测）**：`dsh-agent` 的 peerDependencies 里**没有** agent-loop，而 `dsh-agent-loop` 的 peerDependencies 里**有** `@deepseek-ai/dsh-agent`。依赖是单向的，替换循环包不会反向拖拽接口包。

配套的**事件域**是这条分包的真正用处：`agent/*` 事件让插件「无需依赖循环包即可作用于实时工作」（`packages/core/agent/README.zh.md` 第 67 行）；架构文档把「Agent 事件」与「会话事件」「能力事件」并列为三个事件域，并指出能力事件「无需导入循环即可向某个 seam 附加策略和适配器」（`docs/architecture.zh.md` 第 78–80 行）。

#### 第 1 块 驱动把自己「注册成工厂」的那三行

`packages\core\agent-loop\src\index.ts` 第 329–372 行

```ts
/** Concrete agent factory and driver service. */
export class AgentLoop extends Service implements AgentFactory {   // ← 类头：它既是一个 Cordis Service，又实现 AgentFactory
  static inject = ['agents', 'sessions', 'llm', 'tools', 'systemPrompt', 'sessionProjections']
  // （第 333–346 行的 static Config：声明式 agent 条目的 zod schema，本知识点用不到，此处省略）

  /** Validated configuration owned by the agent-loop service. */
  readonly config: Config
  private readonly ownership: FactoryOwnership
  /** Plain holder prevents Cordis from re-tracing the factory's dependency context through a caller shadow. */
  private readonly runtime: { ctx: Context }

  constructor(ctx: Context, config: Config) {                      // ← 构造函数：注册发生在这一步
    super(ctx, 'agentLoop')                                        // ① 服务键定名 = ctx.agentLoop

    this.config = {
      agents: applyLauncherIdentities(config.agents, ctx.get(CONFIGURED_AGENT_IDENTITIES_KEY)),
      maxParallelToolCalls: config.maxParallelToolCalls,
    }
    validateConfiguredAgents(this.config.agents)
    // Register only after every config validation above has passed, so a
    // rejected constructor leaves no projection unit behind.
    ctx.sessionProjections.register(turnBoundaryProjectionDefinition)
    ctx.sessionProjections.register(inboxProjectionDefinition)
    this.ownership = new FactoryOwnership(ctx.fiber)
    this.runtime = { ctx }
    ctx.effect(() => () => this.ownership.dispose(), 'agentLoop.transactions()')
    ctx.effect(() => ctx.agents.setFactory(this), 'agentLoop.setFactory()')   // ② 反向注册：把自己交给注册表
    ctx.systemPrompt.variable('provider', context => context.agent?.options.provider)
    ctx.systemPrompt.variable('model', context => context.agent?.options.model)
    ctx.systemPrompt.variable('cwd', context => context.agent?.session.header.cwd)
```

按块讲解：

- **做什么**：`AgentLoop` 在构造时（也就是这行配置被激活时）把 `this` 递给 `ctx.agents` 的工厂槽位。此后所有 `ctx.agents.create()` 都会转发到这个对象。
- **与哪个知识点相关**：这是 §4.1 第 2 条「注册方向」的源码本体——**消费方不导入循环包，是循环包主动把能力交出去**。
- **变量从哪来**：`ctx` 由 Cordis 在实例化服务时注入；`config` 来自配置行里的 `config:` 字段；`this.runtime` 是作者刻意留的「普通持有者」（注释原文 *Plain holder prevents Cordis from re-tracing the factory's dependency context through a caller shadow*），用来挡住 Cordis 的上下文追踪，理由在 §4.2 第 3 块会看到另一半。
- **为什么 `ctx.effect(() => …)`**：`ctx.effect` 返回一个**随插件卸载而执行的撤销器**。作者原文（第 362–363 行的注释）说明注册被刻意排在校验之后：*Register only after every config validation above has passed, so a rejected constructor leaves no projection unit behind*——配置坏了就根本不注册，不会留下半个服务。这就是 §3 推论 2「注册是可撤销副作用」的具体形态。
- **`static inject` 的作用**：声明本服务要求 `agents` / `sessions` / `llm` / `tools` / `systemPrompt` / `sessionProjections` 六项在场才激活。所以**漏挂 `ctx.agents` 的循环根本不会启动**，而不是启动后到处 `undefined`（这属于「缺席即显式失败」的家族，见 §4.2 第 2 块）。

#### 第 2 块 注册表那一侧：工厂是「可换的插槽」，不是「写死的依赖」

`packages\core\agent\src\index.ts` 第 346–374 行（只保留与「工厂插槽」直接相关的两个方法；第 375 行的 `requireFactory` 见第 3 块）

```ts
  /**
   * Register the agent-creation factory (the loop calls this on construction,
   * effect-scoped). A traced Cordis service is canonicalized to its concrete
   * target; each create/resume call is then traced through that caller's
   * context so ownership follows the caller without stacking proxy layers.
   * Throws if a factory is already registered. Returns the disposer; on
   * dispose the factory slot is cleared.
   * @param factory - the loop-owned factory {@link create}/{@link resume} delegate to.
   * @returns the disposer that clears the factory slot. The exact
   *   Cordis effect disposer (single-shot): composite (generator) effects may
   *   yield it directly — exact identity nests the teardown in order.
   */
  setFactory(factory: AgentFactory): () => void {                  // ← 方法头：入参就是「谁来当工厂」
    const dispose = this.ctx.effect(() => {                        // ① 整个登记也是一个 effect
      if (this.factory !== undefined) throw new Error('an agent factory is already registered')
      // Avoid stacking two Cordis shadow layers when a caller passes a Service
      // already read through a context. Calls are re-traced through their
      // actual owner context below.
      const target = (factory as AgentFactory & { [symbols.original]?: AgentFactory })[symbols.original] ?? factory
      this.factory = { target }                                    // ② 只保存一个「普通持有者」，不保存代理
      return () => { this.factory = undefined }                    // ③ 撤销 = 把插槽清空
    }, 'agents.setFactory()')
    // （第 368–374 行的注释与 return dispose：解释为什么返回的是「那个原始的 effect disposer」，
    //   属于 Cordis effect 语义细节，与本知识点无关，此处省略）
```

按块讲解：

- **做什么**：给注册表装上一个「造 agent 的人」。装第二个会**抛错**（`an agent factory is already registered`），不是静默覆盖。
- **与哪个知识点相关**：①「工厂」这个词的准确含义就是这两个方法（`createAgent` / `resume`）；②「唯一性来自配置选择」在源码层面的样子——插槽只允许一个占用者，但**占用者是谁由配置决定**。
- **③ 为什么撤销是清空插槽**：卸载循环包时，`ctx.agents` 会**退回「没有工厂」的状态**，而不是留着一个指向已死对象的引用。配合第 3 块的守卫，退回后任何创建请求都会**明确报错**。
- **② 为什么保存 `target` 而不是原对象**：注释原文 *Avoid stacking two Cordis shadow layers when a caller passes a Service already read through a context*。`dsh-agent-loop` 自己就是一个 `Service`，直接存它会在每次调用上多套一层上下文代理；作者取「原始对象」并在真正调用时按调用方上下文重新追踪（第 3 块 ③ 的 `getTraceable`）。
- **为什么这段的「为什么」能直接引作者原文**：`setFactory` 上方的 JSDoc 是本文件作者写的，不是本笔记的推断。

#### 第 5 块 代价那一侧：创建是一笔「受回滚保护的事务」

分包不是免费的。替换循环包意味着你得自己实现整套生命周期语义——README 的原文把顺序写死了（`packages/core/agent-loop/README.zh.md` 第 110、114 行）。下面这段是它在源码里的样子：

`packages\core\agent-loop\src\index.ts` 第 708–751 行

```ts
  /**
   * Create a fresh agent through an explicit owner context: acquire the session,
   * prepare the private agent, enter both registries, announce both creations,
   * and start the loop. Rollback covers every earlier step when a later one
   * fails. Config-declared agents use {@link create} instead, which is owned by
   * this plugin's fiber rather than by a caller.
   * （第 708–713 行 JSDoc 的 @param/@returns 行，与本知识点无关，此处省略）
   */
  async createAgent(ownerCtx: Context, options: CreateAgentOptions): Promise<AgentHandle> {   // ← 方法头：AgentFactory 的公开入口
    const runtime = options.setup === undefined ? this : getTraceable(ownerCtx, this)
    const parent = options.parentAgent
    if (parent !== undefined && !ownerCtx.agents.has(parent.id)) {
      throw new Error(`parent agent ${JSON.stringify(parent.id)} is not live`)
    }
    // Fail before any resource is acquired when a session id is already live,
    // so a rejected call leaves nothing to roll back.
    assertIdle(ownerCtx, options.sessionId)

    const meta = options.meta ?? {}
    const session = this.prepare(ownerCtx, options.sessionId, options.agentOptions, meta)   // ① 组装私有会话
    const prepared = session.prepared
    try {
      prepared.ownerCtx = ownerCtx
      await prepared.transaction.run(async () => {                 // ② 从这里起，任何失败都会被回滚
        // Setup runs before publication, so scoped registrations exist for the
        // first request and the announcement describes a complete world.
        await options.setup?.(prepared.agentCtx, prepared.agent)    // ③ 可选的 setup：只做注册，不驱动
        prepared.commit?.()
        const handle = await prepared.publish('create')             // ④ 进两个注册表 + 宣告 + 放行排队输入
        this.ownership.track(handle.dispose)
        this.ownership.watch(handle.agent)
      })
    } catch (error: unknown) {
      prepared.dispose()                                           // ⑤ 失败 → 回滚这一步已准备的资源
      throw error
    }
    // （第 741–751 行：把新 agent 交给 ownership 跟踪并返回解析出的数据，见下方讲解）
  }
```

按块讲解：

- **做什么**：创建一个新 agent = **取会话 → 组装私有 agent → 跑 setup → 进注册表 → 宣告 → 放行排队的工作**，中间任何一步失败都回滚已准备的资源，最后返回一个 `AgentHandle`。
- **与哪个知识点相关**：§4.1 开头那句「代价由 agent 侧承担」。文档也直接给出适用条件：「只有标准的『调用模型、运行工具、重复』生命周期无法满足需求时，才应选择自定义 `Agent` 实现」（`packages/core/agent-loop/README.zh.md` 第 12 行）。
- **变量从哪来**：`ownerCtx` 是注册表在转发时显式传进来的**调用方上下文**（第 2 块 ③ 提到「重新追踪」就是为它服务）；`options.setup` 来自调用方（`CreateAgentOptions.setup`，定义在 `dsh-agent` 的接口里，语义见 `packages/core/agent/README.zh.md` 第 43 行「setup 只做组合」）；`prepared` 是 `this.prepare(...)` 返回的准备结果，`transaction` / `commit` / `publish` / `dispose` 都是它的成员。
- **①②⑤ 为什么值得单独说**：`assertIdle` 与 `parentAgent` 检查放在**取任何资源之前**（注释原文 *Fail before any resource is acquired … so a rejected call leaves nothing to roll back*），取到资源之后则整段包在 `transaction.run` 里，`catch` 里 `prepared.dispose()`。**「先检查、后取资源、全程可回滚」是这段的全部结构**——换成自己写驱动，这套结构要重做一遍。
- **③ 为什么 setup 必须在 publish 之前**：注释原文 *Setup runs before publication, so scoped registrations exist for the first request and the announcement describes a complete world*——宣告出去的必须是一个**完整的世界**，否则监听器会在半成品上做判断。
- **省略说明**：第 741–751 行的收尾（`ownership.track` / `watch` / 返回值组装）与本知识点无关，此处省略；`prepare()` 的完整实现（第 479–640 行）也没有贴，它属于「创建一台具体驱动器」的实现细节，本课只用到它的**调用位置**。

### 4.2 三件事同时成立，才叫「无特权」

| 机制 | 内容 | 出处 |
|---|---|---|
| 一切皆插件 | 模型适配器、工具注册表、会话日志，以及 **agent loop 本身**都是插件，「因此每个都可以从配置替换」 | `docs/architecture.zh.md` 第 11 行 |
| 挂载而非补丁 | 扩展 = 把插件挂到别的插件旁边；注册是可逆副作用 | `docs/architecture.zh.md` 第 13 行 |
| 配置层叠加 | 空条目列表 → 各 bundle → profile 的 `cordis.patch.yml` → home 级 patch → `--patch` overlay；patch 按 `id` 定位条目并替换其整个 config，或插入新条目 | `docs/architecture.zh.md` 第 27 行 |

第三件事是前两件的**可操作性来源**：只要某个东西出现在 `--dump-config` 里，它就有 `id`，就逃不出 patch 的射程（`docs/architecture.zh.md` 第 39 行）。三件事的源码落点分别是 §4.1 第 1 块（注册 = 副作用）、§4.1 第 2、3 块（工厂插槽可换）、以及 `1.2` 全篇（层叠加与 patch 语义）。

### 4.3 seam：可替换性的落地单位

一个 **seam** 是一项可替换能力，包含三种角色：声明接口的 **Service Definition**、实现它的 **Service Provider**、使用它的 **Consumer**（通常就是面向模型的工具）（`docs/architecture.zh.md` 第 137 行；同一术语的规范条目见 `docs/glossary.zh.md` 第 9 行）。

三条硬性约定：

- **Service Definition 绝不是 TypeScript `interface`**，而是拥有 `ctx.<key>` 的 Cordis `Service`（抽象类或具体注册表）（`.agents/notes/implemented/architecture/2026-06-13-capability-seams.zh.md` 第 17 行）。
- 拆分的动机是**变化速率不同**：约定、实现、消费方 API 以不同速率、因不同原因变化；捆在一个包里会把它们耦合起来（同上第 9 行）。
- **不要预防性拆分**：如果一项能力只有一种可设想的提供方和一个消费方，就保持为一个包，直到出现第二个（同上第 25 行）。LLM seam 就是这么合并的：Definition 与 Consumer 同在 `dsh-llm`，因为它的 Consumer 就是 agent loop 本身。

seam 的杠杆效应写在架构文档里：文件系统与进程提供方共享同一个执行世界，所以把它们指向远程沙箱，也就把 Bash、PTY 和 LSP 一并搬了过去，无需提供方专用 fork（`docs/architecture.zh.md` 第 139 行）。

### 4.4 内核里到底还剩什么

| 东西 | 角色 / 事实 | 出处 |
|---|---|---|
| `ctx.agents`（`dsh-agent`） | 角色 `core`；拥有实时 Agent 句柄、创建／恢复工厂 seam、进程本地发起方传播 | `docs/capability-seams.zh.md` 第 635 行 |
| `ctx.agentLoop`（`dsh-agent-loop`） | 角色标为 `bundle`；「**唯一的具体循环插件**；扩展包依赖 dsh-agent 的事件和服务，而不依赖此包」 | `docs/capability-seams.zh.md` 第 637 行 |

也就是说：「无特权」的准确边界是——**主干服务存在，但它只有一个具象驱动器，而驱动器自身也是可替换的配置行**。`core` 与 `seam` 是角色标签，不是特权等级。

## 5. 极端示例：把「无特权」推到底的 sdk-minimal

`dsh-sdk-minimal` 是刻意保留的例外：一个组合包**拥有完整的显式 Cordis 配置树，不应用 `dsh-base`**（`docs/architecture.zh.md` 第 25 行），其 patch 文件开头即声明「this insert is the complete Cordis tree」（`packages/bundle/sdk-minimal/cordis.patch.yml` 第 1–3 行）。它自己的 README 说得更直白：「该 bundle 的单个 insert 就是完整应用配置树」（`packages/bundle/sdk-minimal/README.zh.md` 第 51 行）。

这个例子的教学价值在于：**每一个行为都是一行显式配置**，包括那些容易被误当成内核的东西。下面四块源码就是这句判断的证据。

#### 第 6 块 一个「包」可以什么都不是：入口只有 `export {}`

`packages\bundle\sdk-minimal\src\index.ts` 第 1–9 行（**整文件照录**）


按块讲解：

- **做什么**：这个包的运行时代码是**零**。它的实体是 `cordis.patch.yml`，通过 manifest 字段 `dsh.bundle.patch` 被 profile 组装器解析（第 3–4 行的作者注释原文）。
- **与哪个知识点相关**：§5 开头那句「一个完整的应用形态可以只是一份配置清单加一个空模块」——**这是「无特权内核」的最强证据**。
- **为什么这么写**：如果产品形态必须由代码决定，那这个包至少得有一段「装配逻辑」；而这里一行逻辑都没有，说明装配逻辑**属于框架与 profile 组装器**，不属于这个产品形态。第一次看到「包入口是空的」会觉得像 bug，但它是有意的：作者在 JSDoc 里直接写了 *this module carries no runtime interface*。
- **粒度说明**：本块只有 9 行（低于 R11 建议的 15–40 行）。它本来就是一个完整文件（第 1–9 行），**整文件照录即自解释**——硬凑行数反而要把不相干的 `package.json` 混进来。

## 附录 A 关键问题与答案

> ✅ 四道题**全部给出明确答案**，不留空、不写「待补充」。

### ① 「无特权内核」的准确含义？

**答**：存在三件同时成立的事实——

1. 产品每一部分都是插件，包括 agent loop 本身，因此每个都可以从配置替换（`docs/architecture.zh.md` 第 11 行）。**源码落点**：`AgentLoop` 是一个 `Service`，构造时用 `ctx.effect(() => ctx.agents.setFactory(this), …)` 把自身交出去（`packages\core\agent-loop\src\index.ts` 第 369 行）。
2. 扩展的方式是把插件挂载到其他插件旁边，而不是修改内核，且注册是会在插件卸载时撤销的副作用（`docs/architecture.zh.md` 第 13 行）。**源码落点**：`setFactory` 的撤销器把插槽清空（`packages\core\agent\src\index.ts` 第 366 行）。
3. 任何出现在 `--dump-config` 里的条目都能被自己的 patch 替换（`docs/architecture.zh.md` 第 39 行）。**实例**：`sdk-minimal` 的 27 行全部带 `id`（`packages\bundle\sdk-minimal\cordis.patch.yml`）。

**准确表述**：「不存在需要打补丁的特权内核」= 不存在「只有修改它才能扩展」的模块。它**不**意味着没有核心服务（`ctx.agents` 等角色仍标为 `core`，`docs/capability-seams.zh.md` 第 635 行），也**不**意味着没有唯一的具象实现（agent loop 就是「唯一的具体循环插件」，`docs/capability-seams.zh.md` 第 637 行）——它意味着**唯一性来自配置选择，而不是来自代码特权**。

**易混点**：不要把这里的「能力（capability，指可替换实现）」与权限／沙箱意义上的能力安全混为一谈（`.agents/notes/implemented/architecture/2026-06-13-capability-seams.zh.md` 第 34 行）。

### ② 至少 3 个「可以被替换掉」的实现，以及替换的代价

|---|---|---|---|
| `ctx.shell`（bash 执行器） | `bash-local`、`bash-sandbox`、`pwsh-local` | 换执行器即可，工具 schema 不动 | `docs/capability-seams.zh.md` 第 642 行 |
| `ctx.llm`（模型适配器） | `llm-deepseek`、`llm-pi-ai`、`llm-replay` | 适配器注册提供方实现，循环与压缩调用与提供方无关的流服务 | `docs/capability-seams.zh.md` 第 587 行 |
| `ctx.fs`（文件系统） | `fs-local`、`fs-sandbox`、`fs-ssh` | `tool-fs` 通过 `ctx.fs` 读写，换提供方不改工具 | `docs/capability-seams.zh.md` 第 650 行 |
| `ctx.subprocess`（进程） | `subprocess-local`、`subprocess-ssh` | Bash 执行器、PTY 后端、LSP Host 与进程外 subagent 后端都经由它 spawn | `docs/capability-seams.zh.md` 第 641 行 |

| `ctx.subagents`（委派） | spawn／fork／acp／codex／claude-code／dsh-sdk 共 6 个 | 同一上下文可并存多个按名注册的提供方 | `docs/capability-seams.zh.md` 第 652 行 |

**替换的代价**（逐条带出处）：

1. **Definition 包不能直接加载，必须换成具体实现包**。config-catalog 专门有「Seam 包（不可直接加载）」一节，说明这些抽象服务类「部署时应改为加载具体的实现包」（`docs/config-catalog.zh.md` 第 4452–4454 行）。该节实为 **16 个**包（第 4459–4474 行）。
2. **契约面常常远超「换个函数」**。会话存储后端的契约是 `create`/`open`/`stat`/`list`/`export`，且 `create`/`open` 返回承担全部日志访问与**单写者所有权**的 `SessionHandle`（`docs/architecture.zh.md` 第 167 行；`docs/subsystems/persistence.zh.md` 第 7 行）。进程提供方则要承担受管的 `DSH_*` 环境命名空间、共享的凭据清除（`scrubbedParentEnv`）与 `CollectedOutput` 形状（`docs/subsystems/subprocess.zh.md` 第 5 行）。
3. **某些替换会连带搬家**。fs 与进程提供方共享同一执行世界，把它们指向远程沙箱会把 Bash、PTY 和 LSP 一并搬过去（`docs/architecture.zh.md` 第 139 行）——这既是收益也是代价：能力包之间必须成对替换才自洽。
4. **角色拆分本身要付样板成本**。设计笔记「后果」一节的原文就是：分离角色会**增加包和样板代码**（`package.json`、`tsconfig`、README 和注入接线）（`.agents/notes/implemented/architecture/2026-06-13-capability-seams.zh.md` 第 38 行）。
5. **提供方缺席时必须显式失败，不能静默兜底**。host 读取方要么在激活时要求服务，要么在注册表或必需 key 缺席时明确失败；贡献方不得为缺失的 host 值静默提供默认值（`docs/architecture.zh.md` 第 133 行）。这意味着替换／漏配的失败会直接暴露，而不是被默认实现掩盖——排障时是好事，装配时是负担。（这条「排障时是好事、装配时是负担」的取舍判断**标注为推断**：文档只写了「必须显式失败」，没有为它评价利弊。）
6. **替换循环本身是最高代价的一档**：需要自己承担创建事务、teardown 顺序与持久化写句柄获取（`packages/core/agent-loop/README.zh.md` 第 110、114 行；源码形态见本文第 5 块），所以文档只建议在标准「调用模型、运行工具、重复」生命周期不敷使用时才自写（`packages/core/agent-loop/README.zh.md` 第 12 行）。

### ③ 这个设计的收益与代价分别是什么？

**答（收益）**：

- **替换一个提供方就能改变整个产品**（`docs/architecture.zh.md` 第 139 行）。例如沙箱化执行器替换 `bash-local` 时无需触碰任何工具 schema（`.agents/notes/implemented/architecture/2026-06-13-capability-seams.zh.md` 第 23 行）。
- **变化速率解耦**：Service Provider 与 Consumer 独立发布和版本管理，「新后端永远不会波及面向模型的约定」（同上第 38 行）。
- **扩展不靠打补丁且可撤销**：注册是副作用，插件卸载即撤销（`docs/architecture.zh.md` 第 13 行；源码形态见本文第 1、2 块）；20 类新行为都有文档化的落点（`docs/architecture.zh.md` 第 147–168 行）。
- **组合即产品形态**：同一套机制既能装出 94 行的共享 base（实测数行数），也能装出 27 行的独立极简树（实测；`docs/architecture.zh.md` 第 25 行）。

**答（代价）**：

- **包与样板增加**：拆角色要付 `package.json`、`tsconfig`、README 与注入接线的成本（`.agents/notes/implemented/architecture/2026-06-13-capability-seams.zh.md` 第 38 行）。
- **装配成本转移到部署侧**：16 个 seam 包不可直接加载，配置必须点名具体实现包（`docs/config-catalog.zh.md` 第 4452–4474 行）；少配一行就是缺服务。
- **缺席即显式失败**，没有静默默认值（`docs/architecture.zh.md` 第 133 行；源码形态见本文第 3 块）。
- **需要按平台／环境手写多行**：极简 profile 里 Bash 与 PowerShell 是两行配置，靠 `disabled` 表达式二选一（`packages/bundle/sdk-minimal/cordis.patch.yml` 第 53–64 行；见本文第 9 块）。
- **极简组合会连调试能力一起被裁掉**：`sdk-minimal` 排除压缩、文件系统工具、workspace 指令、skill、jobs 与 subagent，需要这些就得改选 `dsh --profile sdk`（`packages/bundle/sdk-minimal/README.zh.md` 第 12、95 行）。
- **用户 patch 能扩展配置树，也就能破坏协议**：向 stdout 写普通文本的插件会破坏 JSON-RPC 分帧（`packages/bundle/sdk-minimal/README.zh.md` 第 96 行）——「无特权」把自由度交给了使用者，也把责任交了出去。

### ④ agent 与 agent-loop 分包的用意是什么？

**答**：把**「约定 + 注册表」**与**「构造 + 驱动」**分开，用**已注册工厂**连接，从而让驱动器可替换、让消费方永不依赖具体循环。具体四点：

1. **职责分离**：公开的 `Agent` 接口与注册表在 `dsh-agent`，构造与驱动在循环包；「消费方因此依赖 `dsh-agent` 而不依赖 `dsh-agent-loop`，从而保持驱动器可替换」（`packages/core/agent/README.zh.md` 第 81 行）。
2. **反向注册**：循环包在 `ctx.agents` 上注册为 `AgentFactory`，「消费方从不导入本包」；包内部实现绝不属于公开接口（`packages/core/agent-loop/README.zh.md` 第 89 行）。**源码落点**：本文第 1 块的 `ctx.effect(() => ctx.agents.setFactory(this), 'agentLoop.setFactory()')`。
3. **依赖单向**：`dsh-agent` 不依赖 agent-loop（`packages/core/agent/package.json` 第 34–44 行），agent-loop 以 peer 依赖 `dsh-agent`（`packages/core/agent-loop/package.json` 第 30 行）。能力 seam 表把这条总结为：「扩展包依赖 dsh-agent 的事件和服务，而不依赖此包」（`docs/capability-seams.zh.md` 第 637 行）。**证据形态**：本文第 4 块。
4. **事件域作为稳定面**：`agent/*` 事件让插件无需依赖循环包即可观察或拦截进行中的工作（`packages/core/agent/README.zh.md` 第 67 行），这正是第 3 点得以成立的原因。架构文档的表也是这么分工的：`core/agent` 提供「`Agent` 接口、活跃 agent 注册表和 `agent/*` 事件」，`core/agent-loop` 是「实现该接口的默认驱动器」（`docs/architecture.zh.md` 第 66–67 行）。

**它同时是「无特权内核」的一个实例**：`ctx.agents` 角色是 `core`，`ctx.agentLoop` 是「唯一的具体循环插件」——主干与具体实现被拆到两端，主干保持稳定，具象实现保持可换（`docs/capability-seams.zh.md` 第 635、637 行）。装配上两者仍必须同时在场：「最小的可用组合需要同时加载两者」（`packages/core/agent/README.zh.md` 第 28 行）；源码形态就是第 3 块的 `NO_FACTORY_MESSAGE`。

**不这么拆的后果**：任何想拦截一步、观察流式输出或给单个 agent 加能力的插件，都会被迫依赖具体的循环包实现，替换循环就会牵连全部扩展包——这正是 seam 设计笔记要解决的「变化速率耦合」问题（`.agents/notes/implemented/architecture/2026-06-13-capability-seams.zh.md` 第 9 行）。
