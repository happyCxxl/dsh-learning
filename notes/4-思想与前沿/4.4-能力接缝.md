## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：一条**判据**（什么才配叫 seam）＋ 一套**角色落点**（三角色在仓库里分别落在哪些包）＋ 一张**波及面清单**（换掉一个提供方会动到什么，逐条给源码）。

**不是**：`Service` / `inject` / `ctx.effect` 的机制细节（第二编 `2.2`、`2.3`）；组合文件的语法（`1.3`、`1.4`）；subagent 的运行期语义（第三编 `3.14`）；能力表的生成器实现（工具链）。

### 0.2 现在只要记住这 5 件事

1. **seam 不是"一个接口"，是三种角色的整体**：**Service Definition**（这项能力是什么）、**Service Provider**（它怎么做）、**Consumer**（谁在用）三者齐备才叫 seam；**任何单一角色都不叫 seam**。
2. **Service Definition 一定是 cordis 的 `Service`**——抽象类，或具体注册表服务——**绝不是 TypeScript `interface`**。
3. **seam 的卖点是"换一个提供方就改变整个产品"**：`ctx.fs` 与 `ctx.subprocess` 共享同一个执行世界，把它们指向远程沙箱，Bash、PTY、LSP 就一起搬了过去。
4. **"面向模型的工具 schema 没变"≠"什么都没波及"**：仍有四层会真实变化（§2.3 一张图，§6 逐层给源码）。
5. **多数服务不是 seam**：能力表 92 行 `ctx.<key>` 里只有 33 行角色是 `seam`，55 行是主干 `core`（§10.1 是本次重写的实测）。

### 0.3 明确授权：这些现在**不用管**

- **92 行服务表怎么逐行读** —— 只要会用"角色"这一列就够：`seam`＝可替换、`core`＝主干、`service`＝独立服务、`bundle`＝组合包提供的。
- **`Service` / `inject` / fiber 挂起的实现**（"缺服务就挂起""卸载就撤销"到底怎么做的）——属第二编 `2.2` / `2.3`；本课只在**可见效果**这一层用到它（换提供方可能给组合增加必需服务）。
- **能力表的生成器与完整性守卫**（`scripts/gen-doc-graphs.ts`）——属工具链；本课只用一个结论：**那张表是从 Cordis 声明里生成并做完整性校验的**。
- **subagent 的持续执行（continuable）编排细节** —— 属第三编 `3.14`；本课只用它证明"同一接口后为什么能千差万别"。
- **远程执行家族（SSH）的传输与生命周期** —— 本课只引用它的**坐标语义**这一面，传输细节不展开。

## 1. 最小词汇表（本课新增的 7 个词）

| 词 | 大白话 | 源码/文档里的写法 |
|---|---|---|
| **Service Definition** | 这条能力的**"是什么"**：拥有自己的 `ctx.<key>` 与词汇类型 | `export abstract class FileSystem extends Service` ＋ `super(ctx, 'fs')` |
| **Service Provider** | 这条能力的**"怎么做"**：一个真正实现或注册实现的包 | `fs-local` / `fs-sandbox` / `fs-ssh` |
| **Consumer** | 这条能力的**"谁在用"**：注入该服务的一方（通常是面向模型的工具） | `export const inject = ['tools', 'fs', 'systemPrompt']` |
| **seam** | **三角色合起来的整体**（不是接口，也不是普通扩展点） | 能力表"角色"列里的 `seam` |
| **单服务 seam** | 一个 context **只允许一个**提供方，装第二个会抛错 | `ctx.fs`、`ctx.shell`、`ctx.sandbox`、`ctx.subprocess` |
| **注册表 seam** | 一个 context **可共存多个**提供方，调用方按名字选 | `ctx.subagents`、`ctx.llm` |
| **执行世界（execution world）** | `ctx.fs` 与 `ctx.subprocess` **共同描述**的那个"文件＋进程"世界 | 决策原文 "…jointly define one execution world" |

> ⚠️ 这 7 个词只到"够用"为止。`Service` 怎么挂载、`inject` 怎么挂起，属第二编。
> **角色名的大小写是规范的一部分**：**Service Definition** / **Service Provider** / **Consumer** 用标题式；泛指的 `provider` / `consumer` 用小写。（出处见 §11.1）

## 2. 先建立画面

### 2.1 三角色长什么样（静态结构）

```
┌──────────────────────────── Service Definition ────────────────────────────┐
│ 一个 cordis Service：拥有 ctx.<key> ＋ 词汇类型（类 / 类型 / 错误码）        │

│   注册表：spawn | fork | acp | codex | …     ← 可共存，按名选              │
└───────────────────────────────┬───────────────────────────────────────────┘
                                │ inject 取用（不导入提供方类型）
┌───────────────────────────────┴───────────────────────────────────────────┐
│ Consumer                                                                  │
│   面向模型的工具：tool-fs / tool-bash / tool-subagent                      │
│   其它插件：api/workspace-files / lsp-stdio / fs-observation-policy         │
└───────────────────────────────────────────────────────────────────────────┘
```

**精确性说明（两处简化）**：

1. 图上"实现/注册"画成同一条竖线，但**单服务 seam 与注册表 seam 不是同一件事**——前者"加载第二个就抛错"，后者"注册进一个 Map、同名抛 `DUPLICATE_PROVIDER`"（§3.1 块 2、块 3 与 §9.1 有源码）。
2. 上图画的是**角色，不是包**：一个包可以同时承担多个角色——LLM seam 就把 Definition 与 Consumer 合并在 `dsh-llm` 里（设计笔记第 25 行）。

### 2.2 大白话版：把"文件系统"换成另一个提供方，机器里发生了什么

**完全不用上面的术语**，先建立画面（来源：设计笔记 `2026-07-28-portable-execution-world-consumers.zh.md` 第 9–17 行的"问题/决策"两节＋`packages\fs\fs-sandbox\src\index.ts` 第 47–56 行的类注释；这里只做白话转述）。

1. 产品跑起来时，有一项叫"文件系统"的能力；**谁提供它，写在组合文件的一行上**（不是写在代码里）。
2. 读文件、写文件、编辑文件的那批工具**不认任何具体实现**：它们只认"这项能力在不在"，用的时候现取。
3. 现在把那一行从"本地磁盘实现"改成"沙箱强制实现"（或"远端 SSH 实现"）。
4. 工具一行没改，工具的说明书（schema）也没改。
5. 但**换进来的实现自己可能还要别的服务**（沙箱实现要一份沙箱策略）：缺了它，这个实现起不来。
6. 而且"文件系统"不只搬字节：它还回答**"这个文件在别的能力眼里叫什么"**——子进程能打开的路径、`file:` URL、包含关系。换了实现，这些答案的**含义**就变了。
7. 记录"这个文件我读过没有"的策略插件，是按**实现自己发的 id** 记账的；换了实现，旧账对新实现没有意义。
8. 有些工具会调用"可选动作"（例如"盯着这个文件变化"）。可选动作不是每个实现都支持；换了实现，这类工具会**明确报一个错误码**，而不是默默不响。
9. 最后：如果**连进程能力一起换**（同一个执行世界的两份实现），那么 Bash、终端、语言服务器也一起搬走了——因为它们本来也只认这两项能力。

→ 所以"可替换"不是"随便换一个实现"，而是 **换一行 ＋ 承担四类波及**（第 5–8 步）。

### 2.3 换一条接缝的提供方，会波及哪四层（动态过程）

```
换提供方（组合里的一行）
   │
   ├─ ① 提供方自带的注入依赖     例：fs-sandbox 多要 sandboxPolicy；
   │                               bash-sandbox 多要 subprocess ＋ sandbox ＋ sandboxPolicy
   ├─ ② 跨能力坐标的语义         例：processPath / processPathFromHostPath / fileUrl / contains
   │                               本地＝宿主绝对路径；远端＝远端命名空间里的路径
   ├─ ③ 策略插件记录的 key 空间   例：fs-observation-policy 按 targetKey 记账，而 targetKey 由后端拥有
   └─ ④ 依赖可选原语的消费方      例：watch() 在基类里直接以 FS_IO_ERROR 拒绝；
                                   api/workspace-files 会调它，并把失败映射成 workspace-file/watch-unsupported
   │
   └─ 不被波及：面向模型的工具 schema、工具实现、策略插件的代码
```

来源：这四层全部来自本节所列源码文件的实读——`packages\fs\fs\src\index.ts`、`packages\fs\fs-sandbox\src\index.ts`、`packages\shell\bash-sandbox\src\index.ts`、`packages\ssh\fs-ssh\src\index.ts`、`packages\fs\fs-observation-policy\src\index.ts`、`packages\api\workspace-files\src\changes.ts`（§6 逐块给源码）。

## 3. 角色一：Service Definition

### 3.1 Definition 必须是 cordis `Service`（三例源码）

**结论（带出处）**：Definition 是"拥有 `ctx.<key>` 与词汇类型的 cordis `Service`"，**可以是抽象类**（fs / shell / sandbox / subprocess），**也可以是具体注册表服务**（subagents / llm），**绝不是 TypeScript `interface`**。
出处（文档）：架构文档第 137 行；术语表 `capability-seam` 条目；设计笔记 `2026-06-13-capability-seams.zh.md` 第 15–19、25 行；术语表 `seam` 条目的硬规则——*"任何单一角色、普通边界或扩展点都不能称为 seam"*。

**块 1：`ctx.fs` 的声明与抽象 Service**

`packages\fs\fs\src\index.ts` 第 45–48 行 ＋ 第 81–90 行

```ts
declare module '@deepseek-ai/cordis' {
  interface Context {
    fs: FileSystem
  }
}
// （第 50–79 行：本 seam 的三个 fs/* 事件声明——fs/write-intent、fs/edit-intent、fs/observed——
//   属"策略如何挂上去"的知识点，与"Definition 是什么"无关，此处省略；§6.3 会用到 fs/observed。）

/**
 * Abstract filesystem provider. Targets must preserve identity across aliases;
 * reads expose regular UTF-8 text or typed errors, listings are stable and
 * content-free, and mutations are atomic. Optional guards add stale protection
 * without changing the unguarded provider contract.
 */
export abstract class FileSystem extends Service {
  constructor(ctx: Context) {
    super(ctx, 'fs')
  }
  // （第 92–293 行：watch / sandboxMode 的基类默认实现，以及全部 abstract 方法签名；
  //   基类默认见 §3.3，抽象方法逐个列在 §11.2 的源码出处表里）
}
```

按块讲解：

- **`declare module '@deepseek-ai/cordis'`**：这是**类型层的登记**，让 `ctx.fs` 在 TypeScript 里有类型。它只是类型声明，不带任何运行时行为——所以"`ctx.fs` 存在"这件事最终由 §4 的某个提供方在运行期兑现。
- **`export abstract class FileSystem extends Service`**：**这一句才是"Definition 是 cordis `Service`"的落点**。继承 `Service` 是"我要在共享登记处占一个名字"的机制前提（挂载/卸载机制属第二编 `2.2`、`2.3`）。
- **`super(ctx, 'fs')`**：`ctx.fs` 里那个 `fs` **不是文档起的名字，而是代码里写死的字符串**。想知道某个 `ctx.<key>` 是谁提供的，就搜这个字符串——与 `1.1` §6 的 `super(ctx, 'sessions')` 完全同型。
- **为什么是 `abstract`**：抽象类**不能自己单独加载**，必须由提供方继承后再挂载。所以"Definition 不提供实现"不是纪律，而是形态：`FileSystem` 自己进不了插件树。
- **为什么不能是 `interface`**：`interface` 不能继承 `Service`、不能 `super(ctx, key)`，因此**无法拥有 `ctx.<key>`**。术语表把这一点写成硬规则（§11.1）。

**块 2：`ctx.shell` —— 第二个 Definition，附带"单服务规则"的作者原文**

`packages\shell\shell\src\index.ts` 第 30–34 行 ＋ 第 36–40 行 ＋ 第 64–93 行（JSDoc 只留第一段与两个方法签名）

```ts
declare module '@deepseek-ai/cordis' {
  interface Context {
    shell: ShellExecutor
  }
}

/**
 * Abstract bash execution service. Subclass, implement the abstract methods,
 * and load the subclass as a plugin — it registers as `ctx.shell` (one
 * implementation per context; loading a second throws, which is cordis'
 * standard duplicate-service behavior).
 */
// （第 42–63 行：JSDoc 其余部分——"前台/后台是调用方等什么的属性"，
//   以及 5 条实现必须遵守的语义；与本块的"单服务规则"无关，此处省略。
//   按 R11 的纪律不整段贴 JSDoc。）
export abstract class ShellExecutor extends Service {
  constructor(ctx: Context) {
    super(ctx, 'shell')
  }

  // （第 69–76 行：sandboxMode 的基类默认实现与它的 JSDoc，见 §3.3）
  abstract resolve(request: ShellExecRequest): ShellExecSpec

  abstract execute(spec: ShellExecSpec): Promise<ShellExecution>

```

按块讲解：

- **"one implementation per context; loading a second throws, which is cordis' standard duplicate-service behavior"**（第 38–40 行）是**单服务 seam 的权威表述**，也是 §2.1 图上那处简化的修正依据。它的运行期证据在测试里：装第二个实现时抛 `/service "shell" has been registered/`（`packages\shell\shell\tests\service.spec.ts` 第 83–88 行）；fs 侧同样（`packages\fs\fs\tests\service.spec.ts` 第 101–105 行）。
- **只有两个抽象方法**（`resolve` 第 84 行、`execute` 第 93 行）：Definition 的抽象面**刻意窄**。命令默认值、deadline、输出上限都在 `resolve` 里被实现方补齐——所以换执行器时，**面向模型的工具不需要知道这些**。
- **`sandboxMode` 有基类默认**（第 74–76 行，返回 `undefined`）：这是"能力事实"的第二个实例（与 §3.3 的 `FileSystem.sandboxMode` 同型）。作者在 fs 侧的注释里直接点明这是"mirrors `ShellExecutor.sandboxMode`"。
- 与块 1 的共同点：**两个 Definition 都只依赖"约定所需的词汇"**——`dsh-shell` 导出 `ShellExecutor` / `ShellRunResult` / `ShellProcess` 等，不依赖任何提供方（设计笔记第 17 行）。

**块 3：`ctx.subagents` —— 具体注册表服务（不是抽象类）**

按块讲解：

- 这里的 Definition **不是抽象类，而是具体服务**（`SubagentRuntime extends TypertRemoteService`）。术语表把两种形态并列写出：*"可以是 `ShellExecutor` 这样的抽象类，也可以是 `WebRuntime` 这样的具体注册表服务"*——本块就是后者的实例。
- **`private providers = new Map<string, SubagentProvider>()`：注册表 seam 的实现本体就是一个 Map**。与块 2 的"装第二个就抛错"对照阅读，**"单服务 vs 注册表"的分界就在这一行**。
- 名字从哪来：`SubagentProvider.name`（`packages\subagent\subagent\src\types.ts` 第 345–346 行）；注册时以它为键（§9.1）。
- `TypertRemoteService` 是"这个服务可通过类型化 Remote 暴露给客户端"的基类；它属客户端/服务框架那一编，本课不展开。
- **为什么这一类能力要用注册表**：子系统文档写明理由是"同一上下文中可共存多个提供方实现"，并指出它**跟随 LLM 适配器注册表，而不是单服务的 bash 执行器**（`docs\subsystems\subagent.zh.md` 第 5 行）。

### 3.2 三条接缝的三角色分工（仓库里的落点）

| 角色 | `ctx.fs` | `ctx.shell` | `ctx.subagents` |
|---|---|---|---|
| **Service Definition** | `packages/fs/fs` | `packages/shell/shell` | `packages/subagent/subagent` |
| **Service Provider** | `fs-local`、`fs-sandbox`、`fs-ssh` | `bash-local`、`bash-sandbox`、`pwsh-local` | `spawn`、`fork`、`acp`、`codex`、`claude-code`、`dsh-sdk` |
| **Consumer** | `tool-fs`、`tool-str-replace-editor`、`tool-present`、`lsp-stdio`、`client/ui-deliverables` | `tool-bash`、`tool-pwsh`、`hooks-claude-code`、`hooks-codex` | `tool-subagent`、`tool-subagent-control`、`tool-ralph` |

这份清单的权威来源是 `docs\capability-seams.zh.md`：它由 `scripts/gen-doc-graphs.ts` 从 Cordis 声明中发现并分类，且**设有完整性守卫**（第 669 行）。本文用到的四行：`ctx.fs` 第 650 行、`ctx.subagents` 第 652 行、`ctx.shell` 第 642 行、`ctx.subprocess` 第 641 行。

**其它 Definition 的具体形态**（`ctx.fs` / `ctx.shell` / `ctx.subagents` 已在 §3.1 逐块给出）：

### 4.2 提供方二：`bash-sandbox`（注入依赖从 1 项涨到 3 项）

**块 6：三项 inject ＋ 只包装 argv、不执行命令**

按块讲解：

- **`static override inject = ['subprocess', 'sandbox', 'sandboxPolicy']`**：与 `bash-local` 的 `static inject = ['subprocess']`（`packages\shell\bash-local\src\index.ts` 第 97–98 行）对照——**同类能力换成沙箱版，注入依赖从 1 项增加到 3 项**。这是"波及第①层"的第二个实例，也是**最容易漏掉的一层**：某个提供方要求的新服务若没挂上，组合起不来。

- **一个方法论提醒**：`bash-local` 与 `bash-sandbox` 的差异集中在"注入依赖 + 一层包装"，这正说明**三角色分离要买的东西**是"替换时改动面收窄"，而不是"替换时零改动"。

### 6.0 四层一览（先结论）

### 6.1 第①层：提供方自带的注入依赖

已由块 5（`fs-sandbox`）、块 6（`bash-sandbox`）给出源码，这里只补两条对照事实：

### 6.2 第②层：跨能力坐标的语义

**块 8：远端提供方重写了四个坐标方法**

按块讲解：

- **`static inject = ['ssh', 'sandboxPolicy']`**：第三条提供方、又一次不同的注入依赖。
- **`processPathFromHostPath` 在基类返回 `undefined`**（`packages\fs\fs\src\index.ts` 第 152–155 行），远端 README 明确它"返回 `undefined`，因此需要已安装可执行文件或引导程序的消费方必须显式提供远端产物"（第 30 行）——这是"可选坐标"的又一处诚实默认。

```ts
  //   与本块"key 空间"无关，此处省略）

  /**
   * Decide the write intent: unseen or confirmed absent ⇒ `createIfAbsent`;
   * confirmed present ⇒ `replaceIfVersion` at the observed version.
   */
  writeIntent(target: FsTarget, actor: object | undefined): FsWriteIntent {
    const owner = this.owner(actor)
    const prior = owner ? this.get(owner, target.targetKey) : undefined
    return prior?.kind === 'present'
      ? { kind: 'replaceIfVersion', version: prior.version }
      : { kind: 'createIfAbsent' }
  }
}
```

按块讲解：

- **两层 key：owner（弱引用，通常是会话）→ `targetKey`（后端拥有的不透明 id）**。所以这条策略的状态**按后端发的 id 记账**，而不是按"用户输入的路径字符串"记账。
- **`targetKey` 是什么，由 Definition 的类型注释定义**：*"The local backend uses a realpath-like string; a remote backend might use a workspace URI or file id. Consumers MUST NOT parse it or assume it is a local absolute path."*（`packages\fs\fs\src\types.ts` 第 12–14 行）→ **换后端 ＝ 换 id 空间**。
- **策略插件自己一行都不用改**：它只按不透明 key 存取，对 `targetKey` 的唯一要求是"同一个文件给同一个 key"。所以"波及第③层"的表现不是"插件坏了"，而是"**旧观测对新后端没有意义**"。（标注为**推断**：源码只说明 id 由后端拥有；"跨后端迁移时同一会话里已有观测会怎样"没有找到明文规定。）
- **`writeIntent` 的返回值是数据不是动作**（`createIfAbsent` / `replaceIfVersion`）：策略只决定"意图"，原子性由提供方保证。这与 §2.2 大白话第 7 步对应。
- **该包不注册任何服务**：模块注释第一句是 *"Event-only filesystem observation policy; it registers no service"*（第 1–2 行），它是纯 `fs/*` 事件消费方。这正是"策略插件不在 seam 三角色里、却能在不引入循环依赖的前提下挂上去"的形态（与 `1.1` §8 的"能力事件"一节呼应）。

### 6.4 第④层：依赖可选原语的消费方会降级

**块 10：真实消费方怎么处理"不支持 watch"**

`packages\api\workspace-files\src\changes.ts` 第 78–104 行（其中第 97 行的 `processPath` 在 §6.2 也会用到）


### 6.5 没被波及的（这才正是三角色分离要买的东西）

## 8. 一个执行世界：为什么 fs ＋ 进程能一起搬

### 8.1 决策原文

架构文档把结论写成一句话，并注明来源是那条设计决策（`docs\architecture.zh.md` 第 139 行）：**seam 正是"替换一个提供方就能改变整个产品"的原因**——文件系统与进程提供方共享同一个执行世界，因此把它们指向远程沙箱，也就把 Bash、PTY 和 LSP 一并搬了过去，**无需提供方专用 fork**。

决策原文规定（`.agents\notes\implemented\architecture\2026-07-28-portable-execution-world-consumers.zh.md` 第 17 行）：

> `ctx.fs` 与 `ctx.subprocess` 共同定义一个执行世界。共同挂载的提供方必须描述相同的路径命名空间、可执行文件、进程和终端会话；上层能力消费这两个接口，而不引用具体提供方。

**分工**（同文第 21、23 行）：

- **文件系统**负责路径事实——规范化进程路径、规范化 `file:` URI、包含关系（对应 `processPath` / `fileUrl` / `contains`）。
- **进程管理**负责可执行文件查找、`spawn`、`spawnTerminal`（接口签名见 `packages\subprocess\subprocess\src\index.ts` 第 133–137、153、155–162 行）。

**进程侧 Definition 的形态**（同前文已引处）：

- `export abstract class SubprocessRuntime extends Service` ＋ `super(ctx, 'subprocess')`（第 117–120 行）；
- 模块注释把边界写死：*"Command defaulting, shell semantics, deadlines, protocol framing, terminal readiness, and presentation belong to consumers"*（第 4–6 行）——即**进程 seam 只管机制，语义归消费方**。

### 8.2 三个上层消费方，全都只走这两条接缝

- **Bash**：`bash-local` 只注入 `subprocess`，把 Bash 语义映射到普通 `spawn()`（`packages\shell\bash-local\src\index.ts` 第 97–98 行；决策第 27 行）。
- **PTY**：`terminal-bash` 注入 `['terminals', 'sandboxPolicy', 'sessionProjections', 'subprocess']`（`packages\terminal\terminal-bash\src\index.ts` 第 27 行），并把终端分配交给 `ctx.subprocess.spawnTerminal`（第 190–192 行）；决策第 29 行记录了"本地 `node-pty` 与进程检查实现移入 `dsh-subprocess-local`"。
- **LSP**：`lsp-stdio` 注入 `['fs', 'lsp', 'subprocess']`（`packages\lsp\lsp-stdio\src\index.ts` 第 47 行），用 `ctx.subprocess.resolveExecutable` 找可执行文件（第 146 行）、把 `ctx.fs` 传进连接（第 154 行）、用 `ctx.subprocess.spawn` 启动（第 157 行）；模块注释写明*"Providers read sources through `ctx.fs` and launch servers through `ctx.subprocess`, so both local and remote implementations share one host"*（第 6–7 行）。

### 8.3 被否决的方案（值得单独记，因为它说明"为什么不给每个远程提供方配一套 PTY/LSP"）

**为每个远程提供方各留一套 PTY 与 LSP 包被否决**，理由：那会在既有 seam 之上**重复实现提供方机制**（决策第 43 行）。远程提供方要负责的是可变文件、命令与终端进程、语言服务器进程；宿主仍负责 agent loop、会话日志、模型传输、权限与 subagent 编排（第 35 行）。

### 8.4 落地实例与两条边界

**SSH 家族就是这条例子的落地**：一张表同时给出 `ctx.ssh`、`ctx.fs`（`fs-ssh`）、`ctx.subprocess`（`subprocess-ssh`）、`ctx.sandbox`（`sandbox-ssh`）四个角色（`packages\ssh\README.zh.md` 第 23–28 行）。`fs-ssh` 的卖点正是*"文件工具读写的文件与远端 Bash、终端、语言服务器和 Node 程序看到的文件一致"*（`packages\ssh\fs-ssh\README.zh.md` 第 12 行）——**这就是"共享一个执行世界"的可观察后果**。

**边界一（同一词、不同信任级别）**：`fs-sandbox` 的围栏是**可信代码里的策略检查，不是内核边界**；内核级隔离归 `ctx.shell`（`bash-sandbox`）（`packages\fs\fs-sandbox\src\index.ts` 第 10–18 行）。

**边界二（`ctx.sandbox` 覆盖到哪为止）**：它只覆盖**与宿主共享内核和文件系统**的子进程；容器、microVM 与远程执行是**替换整个能力**，而不是在它下面注册（`packages\sandbox\sandbox\src\index.ts` 第 1–5 行；`packages\sandbox\README.zh.md` 第 12 行）。

## 9. subagent：同一接口后为什么能千差万别

**分化靠四件东西，而接口本身只有两个方法**：`SubagentProvider.start`（必需）＋ 可选的 `prepareContinuable`（`packages\subagent\subagent\src\types.ts` 第 344–390 行）。

### 9.1 第一件：注册名即选择

**块 12：`registerProvider` —— 注册是 effect 作用域的，同名抛 `DUPLICATE_PROVIDER`**

`packages\subagent\subagent\src\index.ts` 第 503–526 行

```ts
  /**
   * Register a provider under its name. Registration is effect-scoped and HMR
   * safe; removing a provider blocks new starts but does not revoke runs that
   * were already returned to their holders.
   * @param provider - the trusted provider implementation.
   * @returns the exact Cordis effect disposer.
   */
  registerProvider(provider: SubagentProvider): () => void {
    const name = provider.name
    // oxlint-disable-next-line typescript/no-misused-promises -- synchronous disposer
    return this.ctx.effect(function* (this: SubagentRuntime) {
      if (this.providers.has(name)) {
        throw new SubagentError(`a subagent provider named "${name}" is already registered`, 'DUPLICATE_PROVIDER')
      }
      this.providers.set(name, provider)
      yield () => {
        this.providers.delete(name)
        this.emitLifecycle('subagent/provider-removed', name)
      }
      // A throwing added-listener unwinds the yielded rollback, matching the
      // repository's fail-loud registration semantics.
      this.ctx.emit('subagent/provider-added', provider)
    }.bind(this), 'subagents.registerProvider()')
  }
```

按块讲解：

- **`provider.name` 就是键**（第 511 行）：注册名即选择名，调用方按名取用（`getProvider` / `list`，第 533–543 行）。
- **`this.ctx.effect(function* …)` 是一个生成器**：`yield () => { … }` 那一块是**回滚函数**——卸载时删掉 Map 项并 emit `subagent/provider-removed`。`effect` / 生成器 / `yield` 的机制属第二编 `2.3`（可逆副作用），本课只读它的可见效果：**注册与撤销是同一个函数里成对写下的**。
- **同名抛 `DUPLICATE_PROVIDER`**（第 514–516 行）——与单服务 seam 的"装第二个就抛错"是同一类纪律，但**粒度不同**：这里冲突的是"名字"，不是"服务键"。所以同一 context 里 `spawn` 与 `acp` 可以共存，但不能有两个 `spawn`。
- **移除提供方不撤销已发出的 run**（JSDoc 第 505–506 行）：改动只影响**后续** start。
- **消费方那一侧**：`tool-subagent` 把提供方名做成配置项——`provider: string`，注释写明*"The `ctx.subagents` provider name to start runs on (e.g. `spawn`, `acp`)"*（`packages\subagent\tool-subagent\src\index.ts` 第 47–50 行），schema 里是必填（第 107 行）。**基础组合里同一个包被挂两次，只差一行配置**：第 370–375 行 `provider: spawn`、第 383–388 行 `provider: fork`（`packages\bundle\base\cordis.patch.yml`）。

### 9.2 第二件：静态能力描述符，在 `start()` 之前校验

**块 13：五个 flag 的定义**

`packages\subagent\subagent\src\types.ts` 第 119–136 行

```ts
/**
 * Which START-TIME features a provider supports. Checked by the service before delegating to
 * {@link SubagentProvider.start}: a request that needs a capability the chosen provider lacks
 * is rejected with a typed error rather than accepted-then-ignored (the "fail loud, no silent
 * degradation" rule). These flags describe the ONE-SHOT
 * {@link SubagentProvider.start} path, where the provider composes the child;
 * continuable children are composed by the continuation manager itself and are
 * gated by {@link SubagentProvider.prepareContinuable} instead. Each flag
 * corresponds one-to-one to a {@link SubagentStartRequest} option: `depthLimit`
 * to `maxDepth`; the other names match.
 */
export interface SubagentCapabilities {
  readonly agentOptions: boolean
  readonly outputSchema: boolean
  readonly depthLimit: boolean
  readonly toolFilter: boolean
  readonly persona: boolean
}
```

按块讲解：

- **五个 flag 一一对应一个"启动期选项"**（JSDoc 最后一句给出映射：`depthLimit` ↔ `maxDepth`，其余同名）。这就是"差异放进**数据**而不是接口膨胀"的形态：接口方法数不变，能力用**布尔表**表达。
- **"fail loud, no silent degradation"**（JSDoc 原话）：请求要求的能力若提供方没有，**明确拒绝**，绝不"接受后静默忽略"。
- **它只管一次性（one-shot）路径**：可继续子级由 continuation 管理器自己组合，用**方法存在性**把关（§9.4）。所以"两类能力、两种发现方式"是**有意设计**（子系统文档第 15 行）。
- **为什么需要它**：注册表里各提供方的实现能力天差地别（进程内 vs 进程外）。若没有这张表，消费方只能"试一下看会不会失败"——那就是静默降级。

**块 14：服务在 `start()` 之前逐项检查（fail loud 的落点）**

`packages\subagent\subagent\src\index.ts` 第 641–658 行（`start()` 里的调用点在第 557–559 行）

```ts
  /** Reject the first requested capability that the provider lacks. */
  private assertCapabilities(provider: SubagentProvider, request: SubagentStartRequest): void {
    const needs: { when: boolean; cap: keyof SubagentCapabilities }[] = [
      { when: request.agentOptions !== undefined, cap: 'agentOptions' },
      { when: request.outputSchema !== undefined, cap: 'outputSchema' },
      { when: request.maxDepth !== undefined, cap: 'depthLimit' },
      { when: request.toolFilter !== undefined, cap: 'toolFilter' },
      { when: request.persona !== undefined, cap: 'persona' },
    ]
    for (const { when, cap } of needs) {
      if (when && !provider.capabilities[cap]) {
        throw new SubagentError(
          `subagent provider "${provider.name}" does not support the "${cap}" capability`,
          'UNSUPPORTED_CAPABILITY',
        )
      }
    }
  }
```

按块讲解：

- **`needs` 是"请求里出现了这个选项"与"它需要哪个能力"的对照表**：`when` 由请求对象解构而来（`request.agentOptions !== undefined` 等），`cap` 是 `SubagentCapabilities` 的键名——**与块 13 的五个 flag 一一对应**。
- **`if (when && !provider.capabilities[cap]) throw`**：报的是**第一个**不满足的能力（JSDoc 首句 *"Reject the first requested capability that the provider lacks"*），错误码 `UNSUPPORTED_CAPABILITY`。因为它在 for 循环里，**一次只报一项**——消费方修好一项再跑，会看到下一项。
- **它在哪里被调用**：`start()` 的第 559 行 `this.assertCapabilities(provider, request)`，**在 `expectProvider(name)`（第 558 行）之后、任何委派之前**——所以"服务在单次 run 存在之前即行检查"（子系统文档第 15 行）在代码上就是这两行的先后顺序。
- **与 §3.1 块 3 的联系**：`provider.capabilities` 是注册表里每个 `SubagentProvider` 自带的字段（`types.ts` 第 348 行），所以**校验用的是提供方自己公布的事实**，服务的代码里没有一张"哪个提供方支持什么"的硬编码表。
- **还有一份"持久描述符"**：`start()` 在委派前先用 `snapshotSubagentDescriptor({ mode: 'one-shot', provider: name, … })` 拍一份**进入子级会话的描述**（`index.ts` 第 562–564 行）。所以"差异写进数据"这句话在 subagent 上其实有**两份数据**：一份是提供方公布的**能力描述符**（决定能不能 start），一份是写进日志的**持久描述符**（决定事后怎么读这个 run）。前者是校验用的，后者是可观测性用的——**两者都以 `provider` 名为核心字段**。

### 9.3 第三件：进程外后端统一公布"全 false"

**块 15：一个共享常量，说明为什么进程外做不到**

`packages\subagent\subagent\src\out-of-process.ts` 第 51–63 行

```ts
/**
 * The capability advertisement of an out-of-process backend: NONE. A child in
 * another process cannot honor parent-enforced start features
 * (`agentOptions`/`outputSchema`/`maxDepth`/`toolFilter`/`persona`), so the service rejects a
 * request needing any of them before `start` runs — never accepted-then-ignored.
 */
export const NO_START_CAPABILITIES: SubagentCapabilities = Object.freeze({
  agentOptions: false,
  outputSchema: false,
  depthLimit: false,
  toolFilter: false,
  persona: false,
})
```

按块讲解：

- **`Object.freeze`**：这是**共享常量**，冻住以防某个后端就地改它——因为四个进程外后端（`acp` / `codex` / `claude-code` / `dsh-sdk`）都引用它。
- **理由写在 JSDoc 里**：*"A child in another process cannot honor parent-enforced start features"*——**能力差异来自结构，不来自实现质量**。所以"公布全 false"不是偷懒，而是诚实。
- **四个后端的引用位置**：`acp` 在自己的类里展开五项全 `false`（`packages\subagent\subagent-acp\src\index.ts` 第 147–151 行）；`codex` 与 `claude-code` 直接 `readonly capabilities = NO_START_CAPABILITIES`（各自第 64、74 行）；`dsh-sdk` **只开一项**：`{ ...NO_START_CAPABILITIES, agentOptions: true }`（`packages\subagent\subagent-dsh-sdk\src\index.ts` 第 110–113 行），并把它接到自己的类字段上（第 135 行）。
- **进程内 `spawn` 五项全 `true`**（`packages\subagent\subagent-spawn-in-process\src\index.ts` 第 41–48 行），并附 `inheritsParentContext = false`（第 49–50 行）。
- **一句话总结这一节**：**"同一接口后千差万别"之所以不破坏约定，是因为差别被写进了数据（这张布尔表），而不是写进了方法签名。**

### 9.4 第四件：可选方法存在即能力

- `prepareContinuable?` 的**方法存在性就是能力**：服务在没有它的提供方上直接拒绝可继续启动，错误码 `UNSUPPORTED_CAPABILITY`（`packages\subagent\subagent\src\index.ts` 第 594–607 行：`if (provider.prepareContinuable === undefined) throw …`）。
- **它只回数据**（可选父级历史 seed），不含 Agent、句柄、提示词投递、结果、dispose 或恢复操作（`packages\subagent\subagent\src\types.ts` 第 231–244 行：`ContinuableCreateSpec` 的注释原话是 *"This is DATA, never a capability: it carries no Agent, `AgentHandle`, prompt delivery, result, disposal, or resume operation"*）。
- 因为**可继续的生命周期由 continuation 管理器持有**（`packages\subagent\subagent\src\index.ts` 第 14–22 行：*"Continuable children never become a `SubagentRun`"*）。
- 消费方配置侧同样把关：`backgroundMode: continuable` 要求提供方有 `prepareContinuable`（`packages\subagent\tool-subagent\src\index.ts` 第 345–349 行）。

### 9.5 第五件（收口）：返回值只承诺公共词汇

- **`SubagentRun` 只有四个成员**：`id`、`localAgent`、`result`、`dispose()`（`packages\subagent\subagent\src\types.ts` 第 308–334 行）。
- **`localAgent` 对远程 run 是 `undefined`**（第 315–320 行；远程发布路径见 `packages\subagent\subagent\src\out-of-process.ts` 第 245–258 行的 `subprocessRunHandle`，其中 `localAgent: undefined` 是写死的）。
- **`result` 绝不 reject**（第 321–328 行：*"Does NOT reject on a child-level failure — a model/transport failure resolves with `stopReason: 'error'`"*）；结算实现见 `out-of-process.ts` 第 182–219 行的 `settleRunResult`（catch 分支把 rejection 压成 `stopReason: 'error'` 或 `'aborted'`）。
- **于是"新建一个进程内子 agent"与"把一个轮次委派给另一个产品"在消费方看来是同一种东西**：靠 `localAgent === undefined` 与 `stopReason` 就能一致处理（原始结论）。
- **一条容易读错的细节**：事件里的 `provider` 字段只标明**启动该 run / Activation 时段时**的提供方，**并不声明该 edge 发出时提供方仍处于注册状态**——作者原文：*"Provider name recorded when the child was first created. The provider may be absent when an accepted one-shot run becomes ready or a persisted Activation cold-resumes, because neither lifecycle depends on continued registration."*（`types.ts` 第 80–94 行；`docs\subsystems\subagent.zh.md` 第 457 行）。这与 §9.1 的"移除提供方不撤销已发出的 run"是同一件事的两面。

### 9.6 最后一道保险：消费方也按能力 fail loud，并随提供方增减挂载工具

**块 16：`tool-subagent` 在加载时校验自己的配置**

`packages\subagent\tool-subagent\src\index.ts` 第 328–358 行

```ts
  const assertSubagentProviderConfiguration = (subagentProvider: SubagentProvider): void => {
    if (ctx.subagents.resolveMaxDepth(config.maxDepth) !== undefined && !subagentProvider.capabilities.depthLimit) {
      throw new Error(
        `tool-subagent: provider "${subagentProvider.name}" cannot enforce maxDepth (no depthLimit capability) — `
        + 'set maxDepth: \'provider-managed\' to leave the recursion budget to the provider',
      )
    }
    if (config.agentOptions !== undefined && !subagentProvider.capabilities.agentOptions) {
      throw new Error(
        `tool-subagent: provider "${subagentProvider.name}" does not support child agentOptions`,
      )
    }
    if (modelSelectionCapable && !subagentProvider.capabilities.agentOptions) {
      throw new Error(
        `tool-subagent: provider "${subagentProvider.name}" does not support child model selection`,
      )
    }
    if (continuable && subagentProvider.prepareContinuable === undefined) {
      throw new Error(
        `tool-subagent: provider "${subagentProvider.name}" does not support \`backgroundMode: continuable\``,
      )
    }
  }

  // Validate provider-owned config outside the optional LLM binding so an
  // invalid provider always rejects its registration or this plugin's load.
  ctx.on('subagent/provider-added', (subagentProvider) => {
    if (subagentProvider.name === config.provider) assertSubagentProviderConfiguration(subagentProvider)
  })
  const initialProvider = ctx.subagents.getProvider(config.provider)
  if (initialProvider !== undefined) assertSubagentProviderConfiguration(initialProvider)
```

按块讲解：

- **变量从哪来**：`config` 是本插件的配置（`provider` / `maxDepth` / `backgroundMode` / `agentOptions` …，第 47–104 行）；`modelSelectionCapable` 与 `continuable` 在同函数上游算出（`config.modelSelectionSettings === true`、`(config.backgroundMode ?? 'one-shot') === 'continuable'`，第 321–325 行）。
- **四道守卫，四类不匹配**：`maxDepth` ↔ `depthLimit`（并给出替代方案 `'provider-managed'`）、`agentOptions` ↔ `agentOptions`、模型选择 ↔ `agentOptions`、可继续模式 ↔ `prepareContinuable`。**每一道都抛异常，一律不降级。**
- **两条校验时机**：`subagent/provider-added` 监听器（第 354–356 行）管**运行期后到的提供方**；`getProvider` 立刻查一次（第 357–358 行）管**已经就绪的提供方**。注释写明理由：*"Validate provider-owned config outside the optional LLM binding so an invalid provider always rejects its registration or this plugin's load."*
- **"随提供方增减挂载/卸载工具"的落点**（同文件第 579–593 行）：`subagent/provider-added` → `mount(provider)`（先 `assertSubagentProviderConfiguration`）；`subagent/provider-removed` → `mounted.disposeTool()`；若当下没有该提供方，只记一条 info 日志*"…not registered yet; the … tool will register when it appears"*。
- **第三层保险在真正 start 之前**（第 509–511 行）：解析完子级 LLM 路由后**再检查一次提供方身份没变**——*"subagent provider … changed while resolving the child LLM route; retry the delegation"*。于是"提供方在配置校验与真正 start 之间被换掉"这种竞态也不会静默通过。
- **本节与三角色的关系**：定义侧（服务）校验一次、提供方侧（布尔表）公布一次、消费方侧（自己的配置）再校验一次——**"fail loud"在三角色上各有一道，这就是"契约"在无特权内核里的样子**。

### Q1 seam 的三角色定义？为什么"单一角色不是 seam"？

**三角色**：

1. **Service Definition** —— 拥有自己的 `ctx.<key>` 与词汇类型的 **cordis `Service`**；**可以是抽象类**（`ShellExecutor`），**也可以是具体注册表服务**（`WebRuntime`、`SubagentRuntime`），**绝不是 TypeScript `interface`**。
2. **Service Provider** —— 实现或注册实现的插件（如 `dsh-bash-local`）；沙箱化与远程提供方是**依据同一 Definition 实现/注册的兄弟包**。
3. **Consumer** —— 注入该服务、面向模型或插件编程的一方（通常是工具，如 `dsh-tool-bash`）；它**注入服务键，从不导入提供方特有的类型**。
出处（文档）：`docs\architecture.zh.md` 第 137 行；`docs\glossary.zh.md` 第 7–9 行；设计笔记 `2026-06-13-capability-seams.zh.md` 第 15–19 行；`docs\i18n\terminology.md` 第 59 行。

**为什么单一角色不是 seam**：seam 的整个卖点是"**替换一个提供方就能改变整个产品**"，这个命题要求三者齐备——只有定义没有提供方＝**空接口**；只有实现没有消费方＝**死代码**；只有消费方没有定义＝**硬编码实现**。术语条目把它写成硬规则：*"任何单一角色、普通边界或扩展点都不能称为 seam"*。

**可验证的反例**：能力表 92 行里只有 33 行角色是 `seam`；`ctx.tools`（工具注册表）角色是 `core`（`docs\capability-seams.zh.md` 第 627 行），因为不存在"工具注册表提供方"这一可替换角色。

**反过来**：允许一个包承担多个角色——LLM seam 把 Definition 与 Consumer 合并进 `dsh-llm`（设计笔记第 25 行：Consumer 是 agent loop 本身，而非可替换的 schema 接口），所以**不要在只有一个提供方时就预防性拆包**。

### Q2 挑一条接缝（fs），说明换提供者会波及哪些层。

**不会被波及的**：面向模型的工具 schema 与工具实现、策略插件代码。
证据：`packages\fs\fs\README.zh.md` 第 32 行*"挂载任一后端都会填充 `ctx.fs`；更换后端不会改变策略插件、工具或工具 schema"*；`docs\subsystems\filesystem.zh.md` 第 5 行*"替换后端不会改变策略或工具 schema"*；`fs-sandbox` 类注释第 48–50 行*"loading it INSTEAD OF `dsh-fs-local` … the model-facing tools are untouched"*。

**会被波及的四层**（§6 每层都有源码块）：

1. **提供方的注入依赖**：`fs-sandbox` 需要 `sandboxPolicy`（`packages\fs\fs-sandbox\src\index.ts` 第 56 行），`fs-local` 不需要；同类对照是 `bash-local` 的 1 项 vs `bash-sandbox` 的 3 项。
2. **跨能力坐标语义**：`processPath` / `processPathFromHostPath` / `fileUrl` / `contains`（`packages\fs\fs\src\index.ts` 第 134–173 行）从**宿主绝对路径**（`fs-local` 第 140–147 行）变成**远端命名空间路径**（`packages\ssh\fs-ssh\src\index.ts` 第 29–36 行）；下游 `api/workspace-files`（第 350、437 行）与 `lsp-stdio`（第 154 行）读的就是这些值。
3. **策略插件的状态 key**：`fs-observation-policy` 按 `targetKey` 存观测（第 21–28、61–71 行），而 `targetKey` 是**后端拥有的不透明 id**（`packages\fs\fs\src\types.ts` 第 11–16 行），换后端就换 id 空间。
4. **依赖可选原语的消费方**：`watch()` 基类以 `FS_IO_ERROR` 拒绝（`packages\fs\fs\src\index.ts` 第 100–105 行），`api/workspace-files` 直接调它（`...\changes.ts` 第 79 行）并映射为 `workspace-file/watch-unsupported`（第 87–88 行），`fs-ssh` 明确不支持（`packages\ssh\fs-ssh\README.zh.md` 第 70 行）。

**替换动作本身只是组合里的一行**：`fs-sandbox` 行（`packages\bundle\base\cordis.patch.yml` 第 516–519 行）；生产基础组合挂的是它，而全仓库 `*.yml` 里 `dsh-fs-local` 只出现在两个测试/快照夹具中（`packages\context\session-reference\tests\fixtures\cordis.yml` 第 4 行；`snapshots\sdk\persistent-tools\cordis.yml` 第 139–142 行）。

### Q3 为什么"把 fs 与进程指向远程沙箱"能把 Bash、PTY、LSP 一起搬走？

**因为 `ctx.fs` 与 `ctx.subprocess` 共同定义一个执行世界**：共同挂载的提供方必须描述**相同的路径命名空间、可执行文件、进程和终端会话**，而上层能力**只消费这两个接口、不引用具体提供方**（决策文档第 17 行；`docs\architecture.zh.md` 第 139 行）。
分工：fs 提供 `processPath` / `fileUrl` / `contains` 等**路径事实**；进程 seam 提供**可执行文件查找、`spawn`、`spawnTerminal`**（决策第 21、23 行；`packages\subprocess\subprocess\src\index.ts` 第 133–162 行）。

**三个消费方早已只走这两条 seam**：

- **Bash**：只注入 `subprocess`（`packages\shell\bash-local\src\index.ts` 第 98 行）。
- **PTY**：把终端分配交给 `ctx.subprocess.spawnTerminal`（`packages\terminal\terminal-bash\src\index.ts` 第 27、190–192 行）。
- **LSP**：通过 `ctx.fs` 读源码 ＋ 通过 `ctx.subprocess` 启动服务器（`packages\lsp\lsp-stdio\src\index.ts` 第 6–7、47、146–157 行）。

本地 `node-pty` 与平台进程检查因此**移进了 `dsh-subprocess-local`**（决策第 29 行）。

**被否决的方案**：为每个远程提供方各留一套 PTY 与 LSP 包——理由只是**在既有 seam 之上重复实现提供方机制**（决策第 43 行）。远程提供方只需负责可变文件、命令与终端进程、语言服务器进程（第 35 行）；产物就是 SSH 家族一张表换掉四个服务（`packages\ssh\README.zh.md` 第 23–28 行），以及 `fs-ssh` 的"同一批文件"承诺（`packages\ssh\fs-ssh\README.zh.md` 第 12 行）。

**边界**：`ctx.sandbox` seam 只覆盖**与宿主共享内核与文件系统**的子进程；容器/microVM/远程执行是**替换整个能力**而非在其下注册（`packages\sandbox\sandbox\src\index.ts` 第 1–5 行；`packages\sandbox\README.zh.md` 第 12 行）。另外 `fs-sandbox` 的围栏是**可信代码的策略检查、不是内核边界**，内核级隔离归 `bash-sandbox`（`packages\fs\fs-sandbox\src\index.ts` 第 10–18 行）——**两条 seam 的信任级别不同，别混用**。

### Q4 subagent 提供者为什么能在同一接口后千差万别？

**因为接口只承诺"一次可 dispose 的前台委派 ＋ 一个终态结果"**（`SubagentRun`：`id` / `localAgent` / `result` / `dispose`，`packages\subagent\subagent\src\types.ts` 第 308–334 行），其余差异全部被推到**数据**与**可选方法**上：

1. **注册名用于选择**：`registerProvider` 以 `provider.name` 为键、同名抛 `DUPLICATE_PROVIDER`（`index.ts` 第 510–526 行）；消费方把提供方名做成配置项 `provider`（`tool-subagent\src\index.ts` 第 47–50、107 行）；基础组合里同一个包挂两次，只差 `provider: spawn` / `provider: fork` 一行。
2. **静态能力描述符在 `start()` 之前校验并 fail loud**：五个 flag（`types.ts` 第 130–136 行）由服务逐项检查，缺了就抛 `UNSUPPORTED_CAPABILITY`，而不是接受后静默忽略（`index.ts` 第 642–658 行）。
3. **可选方法存在即能力**：`prepareContinuable` 的方法存在性就是能力（`index.ts` 第 594–607 行）；它**只回数据**（可选父级历史 seed），不含 Agent、句柄、提示词投递、结果、dispose 或恢复操作（`types.ts` 第 231–244 行）。
4. **返回值只承诺公共词汇**：`localAgent` 对远程 run 是 `undefined`（`types.ts` 第 315–320 行；`out-of-process.ts` 第 245–258 行）；`result` **绝不 reject**，模型/传输失败解析为 `stopReason: 'error'`（`types.ts` 第 321–328 行；结算实现见 `out-of-process.ts` 第 182–219 行）。

**于是差异可以很大而不破坏约定**：进程内 `spawn` 五项全开、直接把 `agentOptions` / `toolFilter` / `persona` 作用到子级（`subagent-spawn-in-process\src\index.ts` 第 42–48 行）；进程外 `acp` / `codex` / `claude-code` 统一公布 `NO_START_CAPABILITIES` 全 `false`，因为*"另一个进程里的子级无法履行由父级强制的启动特性"*（`out-of-process.ts` 第 51–63 行）；`dsh-sdk` 则只开 `agentOptions`（`subagent-dsh-sdk\src\index.ts` 第 110–113、135 行）。消费方靠 `localAgent === undefined` 与 `stopReason` 就能一致处理本地与远端。

**最后一道保险**：消费方在**加载时**也按能力校验自己的配置（`tool-subagent\src\index.ts` 第 328–358 行），并监听 `subagent/provider-added` / `provider-removed` 随提供方增减而挂载/卸载工具（第 579–593 行）。子系统文档把这两类发现方式命名为"静态描述符 vs 方法存在性"（`docs\subsystems\subagent.zh.md` 第 15 行）。

> ⚠️ **第一次读请跳过这一段**："可继续（continuable）子 agent 由 continuation 管理器持有 `AgentHandle`、每个可继续 Activation 为其驻留纪元 emit 一对仅观察事件、冷恢复是新纪元"等细节属**第三编 `3.14`**；本课只用它说明"方法存在即能力"。另有一条容易读错的细节：事件里的 `provider` 字段只标明**启动该 run / Activation 时段**的提供方，**并不声明该 edge 发出时提供方仍处于注册状态**（`types.ts` 第 83–94 行；`docs\subsystems\subagent.zh.md` 第 457 行）。
