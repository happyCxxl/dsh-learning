## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：一次「模型作答」从字节到账本的完整链路——**直播帧 → 持久 settlement → 读模型（计量与展示）**，以及失败/取消/重试在每一层留下什么。
**不是**：`StreamChunk` 的逐字段协议（那是 `3.7` 与 `docs\subsystems\llm-streaming.zh.md`）、compaction 的触发策略（`3.12`）、投影注册机制（`3.3`）。

### 0.2 现在只要记住这 4 件事

1. **一次模型作答有三层载体**：进程内的**帧**（可丢）、持久日志里的**settlement**（不可丢）、从日志折叠出来的**读模型**（可重建）。混层是这一节最大的坑。
2. **帧是直播，settlement 是存档**：循环先把 settlement 提交进日志，**再**发 `end` 帧，`end` 里回指 settlement 的类型与 seq。**帧不是 write-ahead log**。
3. **重试是"同一个 step 的另一次 attempt"**，不是新 step：组装 prompt 与 `agent/pre-step` 在 step 边界只发生一次，请求本身在 step 内部重跑。
4. **计量不另存一份**：provider 报的 `usage` 随 settlement 一起持久，Host / 客户端快照 / ACP / UI 都从同一份读模型派生。

### 0.3 明确授权：这些现在不用管

- `request/header` 的规范化与 `systemPrompt.project()` 的系列规则 —— 属于 `3.6`；本课只在 §3.11 说明"重试会重跑 `agent/request`"时点一下；
- 投影（projection）的注册与 wire 序列化 —— 属于 `3.3`；本课只把两个计量单元当"纯折叠函数"用；
- `compaction` 如何选段 —— 属于 `3.12`；本课只用到"它读 `TokenMeter.measure()`"这一句；
- 背压（backpressure）与 Node Stream —— 见 §3.4，本课给的是**结论 + 源码依据 + 未实测说明**。

判断标准只有一条：**只要你能说清某个东西属于"帧 / settlement / 读模型"这三层里的哪一层，就够了。**

### 0.4 如果你是第一次读

附录 A 的 ⑤（token 计量四步与上报出口）涉及 `token-meter` 的三个投影单元与 compaction 消费方，**第一次读可以跳过**；①②③④ 是第一次读就该能回答的。

## 1. 最小词汇表（7 个词，先不碰投影与 waterfall 内部）

这 7 个词是本节的地基。**先用大白话建立直觉，不要追问它们的实现。**

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **frame（帧）** | 模型边吐字边往外播的**实时通知**，只在进程内活着，发过就没了 | `agent/assistant-stream` 上的 `start` / `chunk` / `end` 三种 |
| **settlement（结算）** | 一次作答结束时，**追加进会话日志的那一条事实** | `assistant/message`（进模型历史）或 `assistant/attempt`（只进日志） |
| **attempt（尝试）** | 一次模型作答的**唯一身份**。重试 = 同一个 step 的另一次 attempt | `AssistantStreamAttempt`；id 形如 `` `${sessionId}:${attempt}` `` |
| **compact stream（紧凑流）** | 把整串 chunk 压成"**几条 run + 几个原始记录**"存进日志，能逐字节还原 | `AssistantStreamRecord[]`（`text-chunks` / `reasoning-chunks` / `tool-call-chunks` / 原始 `chunk`） |
| **usage（用量）** | 适配器在 finish 之前报的**token 账**，随 settlement 一起持久 | `StreamChunk` 里的 `{ type: 'usage' }` → `BlockAssembler.usage` |
| **projection（投影）** | 从日志**纯折叠**出来的派生状态；删掉可重建，不额外存 | `tokenUsage` / `contextPressure` / `contextBreakdown` |
| **waterfall（瀑布事件）** | 一种事件分发方式：监听器**必须调用 `next()`** 才能把决定委托给下一个；谁不调 `next()` 谁就接管 | `agent/request-error`（重试就挂在这上面） |

> ⚠️ **这 7 个词里，`projection` 与 `waterfall` 的机制分别属于 `3.3` 与 `2.4`。** 本课只用到上面这个程度：把投影当"读日志算出来的表"、把 waterfall 当"能被别人接管的决定链"。为什么 `next()` 的语义是这样，**这里不答**。

## 2. 先建立画面

### 2.1 三层载体（静态结构）

```
┌─ 进程内（易失）───────────────────────────────────────────┐
│  agent/assistant-stream 帧：start → chunk* → end          │
│    · chunk 帧没有任何持久证据                              │
│    · revision 在 attach 生命周期内单调递增，attempt 内 index 从 0 密集递增 │
└───────────────────────┬───────────────────────────────────┘
                        │ 同一次 push() 的同一份冻结 chunk
                        ▼
┌─ 会话日志（只追加，永久）──────────────────────────────────┐
│  每条 attempt 恰好一个 settlement：                        │
│    ① assistant/message   ← surface：进 deriveMessages()   │
│       内嵌精确 compact stream + usage + 可能 interrupted:true│
│    ② assistant/attempt   ← log-only：永不进 deriveMessages()│
│       内嵌精确 compact stream（失败/重试/取消/流错误的证据） │
└───────────────────────┬───────────────────────────────────┘
                        │ 纯折叠（不新增持久事实）
                        ▼
┌─ 读模型（可重建）─────────────────────────────────────────┐
│  tokenUsage / contextPressure / contextBreakdown 投影      │
│  + deriveTurnTokenUsage() 的精确披露                       │
│  → 出口：Host 服务、客户端快照、ACP usage_update、Chat UI  │
└───────────────────────────────────────────────────────────┘

另有旁路：llm/retry 与 llm/retry-started —— 由重试执行器追加的
        非 surface 事件；它们**不贡献任何 token**，但会改变计量的折叠结果。
```

> **精确性说明**：严格说帧不是"装在" settlement 里，而是**同一次 `push()` 产生**的两份表示——一份进 accumulator（存档），一份进 assembler（组装），第三份发成帧（直播）（源码见 §3.2）。图上画成包含关系只是为了让你看清"谁可丢、谁不可丢"。

### 2.2 一次 attempt 的动态过程

```
step 开始（step/start 已提交）
  │
  ├─ preStep()：组装 prompt + 工具 schema + runtime context，派发 agent/pre-step
  │              ← 在 step 之外，每个 step 只发生一次（§3.11）
  ▼
while (true)   ← 重试就在这个循环里转
  │
  ├─ prepareRequest()：派发 agent/request waterfall → llm.prepareCall()
  ├─ buildRequest()
  ├─ new AssistantStreamAttempt(...)
  ├─ stream = preparedCall?.stream(request) ?? ctx.llm.stream(request)
  ├─ live.start()            → 发 start 帧（若此之前抛错，则一帧都不发）
  ├─ for await (chunk of stream) { signal.throwIfAborted(); live.push(chunk) }
  │      └─ 每个 chunk：快照 → 紧凑累积 → 组装 → 发 chunk 帧
  ▼
结算（恰好一个分支）
  ├─ 正常成功        → assistant/message（usage + stream）→ end{committed} → 可能执行工具
  ├─ max-tokens      → assistant/message（工具调用被整块丢弃）→ 结束 turn
  ├─ 取消且有可见前缀 → assistant/message{interrupted:true} → 抛错
  ├─ 取消且无可见前缀 → assistant/attempt                    → 抛错
  ├─ 非取消失败       → assistant/attempt → 派发 agent/request-error
  │                      └─ 监听器返回 { kind: 'retry' } → continue（回到 while 顶）
  │                      └─ 否则抛 LlmError → turn/end{error}
  └─ 结算被拒         → abandon() → end{abandoned}，日志里没有该 attempt
```

> 图上的"取消且有可见前缀"判据是 `BlockAssembler.interruptedBlocks()`：只保留 **text/reasoning 且非空白**的块，tool-call 一律丢弃（§3.8）。

### 2.3 大白话版：用户敲一句话，模型边吐字边被记账

**完全不用上面的术语**，先把画面立起来（来源：本文 §3.1–§3.15 的源码；这里是白话转述，术语版本在同节）。

1. 循环决定要问模型了，先把"要给模型看的东西"拼好——这一步一个回合只做一次。
2. 它开一个"本次作答"的小账本，先对外喊一声"我开始了"。
3. 模型的回答是一小片一小片到的。**每来一小片，同时做三件事**：把它压进账本（存档用）、把它拼进"正在成形的回复"（最终消息用）、把它广播出去（界面立刻显字）。
4. 每广播一片，界面上就多几个字。这些广播**没有任何存档**，网络断了重连要靠后面那一步。
5. 如果模型中途说"我要用某个工具"，循环先把"目前已经成形的回复"存成一条正式记录，再对外喊一声"我结束了"，然后去执行工具。
6. 如果模型在中途被取消：**已经吐出来的文字和思考留着**（存成一条"被打断"的正式记录），**没发出去的工具调用整块丢掉**——因为工具还没跑，留着它就得编一个假结果。
7. 如果是失败（限流、超时、传输错），把这一片残骸也存成一条正式记录（只是"不进模型历史"的那种），然后问一圈"有没有人负责善后"。没人管，这个回合就以失败收尾。
8. 如果有人管（重试插件）：它**先把"我要等 500 毫秒再试"写进日志**，然后才真的去等。等完再写一条"我开始了"，回到第 1 步重来一遍请求——**注意：拼提示词那一步不重来**。
9. 不管成功、失败还是取消，模型报的 token 数都跟着那条正式记录一起存下来。**没有单独的账本文件**；谁来问用量，就把日志从头折一遍算出来。

> 本节每个机制类知识点旁边就是源码。每块上方标 `文件路径 第 A–B 行`，块下按"**做什么 / 与哪个知识点相关 / 为什么这么写**"讲解。

### 3.1 一次 attempt 的 owner：两个累积器 + 一个身份

**知识点**：attempt 是"模型作答"的唯一身份；它内部**同时**持有一份紧凑持久流与一份组装结果，两者吃的是**同一批 chunk**。

`packages\core\agent-loop\src\assistant-stream.ts` 第 17–46 行

```ts
/** Folds one model attempt into one compact stream plus ordered transient frames. */
export class AssistantStreamAttempt {                        // ← 类头
  private readonly accumulator = new AssistantStreamAccumulator()   // ① 紧凑持久流
  private readonly assembler = new BlockAssembler()                 // ② 组装结果
  private index = 0                                            // ③ attempt 内密集递增
  private terminal = false                                     // ④ 是否已发过终帧
  /** Attempt identity unique within this Agent lifecycle. */
  readonly attemptId: LlmAttemptId

  /** Whether this started attempt has emitted its terminal frame. */
  get ended(): boolean { return this.terminal }

  // …（第 29–36 行：构造函数的 @param JSDoc，逐条解释下列 6 个入参，此处只留签名）

  constructor(
    sessionId: SessionId,                                      // ← 仅用于拼 attempt id
    attempt: number,                                           // ← 附接生命周期内的自增计数
    private readonly nextRevision: () => number,               // ← 帧 revision 的分配器
    readonly turn: number,                                     // ← 归属的持久轮次
    readonly step: number,                                     // ← 归属的持久步骤
    private readonly emit: (frame: AssistantStreamFrame) => void,  // ← 发帧的口子
  ) {
    this.attemptId = LlmAttemptId(`${sessionId}:${attempt}`)   // ⑤ 身份就是这两个字段拼的
  }
}
```

**做什么**：一个 attempt 对象同时管三样东西——`accumulator`（存档）、`assembler`（成形的回复）、帧的发布（`emit`）。

**与哪个知识点相关**：§1 词汇表的 attempt / compact stream；§2.1 的"三层载体"。

**为什么这么写**：
- **①② 两个累积器并存不是冗余**：`accumulator` 产出的是"能逐字节还原的紧凑记录"（进日志），`assembler` 产出的是"模型可见的内容块"（进模型历史）。两者的**保留规则不同**（例如 `max-tokens` 会丢掉工具调用，见 §3.8），所以不能共用一份。
- **③④ `index` 与 `terminal` 是帧侧状态**：attempt 内 `index` 从 0 密集递增（测试断言它等于 `[0,1,2,…]`），`terminal` 保证"终帧只发一次"。
- **⑤ `attemptId` 的来源**：`sessionId` 与**附接 Agent 生命周期内**的自增计数拼成。计数器与帧 revision 都由 loop 提供（见 §3.4 的 `++this.assistantAttemptCounter` / `++this.assistantStreamRevision`），所以"换回同一个 session"不会复用旧的 attempt 身份。

**省略说明**：第 29–36 行是构造函数的 6 条 `@param` JSDoc，与本块要说明的结构无关，此处只留签名并注明。

### 3.2 一次 push 做三件事：快照、组装、直播

**知识点**：**同一份冻结 chunk** 同时喂给存档、组装与直播——这是"帧与持久流可以逐 chunk 对照"的机制来源。

`packages\core\agent-loop\src\assistant-stream.ts` 第 48–71 行

```ts
  /** Publish the opening marker before the first delivered chunk. */
  start(): void {                                            // ← 方法头
    this.emit({
      type: 'start',
      attemptId: this.attemptId,
      revision: this.nextRevision(),                         // ① revision 由 loop 分配
      turn: this.turn,
      step: this.step,
    })
  }

  /** Snapshot one chunk once, then feed durable compaction, assembly, and live publication. */
  push(chunk: StreamChunk): void {                           // ← 方法头
    const timed = this.accumulator.push({ time: Date.now(), chunk })   // ② 快照一次
    this.assembler.push(timed.chunk)                                 // ③ 组装用同一份
    this.emit({
      type: 'chunk',
      attemptId: this.attemptId,
      revision: this.nextRevision(),
      index: this.index++,                                   // ④ attempt 内密集递增
      time: timed.time,                                      // ⑤ 时间戳也是同一份
      chunk: timed.chunk,                                    // ⑥ 帧里带的是同一份 chunk
    })
  }
```

**做什么**：`push` 的返回值 `timed` 就是"被冻结、带时间戳的那一份 chunk"；随后**同一次返回的 `timed.chunk`** 再喂 assembler，最后发帧。

**与哪个知识点相关**：R11 要求的"帧与持久流等价"这一条断言（`expandAssistantStream(message.data.stream).map(m => m.chunk)` 与帧中的 chunk 序列 `toStrictEqual`）；§2.1 的"同一批 chunk"。

**为什么这么写**：
- **② 快照只做一次**：`AssistantStreamAccumulator.push()` 内部会 `snapshotChunk` + `deepFreeze`（见 §3.6 的第一块）。若存档、组装、帧各拿一份原始对象，适配器之后改动它就会让三份不一致。作者把这一点直接写在 `push` 的文档注释里：*"Snapshot one chunk once, then feed durable compaction, assembly, and live publication."*
- **①④ revision 与 index 是两个不同的计数**：`revision` 由 loop 全局递增（跨 attempt 连续，客户端拿它判连续性），`index` 在 attempt 内从 0 开始（客户端拿它判帧有没有丢）。
- **⑤ 帧与存档共用 `time`**：`time` 是 `Date.now()`，但 accumulator 会校验它是**安全整数**才接受；同一个值同时进日志和帧，所以回放出的时间戳与直播时看到的完全一致。

### 3.3 结算：先落日志，再发终帧

**知识点**：`settle()` 先同步 `append()` 拿 seq，**成功之后**才置 `terminal` 并发 `end` 帧；`append()` 抛错就转 `abandon()`。

`packages\core\agent-loop\src\assistant-stream.ts` 第 73–109 行

```ts
  /**
   * Publish terminal settlement after the matching durable event commits.
   * @param eventType - durable settlement type.
   * @param append - synchronous durable append returning its committed seq.
   */
  settle(                                                    // ← 方法头
    eventType: 'assistant/message' | 'assistant/attempt',
    append: () => SessionSeq,                                // ← 调用方传入的真正 append
  ): void {
    let seq: SessionSeq
    try {
      seq = append()                                         // ① 同步 append，拿 seq
    } catch (error: unknown) {
      this.abandon()                                         // ② 被拒 → 改成"放弃"
      throw error
    }
    this.terminal = true                                     // ③ 成功后才置终态
    this.emit({
      type: 'end',
      attemptId: this.attemptId,
      revision: this.nextRevision(),
      index: this.index,                                     // ④ = 已发出的 chunk 帧数
      outcome: { kind: 'committed', eventType, seq },        // ⑤ 回指 settlement 类型与 seq
    })
  }

  /** Publish abandonment when no durable attempt event can be committed. */
  abandon(): void {                                          // ← 方法头
    this.terminal = true
    this.emit({
      type: 'end',
      attemptId: this.attemptId,
      revision: this.nextRevision(),
      index: this.index,
      outcome: { kind: 'abandoned' },                        // ⑥ 没有 seq —— 因为没落盘
    })
  }
```

**做什么**：把"持久提交"与"对外宣告"绑成一个**有序**动作：先提交，后宣告；提交不了就宣告"放弃"。

**与哪个知识点相关**：§0.2 第 2 条"帧是直播、settlement 是存档"；`AssistantStreamFrame` 的 `end.outcome` 联合（`{ kind: 'committed', eventType, seq } | { kind: 'abandoned' }`）。

**为什么这么写**：
- **`append` 是调用方传进来的**（不是 attempt 自己去 append）：这样 attempt 不需要知道 settlement 的**形状**——到底是 `assistant/message` 还是 `assistant/attempt`、带不带 usage 与 interrupted，全由 loop 决定（见 §3.5）。
- **①② 失败即 `abandon`**：`abandon()` 没有任何 settlement。测试把它固定下来了——把 `session.append` 对 `assistant/message` 打桩成抛错后，最后一帧是 `{ type: 'end', outcome: { kind: 'abandoned' } }`，且日志里查不到 `assistant/message`（`packages\core\agent-loop\tests\loop.spec.ts` 第 123–150 行）。
- **⑤ 为什么要带 `seq`**：seq 是**持久坐标**。消费方拿到它就知道"这条 live 帧对应日志里的第几条"，重连时用它对齐 baseline（见 §3.14）。

### 3.4 请求侧：`AsyncIterable` + 逐 chunk 的取消守卫（语言点）

**知识点**：适配器契约是 `stream(options): AsyncIterable<StreamChunk>`；loop 用 `for await` 拉取，**每两片之间**用 `signal.throwIfAborted()` 检查取消。`started` 标志决定"派发在 `start()` 之前抛错时一帧都不发"。

**做什么**：建 attempt → 拿流 → 查取消 → `start()` → 逐片拉取并转发 → 尾查一次取消。

**与哪个知识点相关**：roadmap 3.8 的「语言点：`AsyncIterable` / 异步生成器；Node Stream 与背压」；§2.2 动态图里"派发在 `start()` 之前抛错则一帧都不发"。

**为什么这么写**：
- **⑦ `for await` 是 async iterator 协议**：`stream()` 返回的不是 Node `Readable`，而是 `AsyncIterable<StreamChunk>`（文档 `docs\subsystems\llm-streaming.zh.md` 第 815、887 行给出的正是这个签名）。所以 loop 侧没有任何 `.pipe()`、`.on('data')` 或 `pause()/resume()`——只有"要下一片"这一个动作。
- **⑧ 取消检查放在每片之前**：这是**唯一的取消介入点**。`throwIfAborted()` 在 signal 已 abort 时抛出取消原因，异常沿 `for await` 冒泡到 §3.5 的 `catch`，走"取消分支"。
- **背压结论（未实测，标注为推断，依据为源码与文档）**：DSH **没有做显式背压握手**——loop 从不告诉适配器"慢一点"。文档把它写成了适配器的责任：*"提供方停顿在传输层受到时限约束。两个已交付的远程适配器都暴露正数且有限的 `streamIdleTimeoutMs`，默认五分钟。watchdog 只在 iterator `next()` 尚未完成时启动……"*（`docs\subsystems\llm-streaming.zh.md` 第 304 行）。**为什么可以这样**：拉取是逐片的，生产者只有在被 `next()` 请求时才需要产出下一片，所以"消费者慢"天然退化为"生产者等着"；真正的失败模式不是"灌爆缓冲"而是"**久等不来**"，因此超时与取消这两件事，一件交给适配器的 idle watchdog、一件交给 abort signal。
- **④⑩ `started` 的意义**：如果 `stream()`（或 `prepareCall`）在 `start()` 之前就抛错，attempt **没有任何帧**，也没有 settlement，只有 `turn/end { kind: 'error' }`（测试：`packages\core\agent-loop\tests\loop.spec.ts` 第 211–238 行断言 `frames` 为空）。
- **⑤ `preparedCall?.stream(...) ?? this.loopCtx.llm.stream(request)`**：先看这次请求是否绑定了适配器专属的流函数（`llm.prepareCall()` 的产物），没有才退回服务级入口。

### 3.6 紧凑流：push 时合 run，snapshot 时深冻结

**知识点**：同一 index 的连续 `text-delta` / `reasoning-delta` 合成一条 run（首时间 `time0` + 逐成员间隔 `dt` + 逐成员文本）；`block-start` / `block-end` / `usage` / `finish` 一律落成**带时间戳的原始 `chunk` 记录**；id 或 name 为空的 tool-call delta 也退回原始记录。

```ts
/** Incrementally compacts one attempt without retaining a second raw-chunk list. */
export class AssistantStreamAccumulator {                    // ← 类头
  private readonly records: MutableRecord[] = []

  // …（第 103–107 行的 @param/@returns JSDoc，此处只留签名）

  push(value: TimedStreamChunk): TimedStreamChunk {          // ← 方法头
    const time = safeTime(value.time)                        // ① 必须安全整数
    const chunk = snapshotChunk(value.chunk)                 // ② 必须可无损 JSON 化 + 拷贝
    const timed = deepFreeze({ time, chunk })                // ③ 冻结后才交出去
    const previous = this.records.at(-1)                     // ④ 只看最后一条
    switch (chunk.type) {

      case 'reasoning-delta': {

        const type = chunk.type === 'text-delta' ? 'text-chunks' : 'reasoning-chunks'
        const gap = previous !== undefined && previous.type === type ? safeGap(previous.lastTime, time) : undefined
        if (previous !== undefined && previous.type === type && previous.index === chunk.index && gap !== undefined) {
          previous.dt.push(gap)                              // ⑥ 合成进上一条 run
          previous.texts.push(chunk.text)
          previous.lastTime = time
        } else {
          this.records.push({ type, time0: time, index: chunk.index, dt: [], texts: [chunk.text], lastTime: time })   // ⑦ 开新 run
        }
        return timed
      }
      case 'tool-call-delta': {
        safeIndex(chunk.index, chunk.type)
        if (typeof chunk.id !== 'string') throw new TypeError('tool-call-delta id must be a string')
        if (Object.hasOwn(chunk, 'name') && typeof chunk.name !== 'string') {
          throw new TypeError('tool-call-delta name must be a string')
        }
        if (typeof chunk.argumentsDelta !== 'string') {
          throw new TypeError('tool-call-delta argumentsDelta must be a string')
        }
        if (chunk.id.length === 0 || chunk.name === '') {    // ⑧ 异常报文：退回原始记录
          this.records.push({ type: 'chunk', time, chunk })
          return timed
        }
```

**与哪个知识点相关**：§1 词汇表的 compact stream；`AssistantStreamRecord` 的四种形态（同文件第 19–44 行定义：`text-chunks` / `reasoning-chunks` / `tool-call-chunks` / 原始 `chunk`）。

**为什么这么写**：
- **⑦ 三个字段分工**：`time0`（run 首片时间）+ `dt`（逐成员间隔）+ `texts`（逐成员原文）= 精确还原所需的最小信息。`lastTime` 只用于算下一个 gap，**不进持久结构**（`snapshot()` 会把它剥掉）。
- **⑥ 合成条件有四条**：类型相同、index 相同、上一条存在、且 gap 能算出来。`safeGap` 要求"两时间都是安全整数且差值安全"（同文件第 94–97 行），任一条不满足就**另开一条 run** —— 宁可多一条记录，也不冒"时间还原不回去"的险。

### 3.7 snapshot 与 expand：持久边界上的严格校验

**知识点**：`snapshot()` 返回**分离且深冻结**的记录数组（并剥掉内部的 `lastTime`）；`expandAssistantStream()` 是持久边界上的**严格校验路径**，逐字节还原原始 delta 边界。

```ts
    const records = this.records.map((record): AssistantStreamRecord => {
      if (record.type === 'chunk') return { ...record }                       // ① raw：浅拷贝即可

export function expandAssistantStream(stream: readonly AssistantStreamRecord[]): readonly TimedStreamChunk[] {
  const chunks: TimedStreamChunk[] = []
  for (const candidate of stream) {                          // ← 逐条记录
    const record = validateRecord(candidate)                 // ⑤ 先校验形状
    if (record.type === 'chunk') {
      chunks.push({ time: record.time, chunk: record.chunk })
      continue
    }
    const members = record.type === 'tool-call-chunks' ? record.args : record.texts
    let time = record.time0                                  // ⑥ 从 run 首时间出发
    for (let index = 0; index < members.length; index += 1) {
      if (index > 0) time += record.dt[index - 1] as number   // ⑦ 逐成员累加间隔
      let chunk: StreamChunk
      if (record.type === 'text-chunks') {
        chunk = { type: 'text-delta', index: record.index, text: members[index] as string }
      } else if (record.type === 'reasoning-chunks') {
        chunk = { type: 'reasoning-delta', index: record.index, text: members[index] as string }
      } else {
        chunk = {
          type: 'tool-call-delta',
          index: record.index,
          id: record.id,
          ...Object.hasOwn(record, 'name') ? { name: record.name } : {},
          argumentsDelta: members[index] as string,
        }
      }
      chunks.push({ time, chunk })                            // ⑧ 每个 delta 都还原成独立一片
    }
  }
  return chunks
}
```

**做什么**：`snapshot()` = "把内部结构变成可以安全写进日志的值"；`expandAssistantStream()` = "把日志里的值精确还原成当初的 chunk 序列"。

**与哪个知识点相关**：R11 的"帧与持久流可逐 chunk 对照"；计量投影读 usage 时用的 `lastAssistantStreamChunk()`（同文件第 373–382 行，倒序扫第一条 `type === 'chunk'` 的 usage 记录）。

- **②③ 分离性**：`lastTime` 是内部记账字段（见 §3.6），不能被写进持久事件；`dt` / `args` / `texts` 三个数组必须逐个复制，否则"snapshot 之后又 push 一片"会**回改已经交出去的日志对象**。
- **④ 深冻结**：日志的值必须是不可变的，否则下游（投影、客户端）读到的状态会悄悄变。`deepFreeze` 让任何写入尝试直接失败。
- **⑤ `validateRecord` 才是持久边界的守门人**：`snapshot`/`assembleAssistantStream` 走的是"信任静态类型"的快路（`assembleAssistantStream` 的注释原文：*"The records are trusted, not validated: validate a stream read at a durable boundary with `expandAssistantStream` first."*）。**从磁盘读回来的**流必须先 `expandAssistantStream` 校验。

### 3.9 重试：判定顺序（策略 → 预算 → 延迟）

**知识点**：重试执行器自身**无配置**；策略由提供方适配器持有。`recover()` 的判定顺序是：无策略 → `next()`；`always` 先结算下游；`normal` 先查 code 资格；再查预算；最后算延迟。

`packages\llm\llm-retry\src\index.ts` 第 194–241 行

```ts
  async function recover(                                    // ← 函数头
    { agent, turn, step, provider, failure, retryPolicy: policy, signal }: Parameters<Events['agent/request-error']>[0],
    next: () => Promise<RequestErrorAction>,                 // ← 委托给下游监听器
  ): Promise<RequestErrorAction> {
    if (policy === undefined) return next()                  // ① 调用未经最终适配器：直接委托
    if (policy.mode === 'always') {                          // ② always：先问下游
      if (signal.aborted || lifetime.signal.aborted) return
      const fusedSignal = AbortSignal.any([signal, lifetime.signal])
      // The loop and plugin lifetime stay open until delegated recovery settles.
      // An abort then wins before the decision or fallback can mutate later state.
      const downstream = await settleDownstream(next)        // ③ 下游抛错被包成 { type: 'error' }
      if (fusedSignal.aborted) return
      if (downstream.type === 'error') {
        ctx.logger.warn(
          `llm-retry: provider "${provider}" always policy ignored a downstream recovery failure: %o`,
          downstream.error,
        )                                                    // ④ 只告警，不中断
      }
      if (downstream.type === 'decision' && downstream.decision?.kind === 'retry') {
        return downstream.decision                           // ⑤ 下游要重试：采纳
      }
    } else if (!policy.retryableCodes.includes(failure.code)) {
      return next()                                          // ⑥ normal：code 不合格 → 委托
    }

    const policyKey = retryPolicyKey(policy)                  // ⑦ 策略键：参与计数的身份
    const retryState = ctx.sessionProjections.stateOf(agent.session, 'llmRetry') as LlmRetryState
    const previous = retryState[retryStateKey(provider, policyKey)]
    const previousRetry = previous?.retry ?? 0
    if (policy.mode === 'normal' && previousRetry >= policy.maxRetries) return next()   // ⑧ 预算耗尽 → 委托
    const retry = previousRetry + 1
    const retryId = previous?.retryId ?? RetryId(randomUUID())   // ⑨ 同一串重试共用一个 id
    let delayMs: number
    if (failure.providerRetryAfterMs !== undefined
      && Number.isFinite(failure.providerRetryAfterMs)
      && failure.providerRetryAfterMs > 0) {                  // ⑩ 提供方给了合法的 Retry-After
      if (failure.providerRetryAfterMs > policy.maxDelayMs) {
        if (policy.mode === 'normal') return next()           // ⑪ normal：超上限就不再重试
        delayMs = localDelay(policy, retry, random)           // ⑫ always：退回本地退避
      } else {
        delayMs = failure.providerRetryAfterMs                // ⑬ 边界内：原样采用
      }
    } else {
      delayMs = localDelay(policy, retry, random)             // ⑭ 否则本地有界指数退避 + 抖动
    }

    return backoff(agent, turn, step, failure, provider, policy, policyKey, retry, retryId, delayMs, signal)
  }
```

**做什么**：在"要不要重试 / 等多久"上做完整决策，并把"谁有权决定"（下游 vs 自己）摆清楚。

**与哪个知识点相关**：§0.2 第 3 条；`agent/request-error` 的 waterfall 契约（`packages\core\agent\src\runtime-types.ts` 第 338–353 行，`@mode waterfall`，返回类型 `RequestErrorAction = { kind: 'retry' } | undefined` 在第 122 行）。

**为什么这么写**：
- **① 无策略即委托**：`retryPolicy` 来自 `preparedCall`（提供方适配器注册路由时捕获），没有它说明这次调用没有走最终适配器——"策略"这件事根本不存在，不该由本插件兜底（README 原文：*"在任何最终适配器被选中之前发生的失败没有提供方策略，原样委派下游。"*）。
- **③④⑤ `always` 的"下游优先"姿态**：`always` 不是"我肯定重试"，而是"**先尊重下游的恢复决定**；下游没决定（或抛错）我才接手"。注释里写清了原因：*"The loop and plugin lifetime stay open until delegated recovery settles. An abort then wins before the decision or fallback can mutate later state."* —— 即"等下游期间不能让别人先把状态改了"。
- **⑦ 策略键为什么要把字段全列进去**：`retryPolicyKey`（同文件第 66–77 行）对 normal 模式编码 `[mode, maxRetries, [...retryableCodes].sort(), initialDelayMs, maxDelayMs, jitterRatio]`，`always` 模式只编码 `[mode, initialDelayMs, maxDelayMs, jitterRatio]`。README 给的判据：*"重试编号只在同一提供方与完整策略键的事件间延续……该键包含每个影响行为的字段，并因资格判断使用集合成员而对 normal mode code 排序。"* 测试把键的字面值钉死了：`'["normal",2,["RATE_LIMIT","SERVER"],500,10000,0]'`（`packages\llm\llm-retry\tests\retry.spec.ts` 第 227 行）。
- **⑧ 预算是"按 provider + 策略键"数的**：所以同一个 session 里换 provider 或换策略，计数各自从 0 开始。
- **⑨ `retryId` 沿用上一条记录的**：`previous?.retryId ?? RetryId(randomUUID())` —— 同一串重试共用一个 id，`llm/retry-started` 靠它配对。
- **⑩⑪⑫⑬ 三档处理 `Retry-After`**：合法且在上限内 → **原样采用**（提供方比我们更清楚该等多久）；超过上限 → normal 放弃重试、always 退回本地退避（README：*"always mode 中，超上限的提供方延迟使用配置的本地退避，因此策略不会因该指令终止。"*）。
- **⑭ 本地退避的形状**见同文件第 59–64 行：`exponential = min(initialDelayMs * 2^min(retry-1, 1024), maxDelayMs)`，再乘一个 `[1-ratio, 1+ratio]` 的对称抖动，最后再夹一次上限。

### 3.10 "先持久、后等待"：重试的唯一纪律

**知识点**：任何定时器启动**之前**，重试就已经通过会话日志被计划；等待完成后、下一次请求之前，再追加 `llm/retry-started`。任何时刻取消或插件释放都不会留下"不可见的待处理重试"。

`packages\llm\llm-retry\src\index.ts` 第 149–192 行

```ts

    agent: Agent,
    turn: number,
    step: number,
    failure: LlmFailure,
    provider: string,
    policy: ResolvedRetryPolicy,
    policyKey: string,
    retry: number,
    retryId: RetryId,
    delayMs: number,
    signal: AbortSignal,                                     // ← 来自 agent/request-error 载荷
  ): Promise<RequestErrorAction> {
    const fusedSignal = AbortSignal.any([signal, lifetime.signal])   // ① 取消 或 插件释放，任一生效
    if (fusedSignal.aborted) return                          // ② 已中止：返回 undefined（不重试）
    const eventData: LlmRetryEventData = policy.mode === 'normal'
      ? {
        retryId, turn, step, provider,
        mode: policy.mode, policyKey, retry,
        maxRetries: policy.maxRetries,                       // ③ normal 才带预算字段
        delayMs, failure,
      }
      : {
        retryId, turn, step, provider,
        mode: policy.mode, policyKey, retry,
        delayMs, failure,
      }
    agent.session.append('llm/retry', eventData)             // ④ 先落盘
    if (!await cancellableDelay(delayMs, fusedSignal)) return   // ⑤ 再等；被取消则返回 undefined
    agent.session.append('llm/retry-started', { retryId, turn, step, retry })   // ⑥ 等完再落一条
    return { kind: 'retry' }                                 // ⑦ 交回决定，loop 重跑请求
  }
```

**做什么**：把"计划 → 等待 → 开始"三步写成两条持久事件夹一段可取消的等待。

**与哪个知识点相关**：R11 要求的"重试的持久顺序"；`llm/retry` 与 `llm/retry-started` 两个事件（载荷定义见 `packages\llm\llm-retry\src\types.ts` 第 15–48 行）。

**为什么这么写**：
- **④⑤⑥ 的顺序就是设计规定**（README 原文：*"**先持久、后等待，打开步骤边界。** 任何定时器启动之前，重试就已通过会话日志计划，因此崩溃或取消永远不会留下不可见的待处理重试。"*）。它直接决定了两件事：进程在退避期间硬中断 → 日志里有 `llm/retry` 但没有 `llm/retry-started`；取消发生在退避期间 → 同样只有 `llm/retry`，而**不会有**重试请求发出。
- **⑤ `cancellableDelay` 返回布尔**：实现见同文件第 83–96 行——signal 已 abort 直接 `Promise.resolve(false)`；否则 `setTimeout`，abort 时 `clearTimeout` 并 `resolve(false)`。返回 `false` 时 `backoff` 用 `return`（即 `undefined`）**放弃重试**，于是 loop 走"失败终局"路径。
- **① `AbortSignal.any` 融合两个信号**：一个是本次 turn 的取消，一个是插件的生命周期。所以"用户取消"与"插件被卸载"都能立刻掐断等待。
- **③ normal 多一个 `maxRetries` 字段**：让日志读者事后能算出"这次重试是在哪个预算下发生的"（`LlmRetryEventData` 的两个变体定义在 `types.ts` 第 16–40 行）。

### 3.12 计量（一）：`usage` 怎么进 settlement，怎么被折成两个投影

**知识点**：`usage` 只来自适配器的 `usage` chunk；`tokenUsage` 投影按 attempt 累加四个**互不重叠**的桶，同 turn/step 的重复样本按**替换**处理，而 `llm/retry-started` 会**清空替换槽**。

`packages\llm\token-meter\src\usage-projection.ts` 第 110–150 行

```ts
/**
 * Token-meter's session projection unit.
 *
 * Each v2 Assistant settlement contributes the last usage sample embedded in
 * its stream. `llm/retry-started` closes the replacement slot so the retried
 * attempt adds to the total.
 */
export const tokenUsageProjectionDefinition = {              // ← 常量头
  key: 'tokenUsage',
  stateVersion: 2,                                           // ① 状态版本
  stateSchema: tokenUsageStateSchema,
  init: () => ({ totals: zeroBuckets(), last: null }),        // ② totals 累计 + last 替换槽
  apply: (state, event) => {                                 // ← 纯折叠函数
    if (event.type === 'llm/retry-started') {                 // ③ 重试开始 → 清替换槽
      return state.last?.turn === event.data.turn && state.last.step === event.data.step
        ? { ...state, last: null }
        : state
    }
    if (event.type !== 'assistant/message' && event.type !== 'assistant/attempt') {
      return state                                             // ④ 其它事件无关
    }
    const sample = usageOf(event)                             // ⑤ 取本次 attempt 的用量
    if (sample === undefined) return state
    const { turn, step } = event.data
    const usage: TokenUsage = sample

    const buckets = bucketsFrom(usage)
    const previous = state.last !== null
      && state.last.turn === turn
      && state.last.step === step
      ? state.last.buckets
      : undefined                                             // ⑥ 同一 turn/step 才有"替换"可言
    if (previous !== undefined && bucketsEqual(previous, buckets)) return state

    return {
      totals: addReplacing(state.totals, previous, buckets),    // ⑦ 先减旧样本再加新样本
      last: { turn, step, buckets },
    }
  },
  wire: { viewSchema: projectionSchema, view: state => state.totals },   // ⑧ 出网的是 totals
} satisfies ProjectionDefinition<'tokenUsage', TokenUsageState>
```

**做什么**：把"每个 settlement 报的用量"折成**一个累计总数**，同时用 `last` 记住"当前 turn/step 上一次报的是多少"以便去重。

**与哪个知识点相关**：§0.2 第 4 条；附录 A ⑤；`pressureFrom()`（用于另一个投影）在同文件第 77–79 行。

**为什么这么写**：
- **②⑦ `totals` + `last` 是"替换语义"的实现**：同一个 attempt 里适配器可能报多次 usage（例如先报一个中间值再报终值），这时**不能累加**，而应该"减掉旧样本、加上新样本"（`addReplacing`，同文件第 34–43 行）。
- **③ 为什么 `llm/retry-started` 要清槽**：清了槽，下一个 attempt 的样本就找不到 `previous`，于是变成**纯累加**。语义后果是：**被重试的失败 attempt 的 usage 留在累计里，重试 attempt 的 usage 再加一次**——因为它们是**两次真实发生的计费**。测试名就是这句语义：`accumulates retried attempts while replacing samples within each attempt`（`packages\llm\token-meter\tests\token-usage-projection.spec.ts` 第 165 行；第 213–218 行断言总数是 `{ uncachedInputTokens: 24, outputTokens: 7, cacheReadTokens: 11, cacheWriteTokens: 1 }`）。
- **⑤ `usageOf()` 的两条取法**：`assistant/message` **优先**用显式 `usage` 字段，否则（以及 `assistant/attempt`）从紧凑流里倒序找最后一条 `usage` 记录（同文件第 82–86 行用 `lastAssistantStreamChunk(event.data.stream, 'usage')`）。所以**失败 attempt 的 usage 也不会丢**——它藏在 stream 里。
- **① `stateVersion: 2`**：投影状态是版本化的；版本变了说明状态形状变过（升级/回放时要按它判断兼容性）。
- **⑧ `wire.view`**：出网的只有 `totals`，`last` 是内部去重用的，不给客户端。

```ts
      continue
    }
    // …（第 262–270 行：step/end 的守卫；第 271 行结束循环）
  }

  return invalid || !sawEnd || state.kind !== 'idle' ? undefined : aggregateAttempts(attempts)   // ⑥ fail-closed
}
```

### 3.14 直播帧的消费方与硬中断的后果

**知识点**：Web Session-follow adapter 全局监听 `agent/assistant-stream`，给每帧补上当时的持久游标，并用 **revision 连续性**判定要不要重开；进程在 settlement 前硬中断时，由恢复路径合成 `interrupted` 收尾。

`packages\api\session-controller\src\assistant-stream.ts` 第 33–60 行

```ts
  /**
   * Fold one trusted frame from the current attached Agent lifecycle.
   * @param frame - next dense process-local Assistant frame.
   * @param durableCursor - last committed Session seq when this frame was observed.
   */
  accept(frame: AssistantStreamFrame, durableCursor: SessionSeqCursor): void {   // ← 方法头
    if (frame.type === 'start' && frame.revision === 1 && this.revision !== 0) {
      this.activeAttempt = undefined                            // ① 新生命周期从头开始
      this.revision = 0
    }
    if (frame.revision !== this.revision + 1) {                 // ② 连续性判定
      this.activeAttempt = undefined
      this.revision = frame.revision
      this.dirty = true
      return                                                    // ③ 断档：丢掉当前 attempt，等下一帧
    }
    this.revision = frame.revision
    switch (frame.type) {
      case 'start':
        this.activeAttempt = {
          attemptId: frame.attemptId,
          startedAfterSeq: durableCursor,                       // ④ 记下"从哪个持久位置开始"
          turn: frame.turn,
          step: frame.step,
          stream: new AssistantStreamAccumulator(),             // ⑤ 重新累积紧凑流
          nextIndex: 0,
        }
        break
      case 'chunk': {
        const attempt = this.activeAttempt
        if (attempt === undefined
          || attempt.attemptId !== frame.attemptId
          || frame.index !== attempt.nextIndex) {                // ⑥ attempt 身份 + index 都要对
          this.activeAttempt = undefined
          break
        }
        attempt.stream.push({ time: frame.time, chunk: frame.chunk })   // ⑦ 服务端也压一份
        attempt.nextIndex += 1
        break
      }
      case 'end':
        this.activeAttempt = undefined                           // ⑧ 终帧即收尾
        break
    }
    this.dirty = true
  }
```

**做什么**：服务端把"直播帧"折成一份**可重连的 baseline**：当前 revision、正在进行中的 attempt 身份、以及它已经累积到哪一片。

**与哪个知识点相关**：§3.3 `end.outcome` 里的 `seq`（这里用 `cursorBeforeNext(agent.session.seq)` 补游标，见 `packages\api\session-controller\src\history.ts` 第 54–61 行）；"revision 是全局递增、index 是 attempt 内密集递增"这条分工。

**为什么这么写**：
- **②③ 连续性判定就是 revision 的用途**：revision **必须**等于"上一个 + 1"，否则客户端与服务端的帧流已经对不上——保守做法是**丢弃当前 attempt 并等下一个 `start`**，而不是拿半截流去拼。
- **⑥ index 也要对**：即使 attempt 身份相同，`frame.index !== attempt.nextIndex` 也说明丢片了，同样丢弃。
- **④ `startedAfterSeq` 是持久坐标**：客户端重连时既拿到事件快照、又拿到这份帧 baseline，用它知道"这个进行中的 attempt 是从日志的哪一条之后开始的"（重连 baseline 由 `snapshot()` 提供，`history.ts` 第 185–202 行把它塞进 `snapshot` 记录）。
- **⑦ 为什么服务端还要再压一份**：重连的客户端需要"当前 attempt 已经吐出的全部内容"，而不能只给它未来帧；这份 accumulator 就是那个补丁来源。
- **"唯一远程消费方"的准确说法**：文档 `docs\architecture.zh.md` 第 113 行写"Web Session-follow adapter 是该 live event **唯一**的远程消费方"；实测**本地**还有一个订阅者——headless bundle 用同一个事件把流式文本写到 stderr（`packages\bundle\headless\src\index.ts` 第 121 行）。**限定词是"远程"**，两者不冲突，此处按源码记录。

**硬中断的后果**（会留下 / 不会留下）：

- **会留下**：此前已提交的事件——`turn/start`、`step/start`、`request/header`、已追加的 `system/message` / `user/message`，以及**已经写下的 `llm/retry`**（它写在退避之前，见 §3.10）。
- **不会留下**：该 attempt 的任何 `assistant/attempt` / `assistant/message`、其 usage、时间戳与 replay state，以及 `turn/end`（turn 敞着口）。
- **恢复时**：`openTurnClosers(events, { kind: 'interrupted' })` 从最后一条真实事件续 seq 与 time，先给未答复的 tool call 补 error `tool/result`，再补 `step/end`，最后 `turn/end { reason: { kind: 'interrupted' } }`（`packages\core\session\src\repair.ts` 第 53–98 行；入口 `interruptedTurnClosers` 在第 209–211 行）。这个 marker **只可能来自恢复，live loop 从不发**（`packages\core\session\src\types.ts` 第 215–221 行）。
- **作者原文**：*"v2 在 settlement 之前没有持久 attempt 证据……如果进程或主机在 settlement 前硬中断，完整的 in-flight stream 都会丢失；`agent/assistant-stream` 不是 write-ahead log。"*（`.agents\notes\implemented\architecture\2026-09-01-v2-embedded-assistant-streams.zh.md` 第 76 行；同一事实写在 `docs\architecture.zh.md` 第 127 行）。

### 3.15 settlement 为什么能"进 surface"或"只进日志"

**知识点**：`assistant/message` 与 `assistant/attempt` 在**事件类型层面**就分开了：`deriveEventMessage()` 的 `default` 分支返回 `null`，所以 `assistant/attempt` **永不进 `deriveMessages()`**。

`packages\core\session\src\surface.ts` 第 120–152 行

```ts
export function deriveEventMessage(                          // ← 函数头
  event: SessionEvent,
  projectedMessages?: ReadonlyMap<SessionSeq, Message>,
): Message | null {
  const projected = projectedMessages?.get(event.seq)
  if (projected !== undefined) return projected              // ① 投影优先
  // Intentionally non-exhaustive: only message-producing events derive
  // history; turn/step boundaries, failed attempts, and errors are trace/replay
  // data.
  switch (event.type) {
    // …（第 130–131 行：user/message 的注释，此处只留分支）
    case 'user/message': {
      return event.data
    }
    // Empty system and developer nodes retain their surface positions without
    // adding wire messages. An empty assistant event hosts a max-tokens step's
    // usage and must not inject a content-less turn into the provider transcript.
    case 'system/message':
    case 'developer/message':
    case 'assistant/message': {
      if (event.data.message.content.length === 0) return null   // ② 空内容不进 wire
      return event.data.message
    }
    case 'tool/result': {
      return event.data.message
    }
    default:
      // A non-surface event (boundary, attempt, log-only record) projects to
      // no message. Merge-extensible union: no assertNever here.
      return null                                            // ③ attempt / 边界 / 错误 → 无消息
  }
}
```

**做什么**：把"持久事件"翻译成"要给模型看的消息"，而**没被列出的类型一律返回 `null`**。

**与哪个知识点相关**：§0.2 第 1、2 条；失败 attempt 的部分输出为什么不会污染模型上下文。

**为什么这么写**：
- **③ `default: return null` 是刻意的**：注释原文 *"Intentionally non-exhaustive: only message-producing events derive history; turn/step boundaries, failed attempts, and errors are trace/replay data."*。**这条 `default` 就是"失败 attempt 不进模型历史"的全部实现**——不需要任何额外标记。
- **② 空内容也返回 `null`**：注释解释了用途——`max-tokens` 的 step 会写一条"只有 usage、没有内容"的 `assistant/message`，这条事件必须**保住 surface 位置**（计量要用）但**不能给模型注入一条空消息**。
- **① 投影优先**：如果某个投影（例如 compaction 的替换）为这个 seq 算出了消息，就以投影为准——这就是"遮蔽而非删除"的接口。

**测试证据**：重试时失败 attempt 的部分输出留在 `assistant/attempt` 的 stream 里，而最终 message 只嵌自己的 stream（`packages\core\agent-loop\tests\cancel.spec.ts` 第 713–746 行分别断言"失败流里有 `doomed partial`"与"最终 message 的流里没有 `doomed partial`"）。

## 附录 A 关键问题与答案

> ✅ 五道题**全部给出明确答案**，不留空、不写"待补充"。①②③④ 第一次读就该能答；**⑤ 涉及后续编（`3.3` 投影、`3.12` compaction）的细节，第一次读请跳过**。

### ① 流式帧（`agent/assistant-stream`）与持久消息（`assistant/message`）是什么关系？

**答案：同一次 attempt 的两种表示——帧是进程内直播（可丢），持久消息是存档（不可丢）；一次 attempt 恰好一个 settlement，`end` 帧只在 settlement 提交成功后发出并回指它的类型与 seq；两者由同一批 chunk 产生，因此可以逐 chunk 对照。**

- **帧类型**：`start`（attemptId/revision/turn/step）、`chunk`（index/time/chunk）、`end`（index + `outcome`）——`packages\core\agent\src\runtime-types.ts` 第 127–161 行；事件文档原文：*"Chunk frames are transient; the loop appends one final v2 `assistant/message` or `assistant/attempt` with the same stream before a committed end frame"*（同文件第 355–357 行）。
- **同一批 chunk**：`push()` 里 `accumulator.push()` 的快照既进持久流也进帧（`packages\core\agent-loop\src\assistant-stream.ts` 第 60–71 行，见 §3.2）。
- **顺序**：`settle()` 先 `append()` 再发 `end`（同上第 78–97 行，见 §3.3）；测试断言 `committedAfterMessage === true`（`loop.spec.ts` 第 83–89、118–120 行）。
- **等价性**：`expandAssistantStream()` 还原出的 chunk 序列与帧序列 `toStrictEqual`（同上第 108–111 行）。
- **三条不能混**：`assistant/message` 是 **surface** settlement（进 `deriveMessages()`）；`assistant/attempt` 只进日志（`deriveEventMessage` 的 `default` 返回 `null`，`surface.ts` 第 147–151 行）；`agent/assistant-stream` **既不是 surface 也不是日志**，只是 live 通知。
- **增量呈现走帧、历史呈现走 settlement**：Session-follow adapter 把帧转成 client-only 更新并可提供重连 baseline（`history.ts` 第 54–61、165–202 行），而恢复/遥测/记账直接读持久 settlement（`usage-projection.ts` 第 110–116 行）。

### ② 失败与取消如何被记录？`assistant/attempt` 与 `assistant/message` 的差别？

**答案：失败与取消都先结算成"有 stream 的持久事件"，区别只在于有没有可安全 finalize 的 surface 内容；两者的分工是 surface settlement 与 log-only settlement。**

**失败**：

- 流内失败（`finish.kind === 'error' | 'aborted'`）→ 写 `assistant/attempt { turn, step, stream }`，**再**派发 `agent/request-error`；恢复者不返回 `{ kind: 'retry' }` 时抛 `LlmError(finish.failure…)`，最终 `turn/end { kind: 'error', error: LlmFailure }`（`agent.ts` 第 487–510、366–381 行）。
- 流**抛错**且已 `start()` → 按"是否取消 / 有无可见前缀"分给两个 settlement（同上第 447–477 行）。
- 失败发生在 `live.start()` **之前** → 既无帧也无 settlement，只有 `turn/end` error（同上第 434–446 行；`loop.spec.ts` 第 211–238 行）。
- 结算本身失败（append 被拒）→ `settle()` 内部转 `abandon()`：live 帧以 `abandoned` 收尾，日志里没有该 attempt（`assistant-stream.ts` 第 83–88、100–109 行；`loop.spec.ts` 第 123–150 行）。
- 失败流里的部分输出**不会**到达模型：它留在 `assistant/attempt` 的 stream 里，只有成功的 message 进 surface（`cancel.spec.ts` 第 713–746 行）。

**取消**：

- 有可见前缀（text/reasoning 非空）→ `assistant/message` + `interrupted: true`，带该 attempt 的 `usage`、`replayState` 与精确 stream，`surfaceOp: 'append'`（`agent.ts` 第 448–465 行；字段语义见 `session\src\types.ts` 第 331–349 行）。
- 无可见前缀（例如只流到半个 tool-call）→ 退化为 `assistant/attempt`（同上第 466–471 行；`cancel.spec.ts` 第 664–687、775–791 行只断言没有 message）。
- 取消发生在"失败已结算、重试等待中"→ 失败流不会被 finalize 成 message，`turn/end` 记为 `aborted`（`cancel.spec.ts` 第 689–711 行）。

**一句话差别**：**`assistant/message` = 参与模型历史的表面结果（可能带 `interrupted: true`）；`assistant/attempt` = 只有日志证据、绝不进 `deriveMessages()`。** 两者的共同点是都内嵌"精确紧凑带时间 stream"，因此失败 attempt 的 usage、时间与 replay 事实都不丢。

### ③ 进程在 settlement 前硬中断会留下什么、不会留下什么？

**答案：留下此前已提交的持久事件（含已在等待中的 `llm/retry`），不留下 in-flight attempt 的任何证据、usage 与 `turn/end`；重启后由恢复路径合成 `interrupted` 收尾。**

**会留下**：

- `turn/start`、`step/start`、`request/header`、已追加的 `system/message` / `user/message`，以及此前各 step 的全部 settlement 与 `tool/result`。
- 已经写下的 `llm/retry`（它在退避**之前**落盘，`llm-retry\src\index.ts` 第 188–189 行，见 §3.10）——但**不会**有对应的 `llm/retry-started`，也不会有失败 attempt 的 settlement，因此 `deriveTurnTokenUsage` 对这一个 turn 返回 `undefined`（`turn-usage.ts` 第 218–225、273 行：缺边界即整份不可用）。

**不会留下**：

- in-flight attempt 的 `assistant/attempt` / `assistant/message`、其紧凑 stream、时间戳、usage 与 replay state——因为 v2 在 settlement 前没有持久 attempt 证据（Agent Note 第 76 行；`docs\architecture.zh.md` 第 127 行）。
- `turn/end`：turn 敞口。
- 任何"已发出的 chunk"记录：`agent/assistant-stream` 不是 write-ahead log（Agent Note 第 76 行），帧发过就没了。

**恢复时**：`openTurnClosers(events, { kind: 'interrupted' })` 从最后一条真实事件续 seq 与 time，先补未答复 tool call 的 error `tool/result`（错误码 `TOOL_NOT_STARTED` / `TOOL_OUTCOME_UNKNOWN`，`repair.ts` 第 14–18、157–197 行），再补 `step/end`，最后 `turn/end { kind: 'interrupted' }`（第 93–96 行；入口 `interruptedTurnClosers` 第 209–211 行）。该 marker **只可能来自恢复，live loop 从不发**（`session\src\types.ts` 第 215–221 行）。

### ④ 重试为什么不重复组装或重新执行 `agent/pre-step`？token 如何计量与上报？

**答案（前半）：因为组装与准入属于 step 边界，重试属于 attempt 边界；loop 把它们分成"step 外层一次"与"step 内层 `while` 循环"。**

- `preStep()` 每步一次：`systemPrompt.assemble()` + `renderContextSections()` + `runtimeContext.project()` + `agent/pre-step` waterfall（`agent.ts` 第 267–286 行），调用点在 turn 循环（第 316 行），在 `step()` **之外**。
- `step()` 内：`renderPrompt(assembly)` 一次（第 404–405 行）；`while (true)` 每轮只做 `prepareRequest()` → 系统提示词协调 → `buildRequest()` → 流式 → 结算（第 407–543 行）；用户消息只在首轮追加（第 419–424 行）。
- 硬数字：3 step / 5 请求下 `assemblies === 1`、`preSteps === 1`、`resolveModel` 5 次（`system-prompt-admission.spec.ts` 第 270–273 行）；两次请求共享一条 `step/start`（`retry.spec.ts` 第 242–243 行）。
- 为什么这样设计：重试必须"仍基于同一份持久历史"重放**同一个**请求，否则重试会变成一次新的、语义不同的请求；同时被拒的输入不该因为重试而被悄悄接纳（该测试第 264 行注释：*"A retry must retain the assembly accepted for this step, not pick up new sections"*）。
- ⚠️ **精确边界**：重试**会**重跑 `agent/request` waterfall 与 `llm.prepareCall()`（`agent.ts` 第 408 行），并重新对同一份 `renderedPrompt` 做一次 `systemPrompt.project()` 协调（第 410–418 行）。所以"不重复组装"**不等于**"不重复解析路由"。

**答案（后半）：计量 = provider 报告的 usage 随 attempt 一起持久 + 三个纯投影折叠；上报 = 同一份读模型分别给 Host、客户端快照、ACP 与 UI 用，不另存一份。**

**计量**：

1. 采样只来自适配器的 `usage` chunk（必须在 `finish` **之前**，`docs\subsystems\llm-streaming.zh.md` 第 300 行），落在 `BlockAssembler._usage`（`assembler.ts` 第 85–88 行），写入 settlement 的 `usage`（`agent.ts` 第 463、526 行）。
2. `tokenUsage` 投影按 attempt 累加四个互不重叠的桶；同 turn/step 的重复样本按**替换**处理，`llm/retry-started` 清掉替换槽使重试 attempt 变成**累加**（`usage-projection.ts` 第 122–147 行，见 §3.12）。
3. `contextPressure` 只取 prompt 侧（`pressureFrom()` 第 78–79 行）并叠加 surface 移动量给出 `projectedTokens`（第 208–217 行）；`contextBreakdown` 是按路由定价的逐节点拆分（`token-meter\src\index.ts` 第 116 行注册）。
4. 需要"精确披露"时用 `deriveTurnTokenUsage()`：任一 attempt 缺 usage 或缺生命周期边界就直接 `undefined`，**绝不用估算补齐**（`turn-usage.ts` 第 170–177、273 行）。

**一次重试 = 一次新的提供方请求 ⇒ 可能重复输入计费**（`llm-retry\README.zh.md` 第 118 行原文：*"每次重试都是一次新的提供方请求，可能重复输入 token 计费。"*），而 `llm/retry` 事件本身**不贡献任何 token**；被重试的失败 attempt 若有 usage，也会被记进累计——这是刻意的：它是真实发生的计费。

### ⑤ token 从 chunk 到账本的完整链路是什么？为什么精确披露宁可不给？

**答案：`usage` chunk → `BlockAssembler._usage` → settlement 的 `usage` 字段（或 stream 里的 raw record）→ 三条纯折叠路径——`tokenUsage`（可替换、可累加的累计）、`contextPressure`（prompt 侧占用率 + surface 移动量）、`deriveTurnTokenUsage`（精确、fail-closed）。** 精确披露宁可不给，是因为它承诺的是"**精确**"：一旦用估算补齐，它就与 `tokenUsage` 没有区别了。

1. **入口唯一**：`StreamChunk` 里只有一个 `usage` 变体（`packages\llm\llm\src\types.ts` 第 458 行），且协议要求它在 `finish` 之前（同文件第 444–451 行的文档 + `docs\subsystems\llm-streaming.zh.md` 第 300 行）。
2. **两种落盘形态**：`assistant/message` 有显式 `usage` 字段（`session\src\types.ts` 第 347 行）；`assistant/attempt` **没有**该字段，usage 只存在于内嵌 stream 里的 raw record。所以 `usageOf()` 必须两条路都走（`usage-projection.ts` 第 82–86 行）。
3. **三个投影的态度不同**：`tokenUsage` 用 `addReplacing` 做"同 attempt 替换、跨 attempt 累加"（§3.12）；`contextPressure` 用 `max(0, pressure + surface - sampledSurface)` 回答**下一个**请求（§3.13）；`deriveTurnTokenUsage` 只要有任何缺口就 `return undefined`（§3.13）。
4. **为什么 fail-closed 是对的**（标注为推断，依据是函数 JSDoc）：这个函数是给"账单/审计"类消费方用的（客户端 turn 页脚、精确汇总），它的价值全在"这几个数字一定对"。如果它像投影那样"缺就少算一点"，消费方就再也分不清"这里真的没用量"和"这里的数据没了"。
