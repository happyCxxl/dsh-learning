## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：一条机制链——**声明依赖 → 解析成数据 → 变成 fiber 自己的字段 → 折成一个门控条件 → 被服务变更唤醒 → 读取时再守一次**。
**不是**：`ctx` 代理的整体实现（那是 2.1）、作用域与 `isolate`（那是 2.5）、effect 的注册与回滚（那是 2.3）。

### 0.2 现在只要记住这 3 件事

1. **`inject` 不是"请求服务"的语法，是"声明前置条件"**：它把 fiber 的启动条件从"被 `ctx.plugin()` 调用"改成"被调用 **且** 列出的服务全部就绪"。
2. **没写 `inject` 就读 `ctx.<服务名>` 一定抛错**，而且**抛在你读它的那一刻**——插件本身照常进入 `ACTIVE`。读服务有三条路：`inject` + `ctx.<名>`（硬依赖）、`ctx.get('名')`（可选、拓扑无关）、`ctx.inject(deps, cb)`（把"需要它的那部分注册"变成子插件）。
3. **依赖是持续的，不是一次性启动检查**：提供方卸载 → 依赖方跟着卸载（跑 disposer）；服务回来 → 依赖方自动重载。

### 0.3 明确授权：这些现在不用管

- `isolate` 的完整语义、`notify` 第三个默认 `filter` 参数到底在比什么——**第一次读只要知道"不同作用域的同名服务互不唤醒"就够了**，展开在 `2.5`；
- `@Inject()` 装饰器在继承链上怎么造 `static inject`（`symbols.checkProto` 那一路）——**跳过不影响本课**，本课只用到"它最终也写进同一份 `static inject`"；
- `!!js` 表达式在 loader 里什么时候求值——属于 `2.6`，本课只在 §5.3 点到"行级 `inject` 决定它有没有服务可读"。

### 0.4 本课依赖 2.1 的四个词

`ctx`（共享登记处）、`plugin`（可挂可卸的代码单元）、`Fiber`（一次插件运行的实例）、`Service`（登记处里一项具名能力）——这四个词由 `notes\2-插件内核\2.1-四个核心对象.md` 定义，本课不重复。

## 1. 最小词汇表（本课新增的 5 个词）

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **inject 依赖声明** | 插件写在门口的**前置条件清单**：这些能力没到位，我就不开工 | `export const inject = ['a']`、`{ apply, inject }`、`static inject`、`inject: { a: cfg }` |
| **provide 提供** | 把一项能力**登记**到共享登记处，并负责在卸载时注销 | `class X extends Service` + `super(ctx, 'name')`；`ctx.provide(name, value, check?)` |
| **PENDING 待命** | fiber 的一种**合法状态**：在等前置条件，不是出错 | `fiber.state === 0`（`FiberState.PENDING`） |
| **epoch 门控值** | 把"依赖齐不齐"浓缩成**一个字符串**：齐了就加载，不齐就卸载 | fiber 上私有的 `_runner.epoch`，不齐时等于 `'__INACTIVE__'` |
| **intercept 配置覆盖** | 随这项依赖**附带给我的那份配置**（不是服务名列表） | `inject: { svc: cfg }`，由服务的 `[symbols.resolveConfig]` 合并 |

> ⚠️ 这五个词都属于 cordis 的词汇体系，而 cordis 是第二编的主题。上表是本课**已经够用**的程度：为什么 fiber 能停在 PENDING、`epoch` 变了之后做什么，下面 §3 全部用源码交代。

## 2. 先建立画面

### 2.1 谁在等谁（静态结构）

```
提供方 fiber                          消费方 fiber
─────────────                        ─────────────
class Counter extends Service         export const inject = ['counter']
  constructor(ctx) {
    super(ctx, 'counter')  ──────┐
  }                              │
                                 │  ctx.reflect.store[<isolate symbol>] = impl
                                 │        { name, value, fiber, check? }
                                 │                    │
  fiber 卸载 ──► disposer 删条目 ─┤                    │
                                 │                    ▼
                                 │        fiber._checkImpl('counter')
                                 │          从 store 取 impl
                                 │          要求提供方 state === ACTIVE
                                 │          再过一次 impl.check()
                                 │                    │
                                 │        fiber._store['counter'] = impl
                                 │                    │
                                 └──────────►  fiber._refresh()
                                              epoch = '' + ':' + impl.fiber.uid
                                                       │
                              全部依赖都有 ──► epoch 有效 ──► 加载 apply()
                              任一依赖缺失 ──► epoch = '__INACTIVE__' ──► 卸载
```

读法：**提供方只负责"登记"，不负责"通知谁"**；能否开工由**消费方自己的 `_store` + `epoch`** 决定。这条分工决定了后面所有行为——比如"服务未就绪时既不报错也不阻塞"。

### 2.2 fiber 的状态机（动态过程）

```
                有未满足的依赖
     ┌──────────────────────────────────┐
     ▼                                  │
  PENDING (0) ──依赖齐了──► LOADING (1) ──apply 跑完──► ACTIVE (2)
     ▲                          │                          │
     │                     config/apply 抛错                │ 提供方消失
     │                          ▼                          ▼
     │                      FAILED (3)              UNLOADING (5)
     │                                                    │
     └──────────── disposer 跑完且依赖仍缺 ◄───────────────┘
                          │
                    被 dispose()
                          ▼
                    DISPOSED (4)
```

枚举顺序与语义出处：`vendor\cordis\src\fiber.ts` 第 139–154 行，原文把六个状态逐个写清（`PENDING` — waiting for required services; `ACTIVE` — loaded and providing; …）。§3.2 的实测数字按这个顺序映射。

### 2.3 大白话版：插件 B 在等插件 A 的东西

**完全不用上面的术语**（来源：`docs\cordis-tutorial\03-services.zh.md` 第 37–42、59、72、74–78 行的叙述，这里只做白话转述，机制留到 §3）。

1. 插件 A 启动时，把"我能干什么"写进一个公共登记本，并写明**我走了要自己划掉**。
2. 插件 B 的门口贴着一张纸条："登记本里没有 `greeter`，我就不开工。"
3. 启动器把 A、B 一起叫起来，**谁先到无所谓**。B 到了，看一眼登记本，发现没有，就**站在门口等着**——不报错、不超时、也不打扰任何人。
4. A 到了，登记完；登记本看门人顺手把"`greeter` 出现了"这件事通知一遍。
5. B 被叫醒，再查一次登记本，这次齐了，于是真的开工（它那段代码这时才第一次被执行）。
6. 运行中 A 被卸下：登记本上 `greeter` 被划掉，看门人再通知一遍；B 被**卸载**（它注册过的东西全部撤销），回到门口继续等。
7. A 再上来：B 重新开工一次。整个过程没有轮询、没有重试定时器。

→ 这就是 `inject` 的全部故事。剩下的是三个追问：**"齐了"是谁判的**（§3.2）、**"通知"是谁发的**（§3.3）、**读的那一刻谁在拦**（§3.4）。

## 3. 结论与机制：五个面拆开看

### 3.0 结论先行（一张表）

| 写法 | 读服务的方式 | 前置条件 | 未就绪时 |
|---|---|---|---|
| `inject: ['svc']` / `export const inject = [...]` / `static inject = [...]` | `ctx.svc`（属性读） | 该服务已在同一 isolate 作用域被 provide，且提供方 fiber `ACTIVE` | fiber 停在 `PENDING`，`apply` **完全不执行**，不报错 |
| 不写 `inject` | `ctx.get('svc')`（显式查询） | 无，随时可读 | 返回 `undefined`，插件照常加载 |
| `ctx.inject(['svc'], cb)` | callback 内的 `ctx.svc` | 同第一行 | 该 callback 对应的**子 fiber** 停在 `PENDING` |

**三条硬结论**（每条都在下方源码里找到落点）：

1. **不写 `inject` 就读 `ctx.svc` 一定抛错**，且抛在读取那一刻——错误文案由 proxy 的 get trap 构造：`cannot get property "<name>" without inject`。这不是"值可能是 undefined"，而是"这个 fiber 没有资格读它"。
2. **服务未就绪时既不等待阻塞、也不报错，而是停在 `PENDING`**——一个合法且静默的终态；若组合里没有别的活动项，Node 进程会以状态码 0 悄悄退出。
3. **依赖是持续的，不是一次性启动检查**：提供方 fiber 卸载会让每个 `inject` 了该服务的 fiber 跟着卸载（跑 disposer），服务回来后再自动重载。

> 口径说明：结论 2 的后半句（静默退出、退出码 0）来自文档 `docs\cordis-tutorial\03-services.zh.md` 第 72 行原文「既不崩溃，也不会只运行一部分……进程会静默地以状态码 0 退出」，**未实测**（原因见 §6.3）；前半句（停在 `PENDING`）已实测，见 §4 的 B1。

### 3.1 声明面之一：两种形态、一份元数据

**知识点**：插件可以只声明"我要哪些服务"，也可以同时声明"这项服务给我的那份配置是什么"。

#### 块 1 — `Inject` 类型只有两种形态

`vendor\cordis\src\registry.ts` 第 12–19 行

```ts
/**
 * Service dependency declaration accepted by plugins and the `@Inject`
 * decorator.
 *
 * Array form requests services without intercept config. Object form maps each
 * service name to optional intercept config for the plugin context.
 */
export type Inject<M = Dict> = (keyof M)[] | { [K in keyof M]?: M[K] }
```

按块讲解：

- **做什么**：定义依赖声明的类型——**数组形态**（只要服务，不带配置）与**对象形态**（服务名 → 该服务给本插件上下文的 intercept 配置）。
- **与哪个知识点相关**：§3.0 表格的第一列与第三列；也是"没有 optional 语法"这一结论的类型层证据。
- **为什么这么写**：作者在 JSDoc 里把两种形态的差别写成一句话（`Array form requests services without intercept config`）。注意类型上**根本没有"可选依赖"这个形状**——想可选就必须不写进 `inject`（见 §3.4）。

#### 块 2 — 归一化：`Inject.resolve()` 把三种来源压平成一张 map

**知识点**：三种插件形态（函数 / `{ apply }` 对象 / 类）最终共用同一份"服务名 → 配置或 `null`"的数据。

`vendor\cordis\src\registry.ts` 第 62–89 行

```ts
/** Utilities for normalizing plugin dependency declarations. */
export namespace Inject {
  /**
   * Convert array/object/class-inherited inject metadata into a plain map.
   *
   * @param inject — the declaration to normalize; `null`/`undefined` add nothing.
   * @param result — the map to fill (service name → intercept config or `null`).
   * @returns `result`.
   */
  export function resolve(inject: Inject | null | undefined, result: Dict = Object.create(null)) {
    if (!inject) return result                                   // 没声明：得到空 map
    if (Array.isArray(inject)) {
      for (const name of inject) {
        result[name] = null                                      // 数组形态：配置写成 null
      }
    } else if (Reflect.has(inject, symbols.checkProto)) {
      Object.assign(result, resolve(Object.getPrototypeOf(inject)))   // 先递归父原型（类继承链）
      for (const name of Object.keys(inject)) {
        result[name] = inject[name] ?? null                      // 再用自身覆盖父原型
      }
    } else {
      for (const name of Object.keys(inject)) {
        result[name] = inject[name] ?? null                      // 对象形态：`?? null` 让 undefined 也变成 null
      }
    }
    return result
  }
}
```

按块讲解：

- **做什么**：把声明统一成 `{ 服务名: 配置|null }`。`result` 有默认值（`Object.create(null)`），所以调用方可以只传一个参数，也可以复用已有 map 累加。
- **与哪个知识点相关**：§3.1 的上一块是类型，这一块是**运行时的归一化**；`null` 的语义是"没有 intercept 配置"，**不是**"可选依赖"。
- **为什么这么写**：`?? null` 是关键——对象形态里写 `{ svc: undefined }` 与写 `{ svc: null }` 等价，都是"只要服务、不要配置"。所以 `inject: { a: null, b: null }` 与 `inject: ['a', 'b']` 完全等价。
- **`symbols.checkProto` 那一路**：`@Inject()` 在类上造出来的 `static inject` 是一条**原型链**（子类原型指向父类的 `inject`）。递归父原型再覆盖自身，就实现了"子类的依赖 = 父类的依赖 + 自己的依赖"。
- **实测**（命令与输出见 §4.2 的 H 段）：`Inject.resolve(['x','y'])` → `{"x":null,"y":null}`；`Inject.resolve({x:{k:1},y:null,z:undefined})` → `{"x":{"k":1},"y":null,"z":null}`；`Inject.resolve(undefined)` → `{}`。

#### 块 3 — `@Inject()`：类形态与方法形态都收敛到同一份数据

**知识点**：装饰器不是第三套机制，它只是"往 `inject` 里写一笔"。

`vendor\cordis\src\registry.ts` 第 26–60 行

```ts
/**
 * Decorator for declaring service dependencies on classes or class methods.
 *
 * On classes it contributes to the plugin's static `inject` map. On methods it
 * delays the method call until the declared services are available.
 */
/**
 * @param name — the required service name.
 * @param config — optional intercept config applied for that service.
 * @returns the class or method decorator.
 */
export function Inject<K extends InjectKey>(name: K, config?: Context[K] extends { [symbols.config]: infer T } ? T : never) {
  return function (value: any, decorator: ClassDecoratorContext<any> | ClassMethodDecoratorContext<any>) {
    if (decorator.kind === 'class') {
      if (!Object.hasOwn(value, 'inject')) {
        defineProperty(value, 'inject', Object.create(Object.getPrototypeOf(value).inject ?? null))
        defineProperty(value.inject, symbols.checkProto, true)   // ← 标记"这条链要递归父原型"
      }
      value.inject[name] = config                               // 类形态：写进 static inject
    } else if (decorator.kind === 'method') {
      const inject = (value[symbols.metadata] ??= {}).inject ??= Object.create(null)
      inject[name] = config
      decorator.addInitializer(function () {
        const property = this[symbols.tracker]?.property
        ;(this[symbols.initHooks] ??= []).push(() => {          // 方法形态：推迟到实例构造之后
          (this.ctx as Context).inject(inject, (ctx) => {
            return value.call(property ? withProps(this, { [property]: ctx }) : this)
          })
        })
      })
    } else {
      throw new Error('@Inject() can only be used on class or class methods')
    }
  }
}
// （第 12–24 行的 `isApplicable`/`Inject` 类型定义块与本节无关，此处省略；本块从第 26 行的 JSDoc 起）
```

按块讲解：

- **做什么**：`@Inject('svc')` 用在**类**上 → 往 `static inject` 上写一笔（必要时先把父类的 `inject` 挂成原型，并打上 `checkProto` 标记，正是块 2 里那一支）；用在**方法**上 → 把配置记在类元数据里，并在实例化后通过 `initHooks` 调一次 `ctx.inject(inject, …)`。
- **与哪个知识点相关**：块 2 的 `checkProto` 分支在这里生成；方法形态的落点是"一次真正的 `ctx.inject`"，等价于 §3.0 表格的第三行。
- **`initHooks` 什么时候跑**：`new` 之后立刻——`vendor\cordis\src\fiber.ts` 第 247–263 行的 `_runner.execute` 里，类形态构造完实例后 `for (const hook of instance?.[symbols.initHooks] ?? []) hook()`。
- **为什么这么写**：作者原文一句就够——`On classes it contributes to the plugin's static inject map. On methods it delays the method call until the declared services are available.` 两种用法共用一个装饰器名，但落到同一条依赖判定上。

### 3.2 门控面：`inject` 变成 fiber 的字段，再折成一个 epoch

#### 块 4 — 绑定：`new Fiber` 时 inject 被写进 fiber 自己的字段与 intercept 表

**知识点**：`inject` 从"插件上的声明"变成"fiber 上的数据"，是 `RegistryService.plugin()` 与 `Fiber` 构造函数交接的。

`vendor\cordis\src\registry.ts` 第 316–330 行

```ts
  plugin(plugin: Plugin, config?: any, getOuterStack = buildOuterStack()) {
    // check if it's a valid plugin
    const callback = this.resolve(plugin)
    if (!callback) throw new Error('invalid plugin, expect function or object with an "apply" method, received ' + typeof plugin)
    this.ctx.fiber.assertActive()                                // ← 守卫：调用方 fiber 已被 dispose 就不许再挂插件

    let runtime = this._internal.get(callback)
    if (!runtime) {
      let name = plugin.name
      if (name === 'apply') name = undefined
      runtime = { name, callback, fibers: new DisposableList(), Config: plugin.Config }
      this._internal.set(callback, runtime)
    }

    const fiber = new Fiber(this.ctx, config, Inject.resolve(plugin.inject), runtime, getOuterStack)
    // …（第 331–335 行：把 fiber 包成 PromiseLike 后返回，与本知识点无关，此处省略）
```

按块讲解：

- **做什么**：`plugin()` 解析插件形态 → 断言当前 fiber 还活着 → 取/建 runtime 记录 → **把 `Inject.resolve(plugin.inject)` 作为第 3 个构造参数**交给 `Fiber`。
- **依赖变量从哪来**：`plugin.inject` 来自三种形态的声明点（函数/命名空间插件的具名导出、`{ apply }` 对象的字段、类的 `static inject`）；`runtime` 是"同一份插件代码的所有 fiber 共享的记录"，`runtime.fibers` 就是后面 `notify` 遍历的对象。
- **与哪个知识点相关**：这是 §3.1（声明）与 §3.2（判定）的接缝——**归一化就发生在这一行**，`Fiber` 拿到的永远是同一种 map。
- **实测 A 段**（§4.1）看到 `fiber.inject = {}`（空对象）而不是 `null`/`undefined`，就是因为这里已经过 `Inject.resolve(undefined)` 返回空 map。

#### 块 5 — 构造函数：intercept 表 + 依赖判定 + 状态互斥

**知识点**：intercept 配置在这里落到本 fiber 的上下文；`_checkImpl` + `_refresh` 是"能不能开工"的全部计算。

`vendor\cordis\src\fiber.ts` 第 212–245 行

```ts
  /**
   * Create a fiber. Plugin authors normally obtain fibers from `ctx.plugin()`
   * rather than constructing them directly.
   *
   * @param parent — the context the plugin was loaded from.
   * @param config — raw config, validated against the runtime's schema.
   * @param inject — resolved dependency map (service name → intercept config).
   * @param runtime — the shared plugin runtime, or `null` for the root fiber.
   * @param getOuterStack — captures the caller stack for effect diagnostics.
   */
  constructor(
    public parent: Context,
    config: any,
    public inject: Dict<any>,                                    // ← 公开字段：注入 map
    public runtime: Plugin.Runtime | null,
    getOuterStack: () => string[],
  ) {
    this._config = config
    const collect = (dispose: Disposable) => {
      this._disposables.push(dispose)
    }

    if (runtime) {
      this.uid = parent.registry.counter
      this.ctx = this.context = parent.extend({ fiber: this })

      const injectEntries = Object.entries(this.inject)
      if (injectEntries.length) {
```

- **做什么**：给 fiber 分配 `uid`、派生自己的 `ctx`（`parent.extend({ fiber: this })`）、把 inject 里**非 null** 的项写进本 ctx 的 intercept 表。
- **依赖变量从哪来**：`this.inject` 就是块 4 里 `Inject.resolve()` 的产物；`parent[Context.intercept]` 是父上下文的表，用 `Object.create` 继承——所以子 fiber 的配置表是"父表 + 自己这一层"，最终由服务的 `[symbols.resolveConfig]` 沿原型链合并。

#### 块 6 — `_checkImpl`：拿到实现，再单独过一次 `check()` 谓词

**知识点**：依赖"存在"与依赖"可用"是两件事。

`vendor\cordis\src\fiber.ts` 第 597–623 行


### 3.3 唤醒面：不是轮询，是服务变更驱动

#### 块 8 — `_updateState`：状态真的跨越 ACTIVE 边界时，主动通知

`vendor\cordis\src\fiber.ts` 第 581–595 行

```ts
  private _updateState(callback: () => void | FiberState) {
    const oldState = this.state
    this.state = callback() ?? this._getState()
    if (oldState === this.state) return                            // 守卫：状态没变，不发事件也不通知
    // FIXME internal/fiber-info

      if (impl.fiber !== this) continue                            // 只关心"本 fiber 提供的"那些服务

    }
  }
```

按块讲解：

- **做什么**：改状态、发 `internal/status`，并在**跨越 `ACTIVE` 边界**时，把本 fiber 提供的每个服务名交给 `notify`。
- **依赖变量从哪来**：`this.ctx.reflect.store` 是全局服务表（键是 isolate symbol，值是 `Impl`）；`this` 是被唤醒方（提供方）的 fiber。
- **与哪个知识点相关**：结论 3"依赖是持续的"——提供方挂载/卸载会走到这里，于是依赖方被重新判定。
- **为什么这么写**：`only notify changes between ACTIVE and NON-ACTIVE states` 这条注释是设计意图：`LOADING → ACTIVE` 要通知（服务可用了），`ACTIVE → UNLOADING` 要通知（服务要走了），而 `PENDING → LOADING` 不通知（这时候还没提供任何东西）。
- **`internal/status` 顺带解释了诊断手段**：`fiber.state === FiberState.PENDING` 就是"缺依赖"的判据（文档 `docs\cordis-tutorial\06-composition-and-hmr.zh.md` 第 63、109 行给的诊断脚本正是这么写的）。

#### 块 9 — `notify()`：遍历所有 fiber，命中的重算，最后发一次 `internal/service`

`vendor\cordis\src\reflect.ts` 第 307–336 行

```ts
  /**
   * Re-evaluate every fiber that requires one of the given services.
   *
   * @param names — the service names that changed.
   * @param filter — restricts notification to matching isolation scopes.
   * @returns the fibers whose dependency state was refreshed.
   */
  notify(names: string[], filter = (ctx: Context, name: string) => ctx[symbols.isolate][name] === this.ctx[symbols.isolate][name]) {
    const fibers: Fiber[] = []
    for (const runtime of this.ctx.registry.values()) {            // ① 所有已注册插件
      for (const fiber of runtime.fibers) {                        // ② 每个插件的每条 fiber
        let hasUpdate = false
        for (const name of names) {
          if (!(name in fiber.inject)) continue                    // ③ 不含这个依赖：跳过
          if (!filter(fiber.ctx, name)) continue                   // ④ 不在同一 scope：跳过
          hasUpdate = true
          fiber._checkImpl(name)                                   // ⑤ 重判这一个依赖
        }
        if (!hasUpdate) continue
        fiber._refresh()                                           // ⑥ 重算 epoch
        fibers.push(fiber)
      }
    }
    for (const name of names) {                                    // ⑦ 名字全部处理完后，逐个发事件
      const self: Context = Object.create(this.ctx)
      self[symbols.filter] = (target: Context) => filter(target, name)
      this.ctx.events.emit(self, 'internal/service', name, this._getImpl(name, false)?.value)
    }
    return fibers
  }
```

按块讲解：

- **做什么**：把所有 fiber 扫一遍，命中"依赖了这个名字 **且** 在同一 isolate 作用域"的，重算门控；最后为每个名字发一次 `internal/service` 事件。
- **依赖变量从哪来**：`names` 由调用方给（`provide` 成功时、`provide` 的 disposer 里、`_updateState` 里各一处）；`filter` 的默认值是**比较两个上下文的 isolate symbol 是否同一个**——这就是"不同作用域的同名服务互不唤醒"。
- **与哪个知识点相关**：结论 3 的另一半；也是 §3.0 表格里"已在同一 isolate 作用域被 provide"这个限定的出处。
- **为什么这么写**：`fiber._checkImpl(name)` 只重判**变化的那几个名字**（而不是全部依赖），`_refresh()` 才遍历全部——**增量重判 + 全量折叠**，代价小且语义干净。
- **`internal/service` 事件的位置**：在**所有 fiber 都重算完之后**才发，所以监听者看到这条事件时，"谁能用这个服务"已经更新完了。

**知识点**：`inject` 不是"允许读"的开关，属性读的每一次都过守卫。

#### 块 10 — get trap：先构造错误，再沿 fiber 祖先链找

### 3.5 生命周期面：提供 / 取用 / 注销

#### 块 12 — `ctx.provide()`：整个注册包成一个 effect，注销顺序写死

`vendor\cordis\src\reflect.ts` 第 267–305 行

```ts
  /**
   * Register a service implementation owned by the current fiber.
   *
   * See the `ctx.provide()` overload above for the full contract.
   *
   * @param name — the service name.
   * @param value — the service value.
   * @param check — optional availability predicate for dependents.
   * @returns a disposer that unregisters the service.
   */
  provide(name: string, value?: any, check?: () => boolean) {
    return this.ctx.fiber.effect(() => {                           // ← ① 注册是一个 effect：随 fiber 卸载自动撤销
      if (!this.props[name]) {
        this.props[name] ??= { type: 'service' }
      } else if (this.props[name].type !== 'service') {
        throw new Error(`property "${name}" is already declared as ${this.props[name].type}`)
      }
      this.props[name] = { type: 'service' }                       // ← ② 声明表（has trap 判的是它，见 §5.2）

      this.ctx.root[symbols.isolate][name] ??= Symbol(name)        // ← ③ 首次出现时分配作用域标签（symbol）
      const key = this.ctx[symbols.isolate][name]
      const impl: Impl = { name, value, fiber: this.ctx.fiber, check }
      if (this.store[key]) {
        throw new Error(`service "${name}" has been registered at <${this.store[key].fiber.name}>`)
      }
      this.store[key] = impl                                       // ← ④ 全局表
      this.ctx.fiber.store![name] = impl                           // ← ⑤ 提供方自己的快照（自己也能读自己）
      if (this.ctx.fiber.state === FiberState.ACTIVE) {
        this.notify([name])                                        // ← ⑥ 已 ACTIVE：立刻唤醒依赖方
      }
      return async () => {                                         // ← ⑦ disposer
        delete this.store[key]
        const fibers = this.notify([name])                         //   先广播，收集受影响的 fiber
        await Promise.allSettled(fibers.map(fiber => fiber.await()))   // 再等它们全部落定
        // ensure self access before dependencies cleanup
        delete this.ctx.fiber.store![name]                         //   最后才删自己的快照
      }
    }, `ctx.provide(${JSON.stringify(name)})`)
  }
```

按块讲解：

- **做什么**：一个函数完成六件事——声明属性、分配 isolate symbol、写全局表、写自己的快照、必要时唤醒、返回一个"顺序写死"的 disposer。
- **依赖变量从哪来**：`check` 是第 3 个参数（块 6 用它）；`this.ctx.fiber` 是"谁提供的"（决定服务寿命）；`symbols.isolate` 是名字到作用域标签的映射。
- **与哪个知识点相关**：§3.0 表格第 1 行的"同一 isolate 作用域被 provide"在这里落实；结论 3 的"提供方卸载 → 依赖方跟着卸载"就在 ⑦ 里。
- **为什么这么写**：作者在 ⑦ 里留了一行注释——`ensure self access before dependencies cleanup`。顺序是**先删全局表 → 再通知并按名字等所有依赖方落定 → 最后删自己的快照**：这样依赖方在被卸载的过程中，若还需要读这个服务，走自己的快照仍能读到（"self access"）。反过来先删自己的快照，依赖方在卸载期读它就变成 `undefined`。
- **撞名的报错**：`service "name" has been registered at <提供方 fiber 名>`——注意 `<...>` 里是**提供方 fiber 的名字**，不是文件路径。
- **`Service` 走的是同一条路**：`vendor\cordis\src\service.ts` 第 42–59 行的构造函数最后一句就是 `self.ctx.reflect.provide(name, self, this[symbols.check])`（第 57 行）；JSDoc 第 8–9 行原文：`The service is registered immediately and is automatically removed with the owning fiber.`

#### 块 13 — 提供方：`ctx.provide` 在命令回调里释放一次调用的结果

```ts
/**
 * Parse and provide the Web invocation as an ordinary Cordis service. The
 * command's action publishes the flags this invocation named; `--host 0.0.0.0`,
 * a non-numeric `--port`, or a malformed `--public-url` is a usage error, so on
 * rejection (and on `--help`) nothing is provided.
 * @param ctx - plugin context carrying the command line.
 */
export function apply(ctx: Context): void {
  const program = webCommand()
  program.action(() => {
    const options = program.opts<WebOptions>()
    if (options.host === '0.0.0.0') {
      program.error('error: --host 0.0.0.0 is intentionally not supported yet for safety: it would expose remote code execution to the network; use 127.0.0.1 instead')
    }
    if (options.port !== undefined && !/^\d+$/.test(options.port)) {
      program.error(`error: --port must be a number, got ${JSON.stringify(options.port)}`)
    }
    if (options.publicUrl !== undefined) {
      try {
        parsePublicUrl(options.publicUrl, '--public-url')
      } catch (error) {
        program.error(`error: ${(error as Error).message}`)
      }
    }
    ctx.provide(WEB_STARTUP_SERVICE, {                            // ← 只在参数全部通过校验后才提供
      openBrowser: options.open,
      ...options.host !== undefined && { host: options.host },
      ...options.port !== undefined && { port: Number(options.port) },
      ...options.publicUrl !== undefined && { publicUrl: options.publicUrl },
      trustedHosts: options.trustedHost ?? [],
    } satisfies WebStartupValues)
  })
  parseCmdline(ctx, program)
}
```

按块讲解：

- **做什么**：这个插件的 `apply` **不直接提供服务**——它注册一个命令回调，**由回调在运行时决定是否提供**。

## 5. 两个易错点（各配结论与源码）

### 5.1 对象形态的 `inject` 不是"三个服务名"

`inject: { svc: cfg }` 的语义是"依赖 `svc`，并把 `cfg` 作为该服务给本插件上下文的 intercept 配置"：块 2 归一化成 `{ svc: cfg }`（`?? null` 只对 `null`/`undefined` 生效），块 5 把它写进本 fiber 的 intercept 表，再由服务的 `[symbols.resolveConfig]` 沿 intercept 原型链合并（`vendor\cordis\src\service.ts` 第 86–102 行）。实测见 §4.2 的 G 段。

**所以：写 `inject: { a: null, b: null }` 等价于 `inject: ['a', 'b']`；要"可选"就完全不要写进 `inject`——写进去就是硬依赖。**

### 5.2 服务注销后 `'svc' in ctx` 仍是 `true`

块 12 的 disposer 只删 `reflect.store[key]`，没删 `reflect.props[name]`；而 proxy 的 `has` trap 判的是 `props`（`vendor\cordis\src\reflect.ts` 第 199–205 行）：

```ts
    has: (target, prop) => {
      if (isSpecialProperty(prop)) {
        return Reflect.has(target, prop)
      }
      if (Reflect.has(target, prop)) return true
      return !!target.reflect.props[prop]                       // ← 声明表还在，于是 in 仍为 true
    },
  }
```

→ **按存在性做门控要用 `ctx.get(name) !== undefined`，不要用 `in`。** 实测见 §4.2 的 F 段。

按块讲解：

- **这一行的 `inject: [webStartup]` 在做什么**：它给一条 **loader 行**声明硬依赖，让紧随其后的 `config` 里那两句 `!!js ctx.webStartup.*` 有服务可读——**表达式求值发生在这一行的 fiber 激活之后**（文档口径：`docs\cordis-primer.zh.md` 第 45 行「Loader 在声明的注入激活后，基于该插件上下文插值条目的 `config`」）。

- **另有两处同构用法**：第 199–207 行的 `web-runtime` 行同样 `inject: [webStartup]`；第 229–236 行的 `connection` 行 `inject: [webRuntime]`，其 `config` 读 `ctx.webRuntime.trustedHosts`，而 `webRuntime` 由 `packages\bundle\web-app\src\index.ts` 第 250 行的 `ctx.provide` 释放。
- **这就是"依赖驱动求值顺序"的完整闭环**：插件级 `inject` 决定**插件什么时候跑**（结论 2），行级 `inject` 决定**配置里的表达式什么时候有值**（本节）。

> ✅ 七道题**全部给出明确答案**，不留空、不写"待补充"。Q1–Q4 是第一次读就该能答的；**Q5–Q7 涉及 DSH 侧的具体配置与易错细节**（行级 inject、`ctx.inject` 的落点、对象形态与 `in` 陷阱），第一次读可以跳过，回查时再看。

### Q1 `inject` 解决什么问题？不写 `inject` 直接取服务会发生什么？

→ 解决的是**加载顺序与可用性保证**：把"谁先启动"从配置文件的行序改成服务依赖图。`inject` 列出的服务全部可用之前，fiber 停在 `PENDING`（块 6 的 `_refresh` 只要有一个 `_store[name]` 缺失就把 epoch 打回 `INACTIVE`），插件 callback 完全不执行；文档 `docs\cordis-tutorial\03-services.zh.md` 第 59 行把这件事写成对插件作者的承诺：「在 `apply` 内可以保证 `ctx.greeter` 已经就绪」，同一行还写明「`cordis.yml` 中的加载顺序无关紧要：决定插件何时启动的是依赖关系，而不是文件顺序」。

不写 `inject` 直接 `ctx.counterSvc`：**抛错**，文案 `cannot get property "counterSvc" without inject`（块 10 的 ③⑦⑧⑨；实测 A 段）。这是**读取时刻**的失败，不是加载时刻——插件本身会正常进入 `ACTIVE`，直到那一行属性访问才炸。0001 号事故就是这个模式的真实翻车：ACP 插件因为 `export default apply` 让 loader 丢掉了 `inject`，于是运行期第一行 `ctx.agents` 抛错，178 个单测全绿、生产环境连不上（出处：`docs\postmortem\0001-acp-default-export-drops-inject.zh.md` 第 13、22、50–52 行）。

### Q2 服务未就绪时依赖它的插件会怎样（等待还是报错）？

→ **等待**，具体是停在 `PENDING`（`FiberState.PENDING = 0`），**既不报错也不超时**，且 `apply` 一次都不执行（实测 B1：状态 0，状态事件串里没有 consumerB）。要区分两种情况：

- 服务**还没被 provide**：`_store` 里没有该项，epoch = `INACTIVE`（块 6）。
- 服务**已被 provide 但 `check()` 谓词为假**：`_checkImpl` 主动 `delete this._store[name]`（块 6 的第二个 `return delete`），效果同样是 `PENDING`（实测 D1）。`ctx.provide` 的第三个参数就是这个谓词（块 12 的 `check`），`Service.check` 静态 symbol 与之对应（`vendor\cordis\src\service.ts` 第 15 行）。

PENDING 是**合法状态而非错误**（文档 `docs\cordis-tutorial\06-composition-and-hmr.zh.md` 第 63 行：「这不是错误，因为 PENDING 是合法状态，提供方可能稍后才挂载」）。两个实践后果：一是插件作者不要靠"没日志"判断自己没加载，要查 fiber 状态（同文件第 109 行）；二是 PENDING 的 fiber 不会让 Node 事件循环保持活跃，组合里没有别的活动项时进程静默退出、退出码 0（文档 `docs\cordis-tutorial\03-services.zh.md` 第 72 行；**本课未实测这一条**，见 §4.3）。

### Q3 可选依赖怎么写？

→ 有两条路，**都不是**在 `inject` 里加标记（源码里根本没有 optional 语法：`Inject` 类型只有数组与"服务名→intercept 配置"两种形态，块 1）：

1. **省略 `inject`，在使用处 `ctx.get(name)` 探测**。`ctx.get` 返回 `undefined` 而不是抛错（块 11，实测 C2），`strict` 默认 `true`，只返回提供方 `ACTIVE` 的实现，所以 teardown 期间不会拿到垂死的后端（实测 F 段）。官方文档给的写法就是 `const metrics = ctx.get('metrics'); metrics?.record(...)`（`docs\user\develop\framework\service.zh.md` 第 95–99 行；`docs\cordis-tutorial\03-services.zh.md` 第 82–90 行同一结论：「`inject` 用于硬性依赖……请跳过 `inject`，并在使用处探测」）。
   **必须用 `ctx.get` 而不是 `ctx.<name>`**：属性读只沿 fiber 祖先链上溯，跨 fiber 拿到的可追踪代理会把查找起点换成 shadow 上下文，兄弟分支的服务永远找不到（块 10 的 ⑤；出处 `docs\postmortem\0001-acp-default-export-drops-inject.zh.md` 第 77、87、111 行）。真实用例见块 14。
2. **把"需要它的那部分注册"变成子插件**：`ctx.inject(['sessionProjections'], (childCtx) => ...)`，服务缺席时该子 fiber `PENDING`（实测 C3：body 执行 0 次），出现时自动执行，消失时自动撤销。`docs\subsystems\session-projection.zh.md` 第 106 行把这种用法写成"贡献方可以保留"的可选注册：`ctx.inject(['sessionProjections'], …)` 让 headless 组装完全不受影响。`packages\bundle\web-app\src\index.ts` 第 253、261、272 行有三处同构实例（见块 15）。

### Q4 服务如何被提供、被取用、被注销？分别给出源码位置。

→ 三类动作、各两条（或三条）路径：

- **提供**：标准路径是 `class X extends Service` 构造函数里的 `super(ctx, name)`，实现体在 `vendor\cordis\src\service.ts` 第 42–59 行，注册调用在第 57 行 `self.ctx.reflect.provide(name, self, this[symbols.check])`；裸路径是插件 callback 里直接 `ctx.provide(name, value, check?)`，实现体在 `vendor\cordis\src\reflect.ts` 第 277–305 行（块 12），注册写 `store[key]` 与 `fiber.store[name]`。真实例子：`packages\bundle\web-app\src\startup.ts` 第 98 行 `ctx.provide(WEB_STARTUP_SERVICE, {...})`（常量 `'webStartup'` 在同文件第 22 行）。
- **取用**：硬依赖用属性读 `ctx.<name>`，解析在 `vendor\cordis\src\reflect.ts` 第 133–171 行（块 10，要求 `name in fiber.inject` 且快照命中，否则抛两种不同文案的错误）；可选读取用 `ctx.get(name, strict?)`，在 `vendor\cordis\src\reflect.ts` 第 225–243 行（块 11，经 `_getImpl` 按 isolate symbol 直查 store）；延迟注册用 `ctx.inject(deps, cb)`，在 `vendor\cordis\src\registry.ts` 第 293–302 行（块 15）。
- **注销**：服务的注销器来自 `ctx.provide()` 的返回值（块 12 的 ⑦：删 store → notify → `await Promise.allSettled(fibers.map(f => f.await()))` → 删自己的 `fiber.store`），`Service` 继承同一个 effect，所以提供方 fiber 卸载时服务自动消失（`vendor\cordis\src\service.ts` 第 8–9 行注释原文：`registered immediately and is automatically removed with the owning fiber`）；**依赖方**的注销是被动的——提供方离开 `ACTIVE` 时 `_updateState` 广播（块 8），依赖方 epoch 打回 `INACTIVE`，`_setEpoch` 走 `_unload()`（块 7），跑自己的 disposer；插件整体注销走 `ctx.registry.delete(plugin)`，在 `vendor\cordis\src\registry.ts` 第 258–267 行（删 runtime 记录 + 逐个 `fiber.dispose()`）。

### Q5（本步真实例子）`packages\bundle\web-app\cordis.patch.yml` 第 180 行的 `inject: [webStartup]` 在做什么？

→ 它给一条 **loader 行**声明硬依赖，让这行的 `config` 里那些 `!!js ctx.webStartup.*` 表达式有服务可读。证据链：

- 该行是 `webserver` 行，第 178 行 `- id: webserver`，第 180 行 `inject: [webStartup]`，紧随其后的 config 第 182–183 行就是 `host: !!js ctx.webStartup.host ?? '127.0.0.1'`、`port: !!js ctx.webStartup.port ?? 3080`。
- 文件顶部注释第 8–12 行说明了意图（原文见 §7.1）。
- 提供方是 `packages\bundle\web-app\src\startup.ts`：第 16 行 `export const name = 'web-startup'`，第 19 行 `export const inject = ['cmdlineArgs']`，第 22 行 `export const WEB_STARTUP_SERVICE = 'webStartup'`，第 98 行 `ctx.provide(WEB_STARTUP_SERVICE, {...})`（块 13）；对应行在 patch 里是第 168–169 行的 `web-startup` 条目。

注意**行级 `inject` 与插件级 `inject` 是相加的，不是替换**：`packages\bundle\web-app\src\index.ts` 第 43 行插件自己声明 `export const inject = ['webServer']`，而 patch 第 199–207 行的 `web-runtime` 行又加了 `inject: [webStartup]`，两条合并后该 fiber 等的是两个服务。合并点在 `vendor\loader\src\index.ts` 第 129–135 行的 `internal/plugin` 监听：`Inject.resolve(fiber.entry!.options.inject, fiber.inject)`——注意 `result` 传的是**已有 map**，所以是往同一张表里追加（块 15）。另有一处同构用法：patch 第 231 行 `connection` 行 `inject: [webRuntime]`，第 236 行 config 读 `ctx.webRuntime.trustedHosts`——`webRuntime` 由 `packages\bundle\web-app\src\index.ts` 第 250 行的 `ctx.provide` 释放。
另外注意**"提供不出来"的边界**：`dsh --profile web --help` 这类调用不会走到命令回调，于是 `webStartup` 从不被 provide，这些行**永远停在 PENDING**、服务器不绑定——patch 第 12 行注释明确写了这个后果（本课**未实跑 `--help` 验证**，见 §6.3）。

### Q6（易错点）`inject` 写成对象形态意味着什么？

→ 它是"带 intercept 配置的依赖"，不是三个服务名。`inject: { svc: cfg }` 会被 `Inject.resolve` 归一成 `{ svc: cfg }`（块 2 的 `?? null`），cfg 在 fiber 构造时写进本 fiber 的 intercept 表（块 5），再由服务的 `[symbols.resolveConfig]` 与祖先配置合并（`vendor\cordis\src\service.ts` 第 86–102 行）。写 `inject: { a: null, b: null }` 等价于 `inject: ['a', 'b']`。**要"可选"就完全不要写进 inject**，写进 inject 就是硬依赖。实测见 §4.2 的 G/H 段。

### Q7（易错点）服务注销后 `'svc' in ctx` 仍是 true？

→ 是。`provide` 的 disposer 只删 `reflect.store[key]`（块 12 的 ⑦），没有删 `reflect.props[name]`（块 12 的 ② 写入的那条 `{ type: 'service' }`）；而 proxy 的 `has` trap 判的是 `props`（`vendor\cordis\src\reflect.ts` 第 199–205 行）。所以按存在性做门控要用 `ctx.get(name) !== undefined`，不要用 `in`。实测见 §4.2 的 F 段。
