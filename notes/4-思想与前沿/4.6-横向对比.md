### 0.2 现在只要记住 4 件事

1. **四个体系回答的是同一个问题**——「运行中的系统如何被第三方改写」——但把答案放在了不同位置。
2. **DSH 的答案**是：注册即副作用 + 无特权内核 + 配置层叠加。
3. **替换的单位**：DSH 是「一整行配置」，Spring 是「一个 bean」，VS Code 是「一次贡献点 / 一次 API 调用」，LangChain 是「构造另一条链」。
4. **撤销的单位**：DSH 是「一个宿主 fiber」（注册方交出 disposer），Spring 是「整个容器」，VS Code 是「整个扩展宿主进程」，LangChain 没有这个概念。

## 1. 最小词汇表（7 个词，只用前文已定义的词解释）

这张表里的词，前六个是**跨体系通用**的说法（别的体系也用得上），第七个是 DSH 特有的落点。**它们都属于 `<repo>` 内已实现的概念，机制在哪一课展开见表末一列。**

| 词 | 大白话 | 在源码／配置里的样子 | 机制展开于 |
|---|---|---|---|
| **extension unit 扩展单元** | 第三方能交出来的**那一份东西**（一份代码、一份清单，或两者） | DSH：插件（函数／`Service` 子类）；Spring：一个 bean；VS Code：一个 npm 包；LangChain：一个 `Runnable` | 本课第 4.1 节 |
| **assembly 装配** | 「什么时候、按什么顺序」把这些单元装上，并让它们拿到彼此 | DSH：`inject` 门控；Spring：容器构造注入；VS Code：`activationEvents`；LangChain：链的拼装顺序 | `2.2`、`2.3` |
| **override 覆盖** | 后来者**改掉**已经在的那一份 | DSH：按 `id` 定位条目、整块替换它的 `config`；Spring：bean 定义按名／类型覆盖；VS Code：贡献点合并 | `1.2`、`1.4` |
| **extension point 扩展点** | 允许被插进来的**位置**（事件、接口、清单字段） | DSH：类型化事件 + 服务 seam；Spring：注解／接口 + 事件；VS Code：`contributes` + `vscode.*` API | `1.1` §4、`2.2` |
| **reversible registration 可逆注册** | 装上时做的每一件事，**卸下时都要能撤销** | DSH：`ctx.effect()` / `ctx.on()` 返回 disposer；VS Code：手工 `Disposable`；Spring／LangChain：无对应原语 | `1.1` §5、`2.3` |
| **scope 作用域** | 「这份贡献**对谁可见**」的划分单位 | DSH：全局或恰好一个 agent（两层，不继承）；Spring：bean scope；VS Code：全局命名空间；LangChain：`RunnableConfig` | `2.4` |

## 2. 先建立画面

### 2.1 对比总图（静态结构：四个体系把「可扩展性」放在了哪一层）

```
              ┌──────────────── 第三方能交出的东西 ────────────────┐
DSH           │ 插件（函数 / Service 子类 / 一份 patch + 空模块）      │
              │   ↓ 通过 inject 声明依赖，服务就绪才启动              │
              │   ↓ 通过 ctx.effect() / ctx.on() 注册（可逆副作用）   │
              │ 挂载到「其他插件旁边」——没有需要打补丁的内核           │
              └──────────────────────────────────────────────────┘

Spring        ┌──────────────────────────────────────────────────┐
              │ 类 / 方法 + 注解（@Component / @Bean / @Conditional）│
              │   ↓ 由 IoC 容器实例化、装配、驱动生命周期            │
              │ 挂载到「容器」——容器本身不是可替换的                 │
              └──────────────────────────────────────────────────┘

VS Code       ┌──────────────────────────────────────────────────┐
              │ npm 包：静态清单 contributes + activate() 导出       │
              │   ↓ 宿主静态读取清单（无需扩展运行）                 │
              │   ↓ activate() 里调 vscode.* API，注册返回 Disposable│
              │ 跑在独立的 Extension Host 进程里——workbench 不可替换 │
              └──────────────────────────────────────────────────┘

LangChain     ┌──────────────────────────────────────────────────┐
              │ 实现 Runnable 的对象 / 函数（或 @tool 函数）         │
              │   ↓ 用 LCEL 的 | 拼成链，配置沿 RunnableConfig 传     │
              │ 没有容器、没有注册表、没有生命周期、没有 dispose      │
              └──────────────────────────────────────────────────┘
```

**图上的纪律说明（R4 的精确性要求）**：这张图只画「第三方交出什么、交给谁」。它**没有**声称四者等价——DSH 与 Spring 都有依赖门控，但 DSH 的门控是「等到服务就绪才启动」（插件停在 `PENDING`），Spring 的是「按依赖图构造」（构造期解析）。两者的差别在第 3.2 节用源码说明。

### 2.2 一次「第三方改写」四个体系各发生什么（动态过程）

**完全不用术语的编号流程**（来源：`docs\architecture.zh.md` 第 17、27 行与 `docs\cordis-primer.zh.md` 第 9–13 行；这里只做白话转述）：

1. 启动时先读一份**空的条目表**（`cordis.yml`，内容就是 `[]`）。
2. 按 profile 点名的顺序，把每个组合包（bundle）带的那份 patch 叠上去——每一份 patch 都是「插入一串条目」。
3. 再叠 profile 自己的 patch、home 级的 patch、命令行给的 `--patch`；**后来者按 `id` 覆盖前面的行**。
4. 组装结果是一串「条目」；每个条目被加载成一个插件。
5. 插件执行时往共享上下文 `ctx` 上**登记**东西（服务、工具、监听器）——这些登记都是**副作用**。
6. 别的插件要它，就**按 key 从上下文里取**，而不是 `import` 它的具体实现。
7. 谁依赖谁写在插件里；依赖没齐，插件**不启动**，停在待命状态，不报错也不胡乱启动。
8. 卸载一个插件时，它登记过的东西**逐条撤销**（宿主按逆序执行注册时交出来的 disposer）。
9. 想让某个 agent 临时换一套能力，就把注册**挂在那个 agent 的作用域上**；作用域一变空，那一层就消失。

→ 第 4–9 步就是 DSH 与另外三个体系分道扬镳的地方；第 3.1–3.7 节逐条给源码。

## 3. DSH 侧：七个机制，逐个给源码

本节每个机制都配一块**就地源码**（R11），块上方标 `文件路径 第 A–B 行`，块下方按「做什么 / 与哪个知识点相关 / 为什么这么写」讲解。所有行号以第 6 节的固定提交为准，全部在写作时打开文件核对过。

### 3.1 无特权内核：「行」的两种来源

**(1) 结论（仓库事实）。** 「不存在需要打补丁的特权内核：扩展 dsh 的方式是把插件挂载到其他插件旁边，而各项注册都是副作用，会在其插件卸载时撤销」（`docs\architecture.zh.md` 第 13 行）。产品的每一部分都是插件，包括模型适配器、工具注册表、会话日志与 agent loop（同文件第 11 行）。

**「挂载到其他插件旁边」不是修辞**——它有两种字面形态，各给一处真实出处。

**(2) 形态一：一份 YAML 就是一个扩展单元。** `packages\bundle\base\package.json` 第 31–35 行

```json
  "dsh": {
    "bundle": {
      "patch": "./cordis.patch.yml"
    }
  },
```

- **做什么**：`package.json` 的 `dsh.bundle.patch` 指向本包自带的 patch 文件。这一行**就是**这个组合包对世界的全部声明——它不导出任何代码（同文件第 14–24 行的 `main` / `exports` 只暴露 `lib/index.js` 与那份 YAML）。
- **与哪个知识点相关**：§3.7「配置层叠加」的输入来源；也是附录 A Q3 表里「替换单位＝一整行配置」的起点。
- **为什么这么写**：作者在 `packages\bundle\base\cordis.patch.yml` 第 1–4 行的注释里写明它是 *"the shared core of each base-backed profile, applied as ONE insert over the empty profile root"* —— 一个组合包 = 一次 `insert`，它插入的一大串行**之后都能被更上层按 `id` 找到并改掉**（第 3 行原文：*"with the last write winning per row"*）。
- ⚠️ 上面这块 JSON **不是连续全文**：第 30 行的 `"license": "MIT",`、第 36 行起的 `dependencies` 与本知识点无关，为压缩篇幅未列出；花括号实际是**闭合**的（第 35 行 `}` 收 `dsh`，第 36 行起的字段属于同一个对象）。

**(3) 形态二：注册入口只认三种形状。** `vendor\cordis\src\registry.ts` 第 304–336 行

```ts
  /**
   * Start a plugin in the current context and return its fiber.
   *
   * Creates (or reuses) the plugin's runtime record, then starts a new fiber
   * under the current context. Throws if `plugin` is not a supported shape or
   * if the current fiber is already disposed.
   *
   * @param plugin — a function, class, or `{ apply }` object plugin.
   * @param config — the plugin config, validated against its `Config` schema.
   * @param getOuterStack — captures the caller stack for effect diagnostics.
   * @returns the fiber; awaiting it settles once loading finished.
   */
  plugin(plugin: Plugin, config?: any, getOuterStack = buildOuterStack()) {   // ← 函数头
    // check if it's a valid plugin
    const callback = this.resolve(plugin)
    if (!callback) throw new Error('invalid plugin, expect function or object with an "apply" method, received ' + typeof plugin)
    this.ctx.fiber.assertActive()

    let runtime = this._internal.get(callback)
    if (!runtime) {
      let name = plugin.name
      if (name === 'apply') name = undefined
      runtime = { name, callback, fibers: new DisposableList(), Config: plugin.Config }
      this._internal.set(callback, runtime)
    }

    const fiber = new Fiber(this.ctx, config, Inject.resolve(plugin.inject), runtime, getOuterStack)
    const wrapped = Object.create(fiber) as Fiber & PromiseLike<Fiber>
    wrapped.then = (onFulfilled, onRejected) => {
      return fiber.await().then(onFulfilled, onRejected)
    }
    return wrapped
  }
// （第 293–302 行的 `inject()` 简写——`return this.plugin({ inject, apply: callback, name: callback.name })`——与本块无关，见第 2 课，此处省略）
```

- **做什么**：`registry.plugin()` 是「把一个插件装上去」的唯一入口。它先把插件**规范化**成一个 `callback`（`this.resolve(plugin)`，不认识的形状在第 319 行直接抛），再为一个 callback 复用一份 `runtime` 记录（第 322–328 行），最后新建一个 `Fiber` 并返回（第 330 行）。
- **与哪个知识点相关**：`docs\cordis-primer.zh.md` 第 9 行说插件「可以是一个带有可选 `inject` 和 `apply(ctx)` 字段的函数，也可以是一个 `Service` 子类」；这段源码把这句话落成了三个入口：函数（`callback` 就是函数本身）、`{ apply }` 对象（走 `resolve`）与类（`Service` 子类，见 §3.3）。`inject` 在第 330 行由 `Inject.resolve(plugin.inject)` 解析成 fiber 的门控条件。
- **为什么这么写**：`register` 的返回值是**一个 fiber**，而且它 `then` 得动（第 331–334 行）——即「`await` 一个插件的挂载」等于「等它真正加载完」。作者在 JSDoc 里写的 *"awaiting it settles once loading finished"* 就是这句。这解释了为什么 DSH 里**不需要一份手写的启动顺序表**：顺序是「谁 await 谁的 fiber」推出来的。

### 3.2 依赖门控：服务就绪才启动

**结论**：「插件声明所需的服务后，会等待这些服务就绪才启动；加载顺序通过服务依赖表达，而非手动编排启动序列」（`docs\cordis-primer.zh.md` 第 11 行）。

`vendor\cordis\src\fiber.ts` 第 597–639 行

```ts
  _checkImpl(name: string) {                                  // ← 函数头：判「某个注入项现在有没有实现」
    const impl = this.ctx.reflect._getImpl(name, true)
    if (!impl) return delete this._store[name]
    try {
      if (impl.check && !impl.check.call(getTraceable(this.ctx, impl.value))) {
        return delete this._store[name]                        // ① 提供方自报「当前不可用」：当它不存在
      }
    } catch (error) {
      impl.fiber.ctx.logger.error(error)
      return delete this._store[name]
    }
    this._store[name] = impl
  }

  _refresh() {                                                // ← 函数头：把所有注入项合成一个"代"标识
    let epoch: string | boolean = false
    epoch = ''
    for (const name of Object.keys(this.inject)) {             // ② this.inject 来自 registry.plugin() 第 330 行的 Inject.resolve
      const impl = this._store[name]
      if (!impl) {
        epoch = INACTIVE                                      // ③ 只要缺一项：INACTIVE
        break
      }
      epoch += ':' + impl.fiber.uid                            // ④ 齐了：把每个提供方 fiber 的 uid 拼成一个字符串
    }
    this._setEpoch(epoch)
  }

  private _setEpoch(epoch: string) {                           // ← 函数头：代变了才动生命周期
    const oldEpoch = this._runner.epoch
    if (epoch === oldEpoch) return                             // ⑤ 没变就什么都不做
    this._runner.epoch = epoch
    if (this.inertia) return
    this._updateState(() => {
      if (epoch !== INACTIVE && oldEpoch === INACTIVE) {
        this.inertia = this._reload()                          // ⑥ 从"缺"变"齐"：加载
        return FiberState.LOADING
      } else {
        this.inertia = this._unload()                          // ⑦ 从"齐"变"缺"（或换了提供方）：卸载
        return FiberState.UNLOADING
      }
    })
  }
// （第 590–595 行：上一轮 _checkImpl 触发的服务变更通知循环；第 641–644 行的 `_resolveConfig` 与本块无关，此处省略）
```

- **做什么**：`_refresh()` 遍历该插件声明的每个注入项（②），把「谁在提供它」编成一个字符串 `epoch`；只要缺一项就置成 `INACTIVE`（③）并 `break`。`_setEpoch()` 只在**这个字符串变化时**才动生命周期：缺→齐就 `_reload()`（⑥），齐→缺或**换了提供方**（提供方 fiber 的 `uid` 变了，字符串就变了）就 `_unload()`（⑦）。
- **与哪个知识点相关**：`FiberState` 枚举的六个值里，`PENDING`（=0）表示「等必需服务」——见同文件第 140–154 行的枚举与它的文档注释（*"`PENDING` — waiting for required services"*）。所以「依赖没齐」不是报错，而是**一个正常状态**；第 3.8 节的实测 A 组直接看到了 `state = 0 → 2 → 0` 的往返。
- **为什么这么写**：`epoch` 用「全部注入项的提供方身份」而不是「一个布尔量」来编码，带来两个后果（标注为推断：由上面 ⑥⑦ 两个分支直接推得，作者注释未展开）：一是**提供方被换掉**（同名服务换了 fiber）也会触发一次卸载再加载，二是提供方只是「暂时不可用」（`_checkImpl` ① 的 `impl.check` 返回假）时，消费者会**退回 PENDING 而不是带着空引用继续跑**。这就是 §3.8 实测 A 里「把提供方 dispose 掉之后消费者回到 `PENDING`」的机制来源。

### 3.3 可逆注册（一）：注册方必须交出 disposer

**结论**：「提示词片段、工具 schema、适配器、提供方和监听器通过 `ctx.effect()` 或 `ctx.on()` 安装，reload 和 teardown 时会按预期撤销」（`docs\cordis-primer.zh.md` 第 13 行）；「每个注册都应有对应的 disposer」（同文件第 51 行）。

**服务自己的登记也是可逆的。** `vendor\cordis\src\service.ts` 第 42–59 行

```ts
  constructor(protected ctx: Context, name: string) {         // ← 函数头：Service 子类的构造函数
    name ??= this.constructor['provide'] as string

    let self = this
    const tracker: Tracker = {
      associate: name,
      property: 'ctx',
    }
    if (self[symbols.invoke]) {
```

### 3.4 可逆注册（二）：作用域与撤销是同一个事实

**结论**：`agent.ctx` 上的注册「既具有 scope 可见性，其生命周期也绑定到该 scope（**同一事实决定两者**）」（`docs\glossary.zh.md` 第 15 行）。

`packages\core\scope\src\store.ts` 第 219–266 行

```ts
  /**
   * Attach one synchronous layer mutation to its registration context.
   * @param ctx - context that determines both scope visibility and effect ownership.
   * @param action - atomic mutation returning its synchronous undo.
   * @param options - Cordis effect label and optional change notification.
   * @returns the exact disposer returned by `ctx.effect()`.
   */
  effect(                                                     // ← 函数头
    ctx: Context,
    action: (layer: L) => () => void,
    options: { label: string; notify?: boolean },
  ): () => void {
    const scope = scopeOf(ctx)                                // ① 从上下文推 scope：可见性由它决定
    const notify = options.notify ?? true
    const dispose = ctx.effect(function* (this: ScopedLayers<L>) {   // ② 生命周期交给 Cordis effect
      let layer: L
      let created = false
      if (scope === undefined) {
        layer = this.global                                  // ③ 没有 scope → 全局层
      } else {
        const existing = this.scoped.get(scope)
        if (existing === undefined) {
          layer = this.createLayer(scope)                    // ④ 这个 scope 还没有层：建一个
          this.scoped.set(scope, layer)
          created = true
        } else {
          layer = existing
        }
      }

      let undo: () => void
      try {
        undo = action(layer)                                 // ⑤ 执行调用方的原子改动，拿回它的同步 undo
      } catch (error) {
        if (scope !== undefined && created && layer.isEmpty()) this.scoped.delete(scope)   // ⑥ 改动失败：回收刚建的层
        throw error
      }

      yield () => {                                          // ⑦ 交出的 disposer：先 undo，再回收空层
        undo()
        if (scope !== undefined && layer.isEmpty()) this.scoped.delete(scope)
        if (notify) this.onChange()
      }
      if (notify) this.onChange()
    }.bind(this), options.label)
    // （第 264 行：一行 oxlint 禁用注释，说明"必须返回精确的同步 disposer 以保持 Cordis effect 身份"，此处省略）
    return dispose
  }
// （第 219–266 行是完整未删节的这个函数；本块没有省略任何函数体行）
```

- **做什么**：调用方（如 §3.3 的 `tools.register()`）只交出「往层里插一条」这个**原子改动**（`action`）；`effect()` 负责三件事：按上下文算出该进哪一层（①②③④）、执行改动并接住它的 undo（⑤⑥）、以及把「撤销 + 层变空就删层」包装成 disposer 交出去（⑦）。
- **与哪个知识点相关**：`docs\glossary.zh.md` 第 15 行的「同一事实决定两者」就在 ① 与 ② 两行上：**`scope` 和 `ctx.effect` 用的是同一个 `ctx`**。所以不存在「这个注册全局可见但生命周期属于某个 agent」这种状态——可见性与所有者不可能对不上。
- **为什么这么写**：⑦ 里那句 `if (scope !== undefined && layer.isEmpty()) this.scoped.delete(scope)` 是这段的关键：**层不是永久容器，它随最后一个贡献者离开而消失**。作者在 JSDoc 里把这一点写成 *"@param ctx - context that determines both scope visibility and effect ownership"* —— 一个参数同时承担两个语义，是刻意为之，不是省事。

`vendor\cordis\src\events.ts` 第 224–243 行（`waterfall` 的实现）

```ts
  /**
   * Compose listeners around the final `next` callback.
   *
   * The last dispatch argument is treated as the innermost `next`. Listeners
   * run outermost-first; a listener that does not call `next()` vetoes the
   * rest of the chain, including the built-in behavior.
   *
   * @param args — optional `this`, the event name, listener arguments, then `next`.
   * @returns the outermost listener's return value.
   */
  waterfall(...args: any[]) {                                 // ← 函数头
    const cbs = this.dispatch('waterfall', args)              // ① 取出本事件的监听器队列（注册顺序）
    const inner = args.pop()                                  // ② 最后一个参数就是最内层 next
    const next = () => {
      const cb = cbs.shift() ?? inner                         // ③ 从队首取一个；取空了就落到最内层
      return cb(...args)
    }
    args.push(next)                                           // ④ 把 next 作为新的最后一个参数
    return next()                                             // ⑤ 从最外层开始跑
  }
// （第 189–196 行的 `emit(...) { this.dispatch('emit', args).map(cb => cb(...args)) }` 与
//   第 204–209 行的 `serial` 是本块的同类方法，已在同文件第 12 行的文档里一句话概括，此处省略）
```

- **做什么**：`waterfall` 把「监听器队列 + 最内层实现」拼成一条链：每次 `next()` 从队首取一个监听器（③），队列空了就落到 `inner`（②）。因为 `next()` 是从最外层第一个监听器开始调用的（⑤），所以执行顺序是**最外层优先**；一个监听器**不调用 `next()` 就返回**，等于把剩下的链（包括 `inner` 的内建行为）整个否决——JSDoc 原文 *"a listener that does not call `next()` vetoes the rest of the chain, including the built-in behavior."*
- **与哪个知识点相关**：`docs\cordis-primer.zh.md` 第 35 行的「环绕中间件、短路」与第 39 行的「策略监听器在拥有决策权时可以不调用 `next()` 直接返回」。第 3.8 节实测 C1/C2 分别验证了「逐层回传」与「短路」。
- **为什么这么写**：`dispatch('waterfall', args)` 返回的队列是**当场取的**（①），后面 `shift()` 会把它消费掉；`inner` 用 `args.pop()` 拿到（②），随后又被 `args.push(next)` 放回去（④）——这样监听器收到的参数形状永远是 `(...原参数, next)`，**不需要额外约定**。⚠️ 注意 ② 是在 ① 之后：`args` 此时仍含最内层回调，所以「最后一个参数」这个约定对分发方和监听方是同一个。

```ts
 * is never mutated: patching shared entry objects would bake earlier patch

 * could never revert a removed or changed patch. Inserted entries are indexed
 * as they are added, so a later patch in the same list can target a row an
 * earlier patch inserted. A patch that matches nothing warns and is skipped.
 * @param data - the parsed entry list (JSON-safe plain data).
 * @param patches - the patch list to apply, in order.
 * @param warn - sink for skipped-patch diagnostics (printf-style, `%C` = code).
 * @returns a detached entry list with every applicable patch applied.
 */
export function applyEntryPatches(                            // ← 函数头
  data: EntryOptions[],
  patches: PatchOptions[] | undefined,
```

按块讲解（两块合讲）：

- **⑧⑬⑫ 三种形态，没有第四种**：`insert` 不带 `id` → 顶层追加（组合包就是靠它把自己那一堆条目推进**空根**）；`insert` 带 `id` → 目标必须**存在且是 group**，推进它的 `config`；非 `insert` → 必须带 `id` 的**原地覆盖**。
- **③④ 索引的覆盖范围**：`entryMap` 登记**所有带 `id` 的条目**，并且遇到 `entry.group` 且 `config` 是数组时递归下沉——所以 patch 既能定位顶层条目，也能定位 group 的子条目。
- **⑭ 一个安全设计**：插入后**立即**补登记。作者原文（第 95–99 行注释）*"a layer must be able to configure or disable a row an earlier layer inserted; without this, inserted rows were silently unpatchable"* —— 即「后一层必须能改到前一层刚插入的行」。
- **⑰ 另一个安全设计**：普通覆盖允许带 `name` 做身份校验，不一致就**警告并跳过整条 patch**（防止 `id` 被复用后打到错误的条目上）。
- **⑱ 覆盖是浅赋值**：`target[key] = value` 逐个键做——`config` 作为**一个整体**被替换，**没有深合并**。`packages\bundle\web-app\cordis.patch.yml` 第 5–6 行的作者注释原文是同一条纪律：*"A patch replaces the targeted row's whole `config`, so each row below restates every key it owns."*

```ts
  /** Merge new options, restart as needed, and persist through the parent tree. */
  async update(options: Partial<EntryOptions>, create = false, force = false) {   // ← 函数头
    const legacy = { ...this.options }

    // step 1: update options
    if (create) {
      this.options = options as EntryOptions
    } else {
      for (const [key, value] of Object.entries(options)) {
        if (isNullable(value)) {
          delete this.options[key]
        } else {
          this.options[key] = value
        }
      }
    }
    sortKeys(this.options)

    // step 2: execute
    if (this.disabled) {
      this.fiber?.dispose()                                    // ① 被禁用 → 直接卸载
      return
    }

    // step 3: check if options are changed
    if (this.fiber?.uid) {
      const changes = Object.keys({ ...this.options, ...legacy })
        .filter(key => !deepEqual(this.options[key], legacy[key], key === 'config'))
      // Only an active fiber in an unchanged context takes volatile-only config changes without a remount.
      const volatileOnly = changes.length === 1 && changes[0] === 'config'
        && this.fiber.state === FiberState.ACTIVE && Object.getPrototypeOf(this.ctx) === this.parent.ctx
        && equalExceptVolatile(legacy.config, this.options.config, this.fiber.runtime?.Config)
      if (volatileOnly) this.fiber._config = this.options.config   // ② 只有 volatile 字段变了：原地改配置，不重挂
      const pending = volatileOnly && this._commitVolatile() ? [] : changes
      if (!pending.length && !force) return
      this.context.emit('loader/partial-dispose', this, legacy, true)   // ③ 通知：这一条要局部拆掉
      this._patchContext(pending)
    } else {
      await this.init()
    }
  }
// （第 159 行起是下一个方法；第 100–116 行的 _patchContext 与 refresh 已在 §4.3 正文里引用，此处省略）
```

- **做什么**：条目更新分三步——合并新选项（`step 1`）、被禁用就 `dispose()`（①）、比对变化决定怎么重启（`step 3`）。中间那条 `volatileOnly` 快路径（②）只在「变化恰好只有 `config`、fiber 是 ACTIVE、上下文原型没变、且差异只涉及 volatile 字段」时命中，此时**不重挂**，只替换 fiber 的配置。否则发 `loader/partial-dispose`（③）再走重启。
- **与哪个知识点相关**：`EntryOptions.id` 是「条目身份」（同文件第 10–14 行：`id` 的注释原文 *"Stable id inside the containing entry tree."*）——这正是 §3.7 上一块里 `entryMap` 的键。`loader/partial-dispose` 与 fiber 的 `update()`（`vendor\cordis\src\fiber.ts` 第 736–753 行：先跑 `internal/update` waterfall，回调里再 `restart()`）共同构成**局部热重载**，也是附录 A Q6 第 8 条的证据。
- **为什么这么写**：`volatileOnly` 那四行连乘是一个**非常窄**的条件，作者还专门写了注释 *"Only an active fiber in an unchanged context takes volatile-only config changes without a remount."* ——意思是：**能省一次重挂的前提必须逐条列出来**，而不是「配置变了就尽量别重启」。这跟 §3.6「宁可炸也不猜」是同一种取向：模糊地带一律走安全路径（重挂）。

#### 3.8.2 命令 2：跑 Cordis 运行时的可逆性与 waterfall

同一个 `node --input-type=module -`，导入 `./vendor/cordis/lib/index.js`（编译产物），实测依赖门控、卸载撤销与 waterfall 语义：

```text
A1 consumer.state = 0 | applied = 0
A2 consumer.state = 2 | applied = 1
A3 after provider dispose -> consumer.state = 0 | applied = 1 | log = ["consumer.apply"]
B events = ["setup","before","teardown"]

```

- **A**：一个 `inject: ['svc']` 的消费者插件在服务缺席时 `state = 0`（`PENDING`，枚举见 `vendor\cordis\src\fiber.ts` 第 147–154 行）且 `apply` 未运行；提供 `svc` 后 `state = 2`（`ACTIVE`）且 `apply` 运行一次；**把提供方 fiber dispose 掉之后，消费者回到 `PENDING`**。这正面验证了「等依赖就绪才启动」与「服务随宿主 fiber 撤销」（`docs\cordis-primer.zh.md` 第 11 行；`vendor\cordis\src\service.ts` 第 32–59 行）。

- **C1**：两个监听器 `next()+1`、`next()*10` 叠加在一个返回 `1` 的内层上，得到 `11`，即最外层优先、下游返回值逐层回传（`docs\cordis-primer.zh.md` 第 35 行）。
- **C2**：第一个监听器不调用 `next()` 直接返回 `{kind:'reject'}`，内层 `{kind:'enter'}` 不再执行——与 `agent/pre-step` 的拒绝语义同形（`packages\core\agent-loop\src\agent.ts` 第 276–285 行）。

### 4.2 DSH 最与众不同的三点

展开见 4.3、4.4 与附录 A Q5/Q6。三条都在 4.1 表里有对应行。

1. **替换的单位是「一整行配置」，不是「一个 bean」也不是「一次 API 调用」**——`--dump-config` 输出里出现的任何条目都能由用户自己的 patch 替换（`docs\architecture.zh.md` 第 39 行；数量上无缺口见实测 3.8.1 结论 1）。
2. **卸载是内建语义而非约定**——监听器与 effect 由宿主 fiber 拥有，卸载即撤销（源码 §3.3、§3.4）；Spring 的销毁是容器级统一动作，VS Code 要手写 `subscriptions`，LangChain 没有卸载协议。
3. **「唯一的具体实现」与「特权」被拆开**——agent loop 是「唯一的具体循环插件」，但它仍然只是一行可替换的配置（`docs\capability-seams.zh.md` 第 637 行原文：*"唯一的具体循环插件；扩展包依赖 dsh-agent 的事件和服务，而不依赖此包。"*）。

### 4.3 seam 三角色与作用域（DSH 侧的两个补充结论）

- **seam 三角色**：一项可替换能力 = Service Definition + Service Provider + Consumer；「seam 正是替换一个提供方就能改变整个产品的原因」（`docs\architecture.zh.md` 第 137、139 行）。规范定义补充了一条硬约束：Service Definition「绝不是 TypeScript `interface`」，而是拥有自身 `ctx.<key>` 的 Cordis `Service`（`docs\glossary.zh.md` 第 9 行）——这条约束与 §3.3 的源码呼应：**只有「有构造函数的类」才能在构造期登记，`interface` 做不到**。
- **作用域只有两层**：「一项贡献要么是全局的，要么是带作用域的……只有两层，采用扁平结构：带作用域的注册不会向下继承给 subagent；子树行为通过 lineage 数据表达，从不通过 scope 结构」（`docs\glossary.zh.md` 第 13 行）。配套三条：scope key 按对象同一性比较、活跃 agent 就是自身 scope 的 key（同文件第 14 行）；`agent.ctx` 上的注册「既具有 scope 可见性，其生命周期也绑定到该 scope（同一事实决定两者）」（同文件第 15 行）；shadowing 是「最具体者胜出」（同文件第 18 行），restriction 在过滤之后合并 scope-local 注册（同文件第 19 行）。注册表**主体**事件则有意保持不过滤（`packages\core\tools\src\index.ts` 第 199–207 行的 `tools/change` 文档注释原文：*"An UNFILTERED registry-subject notification, deliberately not scope-filtered dispatch"*）。
- **热重载是常规能力**：base 启用仅监视配置的 `dsh-hmr`，Headless／SDK／ACP 禁用它，`sdk-minimal` 不包含它（`docs\architecture.zh.md` 第 29 行）；条目更新时会先发 `loader/partial-dispose`（`vendor\loader\src\config\entry.ts` 第 152 行），fiber 的 `update()` 会先跑 `internal/update` waterfall，再 `restart()`（`vendor\cordis\src\fiber.ts` 第 736–753 行）。
- **随附 profile 模板共 5 个**：`acp`／`web`／`headless`／`sdk` 都含 `@deepseek-ai/dsh-base`，`sdk-minimal` 不含（`packages\boot\app-boot\src\profile.ts` 第 179–195 行的 `PROFILE_TEMPLATES`；`docs\architecture.zh.md` 第 25 行）。组合包身份由包自己的 `package.json` 声明（`dsh.bundle.patch`，`docs\architecture.zh.md` 第 23 行；实例见 `packages\bundle\base\package.json` 第 31–35 行）。

### 4.4 外部对照体系（**外部知识**，非仓库事实）

以下是本笔记剩余部分所依赖的外部知识，逐条列明以便审计；**版本差异可能使细节漂移，且本笔记未在本机验证其中任何一条**。

- **Spring（Framework / Boot）**：IoC 容器（`ApplicationContext`）负责实例化、装配与生命周期；扩展面是注解与接口——`@Component`／`@Bean`／`@Configuration`、`BeanPostProcessor`／`BeanFactoryPostProcessor`、`ApplicationListener` 与 `@EventListener`、`@Conditional` 系列（Boot 自动配置用 `@ConditionalOnMissingBean` 主动退让）、`ImportSelector`／`AutoConfiguration.imports`、AOP 代理、`@Order`／`Ordered` 排序；bean 作用域为 singleton／prototype／request／session；销毁由容器统一驱动（`@PreDestroy`／`DisposableBean`／`SmartLifecycle`）；同名 bean 定义覆盖自 Boot 2.1 起默认被禁（需 `spring.main.allow-bean-definition-overriding=true`）；运行期增删 bean 定义需要直接操作 `BeanFactory`，**不是一等公民**。
- **VS Code 扩展**：明确二分为**声明式**（`package.json` 的 `contributes`：commands／menus／keybindings／configuration／views／languages／themes 等，宿主静态读取，无需扩展运行）与**命令式**（`activate(context)` 里调用 `vscode.*` API）；资源释放靠每个注册返回的 `Disposable` 手工 `context.subscriptions.push(...)`；激活时机由 `activationEvents` 决定（自 1.74 起未声明时可由贡献点自动推导）；扩展运行在独立的 **Extension Host 进程**里，与 UI 进程隔离；兼容性由 `engines.vscode` 与 API 的 `@since`／弃用机制管理；**没有依赖注入容器**，扩展之间不声明依赖，也没有卸载协议（卸载/更新扩展要重启扩展宿主或重载窗口）；扩展宿主是所有扩展共用的一个进程。
- **LangChain**：没有容器、注册表或生命周期，组合靠协议——`Runnable` 的 `invoke`／`batch`／`stream` 与 LCEL 的 `|`（`RunnableSequence`／`RunnableParallel`／`RunnableLambda`／`RunnableBinding`）；配置沿 `RunnableConfig` 传递（`callbacks`／`tags`／`metadata`／`configurable_fields`）；最接近「事件」的是 `BaseCallbackHandler`，它沿**调用树**（run tree）传播而非全局类型化事件总线；工具用 `@tool` 装饰器或 `StructuredTool` 声明 schema；替换组件＝构造另一条链，回收靠 GC，没有 dispose 语义；LangGraph 另行引入状态图与 checkpointer，但仍无 DI 与可逆注册。

### 4.5 哪些对比是外部知识（需明确标注，不可伪装成仓库事实）

**答**：分三类，边界如下。

- **纯外部知识（Spring／LangChain 在仓库内零命中，VS Code 的命中均非机制级，全部经 3.9 检索确认）**：第 4.4 节的全部内容，以及 4.1 表中 **Spring、VS Code、LangChain 三列的全部单元格**——包括 Spring 的容器／注解／条件装配／`@ConditionalOnMissingBean`／bean 覆盖默认值／bean 作用域／`ApplicationEvent`／AOP／销毁回调；VS Code 的 `contributes` 与 `activate` 二分／`activationEvents`（1.74 起可自动推导）／Extension Host 进程隔离／`Disposable` 与 `context.subscriptions`／`engines.vscode`／无 DI 与无卸载协议；LangChain 的 `Runnable` 与 LCEL／`RunnableConfig`／callback 沿 run tree 传播／`@tool`／无生命周期／LangGraph。这些**不是本仓库的事实**，也没有在本机运行验证。
- **仓库事实但描述的是外部体系（二手证据）**：`docs\subsystems\claude-code-mods.zh.md` 与 `docs\config-catalog.zh.md` 第 956–962 行中关于 Claude Code 行为的描述，是**桥接文档对上游行为的记录**；在 3.8.3 与 4.1 的补充表中引用时一律标注为「桥接文档所述」，不作为一手事实使用。

### Q1 一张表对比「插件/扩展机制」在 DSH、Spring、VS Code、LangChain 里的解法差异（第一次读请跳过细节，先看正文 4.1）

### Q2 DSH 的选择在哪些点上有别于它们？为什么？（第一次读请跳过）

**答**：八条差异，每条给出 DSH 侧出处与文档给出的理由。

1. **没有「必须先存在的内核」。** Spring 的一切扩展都以容器先存在为前提，VS Code 的一切扩展都以 workbench 与其 API 先存在为前提，LangChain 的扩展以 `Runnable` 协议先存在为前提；DSH 的不一样之处是「不存在需要打补丁的特权内核」，连 agent loop 本身都是插件（`docs\architecture.zh.md` 第 11、13 行；源码形态见 §3.1）。**为什么**：文档把「新行为」全部指向注册服务或监听事件——20 类落点无一指向改内核（同文件第 147-168 行），所以可扩展性不依赖内核的特许。
2. **替换单位是一整行配置，而不是一个 bean 或一次 API 调用。** patch 定位与整块替换的语义由 `applyEntryPatches` 实现并同时服务启动与 dump（`vendor\include\src\index.ts` 第 43-56 行；源码见 §3.7）。**为什么**：配置层叠加让「产品形态」成为可复现的清单，而不是散落在代码里的条件分支。
3. **卸载是内建语义，而注册方必须交出 disposer。** 「每个注册都应有对应的 disposer」（`docs\cordis-primer.zh.md` 第 51 行）；运行时由 `fiber.effect()` 统一收集、逆序执行（`vendor\cordis\src\fiber.ts` 第 402-442 行）。**对比**：Spring 的销毁是容器级统一动作、VS Code 靠手工 `subscriptions`、LangChain 没有卸载协议——三者都无法表达「只撤销这一个插件的贡献」。
4. **依赖是「就绪门控」而不是「构造顺序」。** 依赖不满足时插件停在 `PENDING`，满足才启动（实测 3.8.2-A；源码 §3.2）。**为什么**：这样加载顺序是由服务依赖**推导**出来的，而不是由人排的启动序列，避免了「把插件挂到其他插件旁边」之后还要维护一份全局顺序表。
5. **作用域故意只有两层且不继承。** 「带作用域的注册不会向下继承给 subagent；子树行为通过 lineage 数据表达」（`docs\glossary.zh.md` 第 13 行）。**对比**：Spring 有四种 bean 作用域与 profile，VS Code 只有全局命名空间，LangChain 用配置对象传递——DSH 的选择是「按 agent 切一刀，且只切一刀」，把父子关系留作数据（同文件第 21 行）。
6. **事件的分发模式是公开契约的一部分。** 「新的 harness 事件通过 `@mode` 标签记录模式，以便生成的目录可以将声明与分发调用点做交叉校验」（`docs\cordis-primer.zh.md` 第 29 行）。**对比**：Spring 的 `ApplicationEvent` 与 LangChain 的 callback 都没有「这次分发是否 await、是否有返回值」的类型级约定，监听器能做什么取决于读源码。
7. **缺席即显式失败。** host 读取方要么在激活时要求该服务，要么在注册表或必需 key 缺席时明确失败；贡献方不许静默兜底（`docs\architecture.zh.md` 第 133 行；源码见 §3.6）。**对比**：VS Code 的贡献点缺失是静默无功能；Spring 的条件不满足是正常路径。DSH 选择让漏配在装配期就暴露。
8. **局部热重载是常规能力。** HMR 的启停由 YAML 控制（`docs\architecture.zh.md` 第 29 行），条目更新走 `loader/partial-dispose` 与 `internal/update` waterfall 后再 `restart()`（`vendor\loader\src\config\entry.ts` 第 152 行；`vendor\cordis\src\fiber.ts` 第 736-753 行；源码见 §3.7）。**对比**：VS Code 无法单独卸载一个扩展（要重启扩展宿主），Spring 运行期重建上下文是重活，LangChain 没有这个概念。

### Q3 「无特权内核 + 可逆注册」在对比中体现出什么独特价值？（第一次读请跳过）

**答**：四层价值，每层都有可检验证据。

1. **「改一行配置」与「换一个实现」被合并成同一个动作。** 因为没有特权内核，唯一的具体实现也不特殊：agent loop 是「唯一的具体循环插件」，其角色仍只是配置层里的一行（`docs\capability-seams.zh.md` 第 637 行）；替换一个 provider 就能改变整个产品（`docs\architecture.zh.md` 第 139 行）。对照之下，VS Code 的 workbench 能力不可替换、Spring 的容器自身不可替换、LangChain 的 `Runnable` 协议不可替换——它们能替换的只是协议内部的组件。
2. **可逆注册让「撤销」成为可组合的原语，而不是全局重启。** 实测 3.8.2-A 展示了级联：提供方 fiber 卸载后，依赖它的消费者自动回到 `PENDING`；实测 3.8.2-B 展示了局部性：一次 `dispose()` 撤销了监听器与 effect，且只影响该 fiber 的贡献。Spring 的 bean 销毁在容器级、VS Code 的扩展卸载在宿主级、LangChain 无对应机制——因此只有 DSH 能把「按 agent 临时装配一套能力」变成安全的常规操作（同一事实决定可见性与生命周期，`docs\glossary.zh.md` 第 15 行；源码 §3.4）。
3. **「可见即可撤销」使热重载与诊断一致。** 同一条 effect 机制既支撑 teardown，也支撑 HMR 的局部重载（`vendor\cordis\src\fiber.ts` 第 675-696、736-753 行；`docs\architecture.zh.md` 第 29 行）；并且没有第三套「卸载脚本」需要与注册代码保持一致——注册的返回值就是撤销手段（`vendor\cordis\src\fiber.ts` 第 404-442 行；`packages\core\tools\src\index.ts` 第 1057-1088 行）。
4. **代价同样独特，且是这套设计的判据。** 必须逐条交出 disposer（`docs\cordis-primer.zh.md` 第 51 行）；teardown 顺序有要求时要把相关工作放进同一个 effect（同文件第 51 行）；缺席时必须显式失败而不能兜底（`docs\architecture.zh.md` 第 133 行）；配置层叠加把装配成本推给部署侧——实测 base 为 94 行（3.8.1），而另一极的 `sdk-minimal` 只有 27 行（该数字来自 `notes\4-思想与前沿\4.1-无特权内核.md` 的实测记录，**本笔记未复测**；两者的定位差异见 `docs\architecture.zh.md` 第 25 行）。**换句话说：如果某个体系不能对「撤销一个第三方贡献」给出局部答案，它就必然要把这件事升级成一次重启。**

**答**：见 **第 4.5 节**——三类边界（纯外部知识／仓库事实但描述外部体系／纯仓库事实）与判定方法都在那里。一句总括：**Spring 与 LangChain 在仓库内零命中，VS Code 的命中没有一处是机制级对照，Claude Code 只有一份二手兼容性文档**（检索明细见 3.9）。

### Q5 完全撤掉一个插件，宿主到底做了什么？（第一次读请跳过）

**答**：`ctx.effect()` 契约（`vendor\cordis\src\fiber.ts` 第 402-442 行，作者 JSDoc 原文）：

> `execute` runs immediately; the disposers it produces are collected and run (**in reverse order**) either when the returned disposer is called or when the fiber unloads, whichever comes first. Calling the disposer twice is a no-op. Throws `CordisError('INACTIVE_EFFECT')` if the fiber is already disposed.

三件事因此成立：①**注册与撤销是同一段代码的两半**（effect 体里 `return` 的那个函数就是撤销手段）；②**逆序**执行，符合「后建的先拆」；③**幂等**，重复调用是 no-op，所以「谁先撤销」不会变成竞态。fiber 卸载时 `_unload()` 清空全部 disposables（同文件第 675-696 行），并且每个 disposer 抛错只记日志、不中断其它 disposer（第 683-685 行）。**边界**：`ctx.effect()` 在已 disposed 的 fiber 上会抛 `INACTIVE_EFFECT`（第 419-422 行），所以「往一个正在卸载的插件里注册东西」不是被忽略，而是**当场失败**。

### Q6 局部热重载凭什么能只重挂一个条目？（第一次读请跳过）

**答**：三条机制叠加。①**条目有稳定身份**：`EntryOptions.id`（`vendor\loader\src\config\entry.ts` 第 10-14 行），所以「哪一个条目变了」是可判定的。②**变化检测 + 窄快路径**：`update()` 比对合并前后的键，只有当「唯一变化是 `config`、fiber 是 ACTIVE、上下文原型未变、且差异只涉及 volatile 字段」时才原地改配置、不重挂（同文件第 142-151 行）——其余情况一律走重挂。③**局部拆除通知**：需要重挂时先 `emit('loader/partial-dispose', this, legacy, true)`（第 152 行），再由 fiber 的 `update()` 跑 `internal/update` waterfall、成功后 `restart()`（`vendor\cordis\src\fiber.ts` 第 736-753 行）。**对照**：VS Code 做不到（无「只卸载一个扩展」的协议），Spring 的运行期重建是重活，LangChain 没有这个概念。

### Q7 patch 是替换整个 `config` 还是深合并？（第一次读请跳过）

**答**：**浅赋值覆盖**（`target[key] = value`，§3.7 第二块的 ⑱）。`config` 作为整体被替换，**没有深合并**；只加一个字段也要重述完整 `config`。作者在 `packages\bundle\web-app\cordis.patch.yml` 第 5-6 行把这条纪律写给每个写 patch 的人：*"A patch replaces the targeted row's whole `config`, so each row below restates every key it owns."* 实测 3.8.1 结论 2 直接看到了嵌套字段一并消失。

### Q8 在一个已经被卸载的插件上注册监听器会怎样？（第一次读请跳过）

**答**：**当场抛错**，不是被静默忽略。`ctx.on()` 在动手之前先调 `this.ctx.fiber.assertActive()`（`vendor\cordis\src\events.ts` 第 294 行），它的文档注释写明：*"Throws `CordisError('INACTIVE_EFFECT')` if the fiber is already disposed."*（同文件第 280-281 行）；对应的错误码在 `vendor\cordis\src\fiber.ts` 第 172 行登记为 `'cannot create effect on inactive context'`。这一条与 §3.6「缺席即显式失败」是同一条纪律的两个面：**要么注册成功，要么明确失败，不存在「注册了但不会生效」**。

### Q9 仓库里到底有没有「机制级对照材料」？（第一次读请跳过：这是证据审计）

**答**：**没有**，但「没有」的分界线必须先说清检索范围（明细见 3.9）。结论三条：① **Spring 与 LangChain 在仓库内两轮检索全部零命中**；② **VS Code 有若干命中，但性质都不是机制级对照**（依赖包名 `@vscode/ripgrep`、应用唤起、VS Code 集成终端的 `$TMUX_PANE` 行为、glob 规则类比、`engines.vscode` 字段摆放的一句式决策记录、`area/vscode` 标签）；③ **Claude Code 有仓库内的兼容性文档**，但它是「桥接对上游行为的描述」，属二手证据。

→ 因此本笔记所有关于 Spring／VS Code／LangChain 机制的断言**只能是外部知识**，并已在 4.4 与 4.5 逐条标注。**这同时也是对旧稿的一处更正**：旧稿写「仓库里出现的 `VS Code` 只指 `@vscode/ripgrep` 二进制与 Open In 应用白名单」，范围过窄，正确的表述见 3.9 的更正段。
