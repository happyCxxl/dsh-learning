## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：两套"作用域"各自的机制——**cordis 的 ctx 作用域**（`extend` / `isolate` / `intercept`）与 **DSH 的 `dsh-scope`**（`createScope` 等）。目标是"知道一个带作用域的注册是怎么被隔离或被看见的，以及去哪个文件查"。
**不是**：`inject` 的完整语义（`2.2`）、`effect` / disposer 的逆序规则（`2.3`）、事件五种分发模式的差别（`2.4`）。本课只在"这些机制被作用域借用了一下"的地方点到它们。

### 0.2 现在只要记住这 3 件事

1. **这一节里有"两套完全不同的作用域"**：cordis 那套改的是**服务查找**（`ctx.xxx` 读到哪个实现）；DSH 自建的 `dsh-scope` 改的是**注册表可见性**与**事件放行**，**完全不动服务查找**。
2. **cordis 的三个方法都只做一件事：造一个子 `ctx`，父 `ctx` 永不被修改**。区别只在往子 `ctx` 的自有属性里放了什么：`extend` 放元数据、`isolate` 放一张服务标签表、`intercept` 放一张服务配置表。
3. **"近者优先 / 遮蔽"在四处各有一份实现**，方向还不同：注册/查找是**向下继承**（子看得见祖先，近者赢），事件放行是**向上扩展**（祖先的监听器收得到后代的事件，反之不行）。

### 0.3 明确授权：下面这些现在**不用管**

- `symbols.shadow`（可追踪服务调用链的复套逻辑）——**第一次读不必弄懂**：它是给"服务方法里看到的 `ctx` 仍指向原始调用点"用的追踪机制，**与本节三个方法不是同一机制**。源码与逐块讲解在 §3.1（`extend` 的最后三行），回查时再看。
- `Service[Symbol.hasInstance]`、`createCallable`、`Service[symbols.extend]` 这些 `Service` 基类的其它成员——属于 `2.1` 的遗留细节；
- `restriction`（`tools.restrict`）、preset / realm / setup window——属于第三编；本课只在附录 A 的 Q3 提一句。
- `ScopeParentBinding.rebind`（重新绑父的句柄）——本课只在 §4.2 说清"为什么存在"，它的消费者属第三编。

### 0.4 判断标准只有一条

看到任何一个新词（`isolate` / `intercept` / `label` / `carrier` / `chainLayers`…），只要能回答**"它属于 §1 表里哪一行、改的是服务查找还是注册表可见性"**，就够了。附录 B 的术语索引标了每个词在第几课展开。

### 0.5 如果你是第一次读，跳过附录 A 的 Q5

附录 A 的 Q5 讲的是 `intercept` 的"**表在哪个上下文上**"这一层细节（正文 §3.3 的结尾也提到），第一次读**可以先不看**；Q1–Q4、Q6 是第一次读就该能答的。

## 1. 最小词汇表（本课新增的 7 个词）

前四个词属于 **cordis 的 ctx 作用域**体系；后三个属于 **DSH 自建的 `dsh-scope`** 体系。**两套体系不要混着用**——这正是本课开头那张对照表要防的事。

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **子上下文（child ctx）** | 从某个 `ctx` "生"出来的另一个 `ctx`。它照常能读到父的一切，但**它自己身上多放了几样东西** | `Object.create(父)` 得到的对象；三个方法都返回它 |
| **isolate 隔离** | 把**某一个服务**的查找域"切一刀"：在子 `ctx` 之下，这个服务解析到**另一条标签**上，于是可以放一个不同实现而不影响父 | `ctx.isolate(name, label?)`；表在 `ctx[symbols.isolate]`（`符号.isolate`） |
| **label 标签 / 作用域标签** | 上面那条"切一刀"的**身份**。两条 `isolate` 传**同一个 label** 就是"合流"（共用同一条服务记录） | 一个 `symbol`；默认 `Symbol(name)` |
| **intercept 拦截配置** | 给**某一个服务**挂一份"配置补丁"，供该服务自己按"祖先在前"的次序合并。**只对在此上下文之下启动的插件生效** | `ctx.intercept(name, config)`；表在 `ctx[symbols.intercept]` |
| **scope 作用域（DSH）** | 一个 `ctx` 上贴的**不透明身份标签**。注册表按它归档贡献，事件按它筛监听器 | `dsh-scope` 的 `ScopeKey`（对象，按同一性比较）+ `createScope()` |
| **carrier 载体** | 事件分发时当 `thisArg` 传的那个**只有路由作用、不暴露主体属性**的对象 | `scopeTarget(base, key)` 的返回值；类型 `Scoped<T>` |
| **shadowing 遮蔽** | 链上解析同一个名字时，**离查询点最近的那一层胜出**；远处条目不会消失，只是被盖住（撤掉近处又可见） | 四处实现：`extend` 自有属性、`isolate` 子表、`intercept` 合并顺序、`ScopedLayers.merge` |

> ⚠️ 本课**只**用上表这些词解释机制。`preset` / `realm` / `lineage` / `restriction` 属第三编，正文不出现（只在附录 A 的一处答案里作为"展开于何处"被点到）。

## 2. 先建立画面

### 2.1 静态结构：两套作用域各自挂在哪（谁是谁的一部分）

```
cordis 侧：ctx 是一棵"原型链树"，每个 ctx 就是一条链上的一个对象

   root ctx（构造函数里建的两张根表）
     ├─ root[symbols.isolate]    = Object.create(null)   ← 根标签表：空
     └─ root[symbols.intercept]  = Object.create(null)   ← 根拦截表：空
        │
        │  ctx.extend(meta) / ctx.isolate(name) / ctx.intercept(name, cfg)
        │  三者都只是 Object.create(父) + 往子身上 defineProperty
        ▼
   child ctx ← 自有键（meta / isolate 表 / intercept 表 / kScope 标签）
        │        其余属性沿原型链回落到父
        ▼
   同名键"近者赢"：子身上的自有键盖住父的

DSH 侧：dsh-scope 不另起一棵树，而是**寄生在 cordis 的 ctx 上**

   createScope(ctx, key)  ──►  ctx.plugin(空插件)   ← 造一个"承重 fiber"
                             └─ fiber.ctx.extend({ [kScope]: key })   ← 复用 cordis 的 extend
                                     │
                                     ├─ 注册表读 scopeOf(ctx) → key      （谁看得见）
                                     └─ 事件用 scopeTarget(base, key) 当 thisArg（放行谁）
   key 之间的父子关系另存：scopeParents: WeakMap<key, key>（与 ctx 原型链无关）
```

> **精确性说明**：DSH 侧画的不是"嵌套的 ctx"——`kScope` 只有**最近一个**标签（`packages\core\scope\README.zh.md` 第 99 行："一个上下文只携带一个最近的作用域键"），层级关系存在于**键**的父子关系里，不在 `ctx` 标签里。

### 2.2 动态过程：一次 `ctx.xxx` 读服务时发生了什么（cordis）

```
① ctx.xxx 触发 Proxy 的 get（ReflectService.handler.get）
       │  普通属性（不是 symbol、不是 then/prototype/数字/_开头）才走服务解析
       ▼
② key = ctx[symbols.isolate]['xxx']        ← 我这一层看到的标签
       ▼
③ 从 ctx.fiber 沿 **fiber 父链**向上找 fiber.store['xxx']
       ├─ 找到 → 返回它的实现（值本身还要过一层"可追踪"包装）
       ├─ 命中 inject 声明但没找到 → 抛 "cannot get required service ... in inactive context"
       └─ 再往上时发现父 ctx 的标签 ≠ key → **停止查找并抛错**（这就是隔离）
```

### 2.3 大白话版：把服务"切一刀"到底是什么感觉

**完全不用上表的术语**，先建立画面（来源：`vendor\cordis\src\context.ts` 第 121–125 行的 `isolate` 实现、第 99–107 行的 `extend` 实现；这里只做白话转述）：

1. 每个 `ctx` 上带着一张小纸条，写着"**我这个服务该去哪个柜子拿**"。根 `ctx` 的纸条上什么也没写。
2. 你说"我要隔离 `probe` 这个服务"：系统复印一份父纸条，在复印件上把 `probe` 那一行划掉、写上一个**新柜号**，再把复印件贴到一个新生的 `ctx` 上。
3. 从这个新 `ctx` 往下看，`probe` 就指向新柜子；父 `ctx` 那张纸条**一个字都没动**，所以父那边还是老柜子。
4. 新柜子里**本来是空的**——所以在这个 `ctx` 之下第一次"往柜子里放东西"会直接被拒（必须先显式登记）。登记完，父看父的、子看子的。
5. 如果你把**同一个柜号**给了两次"切一刀"，两次就指向同一个柜子：第二次往柜子里放东西会撞上第一次，报"这个服务已经被登记在 <某处>"。
6. 另外还有一个"配置抽屉"的操作：给某个服务挂一张配置便条。**只有在便条贴出的那个 `ctx` 之下启动的插件**才读得到它，已经存在的服务实例读不到。

## 3. cordis 侧：三个方法，一条共同底座

### 3.1 三者的共同底座：`extend` 是唯一的"造子上下文"操作

`context.ts` 第 99–107 行（`vendor\cordis\src\context.ts`；**本块与下面若干块都省去了类成员统一的那层缩进**，源码里 `extend` 这一行前面还有 2 个空格）：

```ts
extend(meta = {}): this {
  const shadow = Reflect.getOwnPropertyDescriptor(this, symbols.shadow)?.value
  const self = Object.create(getTraceable(this, this))
  for (const prop of Reflect.ownKeys(meta)) {
    Object.defineProperty(self, prop, Reflect.getOwnPropertyDescriptor(meta, prop)!)
  }
  if (!shadow) return self
  return Object.assign(Object.create(self), { [symbols.shadow]: shadow })
}
  // （第 90–98 行的 JSDoc 完整文字与此处无关，只留它给出的三条语义：
  //   "child prototypally inherits every property"、"own properties of meta shadow the inherited ones"、
  //   "The parent is not mutated"；第 109–120 行的 isolate JSDoc 见 §3.2）
```

按块讲解：

- **做什么**：`Object.create(父)` 造一个**原型链子对象**；然后把 `meta` 的每个自有键**原样搬过去**（连属性描述符一起搬，所以 getter/setter 也保留）；父对象一个字节都不改。
- **变量从哪来**：`meta` 是调用方传的（`extend({ tag: 'extend' })` 这种）；`symbols` 来自 `vendor\cordis\src\utils.ts` 第 50–73 行的 symbol 表；`getTraceable` 来自同文件第 117–125 行（它负责给带 tracker 的值套一层可追踪代理——`2.1` 讲过 `ctx` 是 Proxy，这里就是那层的入口）。
- **与哪个知识点相关**：这是 §1 表里"子上下文"和"遮蔽"两行的**唯一实现点**。`extend` 的属性遮蔽是最朴素的一种遮蔽：自有属性盖住原型属性。
- **为什么这么写**：
  - 用 `Object.create` 而**不是拷贝**：拷贝会把服务引用、`fiber` 引用一起冻住，父后来的变化子就看不见了；原型链让子"总是读父的当前值"。
  - `Reflect.ownKeys(meta)` 而**不是** `Object.keys(meta)`：**含 symbol 键**。这是 `isolate` / `intercept` 能用 symbol 表当载荷的前提——只用一个 loop 就能同时搬普通键和 symbol 键。
  - **最后三行（第 105–106 行）是 `symbols.shadow` 的复套**：如果当前 `ctx` 是被追踪包装的（调用链里出现过 shadow），新子上下文要再套一层，保持"服务方法里看到的 `ctx` 仍指向原始调用点"。（标注为推断——作者原话只在 `utils.ts` 第 116 行的函数注释里，写作 "so method calls see the caller's active context"；此处推断的是它"再套一层"的动机。）这一段**与本节三个方法不是同一机制**，第一次读不必弄懂。

### 3.2 `isolate` / `intercept` 各只有一行 `extend`

`context.ts` 第 121–145 行（两个方法连着读，才能看出它们是**同一个模式的两份实例**）：

```ts
isolate(name: string, label?: symbol) {
  const shadow = Object.create(this[symbols.isolate])
  shadow[name] = label ?? Symbol(name)
  return this.extend({ [symbols.isolate]: shadow })
}
// （第 127–138 行：intercept 的 JSDoc，见下面 §3.3；此处省略，只留它的两个 @param 语义：
//   name = 要拦截配置的服务名，config = 要合并进该服务解析后配置的配置）
intercept<K extends InjectKey>(name: K, config: Context[K] extends { [symbols.config]: infer T } ? T : never): this
intercept(name: string, config: any): this
intercept(name: string, config: any) {
  const intercept = Object.create(this[symbols.intercept])
  intercept[name] = config
  return this.extend({ [symbols.intercept]: intercept })
}
```

按块讲解：

- **做什么**：两个方法都是"**复印父的那张表 → 在复印件上写一个自有键 → 用 `extend` 把复印件贴到子 `ctx` 上**"。区别只有两处：`isolate` 的值默认是 `Symbol(name)`（**每次调用都是一个新 symbol**，所以默认不与其他作用域合流），`intercept` 的值是调用方给的配置对象。
- **变量从哪来**：`this` 是父 `ctx`；`this[symbols.isolate]` / `this[symbols.intercept]` 是父身上那张表（根 `ctx` 上它们由构造函数建成空表，见 §3.5）；`Object.create(父表)` 让**子表原型 = 父表**，于是 `in` 查询会向上走到祖先的条目。
- **与哪个知识点相关**：§1 表里"label"和"intercept 拦截配置"两行；也是附录 A 的 Q2 第 2 处（标签遮蔽）的出处。
- **为什么这么写**：
  - **子表是"原型链 + 自有键覆盖"**，而不是"拷一份再改"：拷贝意味着父后来新增的隔离条目子看不见；原型链让子读到**祖先的全部标签**，只把同名那一项换成自己的。实测（§6.1 的 B2 行）：`Object.getPrototypeOf(iso[Context.isolate]) === root[Context.isolate]` 为 `true`。
  - **`label ?? Symbol(name)`**：不传 label 就是"我要一个**独立**的作用域"；传同一个 symbol 才是"我要**加入**某个已有作用域"（文档原文：*"Passing the same `label` to two `isolate()` calls joins their scopes."*，`docs\cordis-api\context.zh.md` 第 61 行）。
  - **`intercept` 有两个重载签名**：带上类型参数的那个让 `config` 的类型跟服务的 `[symbols.config]` 对上；第三个实现签名才是运行时真正执行的那个。**运行时只看第三个**。

### 3.3 `isolate` 真正被消费的地方：服务查找循环

`reflect.ts` 第 153–166 行（`vendor\cordis\src\reflect.ts`，`ReflectService.handler.get` 的服务解析分支）：

```ts
      if (!ctx.fiber.runtime) return ctx.reflect.get(prop, false)
      return ctx.events.waterfall('internal/get', ctx, prop, error, () => {
        const key = target[symbols.isolate][prop]
        let fiber = (ctx[symbols.shadow] as Context ?? ctx).fiber
        while (true) {
          const impl = fiber.store?.[prop]
          if (impl) return getTraceable(ctx, impl.value)
          if (prop in fiber.inject) {
            error.message = `cannot get required service "${prop}" in inactive context`
            throw error
          }
          if (!fiber.runtime) throw error
          if (fiber.parent[symbols.isolate][prop] !== key) throw error
          fiber = fiber.parent.fiber
        }
      })
```

按块讲解：

- **它处在什么结构里**：这是 Proxy 的 `get` 陷阱（第 136 行 `get: (target, prop, ctx) => {`）；上面第 137–152 行先处理三种"不走服务解析"的情况——symbol/保留字/数字/`_` 开头的特殊属性、`Reflect.has` 命中的既有属性、以及 `accessor` 计算属性。**块首那行 `if (!ctx.fiber.runtime) return ctx.reflect.get(prop, false)` 是守卫**："这时的 ctx 不是某个插件运行时用的 ctx（比如根 ctx），走旧路、直接查 store。"
- **变量从哪来**：`prop` 是你要读的服务名；`target` 是 Proxy 的原始对象（即那个 `ctx`）；`key` 是**当前 ctx 自己的标签**；`ctx.fiber`、`fiber.parent`、`fiber.store` 由 `2.1` 定义（`store` 是"该 fiber 就绪依赖的快照"）；`internal/get` 是一个 waterfall 事件（`2.4`），允许别人先插手解析。
- **与哪个知识点相关**：§1 表里"isolate"那一行的**消费端**。§2.2 的动态图讲的就是这一段。
- **为什么这么写**：
  - **沿 fiber 父链找，而不是沿 ctx 原型链找**：服务记录挂在 `fiber.store` 上（`2.1` 讲过 fiber 是"可执行单元"），所以这里走的是"谁启动了我"的链；ctx 原型链在 §3.1 负责的是元数据。
  - **`fiber.parent[symbols.isolate][prop] !== key` 这一句就是隔离的**全部**含义**：一旦发现"上一级的标签和我这级不一样"，**立刻停止查找并抛错**——不许穿透到父标签去看父的实现。`key` 在循环外算一次、循环里比对，所以整条父链上标签必须一直等于 `key` 才能继续往上。
  - **两个 `throw error` 分工不同**：命中 `inject` 声明说明"这个插件**确实**依赖这个服务"，所以要换成更准确的报错（`inactive context`）；`!fiber.runtime` 说明已经走到根 fiber（根 fiber 没有 plugin runtime），此时报原始错误 `cannot get property "xxx" without inject`。

### 3.4 注册侧同源：标签也是 `store` 的键

`reflect.ts` 第 277–292 行（`ReflectService.provide`，省掉 disposer 与通知）：

```ts
provide(name: string, value?: any, check?: () => boolean) {
  return this.ctx.fiber.effect(() => {
    if (!this.props[name]) {
      this.props[name] ??= { type: 'service' }
    } else if (this.props[name].type !== 'service') {
      throw new Error(`property "${name}" is already declared as ${this.props[name].type}`)
    }
    this.props[name] = { type: 'service' }

    this.ctx.root[symbols.isolate][name] ??= Symbol(name)
    const key = this.ctx[symbols.isolate][name]
    const impl: Impl = { name, value, fiber: this.ctx.fiber, check }
    if (this.store[key]) {
      throw new Error(`service "${name}" has been registered at <${this.store[key].fiber.name}>`)
    }
    this.store[key] = impl
    // …（第 293–304 行：写 fiber.store、若已 ACTIVE 就 notify、返回注销用的 disposer，此处省略）
  }, `ctx.provide(${JSON.stringify(name)})`)
}
```

按块讲解：

- **做什么**：登记一个服务实现。三步：把名字登记进 `props`（属性表，声明"这个名字是个服务"）；算出**当前 ctx 的标签** `key`；把实现写进 `this.store[key]`。
- **变量从哪来**：`this.ctx` 是"当前正在登记的那个 ctx"；`this.store` 是 `ReflectService` 上的实例字段（第 209 行 `public store: Dict<Impl, symbol>`）——**全应用只有一份 `ReflectService`，所以 `store` 是全局的一张表，用标签当键分区**。`effect` 是 `2.3` 讲的副作用登记（所以注销是自动的）。
- **与哪个知识点相关**：§1 表里"label"那一行的另一半。`isolate` 写标签、`provide` 用标签当键——**"合流"因此是结构性的**：同 label → 同 `store` 键 → 同一条记录。
- **为什么这么写**：
  - **`this.ctx.root[symbols.isolate][name] ??= Symbol(name)`**：给**根表**补一个默认标签（只在第一次登记这个名字时）。于是"没人 isolate 过"的服务天然只有一条标签、全局唯一。实测（§6.1 的 B4/B5 行）：未隔离的子上下文 `set` 之后，根 ctx 也读到新值——因为两边算出来的 `key` 同一个。
  - **`if (this.store[key]) throw`**：同一个标签下重复登记**直接抛错**，错误信息里带上"已经登记在哪"（`<${...fiber.name}>`）。实测（§6.1 的 B9 行）报的是 `service "probe" has been registered at <root>`。
  - **`props` 与 `store` 分开**：`props` 回答"这个名字算不算服务"（Proxy 的 `has` 陷阱要用），`store` 回答"它的实现在哪"。两件事，两张表。

### 3.5 根 `ctx` 的两张表从哪来

`context.ts` 第 71–84 行：

### 3.7 `intercept` 配置怎么被合并：祖先在前

`service.ts` 第 86–102 行（`vendor\cordis\src\service.ts`，`Service[symbols.resolveConfig]`）：

```ts

  const configs: any[] = []
  while (this.name in intercept) {
    if (Object.hasOwn(intercept, this.name)) {
      configs.unshift(intercept[this.name])
    }
    intercept = Object.getPrototypeOf(intercept)
  }
  if (base) configs.unshift(base)
  if (head) configs.push(head)
  if (this['Config']?.merge) {
    return this['Config'].merge(...configs)
  } else {
    return Object.assign({}, ...configs)
  }
}
// （第 75–85 行：这个方法的 JSDoc，此处省略；它写明了合并次序：
//   "Entries added closer to the root apply first; base is prepended and head appended"，与下面讲解一致）
```

按块讲解：

- **做什么**：从**当前 ctx 的拦截表**出发，沿原型链**一路走到根**，把沿途"自有"的条目按"**祖先在前**"的顺序收集起来，再合并成一个配置。
- **变量从哪来**：`this.ctx` 是"**这个服务实例自己所属的 ctx**"（`Service` 构造函数第 53 行 `self.ctx = ctx` 写进去的），所以 `resolveConfig` 算的是"**在服务实例所在的那个上下文上，配置长什么样**"；`this.name` 是服务名；`this['Config']` 是插件声明的配置 schema（`2.6` 展开）。
- **与哪个知识点相关**：§1 表里"intercept 拦截配置"那一行的消费端；也是附录 A 的 Q2 里"第三处遮蔽"的近亲。
- **为什么这么写**：
  - **`while` + `Object.getPrototypeOf`**：沿**表**的原型链向上，而不是沿 ctx 的原型链——因为表是 §3.2 用 `Object.create(父表)` 造的，父表就是它的原型。
  - **`Object.hasOwn` 判断 + `unshift`**：`hasOwn` 保证同一层只贡献一次；`unshift` 保证**离根近的排前面**，于是后面的（更近的）在 `Object.assign` / `Config.merge` 里**覆盖**前面的。**这就是"近者优先"在配置上的形态。**
  - **没有 `Config.merge` 就退化成浅合并 `Object.assign({}, ...configs)`**：所以"没声明 schema 的服务"只有一层浅合并，不会递归合并嵌套对象。
  - **`logger` 内联了一份同样的逻辑**（`vendor\cordis\src\logger.ts` 第 240–250 行的 `_resolveConfig`，只把服务名换成固定的 `'logger'`）——为什么它不直接调 `resolveConfig`：`LoggerService` 有 `[symbols.invoke]` 体（`ctx.logger(...)` 是可调用的），它的实例化路径不一样。（标注为推断。）

## 4. DSH 侧：`dsh-scope`——同一份"近者优先"，换了个载体

DSH **没有**用 `ctx.isolate` 做 per-agent 隔离，而是自建了 `@deepseek-ai/dsh-scope`（`packages\core\scope\src\`）。原因见附录 A 的 Q4。

### 4.1 `createScope`：复用 `extend`，但标签是自己的 symbol

`index.ts` 第 137–147 行（`packages\core\scope\src\index.ts`）：

```ts
export function createScope(ctx: Context, key: ScopeKey, options?: CreateScopeOptions): Scope {
  if (options?.parent !== undefined) bindScopeParent(key, options.parent)
  const fiber = ctx.plugin(scope)
  const scoped: Context = fiber.ctx.extend({ [kScope]: key })
  let disposing: Promise<void> | undefined
  return {
    ctx: scoped,
    rawDispose: fiber.dispose,
    dispose: () => (disposing ??= quiesceFiber(fiber)),
  }
}
```

按块讲解：

- **做什么**：三步——① 如果给了 `parent`，先把 key 绑到父 key 上（§4.2）；② `ctx.plugin(scope)` 起一个**空插件**当"承重 fiber"（`scope` 就是第 121 行的 `function scope(): void {}`）；③ 在这个 fiber 的 ctx 上 `extend({ [kScope]: key })`，把标签贴上去。
- **变量从哪来**：`ctx` 是调用方给的（**它消费 ctx，不提供 ctx 键**）；`key` 是不透明对象（第 15 行 `export type ScopeKey = object`）；`kScope` 是模块私有的 `Symbol('dsh.scope')`（第 18 行）；`quiesceFiber` 来自第 115–118 行（等 fiber 的 `inertia` 也结束，才算真停稳）。
- **与哪个知识点相关**：§1 表里"scope 作用域（DSH）"那一行。**它复用了 cordis 的 `extend`，但完全不用 `isolate` / `intercept`**——这是本课"两套作用域"的分界点。
- **为什么这么写**：
  - **为什么要"承重 fiber"**：注册的**生命周期**要挂在一个 cordis fiber 上（`2.3` 的 effect 语义），所以哪怕插件体是空的，也得有一个 fiber 来承接"这个作用域拥有的一切"。`dispose()` 就是卸掉这个 fiber。
  - **为什么标签不用 `isolate`**：`isolate` 改的是**服务查找**，而 DSH 要的是**注册表可见性 + 事件放行**（下面 §4.3 / §4.4）。用 `isolate` 会把 `ctx.xxx` 也一起隔离掉——那是它**不**想要的（`packages\core\scope\README.zh.md` 第 98 行的已知限制就是这件事的代价说明）。
  - **`dispose: () => (disposing ??= quiesceFiber(fiber))`**：把"停稳"这件事**记忆化**——竞态调用同一个 `Scope` 的 `dispose()` 会 await 同一个 promise，不会卸两次。

### 4.2 父链：只能绑一次，且拒绝闭环

`index.ts` 第 54–59、72–82 行（`linkScopeParent` 与 `bindScopeParent` 连着读）：

```ts
/** Cycle-checked write shared by the bind and every rebind. */
function linkScopeParent(key: ScopeKey, parent: ScopeKey): void {
  for (let cursor: ScopeKey | undefined = parent; cursor !== undefined; cursor = scopeParents.get(cursor)) {
    if (cursor === key) throw new Error('dsh-scope: scope parent link would form a cycle')
  }
  scopeParents.set(key, parent)
}

export function bindScopeParent(key: ScopeKey, parent: ScopeKey): ScopeParentBinding {
  if (scopeParents.has(key)) {
    throw new Error('dsh-scope: scope key is already bound to a parent; re-linking requires the binding returned by the original bind')
  }
  linkScopeParent(key, parent)
  return {
    rebind(next: ScopeKey): void {
      linkScopeParent(key, next)
    },
  }
}
// （第 61–71 行的 JSDoc 与第 84–91 行的 scopeParentOf JSDoc，此处省略；
//   前者说明"绑一次"的理由，后者与本节无关）
```

按块讲解：

- **做什么**：`bindScopeParent` 把 `key` 的父设成 `parent`，**并且只允许一次**；重复调用抛错。真正的写入在 `linkScopeParent`，它**先沿父链向上走一遍**，发现要形成的链会绕回 `key` 自己就抛 `cycle` 错。
- **变量从哪来**：`scopeParents` 是模块级 `WeakMap<ScopeKey, ScopeKey>`（第 39 行）；`key` / `parent` 都是不透明对象。**注意：这个父关系与 `ctx` 原型链无关**——它是 key 与 key 之间的关系。
- **与哪个知识点相关**：§1 表里"scope 作用域（DSH）"的层级部分；也是 §4.3 里 `chainLayers` 能"远祖先在前"的前提。
- **为什么这么写**：
  - **为什么只绑一次**：绑定者拿到的 `ScopeParentBinding` 是**唯一**能改这条链的句柄（第 77–81 行）。于是"作用域的祖先"不会被别人偷偷改了——否则已经登记的贡献会在没人察觉时换了可见范围。
  - **为什么要防环**：注释写得很直白——"**every chain consumer walks parents to the root**"（第 67 行）。`chainLayers`（§4.3）和 `scopeTarget`（§4.4）都是"走到根为止"的循环；出现环就是死循环。
  - **`rebind` 存在的理由**（作者原文，第 44–47 行 JSDoc）：它服务"空白会话重组合"契约——只有在旧父之下产出的一切都没被保留时，重绑才合法；**注释同时承认这个关系看不到会话记了什么**，所以合法性由持有者自己保证。本课只记这一句，它的消费者属第三编。

### 4.3 注册表侧：`merge` 的"近者优先"与 `peek` 的"故意不继承"

`store.ts` 第 180–217 行（`packages\core\scope\src\store.ts`，`ScopedLayers` 的三个方法连着读——少了任何一个都看不出"peek 不做链继承"这句话在跟谁对比）：

```ts
  peek(scope: ScopeKey | undefined): L | undefined {
    if (scope === undefined) return undefined
    return this.scoped.get(scope)
  }
  // （第 172–179 行：peek 的 JSDoc。作者在此写明"Deliberately chain-blind"，
  //   以及理由：要访问"某个作用域自己的贡献"（它的 restrictions、它的 guards）时，
  //   不能悄悄把祖先的也带进来；要继承请用 chainLayers。）

  chainLayers(scope: ScopeKey | undefined): L[] {
    const layers: L[] = []
    for (const key of scopeChainOf(scope).reverse()) {
      const layer = this.scoped.get(key)
      if (layer !== undefined) layers.push(layer)
    }
    return layers
  }
  // （第 185–191 行：chainLayers 的 JSDoc，此处省略）

  merge<V>(
    scope: ScopeKey | undefined,
    pick: (layer: L) => NamedEntries<V>,
  ): Map<string, V> {
    const merged = new Map(pick(this.global).entries())
    for (const layer of this.chainLayers(scope)) {
      for (const [name, value] of pick(layer).entries()) merged.set(name, value)
    }
    return merged
  }
  // （第 159–170 行：类的字段 this.global（立即构造）、this.scoped（Map，惰性），
  //   以及构造函数；第 201–207 行：merge 的 JSDoc）
```

按块讲解：

- **做什么**：三个方法回答三个不同的问题——`peek(scope)`："**这个作用域自己**有没有层？"；`chainLayers(scope)`："沿它的父链，**哪些祖先**有层，按什么顺序？"；`merge(scope, pick)`："**把这些层铺成一张最终表**，同名的谁赢？"
- **变量从哪来**：`this.global` 是构造时就建好的全局层（第 169 行 `this.global = createLayer(undefined)`）；`this.scoped` 是 `Map<ScopeKey, L>`，**只有真的发生注册才会有条目**（第 236–247 行的 `effect` 负责懒创建）；`scopeChainOf` 来自 §4.2 所在文件，返回 `[key, parent, …]` **最近者在前**。
- **与哪个知识点相关**：§1 表里"shadowing 遮蔽"那一行的正式定义位。
- **为什么这么写**：
  - **`chainLayers` 里那个 `.reverse()`**：`scopeChainOf` 是"最近者在前"，而**铺表要从最远的祖先开始**，这样近的才能盖上去。作者在第 186–188 行的 JSDoc 里把这句话写死了："farthest ancestor first and the exact scope last, **so a caller layering them in order gives the nearest scope the final word**"。
  - **`merge` 先铺 `global` 再铺 `chainLayers`**：全局层是"底"，任何带作用域的层都能盖它。`merged.set(name, value)` 是 **Map 的覆盖语义**——同名后写赢、且**保留第一次插入的位置**（实测证据见 §6.2）。
  - **`peek` 为什么不走链**：因为它的调用方问的是"**这个作用域自己**的限制/守卫"，把祖先的限制混进来会让语义变成两回事。**一句话：`peek` 是"我的"，`chainLayers`/`merge` 是"我能看到的"。**
  - **读取不创建层**：`peek` 只 `get`，`merge` 只读 `this.scoped`——所以"查一次视图"不会在内存里长出层来（作者在第 155–157 行的类 JSDoc 里写了 "Reads never create scoped layers"）。

### 4.4 事件侧：`scopeTarget` 造一个"只负责路由"的载体

`index.ts` 第 170–185 行：

```ts
export function scopeTarget<T extends object>(base: T, key: ScopeKey | undefined): Scoped<T> {
  const baseFilter = (base as { [CordisContext.filter]?: (ctx: Context) => boolean })[CordisContext.filter]
  const carrier = {
    [CordisContext.filter](ctx: Context): boolean {
      if (baseFilter !== undefined && !baseFilter.call(base, ctx)) return false
      const tag = scopeOf(ctx)
      if (tag === undefined) return true
      for (let cursor = key; cursor !== undefined; cursor = scopeParents.get(cursor)) {
        if (cursor === tag) return true
      }
      return false
    },
  }
  carrierKeys.set(carrier, key)
  return carrier as unknown as Scoped<T>
}
```

按块讲解：

- **做什么**：造一个**只有 `Context.filter` 一个方法**的对象。这个方法就是"放行谓词"：先问基对象自己的过滤器（如果有），再按作用域规则判一次。
- **变量从哪来**：`base` 是"主体或服务"（调用方给，比如 agent loop 注册表把 `agent` 自己当 base）；`key` 是**分发键**（这次事件是"关于哪个 scope 的"）；`scopeParents` 是 §4.2 的父链；`scopeOf(ctx)` 读的是 §4.1 贴的 `kScope` 标签。
- **与哪个知识点相关**：§1 表里"carrier 载体"那一行；也是附录 A 的 Q2 第 4 处"事件方向与遮蔽方向相反"的出处。
- **为什么这么写**：
  - **无标签监听器恒放行**（`if (tag === undefined) return true`）：全局监听器对所有作用域都收到事件。
  - **有标签的监听器：只有当它的标签出现在"分发键 → 根"这条链上才放行**：循环是**从 `key` 往上走**的，所以"祖先标签"命中、"后代标签"不命中。作者在第 164–165 行的函数 JSDoc 里写死了这条规则："A tag **BELOW** the dispatch key stays excluded — **events flow up the chain, never down**."
  - **载体不暴露主体属性**：返回的对象只有那个 symbol 方法，主体要通过事件参数传（第 166–168 行 JSDoc）。另外 `Scoped<T>` 这个编译期品牌（第 27 行）让"用裸主体去分发带作用域事件"变成**编译错误**——把约定钉在类型上。
  - **`carrierKeys`（第 30 行的 WeakMap）**：`isScopeCarrier` / `carrierKeyOf`（第 192–204 行）靠它判断"这是不是载体、它的键是什么"，而**检查一个对象是不是载体不需要碰它的标签**。

**它在哪里被消费**：`vendor\cordis\src\events.ts` 第 165–175 行的 `dispatch`——取 `thisArg` 上的 `Context.filter`，用它筛监听器：

```ts
  dispatch(type: string, args: any[]) {
    const thisArg = typeof args[0] === 'object' || typeof args[0] === 'function' ? args.shift() : null
    const name: string = args.shift()
    if (!name.startsWith('internal/')) {
      this.emit('internal/dispatch', type, name, args, thisArg)
    }
    const filter = thisArg?.[Context.filter]
    return (this._hooks[name] || [])
      .filter(hook => hook.global || !filter || filter.call(thisArg, hook.ctx))
      .map(hook => hook.callback.bind(thisArg))
  }
  // （第 160–164 行：dispatch 的 JSDoc；第 177 行起：parallel 等五种分发模式，属 2.4）
```

按块讲解：

- **做什么**：一次事件分发的前半段——摘下 `thisArg` 与事件名，然后**筛出该跑的监听器**。
- **变量从哪来**：`args` 是调用方按"`this` 在前、事件名在后"排好的原始参数数组；`this._hooks[name]` 是该事件名下的监听器列表。
- **与哪个知识点相关**：§4.4 的"载体怎么起作用"的落点——**`ctx.on(...)` 注册的监听器能收到哪些事件，就是这一行 `.filter(...)` 决定的**。
- **为什么这么写**：`hook.global || !filter || filter.call(thisArg, hook.ctx)` 三个条件分别是——① `{ global: true }` 注册的监听器绕过筛选；② 分发时没带 `thisArg` 就不筛；③ 否则把**监听器自己的 ctx** 交给载体的谓词判。**注意第三个条件传的是 `hook.ctx`（监听器注册时的 ctx），不是 `thisArg`**——所以载体判的是"这个监听器属于哪个作用域"。

### 4.5 DSH 的 agent 侧接线：只传 key，不传 `parent`

`agent.ts` 第 122–138 行（`packages\core\agent-loop\src\agent.ts`，`ReactLoopAgent` 构造函数；**本块也省去了类成员统一的那层 2 空格缩进**）：

```ts
  constructor(
    private loopCtx: Context,
    public readonly id: SessionId,
    public readonly options: AgentOptions,
    public readonly session: Session,
  ) {
    this.requestSurfaceGeneration = session.surface.contentGeneration
    this.dispatch = agentEvents(loopCtx, this)
    this.scope = createScope(loopCtx, this)
    this.ctx = this.scope.ctx
    this.inbox = new ReactLoopInbox(this.ctx.sessionProjections, session, this.dispatch)
    // …（第 133–137 行：读 turnBoundary 投影、建 runtimeContext 与 systemPrompt 投影，与本知识点无关）
  }
```

按块讲解：

- **做什么**：构造一个 agent 时，用**自己（`this`）当 key** 建一个作用域，然后把 `this.ctx` 换成这个作用域上下文。后面所有"只对该 agent 可见"的注册都走 `this.ctx`。
- **变量从哪来**：`loopCtx` 是 agent loop 的上下文（构造参数）；`this` 是 `ReactLoopAgent` 实例——**它是不透明的 key，`dsh-scope` 从不检视它**（`docs\subsystems\scope.zh.md` 第 11 行："已交付的 agent loop 使用活跃的 `Agent` 对象作为自身的 key，但该原语从不检视该对象"）。
- **与哪个知识点相关**：§4.1 的 `createScope(ctx, key, options?)` 唯一一处"没传第三个参数"的真实调用——**这就是"带作用域的注册不继承给 subagent"的源码级答案**（附录 A 的 Q3）。
- **为什么这么写**：
  - **约定**：术语表把这条写成规则——"harness 约定：一个活跃的 agent 就是其自身 scope 的 key"（`docs\glossary.zh.md` 第 14 行）。
  - **不传 `parent` 是刻意的**：继承**只**来自 `CreateScopeOptions.parent` → `bindScopeParent(key, options.parent)`（§4.1 第一步）。agent 侧不传，于是每个 agent 都是一个**独立根**。而子 agent 的"父子"事实走的是**另一条完全不同的路**：登记时 `loopCtx.agents.enter(agent, parentAgent)`（`packages\core\agent-loop\src\index.ts` 第 621 行），那个 `parentAgent` 进的是 `AgentEntry.owner`（`packages\core\agent\src\index.ts` 第 468–472 行），用于**所有权/谱系**，与 scope 父链毫无关系。

## 5. 结论汇总：一张对照表（把 §3、§4 压回一页）

| | Cordis 的 ctx 作用域 | DSH 的 `dsh-scope` |
|---|---|---|
| 载体 | 子 `Context`（原型链） | 一个不透明的 `ScopeKey`（对象同一性） |
| 入口 | `extend` / `isolate` / `intercept` | `createScope` / `scopeOf` / `scopeTarget` / `bindScopeParent` |
| 作用对象 | **服务查找**（`ctx.xxx` 读到哪个实现）、**配置合并**、**元数据** | **注册表可见性**（工具/提示词段/命令）与**事件放行** |
| 是否影响服务查找 | 是（`isolate` 改的就是它） | **否**（README 原文："仅仅通过带作用域的上下文调用任意 Cordis 服务，并不会改变该服务仍为上下文全局这一事实"，`packages\core\scope\README.zh.md` 第 98 行） |
| 释放语义 | 随所属 fiber 卸载（`provide` 是一个 effect，§3.4） | 随 `Scope.dispose()` 撤销该作用域做出的**每一项**注册（§4.1） |
| 层级载体 | `ctx` 原型链 + fiber 父链（§3.3） | key 之间的 `scopeParents`（与 ctx 原型链无关，§4.2） |
| 方向 | 查找**向下继承**；配置**祖先在前** | 注册视图**向下继承**；事件放行**向上扩展** |

三个方法各自的**唯一**职责（其余都是副作用）：

1. **`ctx.extend(meta)`** —— 造一个原型链子上下文，把 `meta` 的自有属性（**含 symbol 键**）定义到子上下文上，**不改父**（`context.ts` 第 99–107 行）。
2. **`ctx.isolate(name, label?)`** —— 在子上下文上写一个新的**服务作用域标签**，使 `name` 在它之下解析到另一条标签上；同名 label 可以**合流**（`context.ts` 第 121–125 行）。
3. **`ctx.intercept(name, config)`** —— 在子上下文上挂一条**服务专属拦截配置**，供该服务自己按"祖先在前"的次序合并（`context.ts` 第 139–145 行 + `service.ts` 第 86–102 行）。

一句话对照：**`extend` 管"我是谁"，`isolate` 管"我看到谁"，`intercept` 管"我拿到的配置是什么"**；三者都只创建子上下文，**父上下文永不被修改**（`docs\cordis-api\context.zh.md` 第 12 行）。

### 6.4 一处文档口径 vs 源码口径（以源码为准）

`docs\cordis-api\context.zh.md` 第 91 行（以及它上面第 73–87 行的英文契约代码块）说：拦截配置会**合并进"服务解析后的配置"**。

### Q1 `extend` / `isolate` / `intercept` 各自改变什么？

→ 三者都只做一件事：**造一个新的子上下文**（`Object.create` 原型链，父不动，`context.ts` 第 99–107 行；文档同调：`docs\cordis-api\context.zh.md` 第 12 行）。差别在它们往子上下文的自有属性里放了什么：

| 方法 | 写进子上下文的键 | 改变了什么 | 影响面 |
|---|---|---|---|
| `extend(meta)` | `meta` 的每个自有键（**含 symbol**） | **元数据/身份**（如 `fiber` 自身、`kScope` 标签） | 谁读谁受益；不触碰服务解析（源码 §3.1） |
| `isolate(name, label?)` | `symbols.isolate` 表（`Object.create(父表)` + `[name]=label`） | **服务 `name` 的查找域**：读/写按新标签解析 | `reflect.ts` 第 154、164 行的查找循环；提供方必须在新标签下 `provide`（源码 §3.2 / §3.3） |
| `intercept(name, config)` | `symbols.intercept` 表（同样原型继承 + 覆盖） | **服务 `name` 的拦截配置来源** | 只对 `Service[symbols.resolveConfig]`（`service.ts` 第 86–102 行）、`logger._resolveConfig`（`logger.ts` 第 240–250 行）以及 fiber 的 `inject` 配置条目（`fiber.ts` 第 238–245 行）有意义 |

一句话：**`extend` 管"我是谁"，`isolate` 管"我看到谁"，`intercept` 管"我拿到的配置是什么"。**

### Q2 什么叫「近者优先 / 遮蔽（shadowing）」？给出定义与例子。

→ **定义**：在一条由"祖先 → 后代"组成的链上解析同一个名字时，**离查询点最近的那一层胜出**；远处的条目不会消失，只是被近处的同名条目盖住（**撤掉近处条目就重新可见**）。

要分清四处**同名但不同实现**的遮蔽（第八版把原来的三处扩到四处，第四处是事件方向）：

1. **`extend` 的属性遮蔽**：子上下文的自有属性盖住原型（父）属性。例子：`root.extend({ tag: 'extend' })` 之后 `extended.tag === 'extend'`、`root.tag === undefined`、`Object.hasOwn(root, 'tag') === false`（§6.1 实测 A2–A4）。DSH 自己的用法：`createScope` 就是 `fiber.ctx.extend({ [kScope]: key })`（`packages\core\scope\src\index.ts` 第 140 行）。
2. **`isolate` 的标签遮蔽**：子表 `Object.create(父表)` + `shadow[name] = label`，于是同名服务的标签换了。实测：`iso[Context.isolate].probe !== root[Context.isolate].probe` 为 `true`，且 `Object.getPrototypeOf(iso[Context.isolate]) === root[Context.isolate]` 为 `true`（§6.1 B2/B3）。语义后果：祖先的实现在子作用域"看不见"（§3.3 的标签校验）。
3. **DSH 注册表的具名遮蔽（近者优先的正式定义位）**：`ScopedLayers.merge()` 先铺全局层，再按 `chainLayers()`（远祖先 → 本作用域）依次 `set`（`packages\core\scope\src\store.ts` 第 208–217 行），注释原文即 *"farthest ancestor first and the exact scope last, so a caller layering them in order gives the nearest scope the final word"*（第 186–188 行）。术语表定义："**shadowing**：最具体者胜出的名称解析：一个带作用域的工具／片段／变量仅在该 scope 内替换同名的全局对应项"（`docs\glossary.zh.md` 第 18 行）。**两条独立证据**：单测 `store.spec.ts` 第 143–166 行（全局 `shared=1`、作用域 `shared=2` → merge 得 `2`，撤销后回 `1`）与我 §6.1 的探针二（父 `shadowed=20`、子 `shadowed=30` → 子视图得 `30`）。
4. **事件方向与遮蔽方向相反**（易错点）：注册视图**向下继承**（子看得见祖先），事件放行**向上扩展**（祖先的监听器收得到后代的事件），而**后代监听器收不到祖先键上的分发**——`scope.spec.ts` 第 213–220 行断言：在 agent 键上分发得到 `['agent','preset','untagged']`，在 preset 键上分发只得到 `['preset','untagged']`；我 §6.1 的 D6/D7 独立复现了同一结果。

### Q3 带作用域的注册为什么不继承给 subagent？

→ 因为**没有任何代码给 subagent 的 scope key 绑父**。逐条证据：

- **语义规定**：*"只有两层，采用扁平结构：带作用域的注册不会向下继承给 subagent；子树行为通过 lineage 数据表达，从不通过 scope 结构"*（`docs\glossary.zh.md` 第 13 行）；子系统文档同样写 *"每个子 agent 获得一个新的扁平作用域，而非继承父级注册"*（`docs\subsystems\subagent.zh.md` 第 461 行）。
- **源码路径**：agent 建作用域时**只传 key，不传 `{ parent }`**——`createScope(loopCtx, this)`（`packages\core\agent-loop\src\agent.ts` 第 130 行；见 §4.5）；而继承**只**来自 `CreateScopeOptions.parent` → `bindScopeParent(key, options.parent)`（`packages\core\scope\src\index.ts` 第 125–127、137–138 行，见 §4.1 的第一步）。
- **继承链的另一端同样缺席**：登记子 agent 走的是 `loopCtx.agents.enter(agent, parentAgent)`（`packages\core\agent-loop\src\index.ts` 第 621 行），`parentAgent` 进的是 `AgentEntry.owner`（`packages\core\agent\src\index.ts` 第 468–472 行），用于**所有权/谱系**，与 scope 父链毫无关系。
- **实测对照**：我 §6.1 的 D1–D3 证明了"**只要绑了父就继承**"（手工 `createScope(ctx, agent, { parent: preset })` 之后 `scopeChainOf(agent)` 是 `[agent, preset]`）；而 §4.5 的源码证明 agent 侧**没绑**。→ 结论：subagent 看不到父的注册，**不是因为 `ScopedLayers` 不能继承，而是因为没人给它绑父**。
- **设计意图**：谱系是**数据**（`parentSession`、`delegationDepth`、`subagentDepth`，`docs\glossary.zh.md` 第 21 行），可见性是**控制**。把二者绑在一起会让"子 agent 自动继承父的 persona/工具"变成隐式行为；扁平结构让"要不要给子 agent 同样的能力"变成一次**显式**注册。旁证：`.agents\notes\implemented\feature\2026-07-12-subagent-persona-tool-filter-and-depth.zh.md` 第 31 行——*"父级和兄弟级的人设永远不会进入子 agent 的扁平作用域"*。

> **旧版笔记此处写的是"实测对照（3.2）：subagent 视图只有全局工具"**——那份探针脚本在仓库里**已找不到**（§6.3），所以本笔记改为：**结论保留（有上面四条源码/文档证据），旧探针输出不再作为证据引用**；本次新探针只证明了"绑父即继承"这一半。

### Q4 scope 为什么是「库、无 ctx 键」的包？这与它的角色有什么关系？

→ 因为它的角色是**给注册表作者用的词汇与算法**，而不是"一个可注入的能力"。

- **事实核对（0 处反例）**：`packages\core\scope\src\` 全文只有 `export function/class/type`，**没有任何 `ctx.xxx = ...`、`provide`、`Service` 子类**（对该目录 grep `provide|new Service|ctx.\w+ =|dependencies` → 无匹配）；`package.json` 里 cordis 只出现在 `peerDependencies` / `devDependencies`（`packages\core\scope\package.json` 第 29–34 行），**没有运行时依赖**。
- **文档定调**：`docs\subsystems\scope.zh.md` 第 5 行 *"它是库原语，而不是 Cordis 服务"*；`docs\subsystems\core.zh.md` 第 20 行 *"`scope/` 是这里唯一的非服务包：一个零依赖库（`createScope`/`scopeOf`/`scopeTarget`），在模块图中位于 `session/` 与 `system-prompt/` 之下，**正是为了让它们消费它而不形成环**"*。
- **角色匹配**：服务（`ctx.xxx`）是"**运行时被注入的东西**"，依赖方向自上而下；而 `dsh-scope` 是**被基础设施包 `import` 的纯函数集**——`tools` / `system-prompt` / `session` 这些**比 agent-loop 更低或并列**的包都要用它，如果它自己是个服务，就会出现"注册表要等 agent 层注入作用域服务"的反向依赖。
- **使用形态也印证**：`createScope(ctx, key)` **接收**一个已存在的 ctx（`packages\core\scope\src\index.ts` 第 137–140 行，见 §4.1），用 `ctx.plugin(空插件)` 造承重 fiber——**它消费 ctx，不提供 ctx 键**。
- **代价是已知且被写明的**：只有"感知作用域的 API"才隔离状态；服务查找依旧全局（`packages\core\scope\README.zh.md` 第 98、100 行）。换言之，DSH 把"per-agent 隔离"实现在**注册表 + 事件**两处，而**不用** `ctx.isolate` 去隔离服务。

### Q5 `intercept` 的条目到底"在哪个上下文上"生效？（第一次读请跳过）

→ **在"服务实例自己所属的那个 ctx"上按表原型链收集，因此它只对在该上下文之下启动的插件生效，对已存在的服务实例不即时生效。**

- 收集端源码：`service.ts` 第 87 行 `let intercept = this.ctx[Context.intercept]` —— 起点是**服务实例自己的 `this.ctx`**（由 `Service` 构造函数第 53 行 `self.ctx = ctx` 写入）。
- `intercept` 返回的是**新上下文**（实测 C1：`i3 !== root3`；C2：根表的键数仍是 `0`）。所以在根上下文上"取一个挂在别处的拦截条目"必然得到空——**这是语义的必然结果，不是内核 bug**。
- 文档口径（`docs\cordis-api\context.zh.md` 第 89–91 行）说的是"在返回的上下文下**加载的插件**会看到 `config` 已合并"——与源码一致；容易误读的是同一文档第 91 行把它简写成"合并到服务解析后的配置"，读者可能据此以为"对已存在的实例立刻生效"。**判定依据**：源码第 87 行取的是 `this.ctx`。

### Q6 祖先的监听器与后代的监听器，谁能收到谁的事件？

→ **祖先能收到后代的事件，后代收不到祖先键上的事件**——"events flow up the chain, never down"（`packages\core\scope\src\index.ts` 第 164–165 行）。

- 机制：`scopeTarget(base, key)` 造的载体里，那个 `[CordisContext.filter]` 谓词是**从分发键 `key` 沿 `scopeParents` 向根走**的循环（第 177–179 行）；监听器自己的标签（`scopeOf(hook.ctx)`）必须出现在这条链上才被放行。所以"祖先标签"在链上、"后代标签"不在。
- 消费端：`vendor\cordis\src\events.ts` 第 171–173 行，`.filter(hook => hook.global || !filter || filter.call(thisArg, hook.ctx))`——把**监听器注册时的 ctx** 交给谓词。
- 两条独立证据：仓库单测 `packages\core\scope\tests\scope.spec.ts` 第 213–220 行；我本次探针 §6.1 的 D6/D7（结果逐字一致）。
