## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：把四组「前沿能力」的**身份与边界**钉死——每一组解决什么问题、挂在主干两侧的哪个接缝上、它**不做**什么。
**不是**：它们的实现细节课。每一组各自还有子系统文档与子包 README；本课只到「身份 + 那条关键调用边 + 关键源码」为止。

### 0.2 现在只要记住这 5 件事

1. **它们都不在 agent loop 主干上**：主干不认识 MCP / ACP / skill / workflow / PTC 里的任何一个；一切都是"从模型 → 工具"或"外部程序 → 协议端点"进来的。
2. **四组解决四个不同的问题**：MCP＝外部世界的能力怎么进来；ACP＝DSH 的 agent 怎么被外部程序驱动；skill＝可复用指令怎么**按需**进入上下文；workflow + PTC＝复杂编排与程序化调用怎么在**一次工具调用**里完成。
3. **身份只有三类**：能力 seam（可替换提供方）、面向模型的工具贡献方、协议端点（传输）；认清身份，边界就不会混。
4. **PTC 的正式展开是 programmatic tool calls（程序化工具调用）**，不是 "program-to-tool"：模型写一段程序，用普通异步调用调宿主函数，只拿回打印输出与返回值。
5. **workflow 与 PTC 是「引擎 + 运行时」两层**：已发布的 workflow 引擎就跑在 PTC 运行时之上。

### 0.3 明确授权：这些现在不用管

- `PtcRunSpec` / `PtcRunResult` 的**完整字段表**、`WorkflowErrorCode` 的完整取值集合——**第一次读不必弄懂**：知道"有一个 resolve→run 两步契约、失败分类是正交的"就够了。回查入口在 §4.4 与 §7.5。
- **MCP 协议细节**（协商、通知、鉴权）、**ACP 的 SDK 类型面**——属于各自子系统文档，本课只在 §2.1 / §2.2 点一下它们的落点。
- **预设平面（preset plane）怎么装配**——§5.1 只讲"哪些行留在 host plane、哪些行随预设走"这一条边界；预设机制本身是第三编。

## 1. 最小词汇表（本课新增的 8 个词）

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **seam（能力接缝）** | 主干**不直接依赖实现**的那个插口：谁插进来都行，换掉不影响上层 | 一个继承 `Service` 的抽象类，用 `super(ctx, '<键>')` 占住一个 `ctx` 键 |
| **MCP** | 让模型用上**别人写的**外部工具与资源的协议（Model Context Protocol） | `@deepseek-ai/dsh-mcp-client` / `dsh-mcp-resources` |
| **ACP** | 让**外部程序**按标准协议驱动 DSH agent 的协议（Agent Client Protocol） | `@deepseek-ai/dsh-acp`，一个 JSON-RPC stdio 服务器 |
| **skill** | 一段**可复用的任务指令**；平时只露"名字 + 描述"，要用时才把正文拉进上下文 | `ctx.skills` 注册表 + `SKILL.md` 文件 + `skill` 工具 |
| **workflow** | 一段**纯 JavaScript 编排脚本**，把工作扇出给 subagent，返回脚本最后的 JSON 值 | `ctx.workflowEngine` seam + `workflow` 工具 |
| **PTC** | **程序化工具调用**：模型写程序，程序里调宿主函数，只回传输出与返回值 | `ctx.ptcRuntime` seam |
| **`run_code`** | PTC 面向模型的那个工具名（保留名，不会被改名） | `RUN_CODE_NAME = 'run_code'` |
| **协议端点** | 一个**进程边界**，不是一个工具；它自己不进 `ctx.tools` | ACP 服务器进程、MCP 服务器进程 |

> ⚠️ **这 8 个词是「身份词」，不是「实现词」**：它们只回答"这东西在 DSH 里算哪一类"。seam 的注册与卸载机制、`Service` 的生命周期，都是第二编的主题，本课不答。

### 2.2 一条动态链（PTC 模式下一次 `run_code` 里发生了什么）

**完全不用上面的术语**，先把流程读一遍（来源：`packages/core/tools/src/ptc.ts` 第 685–709 行的实际代码，转述成白话）：

1. 模型不直接调"读文件""跑命令"，而是提交一段程序正文。
2. 宿主先看清"**这个 agent 现在能看见哪些工具**"，把它们逐个包成同名的异步函数。
3. 这些函数被装进一个叫 `tools` 的全局对象，随程序一起交给运行时。
4. 运行时把程序丢进一个**全新的受管进程**里跑。
5. 程序里每一次 `await tools.xxx(args)` 都会**回调宿主**去真正执行那个工具；宿主执行完把结果交回去。
6. 程序自己打印或返回的**才是**给模型看的输出——中间过程不进上下文。
7. 程序跑完（或超时/被取消），宿主动手收尾：中止还没回来的子调用，把它们排干。

> 本节共 16 块源码（编号 B1–B19，其中 B8 / B11 / B19 各是两段对照，B16 / B17 / B18 各由两处不相邻的行拼成）。每块上方标 `文件路径 第 A–B 行`；每块下面按「做什么 / 与哪个知识点相关 / 为什么这么写」讲。**省略处一律写明省了哪些行、为什么省。**

### 4.1 MCP：外部工具的**进程外**能力桥

**结论（回顾）**：每个已配置的 MCP 服务器 = 一个插件实例，其工具注册到 `ctx.tools`，公开名是 `mcp__<serverName>__<rawName>`。

#### 块 B1：公开名是怎么造出来的（命名约定不是文档约定，是代码约定）

`packages/mcp/mcp-client/src/tools.ts` 第 81–87 行

```ts
export function publicToolName(serverName: string, rawName: string): string {   // ← 函数头：参数就是"本地命名空间 + 远端工具名"
  const joined = `mcp__${serverName}__${rawName}`
  const normalized = joined.replace(INVALID_NAME_CHARS, '_')
  if (normalized === joined && normalized.length <= MAX_PUBLIC_NAME_LENGTH) return normalized
  const hash = createHash('sha256').update(`${serverName}\0${rawName}`).digest('hex').slice(0, HASH_LENGTH)
  return `${normalized.slice(0, MAX_PUBLIC_NAME_LENGTH - HASH_LENGTH - 1)}_${hash}`
}
// 本块是完整函数体（第 81–87 行），未省略任何行。
// 该函数依赖的三个模块级常量在同一个文件里早有定义，此处不重复贴：
//   INVALID_NAME_CHARS = /[^A-Za-z0-9_-]/g   （第 51 行）
//   MAX_PUBLIC_NAME_LENGTH = 64              （第 48 行，"DeepSeek 函数名契约"，作者注明是线上协议常量、不是配置）
//   HASH_LENGTH = 12                         （第 54 行）
// createHash 来自 'node:crypto'（第 15 行 import）。
```

按块讲解：

- **做什么**：把一个 `(serverName, rawName)` 二元组变成一个**确定的**公开工具名。干净情形就是字面拼接 `mcp__<serverName>__<rawName>`。
- **与哪个知识点相关**：§3 结论 1 说 MCP 解决"外部能力怎么进来"——**进来之后它必须以什么名字活在 `ctx.tools` 里**，就是这一块。
- **为什么这么写**：作者在函数文档注释里写明命名契约——「每个 MCP 工具都有稳定身份 `(serverName, rawName)`；面向模型的名字是 `mcp__<serverName>__<rawName>`，并按 DeepSeek 函数名约束归一化。**原始名只在线上（`tools/call`）发送，公开名永远不会被反向解析回原名**」（第 6–10 行）。
- **第三行的守卫**：只有当"替换过非法字符"或"超出 64 字符"时，才退化成"截断 + 12 位 SHA-256 尾号"；注释说明这样**不同的 MCP 身份永远不会塌成同一个公开名**（第 73–75 行）。`\0` 分隔符保证 `('a','bc')` 与 `('ab','c')` 不会撞哈希。

#### 块 B2：`serverName` 的预留（重名在**加载时**就失败）

`packages/mcp/mcp-client/src/index.ts` 第 154–176 行

```ts
export async function apply(ctx: Context, config: Config): Promise<void> {   // ← 插件入口；config 是 Schemastery 解析后的配置（第 119–142 行的 z.union）
  // Fail loud at load: reconnect misconfiguration (including programmatic
  // construction that bypassed Schemastery) rejects THIS instance before any
  // effect registers.
  const reconnect = resolveReconnectPolicy(config.reconnect, `mcp-client(${config.serverName}): reconnect`)

  // Reserve the namespace next: a duplicate `serverName` fails THIS instance
  // at load with an actionable error and leaves the earlier instance intact.
  ctx.effect(() => {
    const owner = scopeOf(ctx) ?? ctx.root          // ← owner 从哪来：本插件所在作用域，没有作用域就落到根
    let names = activeServerNames.get(owner)          // ← activeServerNames 是模块级 WeakMap<object, Set<string>>（第 47 行）
    if (!names) {
      names = new Set()
      activeServerNames.set(owner, names)
    }
    if (names.has(config.serverName)) {               // ← 守卫：同作用域内已被别人占走
      throw new Error(
        `mcp-client: serverName "${config.serverName}" is already in use by another mcp-client instance — pick a unique serverName in cordis.yml`,
      )
    }
    names.add(config.serverName)
    return () => void names.delete(config.serverName) // ← 卸载时撤销预留（effect 的返回值就是 disposer）
  }, 'mcp-client.serverName')
  // …（第 178–202 行：启动连接监督器、注册 server context、阻塞等待初次连接与工具发现完成；
  //     这段是块 B3 的主题，此处省略以免两块重复。块收尾的右花括号仍在原文件第 203 行。）
```

按块讲解：

- **做什么**：在真正连服务器**之前**先抢一个名字。抢不到就**抛错**，让这个插件实例加载失败。
- **与哪个知识点相关**：`mcp__<serverName>__<rawName>` 这个命名空间**是全局共享的**；这一块是"共享"二字的执行者。
- **为什么这么写**：作者注释（第 160–161 行）——「**先把命名空间预留掉**：重复的 `serverName` 让**这个**实例在加载时就带着可行动的错误失败，并且**不动先前那个实例**」。这是"要么完整、要么没有"在整个 MCP 桥上的第一道防线。
- **依赖从哪来**：`scopeOf(ctx)` 来自 `@deepseek-ai/dsh-scope`（第 18 行 import）；`ctx.root` 是 cordis 的根上下文；`activeServerNames` 是**模块级** WeakMap，所以同一进程里所有 `mcp-client` 实例共享它。
- **一个边界**：注释说明 agent 作用域的服务器**可以在另一个 agent 里重用同一个名字**，但全局实例之间、以及同一个 agent 内部的重名仍然互斥（第 43–46 行）。

#### 块 B3：初次同步是**阻塞激活**的

`packages/mcp/mcp-client/src/index.ts` 第 178–202 行

```ts
  // The supervisor owns the client/transport generations, the reconnect
  // loop, and the live tool registrations; disposal stops reconnection,
  // quiesces in-flight work, and unregisters the current generation.
  const connection = startConnection(ctx, config, reconnect)     // ← connection 从哪来：本文件 import 的 './connection.ts'（第 20 行）
  registerServerContext(ctx, config.serverName, connection)
  let stopping: Promise<void> | undefined
  const dispose = (): Promise<void> => stopping ??= connection.dispose()
  // Cordis announces unload before awaiting an unfinished apply(). Closing
  // the transport here releases startup requests that are still awaiting a reply.
  // oxlint-disable-next-line typescript/no-misused-promises -- Cordis contains observer failures; the effect also awaits this promise.
  ctx.on('internal/plugin', (fiber) => {                          // ← 守卫：只认"自己这根 fiber 的最终卸载"
    if (fiber !== ctx.fiber || fiber.uid !== null) return
    return dispose()
  }, { global: true })
  ctx.effect(() => dispose, 'mcp-client.connection')
  // …（此处省略第 194–198 行：一段英文注释，说明"为什么必须等初次连接完成才让 fiber 激活"，
  //     下一行的 await 就是它的实现，注释原文在下面的"为什么"里引用）

  // Block plugin activation on the initial connection + tool discovery so
  // Cordis consumers observe the tools immediately after the fiber activates.
  // When failOnStartupError is true, a failed initial attempt rejects the
  // fiber (Cordis rolls it back); otherwise the error is logged and the
  // supervisor enters its reconnect loop.
  const outcome = await connection.ready                             // ← 阻塞点：等"初次连接 + 工具发现"落定
  if (outcome.error !== undefined && config.failOnStartupError) {     // ← 守卫：只有显式要求"启动失败即失败"才抛
    throw new Error(`mcp-client(${config.serverName}): initial connection or tool synchronization failed`, { cause: outcome.error })
  }
}
```

按块讲解：

- **做什么**：把"连上服务器并拿到工具清单"当成**插件启动工作**的一部分——`apply()` 是 `async` 的，它会一直等到 `connection.ready` 落定。
- **与哪个知识点相关**：`inject = ['tools']`（第 34 行）说明这个插件要工具注册表；这一块说明它**什么时候**才能算装好。
- **为什么这么写**（作者原文，第 194–198 行）：*"Block plugin activation on the initial connection + tool discovery so Cordis consumers observe the tools immediately after the fiber activates."* —— 不阻塞的话，别的插件在 fiber 激活后立刻去 `ctx.tools` 找 MCP 工具会**找不到**。
- **为什么 `apply` 必须是 `async` 而不是返回 Promise 的普通函数**（作者原文，第 148–149 行）：*"Cordis treats a prototype-bearing ordinary function as a constructor, whose returned Promise is not startup work."*
- **两个守卫的差别**：`failOnStartupError` 为真 → **抛错**（Cordis 回滚这个 fiber）；为假（默认）→ 只记日志，监督器进入重连循环。
- **`ctx.on('internal/plugin', …)` 那一段**：Cordis 会在 `apply()` 还没结束时先宣布卸载，所以这里要**提前把传输关掉**，好放行还在等回包的启动请求。

```ts
    }
  } catch (error) {
    // A conflict on an `mcp__<serverName>__`-qualified name means a foreign
    // registration occupies this server's namespace. Roll back so the model
    // sees either the full generation or none of it — never a partial set.
    for (const dispose of disposers.values()) dispose()     // ← 回滚：把本代已注册的全部撤掉
    ctx.logger.error(`mcp-client(${opts.serverName}): tool registration failed, no tools registered: ${String(error)}`)
    if (opts.registrationFailure === 'throw') throw error   // ← 守卫：初次严格同步才向上抛
    return new Map()                                        // ← 否则退回"零工具"，让上一代之后的局面保持一致
  }
  return disposers
}
// 本块是 syncTools 的收尾段（第 145–162 行）。函数头在第 113–118 行
// （export async function syncTools(client, ctx, opts, previous): Promise<ToolDisposers>），
// 由块 B3 的 startConnection 经 enqueueSync 串行调用。
```

按块讲解：

- **做什么**：换工具清单分两步——**先造好下一代，再换**。造的时候不能报错；换的时候一旦冲突，就把**本代已注册的全部撤掉**。
- **与哪个知识点相关**：§3 结论 1 的"进来"与附录 Q1 的第 2 条边界（"要么完整世代、要么没有"）在这里有确切实现。
- **为什么这么写**（作者原文，第 153–155 行）：*"A conflict on an `mcp__<serverName>__`-qualified name means a foreign registration occupies this server's namespace. Roll back so the model sees either the full generation or none of it — never a partial set."*
- **为什么"先造后换"能保证安全**（作者在函数文档注释里的两阶段说明，第 92–103 行）：阶段 1 抓取与建表**完全不碰注册表**，任何失败（网络错误、重复原始名）都让上一代**原封不动**；只有阶段 1 成功了才进阶段 2。
- **`registrationFailure` 的两种取值从哪来**：`startConnection` 里按 `config.failOnStartupError` 决定——初次同步用 `'throw'`，重连与通知触发的再同步一律 `'contain'`（`packages/mcp/mcp-client/src/connection.ts` 第 130–140 行）。

#### 块 B5：每次同步串行化（否则会"双重释放一个、漏掉另一个"）

`packages/mcp/mcp-client/src/connection.ts` 第 162–177 行

```ts
  /**
   * Serializes every syncTools call — initial syncs and notification re-syncs
   * across all generations — so two syncs can never interleave their
   * dispose-previous/register-next swap (which would double-dispose one
   * generation and leak another).
   */
  let syncChain: Promise<void> = Promise.resolve()                        // ← 链尾；在 startConnection 函数体里（函数头第 127 行）
  function enqueueSync(generation: Client, syncOpts: ToolBridgeOptions = opts): Promise<void> {
    const run = syncChain.then(async () => {
      if (!isCurrent(generation)) return                                  // ← 守卫：这一代已经不是当前代了 → 直接不做
      disposers = await syncTools(generation, ctx, syncOpts, disposers)
    })
    // The chain tail must survive a failed sync; the enqueuing caller owns reporting.
    syncChain = run.catch(() => {})                                       // ← 让链尾"吞掉"失败，但把 run 原样返回给调用方
    return run
  }
```

按块讲解：

- **做什么**：把所有 `syncTools` 调用排到**一条链**上，任何两次同步都不会交错。
- **与哪个知识点相关**：B4 的"整体换装"只有在**不并发**时才安全——这一块就是它的前提。作者注释把这层依赖写得很直白：交错的换装会*"double-dispose one generation and leak another"*（第 162–166 行）。
- **`isCurrent` 是什么**（第 159–160 行）：`const isCurrent = (generation: Client): boolean => !disposed && client === generation` —— "只有还是当前代、且插件没被卸载，这一代才有权动作"。
- **为什么链尾要 `.catch(() => {})`**：注释原文（第 174 行）——*"The chain tail must survive a failed sync; the enqueuing caller owns reporting."* 失败只让**这一次**的 `run` reject，不让整条链断掉。

**MCP 的其余边界（结论保留，逐条带出处）**

- **资源侧是独立包**：`dsh-mcp-resources` 提供三个共享工具 `list_mcp_resources` / `list_mcp_resource_templates` / `read_mcp_resource`（`packages/mcp/mcp-resources/src/tools.ts` 第 34、43、52 行），并往系统提示词注入服务器名段落（`packages/mcp/mcp-resources/src/index.ts` 第 59–66 行）。
- **MCP 的真实边界**：它只把工具与资源送进 `ctx.tools`。DSH **不消费** MCP 的 prompts 模板，也**不支持**资源订阅（`packages/mcp/mcp-client/README.zh.md` 第 208 行；`packages/mcp/mcp-resources/README.zh.md` 第 122 行）。
- **只桥接图片这一类富结果**，音频/嵌入资源只给诊断文本（`packages/mcp/mcp-client/README.zh.md` 第 211 行）。
- **命名用本地 `serverName`，绝不采用远端 `serverInfo.name`**（`packages/mcp/mcp-client/README.zh.md` 第 107 行）。

```ts
      invalidate: () => {                                                 // ← 提供方"我这边变了"的唯一通道

        if (active !== undefined && active.layer.providers.get(active.name)?.provider === provider) {
          this.invalidateCache()
        }
      },
    }
    try {
      provider = create(control)
      const name = provider.name
      if (name === RUNTIME_PROVIDER) {                                    // ← 守卫：保留名不许被提供方占用
        throw new Error(`"${RUNTIME_PROVIDER}" is reserved for runtime skill registrations`)

      const order = this.nextProviderOrder
      this.nextProviderOrder += 1

          registration = { layer, name }

      throw error
    }
```


- **反向依赖不存在**（结论文档原文）：运行时不了解工具或会话（`packages/ptc-runtime/ptc-runtime/README.zh.md` 第 12 行）。

- **钩子清单**：`agent()` / `parallel()` / `pipeline()` / `phase()` / `log()`（`packages/workflow/workflow/README.zh.md` 第 12、36 行）。
- **PTC 的问题域**：让模型写一个程序，以普通异步调用方式调用宿主函数，**只返回打印输出与返回值**（`packages/ptc-runtime/README.zh.md` 第 12 行）；运行时不了解工具或会话，**每次运行状态不保留**（`packages/ptc-runtime/ptc-runtime/README.zh.md` 第 12 行）。
- **PTC 的消费方恰好有两个**：`dsh-tools` 的 PTC mode（`run_code`）与 `dsh-workflow-ptc`（`packages/ptc-runtime/ptc-runtime/README.zh.md` 第 28 行）。
- **二者共同的硬约束**：脚本无检查点、进程重启不可续；VM **不是安全边界**，真正的约束来自 OS 沙箱（`packages/workflow/workflow/README.zh.md` 第 126–127 行；`packages/workflow/workflow-ptc/README.zh.md` 第 59 行）。
- **一个易错点**：**PTC 模式会省略 `workflow` 工具**（决策记录 `.agents/notes/archived/simplification/2026-09-01-ptc-omits-workflow-tool.zh.md`）。所以「在 PTC 模式里我为什么没有 workflow 工具」是设计，不是缺装。
- **`workflow` 工具可以被 `toolName` 重命名**，而 `run_code` 是保留名、MCP 的 `mcp__` 前缀是固定约定（`packages/workflow/tool-workflow/README.zh.md` 第 48 行；`packages/core/tools/src/ptc.ts` 第 30 行；`packages/mcp/mcp-client/README.zh.md` 第 108 行）。

## 6. 结论复核：四条可背诵的边界规则

> 原第 5 节末尾的四条规则，此处升级为独立结论节，**每条都带出处**。

1. **host plane vs preset plane**：skill 注册表、子 agent 注册表、token meter、goal 服务留在 host plane；per-agent 的 `tool-skill`、`skill-filesystem`、`workflow` 工具随预设走（`packages/bundle/web-app/cordis.patch.yml` 第 493–506、536–559 行）。

3. **协议端点不产生 DSH 呈现数据**：ACP 只发标准语义更新；原始 provider 增量、重试尝试与呈现数据不进协议（`packages/acp/acp/README.zh.md` 第 92 行）。
4. **反向依赖不存在**：PTC 运行时「不了解工具或会话」（`packages/ptc-runtime/ptc-runtime/README.zh.md` 第 12 行）；workflow seam 把「脚本/运行/结果/事件」与「执行」分开，任何引擎都能在同一词汇背后实现（`packages/workflow/workflow/README.zh.md` 第 71 行）。

## 附录 A 关键问题与答案

> ✅ 五道题**全部给出明确答案**，不留空、不写"待补充"。Q1–Q5 都属于本课范围；其中 **Q4 里"PTC 的失败分类与限额字段"、Q5 里"预设平面怎么装配"属于后续编**，第一次读可以只记结论。

### ① MCP 解决什么问题？在 DSH 里的位置与边界？

**答案：MCP 解决「把外部世界的工具与资源接进模型工具列表」的问题，位置是 `ctx.tools` 的注册方——一台服务器一个插件实例；边界是它只贡献工具与资源，不贡献 DSH 的会话语义。**

- 问题：`dsh-mcp-client` 让模型使用外部 MCP 服务器的工具与资源，「每台服务器配置一条记录」，默认一台都不启用（`packages/mcp/mcp-client/README.zh.md` 第 12 行）。
- 位置：插件 `inject = ['tools']`（`packages/mcp/mcp-client/src/index.ts` 第 34 行），工具以 `mcp__<serverName>__<rawName>` 注册进 `ctx.tools`（命名见块 B1，注册见块 B4）。
- 边界（四条，都是文档明确写出的）：
  1. 命名用**本地 `serverName`**，绝不采用远端 `serverInfo.name`（README 第 107 行）；
  2. **要么完整世代、要么没有**：获取失败保留上一代，注册冲突整代回滚（第 110 行；源码见块 B4）；
  3. 资源是**独立包**按需读取，不支持资源订阅与 MCP 提示词模板（第 208 行）；
  4. 只桥接图片这一类富结果，音频/嵌入资源只给诊断文本（第 211 行）。
- 与 ACP 的关系：ACP 客户端声明的 MCP 服务器会被挂成 **agent 作用域**的 MCP 客户端（块 B7）。

### ② ACP 是什么、服务于什么场景？

**答案：ACP（Agent Client Protocol）是 DSH 的「被驱动」接口——一个仅面向自动化的 JSON-RPC stdio 服务器，让受信程序创建/恢复/关闭会话、选择模型选项、挂 MCP 服务器、发提示词、收语义更新、响应权限提示并取消工作。它服务的是进程外 subagent、测试运行器与脚本化控制器；人类需要的 DSH 专用呈现界面它刻意不提供。**

- 定义与场景：`packages/acp/acp/README.zh.md` 第 12、28、32 行。
- 何时避开：需要 DSH 专用呈现卡片、计划、标题、todo、终端视图或 elicitation 时（第 32 行）。
- 启动方式：`pnpm dsh --profile acp`；仓库内客户端是 `dsh-subagent-acp`（第 12、55 行）；`dsh-subagent-acp` 侧配置项是 `subagent-acp`，需要 `command` 与 `cwd`（`cwd` 省略则继承父会话），通过 `ctx.subprocess.spawn` 起子进程（`packages/subagent/subagent-acp/src/index.ts` 第 23、30–31、114–138、179 行）。
- 信任模型：ACP 客户端是**受信控制器**——stdio MCP 条目授权其绝对命令与环境，HTTP 条目授权其绝对 URL 与 header（第 76 行）。

### ③ skills 机制是什么？与工具有什么区别？

**答案：skill 是「可复用任务指令」，机制是「注册表（`ctx.skills`）+ 提供方 + 消费方」三层：先由提供方发现/收集，注册表按作用域分层合并并按名称裁决胜出项，最后 `tool-skill` 把「名称 + 截断描述」的持久目录发布给模型，正文由 `skill` 工具按需加载。**

- 三层结构与 ctx 键：`packages/skill/README.zh.md` 第 27–32 行；注册表只做合并/裁决/校验，自身不含内容（`packages/skill/skill/README.zh.md` 第 12 行）；`registerProvider` 见块 B10。
- 分层合并规则：宿主行与 repository 插件落全局层，preset 常驻插件落 preset 层，读取时合并链、最近层胜出（`packages/skill/skill/README.zh.md` 第 84 行）。
- 有 TTL 吗？**没有**：只有提供方调用 `invalidate()` 或运行时注册/释放才清缓存（同文件第 102、137 行；源码见块 B12——缓存键带 `revision`，代码里没有定时器）。
- **与工具的区别**：见 §4.3 末尾的对照表（本质 / 上下文成本 / 进入方式 / 可见性开关 / 是否执行代码）。

### ④ workflow 与 PTC 各解决什么问题？

**答案：workflow 解决「一次工具调用里编排大量 subagent」的问题（脚本化扇出、结构化结果）；PTC 解决「用程序替代逐个工具调用」的问题（模型写程序，程序内异步调用宿主绑定，只回传输出与返回值）。两者是「引擎」与「运行时」的关系：已发布的 workflow 引擎就跑在 PTC 运行时之上。**

- workflow 的问题域与适用判据：跨多文件审计、一次迁移、多角度研究，「一两项委派时优先使用普通 subagent 调用」（`packages/workflow/workflow/README.zh.md` 第 28 行）。
- workflow 是 seam：`ctx.workflowEngine`，一次上下文只有一个引擎，加载第二个引擎明确报错（同文件第 71 行；源码见块 B13 / B14）。
- PTC 的问题域：让模型写一个程序，以普通异步调用方式调用宿主函数，**只返回打印输出与返回值**（`packages/ptc-runtime/README.zh.md` 第 12 行）；运行时不了解工具或会话，**每次运行状态不保留**（`packages/ptc-runtime/ptc-runtime/README.zh.md` 第 12 行）。
- PTC 的消费方恰好有两个：`dsh-tools` 的 PTC mode（`run_code`，见块 B17）与 `dsh-workflow-ptc`（见块 B15）。
- `PtcRuntime` 的失败分类是正交的 `kind`：`exception` / `timeout` / `abort` / `worker-exit` / `invalid-output` / `output-limit` / `protocol` / `sandbox-unavailable`（`packages/ptc-runtime/ptc-runtime/README.zh.md` 第 53 行）——**第一次读只需记住"程序失败是数据，不是异常"**，具体取值回查时再看。
- 二者共同的硬约束：脚本无检查点、进程重启不可续；VM **不是安全边界**，真正的约束来自 OS 沙箱（`packages/workflow/workflow/README.zh.md` 第 126–127 行；`packages/workflow/workflow-ptc/README.zh.md` 第 59 行）。
- 一个易错点：**PTC 模式会省略 `workflow` 工具**（`.agents/notes/archived/simplification/2026-09-01-ptc-omits-workflow-tool.zh.md`）。所以「在 PTC 模式里我为什么没有 workflow 工具」是设计，不是缺装。

### ⑤ 这几者的边界如何划分（谁调用谁）？

**答案：主干（agent loop）不调用它们中的任何一个；一切从「模型 → 工具」或「外部程序 → 协议端点」进入，再向下落到 seam。**
