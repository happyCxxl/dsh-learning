## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：一个原语的全貌——`ctx.effect(body)` 到底做了什么、它交回来的东西是什么、谁在什么时候把它撤销、撤销的顺序为什么是倒着的。
**不是**：依赖注入怎么决定"什么时候该加载"（那是 `2.2`）；事件分发有几种模式（那是 `2.4`）；热重载的触发条件（那是 `2.7`）。

### 0.2 现在只要记住 4 件事

1. **`ctx.effect(body)` 是"登记"，不是"稍后执行"**：`body` **立刻同步跑**，它返回的每个 disposer 被记在**当前 fiber** 名下。
2. **`effect()` 交回来的东西是一个函数**——调用它就等于撤销；而且它**同时是 thenable**，所以 `await 它` 也等于撤销。
3. **撤销只跑一遍，并且逆序**：一个 effect 内部逆序且异步串行，不同 effect 之间逆序取出后**并发**。
4. **fiber 对父 fiber 来说也是一个 effect**——所以"卸载插件"这件事天然递归，不需要专门的递归代码。

### 0.3 明确授权：这些现在不用管

- **状态机六个状态之间的每一条迁移边**——第一次读只需要知道"有四五个状态、它们由依赖是否就绪驱动"，细节表在 §3.8，回查时再看；
- `inertia`（在飞转换）与 `epoch`（依赖指纹）这两个内部字段的**并发细节**——§3.8 讲了它在防什么，但不必背下来；
- **`Symbol.asyncDispose` 与 `await using`**——本步实测**内核没有用**（§4.5 第 3 条），所以现在完全不用学它；
- 子 fiber 的卸载顺序与 subagent 的动态 child 图的关系——属于第三编（`3.14`），本课只在 §3.9 与附录 A Q5 点一下存在。

## 1. 最小词汇表（本课新增的 6 个词）

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **effect 副作用** | 一次"可以被撤销的登记"：你去做一件事，同时交出"怎么把这件事撤回"的办法 | `ctx.effect(body)`；文档原话是"注册是可逆的副作用"（`docs/cordis-primer.zh.md` 第 13 行） |
| **disposer 撤销函数** | 那个"撤回办法"本身：一个函数，调用它就把当初登记的东西摘掉 | `() => void` / `() => Promise<void>` |

## 2. 先建立画面

### 2.1 谁是谁的一部分（静态结构）

```
Context（共享的登记处，2.1）
└─ Fiber                       ← 一次插件加载的运行时实例；每个 fiber 一个
   ├─ _disposables              ← 本 fiber 名下【全部】待撤销项的清单（一个 DisposableList）
   │   ├─ effect A 的 wrapper   ← 每个 ctx.effect() 往这里塞一个 wrapper（第 520 行）
   │   ├─ effect B 的 wrapper
   │   └─ …
   │        │
   │        └─ 每个 wrapper 自己再持有：
   │           └─ disposables[]（局部数组）  ← 这个 effect 内 body 交出的全部 disposer
   │              ├─ disposer 1
   │           └─ disposer n        ← 撤销时【先】按 reverse() 走这张局部数组
   └─ state                     ← 六态之一
```

> **精确性说明**：`wrapper` 既是"函数"（可调用 = 卸载这个 effect）又携带元数据（`symbols.effect`），所以它既出现在 `_disposables` 里，也出现在 `getEffects()` 的返回里。上图把两层清单画成包含关系只是为了让你看清"谁撤销谁"；严格说**两次 reverse 分别作用在这两张不同的表上**（§3.7）。

### 2.2 大白话版：插件被卸下的那一刻，机器里发生了什么

**完全不用上面的术语**，先建立画面（来源：`docs/cordis-tutorial/02-lifecycle-and-effects.zh.md` 第 62–66、84–94 行；这里只做白话转述，细节在 §3）。

1. 插件当初加载时，每做一件"要留下痕迹"的事（挂监听器、注册路由、起定时器），都会**同时**交出一个小函数："要撤销这件事，就调用我。"
2. 这些小函数被**登记**在插件自己的名下，按交出的先后排成一队。
3. 某个时刻有人决定卸载这个插件（改配置、热重载、显式卸载，或它依赖的服务消失了）。
4. 内核开始跑这支队——但**从队尾开始**：最后登记的**最先**撤。理由：后建立的东西可能依赖先建立的东西。
5. 如果某一步的撤销是异步的（要关连接、要等 flush），内核会**等它**；同一批里若有多个异步撤销，它们**一起跑**（不排队）。
6. 队跑空了，插件名下不再有任何登记项，这个插件就算彻底摘干净了——**不需要它在别处留一份"我的拆卸说明"**。
7. 插件挂的子插件也走同一条路：子插件本身被登记成父插件的一项，所以父插件被卸时会轮到它。

### 3.1 `effect()` 的合同：立即执行 / 逆序 / 幂等

作者把全部语义写在函数上面那段 JSDoc 里，所以先看它——本课 §1 表里的六条结论，三条直接来自这段原文。

`vendor/cordis/src/fiber.ts` 第 402–442 行

```ts
  /**
   * Register a cleanup-aware effect on this fiber.
   *
   * `execute` runs immediately; the disposers it produces are collected and
   * run (in reverse order) either when the returned disposer is called or
   * when the fiber unloads, whichever comes first. Calling the disposer twice
   * is a no-op. Throws `CordisError('INACTIVE_EFFECT')` if the fiber is
   * already disposed, and `TypeError` if `execute` returns an invalid shape.
   *
   * @param execute — the effect body; see {@link Effect} for accepted shapes.
   * @param label — effect label shown in `getEffects()` diagnostics.
   * @returns a disposer that tears the effect down and settles once done.
   */
  effect(execute: () => SyncEffect, label?: string): Disposable<Promise<void>>
  /** Same as above for async effects; the disposer is also awaitable. */
  effect(execute: () => Effect, label?: string): AsyncDisposable<Promise<void>>
  effect(execute: () => Effect, label = 'anonymous'): any {
    this.assertActive()                                        // ① 已 dispose 的 fiber 不许再登记
    if (this.state === FiberState.UNLOADING) {                 // ② 卸载中同样不许
      throw new CordisError('INACTIVE_EFFECT')
    }

    const disposables: Disposable[] = []                       // ③ 本 effect 的局部清单
    let disposing = false                                      // ④ 幂等闩
    let disposalTask: void | Promise<void>                     // ⑤ 共享的"结算 Promise"
    const dispose = () => {
      if (disposing) return disposalTask                       // ⑥ 第二次调用：返回同一个 task
      disposing = true
      let task!: void | Promise<void>
      for (const disposable of disposables.splice(0).reverse()) {   // ⑦ 清空 + 逆序
        if (task) {
          task = task.then(() => runDisposable(disposable))    // ⑧ 已有异步在飞 → 串到它后面
        } else {
          const result = runDisposable(disposable)
          if (isObject(result) && 'then' in result) {
            task = result as any                               // ⑨ 第一个异步结果成为串行链的头
          }
        }
      }
      return disposalTask = task
    }
```

按块讲解：

- **做什么**：`effect()` 是唯一的登记入口。它先校验"这个 fiber 还接受登记吗"，然后准备两样东西——一张**局部清单** `disposables`（③）和一个**幂等闩** `disposing`（④），最后定义一个**闭包** `dispose`，这个闭包就是将来撤销用的函数。
- **与哪个知识点相关**：③④⑤⑦ 就是本课 §1 表里"只在当前 fiber 名下、只跑一遍、逆序"三条的落点。
- **为什么这么写**：
  - **① 校验放在最前**：`assertActive()`（第 351–354 行）只判 `uid === null`，而 **② 单独再判一次 `UNLOADING`**——因为卸载中的 fiber 其 `uid` 还没清空，单靠 ① 拦不住，作者用两句守卫盖住两种"不接受登记"的状态。
  - **⑦ `splice(0)` 而不是 `slice()`**：它把数组**清空**。所以第二次调用时循环体一次都不进——**幂等的一半靠清空、一半靠 ⑥ 的闩**。
  - **⑧ 的 `task.then(...)` 是本课最容易误读的一行**：它让同一个 effect 内一旦出现异步 disposer，**后面所有 disposer 都排到它之后**（实测 E 段：`d1` 等 `d2` 的 120ms 跑完才动）。反过来，如果所有 disposer 都是同步的，`task` 始终是 `undefined`，⑨ 永远不成立，整批**同步立刻跑完**（实测 C 段）。
- **口述边界**："立即执行"（JSDoc 第一句）指的是 **`execute` 这个回调被立即调用**，不是"它产出的 disposer 已全部登记"；body 内部 await 或返回 Promise 时，登记发生在稍后（§3.4）。

### 3.2 effect 的合法形态：一份类型清单

`disposables` 里允许装什么、`body` 允许返回什么，由这几个类型声明界定。它们不是装饰——§3.3 的运行时分支与它们一一对应。

`vendor/cordis/src/fiber.ts` 第 64–93 行

```ts
interface AsyncDisposable<T extends Awaitable<void> = Awaitable<void>> extends PromiseLike<() => T> {
  (): T
}

/**
 * Function returned by an effect to release resources during disposal.
 *
 * Disposers run in reverse registration order when the owning fiber unloads;
 * they may be async, in which case unloading awaits them.
 */
export type Disposable<T = any> = () => T

/**
 * Effect body result accepted by `ctx.effect()` and plugin startup.
 *
 * Either a single disposer, a promise of one, or a (possibly async) iterable
 * yielding several — generator effects register each yielded disposer as it
 * is produced.
 */
export type Effect<T = any> =
  | SyncEffect<T>
  | AsyncEffect<T>

type SyncEffect<T = any> =
  | Disposable<T>
  | Iterable<Disposable<T>, void, void>

type AsyncEffect<T = any> =
  | Promise<Disposable<T>>
  | AsyncIterable<Disposable<T>, void, void>
  // （第 95–101 行：EffectMeta 接口，见 §3.6，此处省略）
```

按块讲解：

- **做什么**：给出 `effect()` 这一对重载的类型边界。`Effect` = 同步形态（单个函数 / 可迭代）∪ 异步形态（Promise<函数> / 异步可迭代）。
- **与哪个知识点相关**：这是 §3.3 运行时那串 `else if` 的**声明侧**。两者必须能对上：声明里没有的形态，运行时就会 `throw new TypeError('Invalid effect')`。
- **为什么这么写**：
  - **`AsyncDisposable` 继承的是 `PromiseLike`，不是 `Promise`**（第 64 行）：`PromiseLike` 只要求一个 `then` 方法——这正是 §3.6 能用一个**普通函数**加一个自有的 `then` 冒充 thenable 的类型依据。
  - **JSDoc 第二句是"逆序 + 卸载会等异步"的原文出处**（第 71–72 行）："Disposers run in reverse registration order when the owning fiber unloads; they may be async, in which case unloading awaits them."
  - **`Iterable<void, void>` 的两个 `void`**：生成器的 `next()` 不接受入参、也不返回 `TNext`——即**你没法从外面往生成器里塞值**，只能从它里面往外拿 disposer（§3.4 的登记循环正是这样用的）。

按块讲解：

- **做什么**：把 body 的返回值分派到五种形态之一，并在每种形态下把 disposer 交给 `runner.collect`。
- **与哪个知识点相关**：①④⑥⑧ 是结论"`effect()` 回调立即执行、但 disposer 可能稍后登记"的机制来源；⑥⑧ 解释了生成器 effect 的"边产出边登记"。
- **为什么这么写**：
  - **`safeCollect` 是唯一的收口**：它只放行 `typeof === 'function'`，其余非空值一律 `TypeError('Invalid effect')`。所以**"disposer 必须是函数"这条纪律不是约定，是硬校验**。
  - **④ 的 `effect.then(safeCollect)` 是"稍后登记"的全部实现**：`body` 返回 Promise 时，`_execute` 立刻返回一个 Promise，登记发生在它兑现之后。
  - **⑤⑧ 的 `info.error = new Error()`**：`composeError` 用它给异步失败补一条像样的调用栈——同步代码天然有栈，异步回调没有，作者手工造一个锚点。这是**诊断代码，不是机制**，读的时候可以跳过。
  - **⑦ 是"重载安全网"**：`oldEpoch` 在进入 `_execute` 前抓一次（第 357 行），异步生成器每轮比对一次。注释里没写原因，我按行为概括：**依赖指纹变了就别再往下产出了**（标注为推断）。实测 L2 段说明它在"卸载"场景下**不生效**（见 §4.4）——卸载走的是"等它跑完"而不是"打断它"。
  - **`runner` 从哪来**：`effect()` 第 445–456 行构造它（§3.5）；`_reload()` 第 656 行传的是 fiber 自己的 `_runner`（第 247–263 行构造）。两份 runner 形状相同，区别只在 `epoch` 的类型（`boolean` vs `string`）。

### 3.4 五种形态对照表（结论复核）

| `body` 返回 | 走哪条分支 | 登记时机 | 实测 |
|---|---|---|---|
| `undefined` / `null` | ② 空分支 | 不登记 | J 段 `return undefined -> 正常` |
| 单个函数 | ① | 立即 | A/C 段 |

### 3.6 `wrapper`：一个函数 + 一个改写的 `then`

`effect()` 最后交回来的东西不是普通函数，是 `defineProperty` 造出来的**函数 + 元数据**，并且 `then` 被改写。这是结论 2（"可调用 = dispose，`await` 也 = dispose"）的全部实现。

`vendor/cordis/src/fiber.ts` 第 504–520 行

按块讲解：

- **做什么**：造出返回值。这个值有三副面孔：**函数**（可调用）、**thenable**（可 `await`）、**元数据载体**（供诊断）。
- **与哪个知识点相关**：①⑦ 是"幂等"；③④ 是"撤销会等异步结算"（结论 5）；⑧⑨ 是"`await effect(...)` = 先跑完再拆掉"（结论 2）。三者都指向同一条设计：**撤销是一次有开始、有结束的异步过程，而不是一个即时开关。**
- **为什么这么写**（逐条对作者意图）：
  - **① 的存在是为了防一个具体竞态**：注释原文（第 505–507 行）说得很清楚——"A synchronous setup failure can race an owner unload that already captured this wrapper but has not invoked it yet."即 body 同步抛错时，父方可能已经把 wrapper 拿走但还没调用；此时返回 `inFlight`（回滚中的 Promise）而不是 `undefined`，让父方能 **await 到回滚结束**。这是"失败也要收干净"的细节，第一次读可以跳过。
  - **② 与⑦ 是同一个闩的两处扣动**：两条路（同步调用 wrapper、或者 `await`）都会先扣闩，所以"跑两遍"在结构上不可能。
  - **③④ 是本课结论 5 的落点**：`disposeAfter(setup)` 是"等它，而不是杀它"（第 475–483 行）。`executing` 为真 → 等 setup 屏障；`task` 有值 → 等它的异步尾巴；两者都没有 → 同步立即撤。**这三档分别对应 §3.6 按块讲解里的 ③ / ④ 前半 / ④ 后半。**
  - **⑥ 的位置很讲究**：`_disposables.push(wrapper)` 发生在**调用 body 之前**（第 522 行在它后面）。作者的注释（第 517–519 行）说明了原因：**让"重入的父卸载"能在这个 effect 跑任何插件代码之前就看到它**。`push` 返回的是"按序号删除"的闭包（`utils.ts` 第 14–19 行），所以清理完成后能把 wrapper 自己摘掉。
  - **⑤ `effectInertia`** 是一个 `WeakMap<Disposable, () => Promise|void>`（第 110–117 行）：`runDisposable` 会先查它。作用是**结构性的 owner 可以"加入"别人已经开始的那次清理**，而不是各撤各的。第一次读可以跳过。
- **⚠️ 一处极易混淆的同名**：本节标题里的 `disposeAsync`（第 550 行）与 §3.1 里的 `dispose`（第 427 行）是**两个不同函数**。`dispose()` 干实事（清空 + 逆序 + 串行），`disposeAsync()` 只负责"扣闩 + 调 `dispose`"。`wrapper` 走的是后者。

### 3.7 撤销的两级：一个 effect 内部 vs 整个 fiber

**不是**"一次 `await wrapper` 就能把整个 fiber 撤干净"：wrapper 管的是自己的局部清单，整个 fiber 的清单由 `_unload` 清。两者都逆序，但**并发性完全不同**。

`vendor/cordis/src/fiber.ts` 第 675–696 行


按块讲解：

- **做什么**：`_unload` 是 fiber 级的唯一撤销出口；`DisposableList.clear()` 提供"取出并逆序"。
- **与哪个知识点相关**：⑧ 是结论 3/4（两级逆序）中"fiber 层逆序"的落点；① 的 `Promise.all` 是结论 4（**effect 之间并发**）的落点。
- **为什么这么写**：
  - **① 一次 `clear()` 就得到数组**：`clear` 内部先 `map.clear()`（⑦）再 `reverse()`（⑧）——**数组拿到手，清单已经空了**，所以重入的第二次 `_unload` 不会重复跑。
  - **① 外面套 `Promise.all`，里面套 `try/catch`**：这是本课第二重要的设计——**并发 + 隔离**。任何一个 disposer 抛错只会被 ③ 记一条日志，**其余照跑**；整批并发等待，所以总耗时取决于最慢的那个（实测 D 段 209ms ≈ 最慢的 200ms，而不是 250ms 之和）。
  - **`clear()` 返回的 `reverse()` 只是启动顺序**：因为外层 `Promise.all` 不保证完成顺序，**"逆序"在 fiber 层只保证"谁先被调用"，不保证"谁先结束"**。
  - **⑤⑥ 是"卸载途中有新依赖"的补救**：`epoch` 不再是 `INACTIVE` 就反向来一次 `_reload()`——这条与 `_setEpoch` 的闸门（§3.8 ⑤）配合，保证同一时刻只有一条 load/unload 链在跑。

### 3.8 状态机：六态、推导函数、迁移入口

**六态与语义**：`vendor/cordis/src/fiber.ts` 第 139–154 行，注释原文逐字对应：

| 枚举 | 值 | 语义（第 141–146 行注释） |
|---|---|---|
| `PENDING` | 0 | 等待所需服务（waiting for required services） |
| `LOADING` | 1 | 插件 callback 正在运行（the plugin callback is running） |
| `ACTIVE` | 2 | 已加载并提供中（loaded and providing） |
| `FAILED` | 3 | callback 或它的 config 抛错（the callback or its config threw） |
| `DISPOSED` | 4 | 已移除、**不可重启**（was removed and cannot restart） |
| `UNLOADING` | 5 | disposer 正在运行（disposers are running） |

> ⚠️ **`DISPOSED` 是 4、`UNLOADING` 是 5**——枚举里两者顺序与直觉相反，教程第 73 行的箭头图不体现这个编号。

**推导函数**（`_getState`，第 574–579 行，优先级从上到下）：`uid === null` → `DISPOSED`；`_error` → `FAILED`；`_runner.epoch !== INACTIVE` → `ACTIVE`；否则 `PENDING`。
→ **`PENDING` 的真实含义是「epoch 还是 `INACTIVE`」**，即还没被 `_refresh()` 通过依赖检查点亮。`LOADING` / `UNLOADING` **不在这个函数里**——它是 `_setEpoch` / `_unload` 显式赋的值。

`vendor/cordis/src/fiber.ts` 第 611–639 行

```ts
  _refresh() {                                                // ① 按依赖算出新的 epoch 字符串
    let epoch: string | boolean = false
    epoch = ''
    for (const name of Object.keys(this.inject)) {             // ② inject 的每一项都要有实现
      const impl = this._store[name]
      if (!impl) {
        epoch = INACTIVE                                       // ③ 缺一个 → 回到"未就绪"
        break
      }
      epoch += ':' + impl.fiber.uid                            // ④ 指纹里含"提供者是谁"
    }
    this._setEpoch(epoch)
  }

  private _setEpoch(epoch: string) {                           // ⑤ 唯一的迁移入口
    const oldEpoch = this._runner.epoch
    if (epoch === oldEpoch) return                             // ⑥ 指纹没变 → 什么也不做
    this._runner.epoch = epoch
    if (this.inertia) return                                   // ⑦ 有在飞转换 → 只改指纹，不动状态
    this._updateState(() => {
      if (epoch !== INACTIVE && oldEpoch === INACTIVE) {
        this.inertia = this._reload()                          // ⑧ 从无到有 → 加载
        return FiberState.LOADING
      } else {
        this.inertia = this._unload()                          // ⑨ 其余（含"有效 → INACTIVE"）→ 卸载
        return FiberState.UNLOADING
      }
    })
  }
```

按块讲解：

- **做什么**：给"什么时候加载、什么时候卸载"一个**可比较的输入**。没写任何 `if (shouldLoad)` 之类的判断，而是让**依赖指纹**变化来驱动：变了才可能迁移。
- **与哪个知识点相关**：这是结论 6"驱动状态机的是依赖 epoch，不是某段 load/unload 代码"的原文出处；④ 还解释了一个容易忽略的事实——**服务提供者换代也算依赖变了**（指纹里带 `impl.fiber.uid`），所以提供者重启会连锁触发依赖者重载。
- **为什么这么写**：
  - **⑥ 是幂等**：指纹相同直接 `return`，同一状态不会被反复推进。
  - **⑦ 是并发闸门**：转换进行中（`inertia` 有值）只改指纹、不改状态，等本次转换结尾（`_reload` 第 665–671 行、`_unload` 第 688–694 行）自己决定收尾还是反向再来一轮。**这保证同一时刻只有一条 load/unload 链。**
  - **⑧ 的判据是"从 `INACTIVE` 变成有效"**，⑨ 兜住其余全部（包括"有效 → `INACTIVE`"）。所以 `restart()` 的实现就是"先 `_setEpoch(INACTIVE)`、再 `_refresh()`"（第 718–723 行）——**先拆后装，不写第二套逻辑**。

- **为什么这么写**：

```ts
          // internal/plugin observer. Its epoch is still INACTIVE, so
          // _setEpoch() has no transition to drive; explicitly unload that
          // pre-activation work before reporting disposal complete.
          if (!this.inertia) {
            this._updateState(() => {
              this.inertia = this._unload()                   // ⑩ 补漏：PENDING fiber 也要清干净
              return FiberState.UNLOADING
            })
          }
          // …（第 287–292 行：4 行注释，说明"inertia 不该 reject，真 reject 就让它崩"，
          //      属异常处理策略，与本知识点无关，此处省略）
          while (this.inertia) {
            await this.inertia                                // ⑪ 等到底才返回
          }
        }
      }, 'ctx.plugin()')                                      // ② label 固定为 'ctx.plugin()'
```

按块讲解：

- **做什么**：把"销毁这个子 fiber"包装成父 fiber 的一条 effect。disposer 里按顺序做六件事：清 `uid`、广播、摘出 runtime、改 epoch（真卸载）、补漏 PENDING 的活、等到 `inertia` 落地。
- **与哪个知识点相关**：① 是本课结论 7 的原文出处；⑨ 与 `_setEpoch`（§3.8 ⑤）是同一个入口，**"卸载"这件事没有第二条实现**；⑪ 是结论 5（卸载会等异步结算）在 fiber 层的又一次体现。
- **为什么这么写**：
  - **⑩ 的补漏不是冗余**：作者注释（第 277–280 行）说明，PENDING 的 fiber 可能已经被 `internal/plugin` 观察者写了 effect，而它的 epoch 还是 `INACTIVE`，`_setEpoch` 没有可驱动的迁移——所以要显式补一次 `_unload()`。
  - **⑪ `while` 而不是 `await this.inertia` 一次**：转换过程中可能又接上新的转换（§3.7 ⑥、§3.8 ⑧），`while` 保证"一直到没有在飞转换"才返回。
  - **顺序决定实测结果**：因为整个 dispose 是父 fiber 的一条 effect，**子插件的拆卸受父 fiber 的逆序支配**——实测 F 段里"外层的 disposer"先打印、"子插件自己的 disposer"后打印，正是 ① 这一项在父表里排在子插件内部 effect 之后的结果。

### 3.11 DSH 侧真实对照：`WebServer.register` 的 disposer 契约

DSH 的最外层注册 API 也遵守同一条契约：**注册返回 disposer，且重复注册直接抛错**。这构成"可撤销"的可验证对称性。

`packages/host/webserver/src/index.ts` 第 160–173 行

```ts
  /**
   * Register a named route. Duplicate (kind, path) throws — route patterns are
   * a composition-level contract, so a collision is a misconfiguration.
   * @param route - kind, path, and the owning handler.
   * @returns the disposer removing the route.
   */
  register(route: WebRoute): () => void {
    const table = route.kind === 'exact' ? this.exact : this.prefixes   // ① 两张表：精确 / 前缀
    if (table.has(route.path)) {
      throw new Error(`webserver: duplicate ${route.kind} route "${route.path}"`)   // ② 撞车即配置错误
    }
    table.set(route.path, route)
    return () => { table.delete(route.path) }                           // ③ 返回值就是撤销句柄
  }
```

`packages/host/webserver/tests/webserver.spec.ts` 第 243–251 行

```ts
    // Duplicate (kind, path) is a misconfiguration and throws; the disposer
    // restores registrability (register/disposer symmetry).
    expect(() => server.register({ kind: 'exact', path: '/probe', handler: () => {} }))
      .toThrow(/duplicate exact route/)                                 // ① 先证明重复会抛
    const disposeOnce = server.register({ kind: 'exact', path: '/once', handler: (_req, res) => { res.writeHead(200); res.end('ONCE') } })
    expect(await request(port, '/once')).toMatchObject({ status: 200, body: 'ONCE' })
    disposeOnce()                                                       // ② 跑一次 disposer
    expect((await request(port, '/once')).body).toContain('shell')       // ③ 路由消失，回退到 fallback
    expect(() => server.register({ kind: 'exact', path: '/once', handler: () => {} })).not.toThrow()   // ④ 同一路径立刻可再注册
```

按块讲解：

- **做什么**：第一块是**提供方**的契约（注册 + 返回撤销句柄 + 撞车抛错）；第二块是**验证方**的断言（重复抛错 → disposer 一跑 → 立刻可再注册）。
- **与哪个知识点相关**：这是结论 4（"每个注册都必须可撤销"）从"机制上成立"升级到"**可验证成立**"的证据。注释原文 "the disposer restores registrability (register/disposer symmetry)" 就是这条对称性的命名。
- **为什么这么写**：
  - **② 抛错与 ③ 返回 disposer 是配套的**：正因为重复注册会抛错，**丢掉 disposer 的后果不是"泄漏一点内存"，而是"下次加载直接失败"**（§附录 A Q6 第 5 层）。
  - **④ 的 `not.toThrow()` 是关键断言**：它证明 disposer 真的把表恢复到了"从未注册过"的状态，而不只是让路由失效。
  - **文档口径**：`packages/host/webserver/README.zh.md` 第 45 行写着"两者返回的 disposer 都会移除注册。同一张表内的重复路径会抛错"。

`<第三方插件目录>/dsh-peek/lib/index.js` 第 8–19 行、第 41–111 行（省略了三个路由 handler 的函数体）


按块讲解：

- **做什么**：一个真实插件的全部装配——取服务（③）、开一个 effect（④）、把三次注册的返回值收进数组（⑤）、返回"把它们都调一遍"的闭包（⑥）。
- **与哪个知识点相关**：①② 是 `2.2` 的 `inject`（本课只示意）；④⑤⑥ 是 §3.11 契约的消费端；⑦ 是 §3.5 的 label。
- **为什么这么写**：
  - **`apply()` 函数返回后，插件不再持有任何拆卸逻辑**：整个 `apply` 里没有 `try/catch`、没有 `unregister` 调用。它只做两件事——**注册，并交出撤销句柄**。这正是本课要讲的形态。
  - **⑥ 是正序（FIFO）而不是逆序**——与内核的"逆序"约定相反。它三条路由互相独立，正序拆没问题；但如果以后有人往这个数组里追加一个**依赖前一条**的拆除步骤（例如先注销 handler 再关闭它持有的连接），FIFO 就会在错误的时机动手。**结论：数组形式适合"互相独立"的注册；有次序要求的拆除，要么自己 `reverse()`，要么塞进一个按序 `await` 的闭包**（§附录 A Q5 第 3 条）。
  - **对端 disposer 就是 §3.11 第 ③ 行那个闭包**：`() => { table.delete(route.path) }`。所以这 6 行"插件侧代码"和 14 行"服务侧代码"合起来才构成一次完整的可逆注册。

### 4.4 从数字里能读出的五件事

1. **A 段的 `own keys = ['length','name','then']`**：wrapper 是**普通函数** + 一个**自有的 `then`**（fiber.ts 第 555 行赋值）。它因此是 thenable——`await wrapper` 会走 dispose 分支（第 555–559 行），这正是"disposer 可 await"的实现方式；`fiber.ts` 第 64–66 行把这个形状写成 `interface AsyncDisposable extends PromiseLike<() => T>`。
2. **D 段 209ms < 250ms**：两个 effect 的 disposer 在 `_unload` 的 `Promise.all`（第 676 行）下并发。教程第 94 行说的"多个异步 disposer 会并发运行"指的是**这一层**。
3. **E 段 126ms**：同一个 effect 内的 `[d3, d2, d1]` 严格串行——`[d2 async 120ms]` 结束后 `[d1 sync]` 才跑（第 432–434 行的 `task.then`）。想保证拆除顺序就把步骤塞进同一个 effect（教程第 94 行同款建议）。
4. **L2 段 dispose 到 318ms 才返回**：异步生成器 effect 的后续 `yield` **没有被卸载打断**，它跑完后注册的 disposer（`a2`）照样执行，最后 `a1`、`a2` 一起跑掉。`_execute` 第 390 行那句 `if (runner.epoch !== oldEpoch) return` 是 epoch **未变**时的安全网（保护重载场景），不是"卸载即中断"的开关；实测 epoch 已变（`runner.epoch = false`，第 509 行）时该守卫仍不生效，因为 `dispose()` 走的是 `disposeAfter(task)`——**它选择等，而不是杀**。所以 `ctx.effect(async function* () {...})` 的异步尾巴必须在 `dispose()` 里老老实实排空，或者在生成器内部自己监听取消信号。
5. **G2 段看不到 `PENDING` 事件**：`[status]` 只有 `ACTIVE → UNLOADING` 与 `UNLOADING → DISPOSED` 两条。原因是 `uid` 被清成 `null` 后 `_getState()` 已经返回 `DISPOSED` 读数，紧接着 epoch 变化把它改成 `UNLOADING`，两次 `_updateState` 之间没有 emit（§3.8 ②）。

## 附录 A 关键问题与答案

> ✅ 七道题**全部给出明确答案**，不留空、不写"待补充"。
> **第一次读请跳过 Q5、Q6 的第 4–5 层**：那两处涉及 subagent 的动态 child 图（第三编 `3.14`）与 DSH 服务的组合级约束（第三编）。

### Q1 `ctx.effect` 的回调是立即执行还是延迟执行？它返回什么？

**答案：立即执行（同步执行到第一个 `await` 或生成器第一次 `next()`）；返回一个「可调用的 disposer」，同时它还是 thenable——`await` 它等于 dispose 它。**

- **立即执行**：`effect()` 第 521–522 行 `try { task = this._execute(runner) }`，而 `_execute` 第 366 行 `const effect = runner.execute.call(this)` 就是**直接调用回调**（§3.3 第一半）。实测 A 段：`before effect()` 之后、`effect()` 返回之前，body 已打印。
- **返回形状**：第 504–514 行 `defineProperty(() => {...}, symbols.effect, meta)`——**函数**（调用即拆）+ `symbols.effect` 元数据（供 `getEffects()` 与父 effect 的 `meta.children` 使用，第 448–453、568–572 行）。
- **可 await**：第 555–559 行改写 `wrapper.then`；实测 A 段 `typeof wrapper.then === 'function'`，且 `await wrapper` 之后 disposer 已跑。
- **"立即"的边界**：如果 body 自己 await 或返回 Promise，那部分登记是**稍后**发生的（`effect.then(safeCollect)`，第 373–374 行）；异步生成器则是**每次 yield 登记一次**（第 391–393 行，实测 K 段）。所以"立即"只保证**回调被调用**，不保证**全部 disposer 已登记**。
- **幂等**：`runner.epoch` 兼作闩（第 508–509 行），重复调用返回同一个 `disposalTask`（第 428 行 `if (disposing) return disposalTask`）。
- **非法返回值**：非函数、非 null、非"函数/promise/可迭代"的对象一律 `TypeError('Invalid effect')`（第 362–364、372、397 行）；实测 J 段 `return 42` 抛 `TypeError: Invalid effect`，`return undefined` 合法。

### Q2 多个 disposer 的执行顺序？这个顺序为什么重要？

**答案：两个层次——(a) 同一个 effect 内部，disposer 按 `reverse()` 逆序、异步的还要串行等待（第 431–441 行）；(b) 不同 effect 之间，fiber 的 `_disposables` 逆序取出后并发执行（`utils.ts` 第 27–31 行 + `fiber.ts` 第 676 行）。顺序重要，是因为 DSH 用"逆序"来表达依赖的方向，而且这是唯一的拆卸排序机制。**

- **逆序的事实**：实测 C 段——注册 `x1 → x2 → x3`，再注册 `y1`，卸载输出 `y1, x3, x2, x1`。既有 effect 之间的逆序（`y1` 在 `x` 之前），也有 effect 内部的逆序（`x3` 在 `x1` 之前）。
- **为什么必须逆序**：后建立的东西可能依赖先建立的东西。`ctx.plugin(child)` 就靠这个：子 fiber 的 dispose 是**父 fiber 的一条 effect**（`fiber.ts` 第 265 行，§3.9）——父卸载时子必须能被正确摘掉，而子内部的 disposer 又必须在子被摘掉之前跑完（否则子就成了"没有主人的活对象"）。
- **并发的边界**：`_unload` 用 `Promise.all`（第 676 行），实测 D 段 200ms 与 50ms 并发、总耗时 209ms。所以"逆序"**只是启动顺序，不保证完成顺序**——异步拆除之间的先后要靠"放进同一个 effect 并逐个 await"（教程第 94 行，实测 E 段串行生效）。

### Q3 fiber 的状态机有哪几态、迁移条件分别是什么？

**答案：六态（`fiber.ts` 第 147–154 行）：`PENDING`(0)、`LOADING`(1)、`ACTIVE`(2)、`FAILED`(3)、`DISPOSED`(4)、`UNLOADING`(5)。迁移全部由「依赖 epoch 是否有效」+「uid 是否已清空」+「是否记了 `_error`」这三条事实驱动（`_setEpoch` 第 625–639 行是唯一的动作入口）。**

完整迁移表见 §3.8（含实测列）。四条补充：

1. **`FAILED` 不是终态**：`update()`（第 736–753 行）在非 ACTIVE 时清 `_error` 并 `_setEpoch(INACTIVE)` + `_refresh()`，所以配置修好后能重新点亮；`DISPOSED` 才不可重启（第 145 行注释 "cannot restart"）。
2. **`PENDING` 是"读数"而不是"驻留地"**：`_getState()` 先看 `uid`/`_error`/epoch，`PENDING` 只是"epoch 还没点亮"的读数；一旦 `_refresh` 点亮就立刻 `LOADING`。
3. **`inertia` 是并发闸门**：`_setEpoch` 第 629 行 `if (this.inertia) return`——转换进行中只改 epoch 不改状态，等本次转换结尾（第 665–671、688–694 行）自己决定是收尾还是反向再来一轮。这保证同一时刻只有一条 load/unload 链。
4. **状态变化会广播**：`_updateState` 第 586 行发 `internal/status`（教程第 73 行的箭头图就是它的语义），并且只在跨 ACTIVE 边界时 `reflect.notify`（第 588–594 行）。

### Q4 为什么实测里看不到 `PENDING` 状态事件？

**答案：因为 `_updateState` 有一条 `if (oldState === this.state) return`（第 584 行）——只有真变化才 emit；而 `DISPOSED` 是由 `uid === null` 推导出来的，它会"盖住"中间的 `PENDING`。**

实测 G2 段的事件序列只有两条：`ACTIVE → UNLOADING`、`UNLOADING → DISPOSED`。拆开看：dispose 的 disposer 先把 `uid = null`（第 268 行），此后 `_getState()` 必返回 `DISPOSED`；紧接着 `_setEpoch(INACTIVE)` 触发迁移，`_updateState` 显式给出 `UNLOADING`。两次广播之间没有第三方观察者能插进去读一次"`PENDING`"，所以事件流里就没有这一态。**这不是 bug，是"状态是推导值 + 变化才广播"两条设计的合成结果。**

### Q5 `await ctx.effect(...)` 与直接调用返回值，有什么差别？卸载顺序为什么能表达依赖方向？

**答案：`await` 与直接调用的拆卸动作完全相同（都走 wrapper 的闩与 `finalizeDisposal`），差别只在时序——`await` 会先等 body 的异步部分结算（第 556–558 行 `Promise.resolve(task).then(...)`），并把最终值当作"返回值"交给调用方。至于顺序：逆序是唯一的拆卸排序机制，所以它能表达的依赖方向只有"一条线"——这正是动态 child 图的短板。**

- **两条入口，一个闩**：`wrapper()`（第 504 行）与 `wrapper.then` 里的 `disposeAsync`（第 550 行）都会先判 `runner.epoch`、再置 `false`（§3.6 ①⑦），所以"一个 effect 撤两次"不可能。
- **`await` 多出来的语义**：`Promise.resolve(task)` 先把 body 的异步尾巴排空，再撤（§4.4 第 4 条的 L2 段就是这个"等"字）。
- **逆序表达依赖方向，但只能是一条线**：`.agents/notes/implemented/feature/2026-07-28-continuable-subagent-conversations.zh.md` 第 112 行把这句写成了设计理由——**「普通 Cordis owner effect 按注册逆序撤销，无法表达动态 child 图」**。正因为它只能表达一条线性逆序，subagent 那套动态 child-first 需求才不得不另建一个私有 scope 来承载结构性 disposer。
- **一个真实反例（本笔记自己的观察）**：§3.12 那个第三方插件的 `for (const d of disposers) d()` 是**正序**（FIFO），和内核的"逆序"约定相反。它三条独立路由，正序拆没问题；但如果以后有人在这个数组里追加一个依赖前一条的拆除步骤（例如先注销 handler 再关闭它持有的连接），FIFO 就会在错误的时机动手。**结论：`disposers` 数组形式适合"互相独立"的注册；有次序要求的拆除，要么自己 `disposers.reverse()`，要么塞进一个按序 await 的闭包。**

### Q6 为什么说「每个注册都必须可撤销」是全插件化、无特权内核的前提？

**答案：因为内核不提供"卸载一个插件"的专门逻辑——它只会把该 fiber 名下登记的 disposer 跑一遍。所以一个注册若没有对应的 disposer，它就永久留在进程里，卸载插件等于"留下一个幽灵"。一个真实插件的最小样本把这个前提压到了 6 行代码：三次路由注册 → 三个 disposer → 一个 effect → 一句话把它们跑掉。**

分五层说清：

1. **登记的入口与撤销的入口是同一个**：`ctx.effect()` 的 `collect`（第 448–453 行）是唯一收口；`_unload`（第 676 行）是唯一出口。所有内置 API（`ctx.on` / `ctx.provide` / `ctx.logger.exporter` / `ctx.plugin`；DSH 侧的注册表）都从 collect 走，也都被同一个出口收走（§3.10 表）。**没有第二条路**——这就是"无特权"的含义：宿主服务 `WebServer` 的注册和第三方插件的注册在机制上完全同构（`packages/host/webserver/src/index.ts` 第 172 行返回的 disposer 就是一个普通闭包）。
2. **需要精确的措辞**：内核里**确实有** `ctx.registry.delete(callback)`（第 273 行）、`fiber.restart()`（第 718 行）、`fiber.update()`（第 736 行）这类"管理型"入口，它们由 boot / HMR 这类**装载方**使用。但**没有**"让 A 插件去卸载 B 插件的登记项"的 API——一个插件想让别人能卸掉自己，只有一条路：**返回 disposer**。（标注为推断：这是对 `fiber.ts` 全部公开成员的归纳，源码没有一句注释直接这样表述。）
3. **真实插件的注册侧**：`apply()` 里建 `disposers` 数组，三次 `webServer.register(...)` 的返回值依次 push（§3.12 ⑤）。**`apply()` 内没有任何 `try/catch`、没有 `unregister` 调用**——它只负责"注册并交出撤销句柄"。
4. **真实插件的撤销侧**：`return () => { for (const d of disposers) d() }`——**这是整个插件唯一的拆卸代码**。它被登记在 `ctx.effect` 的局部 `disposables` 里（`body` 的返回值），因此随 `ctx.fiber._disposables` 走（第 520 行 `removeWrapper = this._disposables.push(wrapper)` 把 wrapper 挂到 fiber 上）。插件被卸载时，`_unload`（第 676 行）逆序取出并调用它，三条路由同时从 `exact` 表消失。
5. **"可撤销"是可验证的对称性，不是礼貌**：`packages/host/webserver/tests/webserver.spec.ts` 第 243–251 行把这条写成了断言（§3.11 第二块）。**反过来看代价**：如果那个插件把 `webServer.register` 的返回值丢掉（只写 `webServer.register(...)`），那么 HMR 重载它时——旧 fiber 卸载不会摘路由，新 fiber 的 `register` 立刻撞上第 168–170 行的重复检查并 **throw**，插件直接进 FAILED。**"省掉 disposer"的后果不是"泄漏一点内存"，而是"下次加载直接失败"。** 这就是"必须可撤销"是硬前提而非最佳实践的原因，也与 `docs/cordis-primer.zh.md` 第 51 行"每个注册都应有对应的 disposer"的实践规则一致。

### Q7 内核用没用 `Symbol.asyncDispose` / `await using`？

**答案：没有。** 整个 `vendor/` 目录 grep `asyncDispose` **0 命中**（本次复核；路线图第 150 行把它列为"若实现中用到"的语言点，实际未用到）。内核自建了 `AsyncDisposable extends PromiseLike<() => T>`（`fiber.ts` 第 64–66 行），并用 `wrapper.then`（第 555–559 行）实现"可 await 的 disposer"。**所以这里不需要 `await using`、也不需要 `Symbol.dispose`。**（若你读的是更晚的版本，这条结论需要重新 grep 验证。）
