## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：把「一次请求是怎么被拼出来的」讲死——**按什么顺序拼、每个输入从哪来、什么时候落进日志、什么时候被冻结、提示词在历史里怎么被安放**。
**不是**：适配器与路由怎么选（那是 `3.7`）、流式帧与重试计量（`3.8`）、工具注册表与 schema 校验（`3.9`）、压缩怎么改写历史（`3.12`）。

### 0.2 现在只要记住这 5 件事

1. **请求不是"拼一段文本"，而是"从日志派生一个不可变对象"**：它由 `header.config`（展开在顶层）+ `deriveMessages()` 派生的历史 + `header.tools` + `toolHistory` + `sessionId` + `signal` 组成，**没有独立的 `system` 字段**。
2. **顺序是"先落日志，再发出"**：`step/start` → 系统消息协调 → 首次尝试的用户消息 → `request/header` / `request/context` → **派生 + 冻结** → 最后才 `stream()`。所以任何一次请求都能从日志重建。
3. **提示词不在 header 里**，它是历史里的一条 `system/message`（surface 第 0 号节点）。
4. **冻结发生在 `buildRequest()` 内部、`stream()` 之前**，唯一被故意保留可变的是 `signal`。
5. **只对「本循环实例亲自完整冻结成功过的对象」跳过重复深冻结**，证据表是按**对象身份**记的，不是按消息 id。

### 0.3 明确授权：这些现在**不用管**

- `WeakSet` 证据表的**性能论证**（211.300 ms 里 132.876 ms 那些数字）——知道它"为什么要证明"就够了，细节在 §4.6；
- `NO_ADAPTER` 回退、`agent/request-error` 的重试语义——属 `3.7` / `3.8`；
- `device` 级的 `system-prompt/assemble` waterfall 怎么扩展——属 `2.4` / `2.8`；
- 三条 `CONTEXT_ORDERS` 之外的段位编号规则——属 `2.8`（扩展点地图）。

判断标准只有一条：**只要你能回答"这个输入是在落日志之前还是之后拼进来的、它在日志里对应哪条记录"，就够了。**

### 0.4 如果你是第一次读，跳过附录 A 的 Q4–Q6

**Q4–Q6 涉及后续编才会展开的细节**（`in-history` 路由能力、`toolUpdate` 与提示词归并的关系、`request/context` 为什么排除容量）。第一次读**跳过它们**，否则会被 `SystemPromptUpdate` / `ToolUpdate` 这两个没解释的模式卡住。

## 1. 最小词汇表（8 个词）

这 8 个词是理解本课的地基。前 4 个是"请求长什么样"，后 4 个是"它是怎么被造出来的"。

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **请求（request）** | 交给模型的那一个**不可变对象**：用哪个模型 + 历史消息 + 工具说明书 + 会话号 + 取消信号 | `GenerateOptions`；`buildRequest()` 的返回值 |
| **header 信封** | 和"消息历史"分开记的一份**调用状态**：配置（provider / model / 采样）+ 工具 schema | `EpochHeader`（`packages\core\session\src\types.ts` 第 240–251 行） |
| **surface 与节点** | 日志里"哪些事件算一条模型可见消息、按什么顺序"的成员名单；名单里的一格叫一个**节点** | `session.surface.nodes`（`3.1` / `3.3` 已定义） |
| **派生（derive）** | 每次请求时**按名单把节点投影成消息数组**，不另存一份消息 | `session.deriveMessages()` |
| **组装（assemble）** | 把各插件贡献的**提示词段**、**上下文**、**工具 schema**、**变量**合成一份中间结果 | `ctx.systemPrompt.assemble()` → `PromptAssembly` |
| **section / context** | section = 拼进提示词的一段文字；context = 拼成一条 **user 角色快照**的动态事实 | `PromptSection` / `PromptContext` |
| **投影（projection）** | 由循环自己持有的一份"我上次提交了什么"的状态，用来决定这次该不该再提交 | `SystemPromptProjection` / `RuntimeContextProjection` |
| **冻结（freeze）** | 把一个对象和它**所有子孙**递归锁死，之后改它就抛错 | `deepFreeze()`；`Object.freeze()` |

> ⚠️ 后 4 个词里，`assemble` / `section` 属于 `2.x`（插件内核的注册表），`projection` 属于 `3.3`。本课只用到上面这个程度——**它们内部怎么注册、怎么撤销**，这里不答。
> 本课还会出现 `bundle`、`profile`、`turn`、`step`、`inbox`、`settlement`、`seam` 等词：前五个已由 `1.x` / `3.5` 定义；`settlement`、`seam` 属后续编，见附录 B 的术语索引。

## 2. 两张图 + 一段大白话

### 2.1 请求由什么构成（静态结构）

```
模型收到的那一个对象（不可变）
├─ ...header.config          展开在顶层：provider / model / reasoningEffort / temperature / maxTokens / stop
├─ messages                  = session.deriveMessages()  ← 从日志的 surface 名单派生
│    ├─ 节点 0：system/message        系统提示词（本课 §5）
│    ├─ user/message                  人说的话 + 运行时上下文快照（§6）
│    ├─ assistant/message             模型已产出的内容
│    ├─ tool/call + tool/result       工具往返
│    └─ developer/message             （只在对模型可见时投影）工具增删通知
├─ tools                     = header.tools（组装时已规范化排序）
├─ toolHistory               = session.toolHistory()  ← 历史工具定义与变更
├─ sessionId
└─ signal                    唯一故意保持可变的对象
```

**没有 `system` 字段**：`EpochHeader` 显式写了 `system?: never`（`packages\core\session\src\types.ts` 第 247–250 行）。提示词只能通过历史传递。

### 2.2 一次请求被拼出来、再发出去（动态顺序）

```
preStep()                      ── 每个 step 只跑一次（重试不重跑）
  turn/start 已落
  ① inbox.claim()                        领取本步骤的输入
  ② systemPrompt.assemble()               段/上下文/工具 schema/变量 求值
  ③ renderContextSections()              上下文逐条插值、丢空
  ④ joinContextSections()                拼成快照文本
  ⑤ runtimeContext.project()             决定是否需要一条新的 user 快照
  ⑥ agent/pre-step waterfall             可改写/拒绝已领取消息
  → 返回 { messages, startsRequestSeries?, assembly }   ← assembly 整个 step 复用
  step/start 落
step() 的每次尝试（含重试）
  ⑦ renderPrompt(assembly)               插值、丢空段、空行连接
  ⑧ prepareRequest() → agent/request → llm.prepareCall()   绑定适配器、解析默认值
  ⑨ systemPrompt.project()               逐节点提交 system/message（append / replace）
  ⑩ 仅首次尝试：user/message 批次
  ⑪ buildRequest()：header 规范化 → 按需落 request/header（+ developer/message）
                     → 按需落 request/context → deriveMessages() → 冻结 → 封装
  ⑫ preparedCall.stream(request) ?? ctx.llm.stream(request)   ← 到这里才发出
```

> **精确性说明**：⑦–⑫ 在 `while (true)` 里，**重试会重跑 ⑦–⑫**，但 ①–⑥ 只在 `preStep()` 里跑一次。所以"重试复用同一份已渲染组装结果"。

### 2.3 大白话版：一次请求是怎么被发出去的

**完全不用上面的术语**，先建立画面（来源：`docs\architecture.zh.md` 第 92–111 行的轮次流程伪代码；此处只做白话转述）。

1. 轮次已经打开，循环把这一步骤该处理的话从队列里**领走**。
2. 它先把"要给模型看的东西"**算一遍**：系统提示词由哪些片段拼成、有没有要附带的动态情况（比如当前工作目录、沙箱策略）、这个模型能看到哪些工具。
3. 这些算出来的东西**先不上屏**，先交给一串"能不能过"的检查点（`agent/pre-step`）。
4. 检查点点头后，循环**开一个步骤**，并把"要用哪个模型、怎么调用"再问一遍（`agent/request` → `prepareCall`）。
5. **接着是关键的次序**：先把系统提示词写进会话记录（占第 0 格）、再把人说的话写进去（只写一次）、再把"这次请求的信封"和"这次路由的元信息"按需写进去——**这些全是"写记录"**。
6. 写完记录之后，才**照着记录算出给模型的消息数组**，并把它连同其它字段一起**锁死**（冻结）。
7. 锁死的这个对象才被交给模型层发出去；发出去以后，模型吐的字按流回到界面和记录里。
8. 如果这一步失败了要重试：**第 2–4 步不再重算**，但第 5–7 步会重走一遍（信封没变就一个字都不写）。

→ 所以判断"某个东西是不是这次请求的输入"，标准是：**它有没有在发出之前落进会话日志。** 没有落进日志的东西，恢复时就重建不出来。

## 3. 结论先行

1. **请求不是「拼一段文本」，而是「从日志派生一个不可变对象」。** 请求 = `header.config`（展开在顶层）+ `session.deriveMessages()`（派生的模型历史）+ `header.tools` + `toolHistory` + `sessionId` + `signal`，**没有独立的 `system` 字段**（`packages\core\agent-loop\src\agent.ts` 第 678–685 行；`packages\core\session\src\types.ts` 第 240–251 行，`system?: never`）。系统提示词本身是历史里的一条 `system/message`（surface 第 0 号节点）。
2. **「先落日志再发出」= 模型可见的一切在 `llm.stream()` 之前就已写进会话日志**：`step/start` → `system/message` 协调 → 首次尝试的 `user/message` 批次 → `request/header` → `request/context` → 然后才 `deriveMessages()` 派生 + `preparedCall.stream(request)` 发出（`agent.ts` 第 405–436 行）。意义是：**任何一次请求都能从日志重建**，这就是 `docs\architecture.zh.md` 第 131 行那句「模型可见即已记录」的落地方式。
3. **冻结发生在 `buildRequest()` 内部、`stream()` 之前**：`deepFreeze(header)` → 逐条 `deepFreeze(message)` + 记入 `WeakSet` → `Object.freeze(boundaryMessages)` → `Object.freeze({...})` + `markAgentLoopRequest`（`agent.ts` 第 670–685 行）。`signal` 是唯一的例外，**故意保持可变**（`packages\util\values\src\index.ts` 第 226 行 `if (node instanceof AbortSignal) continue`）。
4. **只对「本 loop 实例自己完整冻结成功过的对象」跳过重复深冻结**：证据表是 `WeakSet<Message>`（`agent.ts` 第 119–120、672–676 行），因为恢复（`fromRestore`）会**接管独立所有权的未冻结对象图**，浅冻结的根对象也不能证明其后代已冻结（`.agents\notes\archived\simplification\2026-09-06-agent-request-freeze-evidence.zh.md` 第 10、14、62、64 行）。
5. **系统提示词的「分段」发生在注册表侧，「遮蔽」有三个完全不同的层次**：段/变量/上下文按名字**遮蔽**（scoped 覆盖 global，`packages\core\system-prompt\src\index.ts` 第 575–576 行）；`complete: true` 段成为**唯一**段；系统**消息节点**在历史里的归并与清空则是 `SystemPromptProjection` 的职责（`runtime-context.ts` 第 65–111 行）。
6. **空渲染文本 ≠ 省略**：渲染为 `''` 时循环照样在 surface 第 0 号节点占位（append 一条空 `system/message`），但**清除所有生效的系统节点**，模型不再看到任何旧提示词（`runtime-context.ts` 第 88–103 行；`system-prompt/src/index.ts` 第 279–284 行 `renderPrompt` 全空时返回 `''`）。

### 4.2 全课最重要的一个时间差：`step()` 里的次序

这一段是「先落日志再发出」的**唯一现场**。它同时给出三件事：提示词怎么进历史、用户消息只用一次、请求在哪一刻被造出来。

`packages\core\agent-loop\src\agent.ts` 第 398–438 行

```ts
  private async step(decision: Extract<PreparedStep, { kind: 'enter' }>): Promise<StepEndReason | null> {
    /* v8 ignore next -- private callers establish the running phase before executing a step */
    if (this.phase.kind !== 'running') throw new Error(`agent "${this.id}": step outside running phase`)
    const { turn, step, abort: { signal } } = this.phase   // ← turn/step/signal 来自当前运行中的 phase
    signal.throwIfAborted()

    const { assembly } = decision                            // ← assembly 由 preStep() 组装，整个 step 复用
    const renderedPrompt = renderPrompt(assembly)            // ⑦ 插值 + 丢空段 + 空行连接；全空则为 ''
    let firstAttempt = true
    while (true) {                                           // ← 每次模型尝试（含重试）都走一遍循环体
      const { config, preparedCall } = await this.prepareRequest(turn, step, signal)   // ⑧ 见 §4.6
      const startsRequestSeries = firstAttempt && decision.startsRequestSeries === true
      const commits = this.systemPrompt.project(renderedPrompt, {
        inHistory: preparedCall?.systemPromptUpdate === 'in-history',
        startsSeries: startsRequestSeries
          || this.requestSurfaceGeneration !== this.session.surface.contentGeneration
          || (preparedCall?.toolUpdate === undefined && this.toolsChanged(assembly.tools)),
      })                                                     // ⑨ 见 §5.2
      for (const { message, intent } of commits) {
        this.session.append('system/message', { turn, step, message }, intent)
      }
      if (firstAttempt) {                                    // ⑩ 用户消息只提交一次
        for (const message of decision.messages) {
          this.session.append('user/message', message, { surfaceOp: 'append' })
        }
      }
      firstAttempt = false
      const request = this.buildRequest(config, preparedCall, assembly.tools, { turn, step }, startsRequestSeries, signal)  // ⑪ 见 §4.3
      // …（第 426–436 行：构造进程本地流式尝试 AssistantStreamAttempt（参数含 sessionId / 序号 / 上下文轮次戳），
      //     属 3.8，此处省略；正因如此，下面出现的 live 在这块里没有定义）
      let started = false
      try {
        const stream = preparedCall?.stream(request) ?? this.loopCtx.llm.stream(request)   // ⑫ 到这里才发出
        signal.throwIfAborted()
        // …（第 437 行的 live.start() 与第 439–542 行：消费流、结算 assistant/message 或 assistant/attempt、
        //      执行工具调用、agent/request-error 重试分支；属 3.8 / 3.10，此处省略）
      } catch (error: unknown) {
        // …（同上的异常路径）
        throw error
      }
    }
  }
```

按块讲解：

- **⑨ 在 ⑩ 之前**：系统提示词先落，用户消息后落。作者在 `docs\architecture.zh.md` 第 117 行写明理由——"首次接纳的步骤在用户消息之前预留系统头节点，即使提示词为空（不产生协议消息）"。**第 0 号节点的位置是这么保住的。**
- **⑩ 被 `if (firstAttempt)` 包住**：重试不会把同一批用户消息写第二遍。这条对应 README 原话"仅在首次尝试追加已接纳的 `user/message` 批次"（`packages\core\agent-loop\README.zh.md` 第 118 行）。
- **⑪ 在 ⑫ 之前**：`buildRequest()` 是"落日志 + 派生 + 冻结"三件事的合体，它返回的对象已经是冻结好的。**⑫ 拿到的就是成品**，没有任何"发出前再补一笔"的余地。
- **`assembly` 从 `decision` 解构出来**：它是 `preStep()` 的产物（§4.7），所以 `while (true)` 每转一圈用的都是**同一份**已渲染组装结果——这是"重试不重复组装"的落点。
- **`this.requestSurfaceGeneration !== this.session.surface.contentGeneration`**：`requestSurfaceGeneration` 是循环自己记的"上次请求时的 surface 代次"（`agent.ts` 第 113 行声明、第 128 行初始化、第 650 行更新），用来发现"surface 被替换过"（压缩）——它是 `startsSeries` 的来源之一。

### 4.3 `buildRequest()` 前半：header 什么时候写、写哪一种 reason

`packages\core\agent-loop\src\agent.ts` 第 599–651 行

```ts
  private buildRequest(
    config: LlmCallConfig,
    preparedCall: PreparedLlmCall | undefined,
    tools: GenerateOptions['tools'] & object,
    position: { turn: number; step: number },
    startsRequestSeries: boolean,
    signal: AbortSignal,
  ): GenerateOptions {
    const { session } = this
    const surfaceGeneration = session.surface.contentGeneration
    const header = canonicalHeader({                       // ← 规范化：空工具列表变成"字段缺席"
      config,
      ...preparedCall === undefined ? {} : { adapterDefaults: preparedCall.adapterDefaults },
```

### 4.5 `deepFreeze` 本体：为什么是迭代的、为什么放过 `AbortSignal`

```ts
/**
 * Deep-freeze an object graph in place while leaving live AbortSignal objects mutable.
 * @param value - value to freeze.
 * @returns the same value after every reachable enumerable child is frozen.
 */
export function deepFreeze<T>(value: T): T {
  const seen = new WeakSet<object>()                       // ① 防环 + 防重复访问
  const pending: (
    | { kind: 'visit'; node: unknown }
    | { kind: 'property'; source: Record<string, unknown>; key: string }
  )[] = [{ kind: 'visit', node: value }]                   // ② 显式栈，不是递归
  while (pending.length > 0) {
    const task = pending.pop()
    /* v8 ignore next -- the loop condition guarantees one pending task. */
    if (task === undefined) continue
    if (task.kind === 'property') {                        // ③ 取出某个属性值，下一轮再决定要不要冻它
      pending.push({ kind: 'visit', node: task.source[task.key] })
      continue
    }
    const node = task.node
    if (node === null || typeof node !== 'object') continue // ④ 基本类型直接跳过
    if (node instanceof AbortSignal) continue              // ⑤ 唯一被点名的例外
    if (seen.has(node)) continue
    seen.add(node)
    Object.freeze(node)                                    // ⑥ 先冻自己
    const keys = Object.keys(node)
    for (let index = keys.length - 1; index >= 0; index--) {
      const key = keys[index]
      /* v8 ignore next -- the loop is bounded by the captured key count. */
      if (key === undefined) continue
      pending.push({ kind: 'property', source: node as Record<string, unknown>, key })
    }
  }
  return value
}
```

按块讲解：

- **② 为什么"迭代"值得写出来**：长工具对话的历史是**很深的链**，递归实现会爆栈。作者在归档决策里专门说了这是有意的选择（`.agents\notes\archived\simplification\2026-09-06-agent-request-freeze-evidence.zh.md` 第 18 行：该决策"不改变 Session 所有权或通用 `deepFreeze` 行为"）。
- **⑤ 是"故意留一个洞"**：`AbortSignal` 是个**活对象**——冻结它会让 `abort()` 失效，取消就永远传不到适配器。这就是 §3 第 3 条"`signal` 是唯一例外"的机制底座，也是 `request-freeze.spec.ts` 第 214–223 行那条断言的对应物。
- **① `seen` 用 `WeakSet<object>`**：既是防环，也是"同一个对象只冻一次"。注意它**只在一个 `deepFreeze` 调用内有效**——跨调用的"我已经冻过了"由 `buildRequest()` 里的 `frozenMessages` 负责，两者不是一回事。
- **④ 只遍历可枚举属性**（`Object.keys`）：不可枚举属性、symbol 键、原型链上的东西都不在遍历范围。**这意味着"深冻结"是相对这套访问路径而言的**（标注为推断：由本段实现直接读得，我没有构造 symbol 键的用例实测）。

- **⑦ 为什么能"追加"**：`in-history` 路由会把 `messages` 里**任意位置**的最新 `system` 消息当作完整提示词（`packages\llm\llm\src\types.ts` 第 391–396 行），所以变更后的提示词可以跟在缓存前缀之后，而不必改写第 0 号消息。

### 4.12 运行时上下文快照投影：`RuntimeContextProjection`

```ts
/** Tracks the last retained runtime-context snapshot without owning its commit. */
export class RuntimeContextProjection {
  /** `undefined` means no snapshot ever existed; `null` means none is retained. */
  private retained: { seq: SessionSeq; text: string | undefined } | null | undefined   // ① 三态

  /**
   * Restore projection state once, then follow authoritative session events.
   * @param ctx - agent-scoped event context.
   * @param session - session receiving projected messages.
   */
  constructor(ctx: Context, session: Session) {
    const surface = new Set(session.surface.nodes)
    for (const event of eventsNewestFirst(session)) {        // ② 从最新往回扫
      if (event.type !== 'user/message' || !isOwned(event.data)) continue
      this.retained ??= null                                 // ③ 见到过 owned 消息就先记"不保留"
      if (surface.has(event.seq)) {                           // ④ 第一个仍在 surface 上的，就是它
        this.retained = { seq: event.seq, text: textOf(event.data) }
        break
      }
    }

    ctx.on('session/event', (subject, event) => {
      if (subject !== session) return                         // ⑤ 只认本会话
      if (event.type === 'user/message' && isOwned(event.data)) {
        this.retained = { seq: event.seq, text: textOf(event.data) }   // ⑥ 新快照直接接管
      } else if (this.retained
        && isReplacementSurfaceEvent(event)                   // ⑦ 替换事件
        && event.sourceEventSeqs?.includes(this.retained.seq) === true) {
        this.retained = null                                  // ⑧ 被遮蔽 → 记"曾有过但不再保留"
      }
    })
  }

  /**
   * Create an uncommitted snapshot only when the retained value differs.
   * @param current - fully rendered dynamic context.
   * @param sections - named contributions that formed the current snapshot.
   * @returns a candidate user message, or `undefined` when no update is needed.
   */
  project(current: string, sections: readonly ContextSnapshotSection[]): UserMessage | undefined {
    if (this.retained === undefined && current.length === 0) return   // ⑨ 从未有过 + 现在也空 → 什么都不做
    const snapshot = current.length === 0 ? CLEARED : current         // ⑩ 空但有历史 → 用"清除标记"常量
    if (this.retained?.text === snapshot) return                      // ⑪ 与保留值相同 → 不产生消息
    return createUserMessage({
      content: [{ type: 'text', text: snapshot }],
      // The cleared marker has no contributions left to attribute.
      source: sections.length === 0
        ? { kind: SOURCE }
        : { kind: SOURCE, form: 'snapshot', sections },               // ⑫ 带归因来源
    })
  }
}
// （第 164 行是 RuntimeContextProjection 类的收尾大括号，此处照录以保持括号平衡）
```

（同块依赖：`SOURCE = 'runtime-context'` 与 `CLEARED = 'Current runtime context: none. Earlier runtime-context snapshots no longer apply.'` 在第 19–20 行；`isOwned`（第 22–24 行）判 `message.source.kind === 'runtime-context'`；`textOf`（第 26–29 行）只认"恰好一个 text block"；`eventsNewestFirst`（第 51–55 行）是 `session.snapshotEvents().toReversed()`。）

按块讲解：

- **① 三态是这一块的核心设计**：`undefined` = **从未有过**快照（所以"现在也空"就等于什么都没发生）；`null` = **曾有过但已被遮蔽**（所以"现在也空"必须发一条清除标记）；`{seq, text}` = 当前保留的那条。三态混用会直接答错 §9 的 Q1。

### 4.13 header 的规范化、等价与折叠

```ts
/**
 * Normalize a header to canonical form: an empty tool list becomes an absent
 * field, matching how requests are built. …
 */
export function canonicalHeader(header: EpochHeader): EpochHeader {
  const adapterDefaults = header.adapterDefaults
  return {
    config: header.config,
    ...adapterDefaults?.reasoningEffort === true || adapterDefaults?.maxTokens === true
      ? { adapterDefaults }
      : {},
    ...header.tools !== undefined && header.tools.length > 0 ? { tools: header.tools } : {},   // ① 空列表 → 字段缺席
  }
}

/** Canonical JSON equality for tool schemas assembled through the same path. */
function sameSchema(a: ToolSchema, b: ToolSchema): boolean {
  return JSON.stringify(a) === JSON.stringify(b)           // ② schema 按 JSON 文本逐项比
}

/**
 * Field-wise equality over canonical headers. Tool schemas compare in order. …
 */
export function headerEquals(a: EpochHeader, b: EpochHeader): boolean {
  if (
    !callConfigEquals(a.config, b.config)
    || a.adapterDefaults?.reasoningEffort !== b.adapterDefaults?.reasoningEffort
    || a.adapterDefaults?.maxTokens !== b.adapterDefaults?.maxTokens
  ) return false
  const at = a.tools ?? []
  const bt = b.tools ?? []
  return at.length === bt.length && at.every((tool, i) => sameSchema(tool, bt[i] as ToolSchema))
}

/**
 * Fold the header events of a log (or any prefix) into the
 * {@link EpochHeader} in force after the last snapshot. …
 */
export function foldRequestHeader(events: readonly SessionEvent[], from?: EpochHeader): EpochHeader | undefined {
  let state = from
  for (const event of events) {
    if (event.type === 'request/header') state = canonicalHeader(event.data.header)   // ③ 只吃 header 事件，后者胜
  }
  return state
}
```

按块讲解：

- **① 空工具列表被规范化成"字段缺席"**：所以"没有任何工具"和"工具列表为空数组"在日志里是**同一种**表示。这也是 `EpochHeader.tools?` 是可选而不是必填的原因。
- **② schema 用 `JSON.stringify` 比**：这条比较是"同一条装配路径产出的 schema"之间的比，作者用注释写明了这个前提（`assembled through the same path`）。所以它比的是**键顺序敏感的 JSON 文本**——同一份 schema 若键顺序变了就会被判为 `change`（标注为推断：由 `JSON.stringify` 的语义直接读得，我没有构造键顺序不同的用例实测）。
- **③ `foldRequestHeader` 是纯离线重建**：任何持有日志的人都能用它算出"某个请求是在哪个 header 下构建的"。在线的 `Session` 走的是**增量同一套逻辑**（`packages\core\session\src\index.ts` 第 784–794 行），并且把折叠结果 `deepFreeze` 住——作者在行内注释里写了理由：折叠结果是**按引用暴露的会话状态**，有人原地改它就会让后续所有比较与日志脱钩，所以"改它就抛错"。

### 5.1 分段（注册表侧）

### 5.2 遮蔽（三种，必须分清）

| # | 层次 | 机制 | 源码 |
|---|---|---|---|
| 1 | **名字遮蔽** | `layers.merge(scope, …)` 让 scoped 段/上下文/变量盖住同名 global；变量按"由远及近"写入，最近的胜出 | `system-prompt/src/index.ts` 第 563–576 行 |

**第 3 层的四种结果**（全部在 §4.11 的源码里）：

- 没有任何系统节点 → 追加一条（**即使渲染为空也追加**，以预留第 0 号节点）；
- 不具备 `in-history` 能力、或开新序列、或渲染为空 → 把第 2..n 个**非空**系统节点逐个替换为空内容，再按需改写头节点；
- 具备能力且序列延续 → 有效文本未变**不产生事件**，变了则**追加**；
- 读取时 `textOf()` 只认「恰好一个 text block」的消息，多块或非文本段返回 `undefined`。

### 5.3 抑制器：`suppressRuntimeContext()`

`packages\core\system-prompt\src\index.ts` 第 500–512 行注册一个作用域内的抑制器；组装时第 561–562 行判断"全局或作用域链上有没有抑制器"，第 614–616 / 633 行把上下文清成 `[]`。

**它只清空"组装出的上下文列表"，不禁用拥有底层事实的服务**——作者在 JSDoc 里写得很直白：*"without changing the services that own or enforce those facts"*。所以被抑制的是"告诉模型"，不是"事实本身"。

### 5.4 空渲染文本意味着什么

`renderPrompt` 在所有段皆空时返回 `''`（第 279–284 行），`project()` 走到 `rendered.length === 0` 分支后**清空所有生效的系统节点**（§4.11 ③④⑤）。语义是「本轮没有系统提示词」，而**不是**「沿用上一次的提示词」——README 原文（`packages\core\agent-loop\README.zh.md` 第 120 行）：

> 空头节点且没有生效的后续系统节点表示没有提示词；重复清除与恢复会话都保持为空。

注意"空头节点 + 没有生效的后续节点 = 没有提示词"这个判据，以及"重复清除"是幂等的（§4.11 ④ 的 `filter` 让它第二次不再产生事件）。

## 6. 运行时上下文快照：与段分离的一条 user 消息

- **它为什么不是段**：段渲染成提示词文本，上下文渲染成**模型历史里带来源的 user 角色快照**（`packages\core\system-prompt\README.zh.md` 第 96 行："段与动态上下文是独立的输入"）。二者在组装结果里是两个数组（§4.8 ⑧）。
- **它的内容**：`renderContextSections()` 求值出 `{ name, text }[]`，`joinContextSections()` 拼成带固定开场白的文本，`RuntimeContextProjection.project()` 决定要不要追加（§4.12）。
- **它的归因**：`source` 带 `form: 'snapshot'` 与 `sections`，让消费方能回答"这段快照是谁贡献的"。
- **它怎么消失**：压缩的替换事件只要声明替换了快照那条 seq，投影就把 `retained` 置 `null`，下一次投影发出一句 `CLEARED`（§4.12 ⑦⑧⑩）。

## 7. 重试、序列与 header 继承

- **`step()` 的 `while (true)` 每轮都重新走 `prepareRequest()` → `project()` → `buildRequest()`**（`agent.ts` 第 407–425 行），所以**重试也会重新做 header 判定、重新落 `request/context` 判定、重新冻结**；但渲染好的 `assembly` 只在 `preStep()` 里组装一次，重试不会重新组装、不会重跑 `agent/pre-step`、也不会重复追加用户消息（第 404、419–424 行；README 第 118 行）。
- **header 的写入是差分的**：与基线相等且没有新序列时**一个字都不写**；只有 `startsSeries` 为真才写一条 `reason: 'series'`（第 626–634 行，§4.3）。
- **`startsSeries` 的三个来源**：`pre-step` 决策声明、`session.surface.contentGeneration` 变化（surface 替换或图片省略）、以及"路由不支持 `toolUpdate` 但可见工具变了"（第 413–414 行）。
- **因此日志规模与「模型真正看到的变化」成正比**，而不是与「请求次数」成正比；这也是"模型可见即已记录"能同时保持可重建与低成本的原因。
- **每条失败流也会留下痕迹**：`assistant/attempt` 保留已到 settlement 的失败 / 重试 / 取消 attempt 但不进模型历史（`docs\architecture.zh.md` 第 127 行）；请求级失败进入 `agent/request-error`，监听器返回 `{ kind: 'retry' }` **且不调用 `next()`** 时才 `continue` 重试（`agent.ts` 第 494–509 行）。

### Q2 「先落日志再发出」的意义是什么？日志里记了哪些记录？

→ **意义**：契约是「**模型可见即已记录**」，每个模型请求都必须能从日志重建，因此**新增模型可见输入必须对应会话事件**（`docs\architecture.zh.md` 第 131 行）。落日志与派生都发生在 `stream()` 之前（`agent.ts` 第 404–436 行），所以重建路径与在线路径读的是**同一份事实**，不会漂移；`assistant/message` 又反过来嵌入产生它的精确 stream（`docs\architecture.zh.md` 第 127 行）。

→ **记什么**：`step/start`（第 329 行）；`system/message`（第 417 行，带 `append` 或逐节点 `replace` 的 surfaceOp）；`user/message`（第 421 行）；`request/header`（第 620 / 627 / 633 行，reason ∈ `initial` / `resume` / `change` / `series`，可带 `startsSeries`）；工具增删时的 `developer/message`（第 643 行）；`request/context`（第 665 行，仅 4 字段且仅在变化时）；随后的 `assistant/message` / `assistant/attempt`（第 451、522 行）；`step/end`（第 356 行）。其中 `turn/*`、`step/*`、`system/message`、`user/message`、`assistant/message`、`assistant/attempt`、`tool/*` 是**持久会话事件**（`docs\architecture.zh.md` 第 113 行）。

### Q3 请求冻结发生在哪一步？为什么只对完全冻结的对象复用冻结证据？

→ **位置**：`buildRequest()` 的最后一段、**在** `request/context` 落日志与 `signal.throwIfAborted()` 之后、`preparedCall.stream(request)` 之前（`agent.ts` 第 667–686 行 vs 第 436 行）。具体动作：冻结本地规范化 header（第 670 行）→ 对每条未证明的消息 `deepFreeze` 并登记 `WeakSet`（第 671–676 行）→ 冻结消息数组（第 677 行）→ 冻结请求封装并打 marker（第 678–685 行）。

→ **为什么只复用「完全冻结」的证据**：`WeakSet` 里记的是**该实例中 `deepFreeze` 调用成功的对象身份**。恢复路径会接管独立所有权的未冻结对象图（浅冻结的根不能证明后代冻结），而压缩替换可以**保留消息 id 却改变对象身份与内容**，所以按 id 或按 `Object.isFrozen` 走捷径都会让可变内容穿进送达适配器的请求里；只有「对精确对象完整遍历成功」才构成证明（`.agents\notes\archived\simplification\2026-09-06-agent-request-freeze-evidence.zh.md` 第 10、14、62–64 行；`packages\core\agent-loop\README.zh.md` 第 95 行）。用 `WeakSet` 而非强引用 `Set`，是为了**不延长已被压缩掉的历史的生命周期**（同上第 14、32、66 行）。

→ 附带的一条：**事件包装对象不冻结**——README 第 95 行原文"构造请求不会冻结包含消息的事件包装对象"，测试第 97–101 行正是这条（`userEvent.time` 可以改、`assistantEvent.data.stream` 可以 `push`）。

### Q4 系统提示词如何分段与遮蔽？

→ **分段**：注册表把每份贡献存成 `PromptSection`（`name` 唯一、`order` 必为有限数、`text` 可为函数、可 `interpolate: false`、可 `complete: true`）（`system-prompt/src/index.ts` 第 53–76、454–463 行）；仓库自带贡献方用 `getSectionOrder(name)` / `getContextOrder(name)` 取中央分配的位置（第 470–481 行；表在第 125–171 行）；`assemble()` 先合并 global 与 scoped 层、规范化顺序、跑 `system-prompt/assemble` waterfall，最后强制 complete 段（第 558–635 行）；渲染时按 `order` 升序拼接、丢掉空段、用 `\n\n` 连接（第 279–284 行）。

→ **遮蔽**：① scoped 段 / 变量遮蔽同名 global（第 564–576 行）；② 至多一个 `complete: true` 段成为唯一段，多个则组装失败（第 597–600、629–634 行）；③ 历史里的系统**节点**由 `project()` 归并 / 清空（`runtime-context.ts` 第 88–103 行），`in-history` 路由在序列延续时可以**追加**而不改写头部，从而保住前缀缓存（第 101–102 行；`packages\core\agent-loop\README.zh.md` 第 120 行）。

### Q5 空渲染文本意味着什么？

→ **渲染结果为空**（`renderPrompt` 返回 `''`，第 279–284 行）。此时：**(a)** 若历史里还没有系统节点，仍然 append 一条空内容节点，**只预留 surface 第 0 号节点、不产生协议消息**；**(b)** 已生效的后续系统节点被逐个替换为空内容；**(c)** 头节点按需清空。净效果是**本轮没有系统提示词，且旧提示词不再对模型可见**（`runtime-context.ts` 第 91–99 行；`packages\core\agent-loop\README.zh.md` 第 120 行；`docs\architecture.zh.md` 第 117 行）。
→ 每一种 `request/header` 的 reason 都在会话事件词表里写明，且**事件本身还带一个独立于 reason 的 `startsSeries` 标记**（`packages\core\session\src\types.ts` 第 386–395 行）。注意它是幂等的："空头节点 + 没有生效的后续节点 = 没有提示词"，重复清除与恢复会话都保持为空。

### Q6 `toolUpdate` 与提示词归并的关系是什么？

→ 可见工具 schema 变化时，**只有当已准备路由未声明 `toolUpdate` 时**才强制提示词归并（`startsSeries` 的一个或项，`agent.ts` 第 413–414 行）；同时支持工具与系统提示词更新的路由可以"追加变更后的提示词并激活新增工具"，不必改写此前消息（`packages\core\agent-loop\README.zh.md` 第 120 行；`ToolUpdate` 的两种模式见 `packages\llm\llm\src\types.ts` 第 398–407 行）。
