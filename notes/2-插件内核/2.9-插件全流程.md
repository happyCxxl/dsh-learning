## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：一个**npm 组合包插件**从写、打包、安装、激活到卸载的完整链路——它由哪些文件构成、每个字段谁来读、装完为什么有时要重启、不兼容时凭什么被拒。

**不是**：
- 不是 **harness 仓库自己加包**的契约（那是 `packages/<group>/<pkg>` 的规矩：`private: true`、`types: lib/types/index.d.ts`、仓库约束门禁，见 `docs\cookbook\adding-a-package.zh.md` 第 27、38、163–168 行）；
- 不是 **agent preset** 的玩法（preset 只在 `$DSH_HOME\.agent-presets\` 下、只对单会话生效）；
- 不是 **会话内动态插件**（`cordis_define` 只做原型，进程结束即消失）。
- **本课不解释插件之间的依赖注入与事件机制**——那是 `2.2` / `2.4`；本课只讲"包怎么进树、行怎么被准入"。

**三种「包」不要混**（本课的每一处结论都只针对第一种）：

| 形态 | 装在哪 | 生效范围 | 谁读它的声明 |
|---|---|---|---|
| **npm 组合包**（本课主角） | profile 的 `node_modules` | 该 profile 的全部会话 | Host 启动器读 `dsh.bundle`；client-modules 读 `dsh.client` |
| **harness 仓库内的包** | `<repo>\packages\...` | 整棵仓库 | 仓库门禁与 `package.json` 约定 |
| **agent preset** | `$DSH_HOME\.agent-presets\` | 单个会话 | agent-preset 加载链 |

### 0.2 现在只要记住这 5 件事

1. **一个可安装的插件 = 一个 npm 包 + 一份 patch**。包在 `package.json` 里声明 `dsh.bundle.patch` 指向 patch 文件，patch 里 `insert` 出插件行，行的 `name` **就是包名**。
2. **装 = pnpm 装包 + 把包名追加进 profile 的 `dsh.profile.bundles`**。没有 `dsh.bundle` 的包只是普通依赖，**不产生配置层**。
3. **两条读取链互不派生**：`dsh.bundle` 决定"Host 树里多哪些插件行"，`dsh.client` 决定"浏览器里加载哪个 JS bundle"。
4. **不兼容靠 peer 判定，且发生在 import 之前**：被拒的行被改写成 `disabled: true`，插件代码根本不会被 import。
5. **豁免必须是显式的**：写在 profile 自己的 `compatibility.json` 里，键是精确的 `包名@版本`，值是精确的 DSH 版本列表；文件缺失 = 零授权。

### 0.3 明确授权：这些现在不用管

- **Cordis 的 fiber / inject / effect 语义**（为什么"注册是副作用"、`ctx.effect` 的 disposer 怎么跑）——属于 `2.2` / `2.3`。本课只在"插件入口长什么样"这一层用到它们。
- **`!!js` 表达式什么时候求值**——属于 `2.6`。本课只需知道它**只能出现在行的 `config` 与 `disabled`**。
- **patch 的完整语法**（`insert` 两种分支、五个守卫、浅赋值覆盖）——`1.4` 与 `1.2` 已讲；本课只引用"整行覆盖、不是深合并"这一条。
- **HMR 监听什么、重载失败的边界**——属于 `2.7`。本课只用到它的一个结论：在线 profile 的配置变化能就地生效。

判断标准只有一条：**只要你能说清"这件事属于上面 5 件里的哪一件"，就够了。**

### 0.4 如果你是第一次读，跳过 §11 附录 A 的 Q6–Q9

**Q1–Q5 是本课主线**（打包最小结构、两条链、装完为什么重启、兼容性判据、依赖策略），第一次读就该能答。
**Q6–Q9 涉及后续编才展开的内容**（豁免的读写落点、`engines` 与 `peer` 的分工、卸载的完整失败语义、本地目录 add 的禁令），第一次读可以先跳过，回查时再看。

## 1. 最小词汇表（本课新增的 5 个词）

| 词 | 大白话 | 在源码/文件里的样子 |
|---|---|---|
| **bundle 组合包** | 一个**可安装、可分发**的 npm 包；它自带一份 patch，装进 profile 后那层 patch 就会参与组合 | `package.json` 里的 `dsh.bundle.patch` |
| **bundle 层** | 一个组合包对配置树的贡献（可能就是"多出几行插件行"） | `ProfileLayer`：`{ packageName, patchPaths, patches }` |
| **插件行** | patch 里 `insert` 出来的**一行条目**，它才是"一个被加载的插件" | `- id: xxx` + `name: <包名>` |
| **预检 preflight** | 在**真正 import 插件之前**，按 peer 声明判定"这行准不准进树" | `prepareProfileEntries` / `preflight` |
| **豁免 exemption** | 用户**明确点头**，允许某个**精确版本**的包在某个**精确运行时版本**上继续跑 | `compatibility.json` 里的 `包名@版本 → [DSH 版本]` |

> ⚠️ `profile` / `layer` / `entry` / `patch` 这 4 个词由 `notes\1-结构与装配\1.1-名词与分层.md` 定义过，本课不重复。**"组合包"是 `bundle` 的中文对照写法**，本笔记之后只用英文名 `bundle`。

## 2. 先建立画面

### 2.1 一个插件包的组装链（静态结构）

```
作者侧（你写的东西）
  <你的包>\package.json        · name / version / type / exports / files
                               · dsh.bundle.patch = "./cordis.patch.yml"   ← Host 侧声明
                               · dsh.client = { platform: "web", … }       ← 浏览器侧声明（可选）
  <你的包>\cordis.patch.yml    · 一串 patch 条目；标准形态是一处 insert
  <你的包>\lib\index.js        · Host 端插件入口（导出 name / inject / apply）
  <你的包>\lib\client.js       · 浏览器端入口（声明了 dsh.client 时必须有）
        │
        │  pnpm 装进 profile ＋ 包名被追加进 dsh.profile.bundles
        ▼
$DSH_HOME\profiles\<名字>\
  ├─ package.json              · dependencies + dsh.profile.bundles（有序）
  ├─ cordis.patch.yml          · 用户自己的 patch 层
  ├─ compatibility.json        · 精确版本豁免（可选；缺失=零授权）
  └─ node_modules\<你的包>\     · 装好的代码
        │
        │  boot：按 dsh.profile.bundles 顺序读每个包的 dsh.bundle.patch
        ▼
  配置树 ── 你的 patch 层 insert 出的行 ──► 预检（peer） ──► Loader import ──► apply(ctx)
```

**这张图的精确性说明**：`dsh.client` 那一条**不在这条链上**——它由 client-modules 的 Node 半侧**另起一条扫描**读出来，产出的是浏览器端一个懒加载 bundle。图上画在一起只是为了说明"同一个包里两份声明"。

### 2.2 大白话版：一个插件从作者到用户，中间发生了什么

**完全不用上面的术语**（来源：`docs\user\develop\basic\publish.zh.md` 第 26–116 行的教程流程与 `packages\boot\plugin-manager\README.zh.md` 第 14、92 行的实现说明；这里只做白话转述，细节留到 §4–§6）。

1. 你写一个小文件夹：一个清单（说明这是什么包、要往树里加什么）、一个"要加的内容"清单、一段代码。
2. 清单里写一句"我要往树里加这些行"，每行写清"这行的名字 = 我的包名"。
3. 用户敲一条命令，这条命令被**原样转发**给 pnpm；pnpm 把包下载/链接进 profile 的 `node_modules`。
4. 装完后 DSH 检查一遍：这个包装出来的东西里，有没有那句"我要往树里加内容"？没有 → 只当普通依赖，给一句警告；有 → 把包名**追加**到 profile 的清单里（追加在末尾）。
5. 下次启动（或者在线 profile 立刻重新组合）时，DSH 按清单顺序读每个包的"要加的内容"，把行插进树里。
6. 但在**真正加载代码之前**，DSH 先看每个包声明的"我要求宿主是什么版本"：满足 → 放行 import；不满足 → 这行被改写成"禁用"，代码**一个字都不加载**，并在 stderr 报告包名、版本、风险。
7. 用户如果不服，可以**明确点头**给某一个精确版本开一个口子（写在 profile 自己的豁免文件里），然后重试。
8. 卸载时反过来：先从清单里取消勾选、让运行中的插件退出，再让 pnpm 删包。

## 3. 结论先行：十句硬结论

**一句话流程**：写一个 npm 包 → 包在 `package.json` 里声明 `dsh.bundle.patch` → 用 `dsh plugin --profile <名字> add <包>` 装进某个 profile → profile 的 `dsh.profile.bundles` 多一项 → 下次组合时该包的 patch 成为一个层，把它的插件行插进树里。

| # | 结论 | 出处 |
|---|---|---|
| 1 | 最小可用组合包 = **3 个文件**：`package.json`（含 `name`/`version`/`type`/`main`/`files`/`dsh.bundle.patch`）、`cordis.patch.yml`、`index.js` | `docs\user\develop\basic\publish.zh.md` 第 26–44 行 |

| 3 | `dsh.bundle` 管 **Host 侧组合层**；`dsh.client` 管 **浏览器半侧**。两者都在 `package.json` 的 `dsh` 键下，**互不替代、互不派生** | `<第三方插件仓库>\docs\PLUGIN_SPEC.md` 第 32–48 行；`packages\boot\app-boot\src\profile.ts` 第 732–766 行；`packages\client\modules\src\index.ts` 第 835–848 行 |

## 4. 分发契约：Host 半侧与浏览器半侧

### 4.1 一个 Host-only 组合包的最小形态（源码：源码块 1）

先看**仓库内公开的官方模板**——它同时给出了 `package.json` 与 patch 的最小形态：

`packages\preset\agent-preset\skills\cordis-plugin-development\references\host-plugin.md` 第 9–27 行

```json
{
  "name": "@local/my-plugin",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "exports": { ".": "./index.js" },
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
```

`cordis.patch.yml`:

```yaml
- insert:
    - id: my-plugin
      name: '@local/my-plugin'
      config: {}
```

```yaml
# （第 19–21 行：小标题 "## Display metadata and icon" 与本块无关，此处省略；
#   第 28 行的空行删除，其余原样照录）
```

按块讲解：

- **`exports: { ".": "./index.js" }` 是"入口"这件事的落点**：Loader 按**裸包名** import 这个包，于是入口由 Node 的 exports 解析规则决定。所以"入口写在哪"不是 DSH 的约定，而是**包自己的 exports**；`main` 是它的旧式等价物（`docs\user\develop\basic\publish.zh.md` 第 36–43 行的教程示例用的是 `main`）。
- **`type: "module"` + `export const name` / `export function apply`** 是 ESM 形态：插件入口用 `export` 导出，才可能被解析成 `name` / `inject` / `apply`。第三方仓库的规范把入口形态写成三种（函数 / 类 / `{apply}` 对象），并要求 `export const name` 是**短名、不带 scope**（`<第三方插件仓库>\docs\PLUGIN_SPEC.md` 第 80–81 行）。
- **`dsh` 是 DSH 自定义字段**：npm 不认识它，只有 DSH 的读取链会读。
- **patch 的 `name` 写成包名**（这里是 `@local/my-plugin`）：这一句就是本课结论 2 的全部内容——Loader 拿它去解析模块，写相对源码路径在**已安装**的包里必然找不到。
- **`config: {}` 只是占位**：行级可写的能力是 `config` / `disabled` / `inject`（`<第三方插件仓库>\docs\PLUGIN_SPEC.md` 第 73 行）。
- **⚠️ 这段模板是"Host-only"形态**：它不带 `files`、不带 `engines`、`private: true`——那是"本地模板"的取舍；要**发布**的包还得满足 §4.3 的清单。

  > `dsh.client.inject` edges are informational (loading/prefetch metadata, never apply sequencing)

### 4.3 两条链的差别（对照表）

| | `dsh.bundle` | `dsh.client` |
|---|---|---|
| 谁读 | Host 启动器（`loadProfileDirectory`） | client-modules 的 Node 半侧扫描已挂载的 Loader 条目 |
| 读到什么 | patch 文件路径（字符串或有序数组） | `{ platform, inject, external, immediately }` |
| 产出 | profile 的一个**配置层**（Host 端插件行） | 浏览器端一个懒加载 bundle（`__ModuleLoader__` 工厂） |
| 出处 | `packages\boot\app-boot\src\profile.ts` 第 744–756 行 | `packages\client\modules\src\index.ts` 第 835–854 行；`packages\client\modules\src\client\manifest.ts` 第 161–179 行 |
| 关键约束 | patch 行的 `name` 必须是包名 | `platform` 只认 `'web'`，且必须有 `exports["./client"]` |

### 4.4 发布清单：硬性 vs 契约

「**硬性**」= harness 代码真的会读它、缺了就失败或降级；「**契约**」= 第三方仓库规范规定的分发纪律，分发前必须满足但不影响本机 boot。

## 5. 运行期：层怎么被读进去、行怎么被准入

### 5.1 boot 期读取链与 patch 解析（源码：源码块 3、4）

**读取链**：profile manifest 的 `dsh.profile.bundles` → 逐个 `resolveBundleDir` → 读该包 `package.json` 的 `dsh.bundle` → `bundlePatchPaths` 得到绝对路径 → `loadOverlayPatches` 得到这一层；读不到或不兼容的包**被跳过并记入 `skippedBundles`，不改变 manifest**。

**第二块：主循环怎么把每个组合包变成一层**（这一段决定了"顺序从哪来、失败怎么办"）

```ts

  binName: string,
  dir: string,
  installAnchor: string,
  options: { userLayer?: boolean } = {},
): Profile {
  const manifest = dropRetiredBundles(dir, readProfileManifest(binName, dir))
  const bundles = manifest.dsh?.profile?.bundles ?? []                          // ① 顺序的唯一来源
  const layers: ProfileLayer[] = []
  const skippedBundles: SkippedBundle[] = []
  const exemptions = bundles.length === 0 ? {} : readProfileVersionExemptions(dir)
  for (const packageName of bundles) {                                          // ② 按书写顺序遍历，不排序、不去重
    try {
      const packageDir = resolveBundleDir(binName, packageName, installAnchor, dir)
      const bundleManifest = readProfileManifest(binName, packageDir)
      const bundle = bundleManifest.dsh?.bundle
      if (bundle === undefined) {
        throw new Error(`${binName}: profile bundle ${JSON.stringify(packageName)} declares no dsh.bundle in its package.json`)
      }
      // A bundle is not a plugin row, so row admission never reads its own peers.
      const issue = evaluatePluginCompatibility(bundleManifest, exemptions)      // ③ 组合包自己的 peer 也查
      if (issue !== undefined && !issue.exempted) throw new Error(pluginCompatibilityWarning(issue))
      const patchPaths = bundlePatchPaths(packageDir, bundle)                    // ④ 有序文件列表 → 绝对路径
      const patches = patchPaths.flatMap(patchPath => loadOverlayPatches(binName, patchPath))
      layers.push({ packageName, packageDir, patchPaths, patches })              // ⑤ 顺序 = 数组顺序
    } catch (error) {
      skippedBundles.push({ packageName, reason: String(error) })                // ⑥ 只记录、不中断
    }
  }
  // …（第 761–765 行：读 profile 自己的 cordis.patch.yml 并组装返回值；见 1.2 §3.3）
}
```

按块讲解：

- **① `bundles` 从哪来**：`manifest` 来自 profile 目录的 `package.json`（`readProfileManifest`），`dsh.profile.bundles` 是数组，`?? []` 让"没写 bundles"的 profile 得到空数组。**bundle 层的顺序字面上就是数组里书写的先后**——② 的 `for … of` 没有任何排序、没有去重。
- **③ 这一行是结论 6 的第二半**：作者原文注释 *"A bundle is not a plugin row, so row admission never reads its own peers."* —— 因为组合包**不是一行**，行准入（§5.3）读不到它的 peer，所以这里**单独**查一次；不兼容且没有豁免 → **跳过该组合包**（走 ⑥），而不是让启动失败。
- **④⑤ 一个组合包可以贡献多层**：`patchPaths.flatMap(...)` 把该包声明的多个 patch 文件按声明顺序拼成一个列表；`layers.push` 的顺序就是应用顺序（后出现的覆盖先出现的，见 `1.2`）。
- **⑥ `catch` 只 `push`**：这就是"兼容性预检失败／读不到 manifest／patch 加载失败"的组合包**不贡献层但启动继续**的落点。这些原因之后由 `reportSkippedBundles` 打到 **stderr**（同文件第 118–122 行），所以 `--dump-config` 的 stdout 可能干净而 stderr 有警告。

### 5.2 兼容性判据：只有 peer（源码：源码块 5）

三个判定入口（行准入 / 组合包准入 / 安装期校验）**共用同一个纯函数**。这就是本课结论 6 的权威落点：

`packages\boot\app-boot\src\plugin-compatibility.ts` 第 51–88 行

```ts
/**
 * Check every @deepseek-ai/dsh or @deepseek-ai/dsh-* peer against the runtime.
 * @param exemptions - exact plugin name@version keys mapped to exact runtime versions.
 * @param runtimeVersion - running dsh version, defaulting to this app-boot package.
 * @returns incompatible peers and exemption status, or undefined when none are incompatible.
 */
export function evaluatePluginCompatibility(
  manifest: object,
  exemptions: Readonly<Record<string, readonly string[]>> = {},
  runtimeVersion = getDshRuntimeVersion(),                              // ① 默认取 app-boot 自己的版本
): PluginCompatibility | undefined {
  runtimeVersionOf(runtimeVersion)
  const fields = objectOf(manifest, 'Plugin manifest')
  if (!Object.hasOwn(fields, 'peerDependencies')) return undefined       // ② 不声明 peer = 不施加约束
  const dependencies = objectOf(fields.peerDependencies, 'Plugin manifest peerDependencies')
  const peers: Record<string, string> = {}
  for (const [name, range] of Object.entries(dependencies)) {
    if (typeof range !== 'string') {
      throw new Error(`Plugin manifest peerDependencies[${JSON.stringify(name)}] must be a string`)
    }
    if (name !== '@deepseek-ai/dsh' && !name.startsWith('@deepseek-ai/dsh-')) continue   // ③ 只筛这两类
    const requirement = ['workspace:^', 'workspace:~', 'workspace:*'].includes(range) ? runtimeVersion : range
    if (requirement.trim() === '' || !semver.satisfies(runtimeVersion, requirement, { includePrerelease: true })) {
      peers[name] = range                                                // ④ 只收集"不满足"的那些
    }
  }
  if (Object.keys(peers).length === 0) return undefined                  // ⑤ 全满足 = 兼容
  const name = identityField(fields, 'name')
  const version = identityField(fields, 'version')
  const key = `${name}@${version}`
  const exemptedVersions = Object.hasOwn(exemptions, key) ? exemptions[key] : undefined
  const exempted = exemptedVersions?.includes(runtimeVersion) === true   // ⑥ 豁免精确到两个版本
  return { name, version, runtimeVersion, peers, exempted }
}
// （本块省略四处：① 第 53–54 行 JSDoc 的两句——"预发布版本参与范围匹配"与"未列出的非法范围视为
//   不兼容"，其意思已并入下面的"按块讲解"；② 第 55 行 JSDoc 的 @param manifest（原文说明"读的是
//   解析后的 package.json，继承字段被忽略"）；③ 第 59 行 JSDoc 的 @throws 一句（原文说明
```

按块讲解：

- **① `runtimeVersion` 默认值**：`getDshRuntimeVersion()` 读的是 **app-boot 这个包自己的 `package.json`**（同文件第 44–49 行，注释原文说明它同时兼容源码与打包安装两种形态）。所以"运行时版本"不是某个环境变量，而是"这份代码的版本"。
- **② 没有 `peerDependencies` → 直接返回 `undefined`（兼容）**：这是结论 6 里"不声明就不施加版本约束"的确切含义。对插件作者的含义是：**你不写 peer，就没人拦你**；写了，就必须让范围覆盖运行时装的那一份。
- **③ 只筛 `@deepseek-ai/dsh` 与 `@deepseek-ai/dsh-*`**：`@deepseek-ai/cordis`、`@deepseek-ai/schemastery` 这类 peer **不参与**判定（它们不在判定链上），但它们在依赖策略里仍然重要（§6.4）。
- **④ 只有 `requirement.trim() === ''` 或 `semver.satisfies` 为假时才记录**：注意 `{ includePrerelease: true }`——**预发布版本参与范围匹配**。这就是"rc 期版本号（如 `0.2.1-alpha.1`）也能被 `^0.2.0` 一类范围算进去"的原因。
- **⑥ 豁免的精确性**：键是 `包名@版本`，值是数组，判定是 `includes(runtimeVersion) === true` ——**两个版本都必须是精确字符串**，任一维变化（插件升一个补丁号、运行时升级）都失效。
- **两个被省掉的 JSDoc 细节**（都在函数头注释里，本块为守粒度只留了要点）：① `@param manifest` 说明喂进来的是**解析后的 `package.json`**，且**继承字段会被忽略**（所以不会因为原型链上的字段误判）；② `@throws` 说明三类输入会直接抛错而不是返回"不兼容"——**peer 字段畸形**（比如 `peerDependencies` 里某个范围不是字符串）、**运行时版本非法**（不是合法 SemVer）、以及**不兼容时缺少 `name`/`version` 身份**（这就是 `identityField` 存在的理由：没有身份就没法生成豁免键）。
- **JSDoc 第 53–54 行另有两句口径**（本块省略，要点即本节结论）：**预发布版本参与范围匹配**（配合代码里的 `includePrerelease: true`）；**`workspace:^` / `workspace:~` / `workspace:*` 之外的非空非法范围视为不兼容**（配合代码里的 `semver.satisfies`）——注意后者的判据是"`satisfies` 返回假"，所以写一个语法非法的范围同样落到"不兼容"这一支，而不是抛错。
- **`engines` 完全不出现在这段代码里**：harness 侧的口径是"这些检查使用 peer 声明，而不是 `engines.dsh`"（`packages\boot\app-boot\README.zh.md` 第 52 行末句）。

按块讲解：

- **① `structuredClone`**：准入**改写**行的 `disabled`，所以必须在副本上做——否则调用方手里的组合结果会被就地污染。函数头 JSDoc 的 `@returns` 原文也写明返回的是 *"Detached rows with incompatible entries denied"*。
- **② `profile === undefined` 就整体放行**：只有"启动器自己的那份 profile 上下文"才做准入；嵌入方自己通过 `ctx.plugin` 挂的插件不走这条路（`packages\boot\app-boot\README.zh.md` 第 54 行末句）。
- **③ 豁免文件坏了不阻止启动**：读取器把"损坏"翻译成"零授权 + 警告"，所以这一行只是往 stderr 写警告。
- **④ 找不到 manifest → 不判不兼容**：作者原文（第 48 行注释）解释这是**留给 Loader 报它自己的 import 失败**。所以"模块名拼错"和"版本不兼容"是两种不同的诊断来源。
- **⑤ 判定复用同一个纯函数**：行准入、组合包准入、安装期校验三处都调 `evaluatePluginCompatibility`——**判据只有一份**，这本身就是"为什么三处结论一致"的答案。
- **⑥ 读不出来反而拒绝**：注释原话 *"Peer metadata that cannot be read or validated is refused rather than silently admitted."* —— 与④构成一个刻意的对比：**找不到**（ENOENT 一类）交给 Loader，**读到了但坏了**当场拒绝。
- **⑦⑧ 拒绝的落地方式**：把行改成**游离的** `disabled: true`（`group` 行同时把 `group` 置假），再调 `report` 把包名、版本、风险写到 stderr（`prepareProfileEntries` 里传入的 reporter 就是往 `process.stderr` 写，第 79–83 行）。**注意它改的是"启动器自己那份组合"**——patch 文件、依赖清单、组合包列表都不会被改写（`packages\boot\app-boot\README.zh.md` 第 54 行首句）。
- **为什么"插件代码永远不会被 import"**：入口是 `prepareProfilePatches`——它先在**空根**上组合出完整条目表、再交给准入、最后**只返回一个插入 patch**（同文件第 180–187 行）。所以被拒的行从来没有进入"会被 Loader import 的那棵树"。

**源码块 6 之外的两条边界**（同文件第 119–168 行，此处不整段摘录）：
- **group 行保持挂载，被拒的子行不加载**；**原生 Include 若会到达被拒绝的插件，则整体省略该 Include**，因为"它的文件不会被改写"（错误原文：*its included file … reaches an incompatible plugin, and that file is never rewritten*）。
- 这些入口**不覆盖**其他嵌入方自己挂载的插件；也不会去管"运行中插件自己改了自己的 peer 声明"——那要到下一次重新组合或重启才判定。

豁免落在 profile 目录下一个**独立文件**里，与 `package.json`、`cordis.patch.yml` **并列**。文件名的常量与原话：

`packages\boot\app-boot\src\profile-compatibility.ts` 第 9–10 行（摘录）

授权动作本身很短，但每一行都是一个"为什么必须显式"的理由：

`packages\boot\app-boot\src\profile-compatibility.ts` 第 103–130 行

```ts
/** Persist one informed grant or revocation under the compatibility file's own lock.
 * @param profileDir Profile directory; no package manifest is created or modified.
 * @param packageVersion Exact manifest package-name@version.
 * @param runtimeVersion Exact DSH version; grants must name the current runtime, revocations may name historical ones.
 * @param enabled Whether to grant rather than revoke.
 * @param acceptRisk Required true for grants after explicit acknowledgement of possible crashes or data loss.
 * @returns After the atomic write. Existing plugin instances are not reloaded by this operation.
 * @throws For invalid identities, missing consent, a stale runtime, or a file the reader rejected,
 * which the user must repair by hand because rewriting it would discard their content.
 */
export async function setProfileVersionExemption(
  profileDir: string, packageVersion: string, runtimeVersion: string, enabled: boolean, acceptRisk: boolean,
): Promise<void> {
  validatePluginVersionExemption(packageVersion, runtimeVersion)          // ① 两个身份都必须是精确版本
  if (enabled && !acceptRisk) {
    throw new Error('Incompatible plugins may cause crashes or data loss. To grant this exact-version exemption, explicitly acknowledge the risk with --accept-risk (acceptRisk: true).')
  }                                                                       // ② 没有明确点头 = 不给授权
  const current = getDshRuntimeVersion()
  if (enabled && runtimeVersion !== current) {
    throw new Error(`Cannot approve DSH ${runtimeVersion}: this application runs DSH ${current}. Use --dsh-version ${current}.`)
  }                                                                       // ③ 只能授权给"当前"运行时
  await mkdir(profileDir, { recursive: true })
  const filename = join(profileDir, PROFILE_COMPATIBILITY_FILENAME)
  await withFileLock(filename, async () => {                              // ④ 自己的锁
    const current = readProfileCompatibility(profileDir)
    if (!current.rewritable) {
      throw new Error(`${PROFILE_COMPATIBILITY_FILENAME} must be repaired before exemptions change:\n${current.warnings.join('\n')}`)
    }                                                                     // ⑤ 文件被读取器拒绝过 → 拒绝改写
    // …（第 131–140 行：把本次 runtimeVersion 并入 exemptions[packageVersion] 的集合，
    //   再用 writeFileAtomic 落盘；撤销时移除该版本，空了就删键。与本块结论无关，此处省略）
  })
}
```

按块讲解：

- **① 精确到两个版本**：`validatePluginVersionExemption`（同文件第 34–40 行）用 `lastIndexOf('@')` 拆出包名与版本，再要求版本是**规范精确 SemVer**（`isExactPluginVersion`，第 24–27 行：范围、前缀、空白一律为假）。读取端还有第二道关：键不是精确 `包名@版本`、或值不是精确 DSH 版本列表时，该条记录**被跳过并输出警告**（第 80–92 行）。
- **② `acceptRisk`**：这是"授权 = 承担风险"的代码形态。CLI 侧在保存前还会先打印风险警告（`apps\cli\src\plugin.ts` 第 40–42 行），文案与这里一致：*allowing incompatible plugin versions can break the application or corrupt data*。
- **③ 只能授权当前运行时**：想在旧运行时上"预先授权"未来版本？不行——错误文案直接给出正确用法（`Use --dsh-version <当前>`）。**撤销**是例外：`enabled === false` 时允许点名历史版本（JSDoc 原话：*revocations may name historical ones*）。
- **④⑤ 独立文件 + 自己的锁 + 可修复性检查**：豁免**不写进** `package.json`、不写进 patch、不写进组合包列表——所以"给一个不兼容插件开绿灯"这件事**不会改变你的依赖与组合**。而 ⑤ 是"用户的文件优先"：只要读取器拒过任何一条记录（`rewritable === false`），DSH 就**拒绝自动改写**并要求用户手工修复，而不是覆盖掉用户的内容。
- **"文件缺失 = 零授权"**（结论 8）：`readProfileCompatibility` 的 catch 里只有 `ENOENT` 被翻译成 `{ exemptions: {}, warnings: [], rewritable: true }`（第 67–69 行）——**空豁免、无警告、可写**。文件存在但读不了/解析不了则是"零授权 + 警告 + 不可写"（第 70–77 行）。
- **不继承**：授权绑定的是"精确包版本 + 精确运行时"，插件升级或 DSH 升级都会让键/值对不上，于是**自然失效**（`packages\boot\plugin-manager\README.zh.md` 第 65 行：*插件升级和 DSH 升级都不继承授权*）。而且它**不授权依赖构建脚本**（同文件第 63 行末句）。

### 6.1 管理器入口：pnpm 之前判定、装完再校验、最后决定要不要重启（源码：源码块 8）

管理器的 `installBundle`（Web 插件页 / `plugin_manager` 工具的 `install_bundle` 走这里）把"**不下载**"和"**不激活**"分开处理：不兼容的判定尽量前置，装完再校验一次。收尾这一段是全流程里信息量最大的地方：

`packages\boot\plugin-manager\src\index.ts` 第 548–566 行（同函数前段的注册表循环与错误分类见本节末段）

- **④ 顺手解析一遍 patch**：既提前暴露坏 patch（启动时才炸就太晚了），也是"这个 bundle 的行到底有哪些"的来源（`bundleRows` 用的是同一条链，见第 756–761 行）。

### 6.2 包名怎么被追加进 `dsh.profile.bundles`（源码：源码块 9）

命令行通道（`dsh plugin --profile <名字> add <包>`）的收尾只有一个函数：`reconcile`。它同时处理"删掉已不在依赖里的 bundle"和"把本次新增、且声明了 `dsh.bundle` 的包名追加进列表"：

`packages\boot\plugin-manager\src\operations.ts` 第 88–113 行

```ts
/** Reconcile package removals and newly installed bundles without re-enabling retained dependencies. */
async function reconcile(before: ProfileManifest, dir: string, anchor: string, options: PackageOperationOptions): Promise<void> {
  const after = readProfileManifest('dsh', dir)                            // ① pnpm 之后的清单
  const dependencies = Object.keys(after.dependencies ?? {})
  const beforeDeps = new Set(Object.keys(before.dependencies ?? {}))
  const previous = after.dsh?.profile?.bundles ?? []
  const bundles = previous.filter((name) => {                              // ② 清理：已不在依赖里的名字被删掉
    if (!beforeDeps.has(name) && !dependencies.includes(name)) return true
    return dependencies.includes(name) && bundleManifest(name, dir, anchor) !== undefined
  })
  for (const name of dependencies) {
    if (beforeDeps.has(name)) continue                                     // ③ 装之前就有的依赖不再处理
    const metadata = bundleManifest(name, dir, anchor)
    if (metadata?.dsh?.bundle === undefined) {
      options.onOutput?.(`dsh: warning: ${name} declares no dsh.bundle — installed as a plain dependency, not a profile layer\n`, 'stderr')
      continue                                                             // ④ 不是组合包：警告 + 不产生层
    }
    for (const file of bundlePatchPaths(resolveBundleDir('dsh', name, anchor, dir), metadata.dsh.bundle)) loadOverlayPatches('dsh', file)
    if (!bundles.includes(name)) {
      bundles.push(name)                                                   // ⑤ 末尾追加
    }
  }
  if (JSON.stringify(previous) === JSON.stringify(bundles)) return          // ⑥ 没变化就不写文件
  after.dsh = { ...after.dsh, profile: { ...after.dsh?.profile, bundles } }
  await saveManifest(dir, after)                                           // ⑦ 原子改写 package.json
}
// （本块为完整函数，未删节：它是一个独立小函数，整段拿来才自解释；
//   第 105 行的长行是"解析该 bundle 的 patch 以防坏 patch 混进清单"，
//   与 §6.1 的 ④ 同一目的）
```

按块讲解：

- **① `after` 与 `before` 的区别**：`before` 是 pnpm 运行前由调用方保存的清单快照（失败恢复也用它），`after` 是 pnpm 成功后重新读的。**pnpm 只负责依赖表，`dsh.profile.bundles` 由 DSH 自己维护**——这是本课结论 4 的落点。
- **② 过滤的三个条件**：既不在旧依赖、也不在新依赖里 → 保留（那是用户手工选的、pnpm 不持有的名字，例如已下线的组合包）；在依赖里 → 必须仍然是一个 bundle（`bundleManifest` 不是 `undefined`）。所以**删包之后名字会自动消失**，这就是 CLI `remove` "同时移除依赖和对应的层"的机制（`docs\user\develop\basic\publish.zh.md` 第 116 行）。
- **③ 只看"本次新增"**：`beforeDeps.has(name)` 就跳过——所以 `add` 一个已存在的依赖**不会**重排 `bundles`，也不会顺手把历史遗留的名字重新启用。函数名里的 *"without re-enabling retained dependencies"* 说的就是这条纪律。
- **④ 没有 `dsh.bundle` → 警告 + 只当依赖**：警告原文可在源码里逐字看到：`declares no dsh.bundle — installed as a plain dependency, not a profile layer`。**这就是"装了个库却什么都没发生"的标准解释**。
- **⑤ 追加在末尾**：顺序即优先级（后者覆盖前者，见 `1.2`），所以"新装的 bundle 排在最后"意味着**它的 patch 会覆盖先前的层**——这也是 README 里"开启组合包会追加到列表末尾，可能改变配置优先级"那句话的机制。
- **⑥ 没变化就不落盘**：避免无意义地改写文件（也让"装了个普通依赖"这一步不产生任何文件副作用）。
- **⑦ 原子改写**：`saveManifest` 用 `writeFileAtomic`（同文件第 84–86 行），所以中途崩溃不会留下半个 JSON。

### 6.3 卸载：顺序本身就是语义（源码：源码块 10）

卸载没有"尽力而为"的余地——顺序错了就会留一个"清单里没有、进程里还在跑"的悬空状态。所以 `removeBundle` 把检查与动作串成一条链：

`packages\boot\plugin-manager\src\index.ts` 第 616–645 行

```ts

  removeBundle(name: string): Promise<ChangeResult> {

      const installed = await this.configure(async () => {
        const bundle = (await this.listBundles()).find(item => item.name === name)
        if (bundle === undefined || !bundle.removable) throw new ManagementFailure('not-removable')   // ① 列表校验
        if (this.ownerContext.get('hmr') === undefined && (this.profile.startedBundles.includes(name)
          || (bundle.error === undefined && this.bundleRows(name).some(row => [...this.ctx.loader.entries()]
            .some(entry => entry.options.id === row.id && entry.fiber !== undefined))))) {
          throw new ManagementFailure('stop-profile')                                                // ② 无 HMR 且仍在跑

        const contributions = bundle.error === undefined ? this.bundleRows(name) : []
        if (bundle.enabled) {
          await this.selectBundle(name, false)                                                       // ③ 先取消选中
          result.warnings = await this.reload()                                                      // ④ 再让运行中的行退出

        throw new Error(result.packageResult.output)
      }
      await this.configure(() => this.refreshPackages())                                              // ⑧ 发布解析表
    }, { stage: 'remove', target: name }, 'remove')
```

按块讲解：

- **①②⑤ 三道守卫，三个不同的错误码**：`not-removable`（列表说不让卸）、`stop-profile`（**没有 HMR** 且这个组合包是本次启动用的、或它的行还活着）、`bundle-in-use`（取消选中并 reload 之后仍有 entry 持有它的行 id + 模块名）。README 把这三个码与"任一步失败都不继续"写在同一条里（`packages\boot\plugin-manager\README.zh.md` 第 153 行）。
- **③④ 先取消选中、再 reload**：`selectBundle(name, false)` 改的是 `dsh.profile.bundles`，`reload()` 让运行中的行退出——**先把状态改对，再让进程跟上**。
- **⑦ pnpm 在最后**：卸载的哲学与安装相反——安装是"先 pnpm 再收尾"，卸载是"先摘干净再删代码"。这样最坏情况下留下的是"多一个没用的依赖"，而不是"清单里有、代码没了"。
- **⑧ `refreshPackages`**：发布 runtime resolution（解析表），让后续 import 不再解析到已删的包。
- **`configure` / `change` 是同一个"写锁 + 结果包装"骨架**：`change` 用 profile 的 `package.json` 文件锁串行化所有包操作（第 800–818 行），并在其中决定 `application` 字段——**`this.ownerContext.get('hmr') !== undefined ? 'applied' : 'restart-required'`（第 804 行）**，这就是结论 5 里"在线 vs 启动型"判据的代码落点。
- **⚠️ 一个必须摆明的口径差异**：第三方仓库的规范写的是更保守的**绝对**口径——"bundle 层只在 boot 时读取，热重载只覆盖用户 patch 层，不含 bundle 层"，因此"装完必须重启"（`<第三方插件仓库>\docs\PLUGIN_SPEC.md` 第 9 行、第 120 行）。而 harness 侧的实现与文档是：HMR 监视 profile manifest 与 patch 文件后**重新组合所有层**（`apps\cli\README.zh.md` 第 37 行），管理器因此对在线 profile 报 `applied`。两者在"**此前没装过的新组合包**"这一格上不一致；**以源码为准**（`packages\boot\plugin-manager\src\index.ts` 第 804 行 + 第 573–578 行），教学与实务上按 §6.4 的三分法处理最稳。
- **`dsh plugin --profile <名字> remove <包名>`** 走的是另一条路（CLI → `runPluginCommand` → pnpm → `reconcile` 的 ② 过滤），效果是"依赖与层一起消失"（`docs\user\develop\basic\publish.zh.md` 第 116 行）。

### 6.4 「装完要不要重启」的三分法

| 情形 | 结果 | 依据 |
|---|---|---|
| **覆盖/升级一个已安装的包** | **必然重启**：`installBundle` 一旦发现该依赖名此前已存在就直接返回 `restart-required` | `packages\boot\plugin-manager\src\index.ts` 第 573–575 行；`...\references\host-plugin.md` 第 70 行（*replacing an installed package requires restart to load a fresh JavaScript module generation*） |
| **只读 patch 的启动型 profile（无 HMR）** | **必须重启**：`change()` 的 `application` 直接是 `restart-required`；运行中的行保留到重启 | `packages\boot\plugin-manager\src\index.ts` 第 804 行；`packages\boot\plugin-manager\README.zh.md` 第 14 行 |
| **此前没装过的新组合包 + 在线 profile（有 HMR）** | **可以就地激活**：`application: applied`，`refreshPackages` + `reload` 让新行挂上 | `packages\boot\plugin-manager\src\index.ts` 第 576–577 行；`packages\boot\plugin-manager\README.zh.md` 第 67 行 |

**随附模板里只有 `web` 实时重载**，其他随附模板只在启动时应用 patch（`packages\boot\app-boot\README.zh.md` 第 50 行末句）——所以"到底要不要重启"的第一判据是"这个 profile 有没有 HMR"，第二判据才是"装的是什么"。

### 6.5 依赖策略：为什么插件不该 import harness 内部包

三形态，选一并在 README 说明（`<第三方插件仓库>\docs\PLUGIN_SPEC.md` 第 50–56 行）：

1. **peer 复用形态**：需要 harness 公开包（如 `@deepseek-ai/dsh-tools` 的 `defineTool`）时，把 cordis / dsh-tools / dsh-llm 声明为 `peerDependencies`。
2. **零 harness import 形态**：只用 Node 内置模块 + `ctx` 注入的服务。
3. **Config 形态**：只要 `@deepseek-ai/schemastery`。

**机制（harness 侧可验证）**：DSH 在初始化 profile 时写入的 `pnpm-workspace.yaml` 是 `nodeLinker: hoisted` + `autoInstallPeers: false`，源码注释写明理由：

`packages\boot\app-boot\src\profile.ts` 第 236–245 行

```ts
// The hoisted linker gives out-of-tree plugins a flat node_modules whose
// missing peers (cordis and friends) use the runtime resolution, so every plugin shares the
// installation's single cordis instance instead of a duplicate. pnpm ≥10
// reads its settings from pnpm-workspace.yaml, not .npmrc.
const PROFILE_PNPM_WORKSPACE = `packages:
  - .

nodeLinker: hoisted
autoInstallPeers: false
`
// （这段常量由 initProfile 写下：`if (!existsSync(workspacePath)) writeFileSync(workspacePath, PROFILE_PNPM_WORKSPACE)`，
//   同文件第 271–272 行；已有文件永不覆盖）
```

按块讲解：

- **为什么要 `hoisted`**：树外插件本身可能在任意位置，扁平化的 `node_modules` 让它们能按 Node 的常规祖先查找看到同一批依赖。
- **为什么要 `autoInstallPeers: false`**：让**缺失的 peer 落到 runtime resolution**（运行时装的那一份），而不是给每个插件新装一份。
- **代价（结论 10 的另一面）**：进程内若真的出现两份 cordis / dsh-tools，**Symbol key 不匹配会静默崩溃**，所以 peer 警告属预期，**不要为了消警告改写 `dependencies`**（`<第三方插件仓库>\docs\PLUGIN_SPEC.md` 第 52 行）。
- **实证写法**：`dsh-peek` 的 Host 入口把这条纪律写成了文件头注释——只用 Node 内置模块 + ctx 服务，不 import 任何 harness 包（`<第三方插件仓库>\plugins\dsh-peek\lib\index.js` 第 1–7 行）。

**边界要分清**：「不该 import harness 内部包」≠「不能 import 任何 harness 包」。官方 cookbook 的工具示例就 `import { defineTool } from '@deepseek-ai/dsh-tools'`（`docs\cookbook\adding-a-tool.zh.md` 第 12 行），`defineTool` 定义在 `packages\core\tools\src\schema.ts` 第 554 行、从 `packages\core\tools\src\index.ts` 第 67 行再导出。真正要防的是：依赖具体实现而不是能力 seam（`docs\cordis-primer.zh.md` 第 9–11 行「其他插件通过 key 查找服务，而非导入具体实现」），以及改动/替换宿主核心与自带预设（`PLUGIN_SPEC.md` 第 14 行、第 110 行）。

### 9.3 一个真实的打包缺陷（`files` 白名单与读取路径不一致）

## 11. 附录 A 关键问题与答案

> ✅ 九道题**全部给出明确答案**，不留空、不写"待补充"。Q1–Q5 是第一次读就该能答的；**Q6–Q9 涉及后续编才会展开的细节**，**第一次读请跳过**，回查时再看。

### Q1 一个插件包的最小结构是什么？`package.json` 必需哪些字段？

**答案（教程级最小，3 个文件）**：`package.json` + `cordis.patch.yml` + `index.js`。
`package.json` 的最小内容：`name`、`version`、`type: "module"`、`main`（或 `exports["."]`）、`files`、`dsh.bundle.patch`。
出处：`docs\user\develop\basic\publish.zh.md` 第 26–44 行；官方模板给出等价形态并额外要求 `exports["."]`（`...\references\host-plugin.md` 第 9–18 行）。

**按「缺了会怎样」排序**：

- `name`：patch 行的 `name` 必须等于它，Loader 按裸包名解析（`docs\user\develop\basic\publish.zh.md` 第 56 行；`packages\boot\app-boot\src\profile.ts` 第 744–746 行）。
- `dsh.bundle.patch`：缺了就不是组合包——管理器报 `not-bundle`（`packages\boot\plugin-manager\src\index.ts` 第 557 行），命令行只给一句警告并装成普通依赖（`packages\boot\plugin-manager\src\operations.ts` 第 101–103 行）。
- 入口（`main` 或 `exports["."]`）+ `type: "module"`：决定 Loader import 到哪个文件、以什么模块语义导出 `apply`/`name`/`inject`（`...\references\host-plugin.md` 第 57–64 行）。
- 声明了 `dsh.client` 时，`exports["./client"]` 是**硬要求**：缺失直接抛错（`packages\client\modules\src\index.ts` 第 841–848 行）。
- `version`：只有存在未满足 peer 时才被强制（`packages\boot\app-boot\src\plugin-compatibility.ts` 第 31–37 行），但安装结果与豁免键都依赖它（`packages\boot\plugin-manager\src\index.ts` 第 561 行）。
- `files`：发布/打包用（`<第三方插件仓库>\docs\PLUGIN_SPEC.md` 第 41、46 行），**链接目录安装不过滤**（`...\references\host-plugin.md` 第 35 行）；但 §9.3 的实录说明：`files` 漏了运行时真正读的文件，打包后就是 `ENOENT`。

第三方仓库还额外要求 `exports` 三件套（`.`、`./cordis.patch.yml`、`./package.json`）、`engines`、`scripts.prepublishOnly`、`publishConfig.access`、`keywords`/`license`/`repository`（`<第三方插件仓库>\docs\PLUGIN_SPEC.md` 第 40–48 行），并给出每个插件的目录骨架（同文件第 17–30 行）。

### Q2 `dsh.bundle` 与 `dsh.client` 的区别？

**答案：一个是 Host 侧的组合层声明，一个是浏览器半侧的加载声明；前者决定「树里多哪些插件行」，后者决定「页面里加载哪个 JS bundle」，二者互不派生。**

- `dsh.bundle.patch` 由 Host 启动器读：可以是字符串或有序文件数组，读成 profile 的一个配置层（`packages\boot\app-boot\src\profile.ts` 第 58–64 行、第 744–756 行）。缺它就没有层。
- `dsh.client` 由 client-modules 的 Node 半侧扫描读：只认 `platform: 'web'`，并要求 `exports["./client"]`（`packages\client\modules\src\index.ts` 第 835–848 行）；字段形态由 `parseDshClient` 校验（`packages\client\modules\src\client\manifest.ts` 第 161–179 行）。
- 语义差别：`dsh.client.inject` 是信息性的（不排序、不参与激活），真正的激活顺序由 Cordis fiber 的 service inject 决定（`packages\client\ui-workspace\src\client\index.ts` 第 88–95 行；`<第三方插件仓库>\docs\PLUGIN_SPEC.md` 第 96 行）；`dsh.client.external` 只给基础设施/transport，feature 插件禁止互相 external（同文件第 97 行）。
- 一个包可以只有 `dsh.bundle`（Host-only，模板见 `...\references\host-plugin.md` 第 9–18 行），也可以两者都有（`<第三方插件仓库>\plugins\dsh-peek\package.json` 第 32–40 行）。**不能**用 `dsh.client` 代替 `dsh.bundle`：后者才让包成为可安装、可选择的 profile 层。

### Q3 安装与卸载流程是什么？为什么装完要重启？

**安装（两条入口，同一条 pnpm 路）**：`dsh plugin --profile <名字> add <spec>` 把参数转发给 profile 目录里的 pnpm（`apps\cli\README.zh.md` 第 18 行；`apps\cli\src\plugin.ts` 第 92–97 行），pnpm 成功后收尾校验并 `reconcile`：把声明了 `dsh.bundle` 的新包名**追加**进 `dsh.profile.bundles`，原子改写 profile 的 `package.json`（`packages\boot\plugin-manager\src\operations.ts` 第 88–113 行）；失败或装到没有 `dsh.bundle` 的包就恢复快照文件（`packages\boot\plugin-manager\README.zh.md` 第 148 行）。管理器入口则在 pnpm **之前**判定不兼容并拒绝下载（`packages\boot\plugin-manager\README.zh.md` 第 63 行）。

**卸载**：管理器 `removeBundle` 按「列表校验 → 无 HMR 且仍在跑则 `stop-profile` → 取消选中 → reload → 占用检查（`bundle-in-use`）→ `pnpm remove` → 发布解析表」执行，任一步失败即停且不重新启用（`packages\boot\plugin-manager\src\index.ts` 第 617–645 行；`packages\boot\plugin-manager\README.zh.md` 第 153 行）；命令行的 `remove` 同时移除依赖与层（`docs\user\develop\basic\publish.zh.md` 第 116 行）。

**为什么装完要重启——分三种情形，不要一句「必须重启」了事**：

1. **覆盖/升级一个已安装的包 → 必须重启**。`installBundle` 一旦发现该依赖名此前已存在就直接返回 `restart-required`（`packages\boot\plugin-manager\src\index.ts` 第 573–575 行），因为要让进程加载新一份 JavaScript 模块（`...\references\host-plugin.md` 第 70 行：「replacing an installed package requires restart to load a fresh JavaScript module generation」）。
2. **启动型（无 HMR）profile → 必须重启**。组合包层由 `loadProfileDirectory` 在启动与每次重新组合时读取（`packages\boot\app-boot\README.zh.md` 第 54 行），没有 HMR 时运行中的组合保留到重启（`packages\boot\plugin-manager\README.zh.md` 第 14 行）；应用侧同样以 `hmr` 服务是否存在来决定 `applied` 还是 `restart-required`（`packages\boot\plugin-manager\src\index.ts` 第 804 行）。随附模板里只有 `web` 实时重载，其他只在启动时应用 patch（`packages\boot\app-boot\README.zh.md` 第 50 行）。
3. **此前没装过的新组合包 + 在线 profile → 可以就地激活**：`application: applied`（`packages\boot\plugin-manager\README.zh.md` 第 67 行；`...\references\host-plugin.md` 第 70 行）。

**口径差异要摆明**：`<第三方插件仓库>\docs\PLUGIN_SPEC.md` 第 9 行与第 120 行给出的是更保守的绝对口径——「bundle 层只在 boot 时读取，热重载只覆盖用户 patch 层，不含 bundle 层」，因此「装完必须重启」。而 harness 侧文档写的是 HMR 监视 profile manifest 与 patch 文件后**重新组合所有层**（`apps\cli\README.zh.md` 第 37 行），管理器也据此对在线 profile 报 `applied`。两者在「新装包」这一格上不一致；**以源码为准**（§6.3 末段），不确定就重启一次，代价远小于排查悬空状态。

### Q4 兼容性预检凭什么判定不兼容？豁免为什么必须显式？

**判据只有一条链**：读插件 `package.json` 的 `peerDependencies` → 只保留 `@deepseek-ai/dsh` 与 `@deepseek-ai/dsh-*` → `workspace:^`/`~`/`*` 折算成当前运行时版本 → `semver.satisfies(..., { includePrerelease: true })` → 任一不满足即「不兼容」，并带上未满足的 peer 映射（`packages\boot\app-boot\src\plugin-compatibility.ts` 第 61–88 行）。判定前会先按包名/相对路径/裸包名把 manifest 找出来；**找不到 manifest 不算不兼容**，留给 Loader 报它自己的 import 失败（`packages\boot\app-boot\src\compatibility-preflight.ts` 第 29–61 行、第 100–104 行）。`engines` 不参与判定（`packages\boot\app-boot\README.zh.md` 第 52 行）。

判定生效的位置与后果：行 → 改写成游离 `disabled: true`；group → 递归；原生 Include → 整体省略（`compatibility-preflight.ts` 第 114–167 行）；组合包 → 跳过并记入 `skippedBundles`（`packages\boot\app-boot\src\profile.ts` 第 747–758 行）；安装 → 管理器直接拒绝，命令行恢复快照并打印精确的 `allow-version` 命令（`packages\boot\plugin-manager\src\index.ts` 第 558–559 行；`apps\cli\src\plugin.ts` 第 98–101 行）。关键性质：预检发生在挂载根 Include 时与每次重新组合时，所以**被拒绝的插件永远不会 import 它的模块**（`packages\boot\app-boot\README.zh.md` 第 54 行）。

**豁免为什么必须显式**（四条，互相独立）：

1. **代码里不存在默许路径**：豁免只从 profile 的 `compatibility.json` 读，文件缺失即零授权（`packages\boot\app-boot\src\profile-compatibility.ts` 第 62–70 行）；它被刻意放在独立文件里，写豁免不触碰依赖清单、组合包列表或 patch（`packages\boot\app-boot\README.zh.md` 第 56 行）。规范侧同样说明「权限不写进 manifest 或 Cordis patch」（`<第三方插件仓库>\docs\PLUGIN_SPEC.md` 第 9 行注释、第 15 行）。
2. **精确到两个版本**：键必须是 `包名@精确版本`，值必须是精确 DSH 版本列表；范围、前缀、空白一律拒绝（`profile-compatibility.ts` 第 24–27 行、第 80–92 行）。实测复现：一个 `1.0.0` 的豁免对 `1.0.1` 无效、对另一个运行时版本也无效（§9.2）。
3. **必须显式承担风险**：`setProfileVersionExemption` 在 `enabled && !acceptRisk` 时抛错，理由文案是「可能导致崩溃或数据丢失」（`profile-compatibility.ts` 第 117–119 行）；只能授权给当前运行时（第 120–123 行）；CLI 在保存前先打印风险警告（`apps\cli\src\plugin.ts` 第 40–42 行）；诊断文案明确要求 `dsh plugin allow-version` 或插件管理器（`plugin-compatibility.ts` 第 99–101 行）。
4. **授权不继承、不越界**：插件升级与 DSH 升级都不继承授权（`packages\boot\plugin-manager\README.zh.md` 第 65 行）；豁免只影响准入，**不授权依赖构建脚本**（同文件第 63 行）；通过管理器授权属于需要 `danger-full-access` 或逐次批准的操作（同文件第 31 行）。

### Q5 插件为什么不应 import harness 内部包（依赖策略）？

**答案分两层，别说过头**：

**不该做的**：import harness 的**内部实现**（未导出的 `src`、宿主核心、自带预设）。理由与证据：

- 依赖方向：插件之间靠 `ctx.<key>` 取服务，而不是导入具体实现；配置因此才能替换提供方（`docs\cordis-primer.zh.md` 第 9–11 行；`docs\architecture.zh.md` 第 11–13 行「不存在需要打补丁的特权内核」）。
- 组合层纪律：永远不改 deployment 内置的预设与宿主核心，预设/插件不得放松自身沙箱边界（`<第三方插件仓库>\docs\PLUGIN_SPEC.md` 第 14 行、第 110 行）。
- 进程内单实例约束：如果有两份 cordis/dsh-tools，Symbol key 分裂会**静默崩溃**（`PLUGIN_SPEC.md` 第 52 行）；harness 用 hoisted linker + `autoInstallPeers: false` 让缺失 peer 落到运行时的同一份实例（`packages\boot\app-boot\src\profile.ts` 第 236–245 行；解析层规则见 `packages\boot\app-boot\README.zh.md` 第 134 行）。因此「自己装一份 cordis」是本条最危险的做法。
- 实证写法：`dsh-peek` 的 Host 入口明确「只用 Node 内置模块 + ctx 服务，不 import 任何 harness 包——避免进程内出现第二份 cordis / dsh-tools 导致 Symbol 分裂」（`<第三方插件仓库>\plugins\dsh-peek\lib\index.js` 第 1–7 行）。

**可以做的**：声明**公开** harness 包为 peer 并 import 它。`defineTool` 就是官方示例：`import { defineTool } from '@deepseek-ai/dsh-tools'`（`docs\cookbook\adding-a-tool.zh.md` 第 12 行），定义处 `packages\core\tools\src\schema.ts` 第 554 行、再导出 `packages\core\tools\src\index.ts` 第 67 行。三种形态择一并写进 README：peer 复用 / 零 harness import / 仅 schemastery 的 Config 形态（`PLUGIN_SPEC.md` 第 50–56 行）；peer 版本范围必须覆盖 harness 自带版本，且需要共享实例的 dsh 包要同时进 `peerDependencies` 与 `devDependencies`（`PLUGIN_SPEC.md` 第 52 行；`docs\user\develop\basic\publish.zh.md` 第 103 行）。

**一句话判据**：要的是**能力**（服务 key、公开包）就声明 peer 或零 import；要的是**某个实现的内部细节**，那就不是依赖策略问题，而是你该改用事件/扩展点（`docs\cookbook\adding-a-tool.zh.md` 第 61 行：尽量不要把部署策略内建到工具里，改用 `tools/pre-execute` 等扩展点）。

### Q6 豁免文件长什么样、什么时候被读？

**答案：它是一个只有"键值映射"的 JSON，位于 profile 目录下、与 `package.json` 并列；每次组合（含每次 HMR 重新组合）与每次安装校验都会被读。**

结构示意（**取值是示例**，不代表任何实际部署）：

```json
{
  "<某个包名>@<精确版本>": ["<精确的 DSH 运行时版本>"]
}
```

- **谁读**：`loadProfileDirectory` 在遍历组合包前读一次（`packages\boot\app-boot\src\profile.ts` 第 742 行），把它交给 `evaluatePluginCompatibility`；行准入里在 `preflight` 开头再读一次（`packages\boot\app-boot\src\compatibility-preflight.ts` 第 97 行）；安装期校验也读（`operations.ts` 第 479 行、`index.ts` 第 558 行）。
- **读取器**：`readProfileCompatibility`（`profile-compatibility.ts` 第 62–93 行）—— 缺失 → 空豁免且可写；损坏 → 零授权 + 警告 + **不可写**；逐条记录校验，被拒的记录跳过、其余仍生效。
- **谁写**：`setProfileVersionExemption`（第 113–140 行），入口是 `dsh plugin allow-version` / `revoke-version`（`apps\cli\src\plugin.ts` 第 17–62 行）或插件管理器的 `set_version_exemption`。
- **写不进 manifest / patch**：这一点由常量注释原文保证——*"Independent profile metadata; neither package manifests nor Cordis patches carry grants."*（第 9 行）。

### Q7 `engines` 和 `peerDependencies` 在这一课里各管什么？

**答案：只有 `peerDependencies` 参与兼容性判定；`engines` 是"约定口径，运行时不被强制"。**

- 判定链里**根本没有 `engines`**（§5.2 源码块 5 全文可查）；harness 文档也写明"这些检查使用 peer 声明，而不是 `engines.dsh`，也不是防范恶意包代码的沙箱"（`packages\boot\app-boot\README.zh.md` 第 52 行）。
- 第三方规范把 `engines` 的默认值写成 `"^22.19.0 || >=24.0.0"`，并明确标注"该字段是约定口径，运行时不被强制"（`<第三方插件仓库>\docs\PLUGIN_SPEC.md` 第 42 行）；插件真实需要更高下限时（例如 `node:sqlite`）要写真实下限并在 README 说明理由。
- 所以：**Node 版本不够** → 由 Node/加载器自己报错；**DSH 版本不够** → 由预检拒绝（并给豁免通道）。两条链互不代替。

### Q8 卸载失败会留下什么？

**答案：停在失败的那一步，保留已完成的改动，且不会重新启用组合包。**

- `removeBundle` 的顺序与守卫见 §6.3；README 的失败行为表把它写成一句话：*"卸载：任一步失败 → 停在失败步骤，保留已完成的改动和待重试删除的依赖，报告卸载失败。不重新启用组合包。"*（`packages\boot\plugin-manager\README.zh.md` 第 151 行）
- 具体残留：失败的删除**可能留下部分依赖改动**；诊断日志保留在 profile 的 `.plugin-manager\logs\` 目录（同文件第 137 行）。
- 恢复粒度：恢复只会重写 `package.json` 与 `pnpm-lock.yaml` 这两份快照文件；用户写的 patch、应用数据、日志、pnpm 已下载的文件都保持原样（同文件第 155 行）。

### Q9 为什么禁止"add 本地目录"？

**答案：因为 pnpm 会把本地目录 link 成 junction，源目录一改名/移动就成了悬空链接，boot 解析 bundle 时直接失败、整机起不来。**

- 规范原文给出的机制与症状：`dsh plugin add` 把参数原样转发给 pnpm，本地目录走 pnpm link（Windows 上即 junction）→ 源目录改名/移动后成悬空链接 → boot 报 `cannot resolve profile bundle`、整机起不来；并注记"本仓库实战踩过"，以及"DSH 自己在 boot 期也会把 bundle 依赖以 junction 链进 profile node_modules，同类陷阱"（`<第三方插件仓库>\docs\PLUGIN_SPEC.md` 第 75 行、第 119 行）。
- 允许的三通道：npm 包名 / `<tgz 路径>` / `github:user/repo#sha`（同文件第 75 行）。
- **与教程的冲突**：`docs\user\develop\basic\publish.zh.md` 第 80 行仍以 `add ./hello-plugin` 为示例。本笔记按规范方裁定（§7 已写明判定依据，标注为**判断**）。
- 附带一条清理办法（规范原文）：清理悬空链接用 `cmd /c rmdir <链接路径>` —— **只删链接，不碰目标**。
