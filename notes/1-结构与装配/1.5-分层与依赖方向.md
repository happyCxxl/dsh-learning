## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：回答三个问题——**仓库分了几层、层与层之间谁依赖谁、谁在守着这条方向不许被破坏**。
**不是**：单个包的功能（那是各包自己的 README）、`patch` 的语法（那是 `1.2` / `1.4`）、cordis 的注入机制（那是第二编）。

### 0.2 现在只要记住这 4 件事

1. **四类目录 = 四个层**：`vendor/*` 是框架层，`packages/*/*` 是能力层，`apps/*` 是产品装配层，`native/*` 是原生层；方向基本是"上层依赖下层"。
2. **"apps 在 packages 之上"不是口号，是写进 YAML 注释、并用脚本强制的**：`apps/*` 被称为 "Product assemblies over the package tier"，`apps/cli` 独占 `dsh` bin。
3. **依赖方向由四类门禁脚本分段强制**，不是一个脚本一句话：协议/range、编译器 face、依赖区段、应用入口各管一段。
4. **存在两条被刻意允许的"向上"边**（组合包/SDK 客户端 → 产品入口），**恰好两条**，其余 `packages/*/*` 都没有边指向 `apps/*`。

### 0.3 明确授权：这些现在不用管

本课会出现一批你暂时不懂的词（aggregate、face、seam、typert、experimental、OPTIONAL_BUNDLES、`pnpm pack` 的 range 替换…）。**授权：现在不用管它们怎么实现。**

判断标准只有一条：**只要你能说清"这个词属于上面 4 件事里的哪一件"，就够了。** 其余展开位置见附录 B。

### 0.4 本课依赖 1.1 / 1.2 的词汇

`profile` / `bundle` / `patch` / 条目 `entry` / 层 `layer` / `$DSH_HOME` 已由 `1.1-名词与分层.md` 与 `1.2-装配顺序.md` 定义，本课不重复定义，只在新含义上补充。

## 1. 最小词汇表（本课新增的 8 个词）

| 词 | 大白话 | 在源码/路径里的样子 |
|---|---|---|
| **tier 层** | 目录树里"同一高度的一批东西"，例如"能力层" | `vendor/` / `packages/<group>/<pkg>/` / `apps/<app>/` / `native/` |
| **group 分组** | `packages/` 下面那层**纯容器目录**，自己不是包 | `packages/session/`、`packages/api/`（里面没有 `package.json`） |
| **门禁 gate** | 一个会在 CI 里跑、失败就红的检查 | `scripts/check-workspace-constraints.ts` 等 |
| **workspace 协议** | 声明"这个依赖指的是本仓库里的成员，不是网站上的包" | 依赖值写成 `workspace:*` / `workspace:~` |
| **peer / dependency** | 两种依赖区段：前者要求"共享同一个实例"，后者允许"各装一份" | `package.json` 里的 `peerDependencies` / `dependencies` |
| **aggregate** | 编译器侧把一大堆子项目汇到一起的那个"总配置" | `tsconfig.host.json`、`tsconfig.client.json` |
| **face 面** | 同一个包分给两侧（Host / Client）中的哪一侧 | 包目录下同时有 `tsconfig.host.json` 与 `tsconfig.client.json` 就叫"拆分包" |
| **seam 接缝** | 只声明"要有什么能力"、不声明"用哪个实现"的那一层 | `packages/session/session-persistence`（抽象）vs `-jsonl`（实现） |

> ⚠️ `aggregate` / `face` 的机制在 `docs/development.zh.md` 与 `2.6` 展开；`seam` 在 `2.8`、`4.4` 展开。本课只用到上表这个程度。

## 2. 先建立画面

### 2.1 四层与方向（静态结构）

```
                    谁决定"装什么"
  apps/            │  apps/cli      @deepseek-ai/dsh          ← 独占 `dsh` bin、按 profile 选 bundle
  产品装配层        │  apps/web      @deepseek-ai/dsh-web-frontend
   Product          │  apps/desktop  @deepseek-ai/dsh-desktop         (private, 不发布 npm)
   assemblies       │  apps/desktop-host @deepseek-ai/dsh-desktop-host (private)
                    │
                    │  ▲ 装配方向：apps 决定用哪些能力、以什么形态启动
                    │  │
  packages/*/*     │  packages/<group>/<pkg>/    ← group 是纯容器，包必须恰好在这一层
  能力层            │  例：packages/api/gateway、packages/session/session-persistence-jsonl
   package tier     │
                    │  ▲ 能力方向：packages 用框架提供的原语贡献能力
                    │  │
  vendor/*         │  @deepseek-ai/cordis 等 9 个包   ← 源码 vendored，不走 npm
  框架层            │
                    │
  native/*         │  native/system/packages/*       ← 平台原语（Landlock / flock），被 packages 依赖
  原生层            │
```

**精确性说明（必须补的一句）**：图中的箭头画的是**主要依赖方向**，不是"每一对目录之间都存在依赖"。真实的边是逐包声明的，且存在 §2.2 与 §7 里列出的**两条例外**（组合包 / SDK 客户端指向 `apps/*`）。

### 2.2 门禁怎么工作（动态过程）

```
  一次 CI 运行
      │
      ├─ ① scripts/check-workspace-constraints.ts
      │     成员 manifest 从哪来 ── readWorkspaceManifests()
      │     查：层次形状 / workspace 协议 / experimental 隔离 / 编译器 face
      │
      ├─ ② scripts/verify-package-dependencies.ts
      │     读源码 import 事实（用 typescript 解析 AST）
      │     查：每个依赖**区段**是否与事实一致
      │
      ├─ ③ scripts/verify-application-entrypoints.ts
      │     查：包 bin / shebang 源码 / 根脚本 是否都走 apps/cli/src/bin.ts
      │
      └─ ④ scripts/verify-default-product-isolation.ts
            从 apps/cli、apps/web、python/sdk-runtime 三个入口做可达性扫描
            查：默认产品闭包里有没有 experimental 包
      │
      ▼
  全部登记在 scripts/run-gates.ts 的两个 gate 列表里；任一失败 → process.exitCode = 1
```

### 2.3 大白话版：一个新包想"往上爬"会发生什么

**完全不用上面的术语**，先建立画面。来源：`scripts/verify-application-entrypoints.ts` 第 1–5 行的文件头注释、`scripts/check-workspace-constraints.ts` 第 572–582 行的 JSDoc，以及 `.agents/notes/implemented/architecture/2026-08-22-single-dsh-application-launcher.zh.md`；这里只做白话转述。

1. 有人写了个新包，放在 `packages/工具/新包/`，里面放好了清单文件。
2. 他给这个包加了一个"可以直接运行"的入口（清单里写 `bin`）。
3. CI 第一步就红了：**除了 `apps/cli` 的 `dsh` 和那个 build-only 打包器，任何包 bin 都被拒绝**——报错原文是 "package bin bypasses the dsh launcher; applications use apps/cli profiles"。
4. 他改成"写个脚本直接 `node packages/工具/新包/src/main.ts`"，并且在根清单里加了一条 `demo:新东西`。
5. CI 又红了：**根清单里每个 `demo:` 开头的脚本都必须被显式分类**，没分类就是 "demo launcher has no explicit dsh or in-process classification"。
6. 他去看别人的做法，发现正确姿势是：**让 `dsh` 按一个 profile 启动**，自己的包作为插件被 patch 挂进那棵树。
7. 于是他不再抢一个可执行文件，而是交出一份 patch 与一个 profile 需要的清单项——方向就回到"产品装配层决定装什么、能力层只管能被装"。

## 3. 结论先行（四层各自是什么）

1. 仓库的 workspace 成员由 `pnpm-workspace.yaml` 的 `packages:` 列表声明，共 **5 类 glob + 3 个单点成员**：`vendor/*`、`packages/*/*`、`native/system`、`native/system/packages/*`、`apps/*`，以及 `benchmarks`、`website`、`python/sdk-runtime`（`pnpm-workspace.yaml` 第 1–15 行）。按这些 glob 逐个数本仓库（`5badb150` 干净检出）得 **341 份成员 manifest**：`packages/*/*` 319 个、`apps/*` 4 个、`vendor/*` 9 个、`native/system/packages/*` 5 个，加 `native/system`、`benchmarks`、`website`、`python/sdk-runtime` 4 个单点（合计 341）。
2. 四类目录的分层职责可以一句话概括：**vendor 是被仓库完全拥有的框架层（源码 vendored，不用 npm 依赖）；packages 是能力层（插件与库）；apps 是产品装配层（profile 启动器与产品入口）；native 是与 harness 消费方一起开发的原生层**（`vendor/README.md` 第 3 行；`pnpm-workspace.yaml` 第 8 行；`native/README.zh.md` 第 5 行）。
3. 「apps 在 packages 之上」在仓库里是**写进 YAML 注释的显式约定**：`packages/*/*` 是 "package tier"，`apps/*` 是它之上的 "Product assemblies"，并且 `apps/cli` 拥有 `dsh` bin（`pnpm-workspace.yaml` 第 3、8–9 行）。
4. 依赖方向**不是靠一个脚本一句话强制的，而是四类门禁各管一段**：`check-workspace-constraints.ts`（协议与 range）、`project-reference-faces.ts`（编译器 face 隔离）、`verify-package-dependencies.ts`（依赖区段归属）、`verify-application-entrypoints.ts`（应用入口唯一化），外加 `verify-default-product-isolation.ts`（默认产品不得含 experimental）。全部在 `run-gates.ts` 里被登记为 CI gate（`scripts/run-gates.ts` 第 344–356、767–782 行）。
5. 依赖方向**存在被刻意允许的「向上」边**，且是少数、具名的，实测**恰好两条**：`@deepseek-ai/dsh-web-app`（`packages/bundle/web-app`）在 `dependencies` 里依赖 `@deepseek-ai/dsh-web-frontend`（即 `apps/web`，第 171 行），`@deepseek-ai/dsh-sdk-client` 在 `dependencies` 里依赖 `@deepseek-ai/dsh`（即 `apps/cli`，第 29 行）。两条都是「产品组合包 / SDK 客户端 → 产品入口」的组装边，不是能力层反向依赖装配层。

   > **与旧版结论的差异（如实标注）**：本笔记早先版本在第 1 节第 5 条同时写了"这两条向上边"与"除这两条外，`packages/*/*` 中没有任何包依赖 apps 成员"，两句话本身互相矛盾。本次用一个只读脚本重扫全部 `packages/*/*` 的四个依赖区段，确认**就是这两条**，因此这里统一改写为"恰好两条"。

6. 依赖方向的**编译器侧**由 Host / Client 两个 aggregate 表达：`tsconfig.host.json` 与 `tsconfig.client.json` 各自构成独立 `ts.Program`，普通包只登记进其中一个 aggregate（`docs/development.zh.md` 第 63、73–79 行；`tsconfig.json` 第 11–14 行）。
7. `vendor` 与 `native/system` 的依赖 range 是**唯一的两种 `workspace:~`**；所有 `@deepseek-ai/dsh*` 引用必须是 `workspace:*`；其它 workspace 成员只能是 `workspace:` 协议（`scripts/check-workspace-constraints.ts` 第 583–599 行）。

## 4. 四类目录各自是什么

| 层 | 声明位置 | 职责（带出处） |
|---|---|---|
| `vendor/*` | `pnpm-workspace.yaml` 第 2 行 | Cordis 框架与其基础库的**源码 vendored 副本**，因为「harness 要完全拥有自己的框架层（可审计、可打补丁、可钉版本）」，并且全部改用 `@deepseek-ai` scope，包内引用使用 `workspace:~`（`vendor/README.md` 第 3、5 行）。9 个成员与上游版本/commit 见 `vendor/README.md` 第 13–23 行的 manifest 表。 |
| `packages/*/*` | `pnpm-workspace.yaml` 第 3 行 | YAML 注释称其为 **package tier**。层次形状被硬性规定为 `packages/<group>/<pkg>`：group 是不含 `package.json` 的容器，不得再深一层（`scripts/check-workspace-constraints.ts` 第 504–528 行；`docs/cookbook/adding-a-package.zh.md` 第 25 行）。 |
| `apps/*` | `pnpm-workspace.yaml` 第 8–9 行 | YAML 注释原文：*Product assemblies over the package tier; `apps/cli` owns the `dsh` bin.* 实际四个成员：`apps/cli`（`@deepseek-ai/dsh`，非 private，bin 为 `lib/bin.js`）、`apps/web`（`@deepseek-ai/dsh-web-frontend`）、`apps/desktop`（`@deepseek-ai/dsh-desktop`，private）、`apps/desktop-host`（`@deepseek-ai/dsh-desktop-host`，private）。 |
| `native/*` | `pnpm-workspace.yaml` 第 6–7 行 | 维护在仓库内的原生源码与公开包；`native/system/` 负责 Landlock 启动器、POSIX flock 绑定、平台包与发布流程，并与 harness 消费方共用根锁文件（`native/README.zh.md` 第 5、9 行）。YAML 注释解释它为何放在一起：*"The Landlock launcher is developed with its harness consumers but keeps its native build and publication scripts under `native/system`."*（第 4–5 行）。 |
| `benchmarks` / `website` / `python/sdk-runtime` | `pnpm-workspace.yaml` 第 11–15 行 | 私有 benchmark 依赖所有者、文档站点、以及单 exe 构建的部署根（「纯依赖清单，其闭包就是 exe 打包与 Python 运行时分发的内容」）。 |

**发布成员与 private 的区分**由 `scripts/check-workspace-constraints.ts` 第 58–61 行的两个正则决定：`standardReleaseMemberDirectory` 匹配 `packages/<非experimental>/<pkg>`、`apps/<非 desktop/desktop-host>`、`vendor/<dir>`；`desktopApplicationDirectory` 单列 `apps/desktop`，因为它是 electron-builder 组装的安装型应用、不发布到 npm（第 60–61 行）。

**这条划分是有机械后果的**：`checkWorkspaceManifest()` 对 release member 要求「不得 `private: true`」且必须声明 `publishConfig.access: "public"` 与仓库 `repository` 字段，对既不是 release member、也不是 experimental 目录的成员则要求「必须 `private: true`」（`scripts/check-workspace-constraints.ts` 第 414–437 行）。

## 5. 机制一：workspace 成员是怎么被枚举的

### 5.1 源码对照 ①：声明清单就是那份 YAML

`pnpm-workspace.yaml` 第 1–15 行

```yaml
packages:
  - vendor/*
  - packages/*/*
  # The Landlock launcher is developed with its harness consumers but keeps
  # its native build and publication scripts under native/system.
  - native/system
  - native/system/packages/*
  # Product assemblies over the package tier; apps/cli owns the `dsh` bin.
  - apps/*
  # Private package owning repository-level benchmark dependencies.
  - benchmarks
  - website
  # Deploy root of the single-exe build: a pure dependency manifest whose
  # closure is what the exe bundles and what the Python runtime distributes.
  - python/sdk-runtime
```

**做什么**：这是 pnpm 的 workspace 成员声明，**同时**也是本仓库"分层"的第一手文档。

**与哪个知识点相关**：§3 第 1、3 条；§4 全表。

**为什么这么写**：三条注释都在解释**为什么这一项和别的项不同**——`native/system` 之所以放在根 workspace，是因为它与消费方同批开发；`apps/*` 之所以单独一条，是因为它是 package tier **之上**的产品装配层；`python/sdk-runtime` 不是代码包而是"打包闭包的根"。把理由写在声明处，读的人不必去翻设计文档。

**变量来源与相邻守卫**：`overrides:`（第 17–20 行）把两个 vendored 包映射成 `link:vendor/*`，`allowBuilds:`（第 31–55 行）显式审查每个带安装脚本的依赖——它们都不是"分层"知识点，此处不展开。

### 5.2 实测：按 glob 数出来的成员数

按上面 5 类 glob + 3 个单点在 `<repo>`（`5badb150` 干净检出）逐个数目录：

| glob / 单点 | 数量 |
|---|---|
| `packages/*/*` | 319 |
| `apps/*` | 4 |
| `vendor/*` | 9 |
| `native/system/packages/*` | 5 |
| `native/system` / `benchmarks` / `website` / `python/sdk-runtime` | 各 1 |
| **合计** | **341** |

命令形态（只读，不改仓库里的任何东西；`cwd` 敏感——必须在 `<repo>` 根目录跑，因为 `pnpm-workspace.yaml` 是相对它解析的）：

```powershell
# cwd: <repo>
$r = (Get-Location).Path
(Get-ChildItem "$r\packages" -Directory | ForEach-Object {
   Get-ChildItem $_.FullName -Directory -ErrorAction SilentlyContinue
} | Where-Object { Test-Path (Join-Path $_.FullName 'package.json') }).Count
```

**副作用**：无（只列目录）。**输出落在哪**：控制台。**典型报错**：如果在别的目录跑，`Get-ChildItem` 会报"路径不存在"——这是 cwd 错了，不是仓库的问题。

## 6. 机制二：apps 为什么在 packages 之上

### 6.1 (a) 产品装配 vs 能力贡献

运行中的 `dsh` 是一棵插件树，产品的每一部分都是插件（`.learning/notes/1-结构与装配/1.1-名词与分层.md` 转述 `docs/architecture.zh.md`）。`packages/*/*` 里的包是**被挂载的能力**；`apps/cli` 持有唯一的 `dsh` bin，并通过**具名 profile** 决定挂哪些组合包（`docs/architecture.zh.md` 第 45 行；`pnpm-workspace.yaml` 第 8 行）。所以 apps 位于上方：**它决定「装什么」，packages 决定「能装什么」**。

### 6.2 (b) 组合包再往上叠一层

`packages/bundle/*`（`base`、`web-app`、`headless`、`sdk-app`、`sdk-minimal`、`acp-app`）是通过 `cordis.patch.yml` 描述 profile 层的分发单元。`dsh-web-app` 的 patch 里逐条 `name:` 列出它挂载的包，包括 `@deepseek-ai/dsh-api-session-controller`（第 122 行）、`@deepseek-ai/dsh-host-webserver`（第 179 行）、`@deepseek-ai/dsh-client-connection`（第 230 行）、`@deepseek-ai/dsh-client-modules`（第 223 行）；基础层 `dsh-base` 则挂 `@deepseek-ai/dsh-api-gateway`（作为 `typert-gateway` 行，第 52–53 行）与 `@deepseek-ai/dsh-session-persistence-jsonl`（第 130–133 行）。

### 6.3 源码对照 ②：组合包用 manifest 同时够到"产品入口"和"能力包"

`packages/bundle/web-app/package.json` 第 53、171–175 行

```json
  "dependencies": {
    // …（第 54–170 行：web-app 挂载的全部 web/api/host/client 能力包，与本知识点无关，此处省略）
    "@deepseek-ai/dsh-tool-workflow": "workspace:*",
    "@deepseek-ai/dsh-web-frontend": "workspace:*",
    "@deepseek-ai/dsh-workflow-ptc": "workspace:*",
    "@deepseek-ai/dsh-workspace": "workspace:*",
    "@deepseek-ai/dsh-workspace-changes": "workspace:*",
    "@deepseek-ai/schemastery": "workspace:~",
  }
```

**做什么**：声明这个组合包在运行期需要哪些包。

**与哪个知识点相关**：§3 第 5 条（两条向上边之一）；§6.2（组合包是"依赖 + patch"的载体）。

/**
 * Enforce `packages/<group>/<pkg>`: groups are open-named containers without a
 * package.json, and packages may be neither flat nor more deeply nested.
 */
function checkHierarchyShape(): string[] {
  const errors: string[] = []
  const packagesRoot = join(root, 'packages')            // root = resolve(import.meta.dirname, '..')，第 21 行
  for (const group of readdirSync(packagesRoot, { withFileTypes: true })) {
    if (!group.isDirectory()) continue                   // ← 守卫：文件跳过
    const groupRel = join('packages', group.name)
    if (existsSync(join(packagesRoot, group.name, 'package.json'))) {
      errors.push(`${groupRel}: a group dir must not contain a package.json — packages live at packages/<group>/<pkg>, not directly under packages/`)
      continue                                           // ← 守卫：group 自己是包就到此为止，不再往下扫
    }
    for (const pkg of readdirSync(join(packagesRoot, group.name), { withFileTypes: true })) {
      if (!pkg.isDirectory()) continue                   // ← 守卫：文件跳过
      if (localArtifactDirs.has(pkg.name)) continue      // ← 守卫：node_modules 等本地产物不算成员（localArtifactDirs，第 62 行）
      const pkgRel = join(groupRel, pkg.name)
      if (!existsSync(join(packagesRoot, group.name, pkg.name, 'package.json'))) {
        errors.push(`${pkgRel}: expected a package here (no package.json found) — the hierarchy is exactly packages/<group>/<pkg>, no deeper nesting`)
      }
    }
  }
  return errors
}

### 7.3 源码对照 ④：协议与 range——`workspace:*` 与 `workspace:~` 的分工

`scripts/check-workspace-constraints.ts` 第 572–601 行

```ts
/**
 * Require exact DSH ranges, tilde vendor/native ranges, and the workspace protocol elsewhere.
 *
 * A hand-written range says nothing about the version the workspace actually
 * carries, and `pnpm pack` leaves it alone: `^0.0.1` published from version
 * `0.0.2` names a version that does not exist. The protocol makes pack
 * substitute the member's real version. Dependency targets determine the range,
 * regardless of the consuming manifest's name or directory.
 * @param manifests - every workspace manifest.
 * @returns One error per workspace reference with a disallowed range.
 */
export function checkWorkspaceProtocol(manifests: readonly WorkspaceManifest[]): string[] {
  const members = new Set(manifests.map(entry => entry.manifest.name).filter(name => name !== undefined))
  const vendors = new Set(manifests.filter(entry => entry.dir.startsWith('vendor/')
    || entry.dir === 'native/system' || entry.dir.startsWith('native/system/packages/')).map(entry => entry.manifest.name))
  const errors: string[] = []
  for (const { dir, manifest } of manifests) {
    for (const section of dependencySections) {
      for (const [name, range] of Object.entries(manifest[section] ?? {})) {
        if (!members.has(name)) continue          // ← 守卫：只审"指向本仓库成员"的依赖，第三方包不管
        const expected = name === '@deepseek-ai/dsh' || name.startsWith('@deepseek-ai/dsh-')
          ? 'workspace:*'
          : vendors.has(name) ? 'workspace:~' : undefined
        if (expected !== undefined ? range === expected : range.startsWith('workspace:')) continue
        errors.push(`${manifest.name ?? dir}: ${section}.${name} must use ${expected ?? 'the workspace: protocol'}, got ${range}`)
      }
    }
  }
  return errors
}
```

**做什么**：三层循环遍历「每个成员 × 4 个依赖区段 × 每个依赖项」，对指向本仓库成员的依赖判定它"应该是什么 range"。

**与哪个知识点相关**：§3 第 7 条；§1 词汇表的 `workspace 协议`。

**为什么这么写**：JSDoc 给了**真正的理由**，而且不是"风格统一"这种空话——*"`pnpm pack` leaves it alone: `^0.0.1` published from version `0.0.2` names a version that does not exist."* 手写 range 一旦被 `pnpm pack` 原样写进发布产物，就会指向一个不存在的版本。`workspace:` 协议的作用是让打包时**替换成成员的真实版本**，所以它比"写对版本号"更可靠。三段式判定的分工也有理由：`@deepseek-ai/dsh*` 是产品族、要求**精确**（`*`）；vendor / native 是"允许同一 minor 内打补丁"的框架与原生层、要求 `~`；其余成员只要带 `workspace:` 前缀即可。

**它依赖的变量从哪来**：`manifests` 不是这个函数自己读的，而是 `main()` 第 605 行 `readWorkspaceManifests(root)` 的返回值（该函数定义在第 150 行起，扫描 glob 见第 23–29 行的 `workspaceGlobs`）；`dependencySections` 是第 538 行的四元组常量；`vendors` 集合在函数内部按 `dir` 前缀现算，**不看包名**——所以一个 vendored 包即使改了名也仍被算作 vendor。

  facts: PackageDependencyFacts,
): ReadonlyMap<string, ExpectedPackageDependency> {

  const add = (name: string, sectionName: ExpectedPackageDependency['section'], origin: string): void => {

  }

**做什么**：先人工种下"默认产品入口"（所有 `apps/*` 与 `python/sdk-runtime`），再把 profile 的 bundle 列表与 Web 组合的 patch **真叠一遍**得到有效条目，逐条访问；访问到 experimental 就记一次失败，否则把新包压进队列继续扩散。

**与哪个知识点相关**：§7.1 表格里 `verify-default-product-isolation.ts` 那一行；§3 第 4 条；§4 的 private / experimental 划分。

**为什么这么写**：文件头注释（第 1–5 行）把范围写死了——*"Keep experimental packages outside default installations, runtime imports, and shipped compositions."* 注意它查的是**三类**：安装闭包（依赖区段）、运行期 import（源码 specifier）、**shipped composition**（真 patch 叠出来的组合树）。第三类是别的门禁做不到的：只有把 patch 真叠一遍，才知道"默认 Web 形态到底挂了哪些行"。同理，第 262 行还要额外断言"叠出来的 Web profile 里至少有 1 个插件"——防的是"组合过程被改坏、叠出空树却没人报错"。

**它依赖的变量从哪来**：`packages` / `directories` 在第 66–76 行从 5 类 glob 的 manifest 建索引；`selection` 来自 `profilePackages()` 解析 `PROFILE_SOURCE`（第 86–88 行）——所以**默认产品的定义源是 `packages/boot/app-boot/src/profile.ts`，不是任何人的本机 profile**；`PROFILE_SOURCE`、`PRESET_PATTERN`、`EXPERIMENTAL_PREFIX`、`RUNTIME_SECTIONS` 都是第 23–28 行的模块级常量。

## 8. 机制四：`verify-application-entrypoints` 拒绝什么

### 8.1 三类拒绝，三个函数

三个函数合起来构成 `applicationEntrypointViolations`（第 181–187 行）：

1. **`manifestBinViolations`（第 100–117 行）**：扫描 `apps/*/package.json` 与 `packages/*/*/package.json`。任何声明了 `bin` 的包必须命中「bin 允许清单」且内容完全一致，否则报 *"package bin bypasses the dsh launcher; applications use apps/cli profiles"*。允许清单只有两项：`apps/cli/package.json` 的 `{ dsh: 'lib/bin.js' }`，与 `packages/experimental/webworker-packer/package.json` 的 `{ 'dsh-pack-vfs-image': './bin.js' }`（第 27–30 行）——后者是 build-only 打包器。
2. **`executableSourceViolations`（第 119–130 行）**：扫描根与 `apps/**`、`packages/**`、`python/sdk-runtime/*.mjs` 的 ts/js/mjs/cjs（排除 `node_modules`、`lib`、`dist`、`coverage`，第 63–84 行）。任何以 `#!` 开头的文件必须在 `EXECUTABLE_SOURCE_ALLOWLIST`（第 33–49 行）里有一个**显式角色字符串**，否则报 *"executable source has no application/build/test classification"*。该清单里唯一的应用启动器是 `apps/cli/src/bin.ts`（角色：`supported dsh application launcher`），其余全是 build-only 包装器、test-only driver、test-only model server 或 `python/sdk-runtime/runtime-bootstrap.mjs`（角色：`private packaging-only runtime dispatcher`）。
3. **`rootLauncherViolations`（第 140–174 行）**：根 `package.json` 的脚本中，**任何 `demo:` 开头**的脚本都必须在 `ROOT_LAUNCHER_POLICIES` 里被分类；`start:web` 必须是 `dsh-direct`，`dev:web` 必须是 `dsh-wrapper`（第 56–61 行）。分类为 `dsh-direct` 的命令必须包含字面量 `apps/cli/src/bin.ts`（第 132–134、155 行），并且**不得**匹配 `packages/<group>/<pkg>/(src|lib)/...` 的包入口正则（第 136–138、156 行）；`dsh-wrapper` 指向的包装文件必须存在，且其源码同样必须引用 `apps/cli/src/bin.ts`、不得直启包入口（第 159–171 行）。

### 8.2 源码对照 ⑧：白名单是"角色表"而不是"布尔豁免"

`scripts/verify-application-entrypoints.ts` 第 26–49 行（两张允许清单，逐字）

```ts
/** Public product launcher plus the build-only WebWorker packer. */
const MANIFEST_BIN_ALLOWLIST = new Map<string, ManifestBin>([
  ['apps/cli/package.json', { dsh: 'lib/bin.js' }],
  ['packages/experimental/webworker-packer/package.json', { 'dsh-pack-vfs-image': './bin.js' }],
])

/** Every JavaScript executable in an application or packaging workspace has one explicit role. */
const EXECUTABLE_SOURCE_ALLOWLIST = new Map<string, string>([
  ['apps/cli/src/bin.ts', 'supported dsh application launcher'],
  ['apps/desktop/scripts/logged-notarytool.mjs', 'build-only notarization logging wrapper'],
  ['packages/context/time-context/tests/fixtures/driver.ts', 'test-only subprocess driver'],
  ['packages/experimental/webworker-packer/bin.js', 'build-only wrapper'],
  ['packages/experimental/webworker-packer/src/bin.ts', 'build-only implementation'],
  ['packages/sdk/client/tests/fake-runtime.ts', 'test-only SDK runtime peer'],
  ['packages/session/session-telemetry-otel/tests/fixtures/driver.ts', 'test-only subprocess driver'],
  ['packages/shell/tool-pwsh/tests/fixtures/loader/driver.ts', 'test-only subprocess driver'],
  ['packages/subagent/subagent-acp/tests/fixtures/loader/driver.ts', 'test-only subprocess driver'],
  ['packages/subagent/subagent-claude-code/tests/fixtures/loader/driver.ts', 'test-only subprocess driver'],
  ['packages/subagent/subagent-codex/tests/fixtures/loader/driver.ts', 'test-only subprocess driver'],
  ['packages/subagent/subagent-dsh-sdk/tests/fixtures/loader/driver.ts', 'test-only subprocess driver'],
  ['packages/test-support/loader-smoke/tests/fixtures/headless-driver.ts', 'test-only subprocess driver'],
  ['packages/test-support/llm-mock-server/src/bin.ts', 'test-only model server'],
  ['python/sdk-runtime/runtime-bootstrap.mjs', 'private packaging-only runtime dispatcher'],

```

**做什么**：两张"路径 → 身份"的映射表。左边是对照项，右边（或值）是**必须写下来的角色字符串**。

**与哪个知识点相关**：§8.1 第 1、2 类；§3 第 4 条（"应用入口唯一化"是四类门禁之一）。

**为什么这么写**：文件头注释（第 1–5 行）的原文是答案——*"Enforce dsh profiles as the only supported Node application launcher. Vendor CLIs, build tools, and test tools are explicit classifications rather than implicit holes."* 关键词是 **explicit classifications rather than implicit holes**。这就是为什么第二张表的**值**是字符串而不是 `true`：豁免一个可执行文件时，你必须写出它**是什么**（build-only？test-only？打包专用？），审阅者一眼能看出分类是否合理。而只要值可以是任意字符串，机械枚举就无法"自动通过"——新增 shebang、新增包 bin、新增 `demo:` 脚本都会失败，直到有人写下它的角色。

**变量来源与相邻守卫**：两张表都是模块级常量，被 §8.1 的三个函数直接用；`LauncherPolicy` 接口（第 21–24 行）定义 `ROOT_LAUNCHER_POLICIES`（第 56–61 行）的形状；第 92–98 行的 `normalizedBin()` 负责把 `bin` 的字符串/对象两种写法归一化成可比较的 JSON，所以"对象键顺序不同"不会被误判为违规。

### 8.3 为什么要求所有 Node 应用入口都经 `dsh` launcher

三条理由，均有出处：

- **避免第二套生命周期。** 带完整 `cordis.yml` 的专用应用 bin 会在 profile 启动之外形成第二套生命周期：安装到 profile 的插件无法到达它，行为会与 `dsh-base` 偏离，SDK 调用方还要学任意 argv（`.agents/notes/implemented/architecture/2026-08-22-single-dsh-application-launcher.zh.md` 第 9 行）。
- **让 profile 真正负责插件安装、环境加载、关闭与测试。** 被考虑的替代方案之一是「保留直启 bin，只声明推荐 profile」，拒绝理由原文：只要受支持的可执行文件仍然绕过 profile，文档就无法让 profile 真正负责这些职责（同上第 67–69 行；另见被拒绝的「保留转发兼容 bin」第 69 行）。
- **把绕行改成显式分类，而不是隐式漏洞。** 即 §8.2 那段文件头注释。这解释了为什么允许清单是**字符串角色表**而不是布尔豁免。

文档侧一致：`docs/architecture.zh.md` 第 47 行把 vendored CLI、build/test-only 可执行文件、进程内直接挂载插件与私有浏览器 WebWorker 预览都划出「Harness 应用启动器」的范围，并说明该脚本把每个包 bin、可执行源码、根 demo 与根脚本 `start:web`/`dev:web` 归入显式类别。

## 9. 机制五：编译器侧的分层（Host / Client 两个 aggregate）

### 9.1 结论

- 仓库用**相互隔离的 Host 与 Client aggregate**；普通包只登记进其中一个 aggregate，只有 `host/webserver`、`compaction/compaction`、`typert/registry` 三个包被两个 aggregate 同时引用，作为共享 leaf（`docs/development.zh.md` 第 63 行）。
- solution 根 `tsconfig.json` 是 `files: []` + 引用两个 aggregate，永不作为程序种子，因为把两个 aggregate 展平进一个 `ts.Program` 会撞上 `Context` 声明合并冲突（`tsconfig.json` 第 5–14 行；`docs/development.zh.md` 第 73–77 行）。
- **拆分 Host/Client tsconfig 的包只有六个**：`api/remotes`、`api/gateway`、`api/session-controller`、`api/workspace-controller`、`client/connection`、`session-query/session-log-export`（`docs/development.zh.md` 第 79 行）。它们同时携带 `tsconfig.host.json` 与 `tsconfig.client.json`，因此自动落入 §7.1 中 `project-reference-faces.ts` 的管辖（第 65–71 行）。
- `tsconfig.base.json` 的 `paths` 是**源码解析门面**，永远不加 `include`/`files`（`tsconfig.base.json` 第 3–4 行），故 `docs/development.zh.md` 第 75–76 行的两条纪律成立。其中 `./apps/...` 的别名只有两个，都是 CLI 的启动器身份：`@deepseek-ai/dsh/profile-boot` → `apps/cli/src/profile-boot.ts`、`@deepseek-ai/dsh/lib/bin.js` → `apps/cli/src/bin.ts`（`tsconfig.base.json` 第 59–60 行）。

### 9.2 两个 aggregate 各自覆盖什么

`tsconfig.host.json` 第 484–489 行

```json
    { "path": "./packages/lsp/lsp" },
    { "path": "./packages/lsp/lsp-stdio" },
    { "path": "./packages/lsp/tool-lsp" },
    { "path": "./apps/cli" },
    { "path": "./apps/desktop-host" },
    { "path": "./apps/desktop/tsconfig.host.json" }
  ]
}
```

> 注：这段是 `references` 数组的**尾部**；第 484–486 行是同一数组里最后几个 `packages/*` 成员，留在片段里是为了让读者看到"数组项长什么样、`apps/*` 项和包项并列"，从而确认 `apps/*` 是**照常登记进 aggregate 的普通成员**，不是特殊分支。

`tsconfig.client.json` 第 1–14 行

```json
{
  // Client-side typecheck aggregate: packages/client tests and top-level Client benchmarks.
  // Split from the host aggregate because both sides merge cordis Context
  // under the same keys (sessions, loader) with different services; shared
  // leaves (session/llm/tools/...) build once and are referenced by
  // both programs through each client package's own references.
  "extends": "./tsconfig.base.client.json",
  "compilerOptions": {
    "noEmit": true,
    "rewriteRelativeImportExtensions": false,
    // Tests execute under vitest on node (e2e files spawn processes); browser
    // purity of package src is each package's own tsconfig plus
    // scripts/client-bundle-purity.spec.ts.
    "types": ["node"]
```

**做什么**：`tsconfig.host.json` 的 `references` 数组把 `apps/cli`、`apps/desktop-host`、`apps/desktop/tsconfig.host.json` 登记成 Host aggregate 的成员（写在各 aggregate 的 `references` 里，而不是写进某个"包过滤表"）；`tsconfig.client.json` 则通过 `extends: ./tsconfig.base.client.json` 拿到浏览器编译设置。

**与哪个知识点相关**：§9.1；§7.4（face 门禁的输入正是这两个文件）。

**为什么这么写**：`tsconfig.client.json` 的注释把"为什么必须拆"的原文给了出来——*"both sides merge cordis Context under the same keys (sessions, loader) with different services"*。也就是说冲突不在模块解析层，而在**声明合并**层：同一个 `Context` 接口被两侧用不同服务合并，塞进一个 program 就报冲突。所以拆分的对象是 **program**，不是包；这也解释了 §9.1 里"solution 根永不作为种子"这条纪律。

**它依赖的变量从哪来**：`tsconfig.host.json` 是手写的 solution 配置（`references` 长列表，第 213–490 行区间），`tsconfig.client.json` 由 `tsconfig.base.client.json` 提供编译器选项；`apps/desktop` 因为要分两侧检查，同时提供 `tsconfig.host.json` 与 `tsconfig.client.json` 两个 leaf，而别的 app 只提供一个。

## 11. 一条真实链路的包级依赖方向

链路：**浏览器请求 → Host HTTP 载体 → 认证/RPC 桥 → 会话控制器 → 会话日志 → 投影缓存 → 存储**。逐段出处：

| 段 | 包 | 出处 |
|---|---|---|

### ① `packages/*/*`、`apps/*`、`vendor/*`、`native/*` 四类各自的分层职责？

**答案：**

- **`vendor/*` = 被仓库完全拥有的框架层。** 它不是 npm 依赖，而是 Cordis 与其基础库的**源码副本**，理由原文：「so that the harness fully owns its framework layer (auditable, patchable, pinned)」；全部改用 `@deepseek-ai` scope，内部引用用 `workspace:~`，上游 MIT LICENSE 保留在各包目录（`vendor/README.md` 第 3、5 行）。9 个成员的目录名、npm 名、上游名与 commit 见 `vendor/README.md` 第 13–23 行。本地修改必须逐条记进第 29–59 行的 "Local modifications" 日志，pre-commit 钩子强制这一条（`scripts/check-vendor-manifest.sh` 第 9–16 行）。
- **`packages/*/*` = 能力层（package tier）。** 它是插件与库的所在地，形状被硬性钉为 `packages/<group>/<pkg>`，group 只是纯容器（无 `package.json`、无源文件）（`scripts/check-workspace-constraints.ts` 第 504–528 行；`docs/cookbook/adding-a-package.zh.md` 第 25 行）。其中 `packages/client/*` 另有浏览器侧纪律，其 manifest 与非 client 包一起被 `verify-client-packages.ts` 扫描（第 12–13 行）。`packages/experimental/*` 归一套独立策略：包名必须带 `@deepseek-ai/dsh-experimental-` 前缀（第 57 行），且不得进入官方运行时依赖（第 550–570 行）与默认产品可达闭包（`verify-default-product-isolation.ts` 第 110–112、139–140 行）。
- **`apps/*` = 产品装配层。** YAML 注释把它定义为 package tier 之上的 "Product assemblies"，并指定 `apps/cli` 拥有 `dsh` bin（`pnpm-workspace.yaml` 第 8–9 行）。它承载的是**产品形态与启动器**，而不是可复用能力：受支持的 Node 应用通过具名 profile（`web`、`headless`、`sdk`、`sdk-minimal`、`acp`）启动（`docs/architecture.zh.md` 第 45 行）；Desktop 是 Electron 壳，携带匹配的 dsh 生产运行时并拥有保留 profile `$DSH_HOME/profiles/desktop`（同文件第 53 行）。`apps/desktop` 与 `apps/desktop-host` 是仅有的两个 `private: true` 应用（`scripts/check-workspace-constraints.ts` 第 59–61 行）。
- **`native/*` = 与消费方共同开发的原生层。** `native/system/` 及 `native/system/packages/*` 都属于根 pnpm workspace 并共用根锁文件，理由是「开发和 CI 中的 harness 消费方直接使用当前 workspace 的入口包，因此启动器约定变更与消费方更新可以在同一个改动中落地并一起测试」（`native/README.zh.md` 第 9 行）。入口包把平台包声明为 npm **可选依赖**，npm 只装匹配 OS/CPU 的那个（第 11 行）。`packages/session/session-persistence-jsonl`（第 40 行）与 `packages/sandbox/sandbox-local` 在 `dependencies` 里依赖它，`packages/sandbox/sandbox-windows-acl` 与 `packages/util/native-command` 也出现在引用面里。

四者关系一句话：**vendor 提供框架 → packages 用框架贡献能力 → native 给能力提供平台原语 → apps 把能力装配成产品。**

### ② 为什么 `apps/` 在 `packages/` 之上？依赖方向如何被强制（哪个脚本、具体检查什么）？

**为什么在之上**（三段理由，各有出处）：

1. **职责边界**：`packages/*/*` 是被挂载的能力，`apps/cli` 持有唯一 `dsh` bin 与 profile 选择权（`pnpm-workspace.yaml` 第 8–9 行；`docs/architecture.zh.md` 第 45 行）。让能力层依赖装配层会把「装什么」和「能装什么」耦合成环。
2. **生命周期唯一**：专用应用 bin 会在 profile 启动之外形成第二套生命周期，使已安装到 profile 的插件不可达、行为偏离 `dsh-base`（`.agents/notes/implemented/architecture/2026-08-22-single-dsh-application-launcher.zh.md` 第 9 行）。方向反过来（packages 依赖 apps）等价于让能力层依赖某个具体产品形态。
3. **发布形态不同**：`apps/desktop` 是 electron-builder 组装、不发布 npm 的安装型应用（`scripts/check-workspace-constraints.ts` 第 59–61 行），而 `packages/*/*` 与除 desktop 外的 `apps/*` 都是 npm release member（第 58–59 行）。两者若互相依赖，会污染彼此的发布闭包。

**怎么被强制**（逐脚本、逐项）：

### ③ `verify-application-entrypoints` 拒绝的是什么？为什么要求所有 Node 应用入口都经 `dsh` launcher？

**拒绝三类（脚本内对应函数与行号见 §8.1）：**

1. **绕过 launcher 的包 bin**：`apps/*` 或 `packages/*/*` 的 manifest 一旦声明 `bin`，就必须与白名单**逐字节等价**（对象键排序后 JSON 比较，第 92–98 行），白名单只有 `apps/cli` 的 `dsh → lib/bin.js` 与 `packages/experimental/webworker-packer` 的 `dsh-pack-vfs-image`（第 27–30 行）。新增第三个 bin 直接失败。
2. **未分类的可执行源码**：任何 `#!` 开头的 `.ts/.js/.mjs/.cjs`（根、`apps/**`、`packages/**`、`python/sdk-runtime/*.mjs`，排除构建产物）必须有一条**具名角色**，例如 `supported dsh application launcher`、`build-only wrapper`、`test-only subprocess driver`（第 33–49 行）。未分类即失败（第 125–127 行）。
3. **未经 launcher 的根启动脚本**：每个 `demo:*` 都必须分类（第 148–150 行）；`start:web` 必须 `dsh-direct`、`dev:web` 必须 `dsh-wrapper`（第 56–61 行）；`dsh-direct` 的命令必须含 `apps/cli/src/bin.ts` 且不得匹配包入口正则 `packages/<g>/<p>/(src|lib)/...`（第 132–138、154–157 行）；`dsh-wrapper` 指向的包装文件必须存在，其源码同样必须引用 `apps/cli/src/bin.ts` 且不得直启包入口（第 159–171 行）。测试用例把这三类反面情形都钉住了（`scripts/verify-application-entrypoints.spec.ts` 第 32–49、50–67、96–135 行）。

**为什么必须经 `dsh` launcher：**

- **只有一条组装路径。** profile + 有序 patch 是唯一的应用组合模型；专用 bin 带自己的 `cordis.yml` 会绕过它，导致 profile 里安装的插件到不了该进程（`.agents/notes/implemented/architecture/2026-08-22-single-dsh-application-launcher.zh.md` 第 9 行）。
- **否则文档的承诺无法成立。** 被拒方案原文：「只要受支持的可执行文件仍然绕过 profile，文档就无法让 profile 真正负责插件安装、环境加载、关闭和测试」（同上第 67 行）。
- **兼容承诺会被无意扩大。** 另一条被拒方案「保留转发兼容 bin」的理由是：转发可执行文件仍然形成另一个公开启动名称与兼容承诺（同上第 69 行）。
- **范围要显式，不能有隐式洞。** 脚本文件头注释（第 1–5 行）把规则说成「vendor CLI、构建工具、测试工具是**显式分类**，而不是隐式漏洞」。因此 `python/sdk-runtime/runtime-bootstrap.mjs` 也要有自己的角色字符串 `private packaging-only runtime dispatcher`（第 48 行），而不是被忽略。
- **文档侧一致**：`docs/architecture.zh.md` 第 47 行说明 vendored CLI、build/test-only 可执行文件、进程内直接挂载插件、私有浏览器 WebWorker 预览都不属于 Harness 应用启动器，并点名该脚本负责分类与拒绝。

### ④ 挑一条真实链路（如 Web 请求 → 后端 API → 会话 → 存储），写出包级依赖方向。

**链路：浏览器 → HTTP 载体 → 认证/RPC 桥 → 传输网关 → 会话控制器 → 会话日志 → 持久化 → 投影缓存 → KV 存储。** 逐段 manifest 依据见 §11 的表。

依赖方向（箭头读作「左边依赖右边」）：

```text
apps/web  (@deepseek-ai/dsh-web-frontend)                      ← 浏览器产物，被组合包依赖
  ↑ dependencies
packages/bundle/web-app  (@deepseek-ai/dsh-web-app)            ← Web 组合包（patch 挂载下面这些）
  ├─→ packages/host/webserver        @deepseek-ai/dsh-host-webserver       提供 ctx.webServer（零 harness 知识）
  ├─→ packages/client/connection     @deepseek-ai/dsh-client-connection    提供 ctx.connection（认证 + /api 桥）
  ├─→ packages/api/session-controller @deepseek-ai/dsh-api-session-controller
  └─→ packages/workspace/workspace   @deepseek-ai/dsh-workspace

packages/bundle/base  (@deepseek-ai/dsh-base)                  ← 共享第一层（patch 挂载下面这两个）
  ├─→ packages/api/gateway           @deepseek-ai/dsh-api-gateway          peer → dsh-client-connection
  └─→ packages/session/session-persistence-jsonl

packages/api/session-controller
  ├─→ packages/api/gateway                    (peer)
  ├─→ packages/client/connection              (peer)
  ├─→ packages/core/session                   (peer)
  ├─→ packages/session/session-persistence    (peer)
  ├─→ packages/session/session-projection     (peer)
  ├─→ packages/session/session-projection-cache (peer)
  └─→ packages/workspace/workspace            (peer)

packages/core/session
  └─→ packages/core/scope (peer)、@deepseek-ai/dsh-llm、dsh-brand、dsh-util-values

packages/session/session-persistence
  └─→ 只依赖 dsh-util-values；peer: dsh-session、dsh-brand、dsh-timeout、cordis

packages/session/session-persistence-jsonl
  ├─→ packages/session/session-persistence (peer)
  ├─→ packages/session/session-format / -catalog / -v3-to-v4 (dependencies)
  └─→ native/system/packages/entry  @deepseek-ai/node-addon-system  (workspace:~)

packages/session/session-projection-cache
  ├─→ packages/session/session-projection (peer)
  └─→ packages/storage/storage-domain     (peer)  → packages/storage/storage (peer)
```

**读法要点：**

1. **抽象在上、实现在下。** `session-persistence` 是 seam（只有 peer 依赖，`dependencies` 仅 `dsh-util-values`，manifest 第 42–43 行），`session-persistence-jsonl` 是它的一个实现（含 `session-format*` 与 native 依赖）。控制面 `api/session-controller` 只面向 seam，不面向实现——这正是 `packages/bundle/base` 负责选择实现的原因（`packages/bundle/base/cordis.patch.yml` 第 130–133 行）。
2. **Host 与 Client 在包级是两条并列的链，不互相依赖。** `client/connection` 的 peer 只有 `cordis` 与 `dsh-scope`（manifest 第 46–49 行），它不依赖 `api/gateway`；反过来 `api/gateway` peer 依赖 `client/connection`（manifest 第 66 行）。浏览器侧内部方向另有文档：Host 状态 → Remote 传输 → Client model → UI adapter → Conversation/presentation → Slots → React（`docs/subsystems/web-client.zh.md` 第 20 行），那一层是 client 包内部的分层，不是包级依赖。
3. **组合包承担「向上够到产品」的角色。** `packages/bundle/web-app` 一条 `dependencies` 就同时够到 `apps/web`（产品前端，第 171 行）与几十个 `packages/*` 能力包（同一区段）。这就是 §6 说的「apps 之上的组装层」在依赖上的表现：方向是 `bundle → apps`，不是 `apps → bundle`。
4. **native 只被 packages 依赖，不被 apps 直接依赖。** `session-persistence-jsonl`（第 40 行）与 `sandbox-local` 走 `workspace:~` 引用 `node-addon-system`；`tsconfig.base.json` 第 92–93 行把它映射到 `native/system/packages/entry/src`；`tsconfig.host.json` 第 387 行以 `./native/system/packages/entry` 引用。`apps/desktop` 在 `devDependencies` 里也有 `@deepseek-ai/node-addon-system`（`workspace:~`，manifest 第 55 行），用于打包，**不是运行时依赖方向的一部分**。
5. **peer 边用于共享实例，dependency 边用于可复制实体。** 判据在策略里：constructor 身份或模块状态必须共享的导出列入 `peerRequiredHostExports`，一旦命中整条包依赖边保持 `peer-dev`；无状态/结构识别/带版本描述符的值可列入 `duplicateSafePackages` 或 `safeHostDependencyExports` 而走普通 `dependencies`（`.agents/notes/implemented/process/2026-08-26-published-dependency-faces.zh.md` 第 27–29 行；实现见 `scripts/package-dependency-policy.ts` 第 37–68 行，推导见本文 §7.5）。实测当前状态：74 个受管包中 5 个 Client-only、67 个 Client/Host、2 个 configured Host（§10 ③）。

### ⑤ 本课的主题是"依赖方向"，那么"不许出现的边"具体长什么样？

**答案：两类，且脚本给出的报错文案就是最精确的定义。**

1. **能力层反向依赖装配层。** 不许出现 `packages/*/* → apps/*` 的边，例外恰好两条（§3 第 5 条）。注意**例外不是豁免机制，而是"组合包/SDK 客户端"这个角色的必然结果**：`dsh-web-app` 要接产品前端、`dsh-sdk-client` 要驱动产品 CLI。
2. **默认产品触及 experimental。** 不许出现"从 `apps/cli` / `apps/web` / `python/sdk-runtime` 出发、沿依赖或源码或组合树可达某个 experimental 包"的路径；报错原文 *"default product must not include experimental packages"*（`scripts/verify-default-product-isolation.ts` 第 114、140 行）。唯一豁免是 `apps/cli` 的 `dependencies` 里由 `OPTIONAL_BUNDLES` 点名的 4 个组合包（第 296 行；`packages/boot/app-boot/src/profile.ts` 第 223–228 行）——它们**随安装发布但默认不启用**。

> 这两条合起来说明一件事：**"依赖方向"在这个仓库里不是审美要求，而是两个具体不变量**——能力层不许指向产品形态，默认产品不许被实验能力污染。
