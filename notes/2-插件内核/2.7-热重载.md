## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：一条判决 + 一条触发链 —— **"改什么能立刻生效、改什么必须重启"**，以及"一个文件事件要走到哪一步才变成实际动作"。

**不是**：

- 不是 cordis 的 HMR 内部原理（`Context` / `Fiber` / 事件分发这些底座见 `2.1`–`2.4`）；
- 不是浏览器 Client 侧的热更新（`client-hmr` 是另一条独立的线，正文只在 §6.4 点一句）；
- 不是包管理流程本身（装包/删包的完整流程见 `2.9`，本课只讲它和 HMR 队列的边界）。

### 0.2 现在只要记住这 4 件事

1. **HMR 是一个插件**（`@deepseek-ai/dsh-hmr`），不是内核能力。它由 `dsh-base` 组合包插进树里，条目 `id: hmr`，并往共享登记处登记一项叫 `ctx.hmr` 的服务（下文一律写 `ctx.hmr`）；谁把它禁用或干脆不带它，谁就退回"改完必须重启"。
2. **默认只热重载"配置"，不热重载"源码"**：base 给它写的 `config.root` 是 `[]`，也就是"模块监听目录为空"。想看源码热替换，必须自己在 profile patch 里把 `root` 改成非空。
3. **所有自动重载共用一条串行队列**（`runExclusive()`），并且**拒绝嵌套**；应用**没就绪**之前，事件即使排进队列也会被丢掉。
4. **一个文件事件只有四种归宿**：命中已注册的配置路径（跳过，交给独立 watcher）、命中宿主依赖图（调宿主的 `loader.exit()` 全量重载钩子）、命中 Node 的已加载模块缓存（就地替换模块）、命中某个 Include 子树（`include.refresh()`）；四条都不命中，就只发一个 `hmr/change` 事件，什么也不改。

### 0.3 明确授权：这些现在**不用管**

本课会出现这些你现在不必弄懂的词与细节：`AsyncLocalStorage`、`picomatch`、`chokidar` 的 `awaitWriteFinish` 窗口、ESM `loadCache` 与 CJS `Module._cache` 的差别、Node internal binding、`PackageManifests` 的 hook 表、`runtime resolution`（包解析表）。

**判断标准只有一条**：读完能回答 **"这个文件的变化，是热生效还是必须重启"**，就够本课的目标了。上面那些词只是用来解释"为什么如此"，它们各自在 §5 的源码块里就地出现一次，忘了也不影响判据。

### 0.4 如果你是第一次读

- **跳过附录 A 的 Q4 后半（runtime resolution / 包解析表）与 Q6（`patchReload` 与设计笔记的关系）**：它们牵到包管理与设计决策，属后续课与回查材料。

## 1. 最小词汇表（本课新增的 8 个词）

这 8 个词都属于 **DSH 的 HMR 插件**这套词汇（不是 cordis 的通用词汇），除最后两个外都由 `packages\boot\hmr` 自己定义或使用。

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **watcher 监视器** | 盯着某些文件、一有变化就通知你的那个东西 | `chokidar` 的 `watch()` 返回 `FSWatcher`；本课有**两个**：模块 watcher 与精确配置 watcher |
| **root 监听根** | "盯哪些目录"的清单 | `HmrConfig.root`；base 里是 `[]` |
| **ignored 忽略表** | "这些路径不用盯"的 glob 清单 | `HmrConfig.ignored`，默认四项 |
| **debounce 去抖** | 把短时间内的一串事件**合成一批**再处理 | `this.ctx.debounce(fn, this.config.debounce)`，默认 100 ms |
| **transaction 事务** | 一段"不许和别人并跑"的工作；**不许嵌套** | `runExclusive()` + `AsyncLocalStorage` 标记 `executing` |
| **readiness 就绪闸门** | 应用没准备好之前，文件事件一律不算数 | `applicationReady` + 启动器的 `appReady.onReady()` |
| **loadCache** | Node 内部"这个 URL 已经加载过了"的缓存 | ESM 的 `internal.loadCache`；CJS 的 `require.cache` / `Module._cache` |
| **manifest 失效** | 让 Node 缓存的 `package.json` 配置（`exports` / `main` / `type`…）作废 | `PackageManifests.invalidate(filename)` |

> ⚠️ 上一张表里的 `plugin` / `ctx` / `service` / `entry` / `layer`（来自 `1.1`）与 `patch` / 覆盖 / 插入（来自 `1.2`、`1.4`）、`config` / `!!js` / 整块替换（来自 `2.6`）本课直接复用，不再重复解释。**本课唯一需要你新建立的直觉是**：HMR 不是"内核监听文件"，而是"**一个普通插件**注册了两类 watcher，并把所有动作塞进一条队列"。

## 2. 先建立画面

### 2.1 静态结构：谁是谁的一部分（谁盯着谁）

```
插件树
├─ 条目 id: hmr  →  插件 @deepseek-ai/dsh-hmr
│   服务：ctx.hmr（Hmr 实例）
│   ├─ 一条串行队列            operations / executing（AsyncLocalStorage）
│   ├─ 一个就绪闸门            applicationReady  ← 由 appReady.onReady() 兑现
│   ├─ 模块 watcher            chokidar 盯 root 列表；只订阅 change
│   │    └─ 每个事件 → debounce 合并 → 进队列 → 交下面的分派逻辑
│   ├─ 精确配置 watcher ×3     watchConfig()，由 packages/boot/hmr/src/watch-config.ts 实现
│   │    ├─ <profile 目录>\cordis.patch.yml
│   │    ├─ $DSH_HOME\cordis.patch.yml
│   │    └─ <profile 目录>\package.json
│   └─ 两张分类集合            externals（宿主依赖图）/ accepted、declined（要不要重载）
├─ 条目 id: plugin-manager  →  用 ctx.hmr 是否存在来决定结果标 applied 还是 restart-required
└─ 宿主（启动器）           →  提供 profileContext / appReady；可覆写 loader.exit() 钩子
```

> **精确性说明（两处简化）**：① 上图把"三类发现"画成了 `Hmr` 实例的字段，严格说 `accepted` / `declined` 是**每次重载开始时现算的局部状态**（`analyzeChanges()` 里重建），不是长期持有的表；`externals` 才是启动时算一次、之后长期持有的。② 三个配置 watcher 里，`<profile 目录>\package.json` 与两份 patch **走的是同一个 `watchConfig()` 实现**，只是回调里的 `manifestOnly` 参数不同。

### 2.2 动态过程：一个文件事件的一生

```
文件在磁盘上被改动
   │
   ├─(路径属于三条已注册配置路径之一？)────────► 精确配置 watcher
   │                                               │  读盘 → refresh() → 幂等比对 → 重新组合
   │                                               └─ 走的是同一条队列（见 §5 第 2 块）
   │
   └─(落在模块 watcher 的 root ∩ 非 ignored？)────► 收进 changed 集合
                                                        │
                                               debounce 合并成一批
                                                        │
                                        runExclusive（串行队列；嵌套会被拒绝）
                                                        │
                                        await applicationReady（未就绪 → 直接丢弃）
                                                        │
                                          逐路径分类（四个判定，顺序敏感）
                                                        │
             ┌──────────────┬─────────────────┬─────────┴──────────┬───────────────┐
             ▼              ▼                 ▼                    ▼               ▼
        已注册配置路径   externals 命中    loadCache 命中      Include 子树命中   都不命中
        跳过（continue）  全量重载标记      存进 stashed         记进 includes    emit hmr/change
             │              │                 │                    │               │
             └──────────────┴────────┬────────┴────────────────────┘          （不改任何东西）
                                     ▼
                     loader.exit()  ─→ 宿主决定（HMR 自己不重启进程）
                     include.refresh() ─→ 逐个刷新
                     partialReload()   ─→ 分析依赖图 → 清缓存 → 重新 import → 激活新 fiber
                                     ▼
                              await loader.await()
                                     ▼
                        emit hmr/reload（模块替换完成）
```

## 3. 大白话版：保存一个文件之后，机器里发生了什么

**这一节完全不用上面的术语**（来源：`packages\boot\hmr\README.zh.md` 第 57–65 行的实现说明 + `packages\boot\hmr\src\index.ts` 第 381–424 行的分派代码；这里只做白话转述）。

1. 你在编辑器里按了保存，磁盘上的某个文件变了。
2. 有一个一直盯着的程序发现了这件事。它先等一小会儿（默认 0.1 秒），把这一小会儿里发生的所有变化**攒成一批**——因为在编辑器里连续保存几次是很常见的。
3. 攒完之后，它去敲一个"**一次只准一个人进**"的房间的门。房间里可能正有别人在干活（比如你刚在界面上点了"装插件"），那就排队等。
4. 轮到自己时，它先问一句："应用**彻底启动完了**吗？"如果还没启动完，就把这一批变化**扔掉**，不做任何事（因为启动过程中本来就在读这些文件）。
5. 然后它把这一批里的每一个文件**挨个过一遍四个问题**：
   - 这个文件是不是"我已经专门派人盯着的那个配置文件"？是 → 不管（另有专人处理）。
   - 这个文件是不是"程序自己启动时用到的那一堆"?是 → 记一笔"得整个重来"。
   - 这个文件的内容，是不是已经在内存里加载过？是 → 记一笔"这个可以就地换掉"。
   - 这个文件是不是某张"配置清单"？是 → 记一笔"刷新那张清单"。
   - 四个都不是 → 只是**广播一句"这个文件变了"**，让感兴趣的插件自己看着办，机器本身什么也不改。
6. 如果记下了"整个重来"，它就去调用宿主预留的一个钩子，由**宿主**决定怎么退出/重启——**它自己不重启进程**。
7. 如果记下了"刷新清单"，就一张一张刷新。
8. 如果记下了"就地换掉"，就做一次**模块替换**：先看懂"谁依赖谁"（变了的文件会连累谁）、把旧的实现卸下来、清掉"已加载"的记录、重新加载一次、把新的实现装上去；中间任何一步失败，就把缓存和旧实现**原样放回去**。
9. 全部做完之后，等加载器把手上的活干完，然后广播一句"**重载完成了**"。

## 5. 机制（源码对照，13 块）

> 每块上方标 `文件路径 第 A–B 行`；块内所有省略都用注释写明省了哪些行、为什么省。**本课的源码块按"一条机制一块"排列，不按文件排列**，所以同一个文件会出现多次。

### 5.1 串行队列：一次只准一个人进，而且不许嵌套

**与哪个知识点相关**：结论 3；§0.2 第 3 件事。

`packages\boot\hmr\src\index.ts` 第 258–276 行（`class Hmr extends Service` 的成员方法）

```ts
  /** Serialize a caller-owned mutation with all automatic reload paths.
   * @param operation Work that must not overlap module or configuration replacement.
   * @returns The operation result after its asynchronous work completes.
   */
  runExclusive<T>(operation: () => Promise<T>): Promise<T> {
    if (this.executing.getStore()) return Promise.reject(new Error('HMR transactions cannot be nested'))
    const task = this.operations.then(async () => {
      if (this.closing) throw new Error('HMR is disposed')
      return this.executing.run(true, operation)
    })
    this.operations = task.catch(() => {})
    return task
  }

  private runReload(operation: () => Promise<void>): Promise<void> {
    return this.runExclusive(async () => {
      if (await this.applicationReady) await operation()
    })
  }
```

**按块讲解**

- **做什么**：把任意一段异步工作接到一条**单链** `this.operations` 的尾部，返回它自己的 `Promise`；在执行期间用一个 `AsyncLocalStorage` 标记"我在事务里"。
- **依赖的变量从哪来**：`this.operations`（第 251 行，初值 `Promise.resolve()`，一条不断被替换成"尾巴"的 Promise 链）、`this.executing`（第 252 行，`AsyncLocalStorage<boolean>`）、`this.closing`（第 254 行，销毁时置 `true`）、`this.applicationReady`（第 253 行，未接 profile 时默认 `Promise.resolve(true)`）。
- **相邻的守卫**：第一行 `if (this.executing.getStore())` 就是"拒绝嵌套"——**同一个事务里再调 `runExclusive` 直接 reject**，错误文本是 `'HMR transactions cannot be nested'`。第二个守卫在链里：如果 `this.closing` 已为真，抛 `'HMR is disposed'`。
- **为什么这么写**：`this.operations = task.catch(() => {})` 这一句是**队列能活下来的关键**——它让链的尾巴"吞掉"失败，于是**某一次重载抛错不会把整条队列焊死**，后续操作照样能排上。测试 `packages\boot\hmr\tests\coordination.spec.ts` 第 37–60 行钉住了这三件事：串行（`order` 先是 `[1]`，放行后才是 `[1, 2]`）、拒绝嵌套（第 53 行断言错误信息含 `cannot be nested`）、失败后队列仍可用。
- **`runReload` 为什么长这样**：它把"**就绪闸门**"塞进了队列内部——注意是 `if (await this.applicationReady)`，**未就绪就直接跳过这次操作**，而不是报错。所以"未就绪时的事件被丢弃"发生在队列里，不在 watcher 层。

### 5.2 它到底注册了哪三个配置监听（含就绪闸门与幂等早退）

**与哪个知识点相关**：§0.2 第 3、4 件事；结论 2；附录 A Q2。

`packages\boot\hmr\src\index.ts` 第 311–351 行（`class Hmr extends Service` 的初始化生成器）

```ts
        if (manifestOnly && bundles === lastBundles) return
        const inputs = JSON.stringify([bundles, ...patchFiles.map((filename) => {
          try { return readFileSync(filename, 'utf8') }
          catch (error) {
            if ((error as NodeJS.ErrnoException).code === 'ENOENT') return null
            throw error
          }
        })])
        if (inputs === lastInputs) return
        const patches = readProfilePatches('dsh', profile)
        const warnings = await reconcileProfilePatches(this.ownerContext.root, patches, 'dsh')
        lastInputs = inputs
        lastBundles = bundles
        for (const diagnostic of warnings) this.ctx.logger.warn(diagnostic)
      }
      for (const filename of patchFiles) await this.watchConfig(filename, () => refresh(false))
      await this.watchConfig(manifestPath, () => refresh(true))
    }
```

**按块讲解**

- **做什么**：如果宿主提供了 `profileContext`，就（a）建立就绪闸门，（b）给**三条路径**注册精确配置监听：`profile.patchPath`（profile 自己的 `cordis.patch.yml`）、`join(profile.home, PROFILE_PATCH_FILENAME)`（home 级 `cordis.patch.yml`）、`<profile 目录>\package.json`。
- **依赖的变量从哪来**：`profile` 是启动器 `provide` 进来的 `ProfileContext`（声明在 `packages\boot\app-boot\src\profile-context.ts` 第 15–30 行；装配点在 `apps\cli\src\profile-boot.ts` 第 287–298 行）；`appReady` 是启动器提供的就绪服务；`PROFILE_PATCH_FILENAME` 是从 `@deepseek-ai/dsh-app-boot` 导入的常量。
- **相邻的守卫**：`if (profile !== undefined)` —— **没有 `profileContext` 的宿主（例如把 HMR 当普通 cordis 插件用的场景）根本不会注册配置监听**；紧接着 `if (ready === undefined) throw new Error('Profile HMR requires application readiness')` —— 有 profile 却没有就绪信号，**直接抛错拒绝启动**（测试 `packages\boot\hmr\tests\profile.spec.ts` 第 156–164 行钉住了这句话）。
- **为什么有两次 `return`（幂等早退）**：第一次 `if (manifestOnly && bundles === lastBundles) return` 只对 manifest 那条监听生效——**`package.json` 变了、但 `dsh.profile.bundles` 有序列表没变（例如只改了 `dependencies`），什么也不做**。第二次 `if (inputs === lastInputs) return` 比对的是"bundles + 两份 patch 文件内容的 JSON 快照"——**内容没变就早退**。这两行正是"仅 `dependencies` 变化的 manifest 不引发重载"的机制来源，测试 `packages\boot\hmr\tests\profile.spec.ts` 第 101–128 行钉住了它（第 114 行断言 `include.update` 未被调用；第 123–127 行断言改了 `bundles` 后会重读 `node_modules` 里那个 bundle 的 patch，最终出现 `include:bundled`）。
- **`readFileSync` 里为什么要 catch**：`ENOENT` 被翻译成 `null`（文件不存在是**合法状态**——用户可能就没写 home 级 patch），其它错误照抛。这与 `1.2` §3.4 里 `loadOptionalPatches` 的判断完全同构。
- **与结论 7 的关系**：这一段调用的 `readProfilePatches()` 每次都**重新读盘**（`packages\boot\app-boot\src\profile-context.ts` 第 63–74 行：`profile.layers` → profile patch → home patch → `context.overlays`，末尾再叠一条遥测开关 patch），所以 **bundle 的 patch 层不是"只在启动时读取"**——它是在每轮真正执行的重组合里被重新读的。

### 5.3 模块 watcher：盯什么、忽略什么、`externals` 什么时候采集

**与哪个知识点相关**：§0.2 第 2、4 件事；结论 5；附录 A Q2。

`packages\boot\hmr\src\index.ts` 第 353–379 行

```ts
    const { loader } = this.ctx
    const { root, ignored } = this.config
    // …（第 355–360 行：一段 if/else 的 "watching %o" 日志，与本知识点无关，此处省略）
```

**按块讲解**

- **做什么**：用 chokidar 开一个 `FSWatcher` 盯 `root` 列表；并在**开 watcher 之前**先把"宿主依赖图"采集完。
- **依赖的变量从哪来**：`root` / `ignored` 来自插件自己的 `config`（第 354 行解构；默认值在 `static Config` 第 212–222 行：`root: ['.']`、`ignored: ['**/node_modules','**/.*','cache','data']`、`debounce: 100`）；`this.baseDir` 在构造函数第 308 行算出（`fileURLToPath(new URL(config.base || '.', ctx.baseUrl))`）；`this.internal` 是第 307 行拿到的 Node loader 内部对象；`loadDependencies` 是同文件第 68–79 行的递归采集函数。
- **相邻的守卫**：`loadDependencies` 里有两道过滤——`job.url.startsWith('node:')` 与 `job.url.includes('/node_modules/')` 直接 `return`（第 72 行），也就是**内置模块与 `node_modules` 不算宿主依赖图**；`process.argv[1] === undefined` 时 `mainJob` 为 `undefined`、`externals` 退化成空集（测试 `packages\boot\hmr\tests\coordination.spec.ts` 第 203–209 行专门覆盖"没有进程入口模块也能启动"）。
- **为什么"先采集、后开 watcher"**：作者注释给的就是理由——*"Collect externals before opening the watcher so every post-ready change is observed by listeners that already have their classification state."*（译文：如果先开 watcher，就可能在分类状态还没建立时收到事件。）
- **`ignored` 为什么写成函数**：`watch()` 收到的是**绝对路径**，这里用 `match(relative(watchBaseDir, path))` 先转成相对路径再匹配 picomatch，于是配置文件里写的 glob 是**相对于监听根**的。另外注意 `cwd: watchBaseDir` 用的是 `realpathSync()` 之后的目录——`README.zh.md` 第 69 行说明了原因：被监听模块的路径要沿用 Node ESM 解析所用的 `realpathSync()` 表示（含 Windows 短目录名），否则**文件事件与模块缓存对不上**。

### 5.4 分派：一个文件事件的六个判定（本课最关键的一段）

**与哪个知识点相关**：结论 5；§0.2 第 4 件事；附录 A Q1、Q2。

`packages\boot\hmr\src\index.ts` 第 381–411 行

```ts
    const changed = new Set<string>()
    const dispatch = this.ctx.debounce(() => {
      void this.runExclusive(async () => {
        if (!await this.applicationReady) return
        const batch = [...changed]
        changed.clear()
        const includes = new Set<Include>()
        let fullReload = false
        for (const path of batch) {
          const filename = canonicalPath(resolve(watchBaseDir, path))
          const configuredFilename = resolve(this.baseDir, path)
          if (this.configPaths.has(filename) || this.configPaths.has(configuredFilename)) continue
          const isManifest = basename(filename) === 'package.json' && !filename.includes(`${sep}node_modules${sep}`)
          if (isManifest) {
            this.manifests.invalidate(filename)
          }
          const url = pathToFileURL(filename).href
          if (this.externals.has(url)) {
            fullReload = true
            continue
          }
          if (this.internal.loadCache.has(url) || this.internal.loadCache.has(url, 'json')) {
            this.stashed.add(url)
            continue
          }
          if (isManifest) continue
          const include = [...loader.entries()].map(entry => entry.subtree as Include | undefined)
            .find(tree => tree?.filename === filename || tree?.filename === configuredFilename)
          if (include !== undefined) includes.add(include)
          else this.ctx.emit('hmr/change', url)
        }
```

**按块讲解**

- **做什么**：把去抖后的一批路径逐个分类，分类结果只落在四个容器里：`configPaths`（跳过）、`this.manifests`（失效）、`fullReload`（一个布尔）、`this.stashed`（一批 URL）、`includes`（一批 Include）；分类以外的一条路径如果谁都不沾，就发 `hmr/change`。
- **依赖的变量从哪来**：`changed` 是本块上面新建的集合，事件在**第 424 行**灌进来（`this.watcher.on('change', (path) => { changed.add(path); dispatch() })`，即下一块的最后两行）；`this.configPaths` 是 `watchConfig()` 注册时填的（第 286 行）；`watchBaseDir` / `this.baseDir` 来自第 5 块；`this.externals` 来自第 5 块；`this.internal.loadCache` 是 Node 的模块缓存；`loader` 是第 353 行解构出来的 `this.ctx.loader`。
- **相邻的守卫（顺序敏感，逐个说）**：
  1. `if (this.configPaths.has(...)) continue` —— **已注册的配置路径在这里被跳过**，因为精确 watcher 已经负责它了（测试 `coordination.spec.ts` 第 110–136 行钉住了"跳过后 `include.refresh` 只被调一次"）。
  2. `isManifest` 的判定带一个**排除项**：文件名是 `package.json` **且路径中不含 `${sep}node_modules${sep}`**（`sep` 由 `node:path` 提供，Windows 上是 `\`）。所以在 `node_modules` 里的 manifest **不会**做配置失效——`README.zh.md` 第 61 行与决策笔记第 53 行都写了这条边界。
  3. `if (isManifest) this.manifests.invalidate(filename)` —— 注意它**不是 `continue`**：失效之后还要接着往下判（因为同一个 `package.json` 也可能被当成 JSON 模块 import 过、也可能在宿主依赖图里）。这正是"配置失效"与"要不要重载模块"两件事分开的原因。
  4. `if (this.externals.has(url)) { fullReload = true; continue }` —— 宿主依赖图命中就**不再看别的**。
  5. `if (this.internal.loadCache.has(url) || this.internal.loadCache.has(url, 'json'))` —— 第二个参数 `'json'` 是 Node 24 的 `LoadCache` 多类型槽位（JSON 模块单独占一格）。
  6. `if (isManifest) continue` —— **仅仅作为配置的 manifest（不在 loadCache、不在 externals）到此为止，不重载任何模块**。
  7. 最后一段用 `loader.entries()` 找"文件名对得上的 Include 子树"；找不到才 `emit('hmr/change', url)`。
- **为什么这么写**：这段代码是"**判定顺序就是优先级**"的典范。作者把"谁负责这个文件"写成一条瀑布：越靠前的判定越专门、越不可让。要读懂"某个改动会不会热生效"，本质就是**按这七行顺序模拟一遍**。
- **`canonicalPath` 为什么存在**：同文件第 41–50 行。注释原文：*"Node's ESM resolver uses the JS realpath implementation; native realpath expands Windows short names differently and would miss its cache keys."*（译文：Node 的 ESM resolver 用的是 JS 版 realpath，原生 realpath 对 Windows 短名的展开方式不同，会错过它的缓存键。）所以这里用 `realpathSync` 失败就退回到"逐级解析父目录"的写法。

### 5.5 分类之后：三条落地动作

**与哪个知识点相关**：结论 5 的后半；§2.2 动态图的收尾。

`packages\boot\hmr\src\index.ts` 第 412–424 行

```ts

        if (fullReload) {
          loader.exit()
          return
        }
        for (const include of includes) await include.refresh()
```

**按块讲解**

- **做什么**：三条动作的**优先级**：① 什么都没有 → 直接返回；② 有全量重载 → 调 `loader.exit()` 并**立刻返回**（不再做 Include 与模块替换）；③ 否则先逐个 `include.refresh()`，再做 `partialReload()`，最后 `await loader.await()`。
- **依赖的变量从哪来**：`fullReload` / `includes` / `this.stashed` 都来自上一块的分类；`loader` 是 `this.ctx.loader`；`this.config.debounce` 是去抖毫秒数。
- **相邻的守卫**：开头那一行 `if (!fullReload && includes.size === 0 && this.stashed.size === 0) return` 是"**无实际变化就什么也不发生**"的落点——一批全是"仅 manifest"或"只是广播过"的路径，走到这里就结束。`try { … } finally { this.stashed.clear() }` 保证**即使 `partialReload` 抛错，stashed 也会被清空**（否则下一批会被旧的待处理集合污染）。
- **为什么 `loader.exit()` 之后要 `return`**：因为这条路径是"整棵宿主都要重来"，再去做局部替换没有意义。**注意它不重启进程**——`loader.exit()` 是一个空实现的钩子，见第 12 块。
- **`this.watcher.on('change', …)` 只订阅了 `change`**：chokidar 还会发 `add` / `unlink`，这里**都没订阅**。所以"新建一个源码文件"不会触发模块替换（与 `ignoreInitial: true` 一起构成两条独立的理由）。
- **`.catch(...)` 的位置**：它挂在 `runExclusive(...)` 返回的 Promise 上，把队列里的失败降级成一条 `logger.warn`——所以**一次重载失败只会打日志，不会中断进程**。

> **粒度说明**：本块只有 13 行，略低于 R11 的 15 行下限。原因是它必须紧接第 4 块读：`fullReload` / `includes` / `stashed` 三个变量都在上一块产生，单独拎出来读者就不知道它们在说什么；而把它与第 4 块合并会变成 44 行，超出上限。此处选择"略短但可独立理解"。

### 5.6 精确配置 watcher：向上找第一个存在的父目录

**与哪个知识点相关**：§0.2 第 3 件事；附录 A Q2 的第 2 项。

`packages\boot\hmr\src\watch-config.ts` 第 9–25 行

```ts
async function findWatchRoot(filename: string): Promise<{ filename: string; root: string; depth: number }> {
  let root = dirname(filename)
  let depth = 0
  while (true) {
    try {
      if (!(await stat(root)).isDirectory()) throw new Error(`config watch parent is not a directory: ${root}`)
      const canonicalRoot = await realpath(root)
      return { filename: resolve(canonicalRoot, relative(root, filename)), root: canonicalRoot, depth }
    } catch (error) {
      if ((error as NodeJS.ErrnoException).code !== 'ENOENT') throw error
      const parent = dirname(root)
      if (parent === root) throw error
      root = parent
      depth += 1
    }
  }
}
```

**按块讲解**

- **做什么**：给定一个**可能还不存在**的配置文件路径，从它的父目录开始**逐级向上**找第一个真实存在的目录，把"那个目录 + 相对深度 + 规范化后的目标文件名"一起返回。
- **依赖的变量从哪来**：入参 `filename` 由 `watchConfig()` 传入（`index.ts` 第 289 行）；`dirname` / `relative` / `resolve` 来自 `node:path`，`stat` / `realpath` 来自 `node:fs/promises`。
- **相邻的守卫**：三条——① `if (!(await stat(root)).isDirectory())` 抛"父路径不是目录"；② catch 里 `if (code !== 'ENOENT') throw error` 只放行"不存在"这一种错误（权限等问题照抛）；③ `if (parent === root) throw error` 是**到达文件系统根时收手**，防止无限循环。
- **为什么这么写**：`watchConfig()` 要支持"**父目录现在还不在**"的场景——profile 目录、`node_modules`、甚至整个 `$DSH_HOME` 都可能是后建的。chokidar 不能盯一个不存在的目录，所以**先找一个存在的祖先目录，再用 `depth` 限制只看下面 N 层**。
- **配套的两处（同文件，不再单独出块）**：第 45–49 行的 `watch()` 调用把 `awaitWriteFinish: true` 放在展开参数**之前**，作者注释解释了原因：*"Stabilized events bypass Chokidar's lossy 50 ms change-event throttle."*（译文：稳定化后的事件会绕过 chokidar 那个有损的 50 ms 变更节流。）第 71–73 行则同时订阅 `add` / `change` / `unlink`——**这是它和模块 watcher 的关键区别**（模块 watcher 只订阅 `change`），所以配置文件的新建与删除都算变化。

### 5.8 依赖图分析（下）：不动点迭代与兜底

**与哪个知识点相关**：同 5.7；附录 A Q1 的"判据"。

`packages\boot\hmr\src\index.ts` 第 486–523 行

```ts
    while (pending.length) {
      let index = 0, hasUpdate = false
      while (index < pending.length) {
        const url = pending[index] as string
        const children = await this.getLinked(url)
        let isDeclined = true, isAccepted = false
        for (const child of children) {
          if (this.declined.has(child) || isExcluded(child)) continue
          if (this.accepted.has(child)) {
            isAccepted = true
            break
          } else {
            isDeclined = false
            if (!pending.includes(child)) {
              hasUpdate = true
              pending.push(child)
            }
          }
        }
        if (isAccepted || isDeclined) {
          hasUpdate = true
          pending.splice(index, 1)
          if (isAccepted) {
            this.accepted.add(url)
          } else {
            this.declined.add(url)
          }
        } else {
          index++
        }
      }
      if (!hasUpdate) break
    }

    for (const url of pending) {
      this.declined.add(url)
    }
  }
```

**按块讲解**

- **做什么**：反复扫描待定集合，直到**一轮没有任何更新**（不动点）。每个待定节点的判定是：只要有一个依赖者 `accepted` → 自己 `accepted`；所有依赖者都 `declined`/被排除 → 自己 `declined`；两者都不成立 → **留到下一轮**。
- **依赖的变量从哪来**：`pending` 由上一块产出；`isExcluded` 是上一块定义的闭包；`accepted` / `declined` 是实例字段（声明在第 241、247 行）。
- **相邻的守卫**：`if (!hasUpdate) break` 是**迭代终止条件**（一轮什么都没变就停）；`else index++` 是"这一轮判不了，跳过、下轮再看"；循环后面的 `for (const url of pending) this.declined.add(url)` 是**兜底**——不动点停下时还留在 `pending` 里的（互相依赖、判不出结论的）**一律按不重载处理**。
- **为什么这么写**：这是一个典型的**保守算法**：不确定就**不换**——宁可让用户重启，也不换掉一个可能还在用的模块。这与本课结论 7 里"包解析表只在启动时构造"的保守取向一致。
- **与可逆副作用的关系**：`accepted` 集合最终决定谁被清缓存、谁被重新 import、谁被卸载——而"卸载"之所以安全，正是因为 `2.3` 讲过的"每个注册都是可撤销的 effect"。**本课只需要知道**：`accepted` 是"允许被换掉"的白名单。

### 5.9 换模块之前：备份两个缓存

**与哪个知识点相关**：§2.2 动态图里"清掉已加载记录"这一步；附录 A Q1 的"热替换"行。

`packages\boot\hmr\src\index.ts` 第 603–629 行

```ts
    const esmBackup = new Map<string, unknown>()
    const cjsBackup = new Map<string, NodeJS.Module>()
    const require = createRequire(import.meta.url)
    for (const filename of this.accepted) {
      // Backup and clear ESM loadCache
      const job: unknown = Map.prototype.get.call(this.internal.loadCache, filename)
      esmBackup.set(filename, job)
      Map.prototype.delete.call(this.internal.loadCache, filename)

      // Backup and clear CJS Module._cache
      try {
        const filepath = fileURLToPath(filename)
        if (require.cache[filepath]) {
          cjsBackup.set(filepath, require.cache[filepath])
          Reflect.deleteProperty(require.cache, filepath)
        }
      } catch {
        // filename might not be a file: URL (e.g. node: protocol), ignore
      }
    }

    const rollback = () => {
      for (const [filename, job] of esmBackup) {
        Map.prototype.set.call(this.internal.loadCache, filename, job)
      }
      for (const [filepath, module] of cjsBackup) require.cache[filepath] = module
    }
```

**按块讲解**

- **做什么**：为 `accepted` 里每个文件名，**先存一份旧的缓存条目，再删除**；同时准备好一个 `rollback()` 闭包，一旦后面失败就原样放回。
- **依赖的变量从哪来**：`this.accepted` 由 5.7/5.8 算出；`this.internal.loadCache` 是 Node 的 ESM `ModuleLoader` 缓存；`require.cache` 是 CJS 的 `Module._cache`；`createRequire(import.meta.url)` 让 ESM 模块里也能拿到 CJS 的 `require`。
- **相邻的守卫**：CJS 那段包在 `try { … } catch { /* ignore */ }` 里——注释写明"文件名可能不是 `file:` URL（例如 `node:` 协议），忽略"。另外 `if (require.cache[filepath])` 先判存在，不存在就不记备份。
- **为什么用 `Map.prototype.delete.call(...)` 而不是 `this.internal.loadCache.delete(...)`**：作者在第 587–602 行的注释里给了完整理由，原文关键句——*"In Node 24, loadCache is a LoadCache extends Map<url, { [type]: ModuleJob }> where .delete() only sets the type slot to undefined (doesn't remove the entry). Using Map.prototype.delete ensures complete removal in both versions."*（译文：Node 24 的 `loadCache` 是 `Map` 的子类，`.delete()` 只把某个类型槽位置空；用 `Map.prototype.delete` 才能两种版本下都彻底删除。）
- **为什么 CJS 也要清**：同一段注释——*"In Node 24, CJS modules loaded via import() appear in both caches. If you only clear loadCache, the CJS cache may serve stale modules."*（译文：Node 24 里经 `import()` 加载的 CJS 模块同时出现在两个缓存里，只清一个会拿到旧模块。）

### 5.10 换模块：重新 import，失败就回滚

**与哪个知识点相关**：§2.2 动态图里的"重新加载一次"；附录 A Q1 的"热替换"行。

`packages\boot\hmr\src\index.ts` 第 646–659 行

```ts
    try {
      for (const generation of generations) {
        const moduleNamespace: unknown = await this.ctx.loader.import(generation.filename, this.getOuterStack)
        const replacement = this.ctx.loader.unwrapExports(moduleNamespace) as Plugin
        const replacements = await generation.modules.importRemaining(this.ctx.loader, this.getOuterStack, {
          filename: generation.filename, moduleNamespace, plugin: replacement,
        })
        attempts.push({ ...generation, replacement, replacements, activated: [] })
      }
    } catch (e) {
      handleError(this.ctx, e)
      rollback()
      throw e
    }
```

**按块讲解**

- **做什么**：对每一"代"要替换的运行时：先重新 `import` 它的入口文件，把导出归一成插件实现（`unwrapExports`），再把**共享同一运行时的其余模块**也 import 一遍，凑齐一次替换所需的全部实现；全部成功后记进 `attempts`。
- **依赖的变量从哪来**：`generations` 是在**本块之前、第 632–639 行**构造的：它把 `reloads`（"哪个旧插件 → 它的模块图 + runtime"）展开，并把每个 runtime 的 fiber 连同**它自己那份 config**（`entry.options.config` 或 `fiber._config`）一起带上——这是"换实现但不丢配置"的落点。`generation.modules.importRemaining` 是同文件 `ReloadModules` 类第 166–178 行的方法。`this.getOuterStack` 是第 450 行的钩子（默认为 `() => []`），用来在 HMR 自己的报错栈里**过滤掉内部帧**。
- **相邻的守卫**：整个 for 包在一个 `try` 里——**任何一代导入失败，就 `handleError` 打印（esbuild 的 `BuildFailure` 会连代码帧一起打，见 `packages\boot\hmr\src\error.ts` 第 16–41 行）、`rollback()` 恢复缓存、然后 `throw e`**。注意它是"先全部导入，再统一替换"的两段式：**导入期失败时还没有任何插件被卸载**，所以回滚只需恢复缓存。
- **为什么这么写**：这是"**失败必须可逆**"的具体形态——与 `2.3` 的 effect 契约同源。紧接着的第 661–676 行才是激活（把新实现装进 registry、把 `entry` 记录接回新 fiber、`fiber.await()`），第 678–722 行是替换期失败的第二段回滚（重新注册旧插件），本文不再单独出块。

> **粒度说明**：本块 14 行，略低于 15 行下限。原因是它只承担"导入 + 失败即回滚"一件事，再往前一步就是 `generations` 的构造（第 632–639 行，属另一件事），往后一步就是激活（第 661–676 行，属第三件事）。三件事各自成块，读者才不会把"导入失败"和"激活失败"两种回滚混为一谈。

### 5.13 用户看得见的结果：`applied` 还是 `restart-required`

**与哪个知识点相关**：结论 4；附录 A Q1 的最后两行、Q3 的落点。

`packages\boot\plugin-manager\src\index.ts` 第 795–819 行

```ts
  private async change(
    operation: (result: ChangeResult) => Promise<ChangeResult['application'] | void>,
    request: Pick<ChangeResult, 'stage' | 'target' | 'enabled'>,
    reason: PluginChange['reason'],
  ): Promise<ChangeResult> {
    return withFileLock(join(this.profile.dir, 'package.json'), async () => {
      this.abort.signal.throwIfAborted()
      const before = this.diskState()
      const result: ChangeResult = { ...request, changed: false,
        application: this.ownerContext.get('hmr') !== undefined ? 'applied' : 'restart-required' }
      try {
        result.application = await operation(result) ?? result.application
      } catch (error) {
        if (error instanceof InstallCancelledError) {
          result.application = 'cancelled'
        } else {
          result.application = 'failed'
          result.error = managementError(error)
        }
      }
      result.changed = before !== this.diskState()
      this.ownerContext.emit('plugin-manager/changed', { reason })
      return result
    }, { waitMs: this.lockWaitMs })
  }
```

**按块讲解**

- **做什么**：所有会产生磁盘变化的插件管理操作都从这里过一遍：拿 profile 写锁 → 记下磁盘快照 → **先按"有没有 HMR"给出一个默认结论** → 跑真正的操作（操作可以返回更精确的结论覆盖它）→ 比较磁盘快照得出 `changed` → 广播事件。
- **依赖的变量从哪来**：`this.ownerContext.get('hmr')` 就是 `ctx.hmr` 服务（**HMR 插件没装/被禁用时这里是 `undefined`**）；`this.profile.dir` 是当前 profile 目录；`this.lockWaitMs` 是配置项（默认 `120000`，见 `packages\boot\plugin-manager\README.zh.md` 第 81 行）。
- **相邻的守卫**：`this.abort.signal.throwIfAborted()` 在拿锁后立刻检查取消；两个 catch 分支把"取消"与"失败"分成两个不同的状态值。默认值只是**兜底**——`result.application = await operation(result) ?? result.application` 让操作自己决定更精确的结果（例如覆盖已安装包时返回 `restart-required`，见 `packages\boot\plugin-manager\src\index.ts` 第 575 行）。
- **为什么判据是"服务在不在"而不是"配置文件怎么写"**：因为**能不能热生效，取决于树里到底有没有 watcher/重组合能力**，而不是取决于 profile 清单里声明了什么字符串。这就是结论 6（`patchReload` 没有读取者）为什么与本条并不矛盾：真正决定行为的机制就是这一行 `ctx.get('hmr')`。
- **附近的另一处复用**：同文件第 775–779 行的 `configure()` 也是同一判据——**有 HMR 就把操作包进 `hmr.runExclusive(apply)`，没有就直接跑**。所以结论 3 里"包安装/删除在队列之外"要说得准确些：**pnpm 进程在队列之外，把结果应用到组合（发布解析表、重新组合）在队列之内**（`README.zh.md` 第 92 行："pnpm 在 HMR 队列之外执行"）。

### Q2 HMR 在监听什么？重载的触发条件是什么？

**监听两类东西**：

1. **模块目录**：`config.root` 列表（base 里是 `[]`），`cwd = realpathSync(baseDir)`，忽略 `ignored` 默认四项，`ignoreInitial: true`，**只收 `change` 事件**，`debounce`（默认 100 ms）合并（`packages\boot\hmr\src\index.ts` 第 353–379、381–383、424 行）。
2. **三条精确配置路径**：profile 的 `cordis.patch.yml`、home 级 `cordis.patch.yml`、profile 的 `package.json`（**含尚不存在的父目录**，`awaitWriteFinish` 默认开，收 `add` / `change` / `unlink` 三种事件）（`packages\boot\hmr\src\index.ts` 第 328–350 行；`packages\boot\hmr\src\watch-config.ts` 第 9–25、45–49、71–73 行）。

**触发条件链**：文件事件 →（去抖合并）→ 进入 `runExclusive` 串行队列（嵌套会被拒绝）→ 若应用未就绪则**丢弃** → 逐路径分类 → 命中 §5.4/§5.5 里某条处置才产生实际效果 → Include 刷新与 `partialReload` 完成后 `await loader.await()`，最后发 `hmr/reload`。若判定为"无实际变化"（配置快照相同）或"仅 manifest 且不在 `loadCache`"，则**什么也不发生**。若文件既不是配置、也不在 `loadCache`、也不是 Include、也不在 `externals`，则只发一次 `hmr/change` 事件，不改动任何东西（`packages\boot\hmr\src\index.ts` 第 406–411 行）。

### Q3 `package.json` 里的 `patchReload: "live"` 对应什么行为？哪些 profile 启用、哪些禁用？

- **对应行为**（设计笔记的定义）：`live` = 启动后仍监视各 patch 层并重新组合；`startup` = 各层只在启动时应用一次，之后不装 watcher（`.agents\notes\implemented\architecture\2026-08-22-single-dsh-application-launcher.zh.md` 第 35 行）。
- **按设计笔记的清单**：`web` = `live`；`headless`、`sdk`、`sdk-minimal`、`acp` = `startup`；自定义 profile 默认 `live`（同文件第 27–33 行）。
- **代码现实**：**该字段没有任何读取者**（§6.3 实测：源码树、随附运行时、解包目录全部零匹配）。真正决定行为的是 `hmr` 行：`dsh-base` 在存在 `profileContext` 时启用它、`root: []`（`packages\bundle\base\cordis.patch.yml` 第 27–32 行），而 `headless` / `sdk-app` / `acp-app` 各自把它 `disabled: true`，`sdk-minimal` 不含该行。因此：**`web`、`desktop` 这类基于 base 的启动器 profile 得到"配置 live"，四个协议/一次性 profile 得到"startup"**——与设计笔记的清单一致，但**判据是 `hmr` 行的启用状态，而不是 profile manifest 里的字符串**。
- 关于该字段在本机 profile 里的存在形态：`$DSH_HOME\profiles\<名字>\package.json` 的 `dsh.profile` 里**可以**出现 `"patchReload": "live"`（这是**结构示意**，不是任何一台机器的取值）；也可以不出现——`initProfile()` 新建 profile 时只写 `name` / `private` / `dependencies` / `dsh.profile.bundles`，**从不写** `patchReload`（`packages\boot\app-boot\src\profile.ts` 第 254–273 行）。这解释了为什么同一个版本的不同 profile 在这个字段上不一致，而**行为却一致**：没人读它。
- **用户可见的落点**：插件管理器在无 HMR 时把操作结果标成 `restart-required`（`packages\boot\plugin-manager\src\index.ts` 第 804 行；`README.zh.md` 第 67 行）。

### Q4 为什么 bundle 层只在启动时读取？这带来什么限制？

> ⚠️ **第一次读请跳过本节后半**（runtime resolution 那三件事属 `2.9`/后续编）。

**先修正前提**：bundle 的 **patch 层不是**只在启动时读取。每轮真正执行的配置刷新都会重新读盘 bundle 的 `cordis.patch.yml`，因为 `readProfilePatches()` 每次都调用 `loadProfileDirectory()`（`packages\boot\app-boot\src\profile-context.ts` 第 63–74 行；`packages\boot\app-boot\src\profile.ts` 第 732–766 行）。测试直接证明了这点：新建 `node_modules\added\package.json` + `node_modules\added\cordis.patch.yml`、把 `added` 写进 `dsh.profile.bundles` 后，重载把该 bundle 的 patch 读了进来，条目 `include:bundled` 出现在树上（`packages\boot\hmr\tests\profile.spec.ts` 第 115–127 行）。

**真正"只在启动时构造"的三件事**：

1. **runtime resolution（包解析表）**：`createRuntimeResolution()` 在启动时构建整张 installation/profile 范围的包表（`packages\boot\app-boot\src\profile.ts` 第 441–474 行）。决策笔记第 11 行把原始缺陷写成一句原话："runtime resolution 只在启动时构造"。今天的补救是 `PluginPackages.refresh()` → `computeLatestResolution()` → `replace()`（`packages\boot\app-boot\src\profile-resolution\service.ts` 第 101–106 行；`packages\boot\app-boot\src\profile.ts` 第 515–521 行），由插件管理器在包操作的确定时点调用（`packages\boot\plugin-manager\src\index.ts` 第 781–788 行；决策笔记第 38–43 行的发布时点表）。
2. **bundle 包的磁盘内容**：包安装/删除刻意被排除在 HMR 队列之外（`packages\boot\hmr\README.zh.md` 第 57、92 行），HMR 明确"不处理 `node_modules` 包替换"（决策笔记第 22 行），且不支持在线替换/同路径重装（同文件第 82 行；被否决的备选方案见第 93 行）。
3. **bundle patch 文件的变更事件**：**没有任何 watcher 盯着它们**。HMR 只注册三条配置路径（`packages\boot\hmr\src\index.ts` 第 328–350 行），`node_modules` 又被模块 watcher 默认忽略（第 215–220 行），所以"单独改一个已装 bundle 的 patch"不会被察觉；它要等到下一次由 profile patch / home patch / bundles 列表变化引发的重组合，才会被顺带重读。`packages\boot\hmr\tests\profile.spec.ts` 第 124–127 行正好展示了这种"输入未变就不重组合"的早退。

**限制（实际后果）**：

- 装新包或覆盖已安装包后必须重启进程才能使用新版本（`packages\boot\plugin-manager\README.zh.md` 第 94、134 行；决策笔记第 82 行）。
- 新 bundle 想"立刻生效"，前提是它的包已经由 pnpm 装好、且解析表已发布；否则先重启。
- `node_modules` 下的 `package.json` 变化保留 Node 缓存的包配置：HMR 只对 `node_modules` **之外**的 manifest 做配置缓存失效（`packages\boot\hmr\README.zh.md` 第 61 行；`packages\boot\hmr\src\index.ts` 第 393 行；决策笔记第 53 行）。
- 浏览器 Client 的模块图有独立的浏览器侧加载机制（`packages\boot\hmr\README.zh.md` 第 97 行），`client-hmr` 是另一条线（`packages\bundle\web-app\cordis.patch.yml` 第 213–214 行）。
- 这些限制的根因是**可逆性成本**：在 `node_modules` 内在线替换要沿含 `node_modules` 的模块图判定受影响插件、避免共享库与 cordis 被重复求值，还要处理动态 import 漏边、模块副作用与 Worker——决策笔记第 93 行选择不做。

### Q5 HMR 是内核能力还是插件？它对"能不能热生效"这件事负什么责任？

**它是一个普通插件**：`@deepseek-ai/dsh-hmr` 以 `id: hmr` 由 `dsh-base` 插入（`packages\bundle\base\cordis.patch.yml` 第 27–32 行），注册 `ctx.hmr` 服务与两个事件（`packages\boot\hmr\src\index.ts` 第 21–39 行）。它**不重启进程**（`loader.exit()` 是宿主钩子，见 §5.12），也**不管理包**（包操作在插件管理器，见 Q1 表末几行）。

它对"能不能热生效"负的责任**恰好是两件**：① 提供那条串行队列与就绪闸门；② 提供"配置重组合 + 模块就地替换"这两个动作。因此**别人怎么判断"要不要重启"完全是看它在不在**——`ctx.get('hmr') !== undefined`（§5.13）。这也解释了为什么它的启用/禁用写在 YAML 里（结论 1、6）。

### Q6 `patchReload` 字段与「`hmr` 行是否启用」，哪一个才是真相？

> 第一次读请跳过：本题需要读设计笔记，属回查材料。

**真相是后者（`hmr` 行的启用状态）**，`patchReload` 只是一个**没有读取者的设计意图记录**（§6.3 实测）。两者的对应关系是：

| 设计笔记里的 `patchReload` | 代码里的等价物 |
|---|---|
| `live` | `hmr` 行启用（`profileContext` 在 → `disabled` 为 false），`root: []` → **只热重载配置** |
| `startup` | `hmr` 行被 `disabled: true`（`headless` / `sdk-app` / `acp-app`）或整行不含（`sdk-minimal`） |

**为什么设计意图与实现会分岔**：设计笔记第 35 行说得很清楚——`live` 用的是"启动器的**仅配置** watcher"，`startup` 则"不安装 watcher"；也就是说 `patchReload` 描述的是**同一个 `hmr` 行的两种启用状态**。实现时这个二值信息被直接编码进了 base 的 `disabled: !!js "!ctx.get('profileContext')"` 与各 mode bundle 的覆盖里，于是**字段本身就不再需要了**（标注为推断：这是"字段保留但无人读取"的一种合理解释；我未找到删除该字段的记录）。
