## 0. 怎么读这一课（先看这段）

### 0.1 这一课是什么、不是什么

**是**：LLM 层这一条接缝（seam）的**边界**——提供方要交出什么、消费方只能从哪里进、路由键是什么、默认值与路由分别在哪一层定下来。
**不是**：`StreamChunk` 每个字段的逐字定义（那是 `3.8`）、重试执行器怎么跑（`3.8`）、token 计量（`3.8`）、`GenerateOptions` 的完整字段表（`3.6`）。

### 0.2 现在只要记住这 5 件事

1. **整层只有一个必需方法**：提供方实现 `LlmAdapter` 的子类，**必须**写 `stream(options)`；其余 6 个方法都有基类默认实现。消费方只能从 `ctx.llm` 进。
2. **路由键是 `provider` 字符串，不是模型名**。`registerAdapter(['my-provider'], adapter)` 之后，请求里 `provider: 'my-provider'` 才选中这个适配器；换模型不需要重新注册。
3. **一个 `provider` 在一个 Context 里只能有一个适配器所有者**。重复注册以 `DUPLICATE_ADAPTER` 失败，而且**要么全成、要么全不成**——没有"后备适配器"这种配置。
4. **`prepareCall()` 把"这一次调用"钉在一个适配器代次上**，返回一个**只能派发一次**的句柄；派发时不会再查一遍适配器。
5. **默认模型不归 `ctx.llm` 管**。会话用哪条 `provider/model` 由 `ctx.agentDefaultModel`（部署默认）和 loop 的请求信封决定；`ctx.llm` 只负责最后一步"按 `provider` 找到适配器"，并在那里把失败规范化成一个终止 `finish` 分片。

### 0.3 明确授权：这些现在不用管

- **`StreamChunk` 的每个成员、`BlockAssembler` 的组装算法** —— 属于 `3.8`；本课只用到"适配器返回 `AsyncIterable<StreamChunk>`、流以终止 `finish` 结束"这两点。
- **Cordis 的 `ctx.effect` / `fiber` / `waterfall` 内部机制** —— 属于第二编；本课只用到三个可观察事实：注册随 fiber 卸载而撤销、`replace()` 是一个同步区段、`llm/stream` 是 waterfall（监听器可以改写参数或直接产出分片）。
- **`!!js` 表达式、patch 的叠加顺序** —— 属于 `1.2` / `1.4`；本课只在 §6.3 看一条真实的 patch 行。
- **`deepFreeze` / 请求信封字段级语义** —— 属于 `3.6`。

### 0.4 本课依赖前两课的词汇

`ctx` / 服务 / 插件 / `entry` / 层 由 `notes\1-结构与装配\1.1-名词与分层.md` 定义；`patch` / `insert` / 覆盖语义 由 `notes\1-结构与装配\1.2-装配顺序.md` 定义。本课不重复它们。

## 1. 最小词汇表（本课新增的 8 个词）

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **adapter 适配器** | 一个**会讲某种模型协议**的对象。它把 DSH 的通用消息翻译成某个提供方的线上格式，再把回包翻译回通用分片 | `class XxxAdapter extends LlmAdapter` |
| **provider** | **一条路由的名字**（字符串）。它是一个"槽位"，某个适配器占着它 | `'deepseek-official'`；请求里 `GenerateOptions.provider` |
| **seam 接缝** | 一种**按职责切开**的扩展点：一侧定义通用词汇，另一侧由插件实现具体协议 | 本层 = `packages\llm\llm` 定义 + `packages\llm\llm-deepseek` 实现 |
| **waterfall 瀑布事件** | 一种事件：监听器**排成一条链**，每个可以改写参数或**直接产出结果短路** | `ctx.waterfall(this, 'llm/stream', options, next)` |
| **`StreamChunk`** | 流里的**一个分片**，是一个**封闭联合类型**（7 个成员，没有第 8 种） | `types.ts` 第 452–464 行 |
| **`prepareCall`** | "把这次调用需要的事实**当场固定**下来"的动作，产出一个一次性句柄 | `PreparedLlmCall` / `PreparedAdapterCall` |
| **代次（generation）** | 一个适配器**某一时刻的状态**（端点、凭据引用、目录、策略）。HMR 或改配置会让"代次"变 | 代码里的注释用 `generation` 这个词 |
| **catalog 目录** | 适配器**建议性**公布的模型清单。**不是白名单**——没列出的模型 id 照样能请求 | `listModels()` / `LlmModelInfo` |

> ⚠️ 这 8 个词里，`seam` 与 `waterfall` 的完整语义分别属于第四编与第二编；本课只用上面这个程度——**"seam 就是把通用词汇和具体协议分开的那条线"、"waterfall 就是监听器链"**，够用来读本课全部源码。

**术语约定**：源码里是英文的（`provider` / `adapter` / `stream` / `waterfall`）就以**英文为正名**，中文只在这里注解一次。中文文档里的"提供方"指的是 `provider`，"适配器"指的是 `adapter`。

### 2.3 大白话版：用户说了一句话，模型那侧发生了什么

**完全不用上面的术语**，先建立画面（来源：`docs\architecture.zh.md` 第 92–111 行的轮次流程伪代码，本课只补"最后一段落到谁身上"）：

1. 循环要发一次模型请求，先问"这次用哪家、哪个模型"。
2. 如果这个会话从没选过模型，就用部署配好的默认值；如果日志里已经记过，就用日志里的那次。
3. 拿到"哪家/哪个"之后，它去**问 LLM 服务**："这家归谁管？"——服务在一张表里按名字查，查到就把它**当场钉住**，连同这个适配器此刻的模型能力（上下文窗口、输出上限、可选推理强度）和重试策略一起打包成一个**只能用一次**的凭证。
4. 请求被组装好、被记进日志，然后凭那张凭证交给适配器。
5. 适配器把通用消息翻译成自己家的格式发出去，把回包一点点吐成"分片"。
6. 服务在把请求交给适配器**之前**做几件事：校验这个模型真的支持请求里的选项；把适配器配置的默认值填进去；把文件引用换成一行句柄文本、把不支持的图片换成占位文本、按模型声明的模式投影工具更新。
7. 中途任何一步坏了，都不会让调用方去猜异常类型——服务把它变成一个**终止分片**（`error` 或 `aborted`）。

## 3. 结论先行（12 条，逐条带出处）

1. **适配器 seam 的接口边界 = 一个抽象类 + 一个注册函数 + 一个 waterfall。** 提供方侧要实现的只有一个抽象方法 `stream()`（`packages\llm\llm\src\index.ts` 第 290 行），其余 6 个方法都有基类默认实现（同文件第 208–291 行）；消费方侧入口是 `ctx.llm.stream()` / `prepareCall()`；路由键是 **`provider` 字符串**，不是模型名。
2. **`ctx.llm` 本身不含任何提供方代码。** 它由 `LlmRuntime` 实现，只拥有三张表：适配器注册表、可配置 provider 目录、模型发现 offer（第 343–348 行），服务自身没有配置（`packages\llm\llm\README.zh.md` 第 30 行）。
3. **一个 `provider` 在一个 Context 里只能有一个适配器所有者。** 重复注册以 `DUPLICATE_ADAPTER` 失败，且是**全有或全无**（第 425–447 行；测试 `packages\llm\llm\tests\service.spec.ts` 第 1466–1489 行）。所以"换供应商"是在**替换一个路由的所有者**，不是叠加一个后备。
4. **适配器实例不是"每次请求新建"的。** 注册返回的句柄可原位 `replace(providers)`，用于"路由集合由配置决定"的插件；DeepSeek 插件正是用它来在同一次同步区内刷新重试策略（`packages\llm\llm-deepseek\src\host.ts` 第 39–48 行；`packages\llm\llm\src\index.ts` 第 297–315 行、第 456–464 行）。
5. **默认模型与路由在两个不同的层决定，且不是同一件事。**
   - **部署默认（用哪条路由/哪个模型）**：`packages\core\agent-default-model` 的配置，即 `ctx.agentDefaultModel.currentSelection()`（`packages\core\agent-default-model\src\index.ts` 第 24–31 行、第 67–73 行）。它**不碰 LLM 层**，只给入口点一个 `ModelSelection`。
   - **本次调用实际用哪条路由**：写进 `AgentOptions`，再由 loop 落成 `LlmCallConfig` 并记进 `request/header`（`packages\core\agent-loop\src\agent.ts` 第 546–596 行）。
   - **最终按 `provider` 解析到哪个适配器**：`LlmRuntime.registration()`，发生在 `llm/stream` waterfall 的**终端 continuation**（`packages\llm\llm\src\index.ts` 第 978–982 行、第 1132–1142 行）。
6. **`prepareCall()` 是一次"代次绑定"。** 它把「适配器注册 + 适配器代次 + 模型能力 + 重试策略 + 已冻结配置」绑成一个**只能派发一次**的句柄，从而杜绝 HMR 把 A 代次的能力和 B 代次的端点拼在一起（第 929–976 行；`packages\llm\llm\README.zh.md` 第 108 行）。
7. **重试不属于本层。** 注册时只**捕获**策略，一次流仍是一次提供方尝试（`packages\llm\llm\README.zh.md` 第 74、157 行；`.agents\notes\implemented\architecture\2026-07-29-terminal-llm-stream-failures.zh.md` 第 17 行）。
8. **失败只有一种出口形状。** 适配器选择、同步分发、迭代器构造、`next()` 失败都被规范化成一个终止 `finish` 分片；而 middleware / 消费方 / 清理失败照旧抛出（`packages\llm\llm\src\index.ts` 第 1026–1115 行、第 1146–1154 行）。
9. **有且只有 7 种分片。** `StreamChunk` 是封闭联合：`block-start` / `text-delta` / `reasoning-delta` / `tool-call-delta` / `block-end` / `usage` / `finish`（`packages\llm\llm\src\types.ts` 第 452–464 行）。**协议顺序是硬约束**：`usage` 在 `finish` 之前，`finish` 之后不再有任何分片（`docs\subsystems\llm-streaming.zh.md` 第 300 行）。
10. **回放状态只在同一个适配器实例内部传递。** 历史路由与目标路由不属于同一实例时，`LlmRuntime` 在分发前把它剥掉（`packages\llm\llm\src\index.ts` 第 984–999 行、第 1080 行；`packages\llm\llm\README.zh.md` 第 115 行）。
11. **"最后一公里"由服务做，不由适配器做**：能力校验与默认值填入、文件/图片/工具更新投影、回放剥离、失败规范化，全在 `adapterStream()` 里（第 1026–1115 行）。适配器只负责"把这些已定型的消息翻译成我的协议"。
12. **真实适配器的依赖是注入的，不是 import 的。** `DeepSeekAdapterOptions` 里全是钩子（`packages\llm\llm-deepseek\src\types.ts` 第 93–116 行），所以传输库、凭据插件、路由插件可以分开打包、分开挂载。

## 4. 机制（源码对照，按块讲解）

本节共 18 块源码（清单与逐块粒度说明见 §8.5）。每块上方标 `文件路径 第 A–B 行`，块内省略处都有注释说明省了什么、为什么省。

### 4.1 问题①的底稿：接口边界就是这一个抽象类

先看类注释与第一个覆写点（后面每个方法的默认行为都在同一种形状里）：

`packages\llm\llm\src\index.ts` 第 202–226 行

```ts
/**
 * Provider-wire adapter for the harness message and stream vocabulary. Register implementations
 * with `ctx.llm.registerAdapter(providers, adapter)`. Every provider HTTP request must include
 * `attributionHeaders()`; prove the headers are added in the wire request or library header hook. The direct-fetch
 * DeepSeek and library-backed pi-ai adapters meet this contract through different internals.
 */
export abstract class LlmAdapter {                       // ← 类头：提供方边界
  /**
   * Describe one provider route owned by this adapter.
   * @param provider - a route passed to `registerAdapter()` for this instance.
   * @returns detached display metadata whose id must equal `provider`.
   */
  providerInfo(provider: string): LlmProviderInfo {       // ① 可覆写，有默认
    return { id: provider, name: provider }
  }

  /**
   * Return the provider-owned retry policy captured with this route.
   * @param _provider - a route passed to `registerAdapter()` for this instance.
   * @returns a resolved policy, or `undefined` to use the normal defaults.
   */
  providerRetryPolicy(_provider: string): ResolvedRetryPolicy | undefined {   // ② 可覆写
    return undefined
  }
  // …（第 227–284 行：imageRequestPricing / listModels / resolveModel / prepareCall 四个覆写点，
  //   形状完全相同，见下面两块；此处省略是为了先看清"类头 + 默认实现"这个骨架）
}
```

按块讲解：

- **做什么**：`abstract class` 声明了提供方必须遵守的形状；`providerInfo` 的默认实现是"名字就等于路由名"，`providerRetryPolicy` 的默认实现是"不声明策略"。
- **与哪个知识点相关**：结论 1（接口边界）。`abstract class` 在这里的作用是**只给形状、不给实现**——基类除了这一处之外没有别的东西，所以"提供方边界"字面上就是这个类。
- **为什么这么写（作者原文）**：类注释第一句是 *"Provider-wire adapter for the harness message and stream vocabulary."* —— 适配器的职责被限定为"把 harness 的消息与流词汇接到线上协议"，这也解释了为什么下面 `stream()` 的返回类型是分片而不是成品消息。

接着看中间两个覆写点（`listModels` / `resolveModel`），它们的 JSDoc 顺带说明了"目录是建议性的"：

`packages\llm\llm\src\index.ts` 第 240–267 行

```ts
  /**
   * List models this adapter can currently advertise for one owned provider.
   * Core routing accepts unlisted model ids; catalog-driven entry points such
   * as the GUI may require membership. Adapters used there must advertise
   * their available models; the base empty catalog offers no GUI selection.
   * @param _provider - one provider route owned by this adapter.
   * @returns discoverable models in adapter-preferred order.
   */
  listModels(_provider: string): Promise<readonly LlmModelInfo[]> {    // ③ 可覆写
    return Promise.resolve([])                                         //   默认：空目录
  }

  /**
   * Resolve all metadata available for one exact model. This query is
   * independent of the advisory catalog and does not validate request routing.
   * @param provider - one provider route owned by this adapter.
   * @param model - exact model id passed to {@link GenerateOptions.model}.
   * @param _signal - cancellation for this exact-model lookup; asynchronous
   *   implementations must settle promptly after it aborts.
   * @returns provider/model identity plus any context, call-default, and reasoning metadata.
   */
  resolveModel(
    provider: string,
    model: string,
    _signal?: AbortSignal,
  ): Promise<LlmResolvedModelInfo> {                                   // ④ 可覆写
    return Promise.resolve({ provider, id: model, name: model })       //   默认：只有身份三元组
  }
  // …（第 227–239 行的 imageRequestPricing 与第 269–284 行的 prepareCall 见下一块；
  //   此处省略这两块是为了让"目录"与"精确模型"两个概念挨在一起对比）
```

按块讲解：

- **做什么**：③ 给出"选择器里能看到的模型"；④ 给出"某个确切模型 id 的能力元数据"。两者**不是一回事**：注释原文 *"This query is independent of the advisory catalog and does not validate request routing."*
- **与哪个知识点相关**：结论 1（可选覆写点）与词汇表里的 **catalog（建议性目录）**。
- **为什么这么写**：默认值本身就是契约的一部分——基类目录为空（"不向 GUI 提供模型"，`packages\llm\llm\README.zh.md` 第 28 行），基类不给重试策略，基类不给图片定价。**默认值撑起了"最小适配器只需要写一个方法"这件事。**

最后两个覆写点（`prepareCall` / `stream`），它们就是"代次绑定"在提供方一侧的钩子：

`packages\llm\llm\src\index.ts` 第 269–291 行

```ts
  /**
   * Bind exact model metadata and the eventual request dispatch to one adapter generation.
   * Dynamic adapters override this so settings changes between preparation and
   * dispatch cannot combine one generation's capabilities with another's endpoint.
   * @param provider - registered provider route.
   * @param model - exact model id.
   * @param signal - cancellation for model resolution.
   * @returns model metadata and a one-generation stream entry point.
   */
  async prepareCall(provider: string, model: string, signal?: AbortSignal): Promise<PreparedAdapterCall> {
    return {                                                            // ⑤ 默认实现
      model: await this.resolveModel(provider, model, signal),          //    能力 = resolveModel()
      stream: options => this.stream(options),                          //    分发 = stream()
    }
  }

  /**
   * Stream one model call as raw chunks. The only required method.
   * @param options - the fully-assembled request; implementations must honor `options.signal`.
   * @returns the chunk stream, obeying the adapter contract documented on `StreamChunk`.
   */
  abstract stream(options: GenerateOptions): AsyncIterable<StreamChunk>   // ⑥ 唯一必需项
}
```

按块讲解：

- **做什么**：⑤ 的默认实现把"能力查询"和"分发"配成一对（**同一次 `prepareCall` 调用里取到的**）；⑥ 没有任何实现体——`abstract` 那一行就是全部。
- **与哪个知识点相关**：结论 1（唯一必需方法）与结论 6（代次绑定）。**关键**：默认实现之所以"够用"，是因为它把 `resolveModel` 与 `stream` 在**同一次调用**里配对；动态适配器（如 DeepSeek）覆写它，是为了把"端点 + 凭据引用"也一起钉住。
- **为什么是 `AsyncIterable` 而不是 `Promise`**（R8：这是从源码形状直接读出的事实，不是推断）：返回类型是 `AsyncIterable<StreamChunk>`，所以"调用时同步抛"和"迭代中抛"都是适配器的合法失败形态，由服务统一规范化（见 §4.8）。

### 4.3 路由的拓扑：注册、原子校验、同步提交

这是"一个 `provider` 只能有一个所有者"这句话的实现处。先看注册入口与它的守卫：

`packages\llm\llm\src\index.ts` 第 381–418 行

```ts
  /**
   * Register an adapter for the given provider routes. Throws `LlmError` with code
   * `DUPLICATE_ADAPTER` if any provider already has an adapter (all-or-nothing).
   * Disposed with the fiber.
   * @param providers - every provider route this adapter should serve.
   * @param adapter - the adapter that streams calls for those providers.
   * @returns the disposer, carrying {@link AdapterRegistrationHandle.replace}.
   */
  registerAdapter(providers: string[], adapter: LlmAdapter): AdapterRegistrationHandle {
    // The routes this registration currently holds; `replace` rewrites it, and
    // the disposer releases whatever it holds at disposal time.
    const owned = new Set<string>()                      // ① 本次注册当前占着的路由
    // The disposer has run: `owned` being empty cannot say so on its own,
    // because `replace([])` legally leaves a live registration holding none.
    let released = false                                 // ② 已释放标记：空集合不能代表已释放
    const dispose = this.ctx.effect(function* (this: LlmRuntime) {   // ③ 注册被 effect 承载
      if (providers.length === 0) throw new LlmError('an adapter must register at least one provider', 'INVALID_ADAPTER')
      this.commitRoutes(owned, this.prepareRoutes(providers, adapter, owned))   // ④ 先校验，再提交
      yield () => {                                      // ⑤ 卸载时撤销
        released = true
        for (const provider of owned) this.adapters.delete(provider)
        owned.clear()
        this.emitAdaptersUpdated()
      }
    }.bind(this), 'llm.registerAdapter()')
    // ctx.effect's disposer returns Promise<void>; our disposer API is
    // synchronous fire-and-forget — discard the (always-resolved) promise.
    const handle = (() => void dispose()) as AdapterRegistrationHandle      // ⑥ 返回的"释放器"本身是个函数
    handle.replace = (next: string[]): void => {
      // Registering here would leak: the effect's disposer already ran, so
      // nothing remains to release whatever this call would put in the map.
      if (released) {                                    // ⑦ 已释放的注册不允许 replace
        throw new LlmError('a disposed adapter registration cannot replace its routes', 'REGISTRATION_DISPOSED')
      }
      this.commitRoutes(owned, this.prepareRoutes(next, adapter, owned))
    }
    return handle
  }
  // …（没有任何省略：本块是完整的 registerAdapter）
```

按块讲解：

- **做什么**：`registerAdapter` 返回的不是一个普通函数，而是**一个可调用的释放器 + 一个 `replace` 方法**（`AdapterRegistrationHandle`，第 297–315 行定义了它）。
- **依赖的变量从哪来**：`owned` 在闭包里被 `commitRoutes` 与释放器**共用**——所以"这个注册当前占着哪些路由"只有一份事实；`released` 是第二个变量，注释写明它为什么必须存在：`replace([])` 会让一个**活的**注册合法地持有零条路由，于是"集合为空"不能用来表示"已释放"。
- **相邻的守卫**：④ 之前有 `providers.length === 0` 的抛错（**空注册非法**，而 `replace([])` 合法——两处的合法性故意不同）；⑦ 是 `replace` 的第一道守卫。
- **与哪个知识点相关**：结论 3（一个路由一个所有者）、结论 4（原位 `replace`）。
- **为什么这么写**：注册由 `ctx.effect` 承载 = **注册是副作用、随 fiber 卸载自动撤销**（第一编的世界观在这里的具体落点）；`replace` 的存在则是为了"路由集合由配置决定"的场景——不用先撤再注册。

再看"全有或全无"是怎么做到的：

`packages\llm\llm\src\index.ts` 第 420–447 行

```ts
  /**
   * Validate one candidate route set for `adapter`, treating routes this
   * registration already holds as available. Nothing is mutated: a rejected
   * candidate leaves the registry exactly as it was.
   */
  private prepareRoutes(providers: string[], adapter: LlmAdapter, owned: ReadonlySet<string>): AdapterRegistration[] {
    const unique = new Set<string>()                       // ① 本批内的去重
    const registrations: AdapterRegistration[] = []
    for (const provider of providers) {                     // ← 循环头：逐个候选校验
      if (provider.length === 0) throw new LlmError('adapter provider names must be non-empty', 'INVALID_ADAPTER')
      if (unique.has(provider) || (this.adapters.has(provider) && !owned.has(provider))) {   // ② 两道冲突守卫
        throw new LlmError(`an adapter for provider "${provider}" is already registered`, 'DUPLICATE_ADAPTER')
      }
      const info = adapter.providerInfo(provider)           // ③ 问适配器要显示元数据
      if (typeof info.id !== 'string' || info.id !== provider || typeof info.name !== 'string' || info.name.length === 0) {
        throw new LlmError(`adapter metadata for provider "${provider}" must preserve its id and have a non-empty name`, 'INVALID_ADAPTER')
      }
      unique.add(provider)
      const retryPolicy = adapter.providerRetryPolicy(provider)            // ④ 注册时【捕获】策略
        ?? resolveRetryPolicy(undefined, `llm: provider "${provider}" retryPolicy`)
      registrations.push({
        adapter,
        provider: { id: info.id, name: info.name },
        retryPolicy,                                                       // ⑤ 策略随注册一起存
      })
    }
    return registrations
  }
  // …（没有任何省略）
```

按块讲解：

- **做什么**：这个函数**只读不写**：它把候选集合整批检查完，返回一个新数组。真正的写入在下一个函数。
- **相邻的守卫**：② 的 `(this.adapters.has(provider) && !owned.has(provider))` 是"这条路由被别人占了"——`!owned.has(provider)` 那一半让"我自己已经占着的路由"在 `replace` 时不算冲突。
- **③ 的失败条件很具体**：适配器返回的 `providerInfo(provider).id` **必须等于传进来的 `provider`**，`name` 必须非空。这就是抽象类注释里 *"whose id must equal `provider`"* 的执行处。
- **④⑤ 与哪个知识点相关**：结论 4、结论 7。**策略只在注册时读一次**，之后随注册记录保存（`AdapterRegistration.retryPolicy`，第 1156–1160 行），这就是"重试策略是唯一被注册捕获的事实"（`packages\llm\llm-deepseek\README.zh.md` 第 134 行）。
- **为什么"先整体校验再提交"**：注释原文 *"Nothing is mutated: a rejected candidate leaves the registry exactly as it was."* —— 半成功状态在拓扑上是灾难（会出现"一半路由换了新适配器"）。

### 4.5 `prepareCall()`：代次绑定的完整实现

`packages\llm\llm\src\index.ts` 第 921–976 行

```ts
  /**
   * Resolve one call under its current adapter registration. The returned
   * one-shot handle keeps that registration across header logging and dispatch,
   * so HMR cannot combine one adapter's capability result with another adapter.
   * @param config - provider/model route and optional request controls.
   * @param signal - optional cancellation for adapter-owned capability lookup.
   * @returns a prepared config and its registration-bound stream entry point.
   */
  async prepareCall(config: LlmCallConfig, signal?: AbortSignal): Promise<PreparedLlmCall> {
    const registration = this.registration(config.provider)                       // ① 固化注册（NO_ADAPTER 在此抛）
    const adapterCall = await registration.adapter.prepareCall(config.provider, config.model, signal)   // ② 交给适配器钉代次
    const modelInfo = this.normalizeModelInfo(registration, config.model, adapterCall.model)            // ③ 校验能力元数据
    const resolved = this.resolveCallWithInfo(config, modelInfo)                   // ④ 填默认值 / 校验推理强度
    const resolvedConfig = deepFreeze(structuredClone(resolved.config))            // ⑤ 分离 + 深冻结
    const context = resolved.context === undefined
      ? undefined
      : deepFreeze(structuredClone(resolved.context))
    const adapterDefaults = deepFreeze<LlmCallConfigAdapterDefaults>({             // ⑥ 标出"哪些默认值是适配器给的"
      ...config.reasoningEffort === undefined && resolvedConfig.reasoningEffort !== undefined
        ? { reasoningEffort: true }
        : {},
      ...config.maxTokens === undefined && resolvedConfig.maxTokens !== undefined
        ? { maxTokens: true }
        : {},
    })
    let dispatched = false                                                         // ⑦ 一次性闸门
    return Object.freeze({
      config: resolvedConfig,
      retryPolicy: registration.retryPolicy,                                       // ⑧ 策略随句柄出去
      adapterDefaults,
      ...context === undefined ? {} : { context },
      ...modelInfo.inputModalities === undefined
        ? {}
        : { inputModalities: Object.freeze([...modelInfo.inputModalities]) },
      ...modelInfo.systemPromptUpdate === undefined ? {} : { systemPromptUpdate: modelInfo.systemPromptUpdate },
      ...modelInfo.toolUpdate === undefined ? {} : { toolUpdate: modelInfo.toolUpdate },
      stream: (options: GenerateOptions): AsyncIterable<StreamChunk> => {          // ⑨ 唯一出口
        if (dispatched) {                                                          //    闸门一：只能派发一次
          throw new LlmError('a prepared LLM call can only be dispatched once', 'INVALID_PREPARED_CALL')
        }
        if (!callConfigEquals(options, resolvedConfig)) {                          //    闸门二：配置不得漂移
          throw new LlmError(
            'prepared LLM call config changed before adapter dispatch',
            'INVALID_PREPARED_CALL',
          )
        }
        dispatched = true
        return this.streamWithRegistration(options, {                              //    带着固定注册进 waterfall
          registration,
          config: resolvedConfig,
          modelInfo,
          dispatch: options => adapterCall.stream(options),
        })
      },
    })
  }
  // …（没有任何省略）
```

按块讲解：

- **做什么**：一次调用在这里被"定稿"：注册固化了、能力查过了、默认值填好了、配置冻结了，并且产出一个**带两道闸门**的 `stream`。
- **依赖的变量从哪来**：
  - `registration` = `this.registration(config.provider)`（第 978–982 行：`adapters.get(provider)`，查不到抛 `NO_ADAPTER`）。
  - `adapterCall` = **适配器自己的** `prepareCall()` 结果（基类默认实现见 §4.1 ⑤；DeepSeek 覆写它来固定端点与凭据引用）。
  - `modelInfo` = 校验过的能力元数据（`normalizeModelInfo`，第 750–859 行）。
  - `resolved` = 填过默认值的配置（`resolveCallWithInfo`，第 884–919 行）。
- **⑧ 为什么把策略放进句柄**：这样"记 header 的那次解析"和"真正分发的那次调用"用的是**同一份策略**——即使之后 `replace()` 换掉了路由，正在进行的这次失败的恢复策略也不变（`docs\subsystems\llm-streaming.zh.md` 第 312 行的表述："调用选定实际提供服务的注册后…之后释放或替换路由都无法改变进行中失败的恢复策略"）。
- **⑥ 为什么需要 `adapterDefaults`**：调用方没提 `reasoningEffort`、是适配器填的——恢复会话时**不能被当成用户的显式选择**（`packages\api\session-controller\src\agent.ts` 第 303–308 行的注释原文：*"An effort the adapter defaulted is not a conversation choice"*）。
- **⑨ 的两道闸门都是 `INVALID_PREPARED_CALL`**：一是复用（"只能派发一次"），二是漂移（配置在派发前变了）。二者都是**误用错误**，同步抛出，不走失败分片路径。
- **同一约束在 `adapterStream()` 里又查一次**（第 1047–1052 行），这不是重复——`stream()` 返回 iterable 之后，调用方仍可能改写自己传进去的 options 对象（见 §4.6 的 ②）。

   * Final adapter boundary. Adapter selection, dispatch, iterator construction,
   * and iteration failures become one terminal failure chunk. Middleware and
   * downstream consumer failures remain thrown plugin or consumer errors.

  private async * adapterStream(
    options: GenerateOptions,
    prepared?: PreparedDispatch,
  ): AsyncGenerator<StreamChunk> {
    let iterator: AsyncIterator<StreamChunk>
    try {
      const registration = prepared?.registration ?? this.registration(options.provider)   // ① 唯一的查找点
      const adapter = registration.adapter
      let modelInfo: LlmResolvedModelInfo
      let resolvedConfig: LlmCallConfig

      if (prepared === undefined) {                                              // ② 没被 prepareCall 钉过

        modelInfo = this.normalizeModelInfo(registration, options.model, adapterCall.model)
        resolvedConfig = this.resolveCallWithInfo(options, modelInfo).config
        dispatch = options => adapterCall.stream(options)

        resolvedConfig = prepared.config
        dispatch = prepared.dispatch

        throw new LlmError(
          'prepared LLM call config changed before adapter dispatch',
          'INVALID_PREPARED_CALL',
        )

      const resolvedOptions = callConfigEquals(options, resolvedConfig)
        ? options

          : { ...options, ...resolvedConfig }

    const consumer = new AbortController()                                     // ① 本层自己的取消源
    const signal = options.signal === undefined ? consumer.signal : AbortSignal.any([consumer.signal, options.signal])
    using watchdog = idleWatchdog(signal, connection.streamIdleTimeoutMs, 'MESSAGES_IDLE')   // ② 空闲看门狗
    const iterator = this.request(options, connection, watchdog.signal, () => { watchdog.pulse() })
    try {
      while (true) {                                                           // ← 循环头：逐分片搬运
        const next = await watchdog.next(iterator)                             // ③ 由看门狗包住 next()
        if (next.done) return
        yield next.value
      }
    } catch (error) {
      if (timeoutOf(watchdog.signal, 'MESSAGES_IDLE') !== undefined) throw new LlmError('DeepSeek Messages stream idle timeout', 'TIMEOUT', { cause: error })
      if (options.signal?.aborted) throw new LlmError('DeepSeek Messages request aborted', 'ABORTED', { cause: error })
      if (error instanceof LlmError) throw error                               // ④ 已有的 LlmError 原样上抛
      throw new LlmError('DeepSeek Messages transport failed', 'TRANSPORT', { cause: error })
    } finally {
      consumer.abort()                                                         // ⑤ 无论如何都中止自己的 reader
      try { await iterator.return(undefined) } catch (_abortedRequestCleanup) {
        // The request already settled; aborting its reader cannot replace that outcome.
      }
    }
  }

## 6. 问题②的落地：换一个模型供应商要动哪些地方

**结论：最小改动是"1 个适配器类 + 1 个插件包 + 1 条 profile patch 行"；要让它在配置界面可选、能取凭据、能被发现模型，再加 3 处；而**不需要**动 loop、会话日志、工具或 UI 的任何一行。**

必须做的：

1. **实现 `LlmAdapter` 子类**，至少 `stream()`，按 §5 打勾（`docs\cookbook\adding-an-llm-adapter.zh.md` 第 9–21 行）。
2. **写一个插件包**：导出 `name`、`inject = ['llm']`、`Config`（schemastery，可带环境变量回退）与 `apply(ctx, config)`，在 `apply` 内 `ctx.llm.registerAdapter([route], new MyAdapter(...))`（同文件第 14–21、23 行；真实例子见本课 §4.10）。
3. **在 profile / bundle 的 patch 里挂这条插件行**，给它 `id` 与 `config`（patch 的语义见 `1.2`）。

按需要加做的：

4. **凭据**：Cordis 原生方式（schemastery + 环境变量 / `ctx.credentials`），**不要**自创密钥文件约定（`docs\cookbook\adding-an-llm-adapter.zh.md` 第 23 行）。DeepSeek 的做法是 `resolveAuth` 钩子 + `assertUsableApiKey`，缺 key 抛 `MISSING_CREDENTIAL`、格式非法抛 `INVALID_CREDENTIAL`（`packages\llm\llm-deepseek-api-key\src\index.ts` 第 20–35 行）。
5. **配置面与目录**：`ctx.llm.registerConfigurableProviders([...])` 声明"这条路由可以被配置激活"，并指向 settings 命名空间；想让用户"问端点有哪些模型"，再 `registerModelDiscovery`（`packages\llm\llm-deepseek-api-key\src\index.ts` 第 36–38 行；`packages\llm\llm\src\index.ts` 第 483–536、557–577 行）。
6. **模型能力**：覆写 `resolveModel()` 返回 `context` / `defaultMaxTokens` / `reasoning` / `systemPromptUpdate` / `toolUpdate`；只想给选择器用就覆写 `listModels()`。**目录是建议性的、不是白名单**——未列出的模型 id 仍会被转发（`docs\subsystems\llm-streaming.zh.md` 第 437 行；`packages\llm\llm\README.zh.md` 第 28 行）。

明确的**不要做 / 做不到**：

- 不能让两个适配器同时拥有同一路由来"做故障转移"：重复拥有是配置错误，没有顺序规则或回退（`.agents\notes\implemented\architecture\2026-07-14-provider-routed-llm-adapters.zh.md` 第 25 行）。要换实现就换挂载哪一行。

## 附录 A 关键问题与答案

> ✅ 十道题**全部给出明确答案**，不留空、不写"待补充"。Q1–Q4 是路线图（步骤 3.7）点名的验收题；**Q5–Q10 属于后续编才会展开的细节**（`StreamChunk` 逐字段、`!!js` 求值、patch 叠加、HMR 代次、凭据存储实现），**第一次读可以跳过**，回查时再看。

### Q1 适配器接口边界在哪？

**答案：提供方边界 = 抽象类 `LlmAdapter`（唯一必写的方法是 `stream()`）；消费方边界 = `ctx.llm`（`LlmRuntime`）的 `stream()` / `prepareCall()`；路由键 = `GenerateOptions.provider` 字符串；数据形状 = 封闭联合 `StreamChunk`。**

- **提供方必须给的只有一样**：`abstract stream(options): AsyncIterable<StreamChunk>`（`packages\llm\llm\src\index.ts` 第 290 行，JSDoc 写明 *"The only required method."*）。另外 6 个方法是可选覆写点，都有确定默认（§4.1）：基类目录为空、基类不给重试策略、基类不给图片定价。
- **消费方只能从 `ctx.llm` 进**：它是"进入提供方适配器的唯一受支持路径"（`packages\llm\llm\README.zh.md` 第 34 行）；loop、会话标题生成器、压缩摘要器都走它（第 30 行）。
- **边界之外的三件事被显式排除**：重试（归 `dsh-llm-retry`）、缓存与速率限制（同上）、提供方协议细节（归适配器本身）（第 34、157 行）。
- **边界内的"最后一公里"由服务完成，而不是适配器**：能力校验与默认值填入、文件/图片/工具更新投影、跨适配器回放状态剥离、失败规范化，都在 `adapterStream()` 里（第 1026–1115 行，§4.6）。适配器只负责"把这些已经定型的消息翻译成我的协议"。
- **一个容易误解的点**：`stream()` 的**返回类型是 `AsyncIterable`，不是 Promise**，所以"同步抛出"和"迭代中抛出"都是适配器的合法失败形态，由服务统一规范化（第 1082–1085、1096–1100 行，§4.6/§4.7）。

### Q2 换一个模型供应商要动哪些地方？

**答案：最小改动 = 1 个适配器类 + 1 个插件包 + 1 条 patch 行；可选再加 3 处（凭据、可配置目录、模型能力/发现）。loop、会话日志、工具、UI 一行都不用动。** 完整清单与四条"不要做"见 §6；真实布局见 §6.1。

### Q3 默认值与路由怎么定？

**答案：分三层，且"默认模型"这一层完全不经过 `ctx.llm`。`ctx.llm` 只负责最后一层——按 `provider` 解析到适配器。**

| 层 | 决定什么 | 谁决定 | 出处 |
|---|---|---|---|
| L1 部署默认 | 一个会话从未选择过模型时用哪条 `provider/model`（可带 `reasoningEffort`） | `ctx.agentDefaultModel`（`AgentDefaultModelConfig`），配置键 `provider`/`model`/`reasoningEffort` | `packages\core\agent-default-model\src\index.ts` 第 24–31、51–55、67–73 行（§4.11 L1） |
| L2 会话/请求路由 | 这一次调用实际写进请求信封的 `LlmCallConfig` | 入口点把 selection 变成 `AgentOptions`；loop 的 `agent/request` waterfall 可在任意步骤替换；随后落进 `request/header` | `packages\bundle\headless\src\index.ts` 第 332–333 行；`packages\core\agent-loop\src\agent.ts` 第 546–596、609–634 行（§4.11 L2） |
| L3 适配器解析 | 这个 `provider` 由哪个适配器实例服务 | `LlmRuntime.registration(options.provider)`，位于 `llm/stream` waterfall 终端 | `packages\llm\llm\src\index.ts` 第 978–982、1032、1132–1142 行（§4.4） |

补充要点，全部可查：

- **默认值不是 `ctx.llm` 的属性**：`LlmRuntime` 的构造函数只做 `super(ctx, 'llm')`，没有配置（第 350–352 行，§4.2）；base patch 里 `llm` 行也没有 config（`packages\bundle\base\cordis.patch.yml` 第 34–35 行）。
- **部署默认与"文档示例"是两件事**：base 里 `agent-default-model` 写的是 `deepseek-official` / `deepseek-flash`（第 82–86 行）；README 示例里的 `deepseek-v4-flash` 只是协议示例、不是默认值（`packages\llm\llm\README.zh.md` 第 52 行）。二者**不要混用**。
- **恢复会话时不读默认值**：`selectionFor()` 的 `current` 只有"没有已记录 header"时才回落到 `defaultModel.currentSelection()`，否则以日志里的 `request/header` 为准（`packages\api\session-controller\src\agent.ts` 第 293–310 行）。这正是"模型可见 ⟺ 已记录"在路由上的体现。
- **适配器默认值不占会话选择**：由适配器填入的 `reasoningEffort`/`maxTokens` 会被标成 `adapterDefaults`（`packages\llm\llm\src\index.ts` 第 938–945 行，§4.5 ⑥），恢复时不被当成用户的显式选择（`packages\api\session-controller\src\agent.ts` 第 303–308 行）。
- **没有默认值兜底时 loop 直接拒绝**：`provider` 与 `model` 有一个为空就抛 `has no provider/model`（`packages\core\agent-loop\src\agent.ts` 第 581–583 行）。
- **路由可变但不重建生命周期**：`agent/request` 可以在任意步骤返回替换后的 `provider`/`model`，会话无需重启（`.agents\notes\implemented\architecture\2026-07-14-provider-routed-llm-adapters.zh.md` 第 21 行）；`llm/stream` 监听器也能在查找前改写（`packages\llm\llm\src\index.ts` 第 63–75 行的 JSDoc：*"call `next()` to reach the resolved adapter's stream, or yield your own chunks to short-circuit."*）。

### Q4 `prepareCall` 做了什么？

**答案：把"注册 + 代次 + 能力 + 策略 + 冻结配置"绑成一个只能派发一次的句柄，从而让"记 header 的那次解析"和"真正分发的那次调用"用同一份事实。** 逐行看 `LlmRuntime.prepareCall()`（`packages\llm\llm\src\index.ts` 第 929–976 行，源码见 §4.5）：

1. `this.registration(config.provider)` —— 先固化适配器注册，`NO_ADAPTER` 在此抛出（第 930 行、第 978–982 行）。
2. `registration.adapter.prepareCall(provider, model, signal)` —— 让**适配器自己**把"模型元数据"和"最终分发"绑到同一代次；基类默认实现只是把 `resolveModel()` 与 `stream()` 配对（第 931 行、第 278–283 行）。DeepSeek 覆写它来**先取连接快照**（端点 + 凭据引用 + 目录），因此配置在准备之后变化不会污染这次调用（`packages\llm\llm-deepseek\src\adapter.ts` 第 43–46 行，§4.8 ⑦）。
3. `normalizeModelInfo(...)` —— 校验适配器返回的元数据（`provider`/`id` 必须一致、`contextWindow` 必须正整数、`systemPromptUpdate` 只允许 `'in-history'`、`toolUpdate` 只允许两个值、推理强度集合非空且默认值必须在集合内），失败给出 `INVALID_MODEL_INFO` / `INVALID_MODEL_CONTEXT` / `INVALID_MODEL_MAX_TOKENS` / `INVALID_MODEL_REASONING`（第 932 行、第 750–859 行）。
4. `resolveCallWithInfo(...)` —— 填入 `maxTokens` 默认值；推理强度：显式或默认值不在集合内则抛 `UNSUPPORTED_REASONING_EFFORT`（**不裁剪、不改写**），否则落成生效值（第 933 行、第 884–919 行）。
5. `deepFreeze(structuredClone(...))` —— 配置与上下文都分离且深冻结，调用方拿不到适配器内部对象的别名（第 934–937 行）。
6. 计算 `adapterDefaults` —— 明确标出哪些字段是**适配器给的**而不是调用方提的（第 938–945 行）。
7. 返回一个 `Object.freeze` 的 `PreparedLlmCall`：`config`、`retryPolicy`（注册时捕获的不可变策略）、`context`、`inputModalities`、`systemPromptUpdate`、`toolUpdate`、`adapterDefaults`，以及 `stream(options)`（第 947–975 行）。
8. `stream(options)` 的两道闸：`dispatched` 已置位则抛"只能派发一次"；`callConfigEquals(options, resolvedConfig)` 不成立则抛"配置在派发前变化"。两者都是 `INVALID_PREPARED_CALL`（第 957–967 行）。派发时把 `registration/config/modelInfo/dispatch` 一起交给 `streamWithRegistration`（第 968–973 行），因此**后续的适配器查找不会再发生**——注册已被钉住。
9. 该约束在 `adapterStream()` 里被**再校验一次**（第 1047–1052 行），这不是重复：`stream()` 返回 iterable 后调用方仍可能改写自己传入的 options 对象。

**为什么必须这样**：`prepareCall()` 的注释写明 *"so HMR cannot combine one adapter's capability result with another adapter"*（第 921–928 行）；README 的表述是"把这些事实、分离的上下文与重试策略绑定到执行最终分发的精确适配器代次"（`packages\llm\llm\README.zh.md` 第 108 行）。真实适配器的动机更具体——DeepSeek 的 `prepareCall` 要固定端点与凭据引用、固定模型能力，同时允许后续调用读到新配置（`.agents\notes\implemented\feature\2026-09-07-deepseek-messages-adapter.zh.md` 第 13 行；`packages\llm\llm-deepseek\tests\prepared-call.spec.ts` 第 42–59 行）。

**谁用它**：agent loop 的 `prepareRequest()`（`packages\core\agent-loop\src\agent.ts` 第 587 行），并且在 `NO_ADAPTER` 时容忍失败以便 middleware 服务路由（第 589–593 行）。**谁不用它**：一次性辅助调用可以直接 `ctx.llm.stream()`——但那样就只尝试一次、且能力校验仍在终端边界发生（第 1037–1040 行）。

### Q5 seam 三角色（Service Definition / Service Provider / Consumer）在本层分别是谁？*（第一次读请跳过）*

**答案**：Service Definition = `packages\llm\llm`（`LlmAdapter` 抽象类 + 词汇 + `LlmRuntime` 注册表）；Service Provider = `packages\llm\llm-deepseek`（和 `llm-pi-ai` 等）的适配器 + 它自己的 provider 插件；Consumer = agent loop（`packages\core\agent-loop`）。
**为什么 Definition 与 Consumer 在同一个包**：`.agents\notes\implemented\architecture\2026-06-13-capability-seams.zh.md` 第 25 行给出的判断就是"Consumer 就是 agent loop，适配器作为 Service Provider 包"。

### Q6 为什么"重复拥有同一路由"不能当故障转移用？*（第一次读请跳过）*

**答案**：因为注册表是**拓扑的唯一拥有者**，一个 `provider` 键只能映射一个 `AdapterRegistration`；第二次注册在校验阶段就以 `DUPLICATE_ADAPTER` 抛错，**根本不会进入注册表**，所以不存在"顺序规则"或"回退"可依赖。要换实现就换挂载哪一行（`.agents\notes\implemented\architecture\2026-07-14-provider-routed-llm-adapters.zh.md` 第 25 行）。源码见 §4.3 的 `prepareRoutes` 第二道守卫。

### Q7 为什么"一次流 = 一次提供方尝试"，重试在别处？*（第一次读请跳过）*

**答案**：本层在注册时**只捕获策略**（`AdapterRegistration.retryPolicy`，§4.3 ④、§4.12），把策略交给准备好的调用句柄（§4.5 ⑧），但从不自行重跑；`dsh-llm-retry` 在**持久 agent 步骤边界**上执行它（`packages\llm\llm\README.zh.md` 第 157 行；`docs\subsystems\llm-streaming.zh.md` 第 303 行）。适配器还必须**禁用库内部重试**，否则一次调用会变成多次提供方尝试、预算成倍放大（`.agents\notes\implemented\architecture\2026-06-21-bounded-llm-request-recovery.zh.md` 第 71 行）。

### Q8 `usage` 与 `finish` 的顺序为什么是硬约束？*（第一次读请跳过）*

**答案**：因为 `finish` 是**终止**信号，消费方（组装器、计量器）在收到它之后就停止阅读；若 `usage` 排在后面就会被丢掉，计量与结算会静默缺失。文档给的做法是**把两者都推迟到提供方的流结束标记再统一 flush**，这样"末尾只有 usage 的分片"也不会违反顺序（`docs\subsystems\llm-streaming.zh.md` 第 300 行）。`StreamChunk` 的 JSDoc 同样写着 *"Adapters emit usage before the terminal finish and nothing afterward"*（`packages\llm\llm\src\types.ts` 第 444–451 行）。

### Q9 为什么"文件投影"必须无条件做，而"图片投影"有条件？*（第一次读请跳过）*

**答案**：文件（`FileBlock`）**没有任何提供方**能原生接收——所以每条路由都收到一行确定性句柄文本，模型需要时用文件工具去读保存的副本（`packages\llm\llm\README.zh.md` 第 118 行；源码注释 *"Files are never dispatched natively"*，`packages\llm\llm\src\index.ts` 第 1058 行）。图片则取决于**模型声明的模态**：声明了 image 的模型走路由专用请求版本，未声明的模型收到确定性占位符（同文件第 117 行；源码判据在第 1063–1067 行）。而"目录里没列出"的端点被当作**纯文本**（`packages\llm\llm-deepseek\src\model-info.ts` 第 70–74 行的注释，§4.9）——这是同一件事在适配器侧的入口。

### Q10 密钥为什么只出现在"引用名"里？*（第一次读请跳过）*

**答案**：因为密钥可能来自凭据服务、`.env` 行或 shell 导出，任何一种都会带上首尾空白；把原始值送进 HTTP header 会在 `fetch` 层炸出一个**点名 UTF-16 码点**的错误，读者完全不知道该改哪个设置。所以本层统一在 `assertUsableApiKey()` 里裁掉空白并给出**结构化诊断**（`INVALID_CREDENTIAL`），且 JSDoc 明确 *"The key never enters the message"*（`packages\llm\llm\src\index.ts` 第 133–166 行）；缺 key 则是 `MISSING_CREDENTIAL`，消息里只出现引用名（`packages\llm\llm-deepseek-api-key\src\index.ts` 第 30–34 行，§4.10 ⑤⑥）。
