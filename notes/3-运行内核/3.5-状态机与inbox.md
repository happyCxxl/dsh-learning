## 0. 怎么读这一课（阅读许可）

### 0.1 这一课是什么、不是什么

**是**：一台状态机的完整说明书——**对外有几个状态、谁能改变它、改变时先提交什么后提交什么、什么情况下一个轮次里一步都没有**。
**不是**：模型请求怎么拼出来（`3.6`）、工具怎么调度（`3.11`）、系统提示词怎么协调（`3.6`）、事件分发怎么实现（第二编）。本课只在**边界**上碰它们：知道"提交顺序"和"取消能拦住哪一步"就够了。

### 0.2 现在只要记住这 5 件事

1. **对外只有两个状态**：`idle` 与 `running`。内部还有一个 `maintenance`（维护期），它**对外也算 `idle`**。
2. **一次唤醒就"占住"驱动器**：`wakeDriver()` 先同步把内部状态切成 `running`，然后才去跑；所以同一个 agent 不会有两个驱动器并行。
3. **开轮次在前、领取输入在后**：`turn/start` 先落日志，然后把 inbox 里的输入"原子领取"给这一步。因此**拒绝、空输入、取消都可能留下一个没有 step 的轮次**。
4. **inbox 是"两份有序清单 + 一条持久事件"**：`next-turn`（每条起一个独立轮次）与 `next-step`（等下一个步骤边界）；每次变更都提交一条 `agent/inbox/spliced`，折叠成投影后**没有活跃 agent 也能冷读**。
5. **取消是协作式的**：`cancel()` 只做两件事——清 inbox（可保留）+ `abort(cause)`。真正的"停下来"靠循环里那 **15 个 `signal.throwIfAborted()` 检查点**。

### 0.3 明确授权：这些现在**不用管**

- `agent/pre-step` / `agent/request` 的**监听器怎么写**、`startsRequestSeries` 的语义——属 `3.6`。本课只把它们当成"循环会 await 的一道闸门"；
- 工具并发调度（独占屏障、有界并行池）——属 `3.11`。本课只用到它的**返回值** `concluded` / `concludesTurn`；
- `MessageId` 的生成与冻结、`UserMessage.source` 的联合类型——属 `3.1` / `3.4`；
- 投影的注册生命周期（`ctx.sessionProjections`、realm、作用域）——属 `2.x`。本课只用到"注册过就能冷读"这个结论。

判断标准只有一条：**只要你能说清"这件事发生在轮次边界、步骤内部、还是队列里"，就够了。**

## 1. 最小词汇表（6 个词）

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **turn 轮次** | "把手头的活干到没事可干"的一次排空过程 | `turn/start` 与 `turn/end` 两个持久事件之间 |
| **step 步骤** | 一次模型请求 + 它请求的工具执行 | `step/start` 与 `step/end` |
| **phase 阶段** | 驱动器内部的**状态位**（不是公开状态） | `{ kind: 'idle' \| 'maintenance' \| 'running', … }` |
| **wake 唤醒** | "有活了，去跑"这个动作 | `wakeDriver()`；投递方法上的 `wakeup` 布尔参数 |
| **claim 领取** | 在边界上把待处理输入**移出队列并交给这一步** | `inbox.claim(target, turn)` |
| **inbox 收件箱** | 两份待处理清单：一条起一个轮次 / 一条等一个步骤边界 | 投影名 `'inbox'`，两份列表 `next-turn` / `next-step` |

> ⚠️ 这 6 个词里，`turn` / `step` 由 `1.1` 定义过；`phase` / `wake` / `claim` / `inbox` 是**本课新增**。上面只给到"能读懂本课"的程度：`agent/*` 事件分发的实现属第二编，工具调度属 `3.11`。

## 2. 先建立画面

### 2.1 从属关系图（静态：谁包含谁）

```
Session（会话日志，只追加，是唯一真源）
└─ turn 轮次                    ← 由驱动器循环打开/关闭；"一次排空"
   ├─ step 步骤                 ← 0..N 个；每个 = 一次模型调用 + 它请求的工具执行
   │  ├─ 会话事件（持久）        turn/*  step/*  system/message  user/message  assistant/*  tool/*
   │  └─ 实时事件（进程内）      agent/assistant-stream …
   └─ （轮次之间、跨轮次存活）inbox 两份清单，由驱动器在自己的边界上领取
        ├─ next-turn   每条 = 一个独立轮次
        └─ next-step   每条 = 等下一个步骤边界

驱动器（driver）= 一个处于 running 的 phase；同一时刻每个 agent 至多一个
```

**精确性说明**：inbox 并不"装在" turn 里——它是 agent 级、**跨轮次存活**的状态；画在 turn 下面只是因为"它在 turn 的边界上被领取"。同理，实时事件是**在 turn/step 的过程中产生**的，不是装在 step 这个容器里。

### 2.2 一个轮次的生命线（动态过程图）

```
send/followup/steer（wakeup=true）              inject（wakeup=false，不唤醒）
        │                                                  │
        ▼                                                  ▼
 phase.idle ──wakeDriver()──▶ phase.running{turn=lastTurn, step=0}      inbox['next-step'] 待处理
        ▲                                   │                                     │
        │                                   ▼                                     │
        │                   turn(): turn = phase.turn + 1                        │
        │                   session.append('turn/start', {turn})                  │
        │                   claim(next-step 全部 + next-turn 1 条) ◀───────────────┘
        │                   assemble → runtime context → agent/pre-step
        │                        ├─ reject ─────────────▶ turn/end{blocked} ─▶ return false
        │                        ├─ enter 且 messages 空 且 step===0 ─▶ turn/end{completed} ─▶ return false
        │                        └─ enter（后续步骤被改写为空则 break）
        │                   session.append('step/start')
        │                   step()：agent/request → prepareCall → 提交 system/user → 流 → 工具
        │                   session.append('step/end')
        │                   turnEnds 且 next-step 非空 ─▶ target='next-step'，回到 step/start
        │                   turnEnds 且 next-step 空 ──▶ agent/turn-stopping（serial）
        │                   session.append('turn/end', {turn, reason})
        │                                   │
        └── inbox.hasPending ? 重置 abort、step=0、返回 true（继续下一 turn） : 返回 false（退出 driver）
```

看图前先认识图上那 4 个动作词（都是本课 §4 会展开的）：

| 图上的词 | 一句话 | 在源码里 |
|---|---|---|
| `claim` | 在边界上把 inbox 里的待处理输入**移出**交给这一步 | `inbox.claim(target, turn)`（§4.4 块 5） |
| `assemble` | 把系统提示词与工具 schema 拼出来 | `ctx.systemPrompt.assemble(...)`（`3.6`） |
| `agent/pre-step` | 循环 await 的 waterfall：**可以拒绝，也可以改写**这一批输入 | §4.2 块 3 |
| `hasPending` | 两份清单里还有没有待处理项（循环私有，不在 `Agent.inbox` 接口里） | §4.4 块 5 |

### 2.3 大白话版：从"用户敲一句话"到"轮次关闭"

**完全不用术语**，先建立画面（来源：`docs\architecture.zh.md` 第 92–111 行的轮次流程伪代码；这里只做白话转述，细节留到 §4）。

1. 用户的话被投进一个**待处理队列**（不是直接发给模型）。
2. 有个循环被"叫醒"，先去队列里**把这一批活搬走**——搬走之前，先在本子上记一笔"新一轮开始"。
3. 循环把"要给模型看的东西"拼起来：系统提示词 + 历史消息 + 可用工具的说明书。
4. 在真正发请求之前，还有一个**可以让别人插手的环节**：有人可以说"这批活我不接"（那就一跳不跑，把这一轮原地关掉），也可以把要发的内容换掉。
5. 通过了，就记一笔"这一步开始"，然后发一次模型请求——**这才是第一步**。
6. 模型流式吐字；如果它说"我要用某个工具"，循环就去执行，执行前后都有检查点。
7. 工具结果再喂回模型，模型继续；可能重复好几轮——**同一轮里可以有多个步骤**。
8. 模型不再要工具、队列的下一格也空了，循环再问一次"还有没有人要插话"（这也是一个扩展点），没人插话就记一笔"本轮结束"。
9. 队列里如果还剩活，循环回头做第 2 步；否则驱动器退休，回到"没在跑"的状态。

→ 这段白话与 §2.2 那张图是同一件事的两种画法：**图给结构，白话给顺序**。

## 3. 结论先行（10 条，行号已逐一核对）

> **本节的文件名缩写**（后面每节首次出现时会给全路径；只是为了这一节读起来不啰嗦）：
> `agent.ts` = `packages\core\agent-loop\src\agent.ts`；`inbox.ts` = `packages\core\agent-loop\src\inbox.ts`；
> `tool-calls.ts` = `packages\core\agent-loop\src\tool-calls.ts`；`index.ts` = `packages\core\agent-loop\src\index.ts`；
> `runtime-types.ts` = `packages\core\agent\src\runtime-types.ts`；`README.zh.md` = `packages\core\agent-loop\README.zh.md`；
> 测试文件名（`*.spec.ts`）= `packages\core\agent-loop\tests\` 下的同名文件。

1. **step 定义在会话事件词表里，turn 是它的容器**：`step/start` 的注释就是"turn `turn` 的第 `step` 步——一次模型调用加上它请求的工具执行"（`packages\core\session\src\types.ts` 第 298–301 行）；文档口径是"一个步骤是一次模型请求加上它调用的工具。一个轮次包含零个或多个步骤"（`docs\architecture.zh.md` 第 90 行）。
2. **状态机不是 enum，而是三态 `phase` 字段**：`{kind:'idle'} | {kind:'maintenance'} | {kind:'running', turn, step}`，`maintenance` 对外也算 `idle`（`packages\core\agent-loop\src\agent.ts` 第 42–50 行、第 140–142 行）。对外可见状态只有 `'idle' | 'running'`，且 `setPhase` 只在真的变化时 emit `agent/status`（同文件第 144–152 行；`packages\core\agent\src\runtime-types.ts` 第 102–109 行）。
3. **turn 号与 step 号都是循环内的自增计数器，但 turn 号的起点来自持久投影**：`wakeDriver()` 用 `this.phase.lastTurn` 开新驱动器、`step` 归零（`agent.ts` 第 227–233 行），`turn()` 里 `turn = phase.turn + 1`（第 303 行），`step` 在 `turn()` 内 `phase.step + 1`（第 315 行）并每轮重置为 0（第 394 行）；`lastTurn` 又从 `turnBoundary` 投影读入（第 134 行；投影定义 `packages\core\agent-loop\src\index.ts` 第 46–95 行）。所以 fork / 恢复后轮次继续编号。
4. **0 个 step 的 turn 是常态而非异常**，共五条路径：`agent/pre-step` 返回 `reject`（第 317–319 行）、首个 `enter` 被改写为空批次（第 324–327 行）、唤醒消息在领取前被移除（同两行注释）、`turn/start` 之后 `step/start` 之前取消或失败（第 314、328 行闸门 + 第 366–372 行），以及 `step>0` 的后续步骤被改写为空而 `break`（第 321 行）。会话词表把这件事写进注释："拒绝、空输入、取消或失败都可能关闭一个没有步骤的轮次"（`packages\core\session\src\types.ts` 第 283–287 行）。
5. **inbox 解决的是"生产者与边界解耦 + 待处理工作持久化"**：两份有序列表 `next-turn` / `next-step`（`packages\core\agent\src\types.ts` 第 38–45 行），每次变更都提交一条规范化的 `agent/inbox/spliced`（`packages\core\agent-loop\src\inbox.ts` 第 227–235 行），折叠成 `inbox` 投影后**没有活跃 Agent 时也能冷读**（`packages\core\agent-loop\README.zh.md` 第 118 行；`docs\architecture.zh.md` 第 115 行）。
6. **`followup` / `steer` / `inject` 只是 `send()` 的三个固定预设**：`send(msg,'next-turn',true)`、`send(msg,'next-step',true)`、`send(msg,'next-step',false)`（`agent.ts` 第 154–173 行；`docs\subsystems\core.zh.md` 第 59 行）。
7. **取消 = 默认清空 inbox + abort 当前信号**；同一活动内首个 cause 胜出，`keepInbox` 只中止不清队列（`agent.ts` 第 175–181 行；`runtime-types.ts` 第 37–45 行、第 176–183 行）。取消是协作式的：`agent.ts` 里有 15 个 `signal.throwIfAborted()` 检查点（第 273、283、302、314、328、358、361、402、437、441、444、505、580、594、667 行）。
8. **提交顺序决定了"取消能避免什么"**：`agent/pre-step` → `step/start` → `agent/request` → `prepareCall()` → 提交 `system/message` 与 `user/message`（`agent.ts` 第 316–330 行、第 408–423 行、第 580/594 行）。在 `agent/request` 或 `prepareCall()` 这两个异步阶段取消，**系统提示词与已接纳用户消息都不提交**，只留下平衡的 `step/start` + `step/end`（`packages\core\agent-loop\README.zh.md` 第 118 行；测试 `packages\core\agent-loop\tests\system-prompt-admission.spec.ts` 第 372–399 行）。
9. **turn 关闭条件**：某步返回 `completed` 或 `max-tokens`（即不再欠模型一次响应）**且** `next-step` 已空；此时先跑串行 `agent/turn-stopping`，再读一次 inbox，仍为空才 `break`（`agent.ts` 第 338–363 行）。被拒绝或空首批的 turn 直接在 `try` 内 `return false`，**不跑** turn-stopping（第 317–327 行）。
10. **`agent/turn-stopping` 的唯一控制手段是数据（steer），没有返回值**：监听器 `agent.steer(...)` 使 inbox 非空，循环就再开一步（`runtime-types.ts` 第 364–381 行；测试 `packages\core\agent-loop\tests\contract-regressions.spec.ts` 第 319–341 行）。README 明确"没有内置轮次预算"，限流策略必须从这个扩展点执行取消（`packages\core\agent-loop\README.zh.md` 第 217 行）。

### 4.1 状态机不是 enum，而是三态 `phase`

`packages\core\agent-loop\src\agent.ts` 第 42–50 行 与 第 140–152 行（两段拼接）

```ts
// （本块由两段拼成：第 42–50 行的类型定义，与第 140–152 行的两个类成员。
//   第 51–139 行 = StepEndReason、PreparedStep、requestProposal、类的字段与构造函数，
//   与本知识点无关，此处省略；其中第 100 行声明 `private phase: Phase`，
//   第 134–135 行把初值设为 `{ kind: 'idle', lastTurn }`（见 §4.8）。）

type Phase =
  | { kind: 'idle'; lastTurn: number }
  | {
    kind: 'maintenance'
    abort: AbortController
    lastTurn: number
    wakeRequested: boolean
  }
  | { kind: 'running'; abort: AbortController; turn: number; step: number; wakeRequested: boolean }

// …（第 51–139 行：同上，此处省略）

  get status(): AgentStatus {
    return this.phase.kind === 'idle' || this.phase.kind === 'maintenance' ? 'idle' : 'running'
  }

  /** Commit a phase and publish its externally visible status transition. */
  private setPhase(next: Phase): void {
    const previousStatus = this.status
    this.phase = next
    const status = this.status
    if (status !== previousStatus) {
      this.dispatch.emit('agent/status', { status })
    }
  }
```

- **做什么**：`Phase` 是驱动器**唯一的内部状态**，三个变体各自带自己需要的数据；`status` 把 `maintenance` 折叠成 `'idle'`；`setPhase` 是**唯一**改状态的地方，并在对外可见状态真的变化时 emit `agent/status`。
- **与哪个知识点相关**：结论 2（三态 phase）、结论 3（`running` 变体里的 `turn` / `step` 两个计数器）、以及 §0.2 第 1、2 条。
- **为什么这么写**：`maintenance` 需要 `abort` + `wakeRequested`，但没有 `turn` / `step`；`running` 需要全部五个。写成**带数据的联合**而不是"一个 enum + 一堆可空字段"，编译器就能保证"`phase.turn` 只在 `running` 下存在"——这也是 `get status()` 必须写两个 `kind` 比较的原因。`setPhase` 的作者注释只有一句 `Commit a phase and publish its externally visible status transition.`，它同时承担"赋值"和"发通知"两件事，所以**外部永远不会看到一次没发通知的状态切换**（标注为推断：由第 145–151 行的执行顺序直接推得——先记 `previousStatus`，赋值，再读新 `status`，不等就发）。
- **依赖从哪来**：`this.dispatch` 是构造函数里建的融合分发器（第 108 行声明、第 129 行 `agentEvents(loopCtx, this)`）；`AgentStatus` 的类型与语义在 `packages\core\agent\src\runtime-types.ts` 第 102–109 行——注释写明 `running` 表示"唤醒输入开启了可取消的 pre-step 处理，并持续到驱动器排空、关闭或检查点轮次为止"。

### 4.2 轮次边界：开轮次 → 领取 → 三条 0-step 出口

`packages\core\agent-loop\src\agent.ts` 第 296–330 行

```ts
  /** Commit one normalized mutation and publish its live events. */
  private mutate(
    target: InboxTarget,
    start: number,
    deleteCount: number,
    inserted: UserMessage[],
    discardRemoved: boolean,
  ): UserMessage[] {
    const state = this.current()
    const inbox = state[target]
    const truncatedStart = Math.trunc(start)
    const offset = Number.isNaN(truncatedStart) ? 0 : truncatedStart
    const actualStart = offset < 0
      ? Math.max(inbox.length + offset, 0)
      : Math.min(offset, inbox.length)
    const truncatedDeleteCount = Math.trunc(deleteCount)
    const actualDeleteCount = Math.min(
      Math.max(Number.isNaN(truncatedDeleteCount) ? 0 : truncatedDeleteCount, 0),
      inbox.length - actualStart,
    )
    if (actualDeleteCount === 0 && inserted.length === 0) return []
    const candidate = inbox.toSpliced(actualStart, actualDeleteCount, ...inserted)
    const ids = new Set<string>()
    for (const message of target === 'next-turn'
      ? [...candidate, ...state['next-step']]
      : [...state['next-turn'], ...candidate]) {
      if (ids.has(message.id)) throw new Error(`message "${message.id}" is already pending`)
      ids.add(message.id)
    }
    const outcome = discardRemoved && actualDeleteCount > 0 ? 'canceled' as const : undefined
    const splice: SessionEventMap['agent/inbox/spliced'] = {
      target,
      start: actualStart,
      ...(actualDeleteCount === 0 ? {} : { removedCount: actualDeleteCount }),
      inserted,
      ...(outcome === undefined ? {} : { outcome }),
    }
    const removed = inbox.slice(actualStart, actualStart + actualDeleteCount)
    const event = this.session.append('agent/inbox/spliced', splice)
    if (discardRemoved) {
      for (const message of removed) this.dispatch.emit('agent/inbox/discarded', { message })
    }
    for (const message of event.data.inserted) {
      this.dispatch.emit('agent/inbox/inserted', { message })
    }
    return removed
  }
```

```ts
export const inboxProjectionDefinition = {
  key: 'inbox',
  stateSchema: inboxProjectionSchema,
  init: (): InboxState => ({ 'next-turn': [], 'next-step': [] }),
  apply(state: InboxState, event) {
    if (event.type !== 'agent/inbox/spliced') return state
    const splice = event.data
    try {
      const inbox = state[splice.target]
      const removedCount = splice.removedCount ?? 0
      if (!Number.isSafeInteger(splice.start) || splice.start < 0 || splice.start > inbox.length
        || !Number.isSafeInteger(removedCount) || removedCount < 0
        || splice.start + removedCount > inbox.length) {
        throw new Error('invalid inbox splice')
      }
      const next = inbox.toSpliced(splice.start, removedCount, ...splice.inserted)
      const ids = new Set<string>()
      for (const message of splice.target === 'next-turn'
        ? [...next, ...state['next-step']]
        : [...state['next-turn'], ...next]) {
        if (ids.has(message.id)) throw new Error(`message "${message.id}" is already pending`)
        ids.add(message.id)
      }
      return splice.target === 'next-turn'
        ? { 'next-turn': next, 'next-step': state['next-step'] }
        : { 'next-turn': state['next-turn'], 'next-step': next }
    } catch (error: unknown) {
      throw new Error(`invalid persisted inbox splice at session seq ${event.seq}`, { cause: error })
    }
  },
  wire: {
    // The wire value is the fold state itself: every pending message already
    // round-trips the session log as lossless JSON. Only the static type
    // narrows to the JSON-safe projection table entry.
    viewSchema: inboxProjectionSchema as unknown as z.ZodType<InboxWireState>,
    view: (state: InboxState) => state as unknown as InboxWireState,
  },
  stateVersion: 1,
} satisfies ProjectionDefinition<'inbox', InboxState>
```

### 4.5 followup / steer / inject 的插入点

`packages\core\agent-loop\src\agent.ts` 第 154–173 行

```ts
  send(message: UserMessage, target: InboxTarget, wakeup: boolean): void {
    // Waking input cannot join an aborted activity, so it starts the next turn.
    // Captured before the insertion so a reentrant cancel from a splice observer cannot reclassify it.
    const wakingAfterAbort = wakeup && this.phase.kind !== 'idle' && this.phase.abort.signal.aborted
    const resolvedTarget = wakingAfterAbort ? 'next-turn' : target
    this.inbox.splice(resolvedTarget, Infinity, 0, [message])
    if (wakeup) this.wakeDriver(wakingAfterAbort)
  }

  followup(input: UserMessage): void {
    this.send(input, 'next-turn', true)
  }

  steer(input: UserMessage): void {
    this.send(input, 'next-step', true)
  }

  inject(input: UserMessage): void {
    this.send(input, 'next-step', false)
  }
```

- **做什么**：`send` 是唯一入口，三个方法各自把 `(target, wakeup)` 写死成一个预设。
- **与哪个知识点相关**：结论 6（三个固定预设）、以及"唤醒侧的两个特例"之一。
- **依赖从哪来**：`InboxTarget` 来自 `packages\core\agent\src\types.ts` 第 38–39 行；`this.phase` 见块 1；`this.inbox` 在构造函数里建（第 132 行）。
- **为什么这么写（第一个特例）**：第 155–158 行把"唤醒输入不能加入一个**已经中止**的活动"这件事做成**插入前捕获**的一个布尔值：`wakingAfterAbort` 为真时 target 被改判成 `next-turn`。作者注释给了理由：`Captured before the insertion so a reentrant cancel from a splice observer cannot reclassify it.` —— 如果先插入再判断，一个在 splice 观察者里重入的 `cancel()` 会改变判断结果。
- **`Infinity` 是什么**：`splice` 的 `start` 归一化规则（§4.4 块 6 第 207–211 行）把 `Infinity` 夹到 `inbox.length`，所以它表达的是**追加到队尾**（"排队"）。
- **`inject` 与另外两个的真正差别**：不是 target（`inject` 与 `steer` 都用 `next-step`），而是 `wakeup = false`——**它不改变 phase，因此不能启动一个空闲的驱动器**。

插入点对照图：

```
phase=idle                          phase=running（turn 打开，可能正在流式或跑工具）
─────────────                       ────────────────────────────────────────────────
followup() ─▶ next-turn ─▶ 唤醒 ─▶  新轮次：下一轮 turn() 领取它（同一轮的唯一普通消息）
steer()    ─▶ next-step ─▶ 唤醒 ─▶  立刻占住驱动器；本轮下一个 step 边界领取
inject()   ─▶ next-step ─▶ 不唤醒   留在队列里，等下一次可唤醒投递把它带进 pre-step
```

| 方法 | 实现 | 语义要点（出处） |
|---|---|---|
| `followup(msg)` | `send(msg,'next-turn',true)`（`agent.ts` 第 163–165 行） | 成为**自己轮次中唯一的普通消息**；`MessageId` 只证明 inbox 准入，不识别后续输出或 `turn/end`（`runtime-types.ts` 第 217–222 行；`docs\subsystems\core.zh.md` 第 197 行） |
| `steer(msg)` | `send(msg,'next-step',true)`（第 167–169 行） | 空闲驱动器开新轮次；运行中的驱动器在最近步骤边界消费；被拒绝的步骤会让 steering **留在 inbox** 直到下一次唤醒（`runtime-types.ts` 第 224–231 行） |
| `inject(msg)` | `send(msg,'next-step',false)`（第 171–173 行） | 不唤醒；运行中的驱动器在最近的后续 pre-step 领取；**可能错过一个已经领走批次的请求**；idle 时一直挂着直到 followup / steer（`runtime-types.ts` 第 233–241 行；`.agents\notes\implemented\architecture\2026-07-24-separate-context-injection-from-turn-execution.zh.md` 第 29 行） |

两条额外的插入点：工具结果的 `additionalContexts` 经同一个 acceptor 落到 `next-step`（`agent.ts` 第 534–537 行；`tool-calls.ts` 第 157 行，即块 11）；`agent/pre-step` 的 `enter` 分支可以在本步额外追加消息（`interception.spec.ts` 第 196–221 行）。

唤醒侧的第二个特例在 `wakeDriver()` 里（块 2）：非空闲时把唤醒**闩存**下来等 convergence 重放，但 `disposed` 取消永不闩存（第 214–224 行、第 200 行、第 262 行）。

`packages\core\agent-loop\src\agent.ts` 第 214–235 行（块 2：`wakeDriver`，供本节一起读）

```ts
  private wakeDriver(wakeAfterAbort = false): void {
    if (this.phase.kind !== 'idle') {
      // Maintenance and aborted drivers cannot deliver the wake: latch it for
      // replay at convergence. Live drivers claim queued work themselves;
      // disposal never latches, so teardown waits on no model turn.
      const reason = abortedCancelCause(this.phase.abort.signal)
      if (reason?.kind !== 'disposed' && (this.phase.kind === 'maintenance' || wakeAfterAbort)) {
        this.phase.wakeRequested = true
      }
      return
    }
    const driver = Promise.withResolvers<void>()
    this.activityDone = driver.promise
    this.setPhase({
      kind: 'running',
      abort: new AbortController(),
      turn: this.phase.lastTurn,
      step: 0,
      wakeRequested: false,
    })
    this.loopCtx.agents.withInitiator(this, () => this.kick()).then(driver.resolve, driver.reject)
  }
```

- **做什么**：空闲时**同步**占住驱动器（切 `running` + 造 `AbortController`）；非空闲时按条件把唤醒**闩存**到 `wakeRequested`，等这一轮收敛后再重放。
- **依赖从哪来**：`wakeAfterAbort` 由 `send()` 传入（第 160 行）；`this.phase.lastTurn` 来自块 1 的 `idle` 变体（即 §4.8 的投影值）；`activityDone` 在第 101 行声明、第 240 行被 `whenIdle()` 按身份比较轮询。
- **为什么这么写**：注释原文给了三条判据——维护中与已中止的驱动器**没法交付这次唤醒**，所以闩存；**活着的**驱动器自己会去领队列，所以不用闩；而 `disposed` **永不闩存**，理由是 `so teardown waits on no model turn`（拆除不能等一个模型轮次）。
- **`turn: this.phase.lastTurn` 这一行是本课的"轮次号起点"**：新驱动器不是从 0 开始，而是从投影记录的最后一个轮次号开始（`turn()` 里再做 `+ 1`）。

### 4.6 取消：入口 + cause 持久化 + 检查点

`packages\core\agent-loop\src\agent.ts` 第 175–181 行 与 第 72–95 行（两段拼接，顺序已调换）

```ts

      this.inbox.clear()
      if (this.phase.kind !== 'idle') this.phase.wakeRequested = false
    }

// …（本块跳过了第 1–71 行与第 96–174 行两段：前者是 import 与模块级辅助，
//    后者是 runMaintenance / wakeDriver / whenIdle / throwError / kick / preStep / turn，
//    都与"取消的入口与原因"无关，故不摘）

/**
 * Read the cause `cancel()` passed when aborting a loop-owned signal, copying
 * only the fields `turn/end` records. The live reason stays the caller's
 * object, and Node's fetch assigns a `stack` onto it that `Session.append`
 * would either log or reject as data JSON cannot hold.
 * @param signal - a turn or maintenance signal this loop owns.
 * @returns the copied cause, or undefined while the signal is still live.
 */
function abortedCancelCause(signal: AbortSignal): AgentCancelCause | undefined {
  if (!signal.aborted) return undefined
  // `cancel()` is the only aborter of the signals this loop owns.
  const cause = signal.reason as AgentCancelCause
  switch (cause.kind) {
    case 'user':
    case 'parent':
    case 'disposed':
      return { kind: cause.kind }
    case 'hook':
      return { kind: 'hook', reason: cause.reason }
    /* v8 ignore next -- cancel accepts the closed AgentCancelCause union */
    default:
      return assertNever(cause)
  }
}
// （说明：原文里 abortedCancelCause 定义在 cancel() 之前（第 72–95 行）；
//   这里为了"先看入口、再看它依赖的工具"而调换了顺序，两段的行号都按原文标注。）
```

- **做什么**：`cancel()` 只做两件事——（除非 `keepInbox`）清空 inbox + 清掉闩存的唤醒，然后对当前 phase 的 `AbortController` 调 `abort(cause)`；`abortedCancelCause()` 把 live 的 `signal.reason` **拷成一份只含可序列化字段**的对象。
- **与哪个知识点相关**：结论 7（取消 = 清队列 + abort；协作式）。"协作式"的含义在这一块很直白：**`cancel()` 里没有任何 `return` 或状态切换**，它不会让循环停下来，只会让下一个检查点抛错。
- **依赖从哪来**：`cause` 是调用方给的（闭合联合 `'user' | 'parent' | {kind:'hook',reason} | 'disposed'`，`packages\core\session\src\types.ts` 第 188–193 行）；`options` 的 `keepInbox` 定义在 `runtime-types.ts` 第 37–45 行；`abortedCancelCause` 全仓只有 **3 个调用点**，都在本文件：第 199 行（维护任务收尾）、第 219 行（`wakeDriver` 的闩存判定）、第 368 行（`turn()` 区分 aborted 与 error）。

1. **语义**：轮次即将关闭（模型不欠响应、没有新 steering）时、边界提交之前被 await 的 **serial** 监听器；它没有 `next()`，返回值也不参与决策。

3. **失败被容纳为轮次错误**：监听器抛错时该轮 `turn/end{kind:'error'}`，循环继续存活（`contract-regressions.spec.ts` 第 346–369 行），因为 `kick()` 在驱动器边界 catch（`agent.ts` 第 252–257 行）。

`packages\core\agent-loop\src\tool-calls.ts` 第 146–161 行

```ts

  const commitReady = async (): Promise<void> => {

      const slot = slots[committed]
      if (slot === undefined) break
      const call = group[committed]
```

- **与哪个知识点相关**：结论 10 的第 6 条——**"工具结果提前结束轮次"是数据而非控制流**；以及 §4.5 里"工具结果的 `additionalContexts` 落到 `next-step`"。

- **`concludesTurn` 的效果**：`executeToolCalls` 返回 `{ concluded }`（第 100–101 行），`step()` 用它决定返回 `{kind:'completed'}` 还是 `null`（`agent.ts` 第 538 行）——**一步就结束轮次**；但已排队的 `next-step` 工作（同一步的 `additionalContexts` 或竞态 steering）仍会跑完，轮次要等 inbox 排空才关闭。

### 4.8 轮次号从哪来：`turnBoundary` 投影

`packages\core\agent-loop\src\index.ts` 第 57–95 行

```ts

  key: 'turnBoundary',
  stateVersion: 2,
  stateSchema: turnBoundaryProjectionSchema,
  init: () => ({

    lastStepStartSeq: null,
    lastStepBoundary: null,
    lastTurn: 0,

          ...state,
          openTurnStartSeq: event.seq,

      case 'turn/end':

          ...state,
          openTurnStartSeq: null,

      case 'step/start':
        return {
          ...state,
          lastStepStartSeq: event.seq,
          lastStepBoundary: { kind: 'start', seq: event.seq },
        }
      case 'step/end':
        return {
          ...state,
          lastStepBoundary: { kind: 'end', seq: event.seq },
        }
      default:
        return state
    }
  },
} satisfies ProjectionDefinition<'turnBoundary', TurnBoundaryProjection>
// （第 46–54 行的 turnBoundaryProjectionSchema 在本块之前：它声明四个字段的形状，
//   并把两个 seq 字段 transform 成 SessionSeq。）
```

- **做什么**：把会话日志里的 `turn/start` / `turn/end` / `step/start` / `step/end` 折成"当前有没有打开的轮次 / 最后一次步骤边界 / **最新轮次号**"四个字段。
- **与哪个知识点相关**：结论 3——`lastTurn` **不是内存里的计数器**，它来自这份投影；所以 fork 或恢复之后，新的驱动器接着旧日志的轮次号往下数。构造函数的第 134 行正是 `stateOf(session, 'turnBoundary')?.lastTurn ?? 0`。

- **为什么 `turn/end` 只清 `openTurnStartSeq`**：轮次号要**留下来**给下一个驱动器用（第 302–303 行 `turn = phase.turn + 1`），清掉的只是"还开着"这个事实。

### Q1 turn 与 step 的关系？0 个 step 的 turn 是怎么发生的？

**答案：turn 是"一次性领到并跑完的工作单元"，step 是"一次模型调用 + 它请求的工具执行"；一个 turn 含 0..N 个 step，且 step 只在 enter 决策之后才打开。**

- 关系：`step/start` 的注释即定义（`packages\core\session\src\types.ts` 第 298–301 行）；`docs\architecture.zh.md` 第 90 行的口径是"一个轮次包含零个或多个步骤：它在领取首条输入之前打开，并在不再欠下任何工作时关闭"。
- 打开顺序：`turn/start` **先**于领取与 pre-step（`agent.ts` 第 305–309 行、第 316 行）；`step/start` 只在 pre-step 返回 `enter` 后才追加（第 329 行）。因此日志顺序天然是 `turn/start → (step/start → step/end)* → turn/end`。
- 一个 turn 内可以有多个 step：只要某步返回 `null`（工具还欠一次请求，第 538 行）或有 `next-step` 输入（第 359 / 363 行判定失败，第 364 行切换 target），循环就回到 `step/start`，`phase.step` 继续自增（第 315 行）。
- **0 个 step 的 turn 有五条路径**：

| 路径 | 触发条件 | `turn/end` 原因 | 出处 |
|---|---|---|---|
| 1 | `agent/pre-step` 决策为 `reject` | `{kind:'blocked'}` | `agent.ts` 第 317–319 行；测试 `interception.spec.ts` 第 250–271 行、`coverage-edges.spec.ts` 第 491–514 行 |
| 2 | 首个 `enter` 的 `messages` 被改写为空 | `{kind:'completed'}` | `agent.ts` 第 324–327 行；测试 `contract-regressions.spec.ts` 第 187–204 行（断言事件类型恰为 `['turn/start','turn/end']`） |
| 3 | 唤醒消息在领取前被移除（`Inbox.remove` / `cancel` 清队列），`preStep` 领到空批次 | `{kind:'completed'}` | 第 322–324 行注释（"已移除的唤醒消息…仍然拥有初始轮次边界，但不消耗模型调用"） |
| 4 | `turn/start` 已提交、`step/start` 之前取消（含已被 `preStep` 领取的消息随取消消失） | `{kind:'aborted', reason}` | 第 314、328 行闸门 + 第 366–372 行；测试 `cancel.spec.ts` 第 333–350 行 |
| 5 | `step>0` 的后续步骤被 `pre-step` 改写为空 → `break`（保留先前 `turnEnds`） | 先前 `turnEnds`（如 `completed`） | 第 321 行；测试 `interception.spec.ts` 第 223–248 行 |

- 会话词表把这条契约写进注释："拒绝、空输入、取消或失败都可能关闭一个没有步骤的轮次；否则随后的 `user/message` 事件或批次记录进入该步骤的消息"（`packages\core\session\src\types.ts` 第 283–287 行）；`turn/end` 的注释再强调"没有进入步骤的轮次不会有 `step/start` 或 `step/end`"（同文件第 289–297 行）。
- 被拒绝的领取批次不会回流：它**既不是 discarded 也不是 `user/message`**，到此结束（`runtime-types.ts` 第 289–299 行）——这是路径 1 之所以"不消耗模型调用也不留模型可见历史"的原因。

### Q2 inbox 解决什么问题？followup / steer / inject 分别是什么语义？

**答案：inbox 解决"输入的生产者"与"驱动器的 turn/step 边界"之间的解耦，并把待处理工作持久化成可冷读、可回放、有唯一顺序的队列；`followup` / `steer` / `inject` 是同一 `send()` 的三个固定预设，区别只在目标列表与是否唤醒。**

- **解决什么问题**（四点，各有出处）：
  1. **边界由循环独占**：生产者不直接触发模型调用，只投递到 `next-turn` / `next-step`；驱动器在自己的边界上"原子领取"（`agent.ts` 第 271、311、364 行；`inbox.ts` 第 109–114 行）。
  2. **顺序唯一**：Agent inbox 是唯一执行顺序权威——`.agents\notes\implemented\feature\2026-07-28-continuable-subagent-conversations.zh.md` 第 88 行明确"Agent inbox 是唯一队列"，第 164 行否决了"第二条 FIFO"的方案（理由：与已接受消息之间的顺序不明确）。
  3. **一次 send 一个轮次（不隐式批处理）**：轮次边界上 `claim` 只取 1 条 `next-turn`（`inbox.ts` 第 111 行），因此相邻两次 `send` 绝不会被静默合并（`.agents\notes\implemented\simplification\2026-07-17-one-send-one-turn.zh.md` 第 17、23 行）。
  4. **持久且可冷读**：每次变更都落 `agent/inbox/spliced`（`inbox.ts` 第 227–235 行），折叠成投影后在没有活跃 Agent、以及所有 Agent 卸载后仍可读（`README.zh.md` 第 118 行；`docs\architecture.zh.md` 第 115 行）；顺序约定在 `.agents\notes\implemented\architecture\2026-06-11-event-sourced-sessions.zh.md` 第 17 行被记为"先领取 inbox 消息，再运行 `agent/pre-step`；仅在 enter 决策后才打开 `step/start`"。
- **三者语义**（`agent.ts` 第 163–173 行；`runtime-types.ts` 第 217–241 行）：
  - `followup(msg)` = `send(msg,'next-turn',true)`：排队一个**普通后续轮次**并唤醒；该消息成为自己轮次的唯一普通消息。`MessageId` 只标识 inbox 插入 / 领取 / 丢弃事实，不标识之后的 assistant 输出或 `turn/end`（`docs\subsystems\core.zh.md` 第 197 行）。
  - `steer(msg)` = `send(msg,'next-step',true)`：投向**最近的步骤边界**并唤醒；空闲驱动器会开新轮次，运行中的驱动器在下一步领取；步骤被拒绝时 steering 留在 inbox 等下一次唤醒（第 224–231 行）。
  - `inject(msg)` = `send(msg,'next-step',false)`：面向模型的上下文，**不唤醒**；运行中驱动器在最近的后续 pre-step 领取，可能错过已经领走批次的请求；idle 时保持待处理直到 `followup` / `steer`（第 233–241 行；设计依据 `.agents\notes\implemented\architecture\2026-07-24-separate-context-injection-from-turn-execution.zh.md` 第 29、64 行）。
- 两个补充语义：唤醒投递若落在**已中止**的活动上会被改判为 `next-turn`（`agent.ts` 第 154–161 行）；`wakeDriver()` 在维护或已中止活动期间把唤醒闩存到 convergence 重放，`disposed` 永不闩存（第 214–224 行）。

### Q3 取消如何生效？取消发生在异步阶段会怎样（哪些提交被避免）？

> ⚠️ **第一次读请跳过本题**：它涉及 `prepareCall()` 的能力协商与流式结算，属 `3.6` / `3.8`。

**答案：`cancel()` 默认清空 inbox 并对当前 phase 的 `AbortController` 调 `abort(cause)`；生效方式是循环里 15 个协作式 `throwIfAborted()` 闸门 + 流 / 工具执行各自的中止收敛。取消落在 `agent/request` 或 `prepareCall()` 这两个异步阶段时，`system/message`、`user/message`、`request/header` 一律不提交，只留下平衡的 `step/start` + `step/end` 与 `turn/end{aborted}`。**

- 入口：`cancel(cause, options)` 先（除非 `keepInbox`）`inbox.clear()` + 清闩存唤醒，再 `abort(cause)`；`keepInbox: true` 时"活动轮次仍被中止，但未启动与待处理工作存活到后续轮次，且不记录 canceled splice"（`agent.ts` 第 175–181 行；`runtime-types.ts` 第 37–45 行；`docs\subsystems\core.zh.md` 第 279、281–293 行）。
- 原因持久化：`turn/end` 记 `{kind:'aborted', reason: TurnEndCancelCause}`，cause 从 `signal.reason` 拷成新对象，只保留 `kind` 与 hook 的 `reason`（`agent.ts` 第 80–95 行、第 366–372 行；`README.zh.md` 第 124 行；`packages\core\session\src\types.ts` 第 195–204 行）。
- 首个 cause 胜出：同一活动内后续 `cancel` 不改写原因（`runtime-types.ts` 第 178–179 行；测试 `cancel.spec.ts` 第 1040–1061 行）；idle 上取消是 no-op 且不武装后续工作（第 179–180 行；`cancel.spec.ts` 第 147–163 行）。
- **异步阶段的提交避免**（对应 `docs\architecture.zh.md` 第 117 行"在任一异步阶段取消都不会提交这两者"、`README.zh.md` 第 118 行）：
  - `agent/request` 之后、`prepareCall()` 之前：第 580 行检查 → 不提交 system / user / header。
  - `prepareCall()` 之后、提交之前：第 594 行检查 → 同上。
  - 提交发生在第 410–423 行，所以上述两个闸门是"提交前"的最后一道；`step/end` 由 `finally` 补齐（第 354–357 行），日志保持平衡（`system-prompt-admission.spec.ts` 第 396–398 行断言 `['step/start','step/end']` 且三者皆无）。
  - 更早的闸门（第 273、283 行）在 pre-step 内，取消时连 `step/start` 都不会打开（`cancel.spec.ts` 第 333–350 行：1 条 `turn/start`、0 条 `step/start`、`turn/end{aborted}`）。
  - 流式阶段（第 441、444 行）：取消会终结流并按已交付前缀结算——有内容则 `assistant/message{interrupted:true}`，无内容则 `assistant/attempt`（第 445–486 行；`README.zh.md` 第 118 行；`cancel.spec.ts` 第 775–791 行"cancel before any visible content finalizes nothing"）。
  - 工具阶段（`tool-calls.ts` 第 200、212、229 行）：停止新分发、drain 已启动调用并按模型顺序提交，未分发调用补 `tool/call` + 合成 `tool/result`，错误码 `ABORTED_BEFORE_DISPATCH`（同文件第 96–99、238–243、250–260 行；`README.zh.md` 第 126、182 行；`cancel.spec.ts` 第 494–547 行断言工具体执行次数为 0）。
  - 步骤失败路径还会为"尚无结果的工具调用"补结果（`TOOL_OUTCOME_UNKNOWN` / `TOOL_NOT_STARTED`），这一步在 `step/end` 之前完成（`agent.ts` 第 342–353 行；`README.zh.md` 第 128 行）。
- 取消与分派的关系：`cancel` 本身不是"立即停止一切"，它只 abort 信号；所有实际收敛都要靠检查点。这也是 `whenIdle()` 存在的意义——它等到整个 agent 静稳（`agent.ts` 第 237–242 行）。

### Q4 轮次在什么条件下关闭？`agent/turn-stopping` 起什么作用？

> ⚠️ **第一次读请跳过本题**：它涉及 `concludesTurn` 数据通道与限流策略的挂点，属 `3.11` 与策略层。

**答案：轮次关闭的充要条件是"模型不再欠响应 + `next-step` 为空"。等价地：`turn()` 的循环只有在某步返回 `completed` / `max-tokens`（`turnEnds` 非空）且 `inbox.nextStep.length === 0` 时才会 `break`，然后 `finally` 提交 `turn/end`。`agent/turn-stopping` 是这个判定中间插入的、可被数据重新打开的"最后一道检查"。**

- 关闭判定：`if (turnEnds && this.inbox.nextStep.length === 0) { await serial('agent/turn-stopping'); throwIfAborted(); }` 然后**再判一次**同样条件才 `break`（`agent.ts` 第 359–363 行）。`turnEnds` 的来源是步结束原因，且 `max-tokens` 粘性（第 338–341 行），取值来源是 `completed`（无工具调用或工具 `concluded`，第 533、538 行）或 `max-tokens`（第 530 行）。
- 不关闭的情况：步返回 `null`（工具还欠一次请求）→ `turnEnds` 变 null，`target='next-step'`，继续循环（第 341、364 行）；或已有 `next-step` 输入 → 判定失败，继续循环（第 359、363 行）。
- 关闭后是否立刻开下一轮：`if (!this.inbox.hasPending) return false`（第 390 行）——有 pending 就重置 `phase.abort`、清闩存、`step=0`、返回 true，`kick()` 的 `while (await this.turn())` 继续（第 254 行、第 391–395 行）。
- 提前 return 的两条 0-step 路径**不经过**这一步：`reject` 与空首批在 try 内直接 `return false`（第 317–327 行），因此排在后面的工作会停在 inbox 等下一次唤醒（`interception.spec.ts` 第 495–532 行、第 382–438 行）。
- `agent/turn-stopping` 的作用（`runtime-types.ts` 第 364–381 行）：
  1. **语义**：轮次即将关闭（模型不欠响应、没有新 steering）时、边界提交之前被 await 的 serial 监听器；它没有 `next()`，返回值也不参与决策。
  2. **唯一控制手段是数据**：监听器调 `agent.steer(...)` 让 `next-step` 非空，循环重读 inbox 后就会再跑一步——"数据决定一切，所以监听器顺序不能改变结果"（同文件第 366–369 行）。`contract-regressions.spec.ts` 第 319–341 行断言：默认本会停止的一轮，因为 `turn-stopping` 里 `steer` 而产生了第 2 个请求。
  3. **失败被容纳为轮次错误**：监听器抛错时该轮 `turn/end{kind:'error'}`，循环继续存活（`contract-regressions.spec.ts` 第 346–369 行），因为 `kick()` 在驱动器边界 catch（`agent.ts` 第 252–257 行）。
  4. **取消也能在这里生效**：第 361 行的 `throwIfAborted` 让"停止窗口内取消"不再开新步骤（`cancel.spec.ts` 第 859–887 行）。
  5. **它是限流策略的官方挂点**：README 明说没有内置轮次预算，要用 `agent/turn-stopping` 这类既有扩展点执行取消（`README.zh.md` 第 217 行）。
  6. **它不是唯一的提前结束通道**：工具结果的 `concludesTurn` 在同一步就结束轮次，但不会短路已提交的 `next-step` 工作（`runtime-types.ts` 第 371–374 行；`tool-calls.ts` 第 158 行）。
- 边界平衡的保证：`turn/end` 在 `finally` 中提交（`agent.ts` 第 382–389 行），`step/end` 也在 `finally`（第 354–357 行）；恢复路径为崩溃在轮次中途的日志补 `step/end` + `turn/end`（`packages\core\session\src\repair.ts` 第 94–96 行）。
