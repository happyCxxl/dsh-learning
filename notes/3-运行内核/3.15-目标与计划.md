## 0. 怎么读这一课（阅读许可）

### 0.1 这一课是什么、不是什么

**是**：三个**互不相同**的机制，以及它们的分界线——它们回答三个不同问题：

| 机制 | 回答的问题 | 一句话 |
|---|---|---|
| **goal 目标** | "这件事做完了吗？" | 一个跨重启存活的**完成标准**，可以驱动无人值守的多轮续跑 |
| **plan-mode 计划模式** | "动手之前，人批准了吗？" | 一道**动手前的一次性评审闸门** + 一段可替换的提示词 |
| **tool-todo 待办** | "现在做到哪一步了？" | 当前这一步的**可见清单**，整表替换，属调它的那个 agent |

**不是**：三份 API 手册。工具的完整 schema、命令的完整语法不在这里逐字段抄写。

### 0.2 现在只要记住这 4 件事

1. **目标是「状态」，不是「调度器」，也不是「独立对话」**——它附着在**已有**会话上，会话日志是它的唯一真源；同一个页面把它与"调度器""Ralph 的全新 agent"三者明确区分开。
2. **目标自己不会干活**：真正排下一轮的是**可选的** `dsh-goal-round-driver`，它的条件是"agent 空闲 + 目标是 `active` + 已 `armed`"。不挂它，目标就只是一个被记录的状态。
3. **`armed` / `disarmed` 是权限，不是状态**，所以**有意不写进日志、也不参与回放**——这条设计在类型、折叠函数、历史决策三处都被写死；后果是"恢复会话不会静默开工"。
4. **计划与待办的产物形状不同**：计划是"一份完整 markdown + 一次二选一评审"，待办是"当前这一步的清单，整表替换，下一轮次开始就清空"。

### 0.3 明确授权：这些现在不用管

- **严格解码器的逐字段形状**（键集必须精确匹配、哪种 phase 才允许带 `blockedReason`）——第一次读只需记住结论"**多一个键少一个键都会让回放大声失败**"；源码块在 §3.1（块 2）与 §3.3，回查时再看。
- **驱动器的竞态防护细节**（`attempt` 的四个阶段、`stale` / `cancelled` 标志、teardown 的等待顺序）——第一次读只需记住"**先预留、后准入；被拒绝的预留不消耗轮次**"。逐块讲解在 §5。
- **`pendingActivation` 为什么要跨 `session.append` 边界**——这是本课最绕的一处，已降级进附录 A Q3，第一次读跳过。
- **plan-mode 的 `stateVersion: 3` / todo 的 `stateVersion: 2` 迁移语义**——属 `3.3`（那里已定义 `stateVersion` 是"持久缓存的失效版本号"），本课只用到"这两个单元各自升级过"这一事实。

### 0.4 本课依赖前面已定义的词汇

已由前面各课定义、本课**不重复解释**：`turn`（轮次）/ `step`（步骤）/ `Round`（`1.1` §7）；`projection` 与 `stateVersion`（`3.3`）；inbox 的 `next-turn` / `next-step`、`followup` / `steer` / `inject` 三个预设、`agent/pre-step` 这道可 reject 的闸门（`3.5`）。

## 1. 最小词汇表（本课新增的 8 个词）

| 词 | 大白话 | 在源码里的样子 |
|---|---|---|
| **goal 目标** | 附着在**已有**会话上的**一个**持久完成目标：一件事的"做完标准" | `ctx.goal` 服务；一条 `goal/change` 会话事件 |
| **Goal Round** | 为当前目标**接纳的一次续行周期**，具体就是一个轮次；里面有几步由模型决定 | 一条 `source.kind === 'goal'` 的 `user/message` |
| **activation 激活** | 进程**本地**的"是否允许自动续跑"权限位 | `'armed'` / `'disarmed'`；`GoalView.activation` |
| **phase 阶段** | **持久**的生命周期阶段 | `'active'` / `'paused'` / `'blocked'` / `'complete'` |
| **goal round driver 驱动器** | 把"进行中的目标"变成连续轮次的那个**可选**插件 | 包 `dsh-goal-round-driver`，**没有服务键** |
| **plan mode 计划模式** | "先探索、先设计、拿批准再动手"的协作状态 | 一条 `plan/mode` 会话事件 + 提示词段落 |
| **exit_plan_mode** | 把写好的计划交给用户评审的**工具**，批准才离开计划模式 | 工具名常量 `EXIT_PLAN_MODE` |
| **todo 待办** | **当前这一步**的可见清单，整表替换 | 一条 `todo/write` 会话事件 + `todos` 投影键 |

> ⚠️ 这 8 个词里，**只有 `goal` / `phase` / `activation` 属于目标领域本身**；驱动器、计划模式、待办是三个**不同的包**，它们只是恰好能用同一套会话日志串起来。搞清楚"哪个词属于哪个包"，本课就成功了一半。

### 2.2 一次 Goal Round 的完整路径（动态过程）

```

  │ ① driver 的 readyToDrive：fiber 活跃 + 未在停 + agent 仍是注册表里那个 + idle + 无竞争输入

  ▼
  │ ③ 目标是 active 且 armed 吗？额度还有吗？
  │    → 额度耗尽：以稳定码 `round-limit` 记 blocker，退出
  ▼
  │ ④ 预留 round = roundsStarted + 1，渲染 <goal_round> 提示词，agent.followup(message)
  ▼

  │ ⑤ agent/pre-step 再次验证：这条已领取消息仍是"当前目标的下一轮"吗？
  │    → 不是：返回 { kind: 'reject' }，且【不】消耗轮次编号
  ▼
  │ ⑥ 通过：会话追加 user/message（source.kind === 'goal'）
  ▼
回放侧（fold）只在第 ⑥ 步的这类事件上把 roundsStarted 推到 round
```

### 2.3 大白话版：一个长期目标怎么驱动续跑

**完全不用上面的术语**，先建立画面（来源：`packages\goal\goal-round-driver\README.zh.md` 第 49 行的"每轮做什么"一段；这里只做白话转述，细节见 §5）。

1. 用户丢下一句"这件事做到什么程度算完"，助手把这句话记成一条**持久的完成标准**，并**顺手把自动续跑的开关打开**。
2. 助手开始干活。干着干着，手头的活干完了，机器**空闲**下来。
3. 这时有个**旁观者**看了一眼：那条完成标准还在不在？开关还开着吗？额度还有吗？
4. 三个都是"是"，它就**自己往里塞一句话**——这句话不是用户说的，是它替用户排的，内容是"目标是什么、这是第几轮、接着干"。
5. 这句话进入了同一个对话历史，机器被唤醒，继续干活。**没有新开一个助手，也没有复制前面的对话**。
6. 这句话**只有真正进入工作步骤**才算消耗一次额度。如果排队期间情况变了（目标被暂停了、轮次被取消了、人类插话了），这句话会被**退回**，且**不占额度**。
7. 额度用完，旁观者就给完成标准**记一条"卡住了"的说明**（原因是"轮次上限"），然后停手。
8. 从**重启 / 恢复 / fork** 回来的会话，完成标准和历史**都还在**，但那个开关**一定是关的**——必须有人（用户或模型，且必须有人的授权）明确说一句"继续"，续跑才会重新开始。

## 3. 目标领域：类型、持久记录、回放校验

**结论先行**（对应 §0.2 第 1、3 条）：

1. **持久阶段与进程本地激活是"两个字段"**，归属不同、生命周期不同。
2. **一条 `goal/change` 事件，要么是完整快照，要么是墓碑**；七个动词；严格解码器要求**键集精确匹配**。
3. **回放只在一类事件上推进轮次计数器**，并且要求是"紧接着的下一轮"。

### 3.1 类型面：四个持久字段 + 一个进程本地字段

`packages\goal\goal\src\types.ts` 第 44–72 行

```ts
/** Durable continuation phase. Activation is process-local and separate. */
export type GoalPhase =
  | 'active'
  | 'paused'
  | 'blocked'
  | 'complete'

/** Machine-routable and human-readable explanation for a blocked goal. */
export interface GoalBlockReason {
  readonly code: string
  readonly message: string
}

/** Full durable state written by every non-clear goal mutation. */
export interface GoalSnapshot extends GoalRef {
  readonly objective: string
  readonly phase: GoalPhase
  readonly blockedReason?: GoalBlockReason
  readonly maxGoalRounds: number
}

/** Whether this live process may automatically continue an active goal. */
export type GoalActivation = 'armed' | 'disarmed'
// （第 16–25、27–42 行：GoalId 品牌、GoalRef、CreateGoalRequest / EditGoalRequest；
//   各字段的 JSDoc 保留在源码里，此处只留签名；第 73 行起是 GoalActivationChanged，见下一块）
```

按块讲解：

- **本块的省略**：只留"类型签名"与三句**关键** JSDoc。每个字段各自的一句 `/** … */`（原文每字段都有）被省掉——它们是**字段名的同义重复**（`objective` 的注释就是 "Human-requested completion objective."），全部照录会把 29 行的块撑到 40 行以上；需要逐字核对时看源码。
- **做什么**：定义"目标持久长什么样"。`GoalSnapshot` 只有 6 个字段：`id`、`revision`（来自 `GoalRef`）、`objective`、`phase`、`maxGoalRounds`，以及**仅在 `blocked` 时存在**的 `blockedReason`。
- **与哪个知识点相关**：§0.2 第 1、3 条。
- **为什么这么写**：`GoalPhase` 上方那句 JSDoc 是作者原文——*"Durable continuation phase. **Activation is process-local and separate.**"* 这句话不是注解，是**契约**：它预告了后面两个类型（`GoalSnapshot` 不带 activation、`GoalActivation` 单独成类型）的划分依据。**持久**回答"这件事处于什么状态"，**进程本地**回答"这台进程现在准不准自动干活"。
- **`GoalRef` 从哪来**：`GoalSnapshot extends GoalRef`，而 `GoalRef` 是同文件第 20–25 行的 `{ id: GoalId, revision: number }`——所以每个快照自带 CAS（compare-and-set）身份，这就是后面所有变更为什么都要求传一个 `ref`。

按块讲解：

- **做什么**：同一份目标的**三种投影**——持久快照（进日志）、回放值（`GoalProjection`，从日志算出来）、实时视图（`GoalView`，给调用方看）。
- **与哪个知识点相关**：§0.2 第 3 条。
- **三者的差集就是本课的核心结论**：`GoalView` = `GoalProjection` 的字段 + `activation`。而 `activation` 的 JSDoc 只有四个字：**`never persisted`**。
- **`GoalActivationChanged` 为什么需要单独一个类型**：因为权限变化**不写日志**，所以它**不能**挂在 `session/event` 上被回放；它必须是 cordis 的实时事件（`@mode emit`），载荷里只带"哪个会话 + 哪个目标的哪个 revision + 现在的权限"——**故意不带完整目标**。这样 UI 能实时显示开关，而日志侧一无所知。

### 3.3 一条事件：完整快照，或者墓碑

**先说动词，再说事件形状。** 归属上，`'goal/change'` 被声明进 `SessionEventMap`，所以它是**会话事件**（持久、可回放），不是 agent 事件。

`packages\goal\goal\src\domain.ts` 第 13–44 行

```ts

  | 'create'
  | 'edit'
  | 'pause'
  | 'resume'
  | 'complete'
  | 'block'
  | 'clear'

/** Full-snapshot goal mutation committed by a durable `goal/change` event. */
export interface GoalSnapshotChangeMeta {

  readonly roundsStarted: number

  readonly version: 1
  readonly operation: 'clear'
  readonly cleared: GoalRef
```

按块讲解：

- **做什么**：定义"变更长什么样"以及"它挂在哪个事件表上"。
- **与哪个知识点相关**：§0.2 第 1 条（"日志是唯一真源"）。**`declare module` 那一段就是"把它变成持久事实"的那一步**——没有这次声明合并，`session.append('goal/change', …)` 连类型都过不了。
- **为什么快照变体要带全部字段**：`GoalSnapshotChangeMeta` 里既有 `goal`（完整快照）又有 `roundsStarted` / `createdAt` / `updatedAt`——**一次变更写完整状态**，而不是"改了什么"。好处是回放不需要重放差分；代价是每次变更都更大。归档 Agent Note 把这条权衡写成"完整快照便于检查、严格回放与 last-wins 投影，且不会向模型历史添加只用于变更的消息"（`.agents\notes\archived\feature\2026-07-19-persisted-same-session-goal-domain.zh.md` 第 54 行）。
- **墓碑为什么必须是独立变体**：`Exclude<GoalOperation, 'clear'>` 是**类型层**的排除。`clear` 之后目标不存在了，所以载荷里没有 `goal`，只有 `cleared: GoalRef`（"我清掉的是哪个修订"）与 `clearedAt`。这样"清除"仍然是有身份、有顺序的持久事实，而不是把前面的事件抹掉。

```ts
/**
 * Apply one session event to the strict durable goal fold.
 * @param state - mutable fold accumulator.
 * @param event - next event in sequence order.
 */
export function applyGoalEvent(state: GoalFoldState, event: SessionEvent): void {   // ← 每来一条事件就被调一次
  if (event.type === 'goal/change') {
    const change = decodeGoalChange(event.data)
    /* v8 ignore next -- the event's declared payload always identifies itself as a goal change. */
    if (change === undefined) throw new Error(`goal change at session event ${event.seq} has an invalid kind`)
    applyGoalChange(state, change)
    return
  }
  if (event.type === 'user/message') {                        // ← 只有这一类事件可能推进轮次
    const source = goalSource(event.data.source)               // ← 不是 goal 来源就返回 undefined
    if (source === undefined) return                           // ← 人类消息、工具消息在此被滤掉
    const current = state.goal
    if (current === undefined || current.phase !== 'active' || source.goalId !== current.id
      || source.revision !== current.revision || source.round !== state.roundsStarted + 1
      || source.round > current.maxGoalRounds) {               // ← 六个条件，缺一不可
      throw new Error(`goal round at session event ${event.seq} is not the next admitted round of the active goal`)
    }
    state.roundsStarted = source.round                         // ← 唯一的推进点，赋值而不是 ++
  }
}

//   其 JSDoc 原文 "activation is deliberately absent"，见 §4.3）
```

按块讲解：

- **做什么**：把一条会话事件折进累加器。**只有两个 `if` 分支**：`goal/change` 走变更校验，`user/message` 走轮次计数，其它事件**什么也不做**。

  - **人类轮次不计费**——`goalSource`（第 175–183 行）第一句就是 `if (source.kind !== 'goal') return undefined`，普通 `user/message` 在这里被丢掉。

### 4.2 提交一次变更：`pendingActivation` 与 seq 对齐

```ts
  private commit(agent: Agent, runtime: GoalRuntimeState, change: GoalChangeMeta, activation: GoalActivation): void {
    const ref = goalChangeRef(change)                       // ← 从载荷里取 { id, revision }
    runtime.pendingActivation = { offset: agent.session.seq, activation }   // ← 先记"追加前的 seq"

    } finally {

    const notification: GoalChanged = {

      ref: { ...ref },
      ...goal === undefined ? {} : { goal },

  }
```

按块讲解：

- **做什么**：一次变更的完整落地：**埋权限 → 追加持久事件 → 校验 seq → 清状态 → 发实时通知**。
- **与哪个知识点相关**：§0.2 第 3 条；附录 A Q3。
- **为什么先埋 `pendingActivation` 再 append**：因为 §4.1 边沿 ② 的监听器会在 append 的**同步广播**里被调用，而那时它需要知道"这次变更想把权限设成什么"。把 `offset`（append 前的 seq）也记下来，是为了在 append 返回后比对 `event.seq`——**只有两者相等**才说明"这条事件就是我的那条"，此时才真正写 `runtime.activation`。
- **`finally` 为什么必须清 `pendingActivation`**：append 抛错时（磁盘满、会话已关闭），待定值不能留在内存里，否则**下一条无关的 `goal/change`** 可能因为 seq 恰好对上而拿到错权限。**fail-closed**：清掉之后，边沿 ② 的 else 分支会给出 `disarmed`——宁可少权限，不可多权限。
- **`goal/changed` 与 `goal/change` 是两件事**：前者是**进程本地实时通知**（带作用域过滤，见 `domain.ts` 第 104–115 行的 `@mode emit` 声明），后者是**持久会话事件**。驱动器只听前者（§5 的 `needsCheckpoint` 就是被它触发的）。

## 5. 驱动器：什么时候才排下一轮

**结论先行**（对应 §0.2 第 2 条）：驱动器是**可选的**（`packages\goal\README.zh.md` 第 30 行的包表里，它是唯一 `ctx` 键写"无服务键"的一行；它靠 `inject` 使用别人的服务，自己不提供能力）。它的规则可以压成三句：

1. **只在整体空闲时排**：`readyToDrive` 要求 fiber 活跃、未在停、agent 仍是注册表里那个、`status === 'idle'`、且没有竞争输入。
2. **先预留、后准入**：空闲时就为 `roundsStarted + 1` 生成提示词并 `followup`，但**只有进入步骤**才消耗额度。
3. **任何一步不满足就 fail-closed**：disarm、记 blocker、或直接退出——**绝不"试一下看看"**。

按块讲解：

- **做什么**：把 `/plan` 命令的运行与已落库的模式，折叠成"当前是否激活 + 有没有待生效的选择"。
- **与哪个知识点相关**：§0.2 第 4 条。
- **①②③ 是一条完整的因果链**：命令**跑起来**（`command/run`）→ 命令**结算**（`command/done`，只有成功且与现状不同才产生候选）→ 候选被**落库**（`plan/mode` 一到就把候选清空）。**所以 `pending` 是"已经请求、还没落库"这个窗口的可回放表达**——这是它唯一的非持久部分的来源。
- **⑨（`request/header` 那一支）`activeAtLastHeader` 的用途**：模型看到的提示词可能落后于实际模式（模式变了但还没组装下一个请求）。它记的是"**上一次组装的请求描述的是哪个模式**"，用来判断"要不要给模型补一句模式切换通知"（`narration()`，第 455–467 行）。**只有"上次说错了"才通知**，所以不会每轮都念一遍。

- **`pending` 的算法是本块最精巧的一处**：`wanted !== null && wanted !== state.active` —— 候选值**存在**、且与**已落库值不同**，才算"待生效"。所以"请求了与现状相同的模式"不算待生效（`set()` 里那种情况直接返回 `noop`），而"请求了相反模式又改回来"也不算（候选被 `cancelled` 清掉，见 §7.2）。
- **`command/done` 那一支为什么要看 `kind === 'success'`**：命令失败（比如语法错误）**不产生**候选——否则一个打错的 `/plan off` 会让 UI 显示"待生效"，而永远不会生效。

### 7.2 追加时机：有开放轮次时只记"待生效"

`packages\plan\plan-mode\src\index.ts` 第 418–438 行

```ts
  set(agent: Agent, active: boolean): 'committed' | 'queued' | 'cancelled' | 'noop' {
    const session = agent.session
    const pending = this.pendingIntents.get(session)
    const target = pending?.active ?? this.loggedActive(session)     // ← 待生效优先于已落库
    if (active === target) return 'noop'                             // ← ① 幂等：已经是这个目标
    if (this.hasOpenTurn(session)) {                                 // ← ② 有开放轮次：只记待生效
      this.pendingIntents.set(session, { active, narrate: true })
      return this.loggedActive(session) === active ? 'cancelled' : 'queued'
    }
    // No open turn: commit now. Delete only after append succeeds so a
    // failed durable write leaves the selection retryable, not dropped.
    if (active === this.loggedActive(session)) {                     // ← ③ 回到已落库状态 = 取消反向请求
      this.pendingIntents.delete(session)
      return 'cancelled'
    }
    session.append('plan/mode', { active })                          // ← ④ 没有开放轮次：立即落库
    this.pendingIntents.delete(session)
    const narration = this.narration(session, active)
    if (narration !== undefined) agent.inject(narration)
    return 'committed'
  }
```

按块讲解：

- **做什么**：选择计划模式的目标状态，并决定"现在落库还是等下一个边界"。
- **与哪个知识点相关**：§0.2 第 4 条；也是本课唯一"**只在进程内**"的持久化缺口。
- **② 为什么"有开放轮次"就不能立即 append**：`session.append` 会**同步广播** `session/event` 给所有监听器，而在一个轮次**进行中**追加"模式变了"会让正在组装的那次请求与日志**不一致**（组装用的是旧模式，日志却已经变了）。所以选择先留在 `pendingIntents`（进程内存），等**下一个被接受的轮内 `pre-step`**——那是运行时唯一的追加点——再落库。
- **④ 为什么"没有开放轮次"就能立即落库**：因为不会再有 `pre-step` 来接手；此时不加，用户的点击就要等到下一次有人说话才生效。`hasOpenTurn` 读的是 `turnBoundary` 投影的 `openTurnStartSeq`（第 372–376 行），**那是回放量而不是内存标志**——所以"是否在轮次中"这个判断在恢复后依然对。
- **作者注释就是"为什么"**：*"Delete only after append succeeds so a failed durable write leaves the selection retryable, not dropped."* —— append 失败时**不删**待生效项，于是后续的 `pre-step` 会重试。这条纪律在 `onBoundary`（第 441–453 行）里重复了一次。
- **③ `cancelled` 这个返回值容易被误读**：它表示"你这次请求的方向与已落库状态一致，所以我把反向的待生效请求**取消**掉了，什么都没变"。所以返回值是 `cancelled` 但 UI 显示的成功文案是"Plan mode entry cancelled"（第 247 行）——**取消的是那个未生效的相反请求，不是这次操作**。
- **已知代价（作者原文）**：`README.zh.md` 第 185 行，*"待生效选择只存在于进程内——某轮最后一个被接受的 pre-step 之后作出的选择，若进程在另一个被接受的轮内 pre-step 之前退出就会丢失；UI 必须重新应用它。"*

按块讲解：

- **做什么**：注册 `todos` 投影单元与 `todo_write` 工具。
- **与哪个知识点相关**：§0.2 第 4 条。

- **① 与 ③ 合起来是本包最省事的地方**：折叠只有两条规则 + 一个默认分支。`todo/write` **整表替换**（不是增量），所以没有"逐项编辑""合并""回读"这些概念——`README.zh.md` 第 157 行把它写成"整表替换是唯一操作——没有部分更新、没有回读工具、没有逐项编辑"。

- **⑤ 单所有者的落点只有三行**：`if (!exec.agent) throw`。注释给了理由——"无处可写，直接拒绝而不是静默无操作"。所以 subagent 各自有各自的表，**没有跨 agent 共享**的方式（`README.zh.md` 第 156 行）。
- **⑥ 待办是"立即落库"，计划是"等边界"**：这是两个包最本质的差异，也是同一个问题（"什么时候能安全地 append"）的两种答案——**待办只是 UI 状态**（`TodoItem` 的 JSDoc：*"Log-only UI state; never derived history"*，`types.ts` 第 30 行），追加它不会与正在组装的请求冲突；**计划模式会改变提示词内容**，所以必须等边界。

### 7.5 `TodoItem` 的刻意最小

`packages\todo\tool-todo\src\types.ts` 第 11–33 行

```ts
/**
 * One entry in an agent's todo list — the unit of the `todo/write`
 * whole-list snapshot declared by this package.
 *
 * Deliberately minimal: a human-readable `content` line and a three-state
 * `status`. No id, priority, or `activeForm` — the list is replaced wholesale
 * on every write (last-write-wins), so entries need no stable identity. The
 * three statuses describe the complete portable lifecycle needed by model and
 * UI consumers.
 */
export interface TodoItem {
  /** What this task is — a short imperative line shown in the UI. */
  content: string
  /** Lifecycle state. `in_progress` marks a task being worked now; parallel work may mark several. */
  status: 'pending' | 'in_progress' | 'completed'      // ← 三态，就这三个
}

declare module '@deepseek-ai/dsh-session/types' {
  interface SessionEventMap {
    /** Whole-list snapshot; latest write wins on replay. Log-only UI state; never derived history. */
    'todo/write': { todos: TodoItem[] }
  }
}
```

按块讲解：

- **做什么**：定义待办条目与它的持久事件。
- **与哪个知识点相关**：§0.2 第 4 条。
- **"没有 id"是结论而不是疏漏**：作者把理由直接写在注释里——*"the list is replaced wholesale on every write (last-write-wins), so entries need no stable identity"*。**整表替换 ⇒ 不需要稳定身份**。所以整个包里都找不到"按 id 找一条待办"的代码——因为不存在这种操作。
- **`never derived history` 这句限定**：待办**不是**从别的东西推导出来的，它**就是**模型写的那个列表。所以它不能被当作"实际做了什么"的证据——UI 上它只是"自称的进度"。
- **对照**：`GoalSnapshot` 有 `id` + `revision`（要做 CAS、要跨轮次、要持久校验）；`TodoItem` 没有 id（只被人看一眼，下一轮就清）。**两个数据结构的最小性，正是它们机制差异的镜像。**

### Q1 目标是什么？它与调度器、独立对话的差别在哪？

**答案：目标是「附着在现有会话上的单个持久完成目标」**——由 `{ id, revision }` 标识、按修订号演进、带四个持久阶段和 Goal Round 上限，`blocked` 额外保留策略代码与说明；**会话日志是它的唯一真源**（`docs\glossary.zh.md` 第 25 行）。

模型侧的定义写在 `tool:goal` 提示词段里：目标是"让这个会话在自动续行轮次中继续工作"的持久物，**哪怕用户没说「goal」二字**（`packages\goal\tool-goal\src\index.ts` 第 51–54 行的工具描述、第 114–123 行的 `guidance()`）。

与**调度器**的差别，一句话：**目标记录状态，驱动器排轮次**，两者是不同包、不同进程内状态、不同权限。

- 目标不排工作：`packages\goal\README.zh.md` 第 12 行原文——"该目标记录完成状态而不调度工作；因此，自动续行必须单独启用"。
- 真正决定"现在要不要再跑一轮"的是 `dsh-goal-round-driver`：`readyToDrive()` 要求 agent `idle`（§5.1），并且**只有它**会给目标排 `followup`（§5.2 第 ⑩ 行）。
- 驱动器**没有服务键**、是可选件（`packages\goal\README.zh.md` 第 30 行的包表里那一行的 `ctx` 键列就写着"无服务键"）。不挂它，目标就只是一个被记录的状态。

与**独立对话**的差别：

- 它附着在**已有的同一个**会话上；Round 是往同一份历史里追加一条 `<goal_round>` 用户消息（§5.4；`README.zh.md` 第 108–112 行写明"更早的用户消息、goal 状态快照、assistant 输出与工具记录仍保留在同一会话历史中"，第 112 行还有一句"不会创建新 agent，也不会复制对话前缀"）。
- "全新 agent 的独立尝试"是另一个东西：词汇表把它归给 **Ralph 循环**——"由工作流和 subagent 原语组合而成的面向模型的工具策略，**不是**同会话目标"（`docs\glossary.zh.md` 第 43 行）。
- 驱动器 README 把这条线划在包外：**"只在同一会话执行"——此包有意不 spawn 新 agent、不 fork 会话前缀，也不实现 Ralph 风格的独立尝试**（`README.zh.md` 第 126 行）。

### Q2 Goal Round 与 turn 的关系？

**答案：Goal Round 是「由目标触发的那个轮次」，两者是子集关系；差别在于计数器只认 Goal Round。**

- 词汇表定义：`Goal Round` 是"为当前目标接纳的一次续行周期。同会话驱动器将 Goal Round 具体化为一个由目标触发的**轮次**，其中可包含零个或多个步骤；同一会话中无关的人类轮次**不消耗** Goal Round 上限"（`docs\glossary.zh.md` 第 26 行）。`turn` 的定义在同一个文件第 37 行："会话中一次对已接纳输入的排空过程"。
- **驱动器确实是用"开一个轮次"的方式实现的**：它调 `agent.followup(message)`（§5.2 第 ⑩ 行），而 `followup` 的契约是"该项成为**它自己轮次里唯一的普通消息**"（`packages\core\agent\src\runtime-types.ts` 第 217–222 行）。所以 **Goal Round ⊆ turn**——一个 Goal Round 恰好占据一个轮次，而不是"塞进某个轮次"。
- **计数口径反过来不成立**：只有 `source.kind === 'goal'` 且恰好是 `roundsStarted + 1` 的已准入 `user/message` 才推进计数器（§3.6）。人类轮次、陈旧预留都不算（`README.zh.md` 第 49 行："只有进入步骤的 goal 消息消耗上限，人类消息和陈旧预留不会消耗"）。
- **一个 Round 里有几步由模型决定**：`turn()` 内部循环 `step`，直到没有待处理输入才结束轮次（`packages\core\agent-loop\src\agent.ts` 第 296–396 行；`3.5` 已逐段讲过）。
- **Round 会让 Chat 渲染一个自包含的请求头**：驱动器在 `pre-step` 通过后返回 `{ ...decision, startsRequestSeries: true }`（§5.4 末尾所引的第 428 行），agent loop 据此把该请求标成序列起点（`agent.ts` 第 409–425 行）。
- **额度只由"进过步骤的" Round 消耗**：`agent/pre-step` 前后各验一次，不符就 reject（§5.3），且 `README.zh.md` 第 71 行写明"因陈旧而被拒绝的预留不会消耗 Round 编号"。

### Q3 「目标激活」（armed / disarmed）为什么不参与持久回放？

> ⚠️ 本题涉及 `session.append` 的同步广播边界与 `WeakMap` 生命周期，**第一次读请跳过**。

**答案：因为它是「执行权限」，不是「状态事实」；把权限持久化就等于「恢复会话时静默开工」，而这被明确拒绝。**

- **类型层就不给它落地的位置**：`GoalSnapshot`（唯一写进 `goal/change` 的目标载荷）只有 `id` / `revision` / `objective` / `phase` / `maxGoalRounds`（+ `blocked` 时的 `blockedReason`），**没有** activation（§3.1）；`GoalProjection` 的注释是 *"Activation is process-local (never persisted) and deliberately absent"*（§3.2）。
- **折叠函数把这条写进契约**：`foldGoal` 的返回注释是 *"a fresh durable projection; **activation is deliberately absent**"*（§4.4）。
- **历史决策原文**：归档 Agent Note 把"持久化激活态并自动重启"列为**不予采纳**，理由是"打开或恢复会话时必须等待人类输入；持久阶段记录状态，而不是再次消耗资源的授权"（`.agents\notes\archived\feature\2026-07-19-persisted-same-session-goal-domain.zh.md` 第 46 行）。
- **词汇表给出同一句话的用户可见后果**：激活态"有意不参与持久回放，因此在恢复或 fork 后，只有随后通过 `/goal` 或模型工具执行一次经人类授权的恢复变更，自动工作才能开始"（`docs\glossary.zh.md` 第 27 行）。
- **落地成三条边沿 + 一个初值**：
  1. 任何种子的初始 runtime 是 `disarmed`（§4.1 块 7 之后的第 483–493 行，`runtimeState` 的首次构造）；
  2. 每次 `agent/created` 一律 disarm（§4.1 块 7 的边沿 ①；来源是 `startup|resume|clear|compact`，见 `packages\core\agent\src\runtime-types.ts` 第 124–125 行）；
  3. 驱动器加载到已有 agent 上也逐个 disarm（`packages\goal\goal-round-driver\src\index.ts` 第 431–436 行，作者注释："Loading a lifecycle driver over existing agents never inherits hidden automatic authority from an earlier producer instance."）。
- **`pendingActivation` 到底在防什么**（本题的"为什么这么写"）：`session.append()` 是**同步**的，它会在返回之前就把 `session/event` 广播给 §4.1 边沿 ② 那个监听器。所以激活必须"**先声明、后核对**"：
  1. `commit()` 在 append **之前**写下 `pendingActivation = { offset: session.seq, activation }`（§4.2 块 8）；
  2. append 的同步广播里，边沿 ② 看到 `pendingActivation.offset === event.seq`，于是取出待定值；
  3. 若**不相等**（说明触发我的这条事件是别人的），一律取 `disarmed`——**fail-closed**；
  4. append 返回后 `commit()` 再核对一次 `event.seq`，相等才真正把 `runtime.activation` 写实；
  5. `finally` 里无条件清掉 `pendingActivation`，不留悬挂状态。
  没有这套机制，就只能"append 完之后再设激活"——而那时同步监听器已经跑过、已经用**旧**权限评估过一遍了。
- **反面证据（权限可以被单独拿掉、且不留痕）**：`disarm()` 不写事件、不改修订号、不发 `goal/changed`（§4.3 表最后一行）；单元测试 `lets a lifecycle owner disarm without writing a durable revision` 用事件数组长度钉住了这一点（`packages\goal\goal\tests\goal.spec.ts` 第 254–266 行）；§9.4 的探针也复现了同一结果。
- **补充：`armed` 是每次变更显式声明的，不是从阶段推导的。** `create` / `resume` 传 `'armed'`；`edit` 保持 `runtime.activation`；`pause` / `complete` / `block` / `clear` 传 `'disarmed'`（行号见 §4.3 表）。因此 **「`active` 但 `disarmed`」是一个正常状态**——重启后的会话本来就是这样，`command-goal` 也专门为它准备了不同提示语（§6.4）。

### Q4 计划与待办各自解决什么问题？

> ⚠️ 本题涉及 `turnBoundary` 投影与 `userQuestions` 通道，**第一次读请跳过**。

**答案：计划解决「动手前先拿到人的批准」，待办解决「动手过程中让人看见进度」。一个面向"做不做、怎么做"的一次性契约，一个面向"做到哪一步"的持续清单。**

| 维度 | 计划（plan-mode） | 待办（tool-todo） |
|---|---|---|
| 谁决定内容 | 模型探索后自己写完整 markdown 计划，用户 `Approve` / `Keep planning` | 模型每次重发整张清单 |
| 关键产物 | `exit_plan_mode` 的评审交互 + `{ approved: true }` | `todo/write` 整表快照 + 计数回执 |
| 持久事件 | `'plan/mode': { active: boolean }`（整值替换） | `'todo/write': { todos: TodoItem[] }`（整表替换） |
| 投影键 | `plan` → `{ active, pending }`，`stateVersion: 3` | `todos` → `TodoItem[] \| null`，`stateVersion: 2` |
| 生命周期 | resume / fork 后**保留** | 下一轮次开始即清空 |
| 阶段边界 | 有开放轮次时待生效，下一个被接受的轮内 pre-step 才落库 | **立即** `session.append` |
| 所有者 | 每个 agent 会话的日志模式位 | 恰好一个 agent 会话，无共享作用域 |
| 配置 | `section`（必填引导文本） | `allowParallelInProgress`（必填布尔） |

**计划解决什么**：它要求 agent"先探索和设计再执行"，然后把计划呈交批准；`/plan` 进入、`Approve` 或 `/plan off` 离开，反馈则要求继续规划（`README.zh.md` 第 12、55–63 行）。它的核心机制**不是"限制工具"**，而是"**换一段提示词 + 一个评审闸门**"：激活时系统提示词里多出部署方配置的段落（第 216–224 行），工具目录**不变**（第 184 行"引导而非强制"）。模式本身是**可回放的持久日志**，所以 resume / fork 后还在计划模式里（第 12 行；`src/index.ts` 第 141–160 行的投影折叠）。**唯一的非持久部分**是"已选但还没被 pre-step 接受"的待生效项（第 185 行）——它的机制见 §7.2。

**待办解决什么**：把多步工作拆成具体任务、标出正在做的、做完就勾掉，跨轮次与重新打开的会话持续存在（`packages\todo\tool-todo\README.zh.md` 第 12 行）。它的状态也是日志承载的（`todo/write` 快照，回放后写覆盖先写，第 72 行），但投影刻意在**下一轮次开始**就清成 `null`（§7.4 的第 ② 行）——因为它是"当前这一步"的可见清单，**不是完成契约**。它还有两个硬边界：**整表替换是唯一操作**（没有逐项编辑、没有回读工具，第 157 行），以及**单一所有者**（subagent 与非 agent 调用方都写不进这张表，§7.4 第 ⑤ 行）。

**两者的分工在 base bundle 里被显式写死**：plan-mode 的 `section` 里有一句 *"Do not use `todo_write` to track this planning phase: it tracks implementation after an approved plan, while the plan itself belongs in `exit_plan_mode`."*（§8 的 base 配置块；`packages\bundle\base\cordis.patch.yml` 第 330 行）。这就是本问题最直接的官方答案：**计划属于计划模式，待办属于计划批准之后的实施阶段**。

**那目标（goal）和它们的关系呢**：目标是**跨会话持久**的完成标准，允许无人值守地连续跑 Round；计划是**一次性**的、要人批准的执行前契约；待办是**单个轮次范围内**的可见清单。**三者正交，可以同时存在**——同一条 base 配置同时挂载（§8）。
