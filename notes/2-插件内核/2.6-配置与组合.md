## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：回答"插件的配置"这一件事的四问——**在哪声明、谁校验、怎么读、怎么改**，以及 `config` 与 patch 的关系。
**不是**：patch 文件的完整语法与层的组合顺序（那是 `1.2`、`1.4`）；热重载的全部门槛（那是 `2.7`，本课只讲 `config` 这一条路径）。

### 0.2 现在只要记住这 3 件事

1. **插件用导出的 `Config` 声明 schema，用 `apply(ctx, config)` 的第二个参数读配置。** `Config` 同时是 TypeScript 类型和运行时校验器。
2. **校验发生在 `apply` 之前**：失败 ⇒ 该条目的 fiber 进入 `FAILED`，`apply` **一行都不会执行**；成功 ⇒ `apply` 永远收到"补全 + 校验过"的完整配置。
3. **patch 对 `config` 是整块替换**（`target[key] = value`，浅赋值），**没有深合并**；想多一个键，就得把整份 `config` 重述一遍。

### 0.3 明确授权：这些现在不用管

- **Standard Schema 的规范细节**（`~standard` 里还有什么字段）——只需知道"它是一个被 Cordis 认可的校验器接口"；
- **`group` 条目的全部语义**（`isolate`、子条目递归、realm 归属）——本课只讲"它的 `config` 是子条目列表，不走插件级 schema 校验"，其余在 `2.5`；
- **`volatile` 与 HMR 的完整边界**——本课只讲"仅 volatile 变化不进重挂流程"，其余在 `2.7`；
- **`!!js` 的求值时机**——只看 §3.2.4 的三行结论即可，求值细节在 `2.7`。

### 0.4 本课依赖前面已定义的词

`profile` / `bundle` / `patch` / 条目 `entry` / 层 `layer` 由 `1.1` 定义；`override` / `insert` / 浅赋值（整键替换）由 `1.2` 定义。本课不重复，只在其上加"配置"这一层。

## 1. 最小词汇表（本课新增的 5 个词）

| 词 | 大白话 | 在源码/输出里的样子 |
|---|---|---|
| **Config 声明** | 插件写在模块里的**配置说明书**。一份是给 TypeScript 看的类型，一份是同名的运行时校验器 | `export interface Config {...}` + `export const Config = Schema.object({...})` |
| **validator 校验器** | 那个"运行时校验器"本身。Cordis 只认 **Standard Schema** 这一个接口，本仓库统一用 Schemastery 造 | 插件导出上的 `Config` 字段；`Config['~standard']` |
| **sealed config 密封配置** | 校验通过后交给插件的那份配置。默认值已补齐、类型已归一，插件拿到的它**不会再被校验** | `fiber.config` |
| **default 补全** | "这个键没写" ⇒ 用 schema 里声明的默认值填上 | `Schema.string().default('Hello')` |
| **tree carrier 树载体** | 一种**特殊条目**，它的 `config` 装的不是"给自己的字段"，而是**别的条目**。`cordis:group` 与 `cordis:include` 都是 | `Group` / `Include`；标记是 `static readonly [EntryGroup.key] = true` |

## 2. 先建立画面

### 2.1 三段接力（静态结构：谁把 config 交给谁）

```
YAML 一行
  - id: <条目 id>
    name: <包名>
    config:            ← ① 你写的原始值（可能是对象、数组，也可能含 !!js 表达式）
        │
        ▼  Loader（vendor/cordis-plugin-loader）
    插值 !!js  ──►  校验 + 补全（vendor/cordis ↔ vendor/schemastery）
        │                │
        │                └─ 失败 ⇒ fiber 状态 = FAILED，apply 不执行（本条链到此为止）
        ▼
    fiber.config        ← ② 密封配置（sealed config）
        │
        ▼
    apply(ctx, config)  ← ③ 插件读它。volatile 字段要再 .get()
```

### 2.2 谁在哪一段负责（从属关系）

```
vendor/cordis/src/fiber.ts        决定"什么时候校验、失败算哪种状态"
   └─ resolveConfig()             唯一的校验调用点：runtime.Config['~standard'].validate(config)
        └─ runtime.Config         从哪来？registry.ts 抄自插件导出的 Config

vendor/schemastery/src/index.ts   提供校验器本体：~standard / 默认值 / volatile
   └─ Schema.resolve()            校验与补全的实际执行者

vendor/cordis-plugin-loader/      决定"config 从哪来、要不要插值、改完怎么回写"
   ├─ internal/config 钩子        插值 !!js；tree carrier 直接跳过
   ├─ Entry.update()              比对变化；仅 volatile 变化走另一条路
   └─ internal/update 钩子        用 Config['simplify'] 归一后写回文件
```

> 精确性说明：`vendor/cordis-plugin-loader` 在仓库里是 `vendor/loader/`，包名与目录名不同——引用时以**目录名**为准（源码块里写的都是 `vendor/loader/...`）。

### 2.3 白话版：写下一行 `config` 之后，机器里发生了什么

（来源：`docs/cordis-tutorial/05-config.zh.md` 第 5–68 行 与 `docs/cordis-primer.zh.md` 第 41–45 行；这里只做白话转述，源码核对在 §3。）

1. 你在 YAML 一行的 `config:` 下面写了一些值。
2. 启动时 Loader 按顺序读那一行，先把 `!!js` 表达式算成真的值（只算 `config` 和 `disabled` 这两处）。
3. Loader 去 `import` 这个包，把导出的形态归一（`apply` 函数 / `{ apply }` 对象 / class）。
4. 归一后的东西上如果挂了 `Config`，就把它当成校验器；没挂就什么都不校验。
5. 用校验器跑一遍你写的值：该报错的报错，该补默认值的补默认值。
6. 报错的话，这一行对应的 fiber 就停在 `FAILED`，插件代码一次都不跑；不报错就把补全后的结果存成"这一行的配置"。
7. 然后才调用插件：把上下文和这份配置一起交给它。
8. 插件里想读配置，就直接读第二个参数；标记成 `volatile` 的字段要用 `.get()` 读。
9. 之后你改了配置文件：只有 `volatile` 字段变了，就把新值提交进正在运行的引用、通知一次，插件不重挂；其它字段变了才走"重挂"这条路。
10. 改完还要写回文件时，先按 schema 把"等于默认值的部分"剥掉，文件才不会被默认值填满。

## 3. 机制（源码对照）

### 3.1 声明：`Config` 是"同名接口 + 同名运行时 schema"

Schemastery 教程给的模板是 `docs/cordis-tutorial/05-config.zh.md` 第 17–25 行；仓库里真实插件用的是同一个形状，接口与 schema **相邻**写在一起，正好可以逐行对照：

`packages/client/ui-theme/src/index.ts 第 21–44 行`

```ts
/** Runtime preferences projected to the browser. */
export interface Config {          // ← 类型空间：消费方（apply 的签名）拿到它
  /** Browser palette preference. */
  preference: Volatile<ThemePreference>
  /** Browser font size in pixels. */
  fontSize: Volatile<number>
}

/** Live theme and typography preferences. */
export const Config = z.object({   // ← 值空间：Cordis 拿到它当校验器
  preference: z.union([...THEME_PREFERENCES]).default(DEFAULT_PREFERENCE).volatile(),
  fontSize: z.number().step(1).min(FONT_SIZE_MIN).max(FONT_SIZE_MAX).default(DEFAULT_FONT_SIZE).volatile(),
})

/** Supply the current palette before browser plugins start.
 * @param ctx Host plugin context.
 * @param config Validated live theme preferences.
 */
export function apply(ctx: Context, config: Config): void {
  ctx.inject(['settings'], (child) => { child.effect(() => child.settings.configure({ auto: false }, ctx.fiber)) })
  ctx.on('webserver/index-inject', (table) => {
    table.push(...bootThemeInjections(config.preference.get(), config.fontSize.get()))
  }, { prepend: true })
}
```

按块讲解：

- **接口与常量同名不冲突**：一个在类型空间、一个在值空间。所以 `apply(ctx, config: Config)` 里的 `Config` 是接口，而运行时 Cordis 看到的是那个 `const`。这是"一份声明、两个消费者"的全部秘密。
- **`apply` 的第二个参数就是读取点**：`config.preference.get()` 说明这个字段声明了 `.volatile()`，拿到的是**稳定引用**而不是快照（§3.5 会看到它为什么不重挂就能更新）。
- **`config: Config` 而不是 `config = {}`**：本仓库两种写法都有。可省略的配置配合 `Schema.object({...})` 的"可选字段"语义，才写成 `apply(ctx: Context, config: Config = {}): void`——见 §3.2.1 的真实插件。
- **类插件形态不同、语义相同**：写成 class 的插件把 schema 放在静态字段上。实例 `packages/client/product-analytics/src/index.ts 第 28–30 行`：`export default class ProductAnalytics extends TypertRemoteService` + `static Config = z.object({ enabled: z.boolean().default(true).volatile(), appVersion: z.string() })`（对应的 `export interface Config` 在同文件第 13–19 行）。Cordis 读的是同一个字段名。

**这份声明怎么进到运行时记录里** —— `vendor/cordis/src/registry.ts 第 316–336 行`（`plugin()` 的入口与 runtime 建记录那一段）：

```ts
  plugin(plugin: Plugin, config?: any, getOuterStack = buildOuterStack()) {
    // check if it's a valid plugin
    const callback = this.resolve(plugin)                    // ① 形态归一：函数 / class / { apply }
    if (!callback) throw new Error('invalid plugin, expect function or object with an "apply" method, received ' + typeof plugin)
    this.ctx.fiber.assertActive()

    let runtime = this._internal.get(callback)                // ② 同一个 callback 复用同一条记录
    if (!runtime) {
      let name = plugin.name
      if (name === 'apply') name = undefined
      runtime = { name, callback, fibers: new DisposableList(), Config: plugin.Config }   // ③ 就在这里抄走 Config
      this._internal.set(callback, runtime)
    }

    const fiber = new Fiber(this.ctx, config, Inject.resolve(plugin.inject), runtime, getOuterStack)
    const wrapped = Object.create(fiber) as Fiber & PromiseLike<Fiber>
    wrapped.then = (onFulfilled, onRejected) => {
      return fiber.await().then(onFulfilled, onRejected)
    }
    return wrapped
  }
}
// （第 304–315 行的完整 JSDoc（4 个 @param、@returns）与本知识点无关，此处省略；
//   第 330 行之后的 wrapped 包装只是让 fiber 可 await，与本知识点无关，但它连着函数收尾所以保留）
```

按块讲解：

- **③ 一行就是"契约落地"的地方**：`Config: plugin.Config` —— 插件模块上导出的那个校验器，被抄进 `runtime` 记录；**没有第三方注册步骤**，也没要求插件额外调用什么 API。
- **② 按 `callback` 复用 runtime**：所以同一个插件被挂两次也共用一份 schema；`fibers` 是"这个插件的所有实例"的列表。
- **契约的类型面写死在** `registry.ts` 第 103–104 行（`Plugin.Base.Config`，JSDoc 原文 *"Standard-schema validator applied to config before the plugin starts."*）与第 143–144 行（`Plugin.Runtime.Config`）——关键词是 **Standard-schema**，不是"Schemastery"。

### 3.2 校验：Standard Schema 接口 + Cordis 自己的 `ValidationError`

#### 3.2.1 唯一的校验调用点

`vendor/cordis/src/fiber.ts 第 16–62 行`

```ts
const kValidationError = Symbol.for('ValidationError')

/** Error raised when plugin configuration fails standard-schema validation. */
export class ValidationError extends TypeError {
  name = 'ValidationError'

  /**
   * Build the aggregated message from schema issues.
   *
   * @param issues — the standard-schema issues, one message line each.
   */
  constructor(issues: readonly StandardSchemaV1.Issue[]) {
    super(`invalid config:\n` + issues.map(issue => {
      if (issue.path) {
        return `  - ${issue.message} (at ${issue.path.join('.')})`
      } else {
        return `  - ${issue.message}`
      }
    }).join('\n'))
  }
}
// …（第 38–41 行：把 kValidationError 这个 symbol 挂到 prototype 上，供跨包 instanceof 判定；
//      与本知识点无关，此处省略）

/**
 * Validate and normalize config for a plugin runtime before it starts.
 *
 * @param runtime — the plugin runtime whose `Config` schema to apply.
 * @param config — the raw user config.
 * @returns the validated config, or `config` unchanged if the runtime has no schema.
 * @throws {ValidationError} when validation reports issues.
 */
export function resolveConfig(runtime: Plugin.Runtime, config: any) {
  if (!runtime.Config) return config                                   // ① 没声明 schema：原样透传
  // TODO: async validation
  const result = runtime.Config['~standard'].validate(config)          // ② 唯一的校验调用
  if ('then' in result) {
    throw new TypeError('Async config validation is not supported')    // ③ 拒绝异步校验
  }
  if (result.issues) {
    throw new ValidationError(result.issues)                           // ④ 有 issues ⇒ 抛
  } else {
    return result.value                                                // ⑤ 否则返回校验后的值
  }
}
```

按块讲解：

- **① 是"不声明就不校验"的落点**：返回的是**同一个对象**（没有拷贝）。
- **② 只认 `~standard`**：Cordis 完全不知道 Schemastery 的存在，`plugin.Config` 上只要有这个属性就行（第 7 行 `import type { StandardSchemaV1 } from '@standard-schema/spec'`）。
- **③ 同文件第 52 行留下 `// TODO: async validation`**：异步校验器当前直接拒绝，不是"忽略"。
- **④ 的错误文案格式就在这个构造函数里**：`invalid config:` + 每条 issue 一行；有 `path` 时追加 ` (at a.b)`。所以你在终端看到的那三行，是**这里**拼出来的，不是校验库打印的。
- **⑤ `result.value` 才是 `apply` 最终收到的值**：默认值是**校验库在 `validate` 内部补的**，不是 Cordis 补的（§3.2.4）。

#### 3.2.2 校验调用点被插在哪一步（失败为什么等于 `FAILED`）

`vendor/cordis/src/fiber.ts 第 641–673 行`

```ts
  private _resolveConfig(config: any) {
    config = this.context.waterfall(this, 'internal/config', config, () => config)   // ① 先走插值钩子
    return this.runtime ? resolveConfig(this.runtime, config) : config
  }

  private async _reload() {
    this.store = { ...this._store }
    const oldEpoch = this._runner.epoch
    try {
      await Promise.resolve()
      // A disposer queued before this checkpoint may already have invalidated
      // the load. Do not run plugin code for a stale epoch; the state update
      // below will drain any effects collected while the fiber was PENDING.
      if (this._runner.epoch === oldEpoch) {
        this.config = this._resolveConfig(this._config)     // ② 校验在这里发生
        await this._execute(this._runner)                  // ③ 校验通过才执行插件
        this._error = undefined
      }
    } catch (reason) {
      // impl guarantees that the error is non-null (?)
      this.ctx.logger.error(reason)
      this._error = reason                                 // ④ 失败：记进 _error
      this._runner.epoch = INACTIVE
    }
    // …（第 665–672 行：收尾时更新状态；epoch 未变则收 inertia，否则转入 UNLOADING）
  }
```

再把"状态"那两行接上 —— `vendor/cordis/src/fiber.ts 第 574–579 行` 与 `第 704–710 行`：

```ts
  private _getState() {
    if (this.uid === null) return FiberState.DISPOSED
    if (this._error) return FiberState.FAILED        // ⑤ _error 有值 ⇒ FAILED
    if (this._runner.epoch !== INACTIVE) return FiberState.ACTIVE
    return FiberState.PENDING
  }

  /**
   * Wait for current lifecycle work and rethrow startup errors.
   *
   * @returns this fiber, once it has settled into a stable state.
   * @throws the config-validation or plugin-startup error, if any.
   */
  async await() {
    while (this.inertia) {
      await this.inertia
    }
    if (this._error) throw this._error               // ⑥ 谁 await 这个 fiber，谁就拿到这个错
    return this
  }
```

按块讲解：

- **① `internal/config` 瀑布先跑**：Loader 就挂在这个钩子上做 `!!js` 插值（§3.4.1）。**顺序是"插值 → 校验"**，不是反过来。
- **②③ 的顺序就是本课的结论 2**：`this.config = 校验结果` 与 `await this._execute(...)` 是相邻两行，校验抛错就到不了下一行——`apply` 一字不执行。
- **④⑤ "失败 ⇒ FAILED" 是状态机层面的必然**：`catch` 把原因存进 `_error`，而 `_getState()` 第一件正事就是看 `_error`。
- **⑥ 进程层的出口**：`await()` 会把 `_error` 重抛；启动器据此报非零退出（`apps/cli/reference/README.md` 第 9 行原文：*"A parse, schema, resolution, or plugin boot failure is reported and exits nonzero"*）。

#### 3.2.3 校验器那一侧：Schemastery 是怎么被 Cordis 用上的

`vendor/schemastery/src/index.ts 第 290–309 行`

```ts
Object.defineProperty(Schema.prototype, '~standard', {
  get(this: Schema) {
    return {
      version: 1,
      vendor: 'schemastery',                                     // ① 自报家门
      validate: (value: unknown) => {
        try {
          return { value: Schema.resolve(value, this, {})[0] }   // ② 成功：value 就是补全后的配置
        } catch (error) {
          if (ValidationError.is(error)) {
            return { issues: [{ message: error.message, path: error.options.path }] }   // ③ 转成 standard 形状
          }
          throw error                                            // ④ 非校验错误：原样重抛
        }
      },
    }
  },
})

Schema.ValidationError = ValidationError
```

按块讲解：

- **① `vendor: 'schemastery'`**：这是运行时唯一能直接看出"校验器是哪家"的地方（探针里 `has ~standard = object | vendor = schemastery` 指的就是它）。
- **② 一句 `Schema.resolve` 同时干了两件事**：校验 + 补默认值。`[0]` 取的是"值"，第二个元素是"是否需要回写输入"的标记。
- **③ issue 的形状被压成 `{ message, path }`**：Cordis 的 `ValidationError` 只吃这两样（§3.2.1 ④）。
- **④ 区分"校验失败"与"校验器自己崩了"**：只有 `ValidationError` 被翻译成 issues，其它异常照旧抛出。
- **注意它不是 `Object.defineProperty` 在 `Config` 上，而是在 `Schema.prototype` 上**：所以任何用 Schemastery 造的 schema 都自带这个属性，插件作者不用管。

#### 3.2.4 默认值补全：`apply` 永远收到"完整"配置

`vendor/schemastery/src/index.ts 第 515–543 行`

```ts
Schema.resolve = function resolve(data, schema, options = {}, strict = false) {
  if (!schema) return [data]
  if (!(options as Schemastery.Options & { [checkedVolatile]?: boolean })[checkedVolatile]) {
    validateVolatileSchema(schema, options.path)          // ① 构建期位置约束（§3.5.2）
    options = { ...options, [checkedVolatile]: true } as Schemastery.Options
  }
  if (schema.meta?.volatile) {
    const inner = Schema(schema)
    inner.meta = { ...schema.meta, volatile: false }
    const [value, adapted] = Schema.resolve(data, inner, options, strict)
    try {
      return [createVolatile(value), adapted]             // ② volatile 字段包成稳定引用
    } catch (error) {
      throw new ValidationError(error instanceof Error ? error.message : String(error), options)
    }
```

### 3.4 传入路径：从 YAML 行到 `fiber.config`

#### 3.4.1 `config` 从哪来、什么时候插值

`vendor/loader/src/index.ts 第 104–121 行`

```ts
    ctx.on('internal/config', function (this: Fiber, _config, next) {      // ← 注册钩子：ctx.on(...) 这一段
      const config = next()                                               // ① 先让别人的钩子跑
      if (!this.entry || this.parent.fiber?.entry === this.entry) return config
```

按块讲解：

- **钩子类型是 `internal/config`**：它挂在 `listener` 的**全局**作用域（`{ global: true }`），所以每个条目解析配置时都会经过它。
- **① `next()` 先把链上别人的结果拿回来，Loader 的插值作用在它上面**：这个钩子用默认优先级注册（`{ global: true }`，没有 `prepend`），所以链上更靠前的监听器可以先动手；Loader 的插值发生在**它们的输出之上**。
- **② `plugin?.[EntryGroup.key]` 就是"是不是树载体"的判据**：`Group` 与 `Include` 都声明了 `static readonly [EntryGroup.key] = true`（§3.7 引用）。**跳过插值的理由写在上面三行注释里**：树载体的 `config` 装的是**别的行**，那些行的 `!!js` 属于各自 fiber，必须延迟到各自激活时才求值。
- **③ `interpolate` 是递归的**：见下一块。
- **⑤ 回写发生在 `internal/update` 里，用的是 `Config['simplify']`**：这就是"文件里不会堆满等于默认值的键"的原因（§3.6）。

#### 3.4.2 `!!js` 的求值实现（很短，但值得看一眼）

`vendor/loader/src/config/utils.ts 第 3–27 行`

```ts
// eslint-disable-next-line no-new-func
/** Evaluate a JavaScript expression against a loader context scope. */
export const evaluate = new Function('ctx', 'expr', `
  with (ctx) {
    return eval(expr)
  }
`) as ((ctx: object, expr: string) => any)                  // ① with + eval

/** Recursively replace YAML `!!js` expression nodes with evaluated values. */
export function interpolate(ctx: object, value: any) {
  if (isJsExpr(value)) {
    return evaluate(ctx, value.__jsExpr)                   // ② 命中表达式节点就求值
  } else if (!value || typeof value !== 'object') {
    return value                                           // ③ 标量原样返回
  } else if (Array.isArray(value)) {
    return value.map(item => interpolate(ctx, item))        // ④ 数组逐项递归
  } else {
    return valueMap(value, item => interpolate(ctx, item))  // ⑤ 对象逐键递归
  }
}

/** Return true when a value is a serialized loader JavaScript expression. */
export function isJsExpr(value: any): value is JsExpr {
  return value instanceof Object && '__jsExpr' in value     // ⑥ 判据：是不是 { __jsExpr: '...' }
}
```

按块讲解：

- **⑥ 判据是"有没有 `__jsExpr` 字段"**：这个节点由 YAML 的 `!!js` 标签在解析时造出来（`vendor/include/src/index.ts` 第 9–23 行：`construct: (data) => ({ __jsExpr: data })`，`predicate: isJsExpr`）。
- **① 求值作用域是 `with (ctx)`**：所以 `!!js` 里能直接写 `process.env.X`（全局）、也能写 `ctx.get('profileContext')?.name`（loader 上下文里的服务）。这解释了为什么 `!!js` 能"读环境"也能"读服务"。
- **④⑤ 递归到每一层**：数组和对象里的 `!!js` 都会被打到；这就是"整块 `config` 里任意位置都能写表达式"的实现。
- **副作用**：`evaluate` 用 `new Function` + `eval`，所以**表达式是命令式的、可以有任何副作用**，它没有沙箱。`docs/cordis-primer.zh.md` 第 45 行把边界写清楚了：`!!js` 只在**条目 `config`** 与**条目 `disabled`** 两处有效，其余元数据（`name` / `id` / `inject`）保持字面值。

#### 3.4.3 四步串起来

1. 行的 `config` 由 `EntryOptions.config?: any` 承载（`vendor/loader/src/config/entry.ts` 第 10–23 行；同文件第 15 行注释就是 *"Config passed to the plugin."*）。

#### 3.5.2 合法位置由 schema 构建期强校验

`vendor/schemastery/src/index.ts 第 488–509 行`

```ts
function validateVolatileSchema(schema: Schema, path: (keyof any)[] = [], blocked = false, seen = new Map<Schema, Set<boolean>>()) {
  const states = seen.get(schema) ?? new Set<boolean>()
  if (states.has(blocked)) return
  states.add(blocked)
  seen.set(schema, states)
  if (schema.meta?.volatile && blocked) {
    throw new ValidationError('volatile fields require a fixed object path without an enclosing volatile field', { path })   // ①
  }
  const nested = blocked || !!schema.meta?.volatile
  if (schema.dict) {
    for (const [key, child] of Object.entries(schema.dict)) validateVolatileSchema(child, [...path, key], nested, seen)
  }
  if (schema.sKey) validateVolatileSchema(schema.sKey, [...path, '<key>'], true, seen)   // ② 字典的键位置
  if (schema.inner && (schema.type !== 'lazy' || schema.inner[kSchema])) {
    validateVolatileSchema(schema.inner, [...path, '*'], true, seen)                    // ③ 数组元素位置
  }
  if (schema.list) {
    for (let index = 0; index < schema.list.length; index++) {
      validateVolatileSchema(schema.list[index]!, [...path, String(index)], true, seen)  // ④ union/tuple 分支
    }
  }
}
```

按块讲解：

- **① 一句话就是全部规则**：`volatile` 必须落在**固定对象路径**上，且外面不能再套一层 `volatile`。违反它是**造 schema 的时候就抛错**，不是运行时。
- **②③④ 为什么这些位置一律 `blocked = true`**：字典的键、数组的元素、union 的分支都**不是固定路径**——"第几个元素"会变，稳定引用就没意义了。
- **`seen` 那张表**：同一份 schema 会被多次引用（`refs`），表用来避免重复校验与无限递归。
- **这条校验在 `Schema.resolve` 的入口被调用一次**（前一节 ①，由 `checkedVolatile` 标记保证只跑一次）。

- **① `deepEqual(..., key === 'config')`**：比对 `config` 时用"忽略 volatile 字段"的相等语义，其它键用普通深比较。
- **② 五个条件缺一不可**：只有一个键变了、且那个键是 `config`、且 fiber 是 `ACTIVE`、且上下文原型没换（说明没有跨作用域搬家）、且忽略 volatile 后旧新配置相等。**任何一条不成立都退回普通重挂流程**——这是"volatile 是一条窄路"的源码证据。
- **③ `_commitVolatile()` 返回 `false` 时 `pending` 仍是 `changes`**：也就是"候选值里的普通字段其实也变了"，此时不走近路（§3.5.4）。
- **④ `_patchContext(pending)`**：普通变化走这里；`fiber.update(...)` 与 `loader/patch-context` 瀑布在其中（`entry.ts` 第 101–109 行）。
- **顺带一个特例**：`group` 条目的判定被放宽成 `diff.includes('config') || this.options.group`（同文件第 105 行）——组任何变化都走 `fiber.update`，不先比对 `config` 是否真的变了。

#### 3.5.4 提交：值怎么进到正在运行的引用里

`vendor/loader/src/config/entry.ts 第 159–197 行`

```ts
  /**
   * Parse a volatile-only raw config change and commit its values into the running fiber's references.
   * An invalid candidate is logged and leaves the running references unchanged; the raw config stays retained for the next activation.
   * @returns `false` when an ordinary effective value changed, so the caller applies the ordinary update lifecycle.
   */
  private _commitVolatile(): boolean {
    const fiber = this.fiber!
    const refs = volatileEntries(fiber.config)                  // ① 从当前 config 里找出所有 volatile 引用
    if (!refs.length) return true
    const raw = this.options.config
    let candidate: unknown
    try {
      candidate = resolveConfig(fiber.runtime!, fiber.ctx.waterfall(fiber, 'internal/config', raw, () => raw))   // ② 重新插值 + 校验
    } catch (error) {
      this.ctx.logger.warn('volatile config update failed for %C', this.options.id)
      this.ctx.logger.warn(error)
      return true                                              // ③ 候选非法：只记日志，运行中的引用不动
    }
    if (!deepEqual(fiber.config, candidate, true)) {
      this.ctx.logger.debug('ordinary config values of %C changed with its volatile values; applying the ordinary update', this.options.id)
      return false                                             // ④ 普通字段也变了：交回调用方走重挂
    }
    const paths = refs.flatMap(({ path, ref }) => {
      const source = path.reduce<unknown>((value, key) => Reflect.get(value as object, key), candidate) as Volatile<unknown>
      if (deepEqual(ref.get(), source.get(), true)) return []   // ⑤ 值没变：不通知
      updateVolatile(ref, source)                              // ⑥ 把新值提交进运行中的引用
      return [path]
    })
    if (!paths.length) return true
    const self: Context = Object.create(fiber.ctx)
    self[Context.filter] = (owner: Context) => owner.fiber === fiber
    try {
      fiber.ctx.emit(self, 'loader/volatile-update', paths)     // ⑦ 通知：参数是变化路径
    } catch (error) {
      // A listener failure must not fail the entry update; every value is already committed.
      this.ctx.logger.warn(error)
    }
    return true
  }
```

按块讲解：

- **① 引用是从"当前 `fiber.config`"里找的**：这说明 volatile 引用只存在于**运行中的那份配置**里；原始值仍然是普通数据。
- **② 重新走了一遍 `internal/config` + `resolveConfig`**：所以 volatile 的新值同样要**插值 + 校验**，不是直接塞进去。
- **③ "非法候选不生效"**：只 warn，运行中的引用保持原样，原始配置留着等下次激活——**不抛错、不重挂**。这与 `fiber.update()` 抛 `ValidationError` 形成对照（§3.5.5）。
- **⑤ 等值不通知**（教程 05 第 93 行："等值更新不通知"）。
- **⑦ 通知`emit` 带 `Context.filter`**：只投递给"属于这个 fiber 的 ctx"，所以别的插件的同名监听器不会收到。

#### 3.5.5 与 `fiber.update()`（普通变更）的对照

`vendor/cordis/src/fiber.ts 第 725–753 行`

```ts
  /**
   * Validate and apply new config, then restart the plugin.
   *
   * Runs the `internal/update` waterfall first, so update hooks (and HMR)
   * can veto or replace the restart.
   *
   * @param config — the new raw config; validated before anything restarts.
   * @param noSave — hint for persistence hooks not to write the change back.
   * @returns nothing; the restart runs behind the `internal/update` waterfall.
   * @throws {ValidationError} when the new config fails validation.
   */
  update(config: any, noSave = false) {
    this.assertActive()
    this._config = config
    if (this.state !== FiberState.ACTIVE) {
      // Config resolution may access injected services, so defer it until the
      // fiber can activate.
      this._error = undefined
      this._setEpoch(INACTIVE)
      this._refresh()
      return                                    // ① 非 ACTIVE：先记下来，等激活时再校验
    }
    config = this._resolveConfig(config)        // ② 校验在这里，失败直接抛出
    this.context.waterfall(this, 'internal/update', config, noSave, () => {
      this.config = config
      this._error = undefined
      return this.restart()                     // ③ 校验通过才重启插件
    })
  }
```

按块讲解：

- **② 与 §3.5.4 ③ 正好相反**：这里校验失败是**抛出去**，调用方（HMR、settings、`Entry._patchContext`）决定怎么处理；而 volatile 候选值非法是**吞掉 + 记日志**。
- **① 非 ACTIVE 时故意不校验**：注释写明理由——"解析配置可能访问注入的服务"，所以推迟到能激活的时候。
- **③ `restart()` 意味着卸载再挂载**：`volatile` 这条近路绕开的就是它。
- **JSDoc 里 `@throws {ValidationError}` 是契约的一部分**：想知道"改配置失败会不会炸"，看这一行比看实现快。
- **`@param noSave`**：Loader 调 `fiber.update(this.options.config, true)`（`vendor/loader/src/config/entry.ts` 第 106 行）时传 `true`，于是 §3.6 的写回钩子不做事——**避免"读文件触发的更新"再写回文件**。

### 3.6 写回：按 schema 归一后再落盘

`vendor/loader/src/index.ts 第 115–121 行` 已在 §3.4.1 给出（④⑤ 那两行）。补充它的语义来源：

- `simplify()` 的定义（`vendor/schemastery/README.md` 第 255–267 行）：*"Normalize a value by removing parts that are equal to schema defaults."* 教程里的例子是 `Config.simplify({ foo: '', bar: 1 }) // { bar: 1 }`——`foo` 等于默认值 `''`，于是被剥掉。

```ts
export function isNativeConfigSchema(value: unknown): value is NativeConfigSchema {
  if (value === null || (typeof value !== 'object' && typeof value !== 'function')) return false
  const meta: unknown = Reflect.get(value, 'meta')
  return Reflect.get(value, Symbol.for('schemastery')) === true      // ① 品牌位
    && typeof Reflect.get(value, 'type') === 'string'                // ② 有 type
    && meta !== null && typeof meta === 'object'                     // ③ meta 是对象
}
```

### 3.7 `group` 的 `config` 是"子条目列表"，不是"字段表"

`vendor/loader/src/config/group.ts 第 74–90 行`

真实 YAML 形态（`packages/bundle/web-app/presets/minimal.patch.yml` 第 17–26 行，节选）：

- **② `config: EntryOptions[]`**：这是"类型与归属不同"的源码证据——普通条目的 `config` 交给**插件 schema**；组的 `config` 交给 **`EntryGroup.update()`**，后者按 `id` 差分增删子条目（`vendor/loader/src/config/group.ts` 第 48–65 行：`this.data = config` 之后按 `oldMap` / `newMap` 逐 id `create` / `remove`）。
- **① `[EntryGroup.key]` 标记和 §3.4.1 ② 是同一件事**：`Include` 也声明了同一个标记（`vendor/include/src/index.ts` 第 162–167 行，附带三行作者注释解释"嵌套行的 `!!js` 属于各自 fiber"）。
- **组不走插件级 schema 校验**：`Group` 没有声明 `Config`，于是 §3.2.1 ① 的透传分支生效；组的内容靠**子条目各自的 schema**把关。这不是"漏了校验"，而是"校验发生在下一层"。**（标注为推断的部分：仓库没有一句文档把这句话写成结论，但它由"`Group` 类上没有 `Config` 字段"与 §3.2.1 ① 两处事实直接推得。）**
- **组永远启用**：`Entry.disabled` 的第一行注释就是 `// group is always enabled` + `if (this.options.group) return false`（`vendor/loader/src/config/entry.ts` 第 76–78 行）。`--dump-config-schema` 的校验器也照着这个特例放行（`packages/boot/app-boot/src/config-schema/document.ts` 第 113、115–117 行）。
- **patch 能直接改组里的子条目**：索引会递归进组（`vendor/include/src/index.ts` 第 66–73 行：`if (entry.group && Array.isArray(entry.config)) buildMap(entry.config)`）。

**一个必须澄清的边界**：`group` 的行级 `config` 是**数组**，而 patch 的浅赋值对数组同样是**整体替换**——一条 `- id: <组> / config: [...]` 会覆盖**整串子条目**（不是"追加一项"）。想往组里加一行，必须用 `insert` 且带 `id`（`vendor/include/src/index.ts` 第 79–91 行，`1.2` §4.3 有对照表）。**（标注为推断：由浅赋值语义 + 插入分支两处源码推得，我没有实跑一条"用覆盖往组里加子条目"的 patch。）**

### 3.8 一句话把 §3 串起来

**`Config` 在插件模块里声明 → 被 `registry.ts` 抄进 runtime → `fiber._reload()` 里先插值再调 `~standard.validate` → 失败进 `FAILED` 不执行、成功把补全后的值给 `apply` → patch 只按 `id` 整块替换行里的 `config` → 改完回写时按 `simplify()` 剥掉默认值；`volatile` 字段与 `group` 的数组配置各有一条绕过"重挂"的近路。**

### Q4 `config` 与 patch 的关系？为什么 patch 会整体替换 `config` 而不是深合并？

→ **关系**：`config` 是条目（`EntryOptions.config`，`vendor/loader/src/config/entry.ts` 第 15–16 行）的一个字段；patch 用 `id` 定位条目，然后逐 key 浅赋值，`config` 只是被赋值的键之一，因此**整块被替换**（`vendor/include/src/index.ts` 第 120–123 行）。
**这就是"整体替换"的机制性原因**：实现是 `target[key] = value`，**没有任何递归合并分支，也没有为 `config` 开特例**（§3.3 ⑤）。
**为什么这样设计**（读得到的三条自洽理由，均引自仓库文档）：
1. **可预测 + 责任明确**：patch 的 `config` 就是该行的完整配置，读一个文件就能知道这行最终是什么，不存在"base 里还有个键你没看见"。`docs/user/develop/basic/publish.md` 第 129–132 行把它写成 bundle 作者的两条义务：*"must restate every key the row needs, not just the changed one"*。同一语义在 `apps/cli/reference/README.md` 第 9 行、`packages/bundle/base/README.md` 第 84、131 行、`packages/bundle/web-app/README.md` 第 90 行各写了一遍。
2. **深合并会制造"看不见的默认值"**（标注为推断）：如果合并，删除一个 base 键就必须发明"删除语法"；而浅替换下"不写"等于"回到 schema 默认值"——默认值由插件 schema 独占声明，只有一处真相。
3. **一个真实的代价，仓库自己记着**：整体替换会把行里原有的 `!!js` 表达式一起丢掉。`apps/cli/reference/README.md` 第 28 行原文：*"This precedence requires the row to retain that expression; a user patch that replaces the whole `config` with literals removes the runtime read."* `packages/boot/cmdline/README.zh.md` 第 134 行中文同义。`dsh-web-app` 的 patch 正是因此**必须重述** `mode: !!js process.env.DSH_TOOLS_MODE`（`packages/bundle/web-app/cordis.patch.yml` 第 32–38 行，同文件第 5–6 行注释写明 *"A patch replaces the targeted row's whole `config`, so each row below restates every key it owns."*）。

### Q5 `group` 条目的 `config` 是数组，这与普通条目有什么不同？

→ 四点不同，全部有源码落点：
1. **类型与归属不同**：普通条目的 `config` 交给**插件 schema**；`group` 的 `config` 是**子条目列表**（`EntryOptions[]`）。`Group` 的构造函数签名就是 `constructor(public ctx: Context, public config: EntryOptions[])`（`vendor/loader/src/config/group.ts` 第 79 行），`[Service.init]` 里 `await this.update(this.config)` 逐个建条目（第 86–89 行）；`EntryGroup.update(config)` 先 `this.data = config` 再按 id 差分增删（第 48–65 行）。YAML 里它写成一个数组，真实形态见 `packages/bundle/web-app/presets/minimal.patch.yml` 第 17–26 行（`- id: persistent-shell` / `name: cordis:group` / `group: true` / `config:` 下挂子条目）。
2. **不做 `!!js` 插值、也不做插件级 schema 校验**：Loader 的 `internal/config` 钩子对 tree carrier 直接 `return config`（`vendor/loader/src/index.ts` 第 104–113 行，理由写在那三行注释里：嵌套的是**别的行**，那些行的 `!!js` 属于各自 fiber）；`Group` 没有声明 `Config`，因此 `fiber.ts` 第 51 行的透传分支生效——组的内容靠**子条目各自的 schema** 把关（后一句**标注为推断**）。
3. **禁用语义不同**：`Entry.disabled` 第一行就是 `// group is always enabled` + `if (this.options.group) return false`（`vendor/loader/src/config/entry.ts` 第 76–78 行）——带 `group: true` 的组自身永不被 `disabled` 关闭（`--dump-config-schema` 的 schema 也照此特例放行：`packages/boot/app-boot/src/config-schema/document.ts` 第 113、115–117 行）。
4. **更新路径不同**：patch 索引会递归进组（`vendor/include/src/index.ts` 第 66–73 行 `if (entry.group && Array.isArray(entry.config)) buildMap(entry.config)`），所以 patch 能直接改组里的子条目；反过来，**`config` 变化触发重挂**的判定对组放宽为 `diff.includes('config') || this.options.group`（`vendor/loader/src/config/entry.ts` 第 105 行），即组任何变化都走 `fiber.update`，而不是像普通条目那样先比对 `config` 是否真的变了。

### Q6 `apply` 拿到的 `config` 是"我写的那份"还是"补全后的那份"？

→ **补全后的那份**，而且是**校验过的**。两条证据：
- 代码：`resolveConfig` 成功时返回 `result.value`（`vendor/cordis/src/fiber.ts` 第 60 行），而 `result.value` 是 `Schema.resolve(value, this, {})[0]`（`vendor/schemastery/src/index.ts` 第 297 行）——默认值就是在 `Schema.resolve` 的第 533–543 行补上的。
- 文档：教程 05 第 51 行原文"未提供 `greeting`，因此 schema 默认值会将其补齐：**`apply` 始终会收到完整且经过验证的配置**"。
**推论（标注为推断）**：所以插件**不需要**在 `apply` 里写 `config.foo ?? 默认值`（真实代码里出现的 `config.compressionLevel ?? DEFAULT_...` 属于防御式写法，不是必需）。反过来说，**只有 `default` 声明的键才会被补齐**；既无 `default` 又非 `required` 的键在结果里可能不存在——这时 `config.foo` 就是 `undefined`。

### Q7 配置在什么时候被"求值"？`--dump-config` 为什么还能看到 `!!js`？

→ **求值（插值）发生在条目激活路径上**：fiber 解析配置时先走 `internal/config` 瀑布（`vendor/cordis/src/fiber.ts` 第 642 行），Loader 挂在这个钩子上调 `interpolate`（`vendor/loader/src/index.ts` 第 104–113 行），实现是 `with (ctx) { return eval(expr) }`（`vendor/loader/src/config/utils.ts` 第 5–9 行），对数组/对象递归（第 17–21 行）。**顺序是"插值 → 校验"**。
**`--dump-config` 不求值**：它的模块注释写明 *"without booting or evaluating `!!js`"*（`apps/cli/src/dump-config.ts` 第 1–6 行），`renderConfigDump` 的 JSDoc 也写明 *"`!!js` expressions print verbatim, unevaluated"*（`packages/boot/app-boot/src/index.ts` 第 406–407 行）。所以 dump 里的 `mode: !!js process.env.DSH_TOOLS_MODE` 是**文本**（§4.1 实测确认：39 处 `!!js` 全部保持字面量）。
**`!!js` 的合法位置只有两处**：条目的 `config` 与条目的 `disabled`（教程 05 第 107 行；`docs/cordis-primer.zh.md` 第 45 行）。其余元数据（`name` / `id` / `inject`）是普通真值数据——所以写 `- name: !!js ...` 得不到你期望的效果。

### Q8 `volatile` 到底解决什么问题？改一个字段会不会重挂插件？

→ **解决的问题**：让"插件在每次操作中读取的字段"能被改而**不必重挂**（教程 05 第 73 行）。
**会不会重挂**：**只在五个条件同时成立时不会**——只有 `config` 这一个键变了、fiber 是 `ACTIVE`、上下文原型没变、忽略 volatile 后旧新配置相等、且候选值校验通过（`vendor/loader/src/config/entry.ts` 第 143–151 行 + 第 164–180 行）。任何一条不成立都回归普通流程（重挂）。
**改完之后插件的引用会更新但插件不会重跑**：新值由 `updateVolatile(ref, source)` 提交进运行中的引用（第 184 行），然后 `emit('loader/volatile-update', paths)` 通知（第 191 行，参数是**变化路径的数组**）。**等值更新不通知**（第 183 行：`deepEqual` 相等就 `return []`）。
**读法上有两条限制**：必须用 `.get()`（`vendor/schemastery/src/index.ts` 第 526 行 `createVolatile`）；不要把值存下来留给后续操作，`volatile` 的引用只对"当前这次操作"有效（教程 05 第 91 行）。
**位置限制**：只能落在**固定对象路径**上，且外面不能再套 `volatile`——违反时造 schema 就抛 `volatile fields require a fixed object path without an enclosing volatile field`（`vendor/schemastery/src/index.ts` 第 493–495 行；数组元素、字典的键、union 分支都在被禁之列，第 497–508 行）。

### Q9 配置文件里的 `config` 会被写回吗？写回时长什么样？

→ **会**，路径是 `internal/update` 钩子：`this.entry.options.config = unparse ? unparse.call(this.runtime!.Config, config) : config` 然后 `this.entry.parent.tree.write()`（`vendor/loader/src/index.ts` 第 115–121 行）。`unparse` 就是 schema 上的 `simplify`。
**写回的形状**：等于默认值的部分被剥掉（`vendor/schemastery/README.md` 第 255–267 行的定义与例子 `Config.simplify({ foo: '', bar: 1 }) // { bar: 1 }`），`volatile` 引用被解包成普通值（同文件第 393 行）。
**一个反过来的守卫**：Loader 自己调用 `fiber.update(this.options.config, true)` 时传了 `noSave = true`（`vendor/loader/src/config/entry.ts` 第 106 行），于是写回钩子第一行的 `noSave` 判断命中、直接 `next()`——**避免"由读文件触发的更新"再写回文件**。
**字段顺序**：`sortKeys` 把 `config` 排在最后（同文件第 35–40 行 `append = ['config']`），所以你手写的 patch 被回写后会变成 `id` / `name` / 其它 / `config` 的顺序。

### Q10 用"覆盖"的方式能不能往 `group` 里加一个子条目？

→ **不能。** `group` 的 `config` 是数组，而 patch 的覆盖是浅赋值——`target['config'] = value` 会把**整串子条目替换掉**（`vendor/include/src/index.ts` 第 120–123 行）。往组里加一行**必须用 `insert` 且带该组的 `id`**：目标是 group 时走 `target.config.push(...insert)`（第 90–91 行），目标不存在或不是 group 时**警告并跳过**（第 82–89 行）。对照表见 `1.2` §4.3。
**（标注为推断）**：本笔记没有实跑"用覆盖往组里加子条目"的 patch 来观察整串被替换的现场；依据是上面两处源码。

### Q11 为什么"导出一个普通对象当 `Config`"在这套工具链里不行？

→ **两种要求不是一回事**：
- **Cordis 自己**只要 Standard Schema：`runtime.Config['~standard'].validate(config)`（`vendor/cordis/src/fiber.ts` 第 53 行）。教程 05 第 34 行原文：*"Cordis 本身接受任意 Standard Schema 验证器，因此将普通对象导出为 Config 无法工作"*——普通对象没有 `~standard`，所以它在 Cordis 眼里等于"没声明 schema"。
- **本仓库的配置工具链**（JSON Schema 投影、settings 表单、配置目录生成）额外要求**原生 Schemastery**：`isNativeConfigSchema` 要求 `Symbol.for('schemastery') === true`、`type` 是字符串、`meta` 是对象（`packages/boot/app-boot/src/config-schema/native.ts` 第 10–16 行）；不满足就记 `status: 'unsupported'` 并报 `Config is not a native Schemastery schema`（`collect.ts` 第 203–211 行），dump 的 `complete` 随之变 `false`、退出码为 1（`document.ts` 第 163–165 行、`dump-config-schema.ts` 第 47 行）。
**结论**：写 DSH 插件时，"用 Schemastery 造 `Config`"不是风格建议，而是**工具链的硬要求**。
