## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：一条不变量的**因果链**——它的准确表述（§3）、机制的每一处源码落点（§4）、它为什么必须存在（§5.2）、它的四条代价（§5.3–§5.6）、它约束谁与不约束谁（§4.8）。
**不是**：请求拼装的逐行顺序（那是 `3.6`）、surface 节点的完整语义（那是 `3.3`）、消息投影的注册 API（那是 `3.13`）。

### 0.2 现在只要记住这 4 件事

1. **不变量的本体**：*模型可见即已记录——每个模型请求都必须能从日志重建；新增模型可见输入需要会话事件。*
2. **它保护的是一条推导链**：日志 → `deriveMessages()` / `request/header` → 请求。这条链断了，恢复、fork、审计、计量、缓存、UI 全部降级为「大概率一致」。
3. **「⟺」的两半都是硬的**：左边靠**深冻结**（改写会抛错 = 不可伪造），右边靠**公开纯函数 + 逐字节重建测试**（= 不可遗漏）。
4. **想给模型看新东西，只有三条合法路径**：走派生历史（事件）、走 `request/header`、或注册纯消息投影；**没有第四条"分派时临时拼一下"**。

### 0.3 明确授权：这些现在不用管

- **§5.2 的三个故障场景**用了 `llm/stream` 监听器、`agent.inject()`、压缩（compaction）等名词——它们在 `3.2`/`3.5`/`3.12` 展开；本课用到哪讲到哪，**不要求你先懂它们的全貌**。

## 1. 最小词汇表（本课新增的 5 个词）

> 这五个词都属于**这一编自己的词汇**，不依赖后续任何一课。

| 词 | 大白话 | 在源码/日志里的样子 |
|---|---|---|
| **日志 log** | 一串**只追加、永不改写**的事实记录。本课里"真源"指的就是它 | `session.snapshotEvents()` 读到的那个数组；每条都有一个递增的 `seq` |
| **模型可见 model-visible** | 只要**被送进模型请求**，就算模型可见 | 请求里的 `messages`、`tools`、以及调用配置（`provider`/`model`/…） |
| **已记录 logged** | 在日志里**有一条事件**能解释它 | 有对应的 `type`（如 `user/message`、`request/header`） |
| **重建 rebuild** | 只拿日志（+ 日志引用的附件 + 固定代码版本），算出**当时那条请求** | 测试里就是"用一个**全新的 Session** 喂日志前缀，再 `deriveMessages()`" |
| **header 请求头** | 一条事件类型 `request/header`，里面是请求**非历史部分**的完整快照 | `EpochHeader`：`config` + `adapterDefaults`（适配器默认值的标记）+ `tools` |
| （复用）**surface 节点** | 派生历史里**有序的那一串**"会产出消息的事件" | `session.surface.nodes`（`3.3` 已定义） |

> ⚠️ 本课**不解释** header 的四种 `reason`（`initial`/`resume`/`change`/`series`）各自什么时候写字面量——本课只用到"它是一条完整快照"这一点；四种 reason 的语义在 §4.4 的源码块里顺带点出，细节归 `3.6`。

## 2. 先建立画面

### 2.1 从属关系图（静态结构）

```
会话日志（仅追加；唯一真源）
├─ surface 节点序列 ──► deriveMessages() ──► messages ─┐
├─ request/header 事件（每实例 / 每次真实变化一条）──► header ─┤
└─ （投影处理器：注册在 ctx.sessions 上，只改内容、不改节点）  │
                                                          ▼
                                             一次模型请求（GenerateOptions）
                                             = header.config + messages
                                               + header.tools + toolHistory()
                                               + sessionId + signal
                                                        │
                              ┌─────────────────────────┴─────────────────────────┐
                              ▼                                                   ▼
                    不可伪造：整棵请求树深冻结                    不可遗漏：日志前缀足以重建
                    （就地改写在接口层面不可表达）                （公开纯函数，外部重建器同路径）
```

> **精确性说明 1**：严格说 `system` 提示词不是"header 的一部分"——它是 surface 第 0 号节点上的 `system/message` 事件，走的是**派生历史**那条边（§4.3、§4.4）。
> **精确性说明 2**：`request/header` **不是**日志里的"另一层"，它就是日志里的一类事件；图上分成两条边，是为了区分"投影成 messages"和"折叠成 header"两种读法。

### 2.2 一次分派里，日志与请求的先后（动态过程）

```
① pre-step 领取输入 ──► 组装提示词与工具（此刻都还没进日志）
② step/start 打开步骤
③ systemPrompt.project() ──► 逐条 append('system/message')        ← 进日志
④ 首次尝试 ──► 逐条 append('user/message', surfaceOp:'append')     ← 进日志
⑤ buildRequest()：必要时 append('request/header') / ('developer/message') / ('request/context')
⑥ deepFreeze(header) → 逐条冻结 deriveMessages() → 冻结封装 → 打循环标记
⑦ preparedCall.stream(request) 发送                                ← 网络字节在此产生
─────────────────────────────────────────────────────────────────
分派之后才发生的事（注入、压缩），只能进「下一条请求」——边界就是日志位置
```

→ 记住第 ③④ 步**在 ⑦ 之前**：这就是"任意日志前缀都能反推出当时那条请求"（方向二）的全部机制来源。

### 2.3 大白话版：一个插件想给模型"多看一句悄悄话"

**完全不用上面的术语**（来源：`.agents\notes\implemented\architecture\2026-07-05-reconstructable-requests.zh.md` 第 39–46 行的"曾考虑的替代方案"一节，此处只做白话转述）：

1. 有人写了个插件，在请求**正要发出去的那一刻**，往消息列表里塞了一句"悄悄话"。
2. 这一句确实送到了模型面前——模型也照着它回答了。
3. 但**记录本上没有这一句**。记录本是一串"发生过什么"的流水账，而它是在流水账封笔之后才动手的。
4. 于是：下一轮把流水账重新念给模型听的时候，这句悄悄话不见了，模型的前后语境自相矛盾；用户从界面上看到的对话记录里也没有它，没法解释模型为什么那样回答；进程一重启，它永久消失，同一个会话出现了两个无法调和的版本。
5. 更隐蔽的后果：为了让重复的前缀能被提供方缓存复用，第二轮发送的内容必须和第一轮**逐字节相同**。这句悄悄话插在历史中间，从那一点起缓存全部失效，而且没有任何人能解释为什么。
6. DSH 的做法不是"发现这种情况就报警"，而是**让第 1 步根本做不到**——请求那一叠纸从构建完成起就被冻住了，想在上面写字会直接报错。
7. 与之对称的另一半：**只要记录本上有，就必须能把它念出来**。所以"想加内容"的唯一正路是**先写记录本**，再让请求从记录本里算出来。

## 3. 结论先行：这一课的 6 条

> 出处三分表见 §7；下面每条都带定位，全部逐行核对过。

1. **准确表述取自两条独立文档，措辞略有差异但同义**：
   - 架构文档（面向整体）：**「模型可见即已记录。每个模型请求都必须能从日志重建。新增模型可见输入需要会话事件。」**（`docs\architecture.zh.md` 第 131 行）
   - LLM 包（面向调用方，写作不变式）：**「模型可见 ⟺ 已记录——调用方必须确保每个提供方请求中的模型可见输入都可以从会话日志重建；loop 构建的请求以深度冻结状态到达，不可改写。」**（`packages\llm\llm\README.zh.md` 第 114 行）
   - 设计笔记（写作原则）：**「模型可见 ⟺ 已持久引用。」** 即「任何人持有日志、日志引用的附件对象和固定代码版本，即可逐字节重建循环的每个请求」（`.agents\notes\implemented\architecture\2026-07-05-reconstructable-requests.zh.md` 第 17 行）。
2. **它保护的对象是「日志」这个唯一真源**：模型历史由 `deriveMessages()` 从日志投影（`packages\core\session\src\index.ts` 第 856–877 行），请求的非历史部分（调用配置、适配器默认值标记、组装后的工具 schema）由 `request/header` 快照记录（`packages\core\session\src\types.ts` 第 234–251 行），渲染后的系统提示词不是 header 而是 surface 第 0 号节点上的 `system/message`（同文件第 236 行）。三者相加，请求才是「日志的纯函数」。
3. **「⟺」的两半都有强制力**：方向一是**不可伪造**（日志里没有的东西无法以任何就地改写的方式进入请求，因为 loop 构建的请求被深冻结，改写会抛错：`packages\core\agent-loop\tests\request-reconstruction.spec.ts` 第 773–795 行）；方向二是**不可遗漏**（日志里有的东西必须能重建出来，由 `THEOREM: every request rebuilds byte-equal from the session log alone` 断言：同文件第 856–903 行）。
4. **它真正的价值不是「审计好看」，而是消除「两个真相」**：会话日志是持久化、恢复、fork、transcript、遥测、token 计量与 prefix cache 的共同输入；一旦请求可以携带日志之外的内容，这些消费方全部只能与真实请求「大概率一致」。（同文件第 35、39–42 行；`docs\subsystems\session.zh.md` 第 183 行）
5. **代价分三块，都可定位**：(a) 每次模型可见变化都要落一条会话事件（header 全量快照、system 节点替换、注入的 user 消息各一次）；(b) 构造请求时要对历史做一次完整冻结遍历并维护证明表（按对象身份，非按 id）；(c) 插件作者承担「改内容必须注册纯投影」的静态装配义务（`.agents\notes\implemented\architecture\2026-09-11-plugin-owned-message-projections.zh.md` 第 13、33 行）。
6. **新增模型可见输入之所以必须新增会话事件，是因为输入只有三条合法来源**：派生历史（surface 事件）、已记录的 header（`request/header`）、或对已有消息的**已注册纯投影**（不换节点身份）。三条都要求「日志里有东西」。第四条路——在分派时临时拼装——被明确否决过（同笔记第 29 行；`2026-07-05-reconstructable-requests.zh.md` 第 42 行）。

## 4. 机制：源码对照（每块按「做什么 / 与哪个知识点相关 / 为什么这么写」讲解）

### 4.1 真源只有一个：`Session` 日志（先看"写进去"这一步）

`Session` 是类型化 `SessionEvent` 的**仅追加日志**，模型历史、transcript、遥测、标题、持久化**全部**从这条流派生（`packages\core\session\README.zh.md` 第 88 行）。

**源码：`append()` 的入口守卫与"先校验、先快照"** —— `packages\core\session\src\index.ts` 第 678–747 行

```ts
  /**
   * @param data - The event payload; must be JSON-serializable.
   * @param opts - Surface metadata: `surfaceOp` controls how the event enters
   *   the ordered surface; `sourceEventSeqs` lists the seq numbers of earlier
   *   events this one derives from. REQUIRED for
   *   {@link SurfaceEventType} events (every message-producing event must
   *   declare how it joins the surface, the sole source of derived model
   *   history) …
   * @returns the logged event — its assigned `seq`/`time` plus the SNAPSHOT of
   *   `data` that entered the log, so reading `event.data` back sees the logged
   *   value, never the caller's still-mutable input.
   * @throws if `data` or surface metadata is not losslessly JSON-serializable
   *   (BigInt, function, symbol, undefined, negative zero, non-finite number,
   *   circular reference, sparse array, or an exotic object such as
   *   Map/Set/Date/class instance), or when the candidate violates the
   *   request-header empty-field or tool-error consistency rules, or the
   *   canonical surface contract …
   *   One iterative pass reads, validates, and
   *   copies each nested value once, so a stateful getter cannot supply one value
   *   to validation and another to storage. The event log is the durable source
   *   of truth, so a bad event fails at the append site rather than later during
   *   a backend flush. …
   */
  append<T extends SessionEventType>(
    type: T,
    data: SessionEventMap[T],
    ...opts: T extends SurfaceEventType ? [opts: SurfaceIntent<T>] : []
  ): SessionEvent<T> {
    const surfaceOpts: SurfaceIntent | undefined = opts[0]
    const surfaceMetadata = {
      ...surfaceOpts?.sourceEventSeqs === undefined ? {} : { sourceEventSeqs: surfaceOpts.sourceEventSeqs },
      ...surfaceOpts?.surfaceOp === undefined ? {} : { surfaceOp: surfaceOpts.surfaceOp },
    }
    const dataSnapshot = snapshotJsonValue(data)
    if (dataSnapshot === undefined) {
      throw new Error(`session event "${type}" carries non-JSON-serializable data`)
    }
    const surfaceMetadataSnapshot = snapshotJsonValue(surfaceMetadata)
    if (surfaceMetadataSnapshot === undefined) {
      throw new Error(`session event "${type}" carries non-JSON-serializable surface metadata`)
    }
    const entry = attachments.get(this)
    if (entry?.appending) {
      throw new Error('session append cannot reenter while another append is being published')
    }
    const event = deepFreeze({
      type,
      seq: SessionSeq(this.log.length),
      time: Date.now(),
      data: dataSnapshot,
      ...(surfaceMetadataSnapshot as { surfaceOp?: unknown; sourceEventSeqs?: unknown }),
    } as unknown as SessionEvent<T>)
    validateSessionEventData(event, `session event "${type}" at seq ${event.seq}`)
    this.surfaceManager.validateNext(event as SessionEvent)
  }
  // （第 676–677 行的 JSDoc 首行、第 688–689 行第一个 @param、第 717 行前的若干细节行、
  //   第 750–768 行的发布与回调（entry.appending 置位、collectSessionCallbacks、
  //   this.log.push、广播、finally 复位）都不影响"入口如何把关"这个知识点，此处省略；
  //   第 748 行 surfaceManager.validateNext 之后直接进入第 750 行的发布段。）
```

按块讲解：

- **做什么**：这是日志唯一的写入入口。它先把载荷**只读一遍**并复制出一份"快照"，再校验，最后才推进 `this.log`（第 757 行，在省略段里）。
- **与哪个知识点相关**：方向二（不可遗漏）的**地基**。如果写入时既能校验一个值、又能存下另一个值，那么"日志里的东西"本身就不确定了，后面一切重建都失去意义。
- **为什么这么写**（JSDoc 原文）：*"a stateful getter cannot supply one value to validation and another to storage"*；*"a bad event fails at the append site rather than later during a backend flush"*。→ **坏事件在写入点就失败**，不会拖到后端刷盘时才炸。
- **顺带解释两件事**：`seq: SessionSeq(this.log.length)`——序号就是日志长度，所以**序号连续**；被 `deepFreeze` 包住的 `event` 让写进去的那份值**此后不可变**。

**源码：拒绝语义 —— 不改变任何东西** —— `packages\core\session\README.zh.md` 第 56 行原文

> 追加、seed/restore 与事件 adoption/snapshot 会拒绝任何 `header.system` 及恰好为空的可选请求头字段（`tools: []`、`adapterDefaults: {}`），**而不规范化输入**。工具结果的 `data.error` 仅在一等消息的 `isError === true` 时允许存在；失败标识仍是可选的。**被拒绝的追加不会改变日志、派生状态或事件流。**

→ 这三句让「模型可见即已记录」具有**原子性**：不存在"记了一半"的中间态。`types.ts` 第 247–250 行把 `system` 标为 `@persistenceReserved` 且类型为 `never`——想往 header 里塞提示词的旧路径在**类型**与**校验**两层都不成立。

### 4.2 方向二的落点：`deriveMessages()` 是公开纯函数

**源码：缓存的增量投影** —— `packages\core\session\src\index.ts` 第 838–877 行

```ts
  /**
   * Derive the LLM message history by walking the ordered sequences of
   * message-producing events maintained by `surfaceOp` markers. The
   * surface is the single source of derived history: every message-producing
   * append records its `surfaceOp`, so a raw event with no marker (a chunk, a
   * turn boundary) is correctly absent, and a compaction `replace` deletes the
   * shadowed nodes from the derivation. …
   *
   * CACHED: pure tail growth costs O(new nodes); a replacement or message projection
   * ({@link SessionSurface.contentGeneration}) rebuilds. The returned array is
   * a fresh snapshot per call (later appends never grow an array a caller
   * already holds); the `Message` objects in it are SHARED and **deep-frozen**.
   * …
   * @returns a fresh array of the shared, frozen derived history.
   */
  deriveMessages(): Message[] {
    const surface = this.surface
    const nodes = surface.nodes
    const generation = surface.contentGeneration
    if (generation !== this.derivedGeneration) {      // ← 守卫①：代次变了就整体重建
      this.derived = []
      this.derivedNodes = 0
      this.derivedGeneration = generation
    }
    for (const seq of nodes.slice(this.derivedNodes)) {   // ← 守卫②：只处理没见过的尾巴
      // Surface sequences are built from this.log — seq is always a valid
      // index by construction. The non-null assertion expresses that invariant.
      // oxlint-disable-next-line typescript/no-non-null-assertion
      const msg = this.deriveEventMessage(this.log[seq]!)
      // A surface node is one of the five message-producing types, but an
      // empty-content assistant/message (a max-tokens step that hosts only
      // usage) derives to null and must not enter the transcript.
      if (msg) this.derived.push(msg)
    }
    this.derivedNodes = nodes.length
    return [...this.derived]
  }
  // （本块未删节：第 838–877 行整段照录。第 831–836 行的三个缓存字段

/**
 * Normalize a header to canonical form: an empty tool list becomes an absent
 * field, matching how requests are built. Logging, folding, and comparison use
 * this one representation.
 * @param header - the header to normalize (not mutated).
 * @returns the canonical header.

export function canonicalHeader(header: EpochHeader): EpochHeader {
  const adapterDefaults = header.adapterDefaults
  return {
    config: header.config,
    ...adapterDefaults?.reasoningEffort === true || adapterDefaults?.maxTokens === true
      ? { adapterDefaults }
      : {},
    ...header.tools !== undefined && header.tools.length > 0 ? { tools: header.tools } : {},
  }
}

/**
 * Fold the header events of a log (or any prefix) into the
 * {@link EpochHeader} in force after the last snapshot. Non-header events are
 * skipped. This is the pure offline reconstruction path; the live session
 * tracks the same fold incrementally.
 * @param events - session events in log order.
 * @param from - a previously folded state to continue from.
 * @returns the latest canonical header, or undefined when none exists yet.
 */
export function foldRequestHeader(events: readonly SessionEvent[], from?: EpochHeader): EpochHeader | undefined {
  let state = from
  for (const event of events) {
    if (event.type === 'request/header') state = canonicalHeader(event.data.header)   // ← 只认这一种事件
  }
  return state
}

按块讲解：

```

按块讲解：

- **做什么**：`inject()` 不直接写日志，它把消息**放进下一步的待领取队列**（`next-step`）；工具执行返回的 `additionalContexts` 走同一个入口（第 536 行把 context 拼到队列尾部）。
- **与哪个知识点相关**：这正是"**边界就是日志位置**"（设计笔记第 29 行"已打开步骤是重建边界"）：分派之后才发生的注入**不可能**进入本次请求，只能成为**下一步**的一条普通 `user/message`。
- **为什么这么写**（`guard/repeat-tool-reminder` 的反例意义）：guard 工具的重复提醒**没有新增事件类型**，而是走 `additionalContexts` → 循环缓冲 → 在工具结果之后追加为注入的 `user/message`，因此"**无需新会话事件即可从会话日志重建**"（`packages\guard\repeat-tool-reminder\README.zh.md` 第 91 行）。→ **纪律是"复用已有事件类型"，不是"一律造新事件"**。
- **反过来看**：需要影响**本次**请求的监听器**只能**走 `agent/pre-step`（`agent/pre-step` 返回的 `messages` 与当前批次一起结算）。

### 4.8 强制执行的作用域：谁被约束、约束到什么程度

理解这条不变式常犯的四个错，都来自把它的作用域想大了或想小了：

- **它不是运行期断言，而是接口形态。** 没有任何中心代码在请求发出前"检查日志是否解释得通"；可重建性靠三个形态约束共同成立：新增输入必须走事件（§4.7）、请求在分派时已深冻结（§4.5）、派生规则是公开纯函数因而外部重建器不会跑偏（§4.2）。被否决的「检测并报告」方案正是想补一个运行期检查，理由是事后捕获已经晚了（`2026-07-05-reconstructable-requests.zh.md` 第 42 行原文：*"因违规必须在接口层面不可表达而否决"*）。
- **它只约束「循环归属的对话请求」。** 归属靠进程内的 `markAgentLoopRequest()` 标记（§4.5），而**不是**靠「冻结形状」或「带 sessionId」判断：压缩 summarize 之类一次性直连调用即使形状相似也保持排除（同笔记第 31 行；第 17 行末段）。
- **它对内容投影是「必须显式装配」而不是「默认就有」。** 缺处理器的后果是**拒绝**：追加、带历史的创建、恢复和纯折叠全部失败，卸载已使用的处理器后读取缓存也会被拒绝（`packages\core\session\README.zh.md` 第 54 行）。这条设计是有意的——独立读取器显式传入同一份处理器，避免实时路径与离线路径各有一套解释（`2026-09-11-plugin-owned-message-projections.zh.md` 第 19 行）。
- **它对「仅日志状态」是宽容的。** 只要不产生消息，就可以自由新增事件而不支付上述义务：普通仅记录日志事件「不需要这些机制」（同笔记第 33 行）；`request/context` 就是这样的仅日志状态，且被测试断言"不是 `SurfaceEventType`，因此永远无法到达模型请求"（`request-reconstruction.spec.ts` 第 935–938 行）。

### 5.2 三个故障场景：它到底防住了什么

**场景 A（变异型，已被测试固定）**：某插件监听 `llm/stream`，想让模型多看到一句悄悄话，于是对已构建的请求 `options.messages.push(...)`。在没有这条不变量的系统里，这一句会**只存在于本次网络请求**：日志里没有它，模型却按它回答了。后果连锁——(a) 下一轮把日志派生历史（不含该句）重新发出，模型的前后语境自相矛盾；(b) 用户从 Web/SDK 看到的 transcript 与模型实际输入不一致，无法解释模型为何那样回答；(c) 进程重启或 fork 后该句永久丢失，同一会话出现两个不可调和的版本；(d) 前缀缓存按"上一请求是下一请求的前缀"的假设复用，而这次写入发生在历史中间时，缓存从该点起全部失效且无人能解释。在 DSH 里这条路被**堵死**：请求整棵树已深冻结（§4.5），`push` 抛错，错误进入 `turn/end` 的 `reason.kind === 'error'`，测试断言错误文本匹配 `/frozen|read only|readonly/i`。**失败是响亮的，而不是静默的**——这正是该设计要的形态：设计笔记第 42 行原文明确否决了"检测并报告（比较连续请求、发散时告警）"方案，理由是"违规请求仍可构造并发出；因违规必须在接口层面不可表达而否决"。

**场景 B（遗漏型）**：某上下文插件想在每步给模型加一段说明，于是直接在组装阶段把文本塞进请求（而不是走 `agent.inject()` 或 `agent/pre-step`）。结果是**每一轮都付全价 token、却不进历史**：它不属于已缓存前缀、压缩看不见它、`deriveMessages()` 反推不出来，而且这类走漏通常**只在不发 `tools/change` 信号的中途注册路径上暴露**——该笔记第 43 行记录了这条推理：事件驱动组装存在"漏信号的 bug 类别"（会话中途注册的工具发 `tools/change` 而非 `system-prompt/change`，第三方提供方可能什么都不发），所以 DSH 选择"逐步骤渲染 + 值比较"，而模型可见输入必须落到事件上。legacy 代码库的对应反例是"客户端作为真源"与"镜像日志的有状态传输客户端"：两者都会"漂移而无人察觉"或"留下未记录的编辑路径"（同笔记第 39–40 行）。

**场景 C（部分记录型）**：只记录最新工具目录，不记录**当时生效的**工具定义。动态工具场景下，模型在 T1 看到工具 X 的 schema v1、在 T5 看到 v2，日志却只有一份当前目录——回放 T1 会得到错误的 schema，且缓存前缀假设失效。DSH 的解法是把"添加定义"与一次 `request/header` 绑定：`developer/message` 的添加块通过 `headerSeq` 引用那次请求头，且"每个名称必须在所引用的请求头中恰好对应一个完整模式"（`packages\core\session\README.zh.md` 第 52 行），`toolHistory()` 缓存"对已提交请求头和 developer 消息的有状态归约"，按历史 `headerSeq` 解析添加定义（同文件第 173 行）。

→ 三个场景的共同点：**日志与请求一旦允许分歧，分歧点以后的每一条推论都不再可靠**——恢复、fork、审计、计量、缓存、UI 展示全部降级为"大概率一致"。这就是为什么它被写成不变式而不是最佳实践。

### 5.3 开销 1：日志体积（自包含快照 vs delta）

`request/header` 存的是**完整规范快照**（调用配置 + 适配器默认值标记 + 组装后的完整工具 schema），而不是 delta。设计笔记第 56 行原文：*"重复完整工具目录比 delta 编解码器更大，但相对分片密集型日志仍然很小，并保留一种自包含的回放表示。"* 写入是差分的：只有封装真变、实例边界或序列起点才写（`packages\core\session\README.zh.md` 第 92 行；源码见 §4.3）。

**为什么不要 delta**（同笔记第 45 行原文）：*"引用前一个 header 的轻量 series 标记……从该标记开始的窗口若不再读取前序，就无法渲染或重建请求。自包含的完整快照让持久化、局部历史和快照固定共用一种表示。"*

### 5.4 开销 2：请求构造时的完整冻结遍历 + 证明表

**实测归因**：一次 211.300 ms 的请求历史操作里，**132.876 ms** 采样 CPU 自耗时归因于 `buildRequest` 的 `deepFreeze`（`.agents\notes\archived\simplification\2026-09-06-agent-request-freeze-evidence.zh.md` 第 10 行）。优化（按对象身份复用证明）后，同一工作负载的请求历史原始总耗时中位数从 **246.130875 ms** 降到 **67.292833 ms**（第 24–28 行表格）；代价是保留堆样本从约 **22.295 MiB** 升到 **22.59 MiB** 量级（22.591591–22.594795 MiB，预算 28.75 MiB），注释明确写"显示了证明表的小额成本；弱键防止表本身保留已替换消息"（第 32 行）。每个**新的 loop 实例**都要为恢复来的历史重新支付一次完整遍历（第 14、18 行）。

**三条被否决的捷径**（同笔记第 62–66 行原文要点）：

| 捷径 | 否决理由 |
|---|---|
| `Object.isFrozen` 为真就返回 | "已冻结根对象不能证明其后代已冻结" |
| 信任 Session 消息或缓存消息 `id` | "恢复明确允许拥有独立所有权的未冻结数据；替换操作可保留 id，同时改变对象身份与内容" |
| 强引用 Set / 全局证明缓存 | "强引用会延长旧历史的生命周期。全局缓存将所有权扩大到 agent 之外" |

### 5.5 开销 3：纪律与静态装配义务

"修改现有消息内容的插件"必须注册纯消息投影，并且**独立读取器（快照校验、离线查询、format 目录）要显式传入同一份处理器**；缺少处理器时**追加、带历史的创建、恢复和纯折叠都会被拒绝**，"替换处理器需要重新恢复会话"（`docs\architecture.zh.md` 第 131 行；`packages\core\session\README.zh.md` 第 54 行；`2026-09-11-plugin-owned-message-projections.zh.md` 第 13–19、33 行）。普通只记日志的事件不需要这些机制，所以**成本按"是否改变模型可见内容"分摊**。

### 5.6 开销 4：可读性的应对成本（测试侧，不动产品日志）

全量 header 让快照 fixture 变成"一行巨大 JSON"。仓库的应对**不是削弱不变量**，而是测试侧拆分：每种 header 组合类别恰好一个场景标 `pinsHeader`，其目录把提示词拆到 `system-prompt.expected.md`、把 schema 拆到 `tool-schemas.expected.json`，`session.jsonl` 里用 `"{{system}}"` / `"{{tools}}"` 占位，并有守卫强制这种拆分自洽（`.agents\notes\archived\testing\2026-07-06-pin-request-header-content-in-one-scenario.zh.md` 第 14、18 行）。

该笔记第 28 行还明确记下被否决的方案，原文：

> **收窄会话日志本身（记录内容 digest，把请求头存到其他位置）**——违反可重建性契约：产品日志必须逐 bit 复现每个请求。请求头体积是测试产物问题，应在测试规范化中解决；实时日志保持不变。

### Q1 这条不变量的准确表述与它保护的对象？

→ 表述有两个等价版本，引用时建议并给：架构文档写作「**模型可见即已记录。每个模型请求都必须能从日志重建。新增模型可见输入需要会话事件。**」（`docs\architecture.zh.md` 第 131 行）；LLM 包把它列为不变式「**模型可见 ⟺ 已记录**——调用方必须确保每个提供方请求中的模型可见输入都可以从会话日志重建；loop 构建的请求以深度冻结状态到达，不可改写」（`packages\llm\llm\README.zh.md` 第 114 行）。设计笔记把右侧写成「已持久引用」，并给出可检查的推论：**任何人持有日志 + 日志引用的附件对象 + 固定代码版本，即可逐字节重建循环的每个请求**（`2026-07-05-reconstructable-requests.zh.md` 第 17 行）。

→ 它保护的对象是**「日志是模型所见上下文的唯一来源」这个地位**（`docs\architecture.zh.md` 第 127 行原文：「会话日志是模型所见上下文的来源」）。具体保护三类消费方：**恢复/fork**（重建同一条历史，反之会「带可归因漂移」地分裂对话）、**审计与回放**（字节精确）、**提供方前缀缓存**（缓存命中率依赖逐字节稳定的前缀，故「前缀缓存稳定性是推论 #1，而非标题」——同笔记第 17、19 行）。附带还保护两条工程性目标：请求不可被监听器悄悄改写（`agent.ts` 第 669–686 行），以及 token 计量的口径（token-meter 通过回放持久日志测量，因此测量与真实请求同源，`packages\llm\token-meter\README.zh.md` 第 12 行）。

### Q4 新增模型可见输入时，为什么必须新增会话事件？

→ 因为「可重建」是**从日志单向推导**的：模型历史来自 `deriveMessages()`（`packages\core\session\src\index.ts` 第 856–877 行），请求配置与工具来自最新 `request/header`（`packages\core\session\README.zh.md` 第 119 行），提示词来自 `system/message` 节点（`packages\core\session\src\types.ts` 第 236 行）。任何新输入若没有对应事件，就**不在任何一条推导路径上**，重建器只能得到"与真实请求不同"的结果——这不是实现缺陷，而是不变式被破坏，且不会立刻报错。

→ 四种「想加输入」的意图，分别有确定做法，**全部以事件为前提**：
  1. 加一段上下文 → `agent.inject()`，它落入下一次获准的请求，成为带来源的持久 `user/message`（`docs\architecture.zh.md` 第 160 行）；「只付出一次代价并在后续成为可缓存前缀，代价是会在历史中累积直至压缩」（`2026-07-05-reconstructable-requests.zh.md` 第 51 行）。必须影响本次请求时用 `agent/pre-step` 返回消息（第 29、53 行）。
  2. 加一类新的持久状态 → 扩展 `SessionEventMap` 并「从日志渲染和回放」（`docs\architecture.zh.md` 第 163 行）。
  3. **改**已有消息的内容（不是加新消息）→ 注册纯消息投影：需要一个事件类型、一个同步处理器、实时注册与独立装配项；投影「保留消息身份」「不能同时声明 surface 操作」（`packages\core\session\README.zh.md` 第 54 行；`plugin-owned-message-projections.zh.md` 第 13、15、33 行）。
  4. 改工具或改路由 → 落 `request/header` 的 `change` 快照并配 `developer/message` 说明增删；工具变更**不依赖模型能力**，`toolHistory()` 提供提供方声明（`docs\architecture.zh.md` 第 131 行；`agent.ts` 第 626–649 行；`packages\core\session\README.zh.md` 第 173 行）。

→ 反过来看，「不新增事件」的方案为什么都不行，笔记里有逐条记录：**「只转换发出的请求」被否**，因为「压缩、分叉和离线回放也会派生消息。发送时转换无法覆盖这些消费方」（`plugin-owned-message-projections.zh.md` 第 29 行）；**「逐次调用的请求标量」被否**，因为「监听器可以零记账地逐次切换模型，悄然放弃本设计旨在保护的提供方缓存。配置是逐对话的已记录状态；waterfall 提议，日志记录」（`2026-07-05-reconstructable-requests.zh.md` 第 41 行）；**「检测并报告」被否**（第 42 行）。

→ 一句话答案：**因为「新增模型可见输入」在 DSH 里唯一的落地方式就是「新增一条能被投影进请求的事件」；不新增事件等于让这次输入只活在网络字节里，而所有下游消费方（恢复、fork、审计、计量、缓存、UI）读的都是日志。**

### Q5 （补充）这条不变式对 KV cache 的实际含义是什么？〔第一次读请跳过〕

→ 稳定前缀是**涌现的、不是管理出来的**：「一个仅追加的日志经逐节点纯函数投影，在 header 不变时自然产出前一请求的追加扩展」（`2026-07-05-reconstructable-requests.zh.md` 第 19 行）。因此失效只发生在真正变化处：改保留工具的定义或重建声明「会从第一个改变的请求 token 起使复用失效」；替换 surface 第 0 号节点的提示词「会使请求从该节点的第一个 token 起就不同——该节点是第 0 号节点时则整个请求都不同」；而 `in-history` 路由上的非空提示词变更「追加到已缓存历史之后，因此直到该历史末尾的前缀仍可复用」（`packages\core\agent-loop\README.zh.md` 第 162 行）。唯一的端到端验证是 key-gated 的 `request-cache.e2e.ts`（第 73、88–95 行），**当时未运行**。

### Q6 这条不变式的两半，分别在源码/测试的哪里被固定？

→ **方向一（不可伪造）**：`packages\core\agent-loop\tests\request-reconstruction.spec.ts` 第 773–795 行——监听器在 `llm/stream` 上 `options.messages.push(...)`，结果是 `turn/end` 的 `reason.kind === 'error'`。

**源码：变异被"响亮"拒绝** —— `packages\core\agent-loop\tests\request-reconstruction.spec.ts` 第 773–795 行

```ts
  it('a mutation attempt on the frozen request content throws into the step (loud, not silent)', async () => {
    const adapter = new MockAdapter([textResponse('one')])
    const ctx = await harness(adapter)
    const agent = await ctx.agentLoop.create(SessionId('a1'), { provider: 'mock', model: 'mock' })

    ctx.on('llm/stream', (options, next) => {
      // The historical failure mode this design kills: a listener rewriting
      // request content in place. The freeze turns it into a loud error.
      options.messages.push(createUserMessage({
        content: [{ type: 'text', text: 'sneaky' }],
        source: { kind: 'test' },
      }))
      return next()
    })

    send(agent, 'go')
    await waitForIdle(ctx, agent)

    const turnEnd = agent.session.snapshotEvents().findLast(event => event.type === 'turn/end')
    expect(turnEnd).toMatchObject({ data: { reason: { kind: 'error' } } })
    if (turnEnd?.type !== 'turn/end' || turnEnd.data.reason.kind !== 'error') throw new Error()
    expect(turnEnd.data.reason.error.message).toMatch(/not extensible|frozen|read only|readonly/i)
  })
```

按块讲解：三段对应"**变异尝试 → 变成轮次错误 → 错误文本匹配冻结类报错**"。`options` 就是 §4.5 里那个 `Object.freeze` 过的封装（它的 `messages` 是 `Object.freeze(boundaryMessages)`），所以 `push` 必然抛错；抛错发生在 `step()` 的同步区段里，于是被记成 `turn/end` 的 `error` 原因。

→ **方向二（不可遗漏）**：同文件第 856–903 行的 `THEOREM`。

**源码：THEOREM —— 用一个全新 Session 重建** —— `packages\core\agent-loop\tests\request-reconstruction.spec.ts` 第 856–903 行

```ts
  it('THEOREM: every request rebuilds byte-equal from the session log alone', async () => {
    const adapter = new MockAdapter([
      toolCallResponse('c1', 'echo', { text: 'one' }, 'calling'),
      textResponse('done'),
      textResponse('after change'),
    ])
    const ctx = await harness(adapter)
    registerEcho(ctx)
    const agent = await ctx.agentLoop.create(SessionId('a1'), { provider: 'mock', model: 'mock' })

    send(agent, 'go')
    await waitForIdle(ctx, agent)
    ctx.systemPrompt.section({ name: 'extra', order: 2, text: 'now with guidance' })   // ← 制造一次真实变化
    ctx.on('agent/request', async (_payload, next) => ({
      ...await next(), temperature: 0.5, maxTokens: 99, stop: ['<END>'],
    }))
    send(agent, 'again')
    await waitForIdle(ctx, agent)

    expect(adapter.requests).toHaveLength(3)
    const events = agent.session.snapshotEvents()
    const stepStarts = events.filter(e => e.type === 'step/start')
    expect(stepStarts).toHaveLength(3)

    adapter.requests.forEach((request, index) => {
      const stepStart = stepStarts[index]!
      const settlement = events.find(e =>
        (e.type === 'assistant/message' || e.type === 'assistant/attempt')
        && e.data.turn === stepStart.data.turn
        && e.data.step === stepStart.data.step,
      )!
      // Messages: the entered batch is logged after step/start, so rebuild the
      // complete dispatch prefix through a completely fresh Session.
      const rebuilt = Session.create(SessionId(`rebuild-${index}`), structuredClone(events.slice(0, settlement.seq)))
      expect(structuredClone(request.messages)).toEqual(rebuilt.deriveMessages())

      // Header: the latest request/header snapshot up to this step's dispatch
      // (its header event sits between step/start and the Assistant settlement).
      const header = foldRequestHeader(events.slice(0, settlement.seq))!
      expect(request.model).toBe(header.config.model)
      expect(request.reasoningEffort).toBe(header.config.reasoningEffort)
      expect(request.system).toBeUndefined()               // ← 提示词不在 header 里（§4.6）
      expect(structuredClone(request.tools ?? [])).toEqual(structuredClone(header.tools ?? []))
      expect(request.temperature).toBe(header.config.temperature)
      expect(request.maxTokens).toBe(header.config.maxTokens)
      expect(request.stop).toEqual(header.config.stop)
    })
  })
```

按块讲解：`const rebuilt = Session.create(SessionId('rebuild-' + index), structuredClone(events.slice(0, settlement.seq)))` 是**最关键的一行**——它不再是原来那个 session，而是一个**只喂进日志前缀的全新 Session**；`rebuilt.deriveMessages()` 与 `request.messages` 逐字节相等，就是"日志足够"的证明。第二段用 `foldRequestHeader(...)` 从同一段前缀折出 header，并把请求上的每个标量逐一比对。**注意 `expect(request.system).toBeUndefined()`**：它给 §4.6 的结论钉上了测试。

### Q7 （补充）「已记录」是否意味着「模型一定看得见」？〔第一次读请跳过〕

→ 不是，反方向的两个例外都很关键：**(a) 仅日志事件不产生消息**——`assistant/attempt` 保留失败/重试/取消的 attempt 但"不添加模型历史"，原始流分片、生命周期边界同样被 `deriveMessages()` 排除（`docs\architecture.zh.md` 第 127 行；`packages\core\agent-loop\README.zh.md` 第 168 行）。**(b) 表面替换与压缩会遮蔽**已被记录的消息，让它们不再进入后续请求，但**原始日志记录永不删除**（`packages\core\session\README.zh.md` 第 149 行）。所以准确说法是「**模型可见 ⟹ 已记录**」是硬约束，「已记录 ⟹ 模型可见」只在特定投影条件下成立。
