## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：事件这套扩展点的**总账**。三件事——① 事件分几个域、怎么判；② 事件有几种分发模式、写法差在哪；③ 谁发谁听、这份账是怎么生成的。
**不是**：循环里"什么时候发出哪个事件"的时序故事（那是 `3.5` / `3.6`），也不是 Cordis 插件内核本身（那是**第二编**）。

### 0.2 现在只要记住这 4 件事

1. **事件是扩展点，"选对事件域"是大多数改动的第一个决定**；域只有三个——**会话事件**、**Agent 事件**（`agent/*`）、**能力事件**（`fs/*`、`tools/*`、`telemetry/*`）。
2. **同一个事件名，先看它属于哪个域，再看它用哪种分发模式**。模式共五种：`emit` / `parallel` / `serial` / `bail` / `waterfall`；只有 **`waterfall` 会拿到 `next()`**，`serial` **没有** `next()`。
3. **持久 vs 实时不看名字前缀，看"是不是日志成员"**：`agent/*` 全是实时；`turn/*`、`step/*` 全在日志里；而 `session/created`、`session/disposed`、`session/event`、`session/flush` 这**四个带 `session/` 前缀的，是实时总线事件、不进日志**。
4. **生产方、消费方、声明位置三列不是手写的**，由 `pnpm run gen-doc-graphs` 从 TypeScript Program 里推出来，并且**拒绝"有人声明、没人派发"**的事件。

### 0.3 明确授权：这些现在**不用管**

- 五种分发的**实现细节**（`next` 怎么被压回参数、`isBailed` 的判据）：它们集中在 §5，只读 §4 的四种写法就够用了；
- `@mode` 标签的**解析器实现**（正则、JSDoc 解析）：属于第二编的工具链细节，本课只用它的结论；
- `SessionEventMap` 里每个事件的**载荷字段语义**：本课只关心"谁是成员"，字段逐条解释属 `3.3` 与 `3.1`。

判断标准只有一条：**只要你能回答"这个人/这个事件属于上面 4 件事里的哪一件"，就够了。**

### 0.4 两个词先说清楚

- **`next()`**：waterfall 监听器收到的**最后一个参数**，是一个"把剩下的链条跑下去"的回调。**不调用它 = 就地短路**。
- **委托**：调用 `next()` 把控制权交给下游监听器（最终交给内建行为）。本笔记只在"可能否决/可能不否决"这个意义上用这个词。

### 0.5 术语分级声明（哪些词不属于本课）

本文用到的 `ctx` / 服务 / seam / Agent 句柄 / turn / step 这些词，分别由 `notes/1-结构与装配/1.1-名词与分层.md`、`notes/3-运行内核/3.1-会话格式.md` 定义，本课不重复解释。**`@mode` 标签的解析器、`Scope-filtered dispatch` 的作用域机制属于第二编的展开内容**，第一次读请跳过 §5.7 的第二段与附录 A 的 Q6。

## 1. 最小词汇表（5 个词）

这 5 个词是后面一切的地基。

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **事件 event** | 一件"发生了的事"的广播。谁想响应它就提前登记一个**监听器** | `ctx.on('<名字>', (…参数) => …)` |
| **监听器 listener** | 你登记的那个回调函数；插件卸载时它自动被撤掉 | `ctx.on()` 的第二个参数 |
| **分发 dispatch** | "把这件事通知出去"这个动作。**同一个事件只能用一种方式通知** | `ctx.emit` / `ctx.waterfall` / `ctx.serial` / `ctx.parallel` / `ctx.bail` |
| **域 domain** | 一组事件的**归属分类**，决定"这条消息该走哪条路"（持久日志？实时总线？能力接缝？） | 文档里的"三个事件域"；源码里体现为事件声明写在哪个包里 |
| **持久 persistent** | 这件事被写进会话日志，**重新加载后还在** | 是 `SessionEventMap` 的成员 |

> ⚠️ 上表与 `docs/architecture.zh.md` 第 76–80 行是同一套体系的两种说法：文档用三个域讲"选哪个"，本表用"名字—机制—落地写法"讲"看到什么就是什么"。
> 域与分发模式**是两个正交维度**：域回答"这条信号走哪条路"，模式回答"通知时按什么规则叫监听器"。下文 §2 管域，§5 管模式。

## 2. 两张图：域与模式

### 2.1 事件分域图（静态结构）

```
                     事件（一次广播）
                          │
        ┌─────────────────┼─────────────────────────┐
        │                 │                         │
   会话事件            Agent 事件                 能力事件
   (持久事实)          (`agent/*`，实时)          (`fs/*`、`tools/*`、`telemetry/*`)
        │                 │                         │
   写进会话日志      携带活跃 Agent 句柄        挂在某个能力接缝(seam)上
   并经 `session/event`   观察/拦截进行中的工作      不引入循环依赖就挂策略与适配器
   实时广播出去
        │
   ┌────┴─────────────────────────────┐
   │ 同名同域里还有一类"实时总线事件"： │
   │ `session/created` / `session/disposed` / │
   │ `session/event` / `session/flush`  │
   │ —— 前缀是 `session/`，却不进日志    │
   └──────────────────────────────────┘
```

> **精确性说明**：说"`session/*` 分两类"容易误导——它们**同属"会话相关"这个话题，但分属两个完全不同的机制**：四个总线事件是实时广播（域=实时总线），其余 `session/*`（如 `session/end-seed`）是日志成员（域=持久事实）。判据见 §4。

### 2.2 五种分发模式图（动态过程）

```
一次分发：把事件名 + 参数交给监听器链

emit        →  cb₁ cb₂ cb₃ 全部调用，不 await，返回值丢弃（同步抛错会打断后面的）
parallel    →  cb₁ cb₂ cb₃ 全部并发调用，await 全部结束；只能事后 AggregateError
serial      →  cb₁ → await → cb₂ → await → cb₃ …  某个返回"非空非 false"就【停】
bail        →  同上，但同步执行、不 await（同一条"停"判据）
waterfall   →  cb₁(…args, next) ──调用 next()──▶ cb₂(…args, next) ──▶ … ──▶ 内建行为
                    │
                    └─ 不调用 next() 就地返回 = 短路：后面的监听器与内建行为都不跑
```

> 图上不出现未定义术语：`cb` 就是"监听器"，`await` 就是"等它跑完"。`bail` 在本课只用于解释 `isBailed` 这条判据被两处共用（§5.6），harness 自有事件里没有 `bail` 模式的事件。

## 3. 大白话版：一个插件想知道"模型开始说话了"，会发生什么

**完全不用术语**，先建立画面（来源：`docs/architecture.zh.md` 第 92–111 行的轮次流程伪代码；这里只做白话转述，细节留到 `3.5` / `3.8`）：

1. 你的插件被装上时，对"模型开始/持续/结束吐字"这件事**登记了一个回调**。
2. 循环跑一个步骤时，模型开始吐字，循环就**把这件事通知出去**，你的回调被叫醒，拿到一小片增量。
3. 这些增量片**只在这一刻存在**，谁都没把它们写进会话日志——它们是"过程"，不是"事实"。
4. 这一步结束时，循环把**完整的一份模型输出**作为一条事实追加进会话日志。
5. 那条事实一旦进日志，就**同时**触发两件事：日志多了一行；以及"日志长了一行"这件事被广播给所有关心的人（含写磁盘的持久化插件）。
6. 第 5 步的广播发生在**提交之后**——所以收到通知的人看到的已经是"已经进日志的事实"，不能反悔。
7. 而第 2 步那种通知发生在**事情进行中**——它可以是拦截点：有的通知（瀑布式）能让下游决定"要不要继续"。
8. 于是同一套"通知"机制被用在两个完全不同的时机上：**造事实之前**（拦截）和 **事实落地之后**（观察）。这就是为什么要分域。

## 4. 正题一：三个事件域及其判据

### 4.1 三个域的定义与使用判据

| 域 | 性质 | 典型事件 | 何时使用 | 出处 |
|---|---|---|---|---|
| **会话事件** | 追加到日志、经 `session/event` 广播的**持久事实** | `turn/*`、`step/*`、`system/message`、`user/message`、`assistant/message`、`assistant/attempt`、`tool/*` | 某个事实**必须在重新加载后仍然存在** | `docs/architecture.zh.md` 第 78、113 行 |
| **Agent 事件**（`agent/*`） | 携带活跃 `Agent` 的**实时**信号：inbox、步骤、状态、请求、验证、续跑 | `agent/pre-step`、`agent/request`、`agent/request-error`、`agent/turn-stopping`、`agent/status` | 要**观察或拦截进行中的工作** | `docs/architecture.zh.md` 第 79 行 |
| **能力事件** | 挂在某个 seam 上的策略与适配器 | `fs/*`、`tools/*`、`telemetry/*` | 不引入循环依赖就想挂策略与适配器 | `docs/architecture.zh.md` 第 80 行 |

**"选对事件域是第一个决定"这句原话在 `docs/architecture.zh.md` 第 76 行**；第 84 行指向事件映射表。**来源**：`docs/architecture.zh.md` 第 74–84 行。

### 4.2 边界规则（一句话判据）

**持久的、可回放的事实是 `SessionEvent`；实时拦截或瞬态/活对象信号是 Cordis 事件。**

这条规则来自 `.agents/notes/implemented/architecture/2026-06-30-event-domain-semantics.zh.md`：

- 第 27 行给出边界规则原文与推论："轮次或步骤边界是持久事实，因此存在于会话日志中并从 `session/event` 源读取——**不会被镜像为 `agent/*` emit**"；
- 第 24 行明确"轮次和步骤边界不在此处（`agent/*`）"；
- 第 29 行记录：四个边界镜像（`agent/turn-start`、`agent/turn-end`、`agent/step-start`、`agent/step-end`）被**移除**。

→ 所以本课开头那条"`turn/*`、`step/*` **不是** `agent/*` 事件"不是遗漏，是**决策的结果**。

## 5. 正题二：事件有三层生命周期 + 五种分发模式

### 5.1 三层生命周期（先结论）

任务问的"持久 vs 实时"其实要分三层看，三条证据链彼此独立：

| 层 | 判据 | 证据 |
|---|---|---|
| **持久日志事件** | 是 `SessionEventMap` 的成员，被 `session.append()` 写进 `this.log` | `packages/core/session/src/types.ts` 第 281–428 行（`SessionEventMap`）；`packages/core/session/src/index.ts` 第 757 行 `this.log.push(event as SessionEvent)` |
| **持久化到磁盘** | 出现在生成的持久化目录里 | `docs/persistence-catalog.zh.md` 第 25–69 行的 `event:*` 行（共 59 行） |
| **实时总线事件** | 有 `@mode` 与 `ctx.<mode>()` 调用点，但**不是**日志成员 | `packages/core/session/src/index.ts` 第 43–84 行（四个 `@mode` 声明在第 52、61、72、80 行） |
| **进程内瞬态流** | 明说 chunk 帧是瞬态的 | `packages/core/agent/src/runtime-types.ts` 第 354–363 行：`Chunk frames are transient; the loop appends one final v2 assistant/message or assistant/attempt with the same stream before a committed end frame` |

**"模型可见即已记录"** 是这条边界的总纲：任何到达模型请求的内容都必须能从日志重建（`docs/architecture.zh.md` 第 131 行）。

### 5.2 `Session.append` 的执行顺序

`Session.append`（`packages/core/session/src/index.ts`）的关键步骤，行号逐条可查：

- 第 728–735 行：先校验载荷是**无损 JSON**（`snapshotJsonValue` 返回 `undefined` 就抛 `non-JSON-serializable data`）。
- 第 736–739 行：**重入守卫**——正在发布另一次 append 时直接抛错。
- 第 740–746 行：构造 `deepFreeze({ type, seq, time, data, ...surfaceMetadata })`——事件是冻结的，`seq` 取当前日志长度。
- 第 747–748 行：`validateSessionEventData(...)` + `this.surfaceManager.validateNext(...)`，校验在**推入日志之前**。
- 第 750–757 行：**先解析监听器快照，再 `this.log.push(event)` 提交**。
- 第 759–761 行：提交之后才把 `session/event` 回调跑起来。

### 5.3 五种分发模式的实现

**源码对照：`EventsService` 的四种分发 + 判据** —— `vendor/cordis/src/events.ts` 第 13–15、183–243 行（`parallel` 183–187、`emit` 194–196、`serial` 204–209、`waterfall` 234–243；块内只省了同步版 `bail`（211–222 行）与各方法的 JSDoc）：

```ts
export function isBailed(value: any) {                    // ← serial 与 bail 共用的"停"判据
  return value !== null && value !== false && value !== undefined
}                                                         // ← 第 13–15 行

  async parallel(...args: any[]) {
    const results = await Promise.allSettled(this.dispatch('emit', args).map(async cb => cb(...args)))
    const errors = results.filter((result): result is PromiseRejectedResult => result.status === 'rejected')
    if (errors.length) throw new AggregateError(errors.map(error => error.reason))
  }                                                       // ← 第 183–187 行

  emit(...args: any[]) {
    this.dispatch('emit', args).map(cb => cb(...args))    // ← map：同步抛错会打断后续监听器
  }                                                       // ← 第 194–196 行

  async serial(...args: any[]) {
    for (const cb of this.dispatch('serial', args)) {
      const result = await cb(...args)
      if (isBailed(result)) return result                 // ← 顺序 await，遇 bail 值即停
    }
  }                                                       // ← 第 204–209 行

  waterfall(...args: any[]) {
    const cbs = this.dispatch('waterfall', args)
    const inner = args.pop()                              // ← 参数表最后一个是"内建行为"
    const next = () => {
      const cb = cbs.shift() ?? inner                     // ← 逐个取出监听器，取完用内建行为兜底
      return cb(...args)                                  // ← args 是【同一个数组】：next 忽略你传的新值
    }
    args.push(next)                                       // ← 把 next 压回去，成为监听器的最后一个参数
    return next()
  }                                                       // ← 第 234–243 行
```

**按块讲解**

- **做什么**：这是五种模式里四种的**全部实现**。整段的核心只有三个动作：解析监听器（`this.dispatch(...)`）、按模式调用、按模式收尾。
- **与哪个知识点相关**：§5.7 表格（"分发实现"那一行）、附录 A 的 Q3。
- **为什么这么写**：
  - `serial` 用 `for` + `await`：**顺序**且**可停**（第 205–208 行）；
  - `emit` 用 `.map()`：不 await、不收集返回值——代价是**同步抛错会饿死后面的监听器**，这正是 `agent/*` 域自己重写 emit 的原因（§5.7）；
  - `parallel` 用 `Promise.allSettled`：全部跑完，最后才把拒绝聚合成 `AggregateError`（第 184–186 行）——**不能否决，只能事后失败**；
  - `waterfall` 的三行是全局最容易被误解的地方：`args.pop()` 取出内建行为，`next()` 用 `cbs.shift() ?? inner` 逐层下探，最后 `args.push(next)` **把 `next` 放到同一个 `args` 数组末尾**。因此**下游看到的还是原来那个对象**——想让下游看到变化，必须**就地改共享对象**，而不是"给 `next()` 传新值"。
- **`isBailed` 的判据不是布尔**：`value !== null && value !== false && value !== undefined`——返回 `0` 或 `''` 也算"停"（标注为推断：判据只排除这三种值，源码未额外说明理由）。
- **省略说明**：省了同文件第 16–182 行（类型定义、`Context` 接口重载、`EventsService` 的构造与 `dispatch`）、第 188–193 与 198–233 行的 JSDoc、第 211–222 行的同步版 `bail`、第 245–319 行的 `register`/`unregister`/`on`/`once`——它们与本知识点（分发模式差别）无关。
- **一个必须记住的原文**：第 227–229 行的 JSDoc 写着 `a listener that does not call next() vetoes the rest of the chain, including the built-in behavior`——**"短路"包含跳过内建行为**。

- **做什么**：按事件名排序渲染表格行；然后对"声明了但没有可识别派发点"的事件**抛错**，让文档生成失败。

- **省略说明**：省了第 1439 行之前（`events`/`relations`/`pkgsByShort` 的构造）与第 1464 行之后（未声明事件字符串那一张表）——与本知识点无关。

## 8. 五个写法事实（背下来）

1. **只有 waterfall 需要 `next()`**；不调用就是短路否决，连内建行为一起跳过（`vendor/cordis/src/events.ts` 第 227–229 行的注释）。
2. **waterfall 的 `next()` 忽略你传进去的参数**。第 237–240 行的 `next` 只是 `cb(...args)`，`args` 是**同一个数组**——下游看到的还是原来那个对象。所以包装器改变下游行为的方式是**就地改共享对象**。这条在 `tools/execute` 的超时策略上被明确利用：`.agents/notes/implemented/architecture/2026-07-07-tool-call-timeout-policy.zh.md` 第 57 行写明"信号替换采用**就地修改 `exec.signal`** 的方式，而非向 `next()` 传递新对象……Cordis 的 waterfall `next()` 忽略传入的任何参数，并以共享的 payload 数组重新调用下游监听器"。
3. **serial 不是"必须全部跑完"**：只要某个监听器返回非 `null` / 非 `false` / 非 `undefined`，后面的监听器就不再运行（第 13–15、204–208 行）。
4. **`emit` 谁都不 await、返回值被丢弃**（第 194–196 行）；`parallel` 全跑完、只能在最后抛 `AggregateError`（第 183–187 行）。四种约定彼此不可替换。
5. **`agent/*` 的通知自带一层 `try/catch`**（`packages/core/agent/src/dispatch.ts` 第 120–137 行），因为 `emit` 的 `map` 实现会被一次同步抛错打断。

## 11. 关键问题与答案

### Q1 事件分哪几个域？各自性质与使用判据？

**答：三个域——会话事件、Agent 事件（`agent/*`）、能力事件。**

| 域 | 性质 | 使用判据（原文） | 出处 |
|---|---|---|---|
| 会话事件 | 追加到日志、经 `session/event` 广播的**持久事实** | "当某个事实**必须在重新加载后仍然存在**时，使用它" | `docs/architecture.zh.md` 第 78 行 |
| Agent 事件 | 携带**活跃 `Agent`**：inbox、步骤、状态、请求、验证、续跑 | "要**观察或拦截进行中的工作**时，使用它" | 第 79 行 |
| 能力事件 | 无需导入循环即可向 seam（`fs/*`、`tools/*`、`telemetry/*`）附加策略与适配器 | "不引入循环依赖就想挂策略" | 第 80 行 |

补充两条判据：

1. **边界规则**："持久的、可回放的事实是 `SessionEvent`；实时拦截或瞬态/活对象信号是 `agent`/`tools` Cordis 事件"（`.agents/notes/implemented/architecture/2026-06-30-event-domain-semantics.zh.md` 第 27 行）。
2. **域不看前缀看成员**：`agent/*` 全部是实时总线事件，`turn/*`、`step/*` 全在日志里；而 `session/created` 这类带 `session/` 前缀的仍是实时总线事件（§9.4）。

### Q3 waterfall 事件与 serial 事件在写法上的差别（是否需要 `next()`）？

**答：waterfall 需要 `next()`（且不调用就是短路否决）；serial 没有 `next()`，它用"返回非空值"来提前停止后续监听器。** 四个维度的真实差别：

| 维度 | waterfall | serial |
|---|---|---|
| 监听器签名 | `(payload, next: () => Promise<T>)` | `(payload)`，**无 `next`** |
| 典型声明 | `agent/pre-step`，`packages/core/agent/src/runtime-types.ts` 第 320 行 | `agent/created`，同文件第 261 行；`agent/turn-stopping` 第 381 行 |
| 分发实现 | `vendor/cordis/src/events.ts` 第 234–243 行：`next` 压回参数、逐层下探 | 第 204–209 行：`for` + `await`，遇 `isBailed()` 返回即停 |
| 提前终止手段 | **不调用 `next()`**，就地返回（还跳过内建行为，注释见第 227–229 行） | **返回非空非 false 值**，判据 `isBailed()` 在第 13–15 行 |
| 返回值 | 最外层监听器的返回值（第 232 行：`the outermost listener's return value`） | 首个 bail 值（第 202 行） |
| 文档约定 | "仅做标注或观察的监听器则**必须委托**"（`docs/cordis-primer.zh.md` 第 29 行） | 按注册顺序 await，无需委托概念 |

**"是否需要 `next()`"的权威答案在 `docs/architecture.zh.md` 第 113 行**：`agent/pre-step`、`agent/request`、`llm/stream` 和三个 `tools/*` 是 waterfall，"其监听器必须调用 `next()` 才能委托下去"；`agent/turn-stopping` 是 serial 事件，"没有 `next()`"。

**两个必须记住的写法事实：**

1. **waterfall 的 `next()` 忽略你传进去的参数。** `vendor/cordis/src/events.ts` 第 237–240 行的 `next` 只是 `cb(...args)`，`args` 是**同一个数组**——下游监听器看到的还是原来那个对象。所以包装器改变下游行为的方式是**就地改共享对象**，而不是"给 `next()` 传新值"。这条在 `tools/execute` 的超时策略上被明确利用：`.agents/notes/implemented/architecture/2026-07-07-tool-call-timeout-policy.zh.md` 第 57 行写明"采用就地修改 `exec.signal` 的方式……Cordis 的 waterfall `next()` 忽略传入的任何参数"。
2. **serial 不是"必须全部跑完"。** 只要某个监听器返回非 `null` / 非 `false` / 非 `undefined`，后面的监听器就不再运行（第 13–15、204–208 行）。这与 `emit`（谁都不 await、返回值被丢弃）和 `parallel`（全跑完、只能在最后抛 `AggregateError`）是三种完全不同的约定。

### Q4 事件的生产者与消费者如何对应？

**答：由生成器从 TypeScript Program 解析出"声明位置 + 分发调用点 + 监听点"三列，落成 `docs/event-producer-consumer.zh.md` 的一张 81 行表。** 具体对应方式：

1. **声明位置（Declared in）**：给出事件契约所在的源码文件与行号，例如 `session/event` → `packages/core/session/src/index.ts:74`（该表第 68 行）。
2. **生产方（Dispatchers）**：格式为 `包名 (方法)`，方法是 `emit` / `waterfall` / `serial` / `parallel` / `events.dispatch` 之一。表头说明"接收方和事件名称类型还涵盖**有意绕过 `ctx.emit` 的内含派发位置**，例如 subagent 生命周期封装"（第 8 行）——`events.dispatch` 这个写法正是因为 `agent/*` 自己解析监听器集合（§5.5）。
3. **消费方（Listeners）**：列出注册监听器的包；`-` 表示当前无人监听。`session/event` 的消费方最多，一共 **25** 个包（第 68 行）。
4. **多生产者**：同一事件可有多行来源，如 `tools/change` 由 `agent-preset-registry (emit)` 与 `tools (emit)` 各自派发（第 78 行）；`fs/write-intent` 由 `tool-fs` 与 `tool-str-replace-editor` 各派发一次 `waterfall`（第 53 行）。
5. **校验闭环**：生成器要求每个被声明的事件都有可识别的分发调用点，否则报 `no dispatcher found for declared event ... (teach scripts/gen-doc-graphs.ts that form)`（`scripts/gen-doc-graphs.ts` 第 1457–1462 行）。因此"声明了但没人发"不会被静默放过；而"有人发但没人听"是**合法状态**（本次实测 9 个，见 §9.3）。
6. **agent 事件多一层作用域**：`agent/*` 的每一条声明都带 `Scope-filtered dispatch (@deepseek-ai/dsh-scope): agent-scoped listeners receive only that agent`（`packages/core/agent/src/runtime-types.ts` 第 258 行等），生产方通过 `packages/core/agent/src/dispatch.ts` 第 94–148 行的 `agentCarrier` / `agentEvents` 把 agent 作为派发 `this` 融合进去。

**一句话记法**：**声明在 owner 包里，派发在产生事实的那一行，消费在 `ctx.on(...)` 里；三者的对应关系不是靠读代码猜，而是 `pnpm run gen-doc-graphs` 从程序里推出来的。**

### Q5 为什么不能有 0 个消费者？——**第一次读请跳过**（属第二编的生成器约定）

**答：可以。零消费者是合法的，零生产者才被拒绝。** `scripts/gen-doc-graphs.ts` 第 1446–1448 行的注释原文把这条边界写得很清楚：*"Every declared event needs a dispatcher: zero means dead vocabulary or an unrecognized semantic dispatch form. **Listener-free extension points remain valid.**"*——**声明本身就是给将来监听者留的扩展点**，所以只校验"有人发"。本次实测有 9 个这样的事件（§9.3）。

### Q6 `events.dispatch` 这个"生产方写法"是什么？——**第一次读请跳过**（属第二编的派发机制）

**答：它是"自己解析监听器集合、自己调用"的低层入口。** `vendor/cordis/src/events.ts` 第 165–175 行的 `dispatch(type, args)` 负责两件事：从 `args` 里取出可选的 `thisArg` 与事件名，按 `Context.filter` 作用域过滤出监听器列表并绑定 `this`。高层方法（`emit`/`serial`/…）都建立在它之上；`packages/core/agent/src/dispatch.ts` 第 126 行直接调用它，是为了**绕开 `ctx.emit` 的 `.map()` 缺陷**（§5.5），并在每个回调外面各包一层 `try/catch`。所以表里出现 `events.dispatch` 作生产方，意味着"这个包绕过了标准 emit 通道，但仍然走同一套作用域过滤"。
