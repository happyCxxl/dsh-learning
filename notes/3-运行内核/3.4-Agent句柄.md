## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：把「一个实时 agent 怎么被创建、被谁拥有、怎么被拆除」讲死——**谁声明接口、谁提供实现、失败时退回什么、拆除按什么顺序**。
**不是**：循环内部的 turn/step 状态机与 inbox 的插入点（那是 `3.5`）、请求怎么拼装（那是 `3.6`）、会话日志格式（那是 `3.1`）。

### 0.2 现在只要记住 4 件事

1. **句柄 = 一个 agent + 一把只给创建者的拆除钥匙**。`AgentHandle` 只有两个字段：`agent` 与 `dispose()`。
2. **接口在 `dsh-agent`，构造与驱动在 `dsh-agent-loop`**。消费方只依赖前者，循环通过 `setFactory()` 把自己的工厂塞进 `ctx.agents`，所以驱动器可替换。
3. **创建是「先准备、后发布」的事务**：所有东西都在观察者看不见的时候准备好；一旦宣告出去就收不回来，所以任何失败都要把已准备资源退回、并给已送达的宣告补一次配对销毁。
4. **拆除有固定顺序**：排空驱动器 → 撤销作用域 → 关闭会话写路径 → 摘掉 agent → 摘掉会话。

### 0.3 明确授权：这些现在不用管

- **`agent/*` 事件的完整清单与分档**（哪些能否决、哪些不能）——本课只用到其中三个，完整版属于 `3.2`；
- **`Inbox` 的六个变更方法与持久投影**——属于 `3.5`；
- **agent preset、fork/seed 的语义**——属于第五编（对应路线图 5.x）；
- **`AsyncLocalStorage` 发起方作用域**——本课只点出它是「进程本地归因」，`4.4` 展开。

判断标准只有一条：**只要你能说出某个词属于上面 4 件事里的哪一件，就够了。**

## 1. 最小词汇表（本课新增的 6 个词）

| 词 | 大白话 | 在源码里的写法 |
|---|---|---|
| **handle 句柄** | 创建者拿到的「一个 agent + 一把只能自己用的拆除钥匙」 | `{ agent, dispose() }` |
| **registry 注册表** | 记录「现在有哪些 agent 活着」的那张表 | `ctx.agents`（`AgentRegistry` 实例） |
| **entry 条目** | 表里的**一行**：一个 id、一个 agent、一个归属者、三个生命周期布尔 | `AgentEntry` |
| **factory 工厂** | 真正会「造 agent」的那个对象。注册表不会造，它只转交 | `AgentFactory`，由循环实现 |
| **publish 发布** | 把准备好但还看不见的东西**放进注册表并宣告出去** | `enter()` 之后 `announce()` |
| **teardown 拆除** | 把上面这一切**按固定顺序一步步退回** | `prepare()` 里记忆化的 `dispose()` |

> ⚠️ 这 6 个词里，**registry / entry / factory / publish / teardown 都属于第二编「插件内核」的体系**（`2.1` 讲对象、`2.3` 讲可逆副作用、`2.5` 讲作用域）。本课只用到上表这个程度，不追问它们各自的完整机制。

## 2. 先建立画面

### 2.1 从属关系图（谁是谁的一部分）

```
ctx.agents  ←  AgentRegistry（服务，登记在插件上下文里）
│
├─ store: Map<SessionId, AgentEntry>         ← 实时 agent 表（本课核心）
│    每个 entry = { id, agent, owner, carrier, announced, announcing, detachRequested }
│    key = id，且必须满足  id === agent.session.id   （否则 enter() 直接抛错）
│
├─ factory: { target: AgentFactory }         ← 工厂槽位，只允许一个
│    └─ 由 dsh-agent-loop 的 AgentLoop 实例 fill（setFactory）
│         └─ 真正造出来的是 ReactLoopAgent（implements Agent）
│
└─ initiators / initiatorRuns: AsyncLocalStorage   ← 进程本地「谁发起的」归因
```

三层身份别混：

| 你可能听到的说法 | 实际的源码对象 | 谁拥有它 |
|---|---|---|
| 「Agent 接口 / 对外面」 | `interface Agent`（`types.ts` 声明身份，`runtime-types.ts` 合并进实时能力） | `dsh-agent` 包 |

### 2.3 大白话版：一次 agent 创建，机器里发生了什么

**完全不用上面的术语**（来源：`.agents\notes\implemented\architecture\2026-09-09-awaited-agent-creation.zh.md` 第 9–17 行的决策描述；这里只做白话转述）。

1. 有人过来说：「给我一个 agent，身份是 `<id>`，用某个模型」。
2. 服务发现自己不会造，于是去找**当前登记的那个造 agent 的人**（工厂）。没人登记就直接报错。
3. 造 agent 的人先把「这个身份的会话」准备好，如果挂了持久化后端，就**先把写权限拿到手**（这样同一个 id 不可能被两个人同时恢复）。
4. 然后造出循环对象和一个「只属于这个 agent 的登记处」。
5. **在造出任何东西之前**，先把「万一要拆，怎么拆」这张清单挂到工厂和调用方身上——这样即使后面的准备工作中途出事，也有一份能用的拆除清单。
6. 调用方给的准备工作（`setup`）在这里跑：往那个专属登记处里塞工具、提示词段、监听器。**此时外面什么都看不到**——两个 id 都还没登记、也还没广播。
7. 准备工作跑完，把会话和 agent 分别塞进两张表，然后**按顺序广播**「会话建好了」「agent 建好了」。广播是**排队执行**的：一个监听器做完才轮到下一个；有人抛出异常，创建就失败。
8. 成功就把「agent + 拆除钥匙」交给调用方。失败就按第 5 步那张清单退回去，并且给**已经广播过的那一半**补一条「已销毁」通知。

→ 这一整套之所以要这么绕，全是为了**「外面的世界永远看不到半成品」**。§7 会从源码逐条对上。

## 3. 结论先行（十条，与出处一一对应）

1. **句柄是「一次创建事务」的产物，不是一个对象包装**：`AgentHandle` 只有两个字段 `agent` 与 `dispose()`（`packages\core\agent\src\index.ts` 第 146–163 行）。`dispose()` 是 capability——消费方中只有持有者能拆除这个 agent；`ctx.agents.get(id)` 只给裸 `Agent`（同文件第 155–158 行；`packages\core\agent\README.zh.md` 第 117 行）。
2. **`Agent` 的公开面是「两步声明」出来的**：`types.ts` 只声明 `readonly id: SessionId`（`packages\core\agent\src\types.ts` 第 14–18 行），`runtime-types.ts` 用 `declare module './types.ts'` 合并进 `options` / `session` / `inbox` / `status` / `ctx` 与 7 个方法（`packages\core\agent\src\runtime-types.ts` 第 163–243 行）。运行时实现是 `ReactLoopAgent implements Agent`（`packages\core\agent-loop\src\agent.ts` 第 98 行）。
3. **接口在 `dsh-agent`，构造与驱动在 `dsh-agent-loop`**：循环在装配期用 `ctx.agents.setFactory(this)` 把工厂塞进注册表（`packages\core\agent-loop\src\index.ts` 第 369 行；接口定义见 `packages\core\agent\src\index.ts` 第 165–203 行），于是消费方依赖 `dsh-agent` 而不依赖具体循环，驱动器可替换（`packages\core\agent\README.zh.md` 第 81 行；`docs\subsystems\core.zh.md` 第 20 行）。
4. **外部改不动的不是「句柄」，而是「驱动实现」**：`ReactLoopAgent` 类只在 agent-loop 包内被引用，包 `exports` 只暴露 `.` 与 `./package.json`（`packages\core\agent-loop\package.json` 第 16–22 行）；外部要作用于进行中的工作，走 `agent/*` 事件而不是循环对象（`packages\core\agent\README.zh.md` 第 65–67 行）。
5. **`create` 与 `resume` 的差别是「身份从哪来」**：`create` 要 `sessionId`（+ 可选 `meta` / `seed` / `inheritedEventCount`），`resume` 要 `resumeSessionId`，且必须先挂载 `ctx.sessionPersistence`，否则直接抛错（`packages\core\agent\src\index.ts` 第 63–119 行、第 125–144 行；`packages\core\agent-loop\src\index.ts` 第 807–813 行）。
6. **两者的发布与回滚走同一条路**：都汇入 `setupAndPublish()` → `prepare()` → `initializeAgent()`（`packages\core\agent-loop\src\index.ts` 第 754–799 行），只有 `SessionStartSource` 不同：`'startup'` 与 `'resume'`（同文件第 744 行、第 879 行；`packages\core\agent\src\runtime-types.ts` 第 124–125 行）。
7. **回滚的理由是「不让观察者看到半配置的世界」**：setup 在 `agentCtx` 铸造之后、两个 id 发布之前 await（`packages\core\agent\src\index.ts` 第 100–112 行），任何一步失败都要把已准备的资源退回，并为**已送达**的宣告补上配对销毁（`2026-09-09-awaited-agent-creation.zh.md` 第 29 行）。
8. **teardown 顺序的权威定义在 agent-loop**：`docs\architecture.zh.md` 第 82 行把顺序归属明确交给 agent-loop；代码唯一实现在 `packages\core\agent-loop\src\index.ts` 第 523–571 行，文字表述在 `packages\core\agent-loop\README.zh.md` 第 110 行。
9. **顺序是「排空 → 作用域 → 会话写路径 → detach agent → detach 会话」**（第 8 点的 README 句），且 detach 绑定到确切 entry，陈旧 disposer 不会误删同 id 的后来者（`packages\core\agent\src\index.ts` 第 496–510 行）。
10. **`agent/status` 只有两个值**，`dispose` 不是第三种状态（`packages\core\agent\src\runtime-types.ts` 第 102–109 行；`docs\subsystems\core.zh.md` 第 197 行）。

## 4. 机制一：句柄只有两个字段，拆除是唯一被垄断的能力

### 4.1 源码对照 ①：`AgentHandle` 与它的作者注释

`packages\core\agent\src\index.ts` 第 146–163 行 — 这就是本课的主角，整块只有 18 行，没有省略。

```ts
/**
 * An owned agent plus its disposer, returned by {@link AgentRegistry.create} /
 * {@link AgentRegistry.resume}. The disposer is a CAPABILITY: among consumers,
 * only the holder can tear this agent down. The registered factory provider is
 * also a structural owner because the scoped agent depends on that provider's
 * service API; provider unload stops and drains every live handle it made.
 * `dispose()` stops the loop, awaits its exit, unregisters the agent, removes
 * its session from the store, and finally unwinds its scoped world.
 *
 * `ctx.agents.get(id)` still returns a bare {@link Agent} — the handle is
 * exposed only to the consumer owner that created it; the structural provider
 * reaches the same teardown internally. Config-created agents (the loop's own
 * startup) are owned by the loop fiber and never need a handle.
 */
export interface AgentHandle {
  agent: Agent
  dispose(): Promise<void>
}
```

**做什么**：定义一个只有两件事的对象——「哪个 agent」和「怎么拆掉它」。它**不是** `Agent` 的包装层，也没有额外状态。

**与哪个知识点相关**：§3 第 1 条，以及附录 A 第 ② 题的关键——「唯一被句柄垄断的能力是拆除」。

**为什么这么写**：注释用的是标准语汇 *CAPABILITY*（能力），并点明「**among consumers, only the holder can**」——这是**授权**语义，不是「方便」语义。紧接着补了一句容易漏掉的事实：**注册表的工厂提供方也是结构性共同拥有者**，理由写得很直白——*the scoped agent depends on that provider's service API*（这个 agent 的作用域世界依赖提供方的服务 API）。所以句柄的独占性只在「消费方之间」成立，提供方卸载时仍然会把它造的每个句柄拆掉（对应 `packages\core\agent\README.zh.md` 第 117 行）。

**关键事实：`get(id)` 不给句柄。** 这句话写在同一段注释里（*still returns a bare Agent*），源码也如此：第 566–568 行的 `get()` 返回 `this.store.get(id)?.agent`。所以「只有持有者能拆」是**能力上的**，不是「别人看不到这个 agent」。

### 4.2 源码对照 ②：`Agent` 的两步声明（身份 vs 实时能力）

`packages\core\agent\src\types.ts` 第 14–25 行 — 身份声明 + 活动类型合并，只有 12 行。

```ts
/** Public live-agent handle; the runtime face augments its live capabilities. */
export interface Agent {
  /** Session-backed Agent identity. */
  readonly id: SessionId
}

declare module '@deepseek-ai/dsh-workspace/types' {
  interface SessionActivityKindMap {
    /** The session's own Agent is inside a turn, including one waiting for an approval or an answer. */
    turn: true
  }
}
```

`packages\core\agent\src\runtime-types.ts` 第 163–183 行 — 属性合并，**省略第 184–241 行的 7 个方法声明**（`cancel` 到 `inject`，与 §4.3 的知识点无关，那段在附录 A 第 ① 题里按行号列出）。

```ts
declare module './types.ts' {
  interface Agent {
    /** The provider route and model this agent's requests use. */
    readonly options: AgentOptions
    /** The live session this agent drives; its log is the durable source of truth. */
    readonly session: Session
    /** Agent-owned access to durable pending work. */
    readonly inbox: Inbox
    /** The current lifecycle state, mirrored on every `agent/status` transition. */
    readonly status: AgentStatus
    /** Agent-scoped context; its contributions are agent-local, unwind on disposal, and reject registration afterward. */
    readonly ctx: Context

    /** …（第 184–241 行：cancel / whenIdle / runMaintenance / send / followup / steer / inject 七个方法声明，此处省略） */
  }
}
```

**做什么**：把「一个 agent 是什么」拆成两次声明。`types.ts` 只放**身份**（`id`），`runtime-types.ts` 用 TypeScript 的 `declare module` 合并把**实时能力**补上去。

**与哪个知识点相关**：§3 第 2 条。

**为什么这么写**：作者在合并块上一行留了理由（摘句）：**"Public live-agent handle; the runtime face augments its live capabilities."** 即：`id` 是**持久/跨端**的身份，谁都能引用；`session` / `inbox` / `status` / `ctx` 只有**进程内的实时对象**才给得出。这个拆分不是审美，它有一个可观察后果：`types.ts` 还被合并进 Workspace 的活动类型表（第 20–25 行 `turn: true`），Client 端渲染只要 `dsh-agent/types` 就够了，不必把整个运行时类型图拖进来。

### 4.3 源码对照 ③：句柄实际被怎么用

`packages\core\agent\README.zh.md` 第 34–41 行 — 仓库内公开文档里的用法示例（原样摘录，未做改动）。

```text
const handle = await ctx.agents.create({
  sessionId,
  agentOptions: { provider: 'deepseek', model: 'deepseek-chat' },
})
// later:
await handle.dispose()   // stops the loop, unregisters, removes the session, unwinds the scope
```

**做什么**：这是句柄唯一的常规用法——`await ctx.agents.create(...)` 拿句柄，用完 `await handle.dispose()`。

**与哪个知识点相关**：§3 第 1 条、第 5 条。

**为什么这么写**：`dispose()` 的四件事被写进这一行行内注释（*stops the loop, unregisters, removes the session, unwinds the scope*），与 `index.ts` 第 152–153 行的 JSDoc 完全一致，也与 §8 的 teardown 顺序表逐项对应。注意 `provider` / `model` 是**占位示例值**，不是某个人的配置。

> ⚠️ 观察：`dispose()` 是 `Promise<void>`，**必须 await**。§8.3 的测试用例（`packages\core\agent-loop\tests\scope-lifecycle.spec.ts` 第 1052–1071 行）专门断言了「owner 卸载已经先开始时，并发的 `handle.dispose()` 不能提前 resolve」——即两次拆除共享同一个静稳边界。

## 5. 机制二：谁声明接口，谁提供实现

### 5.1 源码对照 ④：工厂接口就放在 `dsh-agent` 里

`packages\core\agent\src\index.ts` 第 165–190 行 — 定义 + 第一个方法。**省略第 191–202 行的 `resume` 方法及其 JSDoc**（结构与本方法对称，没有独立知识点）。

```ts
/**
 * The agent-creation factory the loop implementation provides to the registry
 * via {@link AgentRegistry.setFactory}. Kept on the `dsh-agent` interface so
 * consumers (e.g. the ACP bridge) program against `ctx.agents` without
 * depending on the concrete `dsh-agent-loop` package.
 */
export interface AgentFactory {
  /**
   * Create a new agent on a caller-supplied session id. Async because creation
   * awaits unpublished setup, invokes its optional synchronous commit, inserts
   * both session and agent, announces session creation, and awaits serial
   * `agent/created` listeners before releasing queued work. The sequence is
   * rollback-covered, but notifications delivered before a later listener
   * failure remain observable; every agent or session creation announcement
   * that began is paired by `agent/disposed` or `session/disposed` during
   * rollback. The owner disposes the resolved handle to stop/drain,
   * unregister, remove the session, and unwind the scope.
   * The registry passes a context carrying the `create()` caller's fiber and
   * scope as `ownerCtx`. The implementation attaches the unpublished
   * transaction and resulting lifecycle to that owner; it must not infer
```

### 5.3 源码对照 ⑥：工厂槽位只允许一个，且它的 disposer 身份是承重的

`packages\core\agent\src\index.ts` 第 346–374 行 — `setFactory` 全文，无省略。

```ts
  /**
   * Register the agent-creation factory (the loop calls this on construction,
   * effect-scoped). A traced Cordis service is canonicalized to its concrete
   * target; each create/resume call is then traced through that caller's
   * context so ownership follows the caller without stacking proxy layers.
   * Throws if a factory is already registered. Returns the disposer; on
   * dispose the factory slot is cleared.
   * @param factory - the loop-owned factory {@link create}/{@link resume} delegate to.
   * @returns the disposer that clears the factory slot. The exact
   *   Cordis effect disposer (single-shot): composite (generator) effects may
   *   yield it directly — exact identity nests the teardown in order.
   */
  setFactory(factory: AgentFactory): () => void {
    const dispose = this.ctx.effect(() => {
      if (this.factory !== undefined) throw new Error('an agent factory is already registered')
      // Avoid stacking two Cordis shadow layers when a caller passes a Service
      // already read through a context. Calls are re-traced through their
      // actual owner context below.
      const target = (factory as AgentFactory & { [symbols.original]?: AgentFactory })[symbols.original] ?? factory
      this.factory = { target }
      return () => { this.factory = undefined }
    }, 'agents.setFactory()')
    // The exact cordis effect disposer (the agents.register() convention): a
    // caller's composite effect can yield it for in-order teardown; the
    // loop's constructor effect returns it directly, identity-nesting the
    // registration under that effect.
    // oxlint-disable-next-line typescript/no-misused-promises -- synchronous cleanup; direct return preserves disposer identity
    return dispose
  }
```

**做什么**：登记唯一一个工厂。重复登记直接抛 `'an agent factory is already registered'`；返回的 disposer 一执行就把槽位清空。

**与哪个知识点相关**：§3 第 3 条；附录 A 第 ② 题最后一段（「换驱动器的方式是注册另一个 `AgentFactory`」）。

**为什么这么写**：两条注释都值得抄下来。第一条解释 `symbols.original` 解包：*Avoid stacking two Cordis shadow layers*——传入的如果是从上下文里读出来的 Service，要先**规范化回它的真实对象**，否则每调用一次就套一层代理。第二条解释**为什么直接 `return dispose` 而不是包一层**（摘句）：*exact identity nests the teardown in order*。即：这个 disposer 的**身份本身**是承重的——调用方的复合 effect 把它 `yield` 出去，Cordis 才能把「清空工厂槽位」嵌在**正确的位置**上。包一层包装函数虽然行为一样，但会让它在 owner 卸载时变成**并发兄弟节点**，拆除顺序就乱了。

**这条纪律在别处重复出现**：`register()`（第 429–436 行）用几乎一样的措辞讲同一件事——*Exact identity is load-bearing*。所以本课把它当成一条通用规则记住：**在 DSH 里，disposer 的身份（而不是它的行为）经常是承重的。**

### 6.2 源码对照 ⑩：`setupAndPublish` 与 `initializeAgent`

```ts
  /** Prepare one Agent around an acquired Session, run setup, and publish it. */
  private async setupAndPublish(
    ownerCtx: Context,
    id: SessionId,
    preparation: SessionPreparation,
    agentOptions: AgentOptions,
    setup: AgentSetup | undefined,
    signal: AbortSignal | undefined,
    source: SessionStartSource,
    stored?: StoredSession,
    parentAgent?: Agent,
  ): Promise<AgentHandle> {
    using ownedPreparation = preparation
    const session = ownedPreparation.session
    let prepared: PreparedAgent
    try {
      prepared = this.prepare(ownerCtx, id, agentOptions, session, signal, stored?.handle, parentAgent)
    } catch (error: unknown) {
      await stored?.handle.close().catch(() => {})
      throw error
    }
    return await this.initializeAgent(prepared, async () => {
      const setupCommit = await raceAbort(setup?.(prepared.agent.ctx, prepared.agent), prepared.signal, id)
      setupCommit?.commit()
      await this.appendUnstoredSuffix(stored, session)
      return await prepared.publish(source)
    })
  }

  private async initializeAgent(prepared: PreparedAgent, initialize: () => Promise<AgentHandle>): Promise<AgentHandle> {
    try {
      return await prepared.agent.runMaintenance(async () => {
        try {
          return await initialize()
        } catch (error: unknown) {
          // Teardown owns inbox cleanup and may already have removed its projection.
          prepared.agent.cancel({ kind: 'disposed' }, { keepInbox: true })
          throw error
        }
      })
    } catch (error: unknown) {
      // Rollback swallows a disposal rejection (a failing final handle close):
      // the setup failure is the primary error the caller must see.
      await prepared.dispose().catch(() => {})
      throw error
    }
  }
```

## 7. 机制四：注册表里的「拆开的插入/宣告对」

### 7.1 源码对照 ⑫：`enter()` 与它返回的 detach 闭包

`packages\core\agent\src\index.ts` 第 459–494 行 — `enter` 全文。**省略第 444–458 行的 JSDoc**（关键那句已在下方引用）。

```ts
  enter(agent: Agent, owner: Agent | undefined): () => void {
    const id = agent.id
    if (id !== agent.session.id) {
      throw new Error(`agent id "${id}" does not match session id "${agent.session.id}"`)
    }
    const carrier = scopeTarget(agent, agent)
    // This is the authoritative collision boundary. Concurrent create/resume
    // operations may both prepare, but only one exact entry can publish.
    if (this.store.has(id)) throw new Error(`agent "${id}" is already registered`)
    const entry: AgentEntry = {
      id,
      agent,
      owner,
      carrier,
      announced: false,
      announcing: false,
      detachRequested: false,
    }
    this.store.set(id, entry)
    let entered = true
    const detach = (): void => {
      if (!entered) return
      entered = false
      // Every callback reached by this creation dispatch must observe the same
      // live entry, and disposal must follow creation. A listener may own
      // the advanced detach capability, so make that ordering structural:
      // visibility and the paired disposal are deferred until announce()'s
      // serial dispatch has settled.
      if (entry.announcing) {
        entry.detachRequested = true
        return
      }
      this.detachEntered(entry)
    }
    return detach
  }
```

**依赖的变量从哪来**：`agent` 是准备好的 `ReactLoopAgent`；`owner` 是 `options.parentAgent`（可为 `undefined`，表示运行时根）；`carrier` 由 `scopeTarget(agent, agent)` 造出，用于作用域过滤分发；三个布尔在 `AgentEntry`（第 211–220 行）里声明。

**做什么**：把 agent 放进表里，**但一声不吭**；返回一个「幂等的 detach 闭包」。三处守卫各管一件事：id 与会话 id 不一致 → 抛错；同 id 已在表里 → 抛错（注释称它 *the authoritative collision boundary*）；宣告**正在进行中**时请求 detach → 只置 `detachRequested = true`，**不立刻删**（第 487–490 行）。

**与哪个知识点相关**：§3 第 9 条；§7.2；附录 A 第 ④ 题。

**为什么这么写**：注释把理由写得像论文摘要（摘句）：*disposal must follow creation … make that ordering structural*。也就是说，**「销毁必须排在创建之后」不是靠调用者自觉，而是被做成了结构**：一旦进入 `announcing` 状态，删除请求只能排队，等宣告分发结算后才执行。这正是 `packages\core\agent\tests\agent.spec.ts` 第 208–224 行测试的对象——断言序列是 `['first:true', 'after-detach:true', 'second:true', 'disposed']`：**监听器里请求 detach 之后，同一次分发中的后续监听器仍然看得到这个 entry**。

**配套：未宣告就不发销毁边。** `detachEntered()`（第 496–510 行）在真正删除时会检查 `if (!entry.announced) return`——注释原文：*An insertion rolled back before announce was never externally created, so emitting disposed would invent an impossible lifecycle edge.*（**在宣告前回滚的插入从未被外部创建过，发 `agent/disposed` 等于发明一条不可能的生命周期边。**）同时它用 `if (this.store.get(entry.id) !== entry) return` 把「陈旧 capability」挡在外面。

### 7.2 源码对照 ⑬：`announce()` 与 `emitDisposed()`

`packages\core\agent\src\index.ts` 第 537–559 行 — `announce` 全文。

```ts
  async announce(agent: Agent, source: SessionStartSource, signal?: AbortSignal): Promise<void> {
    const entry = this.store.get(agent.id)
    if (entry === undefined || entry.agent !== agent) {
      throw new Error(`agent "${agent.id}" is not live in this registry`)
    }
    if (entry.announced || entry.announcing) {
      throw new Error(`agent "${entry.id}" was already announced`)
    }
    // Mark before dispatch so a listener cannot recursively create a second
    // lifecycle edge; detach still pairs a partially delivered first edge.
    entry.announcing = true
    entry.announced = true
    try {
      await this.ctx.serial(entry.carrier, 'agent/created', {
        agent: entry.agent,
        source,
        ...signal === undefined ? {} : { signal },
      })
    } finally {
      entry.announcing = false
      if (entry.detachRequested) this.detachEntered(entry)
    }
  }
```

`packages\core\agent\src\index.ts` 第 512–525 行 — `emitDisposed` 全文。

```ts
  /** Emit the paired disposal edge through the entry's stable carrier. */
  private emitDisposed(entry: AgentEntry): void {
    const args: unknown[] = [entry.carrier, 'agent/disposed', { agent: entry.agent }]
    for (const callback of this.ctx.events.dispatch('emit', args)) {
      try {
        const returned: unknown = callback(...args)
        void Promise.resolve(returned).catch((error: unknown) => {
          this.ctx.logger.warn(`agent "${entry.id}": agent/disposed listener rejected: ${String(error)}`)
        })
      } catch (error: unknown) {
        this.ctx.logger.warn(`agent "${entry.id}": agent/disposed listener threw: ${String(error)}`)
      }
    }
  }
```

**依赖的变量从哪来**：`entry` 由 `agent.id` 从 `this.store` 查出；`source` 来自工厂（`'startup'` / `'resume'`）；`signal` 来自 `prepare()` 的融合信号；`this.ctx.serial` 是 Cordis 的**串行**分发（一个监听器 await 完才轮到下一个）。

**做什么**：`announce` 做四件事——确认这个 agent **就是当前活着的那一条 entry**（`entry.agent !== agent` 也拒绝）、拒绝重复宣告、**先把两个布尔标记好再分发**、`finally` 里收尾（清 `announcing`，有排队 detach 就执行）。`emitDisposed` 则逐个容纳监听器的同步抛错与 Promise 拒绝，只记 warn。

**与哪个知识点相关**：§3 第 7、9 条；附录 A 第 ④ 题。这两块合起来解释了「为什么必须有配对销毁」以及「为什么销毁通知不能失败」。

**为什么这么写**：三处注释逐字对应三条纪律。①*Mark before dispatch so a listener cannot recursively create a second lifecycle edge*——先标记后分发，**防止监听器递归造出第二条生命周期边**。②*detach still pairs a partially delivered first edge*——即使分发中途失败，**已送达的那半条边仍然配得上销毁**。③`emitDisposed` 里为什么手动 `for` 循环而不是直接用 Cordis 的 `emit`？因为**销毁通知不能有否决权**：一个监听器抛出不能饿死后面的监听器（这与 `packages\core\agent\src\dispatch.ts` 第 120–137 行的 `emit` 注释是同一句话：*one synchronous throw starves later listeners*）。

**可执行验证**：`packages\core\agent\tests\agent.spec.ts` 第 118–129 行断言监听器抛出后 `lifecycle` 恰好是 `['created:vetoed', 'disposed:vetoed']`（**宣告过就一定要配一次销毁**）；第 131–152 行断言销毁监听器无论同步抛错还是异步拒绝都只变成两条 warn，且后续监听器仍被调用（`heard` 等于 `['contained']`）。

## 8. 机制五：回滚与 teardown 顺序

### 8.1 源码对照 ⑭：`prepare()` 里的 abort 融合与记忆化 `dispose`

`packages\core\agent-loop\src\index.ts` 第 500–571 行 — 本课最长的一块，**省略第 473–499 行的 JSDoc 与前置校验**（那些是签名和「调用方必须以未 aborted 状态进入」的守卫），以及第 572–596 行（`untrack` 与 owner effect）。

```ts
    const loopCtx = this.runtime.ctx

    // Deactivation fuses three owners, each with its own reason: the caller's
    // cancellation signal, the owner fiber's unload, and factory teardown.
    // It is registered BEFORE any resource exists, over mutable slots, so an
    // unload arriving while the scope is still minting finds a working
    // disposer instead of a leak.
    const abort = new AbortController()
    const onCallerAbort = (): void => {
      abort.abort(callerSignal?.reason instanceof Error
        ? callerSignal.reason
        : new Error(`agent "${id}" creation aborted`, { cause: callerSignal?.reason }))
    }
    const onFactoryTeardown = (): void => { abort.abort(this.ownership.signal.reason) }
    callerSignal?.addEventListener('abort', onCallerAbort, { once: true })
    this.ownership.signal.addEventListener('abort', onFactoryTeardown, { once: true })

    let machine: ReactLoopAgent | undefined
    let detachSession: (() => void) | undefined
    let detachAgent: (() => void) | undefined
    let disposing: Promise<void> | undefined
    let publication: ReturnType<typeof Promise.withResolvers<void>> | undefined
    const machineReady = Promise.withResolvers<void>()
    // Reverse teardown, memoized so every racing owner awaits one quiescence:
    // stop the machine, drain and close the session's write path, leave the
    // registries, unwind the scope, release bookkeeping.
    const dispose = (ownerTriggered = false): Promise<void> => (disposing ??= (async () => {
      abort.abort(new Error(`agent "${id}" lifecycle disposed`))
      callerSignal?.removeEventListener('abort', onCallerAbort)
      this.ownership.signal.removeEventListener('abort', onFactoryTeardown)
      // Teardown failures are collected, never swallowed: registry, scope,
      // and ownership cleanup always run to quiescence, then the memoized
      // disposal rejects with what failed so every racing owner observes it.
      const failures: unknown[] = []
      try {
        // Creation listeners retain the session and scope through their awaits.
        if (publication !== undefined) await publication.promise
        // Disposal IS a disposed-cause cancel followed by quiescence. New work
        // sent after this point is the sender's bug — the registries are about
        // to drop the agent, so nothing should still hold it.
        /* v8 ignore next -- Cordis effect teardown waits for synchronous setup before observing the machine slot. */
        if (machine === undefined) await machineReady.promise
        /* v8 ignore next -- setup failure untracks this disposer before resolving without a machine. */
        if (machine !== undefined) {
          machine.cancel({ kind: 'disposed' })
          await machine.whenIdle()
          await machine.scope.dispose()
        }
      } catch (error: unknown) {
        failures.push(error)
      }
      // The loop above committed its closing events synchronously into the
      // session; handle close drains them durably before releasing the write
      // path. The close drain can be the first operation that surfaces a
      // durability failure, so its error is retained, not logged away.
      try {
        await handle?.close()
      } catch (error: unknown) {
        failures.push(error)
      }
      try {
        detachAgent?.()
        detachSession?.()
      } finally {
        untrack()
        if (!ownerTriggered) await unfollowOwner()
      }
      if (failures.length === 1) throw failures[0]
      if (failures.length > 1) {
        throw new AggregateError(failures, `agent "${id}" disposal failed`)
      }
    })())
```

**依赖的变量从哪来**：`callerSignal` 是 `options.signal`；`this.ownership.signal` 来自 `FactoryOwnership`（第 108–110 行，工厂拆除时 abort，reason 是 `new Error('agent loop is not active')`）；`machine` / `detachSession` / `detachAgent` / `publication` / `machineReady` 都声明在上方的**可变槽位**里，在 `dispose` 闭包之后才被赋值（第 572–596 行构造 machine 并注册 owner effect，`publish()` 里才赋 `detach*`）；`handle` 是 `prepare()` 的入参；`untrack` / `unfollowOwner` 是后面两条清理闭包。

**做什么**：这就是**第 8/9 条结论说的「代码唯一实现」**。拆除顺序逐项落在这里：`abort.abort(...)` 摘监听（第 527–529 行）→ 等发布结算（第 536 行）→ `cancel({ kind: 'disposed' })` + `whenIdle()`（第 544–545 行）→ `scope.dispose()`（第 546 行）→ `handle.close()`（第 556 行）→ `detachAgent()` / `detachSession()`（第 561–562 行）→ `untrack()` / `unfollowOwner()`（第 564–565 行）→ 失败聚合（第 567–570 行）。

**与哪个知识点相关**：§3 第 8、9 条；附录 A 第 ④ 题的「teardown 顺序的定义处」。

**为什么这么写**：三条注释给出了三条设计理由。①**为什么要在任何资源存在之前挂好 abort 监听**：*so an unload arriving while the scope is still minting finds a working disposer instead of a leak*（作用域还在铸造时到来的卸载，能找到一份可用的 disposer，而不是泄漏）。②**为什么 disposal 等价于「cancel + 静稳」**：*Disposal IS a disposed-cause cancel followed by quiescence*——注意 `cancel` 用的是 `{ kind: 'disposed' }`，且**不带** `keepInbox`，所以排队输入会被丢弃。③**为什么 `handle.close()` 的错误必须保留**：*The close drain can be the first operation that surfaces a durability failure, so its error is retained, not logged away.*（关闭时的排空可能是第一个暴露出持久化失败的操作。）

另外注意 `disposing ??= (async () => …)()` ——**记忆化**。多个 owner 竞争拆除时，它们 await 的是**同一个 Promise、同一个静稳边界**；`dispose(ownerTriggered)` 这个参数让 owner 触发的拆除跳过 `unfollowOwner()`（第 565 行），避免「已经跑着的 owner effect 从内部注销自己」。

**依赖的变量从哪来**：`phase` 是驱动器的私有状态字段（第 100 行 `private phase: Phase`），在构造函数里初始化为 `{ kind: 'idle', lastTurn }`（第 135 行）；`this.dispatch` 在构造函数里用 `agentEvents(loopCtx, this)` 建好一次复用（第 129 行），注释写着 *built once in the constructor so hot-path dispatches never allocate*。

**做什么**：`status` **不是独立字段**，而是从 `phase` 推导出来的；`setPhase` 先记旧状态、再改 phase、再算新状态，**只有真的变了才 emit**。

**与哪个知识点相关**：§3 第 10 条。

**为什么这么写**：两个设计决定都能从代码直接读出。①**`maintenance` 也算 `idle`**——所以维护任务运行期间，公开 `status` 仍是 `idle`（对应 `Agent.runMaintenance` 的 JSDoc：*while public status stays `idle`*）。②`setPhase` 里那次比较是**去重**：没有它，每次 phase 迁移都会广播一次 `agent/status`，而 `maintenance` ⇄ `idle`、`idle` ⇄ `running` 这类迁移在初始化与拆除路径上非常密集。

### 9.2 源码对照 ⑰：`cancel()` 与 `whenIdle()`

`packages\core\agent-loop\src\agent.ts` 第 175–181 行 + 第 237–242 行 — 两块之间**省略第 183–235 行**（`runMaintenance` 与 `wakeDriver`，属于 `3.5` 的状态机主题）。

```ts
  cancel(cause: AgentCancelCause, options: CancelOptions = {}): void {
    if (!options.keepInbox) {
      this.inbox.clear()
      if (this.phase.kind !== 'idle') this.phase.wakeRequested = false
    }
    if (this.phase.kind !== 'idle') this.phase.abort.abort(cause)
  }
```

```ts
  async whenIdle(): Promise<void> {
    let activity: Promise<void>
    do {
      await (activity = this.activityDone)
    } while (activity !== this.activityDone)
  }
```

**依赖的变量从哪来**：`this.phase.abort` 是该阶段自己的 `AbortController`；`cause` 是闭合联合 `'user' | 'parent' | 'disposed' | 'hook'`（循环只把这四类拷进 `turn/end` 记录，见 `abortedCancelCause()` 第 80–95 行）；`this.activityDone` 是「当前这轮活动结束时兑现」的 Promise，`wakeDriver()` 与 `runMaintenance()` 都会把它换成新的（第 193、226 行）。

**做什么**：`cancel` 三件事——不保留收件箱就清空并清掉 `wakeRequested`；**只有存在活动时才 abort**，否则什么都不做（`no-op`）。`whenIdle` 用一个 `do/while` 循环：**如果等的这段活动结束了、但期间又有新活动顶上来（`activityDone` 被换了），就继续等**。

**与哪个知识点相关**：§3 第 1 条的方法面；§8.3 顺序表第 3–4 步；附录 A 第 ① 题。

**为什么这么写**：`cancel` 的 `if (this.phase.kind !== 'idle')` 这一行同时实现两条语义——「无活动时是 no-op」与「不会武装后续工作」（因为 idle 时 `wakeRequested` 也没被动过）。`keepInbox: true` 的差别写在 `CancelOptions` 的 JSDoc 里（`packages\core\agent\src\runtime-types.ts` 第 39–44 行）：*The active turn is still aborted, but un-started and pending work survives for a later turn and no canceled inbox splice is logged.*
`whenIdle` 的循环写法是「跟随替代工作」的直接实现——它观察的是**整个 agent**，而不是某一条消息的结算（`runtime-types.ts` 第 185–191 行的 JSDoc 原文：*does not identify the settlement of any particular message*）。

**为什么 order 表里 `cancel` 与 `whenIdle` 挨着**：disposal 的定义就是「disposed 来源的 cancel + 静稳」（§8.1 注释原文 *Disposal IS a disposed-cause cancel followed by quiescence*），所以 `machine.cancel({ kind: 'disposed' })` 下一行紧跟 `await machine.whenIdle()`。

> 补充（`Phase` 的形态，方便你对照 `phase.kind` 的四个分支）：`type Phase` 定义在 `packages\core\agent-loop\src\agent.ts` 第 42–50 行，三个成员分别是 `{ kind: 'idle'; lastTurn }`、`{ kind: 'maintenance'; abort; lastTurn; wakeRequested }`、`{ kind: 'running'; abort; turn; step; wakeRequested }`。

## 附录 A 关键问题与答案

> ⚠️ **第一次读请跳过**：本节用到 `waterfall` / `serial` / `scope` / `fiber` / `effect` 等第二编词汇。

### ① Agent 句柄对外暴露哪些方法与语义？

**答案：`AgentHandle` 本身只有 `agent: Agent` 与 `dispose(): Promise<void>` 两个成员（`packages\core\agent\src\index.ts` 第 160–163 行）。真正的「方法面」在 `Agent` 上，共 7 个方法 + 6 个只读属性：**

- 属性：`id`（= session id，`types.ts` 第 14–18 行）、`options`、`session`、`inbox`、`status`、`ctx`（`runtime-types.ts` 第 165–174 行）。
- 方法：`cancel(cause, options?)`、`whenIdle()`、`runMaintenance(task)`、`send(message, target, wakeup)`，以及 `send` 的三个语义预设 `followup()` / `steer()` / `inject()`（`runtime-types.ts` 第 176–241 行）。
- 语义要点：`cancel` 同一活动内首个 cause 胜出、默认清空 inbox、`keepInbox: true` 只中止不丢弃、无活动时是 no-op（第 176–183 行、第 37–45 行；`packages\core\agent\README.zh.md` 第 177 行）；`whenIdle()` 观察的是**整个 agent**（含被观察驱动器退役前启动的替代工作），不是某条消息（第 185–191 行）；`runMaintenance` 只在真空闲期可启动，且公开 `status` 保持 `idle`（第 193–202 行）；`followup` 唤醒、`steer` 唤醒且在下一个步骤边界消费、`inject` 不唤醒（第 217–241 行）。
- 附带面：`Agent.inbox: Inbox` 提供 `nextTurn` / `nextStep` 只读投影与 `clear` / `append` / `prepend` / `replace` / `remove` / `splice`（`runtime-types.ts` 第 47–100 行）。
- 句柄的**能力语义**：`dispose()` 只给创建者；`get(id)` 给裸 `Agent`；注册表工厂提供方是**结构性共同拥有者**，卸载即拆除它造出的每个句柄（`packages\core\agent\src\index.ts` 第 146–163 行、第 155–158 行）。
- 「7 个方法」的核对方式：在 `packages\core\agent\src\runtime-types.ts` 的 `declare module './types.ts'` 块（第 163–243 行）里，形如「标识符 + 参数表 + 返回类型」的**方法**成员声明恰好 7 条（`cancel` 183、`whenIdle` 191、`runMaintenance` 202、`send` 215、`followup` 222、`steer` 231、`inject` 241）；同一块里的 `readonly …`（属性）恰好 5 条（165–174），加上 `types.ts` 第 17 行的 `id`，共 **6 个只读属性**。

### ② 为什么外部只能通过句柄与 agent 交互，而不能直接操作 loop？

**答案：因为「循环」从来不是公开 object，而是一个可替换的工厂实现；对外稳定的是 `ctx.agents` + `Agent` 接口 + `agent/*` 事件这三件东西。** 四条理由逐条有据：

1. **依赖倒置是刻意的**：公开 `Agent` 接口与注册表在 `dsh-agent`，构造与驱动在循环包，循环通过 `setFactory()` 提供工厂；消费方因此依赖 `dsh-agent` 而不依赖 `dsh-agent-loop`，驱动器可替换（`packages\core\agent\README.zh.md` 第 81 行；`packages\core\agent\src\index.ts` 第 165–203 行；`packages\core\agent-loop\src\index.ts` 第 369 行）。
2. **具体驱动类物理上拿不到**：`ReactLoopAgent` 仅在包内被引用（grep 11 处全在 `packages/core/agent-loop` 内），包的 `exports` 只暴露 `.` 与 `./package.json`（`packages\core\agent-loop\package.json` 第 16–22 行），`src/index.ts` 不导出该类。文档也把这条写成结论：「具体实现为 dsh-agent-loop 包内部细节；循环外没有任何组件依赖它」（`docs\subsystems\core.zh.md` 第 59 行）。
3. **能力被收进窄接口**：投递 / 取消 / 静稳 / 维护都落在 `Agent` 的 7 个方法上，待处理工作只暴露结构性 `Inbox`，包内部的 `ReactLoopInbox` 不导出（`packages\core\agent\README.zh.md` 第 89 行；`packages\core\agent-loop\README.zh.md` 第 118 行）。
4. **扩展点走事件而不是对象**：`agent/*` 事件让插件无需依赖循环包即可作用于实时工作——`agent/pre-step` 能否决 / 改写步骤、`agent/request-error` 可重试失败的模型请求、`agent/turn-stopping` 能被 steer 保持轮次打开（`packages\core\agent\README.zh.md` 第 67 行；签名与 mode 见 `packages\core\agent\src\runtime-types.ts` 第 320、337、353、381 行）。

**精确化（这条很重要）**：说「只能通过句柄」并不准确——`ctx.agents.get(id)`、`list()`、`roots()` 任何人都能拿到裸 `Agent` 并调 `followup` / `cancel` / `steer`。**唯一被句柄垄断的能力是拆除**（`dispose()`），因为它是 capability：只有持有者能拆（`packages\core\agent\src\index.ts` 第 146–163 行；`packages\core\agent\README.zh.md` 第 117 行）。而「不能直接操作 loop」的真正含义是：**你不能把 agent 换成自己的驱动器、也不能绕过 `Agent` 接口去触碰 `ReactLoopAgent` 内部状态**；换驱动器的方式是注册另一个 `AgentFactory`（`setFactory` 只允许一个，重复注册抛错，`packages\core\agent\src\index.ts` 第 358–367 行；测试见 `packages\core\agent\tests\agent.spec.ts` 第 336–346 行）。

### ③ `create` 与 `resume` 的差别？

**答案：差别集中在「身份与历史从哪来」，以及「是否需要持久化后端」；发布、setup、回滚、teardown 完全共用一条路径。** 逐维度对照见 §6.4 的表；三段源码见 §6.1（`createAgent`）、§6.2（`setupAndPublish` / `initializeAgent`）、§6.3（`resume`）。

一句话：`create` 是「给你一个新身份并建会话」，`resume` 是「把一个持久身份重新装载成实时 agent」，并且 `resume` 的成功前提比 `create` 多一个（持久化后端）。

### ④ agent 创建的初始化为什么会回滚？teardown 顺序在哪定义？

**答案：回滚是因为初始化的产物会被「外部可观察的发布动作」分成前后两半——setup 期间不可见，一旦 `enter` / `announce` 就再也收不回；任何失败都必须把前半段准备好的资源退回，并为已经送达的宣告补上配对销毁。**

- **回滚的触发面**：setup 抛出 / 拒绝、setup 返回的 `commit()` 抛出、owner dispose（`packages\core\agent\src\index.ts` 第 100–112 行、第 136–141 行），以及串行 `agent/created` 监听器抛出（`packages\core\agent\src\runtime-types.ts` 第 248–261 行；awaited-agent-creation 第 13、29 行）。
- **为什么不可「不回滚」**：setup 被刻意安排在 `agentCtx` 铸造之后、两个 id 插入 / 宣告之前，就是为了让观察者看不到半配置的世界（第 101–107 行）；而通知送出后无法撤回，所以必须配对销毁（`packages\core\agent-loop\README.zh.md` 第 110 行）。反例保护也在代码里：`announce()` 先置 `announcing` / `announced` 再分发，`detach` 在宣告中只做标记、等分发结算才真正移除（`packages\core\agent\src\index.ts` 第 542–558 行）——测试 `packages\core\agent\tests\agent.spec.ts` 第 208–224 行断言 `['first:true','after-detach:true','second:true','disposed']`。
- **回滚动作**：`agent.cancel({kind:'disposed'},{keepInbox:true})` → `prepared.dispose().catch(()=>{})`，且回滚吞掉 disposal 的 rejection 以便让 setup 错误成为主错误（`packages\core\agent-loop\src\index.ts` 第 782–799 行）；`prepare()` 的 catch 分支同理（第 634–639 行）；用于创建的未物化写句柄会被 close，使同 id 可再次创建（第 668–687 行注释 + 第 770–773 行）。
- **teardown 顺序的定义处**：文档层是 `docs\architecture.zh.md` 第 82 行（明确归属 agent-loop）与 `packages\core\agent-loop\README.zh.md` 第 110 行（文字顺序）；**代码层唯一实现**是 `packages\core\agent-loop\src\index.ts` 第 523–571 行的记忆化 `dispose`：排空（`cancel({kind:'disposed'})` + `whenIdle()`，第 544–545 行）→ 撤销作用域（第 546 行）→ 关闭会话写路径（`handle.close()`，第 556 行）→ detach agent → detach session（第 561–562 行）→ 记账收尾（第 564–565 行），失败聚合后抛出（第 567–570 行）。**该顺序有可执行验证**：`packages\core\agent-loop\tests\scope-lifecycle.spec.ts` 第 1016–1050 行断言 `turn/end` 先于 `agent/disposed`，且 `agent/disposed` 时 `agents.get` 已为空而 `sessions.get` 仍在。
