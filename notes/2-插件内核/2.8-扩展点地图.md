## 0. 怎么读这一课（阅读许可）

### 0.1 这一课是什么、不是什么

**是**：一张**地图**。回答"我想加的那件事，该挂在哪个入口上"，并给出每个入口的**真实注册代码**。
**不是**：每个扩展点的完整机制讲解。工具流水线的细节在 `2.2`、事件分发在 `2.4`、作用域在 `2.5`、配置与 patch 在 `2.6`；本课只到"入口长什么样、为什么这么设计"为止。

### 0.2 现在只要记住这 4 件事

1. **扩展点只有两种形态**：**注册式**（调用某个 `ctx.<服务>` 上的方法，把条目放进注册表）与**事件式**（`ctx.on('<事件名>', listener)` 挂到既有流水线上）。
2. **两类都不改循环代码**。想加能力就找入口登记；想改行为就找事件挂监听器。
3. **每个注册都是一个可撤销的副作用**（`ctx.effect` → 返回 disposer），所以卸载插件时它加的东西会自动消失。
4. **另外还有一层不是插件 API 的扩展点**：装配层的 `profile` / `bundle` / `patch`。它决定"哪些插件行进入这棵树"，而不是"插件如何挂上去"。

### 0.3 明确授权：这些现在**不用管**

本课会出现一批你暂时不必弄懂的东西：**能力接缝（seam）的三种角色**、`realm` / `isolate`、preset、PTC mode 的 `run_code` 传输、Web Client 的 slot 体系、`SessionEventMap` 的合并语义细节。

判断标准只有一条：**只要能回答"这个入口属于上面 4 件事里的哪一件"，就够了。** 剩下的按附录 B 的术语索引去对应课看。

### 0.4 本课依赖的最小词汇

`ctx`（共享登记处）、`service`（`ctx.` 后面那一节具名能力）、`effect` / `disposer`（一次可撤销的副作用及其撤销函数）、事件分发模式（`waterfall` 必须调 `next()` 才委托下去；`emit` 只观察；`serial` 依次等待）——这五个说法在 `2.1`–`2.4` 已经定义，本课直接使用。

## 1. 最小词汇表（本课新增的 8 个词）

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **extension point 扩展点** | 一处**被官方承认的挂载位置**。挂在这里的行为不会被下次升级冲掉 | 文档里的「目标 → 机制」表；源码里对应的注册方法或事件名 |
| **注册式** | 你**主动把东西放进一个登记表** | `ctx.tools.register()`、`ctx.commands.register()`、`ctx.llm.registerAdapter()` |
| **事件式** | 你**在别人已有的流程上加一个监听器** | `ctx.on('tools/pre-execute', listener)` |
| **entry / 条目** | 登记表里的**一行** | 注册方法内部 `layer.xxx.insert(name, value)` |
| **waterfall** | 一种事件分发方式：监听器**必须调 `next()`** 才轮到后面的人；返回值是**决策** | 声明处 JSDoc 写 `@mode waterfall`，签名里带 `next` 参数 |
| **emit** | 只**观察**、返回值没人要的分发方式 | 声明处 JSDoc 写 `@mode emit` |
| **单调位（monotonic seat）** | 只能**否决**、不能反过来允许的登记位置 | `ctx.tools.guard()`（返回理由即拒绝） |
| **seat 坑位** | UI 侧的一个**具名可注册位置**（客户端插件往这里注册渲染器） | `ctx.slots.inject('conversation.chat.node', …)` / `ctx.slots.register(…)` |

> ⚠️ 这 8 个词里，`entry` 已在 `1.1` 定义过（这里只是复用），其余 7 个属第二编后半。"`seam`" 出现在本文里时一律按 `2.8` 的说法用：**一种可替换能力的整体**，它的三种角色细节留到第四编。

### 2.1 扩展点地图（静态结构）

```
                 插件（一个 apply(ctx) 函数）
                            │
        ┌───────────────────┴────────────────────┐
        │                                        │
   ① 注册式：往登记表放东西                 ② 事件式：往流程上挂监听器
        │                                        │
   ┌────┴─────────────────────┐          ┌───────┴────────────────────┐
   │ ctx.tools.register()     │          │ 会话事件 turn/* step/*      │
   │ ctx.commands.register()  │          │ agent 事件 agent/*          │
   │ ctx.llm.registerAdapter()│          │ 能力事件 tools/* fs/* …     │
   │ ctx.systemPrompt.section()          └───────┬────────────────────┘
   │ ctx.<seam>.register*()    │                  │
   └────┬─────────────────────┘                  │
        │                                        │
        ▼                                        ▼
   注册表（registry）                     既有流水线（循环、工具分发、请求）
        │                                        │
        └──────────────► 运行中的 agent loop ◄───┘

```

> **精确性说明一**：图里把"事件"画成第三块，严格说事件不是"装"在流水线里，而是**流水线在过程中发布出来的**；这里画成并列，只为让你看清两类扩展点的分界。
> **精确性说明二**：`profile` / `bundle` / `patch` 不在插件 API 里，它属于装配层（`1.2`、`2.6`）。把它画在同一张图上，是因为"扩展点再全，没被装进树也没用"。

### 2.2 白话版：想给 DSH 加一个新能力，实际会发生什么

**完全不用上面的术语**，先建立画面。来源：`docs\cookbook\extension-cookbook.zh.md` 第 7–35 行（工具插件与钩子插件两段示例）、第 108–136 行（"产品功能 → 插件机制"对照表）；这里只做白话转述。

1. 你有一个想法，比如"让模型能查公司内网"。
2. 你写一个小包，包里导出一个函数；装这个包的时候，系统会调用它一次，并把它**放进来的那个登记处**交给你。
3. 你在这段代码里**登记一件事**：一个名字、一段说明、一份参数的形状、以及"真正干活的那段代码"。
4. 登记处**立刻把它记下来**，并且**顺手给你一张收据**：想撤销，就凭这张收据来。
5. 从这一刻起，模型看到的工具清单里就多了一项——因为清单是从登记处现算出来的，不需要你再去改别的地方。
6. 如果这个包被卸载，系统会**按收据把这件事撤销**，清单自动缩回去。
7. 另一个常见的做法不是"加东西"，而是"**改已有的行为**"：你不新增工具，只是**在某个已经存在的检查点上排一个队**。轮到你的检查点时，你可以说"放行"、"拒绝"或者"先问人"。
8. 这两种做法**都不需要改循环本身的代码**——这是 DSH 敢说自己没有特权内核的原因。

## 3. 结论先行

### 3.1 两种形态

**扩展点只有两种形态，其余分类都是它们的实例。**

| 形态 | 做什么 | 谁提供 | 典型入口 |
|---|---|---|---|
| **注册式** | 调用某个 `ctx.<服务>` 上的方法，把条目放进注册表 | `core/tools`、`interaction/commands`、`llm/llm`、`core/system-prompt`、各 seam 服务 | `ctx.tools.register()`、`ctx.commands.register()`、`ctx.llm.registerAdapter()`、`ctx.systemPrompt.section()` |
| **事件式** | `ctx.on('<事件名>', listener)` 挂到既有流水线上，不改循环 | 三个事件域（会话事件 / Agent 事件 / 能力事件） | `tools/pre-execute`、`agent/pre-step`、`session/event` |

出处（文档）：`docs\architecture.zh.md` 第 74–84 行（事件三域与「事件就是扩展点」）、第 143–168 行（「目标 → 机制」对照表，把你想要的行为直接映射到扩展点）；`docs\cookbook\extension-cookbook.zh.md` 第 108–136 行（每个产品功能都映射到某个扩展点上的监听器）。

### 3.2 八类扩展点及入口（本步验收要求「至少 5 类」）

**另有一层不是插件 API 而是装配层的扩展点**：`profile` / `bundle` / `patch`。它决定「哪些插件行进入这棵树」，而不是「插件如何挂上去」（`docs\cookbook\extension-cookbook.zh.md` 第 98 行；`docs\architecture.zh.md` 第 27–29 行）。机制见 `1.2` 与本编 `2.6`。

### 3.3 三条硬结论

1. **没有任何一行修改循环本身**——新行为一律挂到已有扩展点上（`docs\cookbook\extension-cookbook.zh.md` 第 104 行）。
2. **一次注册就是一个 `ctx.effect`**，所以每个扩展点都随插件卸载而撤销、并且天然支持 HMR（同文件第 136 行；`packages\core\tools\src\index.ts` 第 1083–1087 行 `register()` 返回 disposer）。
3. **能力接缝（seam）是「三种角色的整体」，不是「一个接口」**——单一角色不构成接缝（`docs\architecture.zh.md` 第 137 行）。

## 4. 机制与源码对照

### 4.1 注册式扩展点的公共形状

三条形状约束，每条都有源码（下面 ①②③ 三块把"公共形状"钉死）：

- 由一个包声明 `ctx.<key>` 服务：`declare module '@deepseek-ai/cordis' { interface Context { … } }`
  （`packages\interaction\commands\src\index.ts` 第 113–117 行声明 `commands: CommandRuntime`；`packages\core\tools\src\index.ts` 第 137–140 行声明 `tools: ToolRuntime`）
- 服务类实现注册方法，内部用 `ScopedLayers` + `ctx.effect` 落地
  （`packages\core\tools\src\index.ts` 第 833–836 行 `new ScopedLayers(scope => new ToolLayer(scope), () => { this.ctx.emit('tools/change') })`；`packages\interaction\commands\src\index.ts` 第 264–267 行同构）
- 每个注册方法返回**精确的 disposer**，重复注册/非法输入**抛错**而不是静默覆盖
  （`packages\core\tools\src\index.ts` 第 746–748 行的去重错误文本；`packages\interaction\commands\src\index.ts` 第 179–225 行 `normalizeDefinition` 的全部校验）

#### ① 最典型的注册入口：`ctx.tools.register()`

`packages\core\tools\src\index.ts` 第 1057–1088 行

```ts
  /**
   * Register globally or in the calling agent scope. Scoped tools shadow
   * globals; duplicates within one layer and the reserved `run_code` name fail.
   * @param definition - tool schema, execution, and optional finalization/presentation callbacks.
   * @returns the exact disposer that unregisters the tool.
   */
  register(definition: ToolDefinition): () => void {
    const name = definition.name
    const output = (definition as Partial<ToolDefinition>).output
    if (output === undefined || typeof output !== 'object'
      || typeof output.render !== 'function'
      || (output.presentationMeta !== undefined && typeof output.presentationMeta !== 'function')) {
      throw new TypeError(`tool "${name}" must declare output { schema, render, presentationMeta? }`)
    }
    assertSupportedJsonSchema(output.schema)
    const timeoutMs = definition.timeoutMs
    if (timeoutMs !== undefined
      && (!Number.isFinite(timeoutMs) || timeoutMs <= 0)) {
      throw new TypeError(`tool "${name}" timeoutMs must be a positive finite number`)
    }
    // Reserved unconditionally: any agent may select a code mode for itself,
    // so a name free to take under the deployment default would become a
    // collision the moment a preset mounted.
    if (name === RUN_CODE_NAME) {
      throw new Error(`tool name "${RUN_CODE_NAME}" is reserved for the PTC mode presentation transport and cannot be registered or shadowed`)
    }
    return this.layers.effect(
      this.ctx,
      layer => layer.tools.insert(name, definition),
      { label: 'tools.register()' },
    )
  }
```

按块讲解：

- **做什么**：校验一份工具定义，然后把它插进"当前上下文所属的那一层"工具表。
- **与哪个知识点相关**：§3.2 第 2 类；§3.3 结论 2（返回 disposer）。
- **`definition` 从哪来**：调用方直接传（`docs\cookbook\extension-cookbook.zh.md` 第 9 行：`ctx.tools.register()` 直接接受原始 JSON Schema `ToolDefinition`；`defineTool` 只是第一方工具用的类型化辅助）。可运行的最小写法见 `packages\core\tools\README.zh.md` 第 43–59 行。
- **三处守卫，三种语义**：`output` 缺失/形状不对 → `TypeError`（**契约必填**，作者原文：`Mandatory canonical output declaration`，见第 224–225 行）；`timeoutMs` 不合法 → `TypeError`；名字等于 `RUN_CODE_NAME` → 直接拒绝。
- **为什么 `run_code` 无条件保留**：源码注释给了理由原文——*"any agent may select a code mode for itself, so a name free to take under the deployment default would become a collision the moment a preset mounted"*。这不是"当前模式下用不到所以先放过"，而是**任何 agent 都可能自己切模式**，所以从一开始就锁死。
- **为什么"重复注册抛错"而不是覆盖**：错误文本在第 746–748 行，原文后半句是 `(for a per-agent variant, register through that agent's \`agent.ctx\` instead)`——即**同名覆盖不是靠重复注册实现的，而是靠作用域遮蔽**（`2.5`）。
- **`this.layers.effect(this.ctx, …)` 的返回值**就是 disposer；`{ label: 'tools.register()' }` 是给诊断用的标签（1.1 的 `--dump-config` 与 HMR 输出里能看到同类标签）。

#### ② 同构的第二个注册入口：`ctx.commands.register()`

`packages\interaction\commands\src\index.ts` 第 258–292 行

```ts
/**
 * Human-command registry. Plain-context definitions are global; definitions
 * registered through a command-injected child of an agent context shadow
 * globals for that agent.
 */
export class CommandRuntime extends TypertRemoteService {
  private readonly layers = new ScopedLayers(
    scope => new CommandLayer(scope),
    () => { this.notifyChange() },
  )

  /** Monotonic per-instance counter behind {@link mintCommandId}. */
  private commandSeq = 0
  /** Instance token keeping minted ids unique across process restarts over one resumed log. */
  private readonly instanceToken = randomUUID().slice(0, 8)
  /** Optional provider installed by the Session upload owner. */
  private readonly fileReceipts: { resolver: CommandFileReceiptResolver | undefined } = { resolver: undefined }

  constructor(ctx: Context) {
    super(ctx, 'commands')
  }

  /**
   * Register a global or calling-agent-scoped command.
   * @param definition - discovery metadata and direct UI handler.
   * @returns the exact effect disposer that unregisters this definition.
   */
  register(definition: CommandDefinition): () => void {
    const registered = normalizeDefinition(definition)
    return this.layers.effect(
      this.ctx,
      layer => layer.commands.insert(registered.definition.name, registered),
      { label: 'commands.register()' },
    )
  }
```

按块讲解：

- **做什么**：把一份命令定义规范化后放进命令层；作用域规则与工具表**完全同构**（类文档注释原文：*"Plain-context definitions are global; definitions registered through a command-injected child of an agent context shadow globals for that agent."*）。
- **`super(ctx, 'commands')` 这一句就是 §3.2 里 `ctx.commands` 这个键的来源**——键名是代码里写死的字符串，不是文档起的名字（同 1.1 对 `ctx.sessions` 的结论）。
- **`layers` 从哪来**：构造时用 `new ScopedLayers(scope => new CommandLayer(scope), () => { this.notifyChange() })` 建立；第二个参数是"层变化时的通知回调"，对应事件 `commands/change`（`packages\interaction\commands\src\types.ts` 第 89 行，`@mode emit`）。
- **`normalizeDefinition` 做了什么**（第 179–225 行，本块只调用不展开）：校验名字匹配 `/^[a-z][a-z0-9_-]*$/u`（第 32 行）、`description` 非空、`handler` 是函数；然后 `Object.freeze` 出 `definition` 与 `descriptor` 两份（一份给执行，一份给发现 UI）。**非法输入在这里就抛错**，不会等到调用时才炸。
- **与工具的差别**：命令的注册表有一个额外的 `descriptor`（给 UI 列命令用），工具没有；其余形状（层、effect、disposer）一模一样。

#### ③ 服务 / seam 提供方的注册：`ctx.llm.registerAdapter()`

`packages\llm\llm\src\index.ts` 第 389–414 行

```ts
  registerAdapter(providers: string[], adapter: LlmAdapter): AdapterRegistrationHandle {
    // The routes this registration currently holds; `replace` rewrites it, and
    // the disposer releases whatever it holds at disposal time.
    const owned = new Set<string>()
    // The disposer has run: `owned` being empty cannot say so on its own,
    // because `replace([])` legally leaves a live registration holding none.
    let released = false
    const dispose = this.ctx.effect(function* (this: LlmRuntime) {
      if (providers.length === 0) throw new LlmError('an adapter must register at least one provider', 'INVALID_ADAPTER')
      this.commitRoutes(owned, this.prepareRoutes(providers, adapter, owned))
      yield () => {
        released = true
        for (const provider of owned) this.adapters.delete(provider)
        owned.clear()
        this.emitAdaptersUpdated()
      }
    }.bind(this), 'llm.registerAdapter()')
    // ctx.effect's disposer returns Promise<void>; our disposer API is
    // synchronous fire-and-forget — discard the (always-resolved) promise.
```

### 4.2 事件式扩展点：三个域 + 三种分发模式

三个域（`docs\architecture.zh.md` 第 78–80 行）：

| 域 | 性质 | 代表 | 判据 |
|---|---|---|---|
| 会话事件 | 持久、追加日志、经 `session/event` 广播 | `turn/*`、`step/*`、`tool/*`、`command/*` | 事实必须**在重新加载后仍存在** |

| 能力事件 | 挂在 seam 上的策略与适配器 | `tools/*`、`fs/*`、`telemetry/*` | 不引入循环依赖就要挂策略 |

三种分发模式（`docs\architecture.zh.md` 第 113 行）：**waterfall** 必须调用 `next()` 才委托下去（`agent/pre-step`、`agent/request`、`llm/stream`、三个 `tools/*`）；`agent/turn-stopping` 是 **serial**，没有 `next()`；其余是 **emit**（只观察，如 `tools/result`、`tools/change`、`commands/change`）。

### 4.6 Agent 域事件（事件式的"拦截面"）

#### ⑩ `agent/pre-step` 与 `agent/request`：两个 waterfall

`packages\core\agent\src\runtime-types.ts` 第 300–337 行

```ts
    /**
     * Reject a proposed step or replace the messages that enter it. Calling
     * `next()` preserves the current messages.
     * @param payload.agent - the agent proposing the step.
     * @param payload.messages - messages removed from the inbox for this step.
     * @param payload.turn - the turn that will own the step.
     * @param payload.step - the step proposed by the loop.
     * @param payload.signal - the current turn's cancellation signal.
     * Scope-filtered dispatch (`@deepseek-ai/dsh-scope`): agent-scoped listeners receive only that agent.
     * @mode waterfall
     */
    'agent/pre-step'(this: Scoped<Agent>, payload: { agent: Agent; messages: UserMessage[]; turn: number; step: number; signal: AbortSignal }, next: () => Promise<PreStepDecision>): Promise<PreStepDecision>
    /**
     * Replace the frozen call configuration. `await next()` yields the config
     * the machine would use (agent options on the first request, the logged
     * header afterwards); return a replacement to switch. On step admission,
     * this runs after assembly and `step/start`, before the system prompt and
     * accepted user batch are committed. Cancellation here or during subsequent
     * `prepareCall()` resolution commits neither. The prepared call capability
     * governs prompt admission. Model-visible content must use logged channels;
     * this waterfall cannot mutate messages.
     * @param payload.agent - the agent making the model call.
     * @param payload.turn - the open turn number.
     * @param payload.step - the step whose request this is.
     * @param payload.signal - the current turn's explicit abort signal.
     * Scope-filtered dispatch (`@deepseek-ai/dsh-scope`): agent-scoped listeners receive only that agent.
     * @mode waterfall
     */

```

按块讲解：

- **做什么**：Agent 域里唯一两个能"改主意"的位置——`pre-step` 决定**接纳哪些输入**，`request` 决定**这次请求用什么配置**。
- **与哪个知识点相关**：§4.2 三个域里的"Agent 事件"；`3.5` 的轮次流程。
- **`payload` 从哪来**：循环在对应时刻构造并传入；`payload` 是**单参数对象**，事件名后面的 `next` 单独一个位置参数——这条形状对写监听器很关键（见 §6.2 第 6 条"踩坑"）。
- **为什么 `payload` 用对象而不是位置参数**：这两个事件的载荷字段多（agent/turn/step/signal 各 4 个），用对象可以让 `3.x` 后续加字段时不破坏已有监听器——**源码形状本身就是兼容性设计**（标注为推断）。
- **`agent/request` 的 JSDoc 是一条完整的时序说明**：*"this runs after assembly and `step/start`, before the system prompt and accepted user batch are committed"*，以及 *"Cancellation here or during subsequent `prepareCall()` resolution commits neither"*。**它是"能改配置、不能改消息"的**——最后一句原文：*"this waterfall cannot mutate messages."*
- **`agent/pre-step` 的后果**：`next()` 保留当前消息；返回别的决策就是改写或拒绝。首次领取被拒绝或为空 → **关闭一个不含步骤的持久轮次**（`docs\architecture.zh.md` 第 117 行；也就是 1.1 附录 A Q3 的那个结论）。
- **该文件里 `agent/*` 声明的完整清单**：共 **12 个**（第 261、270、280、288、299、307、320、337、353、363、381、393 行）——`agent/created`、`agent/disposed`、`agent/status`、`agent/inbox/inserted`、`agent/inbox/claimed`、`agent/inbox/discarded`、`agent/pre-step`、`agent/request`、`agent/request-error`、`agent/assistant-stream`、`agent/turn-stopping`、`agent/error`。
  > ⚠️ **与首次记录的差异（以源码为准）**：本笔记上一版写"共 9 个"，漏掉了三个 `agent/inbox/*` 事件（第 288、299、307 行）。本次逐行核对后更正为 12 个。
- **分发模式**：`agent/created`、`agent/turn-stopping` 是 serial；`pre-step`、`request`、`request-error` 是 waterfall；`disposed`、`status`、三个 `inbox/*`、`assistant-stream`、`error` 是 emit（各自的 `@mode` 就在声明上方）。
- **会话事件广播口只有一个**：`packages\core\session\src\index.ts` 第 74 行 `'session/event'(this: Scoped<Session>, session: Session, event: SessionEvent): void`，`@mode emit`，JSDoc 写明它是 *"Post-commit, fire-and-forget append feed"*，observer 失败被记录并吞掉、**不会让已提交的追加失败**。

### 4.7 持久扩展点：扩展 `SessionEventMap`

#### ⑪ commands 包怎么把自己的两个事件加进会话日志

`packages\interaction\commands\src\types.ts` 第 93–119 行

```ts
declare module '@deepseek-ai/dsh-session/types' {
  interface SessionEventMap {
    /**
     * A resolved slash command entered its handler. Log-only (never model
     * surface); paired with `command/done` by `commandId`, mirroring the
     * `tool/call`↔`tool/result` pairing. The payload is structured — `name`
     * and `args` are `parseCommand`'s own split (name and verbatim rawInput,
     * separator whitespace included), so a consumer (a projection unit
     * folding its own command records, a rich command card) never re-parses
     * a line. `args` is absent when the definition sets `recordInput: false`
     * because an authoritative domain event owns the input payload.
     */
    'command/run': { commandId: CommandId; name: string; args?: string; source: CommandSource }
    /**
     * The paired command settled. `kind`/`text` carry the handler's verbatim
     * outcome (a thrown/aborted handler settles as `kind: 'error'` with the
     * rendered failure). A successful command may identify the earlier
     * authoritative domain event for a richer client-computed presentation.
     */
    'command/done': {
      commandId: CommandId
      kind: 'success' | 'error'
      text?: string
      sourceEventSeq?: import('@deepseek-ai/dsh-session/types').SessionSeq
    }
  }
}
```

按块讲解：

- **做什么**：用 TypeScript 的 `declare module` 把两个**新事件类型**合并进会话日志的词汇表。做完这一步，`session.append('command/run', …)` 就有了类型，日志与回放也认得它。
- **与哪个知识点相关**：§3.2 第 7 类；文档「添加持久会话状态 → 扩展 `SessionEventMap`；从日志渲染和回放」（`docs\architecture.zh.md` 第 163 行）。
- **词汇表本体在哪**：`packages\core\session\src\types.ts` 第 281 行 `export interface SessionEventMap {` —— 它是**可被合并扩展的**（文件 JSDoc 第 275–280 行原文：*"The merge-extensible, append-only source of truth for an agent interaction."*）。
- **"log-only（非模型表层）"是什么意思**：这两个事件写进日志、`session/event` 广播它们，但**不进入模型历史**（第 451–467 行的注释：*"no turn is opened for it"*）。命令对人类可见、对模型不必可见。
- **`commandId` 的作用**：把 `command/run` 与 `command/done` 配成对，形状上对应 `tool/call` ↔ `tool/result`（JSDoc 原文）。
- **一个硬约束**：**模型可见即已记录**——每个模型请求都必须能从日志重建，新增模型可见输入需要会话事件（`docs\architecture.zh.md` 第 131 行）。所以"扩展 `SessionEventMap`"不是记日志的可选项，而是"让模型看到新东西"的**前置条件**。
- **规模（本次实测，见 §5.1）**：`packages/**/src` 下用 `declare module '@deepseek-ai/dsh-session/types'` 扩展会话事件词汇表的文件有 **30 个**；含词汇表本体在内，出现 `interface SessionEventMap` 字样的源文件 32 个。

### ② 能力接缝的三个角色是什么？为什么单一角色不构成接缝？

**答：三个角色是 Service Definition（声明接口、拥有自己的 `ctx.<key>` 的 Cordis `Service`）、Service Provider（实现它）、Consumer（使用它的消费方，通常是面向模型的工具）。**

出处：`docs\architecture.zh.md` 第 137 行原文——「一个 **seam** 是一项可替换能力，包含三种角色：声明接口的 **Service Definition**、实现它的 **Service Provider**，以及使用它的 **Consumer**（通常是面向模型的工具）。一个包可以合并承担多个角色，但单一角色本身不是 seam；添加一项能力意味着把三者一并设计。」`docs\glossary.zh.md` 第 9 行给出同一结论并强调「seam 是完整能力，绝不是其中一个角色」；`docs\i18n\terminology.md` 第 59 行进一步明确「任何单一角色、普通边界或扩展点都不能称为 seam」。

**为什么单一角色不成立**（文档可支撑的理由）：

1. seam 的价值命题是「**替换一个提供方就能改变整个产品**」（`docs\architecture.zh.md` 第 139 行：把文件系统与进程提供方指向远程沙箱，Bash、PTY、LSP 一并搬过去，不需要提供方专用 fork）。这个命题需要三者齐备才成立：只有定义没有提供方 = 空接口；只有实现没有消费方 = 死代码；只有消费方没有定义 = 硬编码。
2. 语言上的反面参照：`ctx.tools` 在能力表中的角色是 **`core`** 而不是 `seam`（`docs\capability-seams.zh.md` 第 627 行），因为没有「工具注册表提供方」这个角色可替换；而 `ctx.llm`（第 587 行）、`ctx.subprocess`（第 641 行）、`ctx.shell`（第 642 行）、`ctx.approval`（第 647 行）、`ctx.fs`（第 650 行）都带 `实现` 列，即真正的 seam。
3. 能力表因此有「角色」列 + 「实现」列 + 「直接消费方」列 + 「配套插件」列（表头见第 574 行），四列合起来正好验证三角色；例如 `ctx.fs` 行写明 `fs-observation-policy` 是通过 `fs/*` 事件门禁贡献检查的**配套插件**（第 650 行），mermaid 里也是一条虚线 `svc_fs -. event gate .-> pkg_fs_observation_policy`（第 571 行）。
4. 该表由 `scripts/gen-doc-graphs.ts` 从 Cordis 声明中发现服务并分类角色，**设有完整性守卫**（`docs\capability-seams.zh.md` 第 669 行），所以「角色」不是措辞而是被校验的分类。

**量级感**：该表 92 行 `ctx.<key>` 中，`seam` 33 行、`core` 55 行、`service` 3 行、`bundle` 1 行（本课 §5.3 实测复现）。也就是说**多数服务是不可替换的主干**，seam 是少数被刻意设计成可替换的那些。

> **第一次读请跳过**：三角色在**跨包演进**时的拆分判据（何时该把角色拆到不同包）、以及 `isolate` realm 与 seam 的关系，属第四编。

### ④ 为什么说「事件就是扩展点」？

**答：因为循环只发布事实，不提供钩子函数；所有拦截与观察都通过在这些事件上挂监听器完成，产品功能与插件功能走的是同一条路。**

证据链：

1. 定义句：「**事件就是扩展点**，而选对事件域是大多数改动的第一个决定。」（`docs\architecture.zh.md` 第 76 行）
2. 可验证的强主张：「每个产品功能都映射到一个文档化扩展点上的监听器——**微内核声明由此可验证**。没有任何一行修改循环本身。」（`docs\cookbook\extension-cookbook.zh.md` 第 104 行）紧接着是那张「产品功能 → 插件机制」对照表——**27 行数据行**（第 110–136 行，含表头与分隔行共第 108–136 行）：钩子系统挂 `agent/created|pre-step|request` + `tools/pre-execute|post-execute` + `agent/turn-stopping`；`/loop` 挂 `turn/end`；压缩挂 `agent/pre-step` + `agent/request-error`；工具截止时间用 `tools/execute` 包裹；审计用 `tools/result`；沙箱能力级拒绝用 `tools/pre-execute`。
3. 归属判据表给出同一结论：「拦截请求、工具或轮次 → 使用相应的 `agent/*` 或 `tools/*` 事件；`agent/turn-stopping` 会停止轮次」（`docs\architecture.zh.md` 第 159 行）；并规定「新行为附加到已有文档记录的扩展点。改动循环本身时，本映射随之更新」（第 145 行）。
4. 事件不是「通知」而是**有返回值的决策点**：waterfall 监听器必须调 `next()` 才委托下去，返回值是类型化决策（`PreToolDecision` / `PostToolDecision` / `PreStepDecision` / `LlmCallConfig`）（`docs\architecture.zh.md` 第 113 行；`packages\core\tools\src\index.ts` 第 607–620 行）。这使事件具备「策略」能力，而不只是「旁路」。**单调位更进一步**：`guard()` 的返回值类型里**根本没有 allow**，所以排序无法把拒绝翻回允许（第 723–731 行、第 1126–1142 行）。
5. 实测侧证：`packages/**/src` 下 `ctx.on(` 调用 **239** 处，是 `ctx.tools.register(`（65 处）的 3.7 倍、`ctx.commands.register(`（6 处）的 40 倍（本课 §5.1 实测，脚本与输出都在那里）。也就是说这个仓库的扩展**主要靠监听器实现**。
6. 与 seam 的分工：事件让策略**不必**新增 seam，也就不会引入循环依赖（`docs\architecture.zh.md` 第 80 行「能力事件无需导入循环即可向某个 seam 附加策略和适配器」）；两者的边界是「事件是扩展点，seam 是可替换能力，二者是不同概念」（`docs\i18n\terminology.md` 第 59 行）。

**一句话总结**：注册式扩展点决定「系统里有什么」，事件式扩展点决定「已有的东西在何时被谁改写」；两者都不碰循环代码，所以 DSH 才敢自称微内核。
