## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：一次工具调用从"模型说要调"到"结果写进会话日志"的**完整定序**，以及这条路上三种把关物（waterfall 决策、单调 guard、审批 seam）各自的介入条件。
**不是**：工具怎么注册、schema 长什么样（那是 `3.9`）；多个调用怎么并行调度（那是 `3.11`）；工具作者可以挂哪些事件（`3.9` 已给清单）。

### 0.2 现在只要记住这 4 件事

1. **顺序是写死的**：`tool/call` 先落库 → 物化参数 → `tools/pre-execute`（可重排）→ 单调 guard → `tools/execute`（环绕包装）→ `projectContent` → `tools/post-execute` → `finalizeContent` → `tools/result` → 持久 `tool/result`。
2. **"守卫"在仓库里有两个互不相干的意思**：`ctx.tools.guard()` 注册的**单调否决回调**（只有 deny，没有 allow），以及 `packages/guard/` 这个**循环卫生插件家族**（从不否决调用）。混用这两个词就会读错代码。
3. **守卫防顺序，审批防授权**。守卫对付的是"可重排的 `tools/pre-execute` 监听器把已被拒绝的调用放回来"；审批对付的是"危险动作没有人类/机器点头"。审批**失败一律关闭**（没有应答者 = 拒绝）。
4. **失败不会留下悬空的工具调用**：调用一旦被记进日志，就一定有配对的结果——要么是真实结果，要么是三种补齐路径之一写下的 `isError` 结果。

### 0.3 明确授权：这些现在不用管

- `run_code`（PTC 传输）内部的子调用序列、`tools/ptc-dispatch-log`——属于 `4.7`；本课只在"折叠短路"这一处用到"模型直呼 vs 子调用"的区别；
- 工具并发的**分组规则**（独占屏障、有界并行池、乱序回填）——属于 `3.11`；本课只用到它的两个**结论**：结果按模型顺序提交、`dispatch` 可能早于 `finalize`；
- sandbox 模式的完整语义（`read-only` / `workspace-write` / `danger-full-access` 各自拦什么）——属于 `4.4`；本课只用它的**阶梯**（谁比谁严格更宽）；
- `approval/request` waterfall 在 Web / ACP 两侧是怎么渲染成按钮的——属于 `4.x` 客户端编；本课只记"仓库里有两个真实应答者"。

### 0.4 本课依赖的前置词汇

`ctx`（共享登记处）、`service`（`ctx.<键>` 取用的具名能力）、`plugin`（可挂可卸的代码）、`turn`/`step`（轮次/步骤）、`session`（只追加的事件日志）这五个词已由 `1.1` 与 `3.1` 定义；`ctx.tools` 这个键本身由 `3.9` 定义。本课不重复它们，只在用到时点一句"它从哪来"。

## 1. 最小词汇表（本课新增的 7 个词）

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **waterfall 瀑布** | 一个"轮流问下去"的接缝：每个监听器拿到 `next()`，调用它才轮到后面的监听器。所以**能改写、能拦截、顺序可重排** | `ctx.on('tools/pre-execute', async (exec, next) => …)` |
| **emit 广播** | 一个"只通知、不可改"的接缝：监听器没有 `next()`，返回值被丢弃，抛异常只降级成 warn | `ctx.on('tools/result', (exec, result) => …)` |
| **guard 单调守卫** | 一个**只能否决**的回调：返回字符串 = 拒绝，返回 `undefined` = 弃权。**没有 allow**，所以后注册的守卫救不回来 | `ctx.tools.guard(exec => reason \| undefined)` |
| **`exec`（执行对象）** | 这次调用的**身份 + 已物化参数 + 信号**。策略层拿到的是只读视图；`tools/execute` 包装层能改的**只有 `exec.signal`** | `ToolExecution` / `ToolRunContext` |
| **三态 `prepare`** | 注册表把"这次调用该往哪走"编成三态：`dispatch`（继续跑主体）/ `post-result`（还要过 post-execute）/ `final-result`（直接收尾） | `ScheduledToolPreparation` |
| **物化（materialize）** | 把内存里的对象**无损快照**成纯 JSON 再 `deepFreeze`。做不到无损就抛错——**不许静默丢字段** | `snapshotJsonValue` + `deepFreeze` |
| **审批（approval）** | 挂在 `ctx.approval` 上的能力接缝：问一个"准不准"的问题，拿回四态之一，**失败关闭** | `ctx.approval.request({ agent, toolName, callId, reason?, signal })` |

> ⚠️ 最后一个词要立刻和 guard 分开：**审批是一条独立的 seam，不是第四个 waterfall 监听器**。它唯一的进入方式是被注册表的 `ask` 分支调用，或由工具自己在 body 里直接调用（§4.7）。

## 2. 先建立画面

### 2.1 静态阶段图（谁在什么时候被叫到）

```
调用方（agent-loop）
  │ ① appendToolCall：先写 tool/call 事件，拿到 seq
  ▼
ToolRuntime.execute(exec)                     ← 注册表，本课主角
  ├─ ② createExecution：一次物化参数 + 冻结 + 快照两个回调
  ├─ ③ ctx.waterfall('tools/pre-execute')     ← 可重排；四态 allow|deny|cancel|ask
  │     └─ 仅当结果是 allow 时 ↓
  ├─ ④ 单调 guard（全局层 → scope 链）        ← 只能否决
  ├─ ⑤ ctx.waterfall('tools/execute') → 工具体 ← 环绕包装层在这里（超时/重试/指标）
  ├─ ⑥ projectContent → ctx.waterfall('tools/post-execute') → finalizeContent
  └─ ⑦ ctx.events.dispatch('emit', 'tools/result')  ← 冻结后的最终结果
  ▼
调用方：appendToolResult → 持久 tool/result 事件（带 sourceEventSeqs: [callSeq]）
```

**精确性说明（别被图骗了）**：`tool/call` 与 `tool/result` 是**会话事件**，由 agent-loop 写；中间的 ②–⑦ 是**注册表内部的阶段**，不写日志。图上把两者画成一条线只表示先后关系。

### 2.2 动态流水线图（仓库自己的口径）

```
tool/call* -> tools/pre-execute -> tools/execute -> tools/post-execute -> tool/result*
```

出处（文档）：`docs\architecture.zh.md` 第 106 行（轮次流程伪代码里的工具调用那一段）。

把它展开成带闸门的版本：

```
tool/call*  ──►  pre-execute ──allow──► guard ──clean──►  execute ──►  post-execute ──►  tool/result*
                    │ deny                │ deny             │              │
                    ▼                     ▼                  │              │
                 denied 结果            denied 结果          │              │
                    │                     │                  │              │
                    └──── 都还要过 post-execute ───────────┘              │
                                                                          │

```

### 2.3 大白话版：模型说"我要跑个工具"之后发生了什么

**完全不用上面的术语**，先建立画面（来源：`docs\tool-execution-pipeline.zh.md` 第 8、65 行；只做白话转述）。

1. 模型的话被拆成若干条"我要调用某某"的请求。
2. 循环**先把每条请求记进账本**，然后才去执行——所以"记了但没结果"是一个可判定的状态。
3. 注册表接手：把参数**原样复印一份并冻上**（模型给的东西之后谁也改不了），同时**记下这个工具是否声明了"执行前/执行后要加工内容"的两个回调**。
4. 接着挨个问一圈"执行前检查"：钩子、权限策略、沙箱策略。它们可以放行、拒绝、取消，或者反问"要不要问一下人"。
5. 问完这一圈，再看有没有"守卫"想否决。守卫跑在最后，而且**只会说不**。
6. 都通过了，才真正跑工具主体。外面可能还套着几层"包装"——比如超时计时器。
7. 结果出来后再走一圈：先由工具自己"准备内容"，再问一圈"执行后检查"（可以接受、改写、或把成功翻成失败），最后由工具自己"终检内容"。
8. 这时候结果被**冻死**，广播给所有围观者（它们只能看）。
9. 循环按**模型说话的顺序**把结果写进账本，与第 2 步那条请求配对。
10. 如果中途崩了/取消了/步骤失败了，仍有专门的补齐逻辑给"记了却没结果"的请求补一条错误结果——因为模型的下一次请求要求"调用与结果必须配对"。

## 3. 结论先行（细节在 §4–§8，每条都带源码出处）

1. 一次工具调用的流水线是**定序的七段**：`tool/call` 落库 → 参数无损物化 → `tools/pre-execute`（可重排 waterfall）→ 单调 guard → `tools/execute`（环绕包装）→ `projectContent` + `tools/post-execute` → `finalizeContent` → `tools/result`，之后 agent-loop 才把它写成持久的 `tool/result`（`packages\core\tools\src\index.ts` 第 1–5 行；`docs\subsystems\tools.zh.md` 第 182 行；`docs\tool-execution-pipeline.zh.md` 第 8 行）。
2. 循环侧的权威顺序写死在一行图里：`tool/call* -> tools/pre-execute -> tools/execute -> tools/post-execute -> tool/result*`（`docs\architecture.zh.md` 第 106 行）。
3. **「守卫」在本仓库有两个互不相干的意思**，混用就会读错代码：
   - `ToolGuard`：`ctx.tools.guard()` 注册的**单调否决回调**，只有一个返回值语义——返回字符串即拒绝，返回 `undefined` 即弃权，**没有 allow**（第 723–731 行）。全仓库生产代码里只有一处真正注册它（`packages\subagent\subagent-in-process-driver\src\structured.ts` 第 109–111 行）。
   - `packages/guard/`：一个**循环卫生插件家族**（`repeat-tool-reminder`、`timeout-policy`），挂在 `tools/post-execute` / `tools/execute` 事件上，**从不否决调用**（`packages\guard\README.zh.md` 第 12、29–30 行）。
4. **守卫与审批防的不是一回事**：守卫防"顺序问题"（可重排的 pre-execute 监听器把已拒绝的调用放回来）；审批防"授权问题"（危险动作缺少人类/机器决策）。审批只有两条入口，且**失败一律关闭**。
5. 三个 `tools/*` waterfall 必须调 `next()` 才能委托下去；`tools/result` 是 emit，没有 `next()`，监听器失败被包含成 warn（`docs\architecture.zh.md` 第 113 行；`packages\core\tools\src\index.ts` 第 197–198、1695–1714 行）。
6. 结果被**冻结两次**：注册表在 `tools/result` 之前做无损 JSON 快照 + `deepFreeze`（第 1886–1901 行），agent-loop 再以 `surfaceOp: 'append'` + `sourceEventSeqs: [callSeq]` 写成持久 `tool/result`（`packages\core\agent-loop\src\tool-calls.ts` 第 268–289 行）。
7. 失败步骤不会留下"悬空的 assistant tool-call"：实时失败由 `ToolCallRecovery` 补结果（`packages\core\agent-loop\src\agent.ts` 第 331–357 行），崩溃尾部由 `interruptedTurnClosers` 补（`packages\core\session\src\repair.ts` 第 209–211 行）。

## 4. 七个阶段与源码对照

### 4.1 阶段 0：`tool/call` 先落库，再进流水线

**结论**：调用**已被记录**之后才可能失败，所以"有 call 无 result"是一个可判定的状态（§4.9 的三条补齐路径就是为它准备的）。

- agent-loop 从 assistant 消息里筛出 tool-call block（`packages\core\agent-loop\src\agent.ts` 第 532–533 行），交给 `executeToolCalls`（第 534–537 行）。
- `startCall` 先 `appendToolCall(session, …)` 写 `tool/call`，**再** `TOOL_RUNTIME_SCHEDULER.prepare(…)`（`packages\core\agent-loop\src\tool-calls.ts` 第 165–170 行）。`appendToolCall` 返回该事件的 `seq`，供结果引用（第 262–266 行）。
- 事件载荷保存模型原样的参数字符串：`'tool/call': { turn; step; callId; name; arguments }`（`packages\core\session\src\types.ts` 第 356–361 行）。

**源码块 1：先记调用、再准备** —— `packages\core\agent-loop\src\tool-calls.ts` 第 165–197 行

```ts
  const startCall = async (index: number): Promise<void> => {
    // oxlint-disable-next-line typescript/no-non-null-assertion -- bounded index
    const call = group[index]!
    callSeqs[index] = appendToolCall(session, turn, step, call.block)   // ① 先落库，拿到 seq
    started++
    const prepared = await ctx.tools[TOOL_RUNTIME_SCHEDULER].prepare(call.exec)  // ② 再进流水线
    throwSchedulerFailure()
    switch (prepared.kind) {                                            // ③ 三态分派
      case 'dispatch': {
        const promise = ctx.tools[TOOL_RUNTIME_SCHEDULER].dispatch(prepared.exec).then(
          (outcome) => {
            slots[index] = { exec: prepared.exec, result: outcome.result, needsPost: outcome.kind === 'post-result' }
            return index
          },
          (error: unknown) => {
            schedulerFailure ??= { error }
            return index
          },
        )
        inFlight.set(index, promise)
        break
      }
      case 'post-result':                                                 // ④ 还要过 post-execute
        slots[index] = { exec: prepared.exec, result: prepared.result, needsPost: true }
        break
      case 'final-result':                                                // ⑤ 直接收尾
        slots[index] = { exec: prepared.exec, result: prepared.result, needsPost: false }
        break
      /* v8 ignore next -- closed-union exhaustiveness guard */
      default:
        assertNever(prepared, 'tool-call scheduler prepare result')
    }
  }
// （本块是 `startCall` 这个新函数的整段，未删任何行；它属于 `runGroup` 的内层：
//   `group` / `session` / `turn` / `step` / `callSeqs` / `slots` 都是 `runGroup` 的参数与局部变量，
//   见源码块 11（`commitReady`）上方的解释。）
```

按块讲解：

- **① 顺序就是结论**：`appendToolCall` 在 `prepare` **之前**。所以任何"prepare 阶段就抛错/拒绝"的情况，日志里都已经有一条 `tool/call`。
- **② `TOOL_RUNTIME_SCHEDULER` 是什么**：注册表导出的一个 **symbol 键**（`packages\core\tools\src\index.ts` 第 480 行）上的四方法视图（第 816–821 行：`prepare` / `dispatch` / `finalize` / `finish`）。agent-loop 用它把"策略有序"与"派发可重叠"分开——所以 `prepare` 与 `dispatch` 才会是两个调用。
- **③⑤ 三态编码在返回值里**：`ScheduledToolPreparation`（第 445–448 行）的注释原文是 *"A `post-result` still receives post-execute; a `final-result` bypasses it."* —— 这一条就是 §4.3「deny 也要过 post-execute、抛异常则绕过」的机制来源。
- **④ `needsPost` 是唯一携带到提交阶段的布尔**：`commitReady` 靠它决定调 `finalize` 还是 `finish`（源码块 11）。

**源码块 2：调用与结果的配对证据** —— `packages\core\agent-loop\src\tool-calls.ts` 第 262–289 行

```ts
/** Append a started call and return the event seq that its result must cite. */
function appendToolCall(session: Session, turn: number, step: number, block: ToolCallBlock): SessionSeq {
  const event = session.append('tool/call', { turn, step, callId: block.id, name: block.name, arguments: block.arguments })
  return event.seq
}

/** Append a model-ordered result linked to its call event. */
function appendToolResult(
  session: Session,
  turn: number,
  step: number,
  block: ToolCallBlock,
  result: ToolExecutionResult,
  callSeq: SessionSeq,
): void {
  const message = createToolResultMessage({
    callId: block.id,
    content: result.content,
    isError: result.isError,
  })
  session.append('tool/result', {
    turn, step,
    message,
    ...result.error?.info ? { error: result.error.info } : {},
    // The tool's private presentation payload (e.g. a result-time diff),
    // persisted so a UI bridge reproduces the card on replay.
    ...result.meta !== undefined ? { meta: result.meta } : {},
  }, { surfaceOp: 'append', sourceEventSeqs: [callSeq] })
}
// （本块是两个相邻的小函数整段，未删任何行；两段之间的空行保留。）
```

按块讲解：

- **`arguments` 是模型原样的字符串**：`appendToolCall` 把 `block.arguments`（未解析的 JSON 文本）原样落库——所以日志里保存的是"模型当初说了什么"，而不是解析结果。解析发生在 `executeToolCalls` 的 `parseArguments`（同文件第 104–111 行：合法 JSON → 解析，非法 → 保留原字符串，空 → `{}`）。
- **`sourceEventSeqs: [callSeq]` 就是配对证据**：⑵ 的注释原文 *"return the event seq that its result must cite"*。§4.9 的三条补齐路径全都复述这同一个字段。
- **`error` 与 `meta` 都是可选的**：`error` 只带 `{name, code, reason?}`，来自注册表结果的 `error.info`；`meta` 是工具私有的展示载荷（例如 fs 工具的结果期 diff），`Session.append` 会强制它可 JSON 序列化（源码块 12）。

按块讲解：

- **① 为什么"先抓回调"**：这段注释是作者原文，理由有两层——(a) 契约要求回调**在调用开始时快照**；(b) 参数对象可能带 getter，而 `snapshotJsonValue` 会**读**这些 getter，于是 getter 有机会在物化中途把注册表里的回调换掉。把回调先绑到局部常量，这条路径就闭合了。
- **② 物化是全流程唯一入口**：`snapshotJsonValue` 返回 `undefined` 表示"这份数据无法无损表达为 JSON"，此时**抛 `TypeError`**，被外层 catch 收成 `final-result`（第 1476–1480 行）——**监听器根本不会被叫到**。实测见 §7.2 探针 2 的 `LOSSY` 那两行。
- **③ 回调按"执行对象"存**：存在 `WeakMap` 里（字段声明见第 829–832 行），键是 `execution`。所以同一个工具的不同调用各有各的回调选择结果——`collapsed` 的那次得到 `undefined`，于是它的内容不会被工具自己的终检改写。
- **`snapshotJsonValue` 到底是什么语义**：见 §7.2 探针 1——循环引用、函数成员、`undefined` 成员**统统返回 `undefined`**（不是抛错，是"不可无损"）。

### 4.3 阶段 2–3：`tools/pre-execute` waterfall + 单调 guard

`prepareExecution`（第 1493–1539 行）是这段的全部真相：

1. 入口先查调用方取消（第 1500–1502 行）→ `ABORTED_BEFORE_DISPATCH`。
2. `ctx.waterfall(carrier, 'tools/pre-execute', exec, () => ({ kind: 'allow' }))`（第 1505–1508 行）。默认决策是 `allow`；`PreToolDecision` 四态 `allow | deny | cancel | ask`（第 607–611 行）。
3. `ask` 走 `serviceAsk`（第 1509–1511 行）。
4. `cancel` → `ABORTED_BEFORE_DISPATCH`，且标为 `post-result`（第 1516–1517 行）。
5. 拒绝原因的选择是**二选一**：`decision.kind === 'allow' ? this.guardReason(exec) : decision.reason`（第 1519 行）。**只有 waterfall 放行时才会问 guard**；一旦 pre-execute 已 deny，guard 根本不被咨询。
6. 拒绝落成 `isError` 结果并标为 `post-result`（第 1521–1531 行）——即 **deny 也要过 post-execute**。
7. 任何抛出的监听器被外层 catch 收成 `final-result`（第 1536–1538 行）——即**抛异常绕过 post-execute**。

`ScheduledToolPreparation` 的三态正是这条分叉的编码（第 445–448 行）：`dispatch` 继续跑 body；`post-result` 还要过 post-execute；`final-result` 直接进收尾。

按块讲解：

- **★ "没有 allow"是设计意图，不是遗漏**：JSDoc 原文 *"Because guards have no allow result, listener ordering cannot turn a denial back into permission."* —— 这就是 §5 把守卫与审批分开的理由：**守卫防顺序**。
- **①③ 解析顺序是"全局层 → scope 链（远祖先先）"**：`chainLayers` 的契约原文是 *"farthest ancestor first and the exact scope last, so a caller layering them in order gives the nearest scope the final word"*（`packages\core\scope\src\store.ts` 第 185–199 行）。**但 guard 是单调的，所以"最近的最后说"这句话在 guard 上不体现在"后者胜出"**——第一个给出原因的就直接返回了。这是同一个库在 restriction（近者遮蔽）与 guard（先到先否决）上语义不同的一处，容易读错。
- **② 没有 agent 就连 scope 链都不查**：直接返回 `undefined`（弃权）。
- **注册入口返回精确 disposer**：`this.layers.effect(...)` 的返回值就是卸载函数（JSDoc：*"The exact effect disposer is returned for ordered ownership and HMR cleanup."*）；`notify: false` 表示注册 guard **不**触发 `tools/change` 事件。
- **同层内顺序 = 注册（append）顺序**：`this.guards.values()` 是插入序。

```ts
    /* v8 ignore next -- only registry-minted executions reach the staged scheduler methods */
    if (state === undefined) throw new Error('tool registry scheduler invariant violated: missing cancellation state')
    const wrapperSignal = exec.signal                           // ② 包装层可能已经换过它
    const fused = fuseToolSignals(state.callerSignal, wrapperSignal)   // ③ 融合成一条
    const signal = fused.signal

    if (isAborted(signal)) {
      fused.dispose()
      return toolAbortedBeforeDispatchResult()                  // ④ 还没跑主体就已取消

    exec.signal = signal                                        // ⑤ 主体看到的是融合信号

      if (!tool) throw new ToolNotFoundError(exec.name)

      exec.signal = wrapperSignal                               // ⑩ 恢复包装层信号
    }
```

```ts
  private async postExecute(exec: ToolExecution, result: ToolExecutionResult): Promise<ToolExecutionResult> {
    const decision = await this.ctx.waterfall(
      scopeTarget(this, exec.agent), 'tools/post-execute', exec, result,
      () => Promise.resolve<PostToolDecision>({ kind: 'accept' }),     // ① 默认 accept
    )
    const decisionContexts = decision.additionalContexts ?? []
    if (decision.kind === 'block') {                                    // ② block：成功翻失败
      const message = failureMessageFromContent(decision.feedback)
      return this.markCanonical(exec, {
        content: decision.feedback,
        isError: true,
        error: { message },
        ...decisionContexts.length > 0 ? { additionalContexts: decisionContexts } : {},
      })
    }
    if (Object.hasOwn(decision, 'content') && Object.hasOwn(decision, 'value')) {   // ③ 两者不许同时
      throw new TypeError('tools/post-execute accept decision cannot replace both value and content')
    }
    const additionalContexts = [
      ...result.additionalContexts ?? [],
      ...decisionContexts,
    ]
    if (Object.hasOwn(decision, 'value')) {                             // ④ 换 value：重跑 output 契约
      if (result.isError) {
        throw new TypeError('tools/post-execute cannot replace the value of a failed result')
      }
      const tool = this.resolveExecution(exec.name, exec.agent, exec.parent !== undefined)
      if (tool === undefined) throw new ToolNotFoundError(exec.name)
      const replaced = this.createSuccessResult(exec, tool, decision.value)
      return this.markCanonical(exec, {
        ...replaced,
        ...additionalContexts.length > 0 ? { additionalContexts } : {},
      })
```

```ts
    // the containment into the caller.
    const answer: Promise<ApprovalOutcome> = Promise.resolve().then(   // ③ 先把 promise 链搭好
      () => this.ctx.waterfall(
        scopeTarget(req.agent, req.agent), 'approval/request', req,
        () => Promise.resolve<ApprovalOutcome>('unavailable'),         // ④ 零监听器 → unavailable
      ),
    ).then(
      // Normalize a rogue (non-vocabulary) answerer return to the fail-closed
      // outcome instead of leaking it into callers' closed-union switches.
      outcome => OUTCOMES.includes(outcome) ? outcome : 'unavailable', // ⑤ 非法返回值 → unavailable
      // A throwing answerer must fail the QUESTION closed, not the caller's
      // tool call open — the seam contains its callbacks.
      () => 'unavailable',                                             // ⑥ 抛异常 → unavailable
    )
    if (signal === undefined) return answer
    return await new Promise<ApprovalOutcome>((resolve) => {           // ⑦ 与取消赛跑
      const onAbort = () => {
        signal.removeEventListener('abort', onAbort)
        resolve('cancelled')
      }
      signal.addEventListener('abort', onAbort, { once: true })
      void answer.then((outcome) => {
        signal.removeEventListener('abort', onAbort)
        // After an abort won the race this resolve is a settled-promise no-op:
        // the late answer is discarded by construction.
        resolve(outcome)                                               // ⑧ 迟到的回答被丢弃
      })
    })
  }
// （本块是 `decide` 整段，未删任何行；第 261–266 行是它的文档注释。变量来源：`req` 由
//   `request()`（第 231 行）传入，`session` 是 `req.agent.session`；`OUTCOMES` 是第 55 行的
//   四态常量表；`effectivePolicy` 在第 243–245 行。）
```

按块讲解：

- **② 注释是"为什么不能做成监听器"的完整答案**：作者原文说——如果一个监听器用 `prepend: true` 在这个服务之后挂上，它会排在"任何门禁监听器"前面，于是"`never` 一定拒绝"这个承诺就保不住了。**只有服务自己的请求路径**能保证这一点。所以策略门禁放在 `decide` 里，而不是做成一个 waterfall 监听器。
- **③ 为什么要 `Promise.resolve().then(...)`**：让**同步抛出**的监听器也落进同一个 rejection 分支（直接 `Promise.resolve(this.ctx.waterfall(...))` 会让同步异常逃到调用者）。
- **④ 默认值是 `unavailable`**：与 pre-execute/post-execute 的默认 `allow`/`accept` 相反——审批的**默认是不批准**。这条就是"失败关闭"最直白的落点。
- **⑦⑧ 取消优先**：`signal` 中止立即 settle 成 `cancelled`；之后即使应答者给了答案，`resolve` 也是已落定 promise 上的空操作——所以"迟到的批准"不会生效。

**策略的模型可见面**：`ApprovalService` 往 `systemPrompt` 的 `approval:policy` 上下文放一句当前策略文案（第 160–174 行；两句常量在第 72–75 行）。切换策略走 `setPolicy`，会注入一条 `user/message` 通知（第 184–195 行）。

```ts
export async function approveEscalation<A, C>(request: EscalationRequest, approval: EscalationApproval<A, C>): Promise<SandboxMode> {

  if (mode === effectiveMode) return effectiveMode              // ② 同模式重试：不问
  // Strict widening is an EXECUTION check against the call's effective mode —

  // vocabulary; the effective mode is per-call truth).

    throw new Error(`sandbox escalation to "${mode}" requires approval, but no approval service is composed`)
  }
  if (approval.agent === undefined) {                           // ⑤ 缺 agent：抛
    throw new Error(`sandbox escalation to "${mode}" requires approval, but the call has no agent to route it through`)
  }
  // Self-contained for the audit trail: approval/asked stores this reason,
  // and the target mode is part of the grant's identity.
  const outcome = await approval.approver.request({             // ⑥ 真正去问
    agent: approval.agent,
    toolName: approval.toolName,
    callId: approval.callId,
    reason: `escalate sandbox to ${mode}: ${justification}`,
    displayReason: {
      en: `Allow this operation with ${mode} permissions: ${justification}`,
      zh: `允许本次操作使用 ${mode} 权限：${justification}`,
    },
    ...approval.signal ? { signal: approval.signal } : {},

    // The schema enum already pinned `mode` to the closed target vocabulary;
    // the check above proved it is strictly wider.
    case 'allowed-once': return mode as SandboxMode              // ⑦ 唯一成功：返回目标模式

    case 'cancelled': throw new Error(`approval for escalating to "${mode}" was cancelled`)
    case 'unavailable': throw new Error(`sandbox escalation to "${mode}" requires approval, but no approval channel is available`)
    default: return assertNever(outcome, 'EscalationOutcome')
  }
}
```

```ts
  ctx.on('tools/execute', async (exec, next): Promise<ToolExecutionResult> => {   // ① 环绕包装
    const timeoutMs = ctx.tools.get(exec.name, exec.agent)?.timeoutMs            // ② 读工具声明的预算
    // A tool that declares no budget: no deadline, delegate unchanged.
    if (timeoutMs === undefined) return next()                                   // ③ 没预算：原样委托
    using d = deadline(exec.signal, timeoutMs, TOOL_TIMEOUT)                     // ④ 派生信号 + 计时器
    // Swap the derived deadline onto exec for dispatch, then restore the
    // caller's own signal so post-execute listeners never see this plugin's
    // (possibly already-aborted) timeout signal.
    const upstream = exec.signal
    exec.signal = d.signal                                                       // ⑤ 原地换信号
    try {
      const result = await next()                                                // ⑥ 委托下去（主体在这里跑）
      // If OUR timer fired (scoped by code — a nested outer deadline reads as
      // undefined here), the tool/capability saw the abort and reached

        return toolTimeoutResult(timeoutMs)                                      //    换成结构化超时错误
```

**源码块 18：`ToolCallRecovery.observe` —— 分类规则** —— `packages\core\session\src\repair.ts` 第 105–149 行

```ts
export class ToolCallRecovery {
  private readonly pendingCalls = new Map<ToolCallId, { turn: number; step: number; callSeq?: SessionSeqType }>()
  private last: Pick<SessionEvent, 'seq' | 'time'> | undefined

  /** @param cause - defaults to interrupted live/crash recovery; fork-seed construction supplies its own cause. */
  constructor(private readonly cause: OpenTurnCloseCause = { kind: 'interrupted' }) {}

  observe(event: SessionEvent): void {
    this.last = { seq: event.seq, time: event.time }               // ① 记下最后见过的事件
    switch (event.type) {
      case 'turn/start':
      case 'turn/end':
      case 'step/end':
        this.pendingCalls.clear()                                  // ② 边界事件：整批作废
        break
      case 'assistant/message':
        for (const block of event.data.message.content) {          // ③ 建立 pending 集
          if (block.type === 'tool-call') {
            this.pendingCalls.set(block.id, { turn: event.data.turn, step: event.data.step })
          }
        }
        break
      case 'tool/call': {                                          // ④ 只补 callSeq
        const entry = this.pendingCalls.get(event.data.callId)
        if (entry) entry.callSeq = event.seq
        break
      }
      case 'tool/result': {                                        // ⑤ 销账条件很严
        const callId = event.data.message.source.callId
        const entry = this.pendingCalls.get(callId)
        if (event.surfaceOp === 'append' && entry !== undefined
          && entry.turn === event.data.turn && entry.step === event.data.step) {
          this.pendingCalls.delete(callId)
        }
        break
      }
      // SessionEvent is merge-extensible; unrelated events retain pending requests.
      default:
        break
    }
  }
// （本块是 `ToolCallRecovery` 的类头 + 前两个成员（第 100–111 行的类文档注释与 112–115 行的
//   `observe` 文档注释未摘）；第 151–197 行的 `results()` 见源码块 19。`SessionEvent` /
//   `SessionSeq` 来自本包的 `./types.ts`；`OpenTurnCloseCause` 定义在第 29 行。）
```

按块讲解：

- **③ pending 集的建立者是 `assistant/message`**：只有模型**请求过**的调用才可能缺失。所以恢复的判据不是"日志里少了什么"，而是"模型要过、而账本没销账"。
- **④ `tool/call` 的意义**：它**不销账**，只标记"这条调用真的开始过了"（`callSeq`）。这一位决定了错误码：有它 = 结果未知（`TOOL_OUTCOME_UNKNOWN`），没它 = 从未开始（`TOOL_NOT_STARTED`）。
- **⑤ 销账条件里的 `surfaceOp === 'append'`**：`tool/result` 事件可能不是"追加到模型可见表面"的（例如被投影/遮蔽的事件）。只有真正追加的才算销账——这条守卫防止"用一条不可见的结果抵消一条真实调用"。
- **② 边界事件清空整批**：`turn/start` / `turn/end` / `step/end` 一来，之前所有 pending 都作废——因为那些调用所属的步骤/轮次已经结束了。

**源码块 19：`results()` —— 造保守结果** —— `packages\core\session\src\repair.ts` 第 157–197 行

## 5. 守卫 vs 审批：为什么是两个东西

**结论**：**守卫防顺序，审批防授权。**

### 5.1 单调 guard 防的是什么

`tools/pre-execute` 是**可重排 waterfall**：一个 `{ prepend: true }` 的监听器可以插到门禁前面（`auto-review` 就是这么干的，见 §6）。所以如果"允许/拒绝"只靠监听器，顺序就成了安全边界。

guard 跑在**整个 waterfall 之后**，且**没有 allow 返回值**（源码块 5 的 JSDoc 原文：*"Because guards have no allow result, listener ordering cannot turn a denial back into permission."*）——"先 deny 后 allow"这条面因此不存在。

- **介入条件**：`tools/pre-execute` 走完后决策是 `allow`（第 1519 行），且某个已注册 guard 返回了非 `undefined` 字符串。
- **查找顺序**：全局层 → scope 链（farthest first）（源码块 5）；同层内取第一个非 `undefined`。
- **仓库里唯一的真实用例**：subagent 的结构化输出工具一旦拿到结果，就要终止本步骤后续的受支持调用。

**源码块 21：全仓唯一的生产 guard** —— `packages\subagent\subagent-in-process-driver\src\structured.ts` 第 105–111 行

```ts
  // Terminal WITHIN the step. Guards run after the whole pre-execute
  // waterfall and compose monotonically (deny or abstain, never allow), so a
  // later prepended listener cannot resurrect dispatch. Calls that precede
  // capture in the same response remain untouched.
  childCtx.tools.guard(exec => captured === undefined && pending === undefined
    ? undefined
    : `structured output already recorded: the run is complete, so \`${exec.name}\` is not executed`)
// （本块是这一处注册调用的完整上下文（注释 + 调用）——**只有 11 行，低于 15 行下限**，
//   因为机制本体就是"一次 `guard()` 调用 + 作者写下的理由"，它没有函数体可以展开（完整函数
//   见同文件第 109 行的上下文：`staged` / `captured` / `pending` 三个闭包变量）。依赖的变量来源：
//   `childCtx` 是本函数里为子 agent 建的作用域上下文（`ctx.agent(...)` 一类，见同文件上文）；
//   `captured` / `pending` 分别在同文件第 124 行与第 127–129 行的 `tools/result` 监听里被赋值。
//   前一条注释明确引用了本课 §5.1 的结论——它是"守卫防顺序"的现场证据。）
```

按块讲解：

- **注释直接复述了本课的结论**：*"Guards run after the whole pre-execute waterfall and compose monotonically (deny or abstain, never allow), so a later prepended listener cannot resurrect dispatch."* —— 作者写这段守卫的**理由**就是"防重排"。
- **`exec.name` 只用于措辞**：返回的原因文本会带上被拒工具的名字，好让模型知道"是哪个调用没跑"。
- **它是"步骤内的终止"**：`captured` / `pending` 一旦有值（结构化输出已记录），后续所有调用都被拒——但**同一响应里排在它前面的调用不受影响**（注释第三句）。
- **为什么这是唯一一处**：我按 `.guard(` / `tools.guard(` 全仓搜索，生产代码只有这一处，其余都在测试里（`packages\core\tools\tests\scoped.spec.ts`）。（标注为检索结论；这次检索是只读的，命令未在笔记里留档。）

### 5.2 审批防的是什么

**危险动作没有被授权就执行**，且**失败关闭**。两条独立入口：

- **入口 A（pre-execute `ask`）**：某个 `tools/pre-execute` 监听器返回 `{ kind: 'ask' }`。仓库内真实生产者：`auto-review` 的 prepend 门禁——条件是 `exec.agent` 存在、不是模型直呼的 `run_code`、会话预设等于 `AUTO_PRESET`、integration 仍 accepting；reviewer 说 deny 且下游允许时才转 `ask`（`packages\experimental\auto-review\src\index.ts` 第 686–721、657–666 行）；Codex/Claude-Code 钩子桥的 `permissionDecision: ask` 走同一协议（`.agents\notes\implemented\feature\2026-07-06-approval-seam.zh.md` 第 48、60–62 行）。注册表侧再叠加：无 approval 服务 → deny；无 agent → deny；只有 `allowed-once` 放行（第 1727–1768 行）。服务侧再叠加：无开放轮次 → 抛；策略 `never` → 分发前直接 `rejected`；无应答者/应答者抛异常/非法返回值 → `unavailable`（`packages\interaction\user-approval\src\index.ts` 第 217–223、275、280–292 行）。
- **入口 B（沙箱升级）**：模型给了 `sandbox_permissions` + `justification`，且请求模式比本次调用的生效模式**严格更宽**。它不是 `ask` 决策，而是 body 内直接调 `ctx.approval.request`（`packages\sandbox\sandbox\src\escalation.ts` 第 171–208 行；调用点 `packages\shell\tool-bash\src\index.ts` 第 237–257 行）。同模式重试不需审批（第 173 行）。

- **别混进来的第三个"guard"**：`packages/guard/` 下的 `repeat-tool-reminder` 与 `timeout-policy` 既不是审批也不是单调守卫（源码块 16/17）。

## 6. 一条真实产物链：`auto-review` 是怎么"制造 ask"的

`serviceAsk` 只负责"拿到 `ask` 之后怎么办"；"谁会说 ask"在别处。仓库里最完整的生产者是 `auto-review`：它用 `{ prepend: true }` 把自己插到最前面，先问 reviewer，再根据 reviewer 的结论决定 `deny` / 放行 / 转 `ask`。

**源码块 22：`ask` 的真实介入条件** —— `packages\experimental\auto-review\src\index.ts` 第 686–721 行

```ts
    const stopListener = ctx.on('tools/pre-execute', async (exec, next): Promise<PreToolDecision> => {
      const agent = exec.agent
      if (agent === undefined || (exec.parent === undefined && exec.name === RUN_CODE_NAME)) {
        return next()                                    // ① 无 agent / 模型直呼 run_code：不介入
      }
      if (permissionPresets.current(agent.session) !== AUTO_PRESET) {
        return next()                                    // ② 会话不是 Auto 预设：不介入
      }
      if (!accepting || lifecycle.signal.aborted) {
        return { kind: 'cancel' }                        // ③ 正在关闭：取消
      }

      const completed = Promise.withResolvers<void>()
      active.add(completed.promise)
      try {
        const signal = AbortSignal.any([exec.signal, lifecycle.signal])
        const review = await classifyRisk(ctx, agent, exec, signal).then(
          decision => ({ ok: true as const, decision }),
          (error: unknown) => ({ ok: false as const, error }),   // ④ reviewer 失败单独接住
        )
        if (isAborted(lifecycle.signal)) return { kind: 'cancel' }
        if (!review.ok) return failed(exec, review.error)        // ⑤ reviewer 失败 → deny（不是 ask）
        const { decision } = review
        // The permission owner pins an approval policy into every published Session.
        if (decision.decision === 'deny' && ctx.approval.overrideOf(agent.session) === 'never') {
          return denied(exec, decision.reason)                   // ⑥ 策略 never：直接 deny，不问
        }
        const downstream = await next()                          // ⑦ 先让下游定夺
        if (isAborted(lifecycle.signal)) return { kind: 'cancel' }
        if (decision.decision === 'allow' || downstream.kind !== 'allow') return downstream   // ⑧ 下游不准：尊重下游
        return askUser(exec, decision.reason)                    // ⑨ 只有两者冲突才转 ask
      } finally {
        active.delete(completed.promise)
        completed.resolve()
      }
    }, { prepend: true })                                        // ⑩ 插到最前面
// （本块是 `apply` 内那段监听器（第 686–721 行）；第 677–685 行的 `apply` 开头
//   （`permissionPresets` / `accepting` / `active` / `lifecycle` 四个闭包变量的初始化）见正文。
//   变量来源：`classifyRisk` 是同文件函数；`askUser` / `failed` / `denied` 分别在第 657–666、
//   668–675 行与同文件上文；`AUTO_PRESET` / `RUN_CODE_NAME` 是导入的常量。）
```

按块讲解：

- **⑩ `prepend: true` 正是"可重排"的现场**：这条监听器排在所有其它 `tools/pre-execute` 监听器**前面**。这就是为什么 guard 必须跑在整个 waterfall 之后（§5.1）。
- **① 两个"不介入"**：没有 agent 的调用不问（与 `serviceAsk` 的第二道 deny 呼应）；模型直呼 `run_code` 也不问（`exec.parent === undefined` 表示"模型直呼"，见源码块 3 的 `parent`）。
- **⑦⑧⑨ 的哲学**：reviewer 说 allow → 尊重下游；下游说非 allow（deny/cancel/ask）→ 尊重下游；**只有"reviewer 说 deny 而下游放行"这一种冲突**才升级成 `ask`——即"让人类来打破僵局"，而不是"让 reviewer 直接否决"。
- **⑥ 与 `decide` 第 275 行的分工**：这里的 `overrideOf(...) === 'never'` 读的是**同一个会话策略**。它在这里判一次是为了避免"已经注定 `rejected` 的 ask 还要走一遍审批请求"；`decide` 里再判一次是**权威门禁**（自第 275 行的注释：只有服务自己的请求路径能保证顺序无关）。
- **⑤ reviewer 自己炸了 → `deny`**：`failed()` 产出的是 `deny`，不是 `ask`——因为"reviewer 不可用"不能变成"问问人类也许能过"。这是同一个"失败关闭"精神。

### 7.2 我用仓库构建产物做的两组最小探针（实跑）

测试套件证明的是"仓库自己认为对"；下面两组探针是**我直接调注册表**验证本课的几条核心断言。它们**不写仓库文件**：脚本落在系统临时目录，用 `node` 直接运行，导入的是仓库里**已构建**的 `lib/` 产物。

**探针 1：`snapshotJsonValue` / `deepFreeze` 的语义**（对应 §4.2、§4.5）

```
snapshot(cyclic) = undefined
snapshot(function member) = undefined
snapshot(undefined member) = undefined
snapshot(plain) = {"a":[1,{"b":"x"}]}
mutate frozen -> TypeError: Cannot add property 1, object is not extensible
isFrozen(inner array) = true
strictAssign on frozen -> TypeError: Cannot assign to read only property 'a' of object '#<Object>'
```

→ 证实："不可无损"是返回 `undefined`（**不是**抛错），由调用方决定抛出；`deepFreeze` 是**深**冻结。

**探针 2：注册表流水线的四条断言**（对应 §4.1、§4.3、§4.5）

```
PTY-DIRECT isError = true
PTY-DIRECT content = [{"type":"text","text":"Error: unknown tool \"echo\": only `run_code` is callable directly — call `echo` from inside a `run_code` program instead"}]
PTY-DIRECT preExecuteSaw = []
NESTED isError = false
NESTED preExecuteSaw = ["echo"]
GUARD-DENY isError = true
GUARD-DENY text = "Error: patched: this call was already answered"
PRE-DENY text = "Error: denied by policy"
PRE-DENY guardConsulted = []
POST-ACCEPT isError = false text = "rewritten by post-execute"
POST-BLOCK isError = true text = "do it differently" error.message = "do it differently"
RESULT observer = {"isFrozen":true,"contentFrozen":true} returned isFrozen = true
LOSSY isError = true text = "Error: tool execution arguments must be losslessly JSON-serializable"
LOSSY listenersSaw = 0
```

逐条对应：

| 观测 | 证实的结论 |
|---|---|
| `PTY-DIRECT … preExecuteSaw = []` | PTC 折叠的调用**在 pre-execute 之前**就被拒（§4.2 的 collapse 短路）；错误文本给出正确路线 |
| `NESTED isError = false` / `preExecuteSaw = ["echo"]` | 带 `parent` 的子调用**不折叠**，正常经过 waterfall |
| `GUARD-DENY text = "Error: patched: …"` | 守卫返回的字符串变成 `isError` 结果的文本（§4.3） |
| `PRE-DENY guardConsulted = []` | **pre-execute 已 deny 时守卫根本不被咨询**（§4.3 的 ★ 那一行） |
| `POST-ACCEPT` / `POST-BLOCK` | `accept` 可换内容且保持成功；`block` 翻成 `isError` 且 `error.message` 取自 feedback（§4.5） |
| `RESULT observer = {"isFrozen":true,…}` | `tools/result` 观察到的结果**已冻结**（§4.5 源码块 9） |
| `LOSSY … listenersSaw = 0` | 不可无损的参数在 `createExecution` 就被拒，**监听器一个都没被叫到**（§4.2） |

## 附录 A 关键问题与答案

> ✅ 四道题**全部给出明确答案**，不留空、不写"待补充"。Q1–Q3 第一次读就该能答；**Q4 涉及调度器失败后的补齐与崩溃尾部修复**（属于 `3.11`/`3.13` 的地盘），第一次读可以先跳过，回查时再看。

### Q1 一次工具调用经过哪些阶段？

**七段，顺序固定：**

1. **`tool/call` 落库**：agent-loop 先 `session.append('tool/call', …)` 拿到 `seq`，然后才 `prepare`（`packages\core\agent-loop\src\tool-calls.ts` 第 165–170、262–266 行）。
2. **建立执行对象**：`createExecution` 无损物化参数并 `deepFreeze`，同时**先**快照 `finalizeContent`/`projectContent` 回调（`packages\core\tools\src\index.ts` 第 1391–1481 行）。
3. **`tools/pre-execute`**：可重排 waterfall，四态 `allow | deny | cancel | ask`，默认 `allow`（第 1505–1508 行；第 607–611 行）。
4. **单调 guard**：只在 pre-execute 结果为 `allow` 时才咨询；全局层后 scope 链，取第一个拒绝原因（第 1519、1144–1154、766–773 行）。
5. **`tools/execute` + 工具主体**：环绕包装层（超时/重试/指标），信号被融合，包装层换不掉调用方取消（第 1601–1608、1564–1592、1928–1955 行）。
6. **`projectContent` → `tools/post-execute` → `finalizeContent`**：执行准备内容 → 策略 accept/block/replace → 定义自有的仅内容终检（第 1643–1648、1781–1820、1687–1692 行）。
7. **`tools/result` 通知 → 持久 `tool/result`**：emit 观察不可变结果（第 1682、1695–1714 行），然后 agent-loop 按模型顺序写持久事件（`packages\core\agent-loop\src\tool-calls.ts` 第 146–161、268–289 行）。

**一句话版（仓库自己的话）**：`tools/pre-execute → 单调 guard → tools/execute → projectContent → tools/post-execute → finalizeContent → tools/result`（`docs\subsystems\tools.zh.md` 第 182 行）。

### Q2 守卫（guard）与审批（approval）各防什么？介入条件分别是什么？

**防的东西不同——守卫防顺序，审批防授权。**

- **单调 guard（`ctx.tools.guard`）防"顺序可被利用"**：`tools/pre-execute` 是可重排 waterfall，`{ prepend: true }` 的监听器（`auto-review` 就是）能插到门禁前面；guard 跑在整个 waterfall 之后，且**没有 allow 返回值**，所以"先 deny 后 allow"这条面不存在（第 723–731 行）。
  - **介入条件**：`tools/pre-execute` 走完后决策是 `allow`（第 1519 行），且某个已注册 guard 返回了非 `undefined` 字符串。查找顺序：全局层 → scope 链（farthest first）（第 1144–1154 行）。
  - **仓库里唯一的真实用例**：`packages\subagent\subagent-in-process-driver\src\structured.ts` 第 109–111 行（源码块 21）。
- **审批（`ctx.approval`）防"危险动作没有被授权就执行"**，且**失败关闭**（零应答者 → `unavailable` → 拒绝）。两条入口：
  - **入口 A（pre-execute `ask`）**：某个 `tools/pre-execute` 监听器返回 `{ kind: 'ask' }`。生产者实例：`auto-review`（源码块 22；`packages\experimental\auto-review\src\index.ts` 第 686–721 行）、Codex/Claude-Code 钩子桥的 `permissionDecision: ask`。注册表侧叠加两道 deny（无 approval 服务、无 agent），只有 `allowed-once` 放行（第 1727–1768 行）；服务侧叠加四道（无开放轮次 → 抛；策略 `never` → 分发前拒绝；应答者抛异常/非法返回值 → `unavailable`；信号中止 → `cancelled`）（`packages\interaction\user-approval\src\index.ts` 第 217–223、267–307 行）。
  - **入口 B（沙箱升级）**：请求模式**严格更宽**时才问，且**不经过 `tools/pre-execute`**——body 内直接调 `ctx.approval.request`（`packages\sandbox\sandbox\src\escalation.ts` 第 171–208 行；bash 接线 `packages\shell\tool-bash\src\index.ts` 第 237–257 行）。同模式重试不需审批。**注意差别**：入口 A 的失败是 deny 结果，入口 B 的失败是**抛错**（最终仍是 `isError` 结果）。
- **别混进来的第三个"guard"**：`packages/guard/` 下的 `repeat-tool-reminder` 与 `timeout-policy` 既不是审批也不是单调守卫（源码块 16/17）。

### Q3 工具结果如何被 finalize 与持久化？

- **finalize（注册表侧）**：`finalizeScheduledExecution` 跑 `projectContent` → `tools/post-execute` → `finishScheduledExecution`（第 1641–1659 行）。`finishScheduledExecution` 的顺序是 `materializeFinalResult` → `finalizeContent` → **再** `materializeFinalResult` → `notifyResult`（第 1669–1684 行；两次物化分别在第 1672 与 1678 行）。`finalizeContent` 被允许改的**只有 `content`**（第 1687–1692 行），且它在调用开始就被快照，所以参数 getter 无法在物化期间把它换掉（第 1426–1437 行）。`materializeFinalResult` 做无损 JSON 快照，不通过就抛；成功结果额外挂 `value` 后整体 `deepFreeze`（第 652–659、1886–1901 行）。`notifyResult` 先把 `exec` 冻结，再 emit `tools/result`（第 1695–1714 行）。
- **持久化（循环侧）**：agent-loop 按模型顺序调 `finalize`/`finish`，再 `appendToolResult` → `session.append('tool/result', { turn, step, message, error?, meta? }, { surfaceOp: 'append', sourceEventSeqs: [callSeq] })`（`packages\core\agent-loop\src\tool-calls.ts` 第 146–161、268–289 行）。`Session.append` 先做无损 JSON 校验、再 `deepFreeze`、再 `log.push`（`packages\core\session\src\index.ts` 第 718–757 行）。事件形状见 `'tool/result'`（`packages\core\session\src\types.ts` 第 362–385 行），其中 `meta` 必须可 JSON 序列化，否则在源头被拒（第 366–373 行）。
- **物理落盘**：JSONL 后端把事件批量序列化为 JSONL 行（`packages\session\session-persistence-jsonl\src\format.ts` 第 313–315 行），后缀 `.jsonl` 或 `.jsonl.zstd`（第 42–43 行）；durable append 走 `JsonlSessionHandle.append` 与共享 append body（`packages\session\session-persistence-jsonl\src\storage.ts` 第 187–196、318–343 行），活会话通过 live write-behind 缓冲入队（第 534–539 行）。
- **顺带一条**：`additionalContexts`（如重复提醒）**不算**工具结果的一部分，它由 `commitReady` 交给 `acceptContext`，被 splice 进 `next-step` inbox（`packages\core\agent-loop\src\tool-calls.ts` 第 157 行；`packages\core\agent-loop\src\agent.ts` 第 534–537 行），所以它出现在该批结果之后，重建不需要新事件类型。

### Q4 失败步骤如何记录缺失的工具结果？（第一次读请跳过：涉及 `ask` 生产者与折叠规则之外的调度细节）

**分三类，补的都是 `isError: true` 的 `tool/result`，只是错误码与文本不同。**

1. **取消时为未启动的调用补**：`ABORTED_BEFORE_DISPATCH` / `AbortError`，同时补一条 `tool/call`，文本 `Error: tool call aborted before dispatch`（`packages\core\agent-loop\src\tool-calls.ts` 第 238–243、249–260 行）。
2. **实时步骤失败时为待处理调用补**：驱动器在每个 step 建 `ToolCallRecovery` 订阅会话事件（`packages\core\agent-loop\src\agent.ts` 第 331–334 行），catch 中把恢复结果逐条 append（第 344–349 行），追加失败抛 `AggregateError`（第 350–352 行），原始错误继续上抛；`step/end` 仍在 `finally` 中写入（第 354–357 行）。
3. **崩溃尾部 / fork seed 时补**：`interruptedTurnClosers` 在最后一个真实事件后合成结果 + `step/end` + `turn/end`，seq 连续、时间戳复用（`packages\core\session\src\repair.ts` 第 53–98、209–211 行），resume 时读日志后追加（`packages\core\agent-loop\src\index.ts` 第 852–862 行）。

**错误码怎么选**（`ToolCallRecovery.results()`，`repair.ts` 第 157–197 行）：

- 已有 `tool/call` 记录 → `TOOL_OUTCOME_UNKNOWN`（`ToolOutcomeUnknownError`）——"已记录开始但结果没落库"，结果未知（第 166–168、187–189 行）。
- 只有 assistant 消息里的 tool-call block、没有 `tool/call` → `TOOL_NOT_STARTED`（`ToolNotStartedError`）——可以安全重试（第 166–168、187–189 行）。
- 两种情况都带 `surfaceOp: 'append'`，前者还带 `sourceEventSeqs: [callSeq]`（第 191–192 行），与正常结果的写法一致。

**为什么必须补**：如果关闭步骤/轮次时还有调用没有结果，后续提供方请求就不满足"工具调用与结果配对"，而失败轮次已经关闭，崩溃尾部修复不会回头恢复它（`.agents\notes\archived\bug-fix\2026-09-19-failed-step-tool-results.zh.md` 第 10 行）；驱动器的做法就是在关闭失败步骤之前先把恢复结果记上，再传播原始失败（同文件第 14 行）。模型看到的文本明确警告不要盲目重试可能有副作用的操作（`packages\core\session\src\repair.ts` 第 32–41 行）。
