## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：把「模型看到的消息是从哪算出来的」讲死——**三条互不相同的「投影」各自是谁、边界在哪、缺了会怎样**。
**不是**：表面的完整校验规则（那是 `3.1` 的日志/格式侧）、`session/event` 的分发语义（那是 `3.2`）、turn/step 状态机（那是 `3.5`）。

### 0.2 现在只要记住这 4 件事

1. **消息不存，只存事件。** 会话是一份仅追加的事件日志，模型历史每次从日志**算出来**。
2. **算之前先过 `surface`**：只有带 `surfaceOp` 标记的事件才算「节点」，被 `replace` 遮蔽的节点从派生里消失（日志本身不删）。
3. **两条「投影」名字像、作用完全不同**：`surface` + `deriveMessages()` 决定**模型看到什么**；`ctx.sessionProjections` 是给宿主与客户端读的**读模型**，与模型请求无关。
4. **改已有消息内容要显式注册**：拿 `ctx.sessions.registerMessageProjection()` 注册一个纯解释器；**没注册就不许追加**（提交前就拒绝）。

### 0.3 明确授权：这些现在不用管

- `sessionProjections` 的**持久化面**（`checkpoint` / `restore` / `hydrate` / `viewCheckpoint`）——知道"它们是另一条面、不属于本课三个概念"就够了；
- `surface` 的**逐事件校验细则**（`sourceEventSeqs` 归属、system 头节点只能被 system 消息重写、tool 结果的错误元数据一致性）——属 `3.1`；
- `stateVersion` 的**迁移语义**——只需记住"它是持久缓存的失效版本号"。

判断标准只有一条：**只要你能回答"现在说的是哪一条投影、它在提交前还是提交后起作用"，就够了。**

## 1. 最小词汇表（本课新增的 6 个词）

| 词 | 大白话 | 在源码里的样子 |
|---|---|---|
| **event 事件** | 日志里的一行，带 `seq`（自增序号）与 `type` | `SessionEvent`；`session.log[seq]` |
| **surface 表面** | 「哪些事件是产生消息的节点、按什么顺序」这份**成员名单** | `Session.surface`；`SurfaceManager` |
| **`surfaceOp` 标记** | 事件入场时贴的一个标签，说明它是**追加**还是**替换**已有一段 | `'append'` / `{ op: 'replace', startSeq, endSeq }` |
| **node 节点** | surface 名单里的一项，存的就是某个事件的 `seq` | `SessionSurface.nodes: readonly SessionSeq[]` |
| **generation 代次** | 一个**自增计数器**，用来告诉缓存"名单变了，重建" | `replaceGeneration` / `contentGeneration` |
| **projection 投影** | 一台**纯函数机器**：`init` 出初值，然后每个已提交事件过一遍 `apply` | `ctx.sessionProjections` 的注册单元 |

> ⚠️ 这 6 个词里只有 **event** 是 `3.1` 已定义的（`3.1` 讲会话格式与仅追加日志），其余 5 个本课就地定义，**够用即可**。
> 本课还会出现 `realm`、`seam`、`settlement`、`compaction`、`lineage` —— **都不是本课要理解的词**，见附录 B 的展开课号。

## 2. 先建立画面

### 2.1 三条「投影」的从属关系（静态结构）

```
会话日志 session.log（仅追加，唯一真源；事件带 seq + surfaceOp）
│
├─① surface 折叠 ── Session.surface / SurfaceManager
│     「成员资格」：nodes = 产生消息的节点 seq，按模型可见顺序
│     追加 append → 推到尾部；替换 replace → splice 换掉被遮蔽区间
│     产出两个代次：replaceGeneration / contentGeneration
│         │
│         ├─② deriveMessages()  逐节点投影 ⇒ Message[]（模型看到的输入；带增量缓存）
│         │      └─ 逐事件规则是纯函数 deriveEventMessage(event, projectedMessages)
│         │
│         └─（另一条消费方，不参与模型历史）transcript 读「追加来源」的事件
│
└─③ sessionProjection seam ── ctx.sessionProjections（读模型，提交后才跑）
      「领域状态 / 客户端视图」：每个注册单元有自己的 cell
      与 ①② 无代码耦合：README 明说「从不组装或发送提供方请求」
```

> **精确性说明**：①③ 不是父子关系，是**两条并行的消费方**，二者只共享同一份 `session/event` 事件流。图里把它们画在同一个根下，只是表示"同源"。
> 另：`replace` 的产物自己也是一个事件（占据一个新 `seq`），它**替换的是 surface 名单，不是日志**。

### 2.2 一句话串起来（动态过程）

```
append(event)  ──► 提交前校验（缺解释器就在这里拒绝，日志还没变）
      │
      ├─ 落进 log
      ├─ surfaceManager 折一次：append 推尾 / replace 换区间 / project 盖消息
      └─ 广播 session/event ──► ctx.sessionProjections.drive() 让每个单元 apply 一次
                                        └─ 状态引用变了才重算 client view，引用没变就零下游工作
```

## 3. 大白话版：一次请求里的 messages 是怎么来的

**完全不用上面的术语**，先建立画面（来源：`packages/core/agent-loop/src/agent.ts` 第 669–686 行的请求组装代码；这里只做白话转述）。

1. 会话从一开始就只在记"发生了什么"：用户说了话、模型回了话、工具跑了、轮次开了关了。
2. 模型只能读"一条条消息"，所以每次要发请求时，得先把"哪些记录算消息"挑出来。
3. 挑的时候发现：有些记录天生不是消息（比如"轮次开始"），有些记录曾经是消息但现在被一段摘要盖掉了。
4. 于是有一份**名单**，记录"哪些记录是消息、按什么顺序"。这份名单会被两类操作改：**往末尾加一条**，或者**用新记录顶掉中间一段**。
5. 名单之外还有一件小事：插件可能想改**已有消息的内容**（例如把图片从请求里摘掉）。它不能偷偷改日志，必须登记一台"改法机器"；引擎在**写入前**先拿去试算一遍，算不出来就拒绝这次写入。
6. 名单定了，就照着名单把每条记录翻译成消息，拼成数组交给请求。名单没变时，只翻译**新加的那几条**（前面翻译过的结果留着复用）。
7. 与此同时，另有一批插件在读"领域状态"（token 用量、轮次边界……），那是给界面和宿主看的，**和发给模型的消息没有任何关系**。

## 4. 机制（每条带源码对照）

### 4.0 结论先行表：三条投影谁是谁

| 名字 | 位置（真实行号） | 干什么 | 参与模型历史派生吗 |
|---|---|---|---|
| **surface 折叠** | `Session.surface` / `SurfaceManager`（`packages/core/session/src/surface.ts` 第 612–712 行） | 维护「哪些事件是产生消息的节点、以什么顺序」 | ✅ 唯一来源 |
| **deriveMessages()** | `packages/core/session/src/index.ts` 第 856–877 行 | 把 surface 节点逐个投影成 `Message[]`，带缓存 | ✅ 就是模型看到的输入 |
| **session-projection seam** | `ctx.sessionProjections`（`packages/session/session-projection/src/index.ts` 第 199–714 行） | 领域状态 / 客户端视图的**逐会话读模型** | ❌ 不参与，README 明说「从不组装或发送提供方请求」 |

三条一句话串起来（与上一版结论一致，逐条重新核对过出处）：

1. **消息不存，只存事件。** 会话是「类型化 `SessionEvent` 组成的仅追加日志」，模型历史从日志*派生*、**从不单独存储**（`docs/subsystems/session.zh.md` 第 5 行）。
2. **派生不是简单地按 seq 遍历日志**，而是先走 surface：只有带 `surfaceOp` 标记的事件才是节点，被 `replace` 遮蔽的节点从派生里消失（`packages/core/session/src/surface.ts` 第 567–572 行）。
3. **改内容 ≠ 改节点。** 修改已有消息内容的插件必须贡献一个 `SessionMessageProjection`（同上第 35–47 行），否则追加/恢复/折叠都会被**拒绝**（第 529–531 行）。

一句话记忆：**surface 决定「有哪些消息」，deriveMessages 决定「消息长什么样」，sessionProjections 与模型历史无关。**

### 4.1 为什么存在「事件 → 消息」这一层

- 「`Session` 是一份由类型化 `SessionEvent` 组成的仅追加日志，是 agent 完整交互历史的唯一真源。LLM 消息历史从日志*派生*而来，从不单独存储；回放即从同一组事件重新派生。」（`docs/subsystems/session.zh.md` 第 5 行）
- 「**模型可见即已记录。** 每个模型请求都必须能从日志重建。新增模型可见输入需要会话事件。修改现有消息内容的插件注册纯消息投影。」（`docs/architecture.zh.md` 第 131 行）
- 设计理念原文：「其他一切——模型历史、transcript、遥测、标题、持久化——都从这条流派生。」（`packages/core/session/README.zh.md` 第 88 行）

### 4.2 surface：派生历史之前的「成员资格」层

**知识点（结论）**

- `Session.surface` 返回会话稳定的只读视图（`SessionSurface`），成员是 `nodes`（模型可见顺序的事件 seq）、`replaceGeneration`、`contentGeneration`（取值器 `packages/core/session/src/index.ts` 第 448–450 行；接口定义 `packages/core/session/src/surface.ts` 第 245–252 行）。
- 每个 `SurfaceEventType`（`system/message`、`developer/message`、`user/message`、`assistant/message`、`tool/result`）追加时**必须**带 `surfaceOp`；缺失即抛错（`surface.ts` 第 316–318 行）。
- `append` 把 seq 推到 `nodes` 尾部；`replace` 用 `splice` 原地替换被遮蔽区间（第 567–572 行）——这就是压缩（compaction）隐身旧内容的机制，日志本身**不删除**任何事件。
- 被遮蔽的节点从 `nodes` 中消失，因此也**不会**出现在 `deriveMessages()` 里；而原始事件仍留在日志中供 transcript/审计使用（`docs/subsystems/session.zh.md` 第 360 行原文：「面向人类的 transcript（文本记录）是另一个投影，读取的是日志中追加来源的事件，因为 surface 会有意遮蔽替换所概括的范围」）。

**源码：这份名单长什么样、`replace` 怎么改它** —— `packages/core/session/src/surface.ts` 第 244–261 行 + 第 562–585 行：

```ts
// ……（第 244–261 行：对外只读视图 + 内部可变折叠状态）
/** Readonly live projection of the message-producing session events. */
export interface SessionSurface {
  /** Current surface event sequences in model-visible order. */
  readonly nodes: readonly SessionSeq[]
  /** Monotonic count of committed positional replacements. */
  readonly replaceGeneration: number
  /** Monotonic count of committed replacements and plugin-owned message changes. */
  readonly contentGeneration: number
}

/** Mutable state shared by complete and incremental folds. */
interface SurfaceFoldState {
  nodes: SessionSeq[]
  replaceGeneration: number
  contentGeneration: number
  projectedMessages: Map<SessionSeq, Message>
  projections: Set<SessionMessageProjection>
}

// ……（第 263–561 行：planSurfaceEvent 等校验函数，属 3.1 的逐事件校验细则，此处省略）
/** Commit one previously validated surface transition. */
function applySurfacePlan(          // ← 第 563 行，本块开头
  state: SurfaceFoldState,
  plan: SurfacePlan | undefined,
): SurfaceFoldReplacement | undefined {
  if (plan?.kind === 'append') {
    state.nodes.push(plan.seq)                                    // ① 追加：推尾部
  } else if (plan?.kind === 'replace') {
    state.nodes.splice(plan.startIdx, plan.endIdx - plan.startIdx + 1, plan.seq)  // ② 替换：原地换区间
    state.replaceGeneration += 1
    state.contentGeneration += 1
  } else if (plan?.kind === 'project') {
    for (const [seq, message] of plan.messages) state.projectedMessages.set(seq, message)  // ③ 改内容：只盖消息
    state.projections.add(plan.projection)
    state.contentGeneration += 1
  }
  if (plan?.kind !== 'replace') return
  return {
    seq: plan.seq,
    start: plan.start,
    end: plan.end,
    shadowedSeqs: plan.shadowedSeqs,
  }
}
```

**按块讲解**

- **做什么**：把「已经校验过的过渡」落到共享状态上。三种过渡分别是追加、替换、投影。
- **与哪个知识点相关**：这是 §4.2 里「`replace` 用 `splice` 原地替换」和「两个代次」两句话的**唯一落点**。
- **变量从哪来**：`plan` 由 `planSurfaceEvent(...)` 生产（第 510–547 行），调用方是 `applySurfaceEvent`（第 558–559 行）；`plan.startIdx` / `endIdx` / `shadowedSeqs` 由 `replacementRange` 用 `state.nodes.indexOf(op.startSeq/endSeq)` 算出（第 415–435 行）。
- **为什么这么写（引作者原文）**：`replaceGeneration` 的注释是 *"Monotonic count of committed positional replacements"*，`contentGeneration` 是 *"…committed replacements **and** plugin-owned message changes"* —— 说明**两种改动都会推进 contentGeneration**，但只有位置替换推进 replaceGeneration。这就是「两代次为什么要分开」的原文依据：增量消费方要能区分「纯尾部增长」与「重写」。
- **守卫在哪**：注意 ③ 分支**不动 `nodes`** ——改内容不改变成员资格。这条与 §4.6 的契约互相印证。
- ⚠️ 注意 `plan?.kind !== 'replace'` 时才提前返回，也就是说只有替换会产出 `SurfaceFoldReplacement`（给 `foldSurface` 收集用）。

**顺带记两个贴边的行号（本次核对）**：`SurfaceManager` 类体在第 612–712 行；`foldSurface` 在第 594–609 行。

### 4.3 deriveMessages()：缓存 + 代次失效

**知识点（结论）**：`deriveMessages()` **每次调用返回新数组**，但数组里的 `Message` 对象是**共享且深冻结的**；输入是 `session.surface`（`nodes` + `contentGeneration`）与私有日志 `this.log`。

**源码：整个方法与它的三个缓存字段** —— `packages/core/session/src/index.ts` 第 831–877 行：

```ts
/** The derived-message cache: frozen projections, extended per unseen node. */
private derived: Message[] = []
/** Surface position (nodes projected) the cache has reached. */
private derivedNodes = 0
/** {@link SurfaceManager.contentGeneration} the cache was built under. */
private derivedGeneration = 0

/**
 * Derive the LLM message history by walking the ordered sequences of
 * message-producing events maintained by `surfaceOp` markers. The
 * surface is the single source of derived history: every message-producing
 * append records its `surfaceOp`, so a raw event with no marker (a chunk, a
 * turn boundary) is correctly absent, and a compaction `replace` deletes the
 * shadowed nodes from the derivation.
 *
 * CACHED: pure tail growth costs O(new nodes); a replacement or message projection
 * ({@link SessionSurface.contentGeneration}) rebuilds. The returned array is
 * a fresh snapshot per call (later appends never grow an array a caller
 * already holds); the `Message` objects in it are SHARED and **deep-frozen**.
 */
// ……（第 852–855 行的 @param/@returns 三行，与结论无关，此处省略）
deriveMessages(): Message[] {                                       // ← 第 856 行
  const surface = this.surface
  const nodes = surface.nodes
  const generation = surface.contentGeneration
  if (generation !== this.derivedGeneration) {                      // ① 代次不符 → 整块作废
    this.derived = []
    this.derivedNodes = 0
    this.derivedGeneration = generation
  }
  for (const seq of nodes.slice(this.derivedNodes)) {               // ② 只投影新增节点
    // Surface sequences are built from this.log — seq is always a valid
    // index by construction. The non-null assertion expresses that invariant.
    // oxlint-disable-next-line typescript/no-non-null-assertion
    const msg = this.deriveEventMessage(this.log[seq]!)
    // A surface node is one of the five message-producing types, but an
    // empty-content assistant/message (a max-tokens step that hosts only
    // usage) derives to null and must not enter the transcript.
    if (msg) this.derived.push(msg)                                 // ③ null 不入表
  }
  this.derivedNodes = nodes.length
  return [...this.derived]                                          // ④ 新数组、共享元素
}
```

**按块讲解**

- **做什么**：把 surface 名单上的节点按顺序翻译成消息，并**增量复用**上一次的结果。
- **与哪个知识点相关**：这是 §0.2 第 2 条与 §4.0 表格第二行那条结论的正文；也是关键问题 A2 的答案出处。
- **变量从哪来**：`this.surface` 是取值器，直接把私有的 `surfaceManager` 返回（第 447–450 行）；`derivedNodes` 就是「已经翻译到名单的第几项」；`this.log[seq]` 是同一对象里的私有日志数组（第 443 行 `private log: SessionEvent[] = []`）。
- **守卫 / 边界**：① 是**失效闸门**——只有 `contentGeneration` 变了才清空，纯尾部追加不清空；③ 的 `if (msg)` 是「空内容消息不进 transcript」的落点（注释原话点名 max-tokens 的 `assistant/message`）；④ 返回 `[...this.derived]`，因此调用方拿到的是**新数组**，后到的 append 不会偷偷长出一份调用方已经持有的数组。
- **为什么这么写（引作者原文）**：JSDoc 那句 *"CACHED: pure tail growth costs O(new nodes); a replacement or message projection rebuilds."* —— 增量与重建的取舍就是它一句话定的。
- **为什么用 `!` 断言**：作者行内注释解释「seq 由这份日志构造，按构造必然是有效下标」，所以这里不写运行时判空——**不要把它读成"可能越界"**。

### 4.4 deriveEventMessage(event)：逐事件的投影规则

**知识点（结论）**：`Session.deriveEventMessage()` 只是把请求转给 `SurfaceManager`（`packages/core/session/src/index.ts` 第 885–887 行），后者先补折未处理事件再委托给纯函数（`packages/core/session/src/surface.ts` 第 667–671 行）。

**源码：纯函数本体** —— `packages/core/session/src/surface.ts` 第 108–152 行（顶部 JSDoc 只摘与规则相关的一段）：

```ts
/**
 * Project a single event into the LLM message it derives to, or null when it
 * produces none — a non-surface event (attempt, boundary, log-only record) or an
 * empty-content system, developer, or assistant message. A caller
 * reconstructing model input supplies the same prefix's `projectedMessages`
 * from {@link foldSurface}; without that map this function reads original
 * event content.
 */
// ……（第 114–119 行：@param/@returns 四行，此处省略）
export function deriveEventMessage(                                 // ← 第 120 行
  event: SessionEvent,
  projectedMessages?: ReadonlyMap<SessionSeq, Message>,             // ← 它依赖的变量：宿主传来
): Message | null {
  const projected = projectedMessages?.get(event.seq)
  if (projected !== undefined) return projected                     // 0① 投影优先于原始事件
  // Intentionally non-exhaustive: only message-producing events derive
  // history; turn/step boundaries, failed attempts, and errors are trace/replay
  // data.
  switch (event.type) {
    // Ordinary prompts and injected context retain producer-owned framing.
    case 'user/message': {
      return event.data                                               // 0② 原样返回
    }
    // Empty system and developer nodes retain their surface positions without
    // adding wire messages. …
    case 'system/message':
    case 'developer/message':
    case 'assistant/message': {
      if (event.data.message.content.length === 0) return null         // 0③ 空内容 → null
      return event.data.message
    }
    case 'tool/result': {
      return event.data.message                                        // 0④
    }
    default:
      // A non-surface event (boundary, attempt, log-only record) projects to
      // no message. Merge-extensible union: no assertNever here.
      return null                                                      // 0⑤
  }
}
```

**按块讲解**

- **做什么**：一张**判定表**——给定一个事件，回答「它投影成哪条消息，或者干脆不是消息」。
- **与哪个知识点相关**：§0.2 第 2 条（成员资格）在**内容层面**的对应物；也是关键问题 A2「输出契约」里「空内容被过滤」的出处。

- **规则汇总另见**：`docs/subsystems/session.zh.md` 第 668–677 行（标题「派生历史：`deriveMessages()` 与 `deriveEventMessage()`」，第 672–676 行是逐条规则，第 677 行是"其余事件不投影"）。

### 4.7 session-projection seam：三个概念

概念表（Service Definition）在 `packages/session/session-projection/src/index.ts` 第 30–38 行（`ctx.sessionProjections` 的 Context 合并）与第 48–93 行（`ProjectionDefinition`）。

**① 已注册单元（registered unit）** = 一个 `ProjectionDefinition`：

- `key`、`stateSchema`、`stateVersion`、纯同步的 `init(header, inheritedEventCount)` 与 `apply(state, event)`，以及可选的 `wire: { viewSchema, view }`（第 48–93 行）。
- 契约硬性要求（第 40–47 行 JSDoc）：「All functions MUST be synchronous (an async unit would tear the carriers' consistency cut), and `state` MUST be plain JSON」。
- `apply` 对不关心的事件**必须返回同一个 state 引用**（`Object.is` 闸门，第 63–71 行 JSDoc；实现闸门在第 682 行）；`wire.view` 的原始结果用双槽缓存比较，引用不变就不发布（第 686–700 行）。
- 注册入口是 `register(definition)`，签名与两处重载在第 233–293 行；注册是**挂在调用方 fiber 上的 effect**，同一 key 的注册方共享一个 `Registration` 并计数 `refs`，最后一个卸载才删除 key（第 169–174 行 JSDoc、第 273–292 行实现）。
- 硬约束：`stateVersion` 必须是**非负安全整数**，否则抛错（第 270–272 行）；同 key 不同 `stateVersion` 直接抛错（第 279–281 行）。
- 驱动是**主动的**：构造函数只订阅一次 `session/event`（第 220–222 行），每个已提交事件都会过每个单元的 `apply`（`drive()` 第 657–704 行）。cell 惰性构建——注册晚于事件流、或会话早于注册表，都在首次触达时从 `init` 折内存日志（`cellFor` 第 615–630 行）。

**② `stateOf(session, key)`**（第 319–327 行）：

- 读**一个** host 侧单元的**类型化状态**；先把所有已注册单元的 cell 物化到当前游标（`materializeCells` 第 597–600 行），但**不计算无关的 wire view**。
- key 未注册时返回 `undefined`（第 324 行）；返回值是**活引用**，调用方不得修改（JSDoc 第 314 行）。
- 语义约定：宿主读取方要么在 `inject` 里声明 `sessionProjections`，要么在注册表/必需 key 缺失时**明确抛错**，不允许静默降级为默认值（第 190–197 行类级 JSDoc；`.agents/notes/implemented/architecture/2026-08-19-session-projection-mandatory-seam.zh.md` 第 15–17、33 行）。真实例子：plan-mode 在 `stateOf(session, 'turnBoundary')` 为 `undefined` 时抛 `plan-mode requires the turnBoundary session projection`（`packages/plan/plan-mode/src/index.ts` 第 373–374 行）。

**③ `snapshot(session, keys?)`**（第 338–352 行）：

- 返回 `ProjectionSnapshot = { asOfSeq, values }`（接口第 112–117 行）：**一次一致读切面**，只含**客户端可见**单元（无 `wire` 的单元被 `continue` 跳过，第 346 行）。
- `values[key]` 是 `wire.view` 的结果，且必须通过该单元的 `viewSchema.parse` 才能出门（第 349 行 → `viewCell` 第 707–711 行）。
- `asOfSeq` 来自 `cursorBefore(session.seq)`（第 351 行）——即 `session.seq - 1`，空日志为 `-1`（`cursorBefore` 定义在第 176–179 行）。**含义**：`asOfSeq` 是会话日志的切面，不是某个单元自身的 cell 水位；类级 JSDoc 写的是「read from the watermark cache」（第 331 行），但实现取的是日志位置。
- 低配版 `cachedSnapshot()` 只读已物化 cell、不折历史，`asOfSeq` 取所有已服务 cell 的**最小** `observedSeq`，一个都没有就返回 `undefined`（第 362–380 行）——**它不是第三个概念**，是同族的"零 I/O 提示"。
- 只读面之外还有持久化面（`checkpoint` 第 396–407 行、`restoreFloor` 第 425–435 行、`restore` 第 495–540 行、`viewCheckpoint` 第 448–469 行、`hydrate` 第 552–595 行），它们不属于本步要背的三个概念，但解释了点名的 `val` 为何是 `structuredClone`（第 403 行）——防止调用方改坏注册表的权威内存状态。

**源码：注册单元的契约本体** —— `packages/session/session-projection/src/index.ts` 第 40–93 行（两段长 JSDoc 只保留与契约有关的部分）：

```ts
/**
 * One domain's state-driven computation unit: a pure synchronous fold plus
 * declarations and an optional client view — never an opaque getter. The framework drives
 * `apply` on every committed session event; the domain holds no
 * subscriptions and owns only the computation. All functions MUST be
 * synchronous (an async unit would tear the carriers' consistency cut), and
 * `state` MUST be plain JSON (the persisted-cache precondition).
 */
export interface ProjectionDefinition<                              // ← 第 48 行
  K extends keyof SessionProjectionStateMap,
  S extends SessionProjectionStateMap[K] = SessionProjectionStateMap[K],
> {
  /** The projection key this unit owns (its `SessionProjectionStateMap` entry). */
  key: K
  /** Validates persisted state before it seeds a fold. */
  stateSchema: ZodType<S>
  /**
   * State for the empty log and its immutable Session metadata.
   * @param inheritedEventCount - exact fork-inherited prefix length.
   */
  init(header: SessionHeader, inheritedEventCount: SessionLogOffset): NoInfer<S>
  /**
   * Pure transition: previous state + one committed event → next state. A
   * unit uninterested in an event MUST return the same state reference — an
   * unchanged reference (`Object.is`) produces zero downstream work.
   */
  apply(state: NoInfer<S>, event: SessionEvent): NoInfer<S>
  /** Client view. Omit for host-only units. */
  wire?: K extends keyof SessionProjectionMap ? {                    // ← 可选 ⇒ host-only 的开关
    /** Validates the wire payload before it leaves the host. */
    viewSchema: ZodType<SessionProjectionMap[K]>
    view(state: NoInfer<S>): SessionProjectionMap[K]
  } : never
  /**
   * Persisted-cache invalidation version: bump whenever the serialized state fields or the
   * fold semantics change… Non-negative integer.
   */
  stateVersion: number
}
```

**按块讲解**

- **做什么**：定义"一个读模型单元"的**全部**契约——它拥有哪个 key、状态长什么样、怎么从初值折到当前、要不要给客户端看、缓存何时作废。
- **与哪个知识点相关**：这是关键问题 A3 三个概念里的第一个；`wire` 可选这一点直接决定 `snapshot()` 里 `if (registration.def.wire === undefined) continue`（第 346 行）。
- **变量从哪来**：`SessionProjectionStateMap` / `SessionProjectionMap` 是两张 **merge-extensible 空表**，插件用 declaration merging 往里加自己的条目（定义处 `packages/session/session-projection/src/types.ts` 第 11–24 行）。所以这个接口**不认识任何具体 key**，`key: K` 的合法值由各插件补进去。
- **为什么 `NoInfer<S>`**：`init` / `apply` 的返回值不参与 `S` 的推断，避免从实现反推泛型实参——**（标注为推断）**，依据是 `stateSchema` 已经负责校验形状，不需要再靠返回值推断。
- **为什么用 `ZodType`**：`stateSchema` 校验**持久化状态**、`viewSchema` 校验**出门前的客户端值**，两者是"持久缓存前提"与"跨进程边界"这两个不同关口的闸门。
- **约束的可执行性**：`stateVersion` 的非负整数校验与同 key 版本冲突抛错都在 `register` 里（第 270–281 行），不是靠文档喊话。

- **与哪个知识点相关**：关键问题 A3 的后两个概念；§4.7 ② 的「不计算无关 wire view」与 ③ 的「只含客户端可见单元」都在这 34 行里。
- **变量从哪来**：`registrations` 是该 service 的私有 Map（第 200 行）；`session` 由调用方给；`cursorBefore` 是文件内的工具函数（第 176–179 行）。
- **守卫**：① 未注册返回 `undefined` 而不是编一个默认值——这与「必需读取 seam 缺失必须显式失败」的约定互为两面（**注册表**层面给 undefined，**读取方**层面必须自己抛错，见 `plan-mode` 第 373–374 行）；④ 的 `continue` 是 host-only 单元不出现在客户端切面里的落点。
- **差异点（常被问）**：`stateOf()` 与 `snapshot()` **都会**先 `materializeCells(session)`；区别只在 `stateOf` 不做 ④⑤ 那一步。
- ⚠️ **一处文档口径 vs 源码口径**：类级 JSDoc 说 `asOfSeq` 是「read from the watermark cache」，实现却是 `cursorBefore(session.seq)`（**日志位置**）。本笔记按**实现**记录——判定依据：`snapshot` 的返回值必须与"同一切面"的所有 value 一致，只有日志位置能保证这一点，cell 水位可以落后（`cachedSnapshot` 就是这个落后版本，见第 375–377 行取最小值）。

**源码：驱动与惰性 cell** —— `packages/session/session-projection/src/index.ts` 第 656–704 行：

```ts
  /** Eager drive: pass one committed event through every unit; notify on changed raw view references. */
  private drive(session: Session, event: SessionEvent): void {       // ← 第 657 行
    for (const registration of this.registrations.values()) {
      let cell = registration.cells.get(session)
      if (cell !== undefined && cell.observedSeq >= event.seq) continue          // ① 已见过就跳过
      if (cell === undefined) {
        // Late build mid-stream: fold history before this event (seq = log
        // index, so the prefix slice is exact), then take the normal gate.
        cell = this.buildCell(
          registration.def,
          session.header,
          session.inheritedEventCount,
          // oxlint-disable-next-line typescript/no-deprecated -- Existing Session history read; migration deferred.
          session.snapshotEvents(SessionLogOffset(0), SessionLogOffset(event.seq)),
        )
        registration.cells.set(session, cell)
      } else {
        this.advanceCell(
          registration.def, cell, session,
          event.seq === 0 ? -1 : SessionSeq(event.seq - 1),                      // ② 只在本次事件之前推进
        )
      }
      const previousState = cell.state
      const next = registration.def.apply(previousState, event)
      const changed = !Object.is(next, previousState)                            // ③ 引用闸门
      cell.state = next
      cell.observedSeq = event.seq
      const wire = registration.def.wire
      if (changed && wire !== undefined) {                                       // ④ 只有变了才算 view
        const views = cell.views
        views[0] = views[1]
        if (this.listeners.size > 0) {
          views[1] = wire.view(next)
          if (!Object.is(views[0], views[1])) {                                  // ⑤ 原始结果引用没变 → 不发布
            const value = wire.viewSchema.parse(views[1])
            for (const listener of this.listeners) {
              listener(session, registration.def.key as Extract<keyof SessionProjectionMap, string>, value, event.seq)
            }
          }
        } else {
          views[1] = undefined
        }
      }
      // An unchanged state keeps its current view as the valid comparison
      // value for the next state change.
    }
  }
```

**按块讲解**

- **做什么**：每个已提交事件，**主动**推着每个注册单元往前走一格；引用没变的单元到此为止。
- **与哪个知识点相关**：§4.7 ① 最后两条（驱动是主动的、cell 惰性构建）的实现；也是它与 message projection「提交前解释」对照的关键——**这里完全是提交后**。
- **变量从哪来**：`drive(session, event)` 的调用方只有一个：构造函数里 `ctx.on('session/event', (session, event) => this.drive(session, event))`（第 220–222 行）；`cell` 是每个会话各自的 `UnitCell`（第 150–156 行），含 `state` / `observedSeq` / 双槽 `views`。
- **守卫**：① 幂等（同一个事件不会 apply 两次）；② 懒惰 cell 只折到"本次事件之前"，本次事件由下面的 ③ 统一处理，避免重复折一次；⑤ 是"零下游工作"的第二道闸门。
- **为什么这么写（引作者原文）**：JSDoc 头一句就是设计意图——*"Eager drive: pass one committed event through every unit; notify on changed raw view references."*；`apply` 契约里那句 *"an unchanged reference (`Object.is`) produces zero downstream work"* 是 ③ 的原文依据。
- ⚠️ **遗漏风险提示**：`views[1]` 在"没有监听者"时被写成 `undefined`（第 698 行），而注释（第 701–702 行）说明"状态未变时保留当前 view 作为下一次比较值"。两者的交互（谁负责在恢复监听者后补算）本笔记**未实测**，只如实记录代码形状。

### 4.8 修改既有消息内容的插件：注册与缺失后果

**知识点（结论）**

- 声明侧：这类事件在所属 `SessionEventMap` 成员上用 `@messageProjection` 标记，标记生成「必需处理器清单」`MESSAGE_PROJECTION_EVENT_TYPES`（清单本体在 `packages/core/session/src/known-event-types.ts` 第 84–87 行，当前只有 `'image/offload'`；标记用法实例见 `packages/compaction/compaction-image-offload/src/projection.ts` 第 16–27 行）。
- 注册侧：处理器通过 fiber 拥有的 `ctx.sessions.registerMessageProjection()` 注册（`packages/core/session/src/index.ts` 第 938–946 行）；同类型重复注册直接抛 `/already registered/`（第 939–941 行 + 测试第 70 行）。
- 契约要求「Preserve message identities and publish immutable copies without mutating the input」（`surface.ts` 第 38–46 行）；唯一的在产实例 `image/offload` 也只返回 `Map<SessionSeq, Message>`、**不新增/删除节点**（`packages/compaction/compaction-image-offload/src/projection.ts` 第 40–73 行）。
- 而 `replace` 那条路是**位置替换**，走的是 `surfaceOp: { op: 'replace', startSeq, endSeq }`（`surface.ts` 第 289–299 行的形状校验 + 第 340 行文档口径），两者不是一回事。

**源码：注册 API 本体** —— `packages/core/session/src/index.ts` 第 922–946 行：

```ts
export class SessionStore extends Service {                          // ← 本块开头（第 921 行）
  private store = new Map<SessionId, SessionEntry>()
  private counter = 0
  private readonly projections: SessionMessageProjection[] = []     // ← 它依赖的字段

  /** Borrowed definitions for detached replay; contributions live until their registering fibers unload. */
  get messageProjections(): readonly SessionMessageProjection[] {    // ← 活会话把它交给 SurfaceManager
    return this.projections
  }

  /**
   * Register one event interpreter for live creation, restore, and fork.
   * Disposing the contribution makes sessions that used it refuse further derivation.
   * @param projection - pure definition owned by the event's plugin.
   * @returns the fiber-owned disposer.
   * @throws when another definition already owns this event type.
   */
  registerMessageProjection(projection: SessionMessageProjection): () => Promise<void> {   // ← 第 938 行
    if (this.projections.some(item => item.type === projection.type)) {                   // ① 唯一性守卫
      throw new Error(`session message projection "${projection.type}" is already registered`)
    }
    return this.ctx.effect(() => {                                                        // ② 挂在调用方 fiber 上
      this.projections.push(projection)                                                   // ③ 入表（活引用！）
      return () => { this.projections.splice(this.projections.indexOf(projection), 1) }   // ④ 卸载即移除
    }, 'sessions.registerMessageProjection()')
  }
```

**按块讲解**

- **做什么**：把一个纯解释器登记进会话服务，**并保证它随注册方一起消失**。
- **与哪个知识点相关**：关键问题 A4 的「声明侧 / 注册侧」两条；`messageProjections` 这个 getter 就是 §4.6 表格里「影响 deriveMessages」的连接点。
- **变量从哪来**：`this.projections` 是 store 的私有数组；`this.ctx` 是 cordis 上下文；`SessionMessageProjection` 的接口在 `surface.ts` 第 35–47 行。
- **守卫**：① 同 type 二次注册直接抛；② 用 `ctx.effect` 而不是裸 push，**卸载路径与注册路径成对**；④ 的清理函数把**同一个对象引用**从数组里摘掉（`indexOf` 命中即删）。
- **为什么"活引用"很重要**：`surface.ts` 的 `_assertProjections()` 会拿当前活清单去比对"这个会话历史上用到过的定义"，只要有一个不在活清单里就抛错（第 698–711 行）。所以 `projections` 数组**不能**在注册时拷贝一份。
- ⚠️ 注意签名是 `() => Promise<void>`：**卸载是异步的**，所以"卸载与下一次读取"之间的时序由调用方保证（测试里用 `await fiber.dispose()`，见 `packages/core/session/tests/message-projections.spec.ts` 第 85 行）。

- **处理器改内容但不改身份**：见上面的契约引文与 `image/offload` 的返回类型。

## 附录 A 关键问题与答案

### A1 为什么不直接存消息，而要从事件投影出来？

**答案：因为会话日志是唯一真源，其它一切（模型历史、transcript、遥测、标题、持久化）都从这条流派生；直接存消息会立刻制造第二个真源。**

四条可引用的依据：

1. 「`Session` 是一份由类型化 `SessionEvent` 组成的**仅追加日志**，是 agent 完整交互历史的**唯一真源**。LLM 消息历史从日志*派生*而来，**从不单独存储**；回放即从同一组事件重新派生。」（`docs/subsystems/session.zh.md` 第 5 行）
2. 「其他一切——模型历史、transcript、遥测、标题、持久化——都从这条流派生。」（`packages/core/session/README.zh.md` 第 88 行）
3. 压缩语义要求「隐藏而不删除」：`replace` 用 `splice` 把被遮蔽节点移出 surface（`packages/core/session/src/surface.ts` 第 567–572 行），原始事件仍在日志里；README 明写「压缩会在活跃对话中隐藏被取代的条目，但**不会删除它们**」（`packages/core/session/README.zh.md` 第 12 行）。如果消息是独立存储的，压缩就得去改那份存储，回滚/审计立刻失去依据。
4. 「**模型可见即已记录。** 每个模型请求都必须能从日志重建。」（`docs/architecture.zh.md` 第 131 行）

代价与对策（同样是结论的一部分）：派生有成本，所以 `deriveMessages()` **增量缓存**——代次不变时只投影新增节点（`packages/core/session/src/index.ts` 第 860–876 行）；`replace` 或消息投影会推进 `contentGeneration`，把缓存整体作废重建（`surface.ts` 第 570–576 行 + `index.ts` 第 860–864 行）。

### A2 deriveMessages() 做什么？它从哪里取输入？

**答案：它把 surface 上「产生消息的有序事件」逐个投影成模型看到的 `Message[]`，带增量缓存、返回新数组、内部 `Message` 共享且深冻结；输入是 `session.surface`（`nodes` + `contentGeneration`）与私有日志 `this.log`，不是从别处传进来的。**

- 定义：`packages/core/session/src/index.ts` 第 856–877 行。JSDoc 第 838–855 行写明 *"Derive the LLM message history by walking the ordered sequences of message-producing events maintained by `surfaceOp` markers. The surface is the single source of derived history"*。
- 输入 1：`const surface = this.surface` → `nodes`（成员序列）与 `contentGeneration`（缓存代次），第 857–859 行；`surface` 取值器在第 448–450 行。
- 输入 2：日志本体 `this.log[seq]`（字段定义在第 443 行），按节点 seq 取事件，第 869 行。
- 逐节点规则委托给 `deriveEventMessage(event)`（第 869 行），其纯函数版本在 `packages/core/session/src/surface.ts` 第 120–152 行。
- 输出契约：返回 `[...this.derived]`（新数组，第 876 行），元素是共享的深冻结 `Message`；空内容消息被过滤（第 871–873 行）。
- 勘误已写在文首：这个函数在 `packages/core/session/src/index.ts`，**不在** `surface.ts`；`surface.ts` 里的是它调用的纯函数 `deriveEventMessage`。真正的调用方见 `packages/core/agent-loop/src/agent.ts` 第 671 行。

### A3 「投影 seam」（`ctx.sessionProjections`）的三个概念分别是什么？

**答案见下表（都在 `packages/session/session-projection/src/index.ts`）：**

| 概念 | 是什么 | 关键行号 | 三个必须记住的细节 |
|---|---|---|---|
| **已注册单元** | 一个 `ProjectionDefinition`：key + stateSchema + stateVersion + 纯同步 `init`/`apply` + 可选 `wire` | 接口第 48–93 行；注册实现第 233–293 行 | 必须同步、state 必须是纯 JSON（第 40–47 行）；不关心的事件必须返回同一引用（第 63–71 行）；注册是 fiber effect，同 key 共享并计数，最后一个卸载才移除（第 158–174、273–292 行） |
| **`stateOf(session, key)`** | 读**一个** host 侧类型化状态的**活引用**，不计算无关 wire view | 第 319–327 行 | 未注册返回 `undefined`（第 324 行）；调用方不得修改（第 314 行）；读取方必须显式失败而不是取默认值（第 190–197 行） |
| **`snapshot(session, keys?)`** | 一次一致的客户端可见切面 `{ asOfSeq, values }` | 第 338–352 行；类型第 112–117 行 | 只含带 `wire` 的单元（第 346 行）；每个值先过 `viewSchema.parse`（第 349 行）；`asOfSeq = session.seq - 1`、空日志 `-1`（第 351、176–179 行） |

补充两点差异（常被问）：

- `snapshot()` 与 `stateOf()` 都会**先物化全部单元**（`materializeCells`，第 597–600 行）；区别在于 `stateOf` 只算 host state、不算别人家的 wire view（第 311–313 行 JSDoc）。
- `cachedSnapshot()` 不是第三个概念，它是同族的「零 I/O 提示」：只读已物化 cell，`asOfSeq` 取最小 `observedSeq`，可能落后于会话（第 362–380 行）。

### A4 修改现有消息内容的插件为什么必须注册纯消息投影？缺失会怎样？

**答案：因为只有 message projection 能在提交前解释并否决一个事件，并把「改过的消息」交给标准 `deriveMessages()`；普通 session-projection 注册表做不到这两件事。**

为什么必须：

1. 声明侧：这类事件在所属 `SessionEventMap` 成员上用 `@messageProjection` 标记，标记生成「必需处理器清单」`MESSAGE_PROJECTION_EVENT_TYPES`（清单本体在 `packages/core/session/src/known-event-types.ts` 第 84–87 行，当前只有 `'image/offload'`；标记用法实例见 `packages/compaction/compaction-image-offload/src/projection.ts` 第 23 行）。
2. 注册侧：处理器通过 fiber 拥有的 `ctx.sessions.registerMessageProjection()` 注册（`packages/core/session/src/index.ts` 第 938–946 行）；同类型重复注册直接抛 `/already registered/`（第 939–941 行 + 测试第 70 行）。
3. 设计理由（官方原话）：「**使用普通的 session-projection 注册表。** 它的折叠在提交后公开领域状态。没有额外集成点，它**无法否决无效追加**，也**无法提供标准 `deriveMessages()` 内容**。」（`.agents/notes/implemented/architecture/2026-09-11-plugin-owned-message-projections.zh.md` 第 27 行）
4. 为什么不「只改发出的请求」：官方也否决了这条——「压缩、分叉和离线回放也会派生消息。发送时转换无法覆盖这些消费方。」（同上第 29 行）

缺失会怎样（三条路径，都有测试）：

| 场景 | 后果 | 出处 |
|---|---|---|
| 追加该类事件，无处理器 | `append` 抛 `session event "…" requires a message projection; load its owning plugin or supply its projection definition`，日志不变（断言 `session.seq === 0`） | `surface.ts` 第 529–531 行；`tests/message-projections.spec.ts` 第 40–43 行 |
| 用带该类事件的日志构造/恢复会话 | `Session.create` seed 校验、`foldSurface()` 同样抛错 | `surface.ts` 第 510–531 行；测试第 41–42 行 |
| 卸载已使用过的处理器后读缓存 | `deriveMessages()`、`deriveEventMessage()`、`surface.*Generation`、后续 `append` **全部**抛 `… was removed or replaced; restore the session with its owning plugin` | `surface.ts` 第 698–711 行；测试第 88–92 行 |

### A5 哪些事件不是消息？为什么？

**答案：三类。**

1. **没有 `surfaceOp` 标记的事件**（`turn/start`、`turn/end`、`step/*`、`assistant/attempt`、`llm/retry`、`request/header`、`request/context` 等）——它们根本不进 surface 名单，因此 `deriveMessages()` 的循环不会碰到它们。依据：`surface.ts` 第 126–128 行注释原文 *"only message-producing events derive history; turn/step boundaries, failed attempts, and errors are trace/replay data"*；`default: return null`（第 147–151 行）。
2. **内容为空的 `system/message` / `developer/message` / `assistant/message`**——它们是 surface 节点（`nodes` 里有），但投影为 `null`，被 `if (msg)` 丢掉。依据：`surface.ts` 第 141 行 + `packages/core/session/src/index.ts` 第 870–873 行注释（点名的场景是 max-tokens 步骤只承载 usage）。
3. **被 `replace` 遮蔽的节点**——它们**曾经**是消息，但已经被移出 `nodes`，所以不在派生里；原始事件仍留在日志中（`surface.ts` 第 567–572 行；`docs/subsystems/session.zh.md` 第 360 行）。

判定表（一张图记住）：

| 事件 | 在 `nodes` 里吗 | `deriveEventMessage` 返回 | 模型看得到吗 |
|---|---|---|---|
| `turn/start` / `step/*` / `assistant/attempt` | ❌ | `null`（default） | ❌ |
| 空的 `assistant/message`（max-tokens） | ✅ | `null`（内容长度 0） | ❌ |
| `user/message` | ✅ | `event.data` | ✅ |
| `assistant/message`（非空） / `tool/result` | ✅ | `event.data.message` | ✅ |
| 被 `replace` 遮蔽的旧节点 | ❌（已 splice 掉） | ——（不在循环里） | ❌ |
| 有投影覆盖的 seq | ✅（成员不变） | 投影产出的 `Message` | ✅（改过的版本） |

### A6 会话事件与 agent 事件，哪一个在进程重启后还在？为什么分两个域？（第一次读请跳过）

> ⚠️ **第一次读请跳过本节**：它属第三编后面几节的内容。

**答案：重启后仍在的是会话事件；agent 事件是进程本地的实时事件。**
出处（文档）：`docs/architecture.zh.md` 第 74–80、113、127 行。

| 域 | 性质 | 使用判据 |
|---|---|---|
| **会话事件** | 追加到日志、经 `session/event` 广播的**持久事实** | "当某个事实**必须在重新加载后仍然存在**时，使用它" |
| **agent 事件** | 携带**活跃 Agent**：inbox、步骤、状态、请求、验证、续跑 | "要**观察或拦截进行中的工作**时，使用它" |
| **能力事件** | `fs/*`、`tools/*`、`telemetry/*` | 不引入循环依赖就想挂策略与适配器时 |

**为什么必须分域**：实时流式帧**高频、瞬态**（`agent/assistant-stream` 发布进程本地的 start、瞬态 chunk、end frame），逐个写日志会爆炸。所以把**过程**与**事实**分离：收尾时把完整紧凑 stream **一次性**提交为 `assistant/message`（或仅日志的 `assistant/attempt`）。提交后 fork、恢复、transcript、遥测、持久化都从这些持久 settlement 派生；实时 UI 增量则来自 `agent/assistant-stream`。边界情形：进程在 settlement 之前**硬中断**，**不会**留下持久 attempt stream。
→ 与本课的关系：`assistant/attempt` **不是** surface 事件，所以它也**不会被投影成消息**（见 A5 第 1 类）。展开时机：`3.8`（流式、重试与计量）。

### A7 压缩（compaction）改的是消息还是日志？（第一次读请跳过）

> ⚠️ **第一次读请跳过本节**：压缩机制属 `3.12`。
**答案：改的是 surface 名单（遮蔽 + 位置替换），不改日志。**
机制：`replace` 带 `surfaceOp: { op: 'replace', startSeq, endSeq }`，命中的区间用 `splice` 换成新事件，`replaceGeneration` 与 `contentGeneration` 各 +1（`packages/core/session/src/surface.ts` 第 567–572 行）；原始事件全部保留在日志里（`packages/core/session/README.zh.md` 第 12 行）。因此"压缩后还能审计原对话"这件事不需要额外备份——它就是日志。展开时机：`3.12`。

### A8 subagent 的会话会不会影响父会话的派生？（第一次读请跳过）

> ⚠️ **第一次读请跳过本节**：subagent 与 lineage 属 `3.14`。
**答案：不会。** `deriveMessages()` 只读**本会话对象**的 `this.log` 与 `this.surface`（`packages/core/session/src/index.ts` 第 857–869 行），跨会话的关系由 header 里的 lineage 数据表达，不进入本会话的 surface 名单。**（标注为推断）**：本课只核对了"派生输入是本会话私有字段"这一点；lineage 如何在更高层被使用，本课**未读**，故不展开。展开时机：`3.14`。
