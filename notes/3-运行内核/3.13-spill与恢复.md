## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：一条链路的完整交代——**什么东西会被写出去、写到哪、谁来写、断了电之后靠什么找回来**，以及**日志尾部被中断时谁负责修**。
**不是**：上下文压缩策略本身（那是 `3.12`）、工具执行流水线（`3.10`）、会话日志的物理格式细节（`3.6` 与 `docs/subsystems/persistence.zh.md`）。

### 0.2 现在只要记住这 4 件事

1. **spill = 把「太大、塞不进上下文、但必须还能取回」的文本写到会话之外**，回给模型的三件套是：不透明定位信息 `locator` + 精确字节数 `bytes` + 取回指引 `retrievalHint`。
2. **两处触发**：① 工具最终结果估算 token **超过 `maxInlineTokens`**（内置 base 组合是 `12500`）；② **会话引用的预览被截断**。两者都走同一个缝 `ctx.spillStore.saveText()`。
3. **恢复不靠表**：spill 产物是**宿主文件系统上的普通文件**，本身跨进程存活；会话日志里只留一条**普通工具结果消息**，里面写着路径 + read/grep 指引。恢复 = 重放那条消息 → 模型按路径把文件读回来。
4. **日志侧的中断修复是读方的活**：持久化只保**物理有效前缀**，语义配平由纯函数 `openTurnClosers(events, cause)` 完成——**恢复**用 `interrupted`，**fork** 用 `forked`。

### 0.3 明确授权：这些现在不用管

- **`ToolCallRecovery` 的逐事件状态机**（`assistant/message` → `tool/call` → `tool/result` 的配对规则）——第一次读只需知道它的**结论**：未应答的调用会补一条 `isError: true` 的结果，错误码二选一。逐行细节在 §7.1，回查时再看；
- **PTC（program-to-call）那条异步日志分支**——它复用同一个上限函数，但走 `tools/ptc-dispatch-log` 而不是 `tools/post-execute`。本课只在 §5.1 点一下它的存在（展开于 `3.9`/`4.7`）；
- **v3→v4 迁移**与 `session/end-seed`——属于 `3.6`。本课只在 §7.4 用它们划一条**反例边界**；
- **附件存储的生命周期**——本课只需知道一句：图片**字节不进 spill 文件**，文件里只记可读路径（展开于 `3.9`）。

### 0.4 本课依赖前文词汇

`seam`（能力接缝）、`ctx.<键>`（服务）、`turn` / `step`、`session/event`（持久会话事件）这几个词已由 `1.1` / `1.2` / `1.4` 定义，本课不重复。若你对"`ctx.spillStore` 是怎么挂上去的"没有画面，先看 `1.2` §5.2。

## 1. 最小词汇表（本课新增的 6 个词）

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **spill** | 把**塞不进上下文但必须还能取回**的文本写到会话之外的一个文件里 | `spillStore.saveText(...)` |
| **locator** | 回给模型的**不透明定位信息**。本地后端就是文件路径，远程后端可能是 URI／键 | `SpillRef.locator`（类型 `SpillLocator`，品牌化字符串） |
| **retrievalHint** | 回给模型的**取回指引**——告诉它「拿什么工具、怎么读」 | `'Use read with offset/limit, or grep this path to search within it.'` |
| **spill owner** | 保存时的**命名空间**（哪个会话名下存）。**不是访问控制** | `SpillOwner.sessionId` |
| **closer** | 日志尾部被中断时，事后**补上去的合成闭合事件**（缺的工具结果、`step/end`、`turn/end`） | `openTurnClosers(events, cause)` 的返回值 |
| **torn tail** | 日志**物理上撕裂的尾部**——一次从未完成的 append 留下的半个记录 | `tornTruncateTo` / `recoveredTail` |

> ⚠️ **术语统一**：本笔记之后只用上面的英文正名（`spill` / `locator` / `retrievalHint` / `owner` / `closer` / `torn tail`）。「溢出」「落盘」这类中文词只在需要形容动作时出现一次，不作为名词使用。

## 2. 先建立画面

### 2.1 三个包、一个 seam、两处触发（静态结构）

```
        ┌─────────────────────────── 能力接缝（seam）───────────────────────────┐
        │  @deepseek-ai/dsh-spill     ctx.spillStore = 抽象服务 SpillStore        │
        │  只有一个方法：saveText(input) → Promise<SpillRef>                     │
        │  不负责：保留策略 / 结果替换 / 取回与搜索 API                            │
        └───────────────▲────────────────────────────────────▲─────────────────┘
                        │ 实现                                │ 取用
        ┌───────────────┴──────────────┐      ┌──────────────┴──────────────────┐
        │ dsh-spill-local（本地后端）    │      │ 两个触发面（互不重叠）            │
        │ 写到 <root>/session-<hash>/…  │      │ A. dsh-spill-policy             │
        │ 私有 0700 / 独占 0600 / 随机名 │      │    tools/post-execute waterfall  │
        └───────────────────────────────┘      │    超过 maxInlineTokens 就替换   │
                                               │ B. session-reference            │
                                               │    引用预览被截断时自己调用      │
                                               └─────────────────────────────────┘
```

**精确性说明**：`dsh-spill-policy` 不是"spill 的执行者"，它只是**决定何时**替换工具结果；真正写文件的是后端。seam 本身**只有一个方法**，所以"谁来存、何时存、怎么取回"这三件事分别属于三个不同的包。

### 2.2 一次超预算的工具结果，从产生到取回（动态过程）

```
① 工具执行完，产出完整文本（可能含图片位置）
        │
        ▼
② spill-policy 在 tools/post-execute 上先 await next()，拿到已接受的结果
        │
        ├── 结果 ≤ maxInlineTokens ──▶ 原样通过（不写文件）
        │
        ▼ 超过 maxInlineTokens
③ ctx.get('spillStore').saveText({ owner, source, suggestedName, content: 全文 })
        │
        ▼
④ 后端写文件：<root>/session-<sha256 前 12 位>/<6 字节随机>-<安全名>
        │
        ▼
⑤ 调用方把「首尾预览 + 省略提示」放回上下文
   提示里带着 locator + retrievalHint（这就是唯一的持久载体）
        │
        ▼
⑥ 这条工具结果消息作为普通事件进入会话日志（普通消息，不是特殊事件）
        │
        ▼  ── 进程可能在这里崩溃/重启 ──
        │
⑦ 之后任何一次重放这条消息：模型看到路径 → 自己 read / grep 把文件读回来
```

### 2.3 大白话版：一份太大的报告，怎么做到「拿走了还找得回」

**完全不用上面的术语**，先建立画面。（来源：本节是把 `packages/spill/spill/src/index.ts` 第 1–15 行的模块注释、`packages/spill/spill-policy/README.zh.md` 第 49–57 行的行为说明，以及 `packages/spill/spill-local/README.zh.md` 第 50 行的字段说明，改写成不带术语的流程。）

1. 某个工具（比如取网页）交回来一份很长的报告，远超这次对话能承受的篇幅。
2. 负责"篇幅把关"的插件比对预算，发现超了。
3. 它把**完整报告**交给一个"代存服务"，附上三样信息：这份东西属于哪个会话（owner）、它是谁产出的（source）、建议的文件名（suggestedName）。
4. 代存服务把它写成宿主机器上的**一个新文件**，文件名带随机前缀，目录按会话归拢，权限只有自己能读。
5. 服务回三个东西：文件在哪、一共多少字节、以及"你之后用读文件／搜索文件的工具去看它"。
6. 把关插件把原报告换成**头一段 + 中间省略号 + 尾一段**，并在末尾贴一张"便条"，上面写着文件在哪、怎么读。
7. 这张便条就留在对话记录里，跟着记录一起被持久保存——**没有另一本账**。
8. 之后模型想看全文，就按便条上的路径去读；进程重启也不影响，因为文件本来就在磁盘上，不在内存里。

## 3. 结论先行（五条）

**① spill 是什么**：把「太大、不能塞进模型上下文、但必须仍可取回」的文本写到会话之外，返回**不透明定位信息 + 精确字节数 + 取回指引**三件套。seam 只有一个方法 `saveText`；它**不负责**保留策略、结果替换、取回/搜索 API（源码：§4.1，`packages/spill/spill/src/index.ts` 第 8–15、29–44 行）。

**② 什么时候 spill**：两个互不重叠的触发面——(a) 工具最终结果估算 token 超过部署预算 `maxInlineTokens`（内置 base 组合是 `12500`），由 `dsh-spill-policy` 替换成「首尾预览 + 省略提示」；(b) 会话引用（session-reference）的已捕获 transcript 被截断时，由它自己直接调用 `ctx.spillStore.saveText()`。

**③ 恢复靠什么**：spill 的**产物不在会话日志里，它在宿主文件系统上**，因此它本身就跨进程存活；会话日志里只留一条**普通工具结果消息**，里面写着那段文件的路径 + read/grep 指引。恢复 = 重放那条消息 → 模型再按路径把文件读回来。**没有第二个持久登记表，也没有 seam 级的按会话清理或失效 API**（`docs/persistence-catalog.zh.md` 全文 0 处 `spill`；`packages/spill/spill/README.zh.md` 第 135–136、152 行）。

**④ 能力边界（最容易踩的一点）**：`dsh-spill-local` 的默认根目录是**每次进程延迟创建的私有临时目录** `mkdtempSync(join(tmpdir(), 'dsh-spill-'))`。不显式配置 `root` 时，下一个进程不会回到旧根，旧定位信息指向的文件**不再被新进程主动管理**——只有下一次启动清理会按年龄回收它。要「重启后仍按定位信息取回」，必须配置一个稳定的 `root`。

**⑤ 「恢复」与「fork」共用同一份持久 settlement**：两者都调用同一个纯函数 `openTurnClosers(events, cause)`，只是 `cause` 不同（`{kind:'interrupted'}` / `{kind:'forked'}`）。

## 4. 契约层：一个方法、三个字段（源码对照）

### 4.1 整个 seam 就是「一个抽象方法 + 三条必须遵守的语义」

**位置**：`packages/spill/spill/src/index.ts` 第 23–56 行（类体与声明合并；第 1–15 行的模块注释是本课的权威表述，下面摘其要句）

```ts
// （第 1–15 行模块 JSDoc：说明这是 `ctx.spillStore` 的 Service Definition、
//   只定义"后端做什么"不说"怎么做"，并列出它不负责的三件事；此处只留结论，不整段照录）
import { Context, Service } from '@deepseek-ai/cordis'
import type { SaveTextSpill, SpillRef } from './types.ts'
// （第 20–21 行：re-export `SpillLocator` 与四个类型，供消费方使用）

declare module '@deepseek-ai/cordis' {          // ← 声明合并：把一个键挂到共享上下文上
  interface Context {
    spillStore: SpillStore
  }
}

/**
 * Abstract spill storage service. Subclass, implement {@link saveText}, and load
 * the subclass as a plugin — it registers as `ctx.spillStore` (one
 * implementation per context; loading a second throws, cordis' standard
 * duplicate-service behavior).
 *
 * Semantics every implementation must honor:
 * - {@link saveText} persists the FULL `content` verbatim and returns an opaque
 *   locator, exact byte length, and model-facing retrieval guidance.
 * - Storage is scoped by the request's {@link SaveTextSpill.owner} session; the
 *   backend chooses a private (not world-readable) location and a collision-free
 *   name derived from — never equal to — the caller's `suggestedName`.
 * - `saveText` REJECTS on a real storage failure (permissions, ENOSPC, backend
 *   unavailable); the caller decides how to degrade (the spill policy treats a
 *   rejection as best-effort and keeps the inline result).
 */
export abstract class SpillStore extends Service {
  constructor(ctx: Context) {
    super(ctx, 'spillStore')                     // ← 这一句决定了它的 ctx 键叫 spillStore
  }

  /**
   * Persist `input.content` to a session-scoped spill artifact.
   * @param input - the owner, caller-supplied source fields, suggested name, and full text to save.
   * @returns the saved artifact's {@link SpillRef}; rejects on a storage failure.
   */
  abstract saveText(input: SaveTextSpill): Promise<SpillRef>
}

export default SpillStore
```

按块讲解：

- **`extends Service` + `super(ctx, 'spillStore')`**：一个包要"贡献一项具名能力"，做法就是定义一个继承 `Service` 的类并在构造里注册键名。所以 §2.1 图里那个 `ctx.spillStore` 不是文档起的名字，是**代码里写死的字符串**——想知道某个 `ctx.<键>` 是谁提供的，搜这个字符串。
- **`abstract saveText`**：seam 只声明"必须能存一段文本"，不规定怎么存。这就是为什么 `spill-local`（文件系统）与"未来的远程/数据库后端"能并列存在同一缝上。
- **三条 `Semantics every implementation must honor`（作者原文）** 是本课最重要的三句话：
  1. *persists the **FULL** `content` verbatim* —— 存的是**逐字全文**，不是摘要、不是截断；
  2. *the backend chooses a private (not world-readable) location and a collision-free name derived from — **never equal to** — the caller's `suggestedName`* —— `suggestedName` 只是**提示**，后端必须自己造一个安全的、不会撞的名字；
  3. *`saveText` **REJECTS** on a real storage failure … the caller decides how to degrade* —— 缝只负责"如实失败"，降级策略归调用方。
- **模块 JSDoc 的"不负责清单"**（第 8–12 行）：*"It owns NO retention policy (that is `@deepseek-ai/dsh-output-retention`), NO tool-result replacement (that is `@deepseek-ai/dsh-spill-policy`), and NO retrieval or search API."*——**取回没有 API**，这是 §3 ④ 与 §9.2 那两条"能力边界"的源头。
- **一个实现 per context**：加载第二个实现会按 cordis 的重复服务惯例抛错。所以"换后端"是**组装期**的决定，不是运行期切来切去。

### 4.2 四个词的确切形状（`SpillRef` / `SpillOwner` / `SpillSource` / `SaveTextSpill`）

**位置**：`packages/spill/spill/src/types.ts` 第 30–39 行（`SpillOwner` —— **谁的东西**；`SaveTextSpill` / `SpillRef` 见下面第二段，回答的是另一个问题：**一次请求/一次回执长什么样**。两段合起来覆盖第 30–80 行，分开是因为合在一起超过"能自解释"的粒度上限）

```ts
/**
 * Save-time storage namespace for a spilled artifact. The session id lets a
 * backend group storage under the producing session, but the returned
 * {@link SpillLocator} is the model-facing handle. Forked sessions inherit
 * locators already present in the seeded log; those artifacts are not copied or
 * re-owned, and spills produced after the fork use the child session id.
 */
export interface SpillOwner {
  sessionId: SessionId
}

/**
 * Producer of a spilled artifact. Tool results carry their model-issued call id;
 * session references identify the captured source session instead. Descriptive
 * source description only, never access control.
 */
export type SpillSource = {
  kind: 'tool'
  /** The tool whose result was spilled (e.g. `web_fetch`). */
  toolName: string
  /** The model-issued call id the result belongs to. */
  callId: ToolCallId
  /** A short human label for the artifact (e.g. `result`). */
  label: string
} | {
  kind: 'session-reference'
  /** Session whose projected conversation was captured. */
  sessionId: SessionId
  /** Host-provided label for the referenced session. */
  label: string
}
// （第 13–28 行的 SpillLocator 品牌化类型与它的构造函数、第 1–7 行的模块注释，与"谁的东西"无关，此处省略）
```

**位置**：`packages/spill/spill/src/types.ts` 第 62–80 行（一次请求与一次回执）

```ts
/** One request to persist text to a spill artifact. */
export interface SaveTextSpill {
  owner: SpillOwner
  source: SpillSource
  /**
   * A caller-suggested base name (e.g. `web_fetch.txt`). The backend sanitizes
   * it to a single safe path segment before use — it is a hint, never a path.
   */
  suggestedName: string
  /** The full text to persist (UTF-8). */
  content: string
}

/** A saved spill artifact: its locator, byte length, and backend-specific retrieval guidance. */
export interface SpillRef {
  locator: SpillLocator
  bytes: number
  retrievalHint: string
}
```

按块讲解：

- **第一段：`SpillOwner` 的 JSDoc 直接回答了"fork 之后怎样"**（作者原文）：*"Forked sessions inherit locators already present in the seeded log; those artifacts are **not copied or re-owned**, and spills produced after the fork use the **child session id**."* → 这是 §Q4 那条结论的出处本体。
- **`SpillSource` 是两种形态的和类型**：`kind:'tool'` 带 `toolName/callId/label`（工具结果）；`kind:'session-reference'` 带被引用会话的 `sessionId` 与 `label`（**不伪造工具调用 id**）。
- **`SpillSource` 的 JSDoc 写死了一句边界**：*"Descriptive source description only, **never access control**."* → 与 `SpillOwner` 的 JSDoc 合起来，就是"会话 id 只是命名空间，不是权限"。
- **第二段：`suggestedName` 的两处原文**：`it is a hint, never a path`（类型 JSDoc）与"后端必须先把它净化成单个安全路径段"。§6.2 的 `encodeSegment` 就是这句的落地。
- **第二段：`SpillRef` 就是那三件套**：`locator`（不透明）、`bytes`（精确长度）、`retrievalHint`（取回指引）。**三个字段缺一不可**——少了 `bytes`，模型无法判断"要不要读"；少了 `retrievalHint`，消费方就得自己猜后端能怎么读。

### 4.3 真实产品配置：内置 base 组合的挂载点

**位置**：`packages/bundle/base/cordis.patch.yml` 第 404–410 行（完整未删节；上下文是它所在的 group 条目内部）

```yaml
    - id: spill-local
```

按块讲解：

- **`spill-local` 不带 `config`**：所以它用默认的**每进程私有临时根**（§6.1）。这正是 §3 ④ 那条边界的**产品层面证据**——默认部署下根目录是易失的。
- **`spill-policy` 带 `maxInlineTokens: 12500`**：这就是 §3 ② 里"内置 base 组合是 12500"的确切来源。它是个**组装期常量**，不是代码里的默认值——源码里 `maxInlineTokens` 是可选字段，**不配就整个策略不安装**（§5.1）。
- **两条 `- id:` 前面缩进 4 格**：说明它们被 `insert` 进某个 group 条目的 `config` 数组里（patch 的插入语义，见 `1.2` §4.1），不在顶层。

### 5.1 两个监听器：先 `next()`，再限制已接受内容

**位置**：`packages/spill/spill-policy/src/index.ts` 第 133–156 行（`apply` 函数体的最后一段；第 48–54 行的预算解析是本块依赖的变量来源）

```ts
  ctx.on('tools/post-execute', async (exec, result, next): Promise<PostToolDecision> => {
    const decision = await next()                              // ← 先委托：拿到别人处理过的决策

  ctx.on('tools/ptc-dispatch-log', async (dispatch, next): Promise<ContentBlock[]> => {

```

依赖变量从哪来：

- `ctx` / `config` 是 `apply(ctx, config)` 的入参；`maxTokens` 在第 54 行由 `config.maxInlineTokens` 落成局部常量（第 49–53 行先做 `undefined` 与合法性判断，**`undefined` 时第 50 行直接 `return`——整条策略不安装**）。

按块讲解：

- **① 委托顺序是「先 `next()` 再限制」**：这是本策略的第一个设计决定。它让**别人先有说话的机会**（例如别的守卫把结果改成错误、或直接替掉值），本策略只在**最终被接受的内容**上动手。所以 `decision.kind !== 'accept'` 直接返回——**被拒绝的结果不 spill**，它压根不会进上下文。
- **② 三个前置守卫，各自防一件事**：
  - `Object.hasOwn(decision, 'value')`：别人已经用 `value` **整块替换**了结果 → 不重复处理（"值替换"这一条否证，见 §9.1）；
  - `exec.name === 'read'`：**`read` 的结果不限制**。理由在文档里：*"`read` 的模型可见结果跳过自动省略，避免重复读取产生循环"*（`.agents/notes/implemented/architecture/2026-07-08-tool-output-spill-files.zh.md` 第 69 行）。**如果没有这个守卫，模型读 spill 文件这件事本身又会被 spill 一次，形成死循环。**
  - `exec.parent !== undefined && !hasImages`：纯文本的 PTC 子调用走**另一条异步日志分支**（下面那个 `tools/ptc-dispatch-log`），不在这里同步处理。
- **③ `{ prepend: true }`**：本监听器插到 waterfall **最前面**。因为 waterfall 是顺序传递的链，`prepend` 保证"先 `next()` 拿到最终结果"这个语义成立。
- **④ `label` 是 `'result' | 'dispatch'`**：同一个 `bound` 被两个入口复用，靠 `label` 区分产物是"工具结果"还是"PTC 分发日志副本"——这个值最终会进 `SpillSource.label`。
- **⑤ 第二段 `tools/ptc-dispatch-log`**：`await next()` 之后再 `bound(...) ?? content`。注意 `bound` 返回 `undefined` 表示"没替换"，所以用 `?? content` 兜回原值。**这两段合起来就是"两处触发面"里的 A 面完整形态。**

### 5.2 预算判定与替换：`bound()` 里的五步（本课最重要的一段）

**位置**：`packages/spill/spill-policy/src/index.ts` 第 90–131 行（`bound` 整个函数；它依赖的 `retainable` 在第 37–39 行、`GAP` 在第 41 行、`pricing` 在第 57–75 行、`fullText` 在第 77–88 行）

```ts
  /** Recoverably bound one display copy; failures leave successful tool content visible. */
  async function bound(
    exec: ToolExecution, content: ContentBlock[], toolName: string, callId: ToolCallId, label: 'result' | 'dispatch',
  ): Promise<ContentBlock[] | undefined> {
    if (!retainable(content)) return undefined                  // ① 有不可切分的块类型 → 不处理
    try {
      const images = content.filter((block): block is ImageBlock => block.type === 'image')
      const price = pricing(exec, images)                       // ② 按模型路由取计价函数
      if (content.reduce((total, block) => total + price(block), 0) <= maxTokens) return undefined   // ③ 预算内 → 放行
      const owner = (exec as SpillPolicyExec).agent?.session.header.id
      if (owner === undefined) throw new Error(`no session owner for ${toolName} ${label}`)
      const spillStore = ctx.get('spillStore')                  // ④ 没有后端 → 抛错，被下面 catch 兜住
      if (spillStore === undefined) throw new Error('no ctx.spillStore backend loaded')
      const ref: SpillRef = await spillStore.saveText({
        owner: { sessionId: owner }, source: { kind: 'tool', toolName, callId, label },
        suggestedName: `${toolName}.txt`, content: fullText(content),
      })
      const totalBytes = content.reduce((total, block) => total + (block.type === 'text' ? Buffer.byteLength(block.text, 'utf8') : 0), 0)
      const notice = (bytes: number, count: number): Extract<RetainableBlock, { type: 'text' }> => ({
        type: 'text', text: formatSpillNotice({ kind: 'exact', count: bytes }, ref, count),
      })
      const worstNotice = notice(totalBytes, images.length)
      const reserved = price(GAP) + price({ type: 'text', text: `\n\n${worstNotice.text}` })
      if (price(worstNotice) > maxTokens) throw new Error(`spill notice for ${toolName} exceeds maxInlineTokens`)
      const retained = retainContent(content, Math.max(0, maxTokens - reserved), price)   // ⑤ 首尾保留
      const footer = notice(retained.omittedBytes, retained.omittedImages)
      const result = retained.head.length + retained.tail.length === 0
        ? [footer]
        : [...retained.head, GAP, ...retained.tail, { type: 'text' as const, text: `\n\n${footer.text}` }]
      // Adjacent text has one framing cost on the wire and in the spill preview.
      const merged: ContentBlock[] = []
      for (const block of result) {
        const previous = merged.at(-1)
        if (block.type === 'text' && previous?.type === 'text') previous.text += block.text
        else merged.push(block.type === 'text' ? { ...block } : block)
      }
      return merged
    } catch (error: unknown) {
      ctx.logger.warn(`spill-policy: ${String(error)}; keeping the inline content`)
      return undefined                                          // ⑥ 任何失败 → 保留原内联内容
    }
  }
// （第 37–39 行的 retainable 与第 41 行的 GAP 是本块依赖的定义，见正文说明；
//   第 57–88 行的 pricing / fullText 见 §5.3 与 §5.4，此处不重复照录）
```

依赖变量从哪来：

- `maxTokens`：`apply` 第 49–54 行从 `config.maxInlineTokens` 解析出的闭包常量；`undefined` 时整个 `apply` 已提前返回，所以这里必然有值。
- `retainable(content)`：第 37–39 行的类型守卫，`content.every(block => block.type === 'text' || block.type === 'image')`——**只接受 text / image 两种块**，其余一律不碰。
- `price(block) => number`：`pricing(exec, images)` 返回的闭包。图片按**当前模型路由**的图片计价器算，文本走 `estimateContent`；模型路由取自 `exec.agent?.session.requestHeader()?.config`，回退到 `exec.agent?.options`（第 60–62 行）。
- `retainContent` / `formatSpillNotice`：分别来自 `./retention.ts` 与 `./notice.ts`（第 18–19 行导入）。

按块讲解（六步，对应 §2.2 的 ③④⑤）：

- **① `retainable` 守卫**：结果里只要出现第三种块类型（例如工具自定义块），整块**放弃处理**、原样通过。这是"不重写不支持的块"的字面落地。
- **② 计价函数是一次性的**：`pricing()` 会先把所有图片的价格**预先算好放进 Map**（第 58–73 行），返回的闭包只做查表。这样后面二分查找时不用重复请求计价器。
- **③ 判据是 `<= maxTokens` 就 `return undefined`**：注意**返回 `undefined` 表示"不替换"**，不是"失败"。这条判据是 §9.1"触发条件"的第一条的出处本体——**超过才 spill，等于不 spill**。
- **④ `ctx.get('spillStore')` 而不是静态 `inject`**：spill 是**可选能力**。取不到就 `throw`，由 ⑥ 的 `catch` 兜住——**注意这不是"启动失败"，是"这次不替换"**。
- **⑤ 保留预算要先扣掉"提示本身"**：`reserved = price(GAP) + price(提示)`，然后 `retainContent(content, maxTokens - reserved, price)`。所以最终内容和提示加起来仍在上限内。`worstNotice` 用**最坏情况**（省略全部字节 + 全部图片）估一次，`price(worstNotice) > maxTokens` 时**直接抛错**，同样落到 ⑥——这解释了文档那句"连提示也超出上限时保留原内容"。
- **⑥ 一个 `catch` 管住所有降级**：缺 owner、缺后端、后端 reject、图片没有可读路径、提示放不下——**全部只记 `warn` 并返回 `undefined`**。作者在 JSDoc 里写了理由：*"failures leave successful tool content visible"*（第 90 行）。**所以 spill 失败绝不会把一次成功的工具调用变成 `isError`，也不会隐藏内容。**
- **末尾的 `merged` 循环**：把相邻的 text 块合并成一块。注释原文 *"Adjacent text has one framing cost on the wire and in the spill preview."*——不合并的话，每个块都要付一次"消息框架"的 token 开销，预算会算不准。

### 5.3 存进文件的到底是什么：`fullText()` 与图片位置

**位置**：`packages/spill/spill-policy/src/index.ts` 第 77–88 行（`fullText` 整个函数）

```ts
      if (block.type === 'text') return block.text

      return `\n[Image: ${JSON.stringify(access.readonlyPath)}; ${block.attachment.mediaType}; ${block.attachment.width}x${block.attachment.height}. Use read_image to view it.]\n`
```

按块讲解：

- **这是一个"投影成纯文本"的函数**：按**原顺序**遍历内容块，文本块原样拼接，图片块换成一行**描述 + 可读路径**。
- **图片位置的格式是固定模板**：`[Image: "<可读路径>"; <mediaType>; <宽>x<高>. Use read_image to view it.]`。所以 spill 文件里**有图片的地址，没有图片的字节**——字节仍留在附件存储里。

### 5.4 首尾保留的确切规则：`retainContent` 与代理对安全切片

整段从第 5 行（`RetainableBlock` 类型）到第 104 行（函数收尾）超过"能自解释"的粒度上限，所以切成**两块**：**第一块**回答"一个小函数在防什么"（切片与二分查找），**第二块**回答"首尾到底怎么选"。两块都带上各自的函数头与依赖。

**第一块：代理对安全切片 + 二分查找**（这一段决定了"预算边界切在哪"）

**位置**：`packages/spill/spill-policy/src/retention.ts` 第 5–37 行（第 7–13 行的 `RetainedContent` 接口与第 15、26、39 行的三处 JSDoc 此处省略——它们是类型与文档注释）

```ts
/** Content whose text can be split and whose images must remain whole. */
export type RetainableBlock = Extract<ContentBlock, { type: 'text' | 'image' }>

// （第 7–13 行 RetainedContent 接口：head / tail / omittedBytes / omittedImages 四个字段，
//   含义见 §5.4 第二块的 omittedBytes / omittedImages 计算）

/** Preserve a UTF-16 code point when a text budget cuts between its surrogates. */
function textSlice(text: string, length: number, tail: boolean): string {
  let cut = tail ? text.length - length : length
  const previous = text.charCodeAt(cut - 1)
  const current = text.charCodeAt(cut)
  if (previous >= 0xd800 && previous <= 0xdbff && current >= 0xdc00 && current <= 0xdfff) {
    cut += tail ? 1 : -1
  }
  return tail ? text.slice(cut) : text.slice(0, cut)
}

/** Largest contiguous text end fitting a monotonic token estimate. */
function fitText(text: string, budget: number, tail: boolean, price: (block: RetainableBlock) => number): string {
  let low = 0
  let high = text.length
  while (low < high) {
    const middle = Math.ceil((low + high) / 2)
    const candidate = textSlice(text, middle, tail)
    if (candidate.length === 0 || price({ type: 'text', text: candidate }) <= budget) low = middle
    else high = middle - 1
  }
  return textSlice(text, low, tail)
}
```

**第二块：首尾保留主循环**（这一段决定了"哪些块进 head、哪些进 tail、省略量怎么算"）

**位置**：`packages/spill/spill-policy/src/retention.ts` 第 48–103 行（`retainContent` 函数体；第 39–47 行的 JSDoc 是规格说明，不整段照录）

```ts
export function retainContent(
  content: readonly RetainableBlock[],
  budget: number,
  price: (block: RetainableBlock) => number,
): RetainedContent {
  const head: RetainableBlock[] = []
  const tail: RetainableBlock[] = []
  let first = 0
  let last = content.length - 1
  let headCharacters = 0
  let remaining = Math.ceil(budget / 2)                       // ← 两端各拿一半（头）
  while (first <= last) {
    const block = content[first] as RetainableBlock
    const cost = price(block)
    if (cost <= remaining) { head.push(block); remaining -= cost; first++; continue }
    if (block.type === 'text') {
      const text = fitText(block.text, remaining, false, price)
      headCharacters = text.length
      if (text.length > 0) head.push({ type: 'text', text })
    }
    break                                                     // ← 装不下就停（不再往后跳）
  }
  remaining = Math.floor(budget / 2)                          // ← 尾端（向下取整，见讲解）
  while (last >= first) {
    const original = content[last] as RetainableBlock
    const block = last === first && original.type === 'text'
      ? { type: 'text' as const, text: original.text.slice(headCharacters) }   // ← 首尾撞到同一块文本
      : original
    const cost = price(block)
    if (cost <= remaining) { tail.push(block); remaining -= cost; last--; continue }
    if (block.type === 'text') {
      const text = fitText(block.text, remaining, true, price)
      if (text.length > 0) tail.push({ type: 'text', text })
    }
    break
  }
  tail.reverse()
  const bytes = (blocks: readonly RetainableBlock[]): number => blocks.reduce(
    (total, block) => total + (block.type === 'text' ? Buffer.byteLength(block.text, 'utf8') : 0), 0)
  const images = (blocks: readonly RetainableBlock[]): number => blocks.filter(block => block.type === 'image').length
  return {
    head, tail,
    omittedBytes: bytes(content) - bytes(head) - bytes(tail),
    omittedImages: images(content) - images(head) - images(tail),
  }
}
// （第 8–13 行 RetainedContent 字段定义、第 15–24 行 textSlice 的完整 JSDoc 与第 39–47 行
//   retainContent 的 JSDoc，是类型声明与文档注释，此处省略；textSlice / fitText 本身见第一块）
```

按块讲解：

- **（第一块）`textSlice` 防的是"切在代理对中间"**：如果预算边界正好落在 UTF-16 代理对（emoji 这类字符）之间，`previous`/`current` 的判断会**把切口挪一格**，避免产生半个无效字符。
- **（第一块）`fitText` 是二分查找**：对"要保留的字符数"做二分，找**能装进预算的最大连续端**。前提写进了 JSDoc：*"Text pricing must be monotonic in retained length."*——计价必须随保留长度单调，二分才成立。
- **（第二块）预算是"两端各一半"**：头用 `Math.ceil(budget/2)`，尾用 `Math.floor(budget/2)`。取整方向不同是有意的，保证奇数预算不会两边都向上/向下偏离。
- **`break` 而不是 `continue`**：一旦某个块装不进剩余预算就**停止扩展这一端**——不做"跳过这个块再试下一个"。理由是保留必须是**连续的两端**，中间不允许有洞，否则模型读到的上下文会出现"不连续但看起来完整"的危险形状。JSDoc 原文：*"Retain contiguous ends without moving or partially retaining an image."*
- **图片是"整块保留或整块省略"**：图片 `cost > remaining` 时不会像文本那样被切一半——`block.type === 'image'` 落在 `if (block.type === 'text')` 之外，直接 `break`。JSDoc 里也写明：*"unused space at an indivisible image stays unused."*（**空间宁可浪费，也不半张图**。）
- **`headCharacters` 与"首尾撞到同一块"**：当内容少到一个文本块同时被头尾选上（`last === first`），尾部会 `slice(headCharacters)` 跳过已经被头部拿走的部分——**同一块内容不会被算两遍**。
- **省略量是"算出来的"，不是"累计的"**：`omittedBytes` / `omittedImages` 用"原文总量 − 头 − 尾"得出，因此不会因为分支差异而漏计。这两个数字最终会进模型的省略提示（§5.5）。

### 5.6 触发路径 B：会话引用被截断时自己调用（源码对照）

**位置**：`packages/context/session-reference/src/spill.ts` 第 23–50 行（`prepareReferenceOmission`；第 12–13 行的返回类型与第 52–60 行的 `omission()` 见下面第二段）

```ts
type FullSnapshot = ({ status: 'saved' } & SpillRef)
  | { status: 'unavailable'; reason: 'storage-not-configured' | 'save-failed' }

/**
 * Save the full captured projection only when its preview omits text.
 * @param store - optional composed spill backend.
 * @param ownerId - target session receiving the context.
 * @param source - full projection and preview omission facts from the same capture.
 * @param inputIndex - reference position used to distinguish transcript filenames.
 * @returns an omission notice, absent for intact previews; storage failures report unavailable.
 */
export async function prepareReferenceOmission(
  store: SpillStore | undefined,
  ownerId: SessionId,
  source: { fullData: ReferencedSessionData; stats: ReferenceRetentionStats; capturedFormatVersion: number },
  inputIndex: number,
): Promise<ReturnType<typeof omission> | undefined> {
  if (!source.stats.truncated) return undefined                  // ← ① 没截断就不存
  let fullSnapshot: FullSnapshot
  if (store === undefined) {
    fullSnapshot = { status: 'unavailable', reason: 'storage-not-configured' }   // ← ② 没后端
  } else {
    const request: SaveTextSpill = {
      owner: { sessionId: ownerId },                              // ← 目标会话（接收方）
      source: { kind: 'session-reference', sessionId: source.fullData.sessionId, label: source.fullData.label },
      suggestedName: `session-reference-${inputIndex + 1}.txt`,
      content: renderTranscript(source.fullData, source.capturedFormatVersion),
    }
    let saved: SpillRef
    try {
      saved = await store.saveText(request)
    } catch {
      // Optional storage failures cannot turn an incomplete preview into a claimed full snapshot.
      return omission(source, { status: 'unavailable', reason: 'save-failed' })   // ← ③ 保存失败降级
    }
    fullSnapshot = { status: 'saved', ...saved }
  }
  return omission(source, fullSnapshot)
}
// （第 52–60 行的 omission()：把 sessionId / capturedThroughSeq / omittedMessages / omittedBytes /
//   fullSnapshot 打包成一条通知，见下面第二段——它决定"省略多少"这件事怎么被记下来）
```

### 6.2 会话目录与文件名：稳定分桶 + 不可预测前缀

**位置**：`packages/spill/spill-local/src/store.ts` 第 41–68、71–81、103–131 行（`encodeSegment` / `sessionDir` / `saveTextFile`）

```ts
/**
 * Encode an arbitrary string as one safe path segment, injectively over ALL JS
 * (UTF-16) strings. A session id / suggested name is untrusted input, so this
 * neutralizes `../`, absolute paths, NUL, and separators before any filesystem
 * use. Each code unit is kept literal (`[A-Za-z0-9._-]`, minus `~`) or escaped
 * as `~XXXX`; `~` is itself escaped, so the mapping is reversible and distinct
 * inputs never collide. The whole-segment tokens `.`/`..` are escaped so they
 * can never traverse. An empty string encodes to `~` (never an empty segment).
 */
export function encodeSegment(raw: string): string {
  if (raw.length === 0) return '~'
  if (raw === '.') return '~002E'
  if (raw === '..') return '~002E~002E'
  let out = ''
  for (let i = 0; i < raw.length; i++) {
    const code = raw.charCodeAt(i)
    const ch = String.fromCharCode(code)
    out += ch !== '~' && /^[A-Za-z0-9._-]$/.test(ch)
      ? ch
      : '~' + code.toString(16).toUpperCase().padStart(4, '0')
  }
  return out
}

/**
 * Derive the stable session-scoped directory under a spill root.
 */
export function sessionDir(root: string, sessionId: string): string {
  const hash = createHash('sha256').update(sessionId).digest('hex').slice(0, 12)
  return join(root, `session-${hash}`)
}
// （第 83–101 行 SaveTextOptions / SavedText 两个接口是参数与返回值的类型声明，此处省略）
```

```ts
// packages/spill/spill-local/src/store.ts 第 108–131 行
export async function saveTextFile(options: SaveTextOptions): Promise<SavedText> {
  const dir = sessionDir(options.root, options.sessionId)
  const path = join(dir, `${randomBytes(6).toString('hex')}-${encodeSegment(options.suggestedName)}`)
  let handle
  for (;;) {
    await mkdir(dir, { recursive: true, mode: 0o700 })      // ← 目录 0700
    try {
      handle = await open(path, 'wx', 0o600)               // ← 'wx'：已存在就失败；文件 0600
      break
    } catch (error: unknown) {
      /* v8 ignore start -- requires another process to remove the directory
         between mkdir and open, or an external permission/IO race. */
      if (isErrno(error, 'ENOENT')) continue               // ← 目录被并发删掉 → 重来
      throw error
      /* v8 ignore stop */
    }
  }
  try {
    await handle.writeFile(options.content)
  } finally {
    await handle.close()                                    // ← 无论成败都关句柄
  }
  return { path, bytes: Buffer.byteLength(options.content, 'utf8') }
}
```

按块讲解：

- **`encodeSegment` 是单射的**（JSDoc 原文：*injectively over ALL JS (UTF-16) strings*）：`[A-Za-z0-9._-]` 与 `~` 之外的**每个码元**写成 `~XXXX`（UTF-16 码元的 4 位大写十六进制）；`~` 本身也转义，所以映射**可逆且不撞**。整段 `.` / `..` 也被特判转义——**路径穿越在这里被掐死**。空串编码成 `~`，**绝不留空路径段**。
- **`sessionDir` = `root/session-<sha256(sessionId) 前 12 位十六进制>`**：**稳定**（同一个会话永远同一个桶），所以同会话的 spill 归在一起，清理时也能按桶剪枝。
- **文件名 = `<6 字节随机十六进制>-<安全名>`**：随机前缀保证**不可预测**——预置一个同名符号链接来重定向写入是行不通的。
- **写入用 `open(path, 'wx', 0o600)`**：`'wx'` 是"**排他创建**，已存在就失败"。所以哪怕是预置的符号链接，这一步也会**必然失败**而不是跟随它写。配合 `mkdir(..., {mode: 0o700})`，得到"私有目录 + 独占且仅所有者可写的文件"。
- **`for (;;)` + `if (isErrno(error, 'ENOENT')) continue`**：唯一会重试的错误是"目录在 `mkdir` 与 `open` 之间被并发清理掉了"。**其它错误一律抛出**——不掩盖真实故障（准则：不取巧）。
- **返回值 `bytes = Buffer.byteLength(content, 'utf8')`**：**精确 UTF-8 字节数**，不是字符数。它最终成为模型的 `SpillRef.bytes`。

```ts
// （第 20–41 行：OpenTurnCloseCause 类型与 CLOSER_TEXT 文案表，见 §7.3，此处省略）

/**
 * Return deterministic synthetic events that close an open tail turn. Unmatched
 * calls receive error results first, followed by an open `step/end` and a
 * cause-specific `turn/end`; sequences continue the log and timestamps reuse the
 * last real event. A balanced or empty log returns no events.
 *
 * @param events - the loaded durable log to scan (a valid committed prefix, possibly with a crash tail).
 * @param cause - the owning close operation: selects result wording and the turn-ending reason.
 * @returns the synthetic closer events to append after `events`, in order; empty when the log is already balanced.
 */
export function openTurnClosers(events: readonly SessionEvent[], cause: OpenTurnCloseCause): SessionEvent[] {
  let openTurn: number | null = null
  let openStep: number | null = null
  const recovery = new ToolCallRecovery(cause)             // ← 只留"待配对调用"的轻状态
  for (const event of events) {
    recovery.observe(event)
    switch (event.type) {
      case 'turn/start':
        openTurn = event.data.turn
        openStep = null
        break
      case 'turn/end':
        openTurn = null
        openStep = null
        break
      case 'step/start':
        openStep = event.data.step
        break
      case 'step/end':
        openStep = null
        break
      // Other event types do not move the turn/step boundary cursor.
      default:
        break
    }
  }

  // Balanced log (no open tail turn): nothing to close. An open turn implies
  // `events` is non-empty (its turn/start was logged), so `last` exists.
  const last = events.at(-1)
  if (openTurn === null || last === undefined) return []   // ← ① 日志本就配平 → 空数组

  // The last real event supplies the seq base and the timestamp for the
  // synthetic closers (reusing the last timestamp keeps them deterministic and
  // never invents a "future" time).
  const closers: SessionEvent[] = recovery.results()       // ← ② 先补未应答的工具结果
  let seq = last.seq + closers.length + 1
  const time = last.time

  // Close an open step before its turn.
  if (openStep !== null) {
    closers.push({ type: 'step/end', seq: SessionSeq(seq++), time, data: { turn: openTurn, step: openStep } })
  }
  closers.push({ type: 'turn/end', seq: SessionSeq(seq++), time, data: { turn: openTurn, reason: { kind: cause.kind } } })
  return closers
}
```

按块讲解：

- **这是一个纯函数**：输入 `events` + `cause`，输出要追加的事件数组。**不写文件、不改输入、不依赖当前时间**。这是"语义修复属于读方"的实现形态。
- **依赖变量**：`recovery` 是第 105–198 行的 `ToolCallRecovery` 实例（构造在第 110 行，`cause` 影响文案与错误码）；`closers` 的起点是 `recovery.results()` 的返回。
- **① 日志本就配平 → 返回 `[]`**：`openTurn === null` 表示扫完没有未闭合的轮次。**调用方靠"长度为 0"判断要不要写**（§7.4 的 `if (closers.length > 0)`）。
- **② 顺序是"结果 → `step/end` → `turn/end`"**：作者注释给了理由（第 164–165 行）：*"Close calls before their step: providers reject dangling assistant calls, and Map insertion order preserves their transcript order."* → **提供方不接受悬空的 assistant 调用**，所以必须先补结果；`Map` 的插入顺序恰好保留了它们在 transcript 里的顺序。
- **`seq` 与 `time` 都从最后一条真实事件续**：`let seq = last.seq + closers.length + 1`，`time = last.time`。注释原文解释了为什么复用时间戳：*"reusing the last timestamp keeps them deterministic and never invents a 'future' time."* → **合成事件不会"来自未来"**。
- **`turn/end.reason` 的 `kind` 直接取 `cause.kind`**：这就是"恢复"与"fork"共用函数体、只差一个字段的地方（对照表见附录 A Q4）。
- **`step/end` 是可选的**：`if (openStep !== null)`——崩溃点可能在步骤之间（那时没有开着的步骤）。

### 7.2 未应答的调用怎么变成一条错误结果

**位置**：`packages/core/session/src/repair.ts` 第 151–197 行（`ToolCallRecovery.results()`；第 105–149 行的字段与 `observe` 是本块的依赖）

```ts

   * @returns pending tool-result events, empty when no request remains unanswered.

  results(): SessionEvent<'tool/result'>[] {

    let seq = this.last.seq + 1

    // and Map insertion order preserves their transcript order.

        role: 'tool',
        toolCallId: callId,
        isError: true,
        source: { kind: 'tool', callId },
        content: [{
          type: 'text',
          text: started ? text.started : text.notStarted,
        }],
      })
      results.push({
        type: 'tool/result',
        seq: SessionSeq(seq++),
        time,
        data: {
          turn, step, message,
          error: started
            ? { name: 'ToolOutcomeUnknownError', code: TOOL_OUTCOME_UNKNOWN }
            : { name: 'ToolNotStartedError', code: TOOL_NOT_STARTED },
        },
        surfaceOp: 'append',
        ...started ? { sourceEventSeqs: [callSeq] } : {},
      })
    }

    return results
  }

```

按块讲解：

- **`pendingCalls` 的语义**：在一次 `assistant/message` 里出现的每个 `tool-call` 块都登记进来；遇到 `tool/call` 事件就记下 `callSeq`（**"已经开始过"的证据**）；遇到对应的 `tool/result`（且 `surfaceOp === 'append'`、turn/step 匹配）就**删除**。扫完还剩在 Map 里的，就是**未应答**的。
- **`started = callSeq !== undefined` 决定了两件事**：
  - **错误码**：有 `tool/call` → `TOOL_OUTCOME_UNKNOWN` + `ToolOutcomeUnknownError`；没有 → `TOOL_NOT_STARTED` + `ToolNotStartedError`。
  - **`sourceEventSeqs: [callSeq]`**：只在"确实开始过"时挂上来源事件序号。
- **合成 message id 是确定性的**：`${cause.kind}-tool-result-${callId}-${seq}` → 恢复场景下形如 `interrupted-tool-result-…`，fork 场景下形如 `forked-tool-result-…`。**确定性**很重要：同样的日志重放两次，得到同样的 id。
- **`isError: true` 一律为真**：语义是"这条结果**未知/未发生**"，不是"工具失败了"。真正的判据在 `error.code` 与模型可见文案里。
- **`surfaceOp: 'append'`**：它作为**普通追加**进入日志表面——不是特殊存储入口（对照 §7.4 的 resume 路径）。
- **`results()` 不改自身状态**（JSDoc：*without changing tracked state*）：调用方提交并**观察到这些提交之后**才能再修一次。这是"纯"的具体含义。

```ts
  private async persistContiguous(batch: readonly SessionEvent[]): Promise<void> {
    if (this.access !== 'write') throw new SessionReadOnlyError(this.id, 'append')
    if (batch.length === 0) return
    await this.ensureLease()
    assertContiguous(this.id, batch, this.state.cursor)

    if (this.state.recoveredTail !== undefined) {
      if (this.state.recoveredTail.length > 0) {

    }
```

- **"双重解码"是本节的核心机制**：① `scanZstdFrames` 做**结构扫描**，得出"完整帧"与"最后那个不完整帧的起点 `tornStart`"；② 完整帧照常解码；③ 对撕裂帧再走一次 `decompressZstdPrefix(buffer.subarray(tornStart))`——**能解出多少算多少**。
- **为什么值得费这个劲**（作者注释原文）：*"A torn final frame's append never resolved, but complete JSONL records already flushed into it are real emitted events: recover them."* → **那次 append 确实没成功，但其中已经 flush 出去的完整记录是真实发生过的事件**，丢掉就等于篡改历史。
- **返回的两个字段分工明确**：`tornTruncateTo`（截到哪个字节）+ `recoveredTail`（从撕裂帧里救回的**完整**记录，用 `slice(complete.eventCount)` 切出来）。
- **真正动磁盘的是 `persistContiguous`**：它按**① 截断 → ② 重写救回记录 → ③ 写本批次**的顺序做，而且**每一步落地后才清状态**——注释写明 *"clearing each step's state only once it lands so a failed step retries on the next mutation"*（**失败就下次重试，不会丢**）。

- **无撕裂时两条路径都不走**：`tornTruncateTo: undefined` / `recoveredTail: []` → 正常的 append **零额外 IO**。
- **本块未实跑**：没有构造撕裂帧的现成脚本，只做了源码核对（§9.3）。

```ts
 * backend, a call with no session owner, or a `saveText()` rejection logs a
 * warning and returns `undefined` — the caller keeps the inline result and
 * reports that the complete result could not be saved; search success never
 * turns into `isError` because spill storage is unavailable.
 */
export async function trySaveFormattedResult(
  ctx: Context,
  exec: ToolExecution,
  suggestedName: string,
  content: string,
): Promise<SpillRef | undefined> {
  const sessionId = exec.agent?.session.header.id
  if (sessionId === undefined) {
    ctx.logger.warn(`tool-fs-search: no session owner for ${exec.name} result; complete result not saved`)
    return undefined
  }
  const spillStore = ctx.get('spillStore')
  if (!spillStore) {
    ctx.logger.warn(`tool-fs-search: no ctx.spillStore backend loaded; complete ${exec.name} result not saved`)
    return undefined
  }
  const save: SaveTextSpill = {
    owner: { sessionId },
    source: { kind: 'tool', toolName: exec.name, callId: exec.callId, label: 'result' },
    suggestedName,
    content,
  }
  try {
    return await spillStore.saveText(save)
  } catch (error: unknown) {
    // Best-effort: a storage failure must never fail the search or hide the
    // inline result — the footer reports the unsaved remainder instead.
    ctx.logger.warn(`tool-fs-search: saveText failed for ${exec.name}: ${String(error)}; complete result not saved`)
    return undefined
  }
}
```

按块讲解：

- **这是"另一条独立路径"**：调用方是**工具自己**（在 `glob`/`grep` 的结果被自己截断时），不是 `spill-policy`。所以"什么时候 spill"的答案在这里**归工具**。
- **`source` 与路径 A 完全同形**：`{ kind:'tool', toolName, callId, label:'result' }`——同一套词汇、同一个 seam。
- **`ctx.get('spillStore')` 同样是可选取用**：注释写明 *"`spillStore` is read with `ctx.get()` (not static inject) because formatted-result spill is optional"*。
- **降级策略与 `spill-policy` 一致**：任何失败只 `warn` 并返回 `undefined`，注释原文 *"search success never turns into `isError` because spill storage is unavailable."*
- **注意区分：这不是 `ctx.spillStore` 的唯一提前 spill**。工具执行器还有一条**不同性质**的机制：bash / pwsh 的 stdout/stderr 超出**每流内存上限**时，溢出到**执行器自己的临时文件**并把路径回报（`packages/shell/bash-local/README.zh.md` 第 47–48、126 行；`packages/shell/tool-bash/README.zh.md` 第 55 行：*"完整输出保存到 spill 文件并报告其路径"*）。它**不经过 `ctx.spillStore`**——属于 subprocess 服务的 managed-range 机制（展开于 `3.10`）。

## 9. 实测证据、未验证事项与能力边界

### 9.1 结论复核：spill 到底存什么、不存什么

**存什么**：`saveText` 的 `content` **逐字全文**（UTF-8），返回不透明 `locator`、精确字节数 `bytes`、模型取回指引 `retrievalHint`（§4.1 的三条语义；`docs/subsystems/spill.zh.md` 第 90 行把这一句写成 *"它持久保存完整的 `content`"*，英文版第 90 行原文即 *"persists the FULL `content`"*）。两种来源、两种内容：

- `kind:'tool'`：**格式化后的最终工具文本 + 每个图片位置的附件可读路径**（§5.3）。**图片字节留在附件存储，不进 spill 文件**。
- `kind:'session-reference'`：被引用会话的**已捕获文本投影 transcript**，按每行至多 64 个 Unicode 码点的 JSON 字符串片段序列化（`packages/context/session-reference/src/spill.ts` 第 62–81 行；`README.zh.md` 第 38 行）。

**不存什么**：不是"所有工具输出"。预算内的结果、`read` 的结果、被阻止的决策、值替换、不支持的内容块类型都**原样通过**（§5.1 的三个守卫 + §5.2 ①；`packages/spill/spill-policy/README.zh.md` 第 61 行）。另外 `maxInlineTokens` **不配置时整个策略不安装**（源码第 49–50 行直接 `return`）。

**触发条件**，三条按优先级：

1. **工具结果超预算**：估算 token 之和 **> `maxInlineTokens`**（判据是 `<= maxTokens` 就返回 `undefined`，即不 spill）——源码第 98 行。内置 base 组合设为 `12500`（§4.3）。
2. **会话引用预览被截断**：`if (!source.stats.truncated) return undefined`——`packages/context/session-reference/src/spill.ts` 第 29 行。
3. **工具自有提前 spill**（独立路径，不是本策略）：`tool-fs-search` 通过 `ctx.spillStore.saveText()` 保存被截断的搜索结果（§8）；bash/pwsh 的执行器溢出走**另一套**临时文件机制（§8 末）。

两条**否定性**结论同样重要：spill **不是**按结果大小自动发生的"日志压缩"，也**不是**持久化 seam 的一部分——`docs/persistence-catalog.zh.md` 搜索 `spill` 为 **0 命中**（实查：该文件 810 行，全文无 `spill`），即持久事件目录里**没有任何 spill 事件类型**。

### 9.2 结论复核：中断/重启后如何恢复

分三层，**依据各不同**：

**第一层：spill 产物本身**。它是宿主文件系统上的普通文件，**与进程生命周期无关**，因此中断/重启不使它失效。依据：§9.3 的跨进程实测；写入路径 `saveTextFile` 只做 `mkdir` + `open('wx')` + `writeFile`（§6.2），**没有任何内存态或句柄绑定**。

**第二层：定位信息的来源**。恢复时**不查表、不重建**，唯一依据是会话日志里那条已提交的工具结果消息（内含路径 + read/grep 指引）。它随会话日志被持久化、被原样重放；预览与省略事实（`omittedMessages` / `omittedBytes` / 定位信息）**在同一条持久上下文消息里**（`packages/context/session-reference/README.zh.md` 第 38 行；`packages/spill/spill-policy/README.zh.md` 第 57 行）。**恢复时不会重新 spill**：那条消息是已提交历史的一部分，原样重放，模型再 `read`/`grep`。

**第三层：日志自身的可用性**由持久化 seam 保证：只暴露**物理有效连续前缀**，撕裂尾部要么丢弃、要么把其中完整记录在首次新 append 前重写（§7.5；`docs/subsystems/persistence.zh.md` 第 110 行）。语义缺口（未闭合的轮次、未应答的工具调用）由**读方**补（§7.4）。

**两条必须写清的边界**（这是本步最容易出错的推论）：

- **默认根是每进程的临时目录**：不配 `root` 时，重启后的新进程**不会**回到旧根；旧文件只等着被下一次启动清理按年龄删除。要建立"重启后按老定位信息取回"的部署保证，**必须显式配置稳定的 `root`**（§6.1；`packages/spill/spill-local/README.zh.md` 第 32、43 行）。
- **没有逐会话清理/失效 API**：`spill` 包明确把「按会话清理」「刷新定位信息」列为未定义的开放方向（`packages/spill/spill/README.zh.md` 第 135–136、152 行）。因此「会话被删除后它的 spill 文件怎样」在本 seam 内**无答案**；产品侧只有**启动按年龄扫描**这一条回收路径。

**最佳努力的失效语义**：`saveText` 只在真实存储故障（权限、`ENOSPC`、后端不可用）时拒绝，由调用方决定降级；已交付策略记 warning 并**保留原内联结果**（§5.2 ⑥），所以 spill 失败**绝不会**把成功的工具调用变成错误或隐藏内容。测试 `a saveText failure keeps the complete content in the durable log (best-effort)` 实测通过（§9.4）。

**`SpillOwner.sessionId` 是保存时的命名空间，不是访问控制**：fork 的子会话从种子日志继承既有定位信息，「不需要复制它们或重新取得所有权；fork 后的新 spill 使用子会话 id」（`packages/spill/spill/src/types.ts` 第 30–39 行；`.agents/notes/implemented/architecture/2026-07-08-tool-output-spill-files.zh.md` 第 63 行）。

### 9.3 跨进程存活：spill 文件确实不随进程消失（本机实测）

两个脚本（写在 `<临时目录>\dsh-313-demo\`，**未触碰仓库**）：

- `save.mjs`：用真 `Context` + 真 `LocalSpillStore`（`root` = 新建临时目录，`cleanupPeriodDays: 0`）保存 50010 字节文本，打印 `ref.locator`。
- `read.mjs`：**另起一个 node 进程**读取该路径。

结果（原样搬运，**路径中的用户名与本机临时目录已改为占位符**）：

```text
locator=<root>\session-47f0a5d2a0ef\5d3b692af053-web_fetch.txt
{"exists":true,"bytes":50010,"head":"HEAD-","tail":"-TAIL","fullLength":50010}
```

三点确认：① 路径形状 = `<root>/session-<12 位十六进制>/<12 位随机十六进制>-<safeName>`，与 §6.2 一致；② 会话桶 `session-47f0a5d2a0ef` 就是 `sha256('session-313')` 的前 12 位十六进制（可自行用同一个哈希规则复核）；③ 内容**逐字节完整**、可被另一个进程读回，且字节数与 `saveText` 的 `bytes` 一致。**这次实验只覆盖纯文本**——含图片的结果里，文件记的是图片的**可读路径**（§5.3），要看到图还得再走附件与 `read_image`（本步未跑含图的跨进程用例）。

同一次运行里 `stat().mode` 打出 `100666`——这是 **Windows 无 POSIX mode 语义**的表现，**不能**当作"写入不是 0600"的证据；0600/0700 的权威出处是代码本身（§6.2）与测试断言（`packages/spill/spill-local/tests/spill-local.spec.ts` 第 119–120 行：`expect(directory.mode & 0o777).toBe(0o700)` / `expect(file.mode & 0o777).toBe(0o600)`，且第 118 行有 `if (process.platform !== 'win32')` 守卫）。

## 附录 A 关键问题与答案

> ✅ 四道题**全部给出明确答案**，不留空、不写"待补充"。四题都是第一次读就该能答的；带「第一次读请跳过」标记的子问题涉及后续编才展开的细节，回查时再看。

### Q1 spill 存什么？触发什么条件时发生？

**答案（一句话）**：存**逐字全文**（附图片位置的可读路径），触发条件是「工具最终结果估算 token **超过** `maxInlineTokens`」或「会话引用预览**真的丢了内容**」。

**存什么**：`saveText` 的 `content` **逐字全文**（UTF-8），返回不透明 `locator`、精确字节数 `bytes`、模型取回指引 `retrievalHint`（§4.1；`docs/subsystems/spill.zh.md` 第 90 行的原文就是 *persists the FULL `content`*）。两种来源、两种内容：

- `kind:'tool'`：**格式化后的最终工具文本 + 每个图片位置的附件可读路径**（§5.3）。图片字节留在附件存储，**不进 spill 文件**。
- `kind:'session-reference'`：被引用会话的**已捕获文本投影 transcript**，按每行至多 64 个 Unicode 码点的 JSON 字符串片段序列化（§5.6）。

**不存什么**：不是「所有工具输出」。预算内的结果、`read` 的结果、被阻止的决策、值替换、不支持的内容块类型都原样通过（§5.1 的三个守卫）；`maxInlineTokens` 不配置时**整个策略不安装**（源码第 49–50 行）。

**触发条件**，三条按优先级：

1. **工具结果超预算**：估算 token 之和 **> `maxInlineTokens`**（判据是 `<= maxTokens` 就返回 `undefined`，即不 spill）——`packages/spill/spill-policy/src/index.ts` 第 98 行。内置 base 组合设为 `12500`（§4.3）。
2. **会话引用预览被截断**：`if (!source.stats.truncated) return undefined`——`packages/context/session-reference/src/spill.ts` 第 29 行。
3. **工具自有提前 spill**（独立路径，不是本策略）：`tool-fs-search` 通过 `ctx.spillStore.saveText()` 保存被截断的搜索结果（§8）。

另外两条**否定性**结论同样重要：spill **不是**按结果大小自动发生的「日志压缩」，也**不是**持久化 seam 的一部分——`docs/persistence-catalog.zh.md` 搜索 `spill` 为 **0 命中**，即持久事件目录里**没有任何 spill 事件类型**。

### Q2 中断/重启后如何恢复？依据是什么？

**答案（一句话）**：**不查表、不重建**——spill 产物本来就在宿主文件系统上（跨进程存活），会话日志里那条普通工具结果消息是定位信息的**唯一持久载体**；日志本身的可用性由持久化保证，语义缺口由读方补。

分三层，**依据各不同**：

**第一层：spill 产物本身**。宿主文件系统上的普通文件，**与进程生命周期无关**。依据：§9.3 的跨进程实测；写入路径 `saveTextFile` 只做 `mkdir` + `open('wx')` + `writeFile`，**没有任何内存态或句柄绑定**（§6.2）。

**第二层：定位信息的来源**。恢复时**不查表、不重建**，唯一依据是会话日志里那条已提交的工具结果消息（内含路径 + read/grep 指引）。它随日志持久化、被原样重放；预览与省略事实（`omittedMessages` / `omittedBytes` / 定位信息）**在同一条持久上下文消息里**（§5.5、§5.6）。**恢复时不会重新 spill。**

**第三层：日志自身的可用性**由持久化 seam 保证：只暴露**物理有效连续前缀**，撕裂尾部要么丢弃、要么把其中完整记录在首次新 append 前重写（§7.5）。语义缺口（未闭合的轮次、未应答的工具调用）由**读方**补（§7.4）。

**两条必须写清的边界**：

- **默认根是每进程的临时目录**：不配 `root` 时，重启后的新进程**不会**回到旧根；旧文件只等着被下一次启动清理按年龄删除。要「重启后按老定位信息取回」，**必须显式配置稳定的 `root`**（§6.1）。
- **没有逐会话清理/失效 API**：`spill` 包明确把「按会话清理」「刷新定位信息」列为未定义的开放方向（`packages/spill/spill/README.zh.md` 第 135–136、152 行）。因此「会话被删除后它的 spill 文件怎样」在本 seam 内**无答案**；产品侧只有**启动按年龄扫描**这一条回收路径（默认 30 天，`0` 关闭）。

**最佳努力的失效语义**：`saveText` 只在真实存储故障（权限、`ENOSPC`、后端不可用）时拒绝；已交付策略记 warning 并**保留原内联结果**（§5.2 ⑥），所以 spill 失败**绝不会**把成功的工具调用变成错误。

### Q3 未被后续事件封住的普通中断尾部如何处理？

**先给一句话答案：内核不自动修它。** 持久化保留它；修复属于**读方**，且修法因读者身份而异——**只读观察在内存里配平、不回写；取得写所有权的 resume 才把它作为普通批次持久追加**。

三档处理：

1. **只读观察（session-query / 冷读）**：`readColdSessionLog` 打开 `read` 句柄读完，然后返回 `[...events, ...interruptedTurnClosers(events)]`——**只在内存里配平，不回写任何内容**（§7.4 路径一）。
2. **取得写所有权的恢复（agent-loop.resume）**：先 `open(id,'write')`（在进程内**先拿到写所有权**，从而排除并发 resume 抢修），再 `read` 冷日志，计算 `interruptedTurnClosers(persisted)`，非空则 `await handle.append(closers)`——**作为普通批次走同一个句柄**，不是特殊存储入口（§7.4 路径二）。
3. **进程被 dispose 而非 resume**：`turn` 中途的根 dispose 会按设计丢掉该轮**尚未发出**的剩余部分，由「下一次恢复的 `interruptedTurnClosers`」持久修复（作者笔记第 15 行）。

**「未被后续事件封住」到底指什么**：日志以打开的 `turn/start` 结束，**后面没有** `turn/end`，也没有能间接把它封住的事件。此时的合成闭合是（§7.1–§7.3）：

- 每个未应答的 assistant 工具请求 → 一条 `isError: true` 的 `tool/result`，带 `error.code` 二选一：该调用**有** `tool/call` 记录 → `TOOL_OUTCOME_UNKNOWN`（文案：结果未知，只重试只读/幂等工作，可能有副作用时先验证外部状态或问用户）；**没有** `tool/call` 记录 → `TOOL_NOT_STARTED`（文案：重试即可）。
- 开着的步骤 → `step/end`。
- 轮次 → `turn/end { turn, reason: { kind: 'interrupted' } }`。`interrupted` 是**唯一一个不由循环实时发出**的 `TurnEndReason`（`packages/core/session/src/types.ts` 第 215–221 行，JSDoc 原文：*"The loop never emits this marker live, and the events recorded before the crash remain intact."*）。

**反例（必须区分，第一次读请跳过）**：如果尾部**已经被后续事件封住**——具体是「后一条 `turn/start` 紧接在一次 `agent/inbox/spliced`（`target:'next-turn'`）之后，且步骤未开」——那么 **V3→V4 升级迁移**会插入缺失的 `turn/end {reason:{kind:'interrupted'}}`（`packages/session/session-format-v3-to-v4/src/migration.ts` 第 65–71、117–134 行；未在本课实读全文，**标注为文档转述**）。`docs/architecture.zh.md` 第 129 行把这条界线讲得最清楚：*"只有在后续 `turn/start` 已经封住一种有限的已发布 restart 时，migration 才会插入缺失的 interrupted `turn/end`"*，而普通未封住的中断尾部仍归句柄消费方。

顺带一条被拒绝的替代方案（说明为什么今天要留着这种「半开」状态）：`truncate-interrupted-turns` 提议直接截断未闭合轮次并删除 `interruptedTurnClosers()` 及其测试，被否决，因为当前约定要求保留已持久写入却从未关闭的最终轮次（`.agents/notes/rejected/simplification/2026-06-20-truncate-interrupted-turns.zh.md` 第 9、22 行）。

### Q4 恢复与 fork 共用哪些持久 settlement？

The cause selects the synthetic `turn/end` reason, the model-visible wording of synthetic error tool results, and the deterministic synthetic message-id prefix. The error codes … **are shared**: both causes state the same fact about the call's recorded lifecycle."*

**两者的持久边界也不同**：resume 走**写句柄的普通批次**（会持久化）；fork 种子里的合成闭合事件落在**继承前缀之外**，由 `inheritedEventCount` 排除，且 `turn/end {forked}` 的 JSDoc 明确「只有 fork 种子携带这个标记，且边界之前的源事件在子会话里保持原样」（`packages/core/session/src/types.ts` 第 222–228 行）。

**对 spill 的直接含义**：`SpillOwner.sessionId` 是**保存时**的命名空间，fork 子会话**不会**重新拥有或复制祖先的 spill 产物；fork 之后新产生的 spill 才使用子会话 id（§4.2）。所以子会话读到祖先的定位信息时，那个路径指向的仍是**祖先会话目录**下的文件——这也是本地后端刻意保留旧文件 30 天的原因（`cleanupPeriodDays` 的 JSDoc 原文：*"a resumed or forked session may still reference an older locator until it ages out"*）。
