## 0. 怎么读这一课（先看这段）

### 0.1 这一课是什么、不是什么

**是**：会话日志的**两层格式**（逻辑 / 物理）、**只追加**这条纪律的物理前提、**不可变 generation** 与**排他发布**的落地方式、以及**迁移链**的组织规则。
**不是**：事件类型全景（`3.2`）、投影与消息推导（`3.3`）、压缩（`3.12`）。本课只关心"字节怎么落盘、版本怎么演进"。

### 0.2 现在只要记住这 5 件事

1. **格式分两层、归两个包**：`dsh-session-format` 只管**逻辑**（header 分类、相邻迁移、JSON 无损检查）；**物理**分帧、压缩、generation 命名、排他发布归 `dsh-session-persistence-jsonl`。
2. **物理文件 = 一串互相独立的 Zstandard 帧的拼接**：第一帧只装 header 那一行，其后**每个持久 append 批次各占一帧**，所有帧都带校验和。
3. **分帧不是为了省空间，是为了让"追加"成立**：追加时只需再写一个自包含帧，**完全不用重压缩前面的字节**。
4. **文件名就是 generation 编号**：v0 叫 `session.jsonl[.zstd]`，v1 起叫 `session.vN.jsonl[.zstd]`；文件名里的版本必须与 header 里的 `version` 一致，否则报错。
5. **已提交的 generation 路径绝不重命名、替换或删除**——新代际是**发布**出来的（不覆盖），迁移只写**最终 current target**，源文件逐字节保留。

### 0.3 明确授权：其余这些词，现在**不用管**

本课会出现一批你暂时不懂的词：`Zstandard 帧`、`校验和`、`flock`、`MOVEFILE_WRITE_THROUGH`、`inherited cut（继承切点）`、`stage`、`codec`、`Worker 校验`、`sourceEventSeqs`、`subagent/catalog`。**这些都是我在别处学的，现在不需要你懂。**

## 1. 最小词汇表（7 个词）

这 7 个词是理解后面一切的地基。前 5 个属**物理层**，后 2 个属**逻辑层**。

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **generation 代际** | 同一个会话的**某一版格式**的那份日志文件。文件名里的 `vN` 就是它的编号 | `session.v4.jsonl.zstd` 里的 `v4`；`version` 字段 |
| **frame 帧** | 一次压缩的**独立产物**：自己能解压、自己带校验和。多个帧首尾相接就是一个文件 | `ZstdFrameRange { start, end }` |
| **framing 分帧** | 决定"哪些行压进同一个帧"的规矩。本课的规矩是**一批一帧**，且**第一帧只有 header** | `encodeMaterialization` / `encodeEventBatch` |
| **仅追加（append-only）** | 文件只往后写，**已写下的字节永不改写** | `open(path, 'a')`；"已提交事件绝不重写" |
| **committedBytes 已提交字节** | 从文件头算起、**每一个字节都已成功解码成事件**的那一段的长度。游标只增不减 | `SessionLogScanner.committedBytes` |
| **header 头** | 文件**第一行**那条记录：会话的身份与格式版本。它不含事件 | 物理 `HeaderLine`；逻辑 `SessionFormatHeader` |
| **migration edge 迁移边** | **一个版本到下一个版本**的一步转换。四条边串成一条链 | `SessionFormatMigration { fromVersion, toVersion }` |

> ⚠️ **这 7 个词分属两层。** 第 1–5 个是 `dsh-session-persistence-jsonl` 的词汇，第 6–7 个跨两层。本课只用到上面这个程度——**帧头每个 bit 什么意思、Zstandard 的 block 结构、`flock` 的语义**，这里不展开。

## 2. 两张图 + 一段大白话

### 2.1 两层格式（静态结构：谁归谁管）

```
逻辑层  dsh-session-format（纯函数，不是插件）
  ├─ SessionFormatHeader      9 个字段，封闭集合（version/id/createdAt/…）
  ├─ SessionFormatEvent       恒 4 个字段（type/seq/time/data）
  ├─ filename.ts              规范名 session[.vN].jsonl  ← 逻辑层也管"名字"
  └─ chain.ts                 把四条相邻边编译成一条链
        │
        │  上层只说"给我当前逻辑事件"，不问字节
        ▼
物理层  dsh-session-persistence-jsonl（插件，占用 ctx.sessionPersistence）
  ├─ format.ts    路径派生 + header 行编解码 + 当前记录扫描器
  ├─ zstd.ts      帧压缩 / 帧解码 / 不解压的结构性帧扫描
  ├─ generation.ts 单遍历史还原 + stage 编码 + 源修订复查 + 排他发布
  ├─ win32.ts     Windows write-through 发布与目录创建
  └─ lease.ts     跨进程单写者内核锁（session.lock）
```

> **精确性说明**：`filename.ts` 在逻辑包里，但"文件名"本身是**物理落地**的产物——为什么放在逻辑包？因为**导出、fixture、持久化三方要共用同一个名字定义**（`session-format/README.zh.md` 第 65 行）。这是刻意为之，不是分层失误。

### 2.2 一次 append 落到磁盘（动态过程）

```
写句柄 append(events)
  │
  ├─ 首次写入（实体化 materialize）
  │     header 行 ──压缩──▶ 帧①（只装一行）
  │     首批事件 ──压缩──▶ 帧②
  │     Buffer.concat([帧①, 帧②]) → 临时文件 → fsync → 不覆盖发布 → 目录 fsync
  │
  └─ 后续写入（append）
        整批事件行 ──压缩──▶ 一个帧
        写进临时文件的是"追加"：open(path,'a') → write → fsync
        写/同步失败 → truncate 回之前的长度（回滚）
  │
  ▼
读回来
  scanZstdFrames(bytes)   ← 不解压，只走字节结构，切出每个帧的 [start,end]
  ├─ 帧① ──解压──▶ 必须"恰好一行 header"，否则拒绝
  ├─ 帧②…N ──逐个解压──▶ 喂给 SessionLogScanner（只按换行切行）
  └─ 末尾残缺帧 → 记下 tornStart，只取其中完整解出的行
```

### 2.3 大白话版：从"用户说一句话"到"磁盘多了一个帧"

**完全不用上面的术语**，先建立画面（来源：`packages/session/session-persistence-jsonl/README.zh.md` 第 104 行的物理编码描述，加上本课 §9 实测步骤的转述）：

1. 模型跑了一轮，产生了若干"值得留下的事实"。
2. 写日志的那一层把这些事实攒成**一批**（不是一个一个写）。
3. 批里的每一条事实被写成**一行 JSON**。
4. 这一行行文字被**整体压成一小段自包含的字节**——这一段自己就能解开，不需要文件里别的部分。
5. 这段字节被**接到文件末尾**，然后调用系统的"刷到盘上"。
6. 如果第 5 步失败（写了一半、或刷盘失败），就把文件**截回原来的长度**——因为上层会拿同一批重试，留着半截会写出重复的序号。
7. 如果进程在第 5 步中途被杀掉，文件末尾会留下**一段解不开的残缺字节**。下次读的时候，能认出"这是残缺的一帧"，把它丢掉；**它前面那些完整的段一个都不会受影响**。
8. 从头读的时候，先解开头那一段——如果它不是**恰好一行**，这个文件就直接被判为损坏。

第 4 步和第 7 步是同一件事的两面：**正因为每一段是自包含的，追加和崩溃恢复才都成立**。

## 3. 结论先行

1. **逻辑格式与物理格式是两件事，分别归两个包。** `dsh-session-format` 只管逻辑（header 分类、相邻迁移编译、JSON 无损检查）；物理分帧、压缩、不可变 generation 命名、排他发布**明确不属于它**（`packages/session/session-format/README.zh.md` 第 12 行、`packages/session/session-format/README.md` 第 12 行）。物理那一半归 `dsh-session-persistence-jsonl`。

2. **物理格式 = "独立 Zstandard 帧的标准拼接"**：`[仅含 header 一行的一个带校验和帧][每个持久 append 批次一个带校验和帧][...]`（`packages/session/session-persistence-jsonl/README.zh.md` 第 104 行）。压缩关闭时退化为纯换行分隔 UTF-8 文本（同文件第 104 行；后缀由 `packages/session/session-persistence-jsonl/src/format.ts` 第 42–48 行决定）。

3. **分帧不是为了省空间，而是为了让"追加"成立。** 一个追加批次 = 一个自包含、带校验和、可独立解压的帧，所以追加时**完全不需要重压缩前面的字节**，也不需要动前面的帧。这是"仅追加"能落地的物理前提。

4. **文件名就是 generation（代际）编号。** v0 用 `session.jsonl[.zstd]`，v1 起用 `session.vN.jsonl[.zstd]`（`packages/session/session-format/src/filename.ts` 第 5、14–17 行；`packages/session/session-persistence-jsonl/src/format.ts` 第 58–60 行）。**版本号同时出现在文件名和第一行 header 的 `version` 字段里，并且两者必须一致**，否则报错（`packages/session/session-persistence-jsonl/src/generation.ts` 第 383–385 行）。

5. **已提交的 generation 路径绝不重命名、替换或删除**——这是文档里的原话（`docs/architecture.zh.md` 第 129 行），实现上由三件事共同保证：新代际用**不覆盖发布**（POSIX `link()` / Win32 `MoveFileExW` 不带 replace 标志）、迁移**只写最终 current target**、迁移后**逐字节校验源未变**（`packages/session/session-persistence-jsonl/src/index.ts` 第 1210–1215 行；`packages/session/session-persistence-jsonl/src/win32.ts` 第 39、127–138 行；`generation.ts` 第 905–910 行）。

6. **迁移链是"每组相邻版本一个包、一个包只负责一步"**：v0→v1、v1→v2、v2→v3、v3→v4 各自一个包（`packages/session/session-format-catalog/src/generated.ts` 第 26–31 行）。链在构造时校验**唯一且无缺口**（`packages/session/session-format/src/chain.ts` 第 64–76 行）。

7. **generation 选择规则一句话：选文件名解析出的数值最高的规范 generation。**（`packages/session/session-persistence-jsonl/src/index.ts` 第 1446、1473 行；`README.zh.md` 第 72 行。）

## 4. 机制：逻辑格式（源码对照）

### 4.1 逻辑 header 与事件信封

`packages/session/session-format/src/types.ts` 第 15–34 行：

```ts
/** Logical Session metadata shared by supported historical and current formats. */
export interface SessionFormatHeader extends SessionFormatJsonObject {
  readonly version: number
  readonly id: string
  readonly createdAt: number
  readonly cwd?: string
  readonly parentSession?: string
  readonly isSeeded: boolean
  readonly origin?: 'subagent'
  readonly delegationDepth: number
  readonly agentPreset?: string
}

/** One decoded logical Session event. */
export interface SessionFormatEvent extends SessionFormatJsonObject {
  readonly type: string
  readonly seq: number
  readonly time: number
  readonly data: SessionFormatJsonValue
}
```

按块讲解：

- **做什么**：定义"逻辑层"的两件事物——会话的头（9 个字段）与一条事件（恒 4 个字段）。
- **与哪个知识点相关**：结论 1（逻辑/物理分层）、结论 4（`version` 字段）。
- **为什么这么写**：注意 `SessionFormatHeader extends SessionFormatJsonObject`（第 16 行）——类型上它是"一个 JSON 对象"，只是**额外要求**这 9 个键。这就是"header 是封闭集合"的源码根：多余字段在物理层会被白名单挡掉（见 §4.3）。
- **`version` 在这里是 `number`，不是字面量 `4`**：这个接口要同时描述 v0…v4 五个版本，所以它必须能表示任意版本；"当前是 4"由另一个常量说（见 §4.2）。

**字段表**（`必需` 一列来自第 16–26 行的 `readonly` 与 `?`）：

| 字段 | 必需 | 类型/取值 | 备注 |
|---|---|---|---|
| `version` | 是 | number | 当前写入器为 4 |
| `id` | 是 | string | 会话标识 |
| `createdAt` | 是 | number | epoch 毫秒 |
| `isSeeded` | 是 | boolean | 是否继承过前缀 |
| `delegationDepth` | 是 | number | 委派深度（0 = 顶层） |
| `cwd` | 否 | string（**必须绝对路径**） | 物理层用 `isAbsolute` 校验，见 §4.3 |
| `parentSession` | 否 | string | 父会话 id |
| `origin` | 否 | 仅 `'subagent'` | 取值只有一个 |
| `agentPreset` | 否 | string | 该会话用的 preset 名 |

### 4.2 写入器版本常量的唯一手工真源

`packages/core/session/src/types.ts` 第 74–89 行：

```ts
 * The version is a single monotonic integer with no major/minor split. Whether
 * a bump is needed is decided by what the WRITER emits, never by what a newer
 * reader can accept: bump exactly when an older runtime could no longer handle
 * a new log with full semantic correctness ("parses without error" is not
 * correctness — silently skipping content that shapes reconstruction is a
 * wrong read). Only structural changes reach that bar: the header shape, the
 * {@link SessionEvent} envelope, core event semantics, or the surface
 * mechanism (the {@link SurfaceEventType} set and {@link SurfaceOp} variants).
 * Adding an ordinary event type does not bump — the per-event
 * {@link SessionEvent.ignorable} guard covers vocabulary growth instead. When
 * in doubt, bump: a near-identity upgrade step is almost free, a missed bump
 * makes older runtimes read new logs wrong silently. The released migration,
 * immutable prior-generation, and current fast-path rules are recorded in
 * `.agents/notes/implemented/architecture/2026-08-31-released-session-format-migrations.md`.
 */
export const SESSION_FORMAT_VERSION = 4
```

> 上面这块从 JSDoc 中段开始（第 74 行），因为 JSDoc 开头那几行在讲"header-only 读取/发布"的流程，与本知识点无关，此处省略。

按块讲解：

- **做什么**：这里定义了 `SESSION_FORMAT_VERSION = 4`，以及**什么时候该抬版本**的判据。
- **与哪个知识点相关**：结论 4（文件名与 header 的一致性）、结论 6（版本如何演进）。
- **为什么"以写入器为准"**：判据是 **older runtime 能否完全正确地处理新日志**，而**不是**新 reader 能否接受旧日志。作者原文给了一个关键区分——*"parses without error" is not correctness*（第 77–78 行）：**能解析不等于读对了**，静默跳过影响重建的内容就是错读。
- **只有结构性变更才抬版本**：header 形状、事件信封、核心事件语义、surface 机制（第 79–81 行）。**加一个普通事件类型不抬版本**，那由每条事件的 `ignorable` 守卫覆盖（第 82–83 行）。
- **`docs/session-format-status.zh.md` 第 20 行明确说这是"代码中唯一手工维护的当前写入器版本号"**，并指出包版本、codec 导出名、fixture 文件名、投影缓存版本**都不是**权威来源。

## 5. 机制：物理 framing（源码对照）

### 5.1 规范文件名 = generation 编号

`packages/session/session-format/src/filename.ts` 第 5–32 行（整个文件的问题只在这一段）：

```ts
const CANONICAL_LOG_FILENAME = /^session(?:\.v([1-9][0-9]*))?\.jsonl$/u

/**
 * Name the raw JSONL log of one immutable Session format generation. Version
 * zero keeps the original `session.jsonl`; every later generation carries a
 * lowercase numeric `.vN` component before the `.jsonl` suffix.
 * @param version - non-negative safe integer Session format version.
 * @returns the canonical basename, without any compression suffix.
 */
export function sessionFormatLogFilename(version: number): string {
  const generation = sessionFormatVersion(version, 'Session log generation version')
  return generation === 0 ? 'session.jsonl' : `session.v${generation}.jsonl`
}

/**
 * Read the generation named by one raw JSONL log basename. Temporary,
 * uppercase, leading-zero, `.v0`, and compression-suffixed names are not
 * canonical.
 * @param filename - one basename from a Session directory or archive.
 * @returns its Session format version, or `undefined` when the name is not canonical.
 */
export function parseSessionFormatLogFilename(filename: string): number | undefined {
  const match = CANONICAL_LOG_FILENAME.exec(filename)
  if (match === null) return undefined
  if (match[1] === undefined) return 0
  const version = Number(match[1])
  return Number.isSafeInteger(version) ? version : undefined
}
```

按块讲解：

- **做什么**：一对互逆函数 + 一条正则，定义"什么名字算一个 generation"。
- **与哪个知识点相关**：结论 4、结论 7。
- **第 5 行的正则就是全部规矩**：`session` + 可选 `\.v([1-9][0-9]*)` + `.jsonl`。逐条读它能得到所有排除规则：
  - `[1-9][0-9]*` —— **不允许前导零**，所以 `session.v01.jsonl` 不是规范名；也**不允许 0**，所以 `session.v0.jsonl` 不是规范名（v0 就是不带 `.vN`）。
  - 小写 `v` —— `session.V1.jsonl` 不是规范名。
  - `\.jsonl$` 是**结尾锚定** —— 所以带压缩后缀的 `session.v1.jsonl.zstd` 在这里**不匹配**；压缩后缀由物理层先剥掉再交给它（`format.ts` 第 74–76 行）。
  - 中间不能有别的东西 —— `session.v1.backup.jsonl`、`session.migration.deadbeef.tmp.jsonl`、`session.1.jsonl` 全部不是规范名。

### 5.4 不解压就能切帧

```ts
export function scanZstdFrames(buffer: Buffer, maxFrames = Number.POSITIVE_INFINITY): ZstdFrameScan {
  const frames: ZstdFrameRange[] = []
  let offset = 0

  while (offset < buffer.length) {
    const start = offset
    if (buffer.length - offset < 4) return { frames, tornStart: start }
    if (buffer.readUInt32LE(offset) !== ZSTD_MAGIC) {
      throw new Error(`corrupt Zstandard session log: invalid frame magic at byte ${offset}`)
    }
    offset += 4

    if (offset === buffer.length) return { frames, tornStart: start }
    const descriptor = buffer.readUInt8(offset)
    offset += 1
    if ((descriptor & 0x18) !== 0) {
      throw new Error(`corrupt Zstandard session log: reserved frame-header bit at byte ${offset - 1}`)
    }

    const contentSizeFlag = descriptor >>> 6
    const singleSegment = (descriptor & 0x20) !== 0
    const checksum = (descriptor & 0x04) !== 0
    const dictionaryFlag = descriptor & 0x03
    const dictionaryBytes = dictionaryFlag === 3 ? 4 : dictionaryFlag
    const contentSizeBytes = contentSizeFlag === 0
      ? (singleSegment ? 1 : 0)
      : 1 << contentSizeFlag
    const remainingHeaderBytes = (singleSegment ? 0 : 1) + dictionaryBytes + contentSizeBytes
    if (buffer.length - offset < remainingHeaderBytes) return { frames, tornStart: start }
    offset += remainingHeaderBytes

    // …（第 79–93 行：循环读 3 字节 block header，据 blockType 跳过 payload，跳到 lastBlock；与上面同一套"读长度、跳过、越界即 torn"的写法，此处省略）

    if (checksum) {
      if (buffer.length - offset < 4) return { frames, tornStart: start }
      offset += 4
    }
    frames.push({ start, end: offset })
    if (frames.length === maxFrames) return { frames }
  }

  return { frames }
}
```

## 6. 机制：仅追加与崩溃恢复（源码对照）

### 6.1 追加与"失败必须回滚"

`packages/session/session-persistence-jsonl/src/index.ts` 第 1319–1352 行：

```ts
  /**
   * Append and fsync event lines. On a partial write or sync failure, restore the
   * previous size before rethrowing because the unchanged cursor will retry the
   * batch; leaving partial bytes would create duplicate sequence numbers.
   */
  private async appendLines(meta: SessionHeader, events: readonly SessionEvent[]): Promise<void> {
    const content = await this.encodeEventBatch(events)
    const path = logPath(this.root, meta.cwd, meta.id, this.compression)
    const handle = await open(path, 'a')
    let closed = false
    const closeAppendHandle = async (): Promise<void> => {
      if (closed) return
      closed = true
      await handle.close()
    }

    try {
      const { size: before } = await handle.stat()
      try {
        await handle.writeFile(content)
        await handle.sync()
      } catch (error) {
        try {
          await closeAppendHandle()
          await this.rollbackAppend(path, before)
        } catch (rollbackError) {
          throw new AggregateError([error, rollbackError], `failed to roll back append to "${path}"`)
        }
        throw error
      }
    } finally {
      await closeAppendHandle()
    }
  }
  // …（第 1354–1362 行：rollbackAppend 以 'r+' 重新打开同一路径，truncate(size) 后再 fsync；与本块是同一件事的收尾，此处省略）
```

按块讲解：

- **做什么**：一次追加的完整动作：编码 → 以追加模式打开 → 记下当前长度 → 写 → 刷盘；**任何一步失败都回到原长度**。
- **与哪个知识点相关**：词汇表的"仅追加"与"已提交字节"；结论 3。
- **第 1327 行 `open(path, 'a')`**：追加模式的语义是"每次写都落在当前文件末尾"——**只追加在系统调用层面就成立**，不靠上层自觉。
- **`before` 从哪来（第 1336 行）**：`handle.stat()` 拿到的 `size`，在写之前取。
- **为什么必须回滚**——**方法文档就是答案，直接引原文**：*"the unchanged cursor will retry the batch; leaving partial bytes would create duplicate sequence numbers"*。也就是：上层记录的是"已提交到第几个事件"，写失败时那个游标**没有前进**，所以它会重发同一批；如果文件里留着半批字节，重发就会写出**重复的 seq**。
- **两层错误都不吞**：回滚本身失败时抛 `AggregateError([error, rollbackError], ...)`（第 1345 行）——原始写失败和回滚失败**都要报出来**，不能只报一个。
- **`closed` 布尔量与 `closeAppendHandle`（第 1328–1333 行）**：因为回滚路径与 `finally` 都会关句柄，用一个幂等包装避免二次 `close()` 抛错。
- **顺带回答"为什么不用覆盖写"**：覆盖写要求先知道旧内容边界，而"已提交字节"这个概念本身就是"文件开头一段连续前缀"；截断/覆盖会让**已经承诺过的字节消失**，而 append + `fsync` 最坏只留下一个**可识别的**撕裂尾部（§6.3）。

- **第 999–1004 行的 `catch` 是故意吞掉的**：残缺帧可能在解码器吐出任何东西之前就断了。作者注释写明了这一点，并只保留"取消"这一种必须传播的失败（`signal.aborted` 时重新抛）。

### 6.4 三类读取方式：谁都不改写日志

"仅追加"这条纪律在**读侧**同样成立。同一份日志有三种被打开的方式，**没有任何一种会改写已提交字节**（`README.zh.md` 第 76、82 行）：

| 方式 | 读多少 | 会不会迁移 | 会不会发布后继 |
|---|---|---|---|
| `stat(id)` / `list()` | **只第一帧**（只转 header） | 只转换 header | 不会。**也不碰事件行** |
| `open(id, 'read')` | 全部事件行 | **会**完整解码并迁移受支持的历史 | **不会**——返回内存里的结果就结束 |
| `open(id, 'write')` | 全部事件行 | 会（可用时复用按 revision 为键的 preparation） | **会**：编码 → Worker 校验 → 复查源 → 不覆盖发布 |

由此得到三条纪律：

1. **已提交事件绝不重写**（`README.zh.md` 第 76 行）——上表三种方式都不改写已有字节；写 open 也只**新增**一个 current generation 文件。
2. **只读访问从不发布升级**——所以"读一遍旧日志"这件事**不会**在磁盘上留下任何东西。`README.zh.md` 第 86 行点明了代价：冷进程与被淘汰的准备缓存会**重复**历史全库扫描的工作。
3. **`stat()` / `list()` 不做迁移**——它只做 header 分类（`catalog.ts` 第 45–90 行的 `current` / `migration-required` / `unsupported` / `malformed`）。所以它能在"事件行已经损坏"的情况下**仍然报出正确的会话身份**，这也是"不可读 header 不参与 `list()`、但可读 header 永远能列出"的原因（`README.zh.md` 第 84 行）。

### 7.1 POSIX：用 `link()` 而不是 `rename()`

- **做什么**：POSIX 上的"不覆盖发布"：先把内容写进一个同目录临时文件并 `fsync`，再用 `link()` 把它变成正式名字。
- **与哪个知识点相关**：结论 5（不可变 generation）。
- **为什么是 `link()` 而不是 `rename()`**——**作者原文（第 1210–1212 行）**：*"Publish via link()+unlink(), NOT rename(): link fails with EEXIST if the final path already exists, so two processes materializing the same id concurrently cannot clobber each other. rename() would silently overwrite."* 一句话：**`rename()` 会静默覆盖**，而 `link()` 在目标已存在时返回 `EEXIST`——这就把"同 id 竞态"变成了**一个必然失败**，而不是一次静默的数据毁坏。
- **临时文件从哪来**：第 1209 行的 `writeSyncedTempFile`（定义在第 1272–1282 行）以 `open(tmp, 'wx', 0o600)` **独占创建**（`wx` = 存在即失败），写完 `handle.sync()` 再关。
- **`linked` 这个布尔量（第 1213 行）的用途**：`finally` 里只有在**没有成功 `link`** 时才删临时文件。一旦 `link` 成功，这个临时文件已经**变成**了正式日志的另一个名字，此时删它必须等到目录项持久化之后——所以删的动作被搬到了第 1230–1234 行，而且**失败被吞掉**（理由写在注释里：日志已经发布且持久，删不掉一个多余硬链接不该让 append 失败）。
- **第 1223–1226 行的 `syncDirPosix(dir)`**：`link()` 只保证**目录项**被创建，不保证它**在掉电后还在**——所以要 `fsync` 父目录。
- **还有一道前置检查**：第 1208 行 `rejectExistingLog`（第 1260–1270 行）在写之前先查目录里**是否已有 generation**，有就抛 `refusing to materialize "<id>": a log already exists on disk (open it instead)`。源码注释标明这是 **TOCTOU 兜底**（真正的守卫在 `create` 路径），所以它用了 `/* v8 ignore */`。

- **争用怎么识别**：POSIX 上 `EAGAIN` / `EWOULDBLOCK` 都算（第 48–52 行 `isLockContention`，注释说明两种拼法）；Windows 上 `EBUSY`（第 82 行，来自 `ERROR_SHARING_VIOLATION` 的翻译）。

- **刻意不设过期**：头注释第 10–13 行原话——*"A live but wedged holder keeps the lock until its process exits: there is deliberately no expiry that could expropriate a stalled writer whose resumed appends would tear the log."* 也就是：**宁可让写者卡住，也不能让一个"卡了很久但还活着"的写者被抢走锁、然后恢复写入把日志撕裂**。崩溃的持有者不在此列——进程一死，描述符/句柄被内核关掉，锁自动释放（第 8–10 行）。
- **获取时机**：打开**已存在的**产物时立刻获取；对**新建**会话，只在"第一次实体化写入"之前才获取——未实体化的会话在磁盘上没有任何足迹（第 20–22 行）。

```ts
      currentPath: join(
        dir,
        generationLogFilename(sessionFormatCatalog.currentVersion, this.compression),
      ),
    }
  }
```

按块讲解：

- **做什么**：在一个会话目录里枚举文件，挑出**唯一一份**要用的 generation，并同时算出"当前版本的路径"。
- **与哪个知识点相关**：结论 4、结论 7。
- **输入从哪来**：`dir` 是会话目录（`join(projectKey 目录, encodeSegment(id))`，见 `format.ts` 第 225–269 行）；`this.compression` 是本后端配置的编码。
- **`generations` 与 `opposite` 两个数组（第 1460–1471 行）**：一次遍历同时收集"符合当前编码的规范名"和"符合**相反**编码的规范名"。后者**不是候选，而是错误**——只要存在一个就抛 `encodingMismatch`（第 1472 行）。这就是"一个根只属于一种编码"的落点。
- **第 1473 行就是选择规则的全部实现**：`generations.sort((l, r) => r.version - l.version)[0]` —— **按版本号降序排序取第一个**。没有别的优先级（不看 mtime、不看大小）。
- **`sourcePath` / `sourceVersion` / `currentPath` 三个字段的用途不同**：前两个是"这次要读哪份"；`currentPath` 是"如果它是历史版本，迁移产物该写到哪"——注意它按 `sessionFormatCatalog.currentVersion`（=4）生成，所以**迁移永远只写最终 current target**（§7.3）。
- **`latest.version` 与当前版本的关系由调用方分三路**（第 835–847 行 `resolveCurrentLog`）：
  - `=== SESSION_FORMAT_VERSION` → 直接用这份路径（当前代际）；
  - `<` 当前版本 → 返回 `undefined`（**当前代际尚不存在**，需要迁移或写 open 去创建）；
  - `>` 当前版本 → 抛 `SessionFormatUnsupportedError`，提示**升级 harness**，而不是说"日志损坏"。
- **"未来版本先于结构校验被拒绝"**这条原则在 `format.ts` 第 340–346 行的 `refuseForeignFormatVersion` 里重复了一遍，理由写在它的文档注释里：*"a future format need not satisfy this build's structural checks at all, and its user must see 'upgrade the harness', never 'corrupt session log'"*。
- **还有一道跨目录唯一性检查**（第 1486–1501 行 `findLog`）：同 id 出现在多个项目目录时抛 `duplicate JSONL session id "<id>" appears in multiple project directories`。

### 8.2 迁移链的编译期校验

`packages/session/session-format/src/chain.ts` 第 50–86 行：

```ts
  constructor(options: SessionFormatChainOptions) {
    this.currentVersion = sessionFormatVersion(options.currentVersion, 'current Session format version')
    this.restoreCurrentHeader = options.restoreCurrentHeader
    const byFrom = new Map<number, SessionFormatMigration>()
    const names = new Set<string>()
    for (const candidate of options.migrations) {
      const migration = defineSessionFormatMigration(candidate)
      if (byFrom.has(migration.fromVersion)) {
        throw new SessionFormatError(`Session migration v${migration.fromVersion}->v${migration.toVersion} is duplicated`)
      }
      if (names.has(migration.name)) throw new SessionFormatError(`Session migration name ${JSON.stringify(migration.name)} is duplicated`)
      byFrom.set(migration.fromVersion, migration)
      names.add(migration.name)
    }
    const ordered: SessionFormatMigration[] = []
    for (let version = 0; version < this.currentVersion; version += 1) {
      const migration = byFrom.get(version)
      if (migration === undefined) {
        throw new SessionFormatUnsupportedMigrationError(`Session migration v${version}->v${version + 1} is missing`)
      }
      ordered.push(migration)
    }
    if (byFrom.size !== ordered.length) {
      const invalid = [...byFrom.keys()].find(version => version >= this.currentVersion) as number
      throw new SessionFormatError(`Session migration from v${invalid} does not lead to current v${this.currentVersion}`)
    }
    this.migrations = Object.freeze(ordered)
  }

  private plan(fromVersion: number): readonly SessionFormatMigration[] {
    const from = sessionFormatVersion(fromVersion, 'stored Session format version')
    if (from > this.currentVersion) {
      throw new SessionFormatUnsupportedMigrationError(
        `stored Session uses newer format v${from}; this build writes v${this.currentVersion}`,
      )
    }
    return Object.freeze(this.migrations.slice(from))
  }
```

按块讲解：

- **做什么**：`CompiledSessionFormatChain` 的构造函数把"一串迁移声明"编译成"一条唯一、完整、有界的链"。**校验发生在构造期**（也就是进程启动装配 catalog 时），不是读到日志时才查。
- **与哪个知识点相关**：结论 6；`session-format/README.zh.md` 第 58 行（*"迁移链在构造时校验唯一且无缺口的顺序"*）。
- **`byFrom` / `names` 从哪来**：从 `options.migrations` 逐个过一遍 `defineSessionFormatMigration`（第 56 行）——那个函数会先校验"严格相邻"（第 30–32 行：`to !== from + 1` 就抛 `must declare adjacent vN->vN+1`）。
- **四类拒绝**：
  1. **同一起点重复**（第 57–59 行）→ `is duplicated`；
  2. **同名重复**（第 60 行）→ `is duplicated`；
  3. **缺口**（第 65–71 行）：从 0 到 `currentVersion - 1` 逐个必须命中 → `Session migration vN->vN+1 is missing`；
  4. **多余或越界**（第 72–75 行）：声明数多于用到的数，说明有边指向 `currentVersion` 之外 → `from vN does not lead to current vN`。
- **第 76 行 `Object.freeze(ordered)`**：编译结果冻结，之后只读。**这正是"边与边之间不共享可变状态"的前提**——设计笔记第 28 行原话：*"静态 migration declaration 描述一条相邻版本边，并为每次 artifact restore 创建新的 stage。Stage 拥有该 artifact 的可变状态；不同 Session 之间绝不共享 stage instance。"* 声明是不可变的，**状态在 stage 里**。
- **`plan()`（第 79–87 行）是"从某一版出发要跑哪些边"**：`this.migrations.slice(from)`——因为链是有序且无缺口的，**从下标 `from` 切到最后**就是完整路径。第 81–85 行挡"源版本比本 build 新"。
- **流式执行**：`createStream`（第 89–127 行）按 plan 依次 `createStage`，把每一级的 stage 串成链（第 208–227 行反向装配 `ChainedMigrationContext`）；每级 `finish()` 返回切点，且**必须与预声明的 `headerInheritedEventCount` 一致**，否则抛 `changed its predeclared inherited cut`（第 200–203 行）。设计意图写在 `session-format/README.zh.md` 第 12 行：**单遍消费物理行，不复制也不冻结中间产物**。

```js
// 复刻 zstd.ts 第 48–104 行的 scanZstdFrames，逐帧独立解压。
import { readFileSync, readdirSync, statSync } from 'node:fs'
import { join } from 'node:path'
import { zstdDecompressSync } from 'node:zlib'

const MAGIC = 0xFD2FB528
function scan(buffer) {
  const frames = []
  let offset = 0
  while (offset < buffer.length) {
    const start = offset
    if (buffer.length - offset < 4) return { frames, tornStart: start }
    if (buffer.readUInt32LE(offset) !== MAGIC) throw new Error(`bad magic at ${offset}`)
    offset += 4
    if (offset === buffer.length) return { frames, tornStart: start }
    const d = buffer.readUInt8(offset); offset += 1
    if ((d & 0x18) !== 0) throw new Error('reserved frame-header bit')
    const contentSizeFlag = d >>> 6
    const singleSegment = (d & 0x20) !== 0
    const checksum = (d & 0x04) !== 0
    const dictionaryFlag = d & 0x03
    const dictionaryBytes = dictionaryFlag === 3 ? 4 : dictionaryFlag
    const contentSizeBytes = contentSizeFlag === 0 ? (singleSegment ? 1 : 0) : 1 << contentSizeFlag
    const remaining = (singleSegment ? 0 : 1) + dictionaryBytes + contentSizeBytes
    if (buffer.length - offset < remaining) return { frames, tornStart: start }
    offset += remaining
    for (;;) {
      if (buffer.length - offset < 3) return { frames, tornStart: start }
      const bh = buffer.readUIntLE(offset, 3); offset += 3
      const last = (bh & 1) !== 0
      const type = (bh >>> 1) & 0x03
      const size = bh >>> 3
      if (type === 0x03) throw new Error('reserved block type')
      const payload = type === 0x01 ? 1 : size
      if (buffer.length - offset < payload) return { frames, tornStart: start }
      offset += payload
      if (last) break
    }
    if (checksum) {
      if (buffer.length - offset < 4) return { frames, tornStart: start }
      offset += 4
    }
    frames.push({ start, end: offset, checksum })
  }
  return { frames }
}

const root = join(process.env.DSH_HOME, 'sessions')
const files = []
;(function walk(dir) {
  let entries
  try { entries = readdirSync(dir, { withFileTypes: true }) } catch { return }
  for (const e of entries) {
    const p = join(dir, e.name)
    if (e.isDirectory()) walk(p)
    else if (/^session.*\.jsonl(\.zstd)?$/.test(e.name)) files.push({ path: p, size: statSync(p).size })
  }
})(root)

const rows = []

  rowsPerFrame.push(lines.length)
  rows.push(...lines)
}

console.log('completeFrames=', frames.length, 'tornStart=', tornStart)
console.log('magic0=0x' + buf.readUInt32LE(0).toString(16), 'expectedZstd=0x' + MAGIC.toString(16))
console.log('rowsPerFrame=', JSON.stringify(rowsPerFrame))
console.log('totalRows=', rows.length, 'rowsInFirstFrame=', rowsPerFrame[0])
```

**本次最重要的一个现场发现（并且它纠正了本笔记上一版的结论）**：**有 3 个会话目录里同时存在两代文件**。上一版笔记在更早的一次快照里测得"含 >1 个 `session*.jsonl*` 的目录"为 **0**，据此写过"本机没有发生过真实的跨代迁移"。**本次复测为 3**，并且这 3 个目录的内容构成完全一致：

```text
["session.jsonl.zstd", "session.v4.jsonl.zstd"]
["session.jsonl.zstd", "session.v4.jsonl.zstd"]
["session.jsonl.zstd", "session.v4.jsonl.zstd"]
```

逐个核对这三个目录里两份文件的**第一帧 header**（id 只打印哈希前 12 位，用来判断是不是同一个会话）：

```text
dir #1  session.jsonl.zstd    bytes=111339    mtimeUtc=2026-09-24T12:07:37Z  version=0  createdAt=1790251469439  idHash12=fc9e63c29494  keys=[type,version,id,createdAt,cwd,delegationDepth,agentPreset]
        session.v4.jsonl.zstd bytes=319287    mtimeUtc=2026-09-24T12:34:03Z  version=4  createdAt=1790251469439  idHash12=fc9e63c29494  keys=[type,version,id,createdAt,cwd,isSeeded,delegationDepth,agentPreset]
dir #2  session.jsonl.zstd    bytes=1059914   mtimeUtc=2026-09-23T16:00:04Z  version=0  createdAt=1790178126409  idHash12=6ffe0ff527a2
        session.v4.jsonl.zstd bytes=288095    mtimeUtc=2026-09-24T12:27:31Z  version=4  createdAt=1790178126409  idHash12=6ffe0ff527a2
dir #3  session.jsonl.zstd    bytes=49988496  mtimeUtc=2026-09-24T12:03:59Z  version=0  createdAt=1789912470589  idHash12=04f91e70ae35
        session.v4.jsonl.zstd bytes=11568607  mtimeUtc=2026-09-24T12:34:59Z  version=4  createdAt=1789912470589  idHash12=04f91e70ae35
```

**这三对文件证明了三件事**（都是结论 5 的直接现场证据，不再只是文档与测试）：

1. **同一个会话 id、同一个 `createdAt`** → 两份文件确实是**同一条会话的两个代际**，不是两条独立会话碰巧同目录。
2. **源代际原地保留、字节未被改写** → v0 那份的 header **仍然写着 `version: 0`**，没有 `isSeeded` 键（v0 与 v4 的字段差异就在这里）。如果真的发生过"原地迁移/替换"，它应该已经是 v4 的形状。这与测试 `generation.spec.ts` 第 763–781 行的断言同类：*发布后 `expect(await readFile(sourcePath)).toEqual(source)`*（第 778 行），目录里是 `['session.jsonl', 'session.v4.jsonl']`（第 780 行）。
3. **新代际是"发布"出来的，不是改名出来的** → 三对的 `session.v4.jsonl.zstd` 的 mtime **都晚于**对应的 v0 文件，符合"先有 v0，后来在它旁边发布 v4"的顺序。

> **标注为推断**：dir #2 的 v4 文件（288,095 字节）**比它的 v0 源（1,059,914 字节）小**，dir #3 同样（11,568,607 vs 49,988,496）。这**很可能**是因为 v0 的历史 codec 用打包的 Assistant delta 行表示流式内容，而 v4 每条事件一行并把完整紧凑 stream 内嵌进 `assistant/message`——但**我没有做逐事件的字节比对**，所以这里只写"观察到体积下降"，不写"因为所以"。

## 附录 A 关键问题与答案

> 本附录就是本课的验收题答案。**A/B 两组请读完**；**D 组属于 `3.14` 的内容，第一次读请跳过**。

### A 组

#### Q1 会话日志的物理格式是什么？为什么用 JSONL + zstd 分帧？

**答案：物理格式是独立 Zstandard 帧的标准拼接**——第一帧只装 header 那一行，其后**每个持久 append 批次各占一帧**，所有帧都带校验和；`compression: 'none'` 时退化为纯换行分隔 UTF-8 文本（`packages/session/session-persistence-jsonl/README.zh.md` 第 104 行；`index.ts` 第 1284–1305 行）。文件名后缀由 `logSuffix()` 给（`format.ts` 第 42–44 行），默认 `zstd`（`README.zh.md` 第 48 行）。

分帧的理由有四个，都能在源码里看到：

1. **让追加免于重压缩**。整文件压缩的话，每次 append 都要重写整个文件，那就不是追加日志、而是"整文件替换"了；分帧后 append 只是 `open(path,'a')` 再写一个自包含帧（`index.ts` 第 1302–1305、1324–1352 行）。
2. **让崩溃恢复有精确边界**。帧是可结构扫描的，`scanZstdFrames()` 不解压就能区分"完整帧"和"末尾撕裂帧"（`zstd.ts` 第 48–104 行）；撕裂的最后一帧只贡献其中完整解出的行，被撕开的半行丢弃（`index.ts` 第 992–1014 行）。
3. **让"只读 header"变成 O(第一帧)**。`stat()` / `list()` 只需第一帧，且被强约束为"第一帧恰好一行 header"（`assertIndependentHeaderFrame`，`generation.ts` 第 628–632 行；`assertZstdHeaderFrame`，`index.ts` 第 76–81 行；`README.zh.md` 第 82 行）。
4. **行内用 JSONL**，因为格式层本来就是"一次消费一条物理行"的模型：`SessionFormatRestore.decodeRow(rowValue)` 一次一行，迁移 stage 也是逐行 transform（`packages/session/session-format/src/types.ts` 第 222–230、141–157 行）。JSONL 还让 `compression: 'none'` 时日志可直接被外部按行读取（`README.zh.md` 第 159 行）。

另外两个细节：**不设压缩级别开关**，用 Node 内置 Zstandard 默认级别（`README.zh.md` 第 104 行）；**一个根只属于一种编码**，混用后缀的 generation 会在发现阶段被拒绝（`index.ts` 第 1468–1472 行）。

#### Q2 为什么日志只能追加、已提交的 generation 路径绝不重命名/替换/删除？

**答案：文档原话是** `docs/architecture.zh.md` 第 129 行：「JSONL v0 使用 `session.jsonl[.zstd]`，v1 及后续版本使用小写 `session.vN.jsonl[.zstd]`；**已提交 generation 路径绝不重命名、替换或删除**。」设计笔记里对应的句子是第 114 行：「Migration 不会移动、覆盖或删除任何 committed generation，并且只写最终 current target；中间版本只存在于 stage state。」

理由可以归纳成四条，每条都有实现落点：

1. **已提交字节是模型的唯一真源**。`docs/architecture.zh.md` 第 127 行说"会话日志是模型所见上下文的来源"，`deriveMessages()` 从它投影模型历史；第 131 行说"**模型可见即已记录**"。真源被原地改写，历史就无法自证。
2. **追加是唯一能在崩溃下保持单调的操作**。截断/覆盖会让"已经承诺过的字节"消失；而 append + `fsync` 最坏只留下一个可识别的撕裂尾部，且**已提交前缀的每条记录都保留**（`README.zh.md` 第 76 行）。写失败时甚至要把文件回滚到之前长度，因为不变的游标会重试该批次、半截字节会造成**重复序号**（`index.ts` 第 1319–1323 行）。
3. **迁移不能破坏被迁移的数据**。源是不可变代际，迁移**只新增**最终 current 文件：POSIX 用 `link()` 而非 `rename()`，源码注释直接写"rename() 会静默覆盖"（`index.ts` 第 1210–1212 行）；Win32 用 `MOVEFILE_WRITE_THROUGH` 且不带 replace 标志，目标已存在即失败（`win32.ts` 第 39、127–138 行）。发布前还复查源 stat 身份（`generation.ts` 第 905–910 行），源变了就报 `JsonlGenerationSourceChangedError` 且**已发布的 generation 绝不回滚**（设计笔记第 106 行）。
4. **低代际要留给 operator 排查**。设计笔记第 240 行：「低 generation 为 operator 检查而保留。Retention 不承诺 downgrade compatibility、automatic fallback，也不保证旧 runtime 能安全理解新 generation。」也就是说保留不等于兼容承诺——留着是为了**可审计**。

**本次实测已经拿到了现场证据**：`$DSH_HOME\sessions` 下有 3 个会话目录**同时**存在 v0 源与 v4 后继，同 id、同 `createdAt`，v0 那份的 header 仍是 `version: 0`、字节未被改写（详见 §9.4）。这比上一版笔记（当时测得 0 例）更强。

顺带一个反面推论：正因为路径不可替换，才有了"同 id 不能重复实体化"的硬拒绝——`rejectExistingLog()` 发现目录里已有 generation 就报 `refusing to materialize ... a log already exists on disk (open it instead)`（`index.ts` 第 1260–1270 行），而 `open` 侧则由 `session.lock` 内核锁保证单写者（`lease.ts` 第 40、70–116 行）。

### B 组

#### Q3 格式版本如何演进？迁移链是怎么组织的（一个包负责一步？）？

**答案：是，一个包负责一步，而且是强制的一步。**

- **组织方式**：每条边一个包——`session-format-v0-to-v1`、`session-format-v1-to-v2`、`session-format-v2-to-v3`、`session-format-v3-to-v4`，在 `packages/session/session-format-catalog/src/generated.ts` 第 26–31 行按序装配进 catalog；每个包同时提供自己那版的 codec（第 18–24 行）。`docs/architecture.zh.md` 第 129 行原话：「每个相邻迁移包只负责一个 `vN -> vN+1` 步骤」。
- **一步的强制性在编译期就钉住**：`defineSessionFormatMigration()` 要求 `to === from + 1`，否则抛 `must declare adjacent vN->vN+1`（`packages/session/session-format/src/chain.ts` 第 30–32 行）。
- **链必须唯一且无缺口**：同一 `fromVersion` 重复、同名重复都被拒（`chain.ts` 第 57–62 行）；0..currentVersion-1 缺任一条就抛 `Session migration vN->vN+1 is missing`（第 64–71 行）；指向 currentVersion 之外的边被拒（第 72–75 行）。
- **版本号推进方式**：`SESSION_FORMAT_VERSION` 手工改（`packages/core/session/src/types.ts` 第 89 行，当前 4），codec 顺序与"相邻迁移是否到达该版本"由 `scripts/gen-session-format-catalog.ts` 推导检查（`docs/session-format-status.zh.md` 第 20 行）。
- **什么时候才该抬版本**：判据是"older runtime 能否**完全正确地**处理新日志"，而**不是**"新 reader 能否解析旧日志"——作者原文明确说 *"parses without error" is not correctness*（`core/session/src/types.ts` 第 74–89 行）。只有结构性变更（header 形状、事件信封、核心事件语义、surface 机制）够格；**加一个普通事件类型不抬版本**，由每事件的 `ignorable` 守卫覆盖。
- **版本号与发布状态是两件事**：**写入器 v4、定稿基线 v4、但已发布版本仍是 3**（`docs/session-format-status.zh.md` 第 31–33 行定稿、第 44–47 行发布记录 + 证据标签 `dsh-v0.1.5-alpha.1`）。文档还明确"缺少发布记录不代表尚未发布"，且 alpha/beta/RC 发布同样确立持久化义务（第 24 行）。
- **结构性变更的规则**：**向后兼容的 schema 变更可以复用 V4 基线；破坏性变更必须抬写入器版本并自带头版本转换，不能复用已接受的 3→4 转换**（第 35 行）。
- **边与边之间不共享可变状态**：每次 restore `createStage` 一个新的 stage 实例，artifact 级状态归 stage 所有，**不同 Session 之间绝不共享 stage instance**（设计笔记第 28 行；`chain.ts` 第 76 行的 `Object.freeze` 保证声明侧只读）。
- **并非所有边都能独立跑**：v3→v4 的 body 恢复**要求显式子级证据**，不带绑定的 `sessionFormatV3ToV4.createStage()` 会拒绝，**空数组才是"明确声明没有子级"**（`packages/session/session-format-v3-to-v4/src/migration.ts` 第 23–25、29–39 行；`packages/session/session-format-v3-to-v4/README.zh.md` 第 51 行）。

> **一处行号纠错（R6 纪律）**：本笔记的上一版把这句出处写成 `` `README.zh.md` 第 51 行 ``。`packages/session/session-format/README.zh.md` 的第 51 行是空行、并不含这句话；真正写着"历史正文恢复要求显式的子级证据……空数组明确声明没有子级"的是 **`packages/session/session-format-v3-to-v4/README.zh.md` 第 51 行**。本版已改。

#### Q4 generation 选择规则是什么？

**答案：选"文件名解析出的数值最高"的规范 generation**，仅此一条，没有别的优先级（不看 mtime、不看大小、不看目录顺序）。

- **出处**：`packages/session/session-persistence-jsonl/src/index.ts` 第 1446 行方法文档 "Select the numerically highest canonical generation in one Session directory"，第 1473 行 `generations.sort((left, right) => right.version - left.version)[0]`；`README.zh.md` 第 72 行/第 82 行"选择数值最高的规范 generation"。
- **"规范"由 `parseGenerationLogFilename()` 定义**：先剥掉配置的压缩后缀，再要求匹配 `^session(?:\.v([1-9][0-9]*))?\.jsonl$`（`format.ts` 第 70–77 行；`packages/session/session-format/src/filename.ts` 第 5、26–32 行）。于是 `session.jsonl` → 0；`session.v0.jsonl`、`session.v01.jsonl`、`session.V1.jsonl`、`session.v1.backup.jsonl`、`session.migration.*.tmp.jsonl`、`session.1.jsonl` **全部不是 generation**（`filename.spec.ts` 第 14–30 行逐一钉住）。
- **因为解析结果参与排序，临时 stage 文件名结构上不可能被误选**为 generation。
- **相反后缀的 generation 不是"候选"，而是错误**：只要目录里出现另一编码的规范名就抛 `encodingMismatch`（`index.ts` 第 1468–1472 行）。
- **选中之后按版本分三路**（`index.ts` 第 835–847 行 `resolveCurrentLog`）：等于当前版本 → 直接用该路径；**低于**当前版本 → 返回 `undefined`（当前代际尚不存在，需要迁移/写 open 去创建）；**高于**当前版本 → 抛 `SessionFormatUnsupportedError`，提示升级 harness 而不是"日志损坏"。这条"未来版本先于结构校验拒绝"的原则在 `format.ts` 第 340–346 行 `refuseForeignFormatVersion` 里也重复了一遍，理由写在它的文档注释里。
- **还有一道跨目录唯一性检查**：同 id 出现在多个项目目录时抛 `duplicate JSONL session id "<id>" appears in multiple project directories`（`index.ts` 第 1486–1501 行）。项目目录名由 `projectKey()` 把 cwd 的 `/`、`\`、`:` 折叠成 `-` 并截断到 251 字符得到（`format.ts` 第 225–245 行）。
- **`stat()` / `list()` 与 `open` 用的是同一套选择逻辑**，区别只在"选完之后做什么"：前者只转换 header、不读事件行、不启动迁移；后者才解码事件（`README.zh.md` 第 82 行）。

### D 组（⚠️ 第一次读请跳过——属于 `3.14` 子代理与委派）

#### Q5 为什么 v3→v4 的 body 迁移需要"显式子级证据"？为什么空数组不算"没给"？

**答案：因为 v4 把"父会话有哪些子代理"这件事从 header 的数值字段搬走了。**

- v3 及更早：header 里有一个**数字 `seedLength`** 来表达继承前缀（`README.zh.md` 第 56 行：*"当前格式在 header 中存储 `isSeeded`，并从最后一个带标记的 `session/end-seed` 推导 inherited cut；历史 codec 则转换其数字 `seedLength`"*）。
- v4：**继承切点不在 header 的数值字段里**，而是从最后一个带标记的 `session/end-seed` 事件推导（`format.ts` 第 79–82 行注释；`packages/session/session-format-v3-to-v4/src/validation.ts` 第 70–78 行：只有 `data.inherited === true` 的那条才算，且必须与 `isSeeded` 一致，否则抛 `format v4 seeded header disagrees with its last inherited end-seed marker`）。
- 于是"父会话的子代理发现记录"必须在 body 迁移里**补写**——而补写需要**真实的子会话清单**，这个清单只有调用方（持久化后端）能提供：它得去父目录下**发现直属子会话**并读它们的自身 descriptor（`README.zh.md` 第 84 行）。
- 所以裸的 `sessionFormatV3ToV4.createStage()` 直接抛 `SessionFormatUnsupportedMigrationError`（`migration.ts` 第 23–25 行），而 `createSessionFormatV3ToV4(children)` 才把它绑上（第 34–39 行）。
- **空数组 ≠ 没给**（第 24 行原文 *"including an empty array for a parent without children"*）：`[]` 是"我查过了，这个父会话没有子级"这一**肯定的事实**；`undefined` 是"我不知道"。二者在语义上不能互换——前者可以安全地写出"无子级"的目录记录，后者必须让迁移失败，否则会**编造**历史。
- 这条设计与"迁移不破坏被迁移数据"（Q2 第 3 条）是同一条原则的两个面：**宁可不迁移，也不猜**。
