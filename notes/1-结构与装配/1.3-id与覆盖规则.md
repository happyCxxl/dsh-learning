## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：`id` 的用法规则。把"patch 怎么找到一行、找到之后怎么改、找不到会怎样"讲死。
**不是**：

- `cordis.yml` / `cordis.patch.yml` 的完整语法 —— 那是 `1.4`；
- `!!js` 表达式的求值引擎细节 —— 那是 `2.6`（本课只讲"为什么允许写、什么时候求值"）；
- `group` 条目的完整语义 —— 那是 `2.6`（本课只在"`insert` 带 `id` 时目标必须是 group"这一处用到它）；
- 兼容性预检为什么跳过某个 bundle —— 那是 `2.9`、`4.5`。

### 0.2 现在只要记住这 4 件事

1. **一个 bundle 可以带多份 patch**：`dsh.bundle.patch` 既可以是**一个**文件路径，也可以是**有序的文件列表**；这些文件按列表顺序拼成**该 bundle 的那一层**。
2. **`id` 是唯一的寻址键**：patch、插件管理器的启停、热重载，全都按 `id` 找行；`name` 只说"这一行要加载什么"。
3. **同一个 `id` 被多层写到时，后出现的覆盖先出现的**——而且是**整键替换**，`config` 作为整体被换掉，没有深合并。
4. **写错 `id` 不会让启动失败**：只得到一条 `patch: entry ... not found` 警告，那一行**静默失效**。所以 `id` 必须当成稳定契约。

### 0.3 明确授权：这些现在不用管

- `group` 的完整语义（`2.6`）、`inject` 的依赖解析（`2.2`）、`!!js` 的求值时机与沙箱（`2.6`）；
- dump 输出里 `# ==` 是怎么算出来的 —— `1.2` 已讲，本课不重复；
- preset / realm 里的 `id` 命名空间 —— 第三编。

判断标准只有一条：**看到一行配置，你能说出"它的 `id` 是什么、这一行是谁写的、后写的会不会盖掉它"，就够了。**

### 0.4 本课依赖 1.1 / 1.2 已经定义过的词

`profile` / `bundle` / `patch` / 条目 `entry` / 层 `layer`（`1.1`），`override` / `insert` / `group`（`1.2`）。本课不重新定义它们。

每处都是**一段能自解释的源码 + 按块讲解**。块上方标 `文件路径 第 A–B 行`；块内凡有删减，都写了省了哪些行、为什么省；讲解按「**做什么 / 与哪个知识点相关 / 为什么这么写**」三段。**所有行号都以固定提交为准**（见文末「如何获取源码」）。

## 1. 最小词汇表（本课新增 7 个词）

| 词 | 大白话 | 源码 / 配置里的写法 |
|---|---|---|
| **`id`** | 一行在树里的**门牌号**。所有"改这一行"的动作都靠它 | `- id: tool-bash` |
| **`name`** | 这一行**要加载什么**：包名，或包的**子路径导出** | `name: '@deepseek-ai/dsh-tool-bash'`、`name: '@deepseek-ai/dsh-web-app/startup'` |
| **`disabled`** | 这一行**要不要挂载**（注意：是"不挂载"，不是"删掉"） | `disabled: true`、`disabled: !!js process.platform === 'win32'` |
| **`inject`** | 这一行**等哪些服务就绪**再挂载（依赖注入） | `inject: [webStartup]` |
| **`!!js` 表达式** | 配置里写的一小段 JavaScript，**加载时才求值** | `disabled: !!js "!ctx.get('profileContext')"` |
| **一次拍平（single flat list）** | 所有层被拼成**一份有序的 patch 列表**，交给**同一个函数跑一遍** | `applyEntryPatches([], layers.flat(), warn)` |
| **unaddressable** | 插件管理器给某一行打的标记：**这行没法按 `id` 改**（找不到唯一目标） | `readOnlyReason: 'unaddressable'` |
| （复用）**`group`** | 一种特殊条目，它的 `config` 本身是一串**子条目** | `- id: <组名>` + `- group: true` + `config:` 数组 |

> ⚠️ `group` 的完整语义与 `inject` 的解析规则分别在 `2.6` / `2.2` 展开。本课只用到上面这个程度。

## 2. 先建立画面

### 2.1 静态结构图：一个 bundle 的多份 patch 怎么变成"层"

```
bundle 包（npm 包）                         <该 bundle>/package.json
  └─ dsh.bundle.patch                      "patch": "./cordis.patch.yml"
       │                                   或 "patch": [ "./cordis.patch.yml",
       │                                                     "./presets/standard.patch.yml", … ]
       ▼  按列表顺序读、按顺序拼接
   该 bundle 的「层」= 一份有序的 patch 列表
       └─ 每份 patch 只做两件事
            ├─ override：`- id: <已有 id>` + 要改的键   → 改已有行
            └─ insert  ：`- insert:` + 行数组           → 加新行
       ▼  与其他 bundle 的层、profile 的层、home 层、--patch 层一起拍平
   一份有序的 patch 列表  →  交给同一个 applyEntryPatches 跑一遍  →  条目列表
```

> 精确性说明：图上把"层"画成 bundle 的属性，实际在源码里"层"是**加载时算出来的中间结果**（`ProfileLayer`），`patchPaths` 与拼好的 `patches` 都存在这个对象里。

### 2.2 动态过程图：同一个 `id` 被两层先后写到

```
初始树（空）                               patch 列表（按应用顺序）
  []  ──────────────────────────────►  ① base 的 insert：新增 id=tool-bash（带平台门控）
                                         ② web-app 的 override：- id: tool-bash / disabled: true
                                         ③ profile / home / --patch 若有同 id 的行，继续往后排
                                                    │
                                                    ▼  同一个 id 被反复写
                                     生效的是【最后一条】，前面的写法整键被换掉
```

### 2.3 大白话版：一行是怎么被"写两次"的

**完全不用术语**，先建立画面（来源：`vendor\include\src\index.ts` 第 76–127 行的 patch 循环，见源码 4、源码 5；行数据取自 `packages\bundle\base\cordis.patch.yml` 与 `packages\bundle\web-app\cordis.patch.yml`）：

1. 手上先有一张**空清单**。
2. 第一个包递来一张"修改单"：**加一批新行**。清单里于是出现了 `tool-bash` 这一行，并注明"Windows 上不用它"。
3. 第二个包也递来一张"修改单"，但它写的是"**把叫 `tool-bash` 的那行改成：不用**"。第二张单子不新增行，只是找到那一行，把它标注的"要不要用"整个换掉——**原来那句"Windows 上不用它"就不存在了**，换成了硬性的"不用"。
4. 如果第二张单子点名的那行**根本不存在**（名字写错、或提供那行的包这次没装上），程序**不报错**，只打印一句 `patch: entry xxx not found`，然后跳过这张单子，继续处理后面的。
5. 全部单子处理完，剩下的这张清单就是真正要挂载的东西。

→ 所以"改一行"这件事，本质是**在一条有序的修改单流水线上按门牌号找行**；写错门牌号的代价是**那一条修改静默失效**，而不是启动失败。

## 3. bundle 层：一个 bundle 可以带多个 patch 文件

**结论**：`dsh.bundle.patch` 的值**可以是单个文件路径，也可以是按应用顺序排列的文件列表**；一个 bundle 因此可以贡献**多层** patch。

**出处（文档）**：`packages\boot\app-boot\README.zh.md` 第 50 行原文——"组合包的 `dsh.bundle.patch` 指定一个 patch 文件或一个有序的文件列表；`bundlePatchFiles` 校验该声明，`bundlePatchPaths` 把它解析为绝对路径；该层按此顺序拼接各文件的 patch 列表。"

### 源码 1：这个声明是怎么被读的

`packages\boot\app-boot\src\profile.ts` 第 51–75 行

```ts
/**
 * The patch files a bundle declares, as written: one file for a string
 * `patch`, the listed files in order for an array.
 * @param bundle - the bundle's `dsh.bundle` declaration, as read from package.json.
 * @returns the package-relative patch file paths in application order.
 * @throws {Error} when `patch` is neither a string nor a list of strings.
 */
export function bundlePatchFiles(bundle: DshBundleManifest): string[] {
  const declared = typeof bundle.patch === 'string' ? [bundle.patch] : bundle.patch
  if (!Array.isArray(declared) || !declared.every(file => typeof file === 'string')) {
    throw new Error('dsh.bundle.patch must be a file path or a list of file paths')
  }
  return declared
}

/**
 * Resolve a bundle declaration to its ordered absolute patch files.
 * @param packageDir - absolute directory of the bundle package.
 * @param bundle - the bundle's `dsh.bundle` declaration, as read from package.json.
 * @returns the absolute patch file paths in application order.
 * @throws {Error} when `patch` is neither a string nor a list of strings.
 */
export function bundlePatchPaths(packageDir: string, bundle: DshBundleManifest): string[] {
  return bundlePatchFiles(bundle).map(file => join(packageDir, file))
}
```

按块讲解：

- **做什么**：把 `package.json` 里的声明（字符串或数组）统一成"字符串数组"，再拼上包目录变成绝对路径。
- **与哪个知识点相关**：**0.2 的第 1 条**（多份 patch）。`bundle.patch` 是入参，来自 `package.json` 的 `dsh.bundle` 字段（变量来源见源码 2 第 747 行 `bundleManifest.dsh?.bundle`）。
- **为什么这么写**：第 59 行先把"一个文件"包成单元素数组——**两种写法在后续代码里没有分支**；第 60–62 行是守卫：既不是字符串、也不是字符串数组就直接 `throw`（错误信息就是那句 `dsh.bundle.patch must be a file path or a list of file paths`）；第 63 行的返回**顺序即应用顺序**，第 74 行的 `join(packageDir, file)` 说明列表里写的是**包内相对路径**。

`packages\bundle\web-app\package.json` 第 42–52 行（摘录）：

→ **一个 bundle 可以贡献多层 patch**，按列表顺序依次应用；`dsh-web-app` 就是"主 patch + 4 个 preset 声明"共 5 层的例子。

## 4. patch 的确切语义：id 索引 + 三种形态

**出处（源码，权威）**：`vendor\include\src\index.ts` 第 57–127 行的 `applyEntryPatches` —— 它是**挂载路径与 `--dump-config` 共用的同一份算法**（所以 dump 与真实启动不会漂移）。函数自己的 JSDoc 第 43–51 行给了一段关键说明（摘一句）：

> Apply patch lists to an entry list — THE patch semantics of this include, shared by mounting (`applyPatches`) and offline config tooling (`dsh --dump-config`) so a dump can never drift from what boots. … Inserted entries are indexed as they are added, so a later patch in the same list can target a row an earlier patch inserted. A patch that matches nothing warns and is skipped.

### 源码 2：`bundles` 列表是怎么变成"有序的层"的

`packages\boot\app-boot\src\profile.ts` 第 732–766 行

```ts
export function loadProfileDirectory(
  binName: string,
  dir: string,
  installAnchor: string,
  options: { userLayer?: boolean } = {},
): Profile {
  const manifest = dropRetiredBundles(dir, readProfileManifest(binName, dir))
  const bundles = manifest.dsh?.profile?.bundles ?? []
  const layers: ProfileLayer[] = []
  const skippedBundles: SkippedBundle[] = []
  const exemptions = bundles.length === 0 ? {} : readProfileVersionExemptions(dir)
  for (const packageName of bundles) {
    try {
      const packageDir = resolveBundleDir(binName, packageName, installAnchor, dir)
      const bundleManifest = readProfileManifest(binName, packageDir)
      const bundle = bundleManifest.dsh?.bundle
      if (bundle === undefined) {
        throw new Error(`${binName}: profile bundle ${JSON.stringify(packageName)} declares no dsh.bundle in its package.json`)
      }
      // A bundle is not a plugin row, so row admission never reads its own peers.
      const issue = evaluatePluginCompatibility(bundleManifest, exemptions)
      if (issue !== undefined && !issue.exempted) throw new Error(pluginCompatibilityWarning(issue))
      const patchPaths = bundlePatchPaths(packageDir, bundle)
      const patches = patchPaths.flatMap(patchPath => loadOverlayPatches(binName, patchPath))
      layers.push({ packageName, packageDir, patchPaths, patches })
    } catch (error) {
      skippedBundles.push({ packageName, reason: String(error) })
    }
  }
  const patchPath = join(dir, PROFILE_PATCH_FILENAME)
  const patches = options.userLayer !== false && existsSync(patchPath)
    ? loadOverlayPatches(binName, patchPath)
    : []
  return { name: basename(dir), dir, layers, patchPath, patches, skippedBundles }
}
```

> 省略说明：该函数上方第 720–731 行是 JSDoc（讲了 `userLayer: false` 的用途），与本知识点无关，此处省略；返回值里的 `patches` 是 **profile 自己那一层**，它在**所有 bundle 层之后**才被读，正是 1.2 讲的顺序。

按块讲解：

- **做什么**：读 profile 的 `dsh.profile.bundles`（第 739 行，变量来自 profile 的 `package.json`），对每个包名解析目录 → 校验它确实声明了 `dsh.bundle` → 兼容性预检 → 取它的 patch 文件列表 → **`flatMap` 按顺序把 5 个文件的 patch 拼成一份 `patches`** → 推进 `layers`。
- **与哪个知识点相关**：**0.2 的第 1 条**（多文件拼成一层）与 `1.2` 的顺序结论。第 755 行的 `flatMap` 就是"列表顺序 = 拼接顺序 = 应用顺序"的落点。
- **为什么这么写**：三条守卫决定了"层可能缺席"——① 第 748–750 行：包里没有 `dsh.bundle` 就抛错；② 第 752–753 行：兼容性不过关就抛错（除非 profile 显式豁免）；③ 第 757–759 行：上面任何一步抛错都被 `catch` 吃掉，只记进 `skippedBundles`，**该 bundle 不贡献层，其余 bundle 继续**。这就是 1.2 里"某些 bundle 被跳过"的源码位置。
- **一个容易看漏的点**：第 762 行 `existsSync(patchPath)` —— profile 自己的那层是**存在才读**，缺失不报错。

### 4.1 所有层最后被拍平成一份列表

`packages\boot\app-boot\src\profile.ts` 第 800–815 行的 `composeEntries`，全函数只有一句实质代码（函数头在第 808 行，JSDoc 在第 800–807 行）。摘录那一行：

`packages\boot\app-boot\src\profile.ts` 第 811 行

```ts
return applyEntryPatches([], structuredClone(layers.flat()), (message: string, ...args: unknown[]) => {
```

- `layers.flat()` —— 把"层"的数组**拍平成一维**的 patch 列表；
- `[]` —— 起点是**空条目列表**（1.2 讲过的空根）；
- 它的 JSDoc 第 801–803 行写明：这**就是 boot include 做的那一次调用**，"so flag derivation and config dumps see exactly what mounts"。

### 源码 3：id 索引是怎么建的

`vendor\include\src\index.ts` 第 57–74 行

```ts
export function applyEntryPatches(
  data: EntryOptions[],
  patches: PatchOptions[] | undefined,
  warn: (message: string, ...args: any[]) => void,
): EntryOptions[] {
  if (!patches?.length) return [...data]
  data = structuredClone(data)

  const entryMap = new Map<string, EntryOptions>()
  const buildMap = (entries: EntryOptions[]) => {
    for (const entry of entries) {
      if (entry.id) entryMap.set(entry.id, entry)
      if (entry.group && Array.isArray(entry.config)) {
        buildMap(entry.config)
      }
    }
  }
  buildMap(data)
```

> 省略说明：第 43–56 行是该函数的 JSDoc（本节开头已摘引关键句），此处省略以免重复。

按块讲解：

- **做什么**：先 `structuredClone` 复制一份（**不改动传进来的数据**，第 46–51 行的注释解释了原因：patch 共享同一份缓存解析结果时，反复应用会"把早先的 patch 值烤进去"，热重载就再也回不去了）；然后建立 `entryMap`：**所有带 `id` 的条目**都登记进去，遇到 `entry.group` 且 `config` 是数组时**递归登记子条目**。
- **与哪个知识点相关**：**0.2 的第 2 条**（`id` 是寻址键）。
- **为什么这么写**：`entryMap` 是一个 `Map`，键就是 `id` 字符串——所以"按 `id` 找行"是 O(1) 查表；`entryMap.set` 在重复 `id` 时**后写覆盖先写**，并且**不报错**（重复 `id` 的后果见 §6.3）。
- **边界（读代码所得）**：`entryMap` 是**一棵树共享的一个扁平 Map**，group 子条目与顶层条目同名时，同样是"后登记进 Map 的赢"。另外，`Array.isArray(entry.config)` 这个条件意味着**只有 `group: true` 且 `config` 为数组的行才会被递归登记**——`config.plugins` 这类"配置数据里的 id"（见下文 §4.4 的实测数字）根本不是条目。

```ts
      // layer, then the user's, then `--patch` overlays), and a layer must be
      // able to configure or disable a row an earlier layer inserted; without
      // this, inserted rows were silently unpatchable.
      buildMap(insert)
      continue
    }
```

> 省略说明：块尾正好停在第 102 行的 `continue`；紧接的第 104 行起是"非 insert"分支，属源码 5，此处不断开。

按块讲解：

- **做什么**：`for (const patch of patches)` 逐张修改单处理。第 77 行把每张单子的字段拆开：`id` / `insert` / `name` **单独取出**，`...overrides` 是**其余所有键**（比如 `config`、`disabled`、`inject`）——这三个变量的来源就是这一行解构。
- **与哪个知识点相关**：`1.2` 的三种形态表；本课 **0.2 的第 4 条**（找不到只警告）。
- **两条 `insert` 路线**：
  - **不带 `id`**（第 92–94 行）：`data.push(...insert)` **追加到顶层**——bundle 就是靠这个把自己那一堆行推进空根的；
  - **带 `id`**（第 80–91 行）：目标必须**存在**且**是 group**，然后把 `insert` 推进 `target.config`。两条守卫都写明了"警告 + `continue`"：`patch insert: entry %C not found`、`patch insert: entry %C is not a group`。
- **为什么这么写（作者原文）**：第 95–99 行的注释——"a layer must be able to configure or disable a row an earlier layer inserted; without this, inserted rows were silently unpatchable"。即 `buildMap(insert)` 是**故意在插入后立刻重建索引**，让后面的层能改到刚插入的行。
- **关于 `%C`**：它是**调用方负责替换**的占位符（printf 风格）。boot 路径的替换代码在 `packages\boot\app-boot\src\profile.ts` 第 811–814 行（`warn(message.replace(/%C/g, () => JSON.stringify(args[index++])))`），替换后你看到的是 `patch: entry "xxx" not found`；如果自己直接调用而不替换，警告里就会留着字面的 `%C`（本课 §6.3 的实测输出就是这样，属正常）。

### 源码 5：非 insert 的守卫、身份校验与"浅赋值"

`vendor\include\src\index.ts` 第 104–127 行

```ts
    if (!id) {
      warn('patch: id is required for non-insert patches')
      continue
    }

    const target = entryMap.get(id)
    if (!target) {
      warn('patch: entry %C not found', id)
      continue
    }

    if (name && name !== target.name) {
      warn('patch: name mismatch for %C (expected %C, got %C), skipping', id, target.name, name)
      continue
    }

    for (const [key, value] of Object.entries(overrides)) {
      if (key === 'id') continue
      target[key] = value
    }
  }

  return data
}
```

按块讲解：

- **做什么**：处理"覆盖"这一类 patch：必须带 `id` → 查 `entryMap` → 找不到就**警告并跳过（不中断）** → 若这张单子还写了 `name`，就拿它和目标的真实 `name` 比对，不一致就**警告并跳过整条单子**。
- **与哪个知识点相关**：`id` 与 `name` 的分工（§5）、`id` 必须稳定（§6）、浅赋值（§4.4）。
- **为什么这么写**：
  - 第 104–107 行的守卫把"漏写 `id`"变成一条明确的警告，而不是静默把整行数据糊到树上；
  - 第 115–118 行的 `name` 校验是**防串号**：如果某个 `id` 被复用到了另一行上，写 `name` 的单子会拒绝生效，而不是打到错误的条目上；
  - 第 120–123 行是**最容易误解的一段**：`for (const [key, value] of Object.entries(overrides))` **逐个顶层键浅赋值**，所以 `config` 是**作为一个整体被替换**的（下一节有实测）。

### 4.4 覆盖是浅赋值（实测）

**代码依据**：源码 5 第 120–123 行 —— `target[key] = value`，没有任何递归合并。

**实测输出**（跑法与注意事项见下表）：


> **这也是 bundle 作者要遵守的纪律**：`packages\bundle\web-app\cordis.patch.yml` 第 5–6 行的注释原文就写着 *"A patch replaces the targeted row's whole `config`, so each row below restates every key it owns."*

|---|---|

## 7. 为什么 `id` 必须稳定

因为它是**所有寻址行为共用的键**：

1. **patch 定位**：bundle 层、profile 层、home 层、`--patch` 层全都按 `id` 打（源码 3–5）。
2. **插件管理器的启用 / 禁用 / 移除**：它按 `id` 把结果写回 profile 的 patch 文件（源码 7）。
3. **热重载**：重放走的是同一个 `applyEntryPatches`。源码依据是 `vendor\include\src\index.ts` 里的**唯一漏斗** `applyPatches`（第 239–243 行）：

```ts
  private applyPatches(data: EntryOptions[], patches = this.config.patches): EntryOptions[] {
    return applyEntryPatches(data, patches, (message, ...args) => {
      this.ctx.root.logger?.('loader').warn(message, ...args)
    })
  }
```

   挂载（第 262 行 `this.root.update(this.applyPatches(this.data!))`）、热重载（第 279–282 行 `refresh()`）、文件更新（第 197 行）**三处都调用它**；告警也因此统一走 loader 的 logger——这就是你启动时看到 `patch: entry xxx not found` 的地方。

**插件管理器自己的说法**（工具描述原文，`packages\boot\plugin-manager\src\tools.ts` 第 21 行）：

> … Changes affect every session in this profile. **List first to obtain exact identifiers.** …

### 7.1 源码 6：加载器**不检查**重复 `id`

`vendor\loader\src\config\tree.ts` 第 51–72 行

```ts
  ensureId(options: Partial<EntryOptions>) {
    if (!options.id) {
      do {
        options.id = Math.random().toString(16).slice(2, 10)
      } while (this.store[options.id])
    }
    return options.id!
  }

  /** Resolve an entry by id, including nested ids separated by `EntryTree.sep`. */
  resolve(id: string) {
    const parts = id.split(EntryTree.sep)
    let tree: EntryTree | undefined = this
    const final = parts.pop()!
    for (const part of parts) {
      tree = tree.store[part]?.subtree
      if (!tree) throw new Error(`cannot resolve entry ${id}`)
    }
    const entry = tree.store[final]
    if (!entry) throw new Error(`cannot resolve entry ${id}`)
    return entry
  }
```

> 变量来源说明：`this.store` 是这一行的声明——`vendor\loader\src\config\tree.ts` 第 13 行 `public store: Dict<Entry> = Object.create(null)`，**一个以 `id` 为键的对象**；本方法在抽象类 `EntryTree`（第 7 行）里。

按块讲解：

- **做什么**：`ensureId` 只做一件事——**当 `id` 缺失时**生成一个随机十六进制串，并循环到不撞车为止；`resolve` 按 `:` 拆分 `id` 逐层找子树，最后 `tree.store[final]` 取条目。
- **与哪个知识点相关**：**0.2 的第 2、4 条**（`id` 是寻址键 / 写错只警告）。
- **为什么这么写**：`while (this.store[options.id])` 这个撞车检查**只在自动生成的分支里**——也就是说，**你显式写的 `id` 重复时，加载器不会报错**。而 `store` 是普通对象，同一 `id` 反复写入只会**后写覆盖先写**。
- **实测（本课跑了的是 patch 层）**：`vendor\loader\src` 全目录搜 `duplicate` 只有 `vendor\cosmokit` 里一个无关函数（不涉及 loader）；把 `id` 当索引键的是 `vendor\include\src\index.ts` 的 `entryMap`，它 `set` 而不报错。
- **一个更狠的边界（读代码所得，本课未跑真实 Loader 实测）**：`vendor\loader\src\config\group.ts` 第 52 行在建映射时用的是 `Object.fromEntries(config.map(options => [options.id ?? Symbol('anonymous'), options]))` —— 同一 `id` 出现两次会**丢掉靠前那条**；第 22 行又是 `this.tree.store[id] ??= new Entry(...)`——同一个 `id` 只对应**一个** Entry 对象。所以重复 `id` 不只是"其中一行 patch 打不到"，靠前那一条连**自己的 fiber 都不会有**（它没被挂载）。

### 7.2 源码 7：插件管理器就是按 `id` 把结果写回 patch 文件

`packages\boot\plugin-manager\src\patch.ts` 第 7–43 行

```ts
/** Replace the last matching override or append one after existing insertions.
 * @param filename Current profile patch file.
 * @param id Unique composition entry id.
 * @param name Module name used to match name-qualified overrides.
 * @param enabled Desired entry enablement.
 * @returns Whether the file changed.
 */
export async function writePluginEnabled(filename: string, id: string, name: string, enabled: boolean): Promise<boolean> {
  let text: string
  try {
    text = await readFile(filename, 'utf8')
  } catch (error) {
    if ((error as NodeJS.ErrnoException).code !== 'ENOENT') throw error
    text = '[]\n'
  }
  const document = parseDocument(text, {
    customTags: [{ tag: 'tag:yaml.org,2002:js', resolve: (value: string) => value }],
  })
  const error = document.errors[0]
  if (error !== undefined) throw error
  if (!isSeq(document.contents)) throw new Error('Profile patch must be a YAML sequence')
  loadOptionalPatches('dsh', filename)
  const items = document.contents.items
  const target = items.findLast((item, index) => {
    if (!isMap(item) || document.getIn([index, 'id']) !== id || item.has('insert')) return false
    const expectedName = document.getIn([index, 'name'])
    return !expectedName || expectedName === name
  })
  if (isMap(target)) {
    if (document.getIn([items.indexOf(target), 'disabled']) === !enabled) return false
    document.setIn([items.indexOf(target), 'disabled'], !enabled)
  } else {
    document.add({ id, disabled: !enabled })
  }
  await writeFileAtomic(filename, String(document), { mode: 0o600 })
  return true
}
```

按块讲解：

- **做什么**：在 profile 的 patch 文件里，**从后往前**找最后一条"`id` 相同、不是 `insert`、且没写 `name` 或 `name` 与目标一致"的覆盖行；找到就改它的 `disabled`，找不到就**在文件末尾追加** `{ id, disabled }`。写回是原子的（`writeFileAtomic`）且保留注释（用 `parseDocument` 而非 `parse`）。
- **与哪个知识点相关**：**0.2 的第 2 条**（`id` 是寻址键）与 §5.2 的 `name` 校验——这里 `!expectedName || expectedName === name` 与源码 5 第 115 行的 `if (name && name !== target.name)` 是**同一条规则的两个方向**：*校验*时"没写 `name` 就放行"，*查找*时"没写 `name` 也能匹配"。
- **为什么这么写**（都在注释里）：第 7 行"Replace the last matching override or append one after existing insertions"——追加在末尾保证了**它是最后一层**（后写者赢）；第 32–34 行的 `return !expectedName || expectedName === name` 解释了为什么同名多行也能被改。
- **推论（标注为推断）**：正因为写回是"改最后一条匹配的、否则追加到末尾"，**用户手动写过的行不会被删掉或重写**，插件管理器的开关与手写 patch 可以共存；代价是文件会逐渐积累多条同 `id` 的行。
- **配套的调用者**：`packages\boot\plugin-manager\src\index.ts` 第 439 行 `await writePluginEnabled(this.profile.patchPath, row.patchId, row.moduleName, enabled)`；而 `row.patchId` 是在第 252–272 行的 `listPlugins` 里算出来的——它把运行时条目的 `options.id` 与组合后的 patch 行逐个比对，**只有当恰好一条候选、且 `name` 也对得上时**才给出 `patchId`，否则把该行标成 `readOnlyReason: 'unaddressable'`（即"这行没法按 `id` 改"）。这就是重复 `id`/`name` 不符在**用户可见层面**的后果：插件管理器拒绝改它。
- **顺带一封出处**：`packages\boot\plugin-manager\tests\patch.spec.ts` 第 18–31 行是这条写回逻辑的现成测试（"preserves comments, expressions, unrelated configuration and the last override"），第 78–79 行还用真实的 `applyEntryPatches` 断言了"多条同 `id` patch 按顺序应用、最后一个生效"。

### 7.3 重复 `id` 的第三种后果：某些注册表**直接拒绝**

加载器不拒绝重复，但**服务自己的注册表可能拒绝**。`packages\bundle\web-app\cordis.patch.yml` 第 160–164 行的注释写明了：

```yaml
    # The Host inspect providers are process-global: the registry rejects a
    # duplicate id, so they register here once and every preset's `tool-cordis`
    # row reads them.
    - id: cordis-inspect-providers
      name: '@deepseek-ai/dsh-tool-cordis/host'
```

对应的插件源码 `packages\extensions\tool-cordis\src\host.ts` 第 9–18 行（JSDoc 摘一句）：

> Register the Host inspect providers once per process. **The registry keys providers by id and rejects a duplicate**, so this row belongs to the host composition beside `cordis-host-runner`; every per-session `tool-cordis` row reads the shared set through its tools.

### 7.4 改 `id` 的后果：静默失败（有真实事故记录）

**症状**：下游 patch 全部失配，但**只得到一条警告**，不中断：

```
patch: entry xxx not found
```

**真实事故**：`docs\upgrade-guide\v0.1.7-rc.2\schedule-optional-bundle\guide.zh.md` 第 16 行原文记着一次这样的迁移——某版本把三行从 Web 组合里移走、改由另一个 bundle 插入，于是：

> 按 id 开启 Schedule 的 profile 升级后会**失去 Schedule**：loader 警告 `patch: entry schedule not found`（`time-context` 和 `ui-schedule` 同理），`schedule_*` 工具和自动化任务页面消失，已存储的提醒不再投递。已存储的任务和投递记录仍保留在磁盘上。

→ 也就是说 `id` 变更（或**行换了归属的 bundle**）造成的是**静默失败**：树能起来，效果却没了。所以 `id` 必须当成稳定契约对待。

### 7.5 实测：重复 `id` 到底打到了谁

复现窗口就是源码 5 里的那两处守卫（`vendor\include\src\index.ts` 第 109 行到第 118 行）。构造两行同 `id` 的条目 + 三张 patch 单（打重复 `id`、打不存在的 `id`、`name` 不符），跑法与注意事项同 §4.4：

```powershell
# 在 <repo> 根目录执行
@'
import { applyEntryPatches } from './vendor/include/src/index.ts'
const rows = [
  { id: 'a', name: 'pkg', config: { v: 1 } },   // 第一条 a
  { id: 'a', name: 'pkg', config: { v: 1 } },   // 第二条 a（重复 id）
  { id: 'b', name: 'pkg' },
]
const patches = [
  { id: 'a', config: { v: 2 } },                // 打到谁？
  { id: 'ghost', disabled: true },              // 目标不存在
  { id: 'b', name: 'other-pkg', disabled: true }, // name 不符
]
const seen = []
const tree = applyEntryPatches(rows, patches, (m, ...a) => seen.push(`${m} :: ${a.join(' | ')}`))
console.log(JSON.stringify(tree))
console.log(seen.join('\n'))
'@ | node --import tsx --input-type=module
```

实测输出（原文照录）：

```
[{"id":"a","name":"pkg","config":{"v":1}},{"id":"a","name":"pkg","config":{"v":2}},{"id":"b","name":"pkg"}}]
patch: entry %C not found :: ghost
patch: name mismatch for %C (expected %C, got %C), skipping :: b | pkg | other-pkg
```

读出来的三条结论：

1. **重复 `id` 时，只有靠后那一行被改到**（`v: 1` → `v: 2` 发生在第二条），靠前那条**永远是 `v: 1`**——它变成了"patch 打不到的行"；
2. **目标不存在** → 警告 + 跳过，**不中断**：后面的 `name` 校验照样执行；
3. **`name` 不符** → 整条 patch 跳过并告警。

> 警告里的 `%C` 没有被替换，是因为**替换由调用方负责**（见源码 4 的讲解）；在真实启动路径里你会看到 `patch: entry "ghost" not found`。

## 8. 为什么 `disabled` 可以写成表达式

### 8.1 仓库里实际出现的五种写法（静态计数，可复现）

对 `packages\bundle\base\cordis.patch.yml` + `packages\bundle\web-app\` 下的 5 个 patch 文件做行级统计（命令见下），得到：

| 写法 | 出现次数 | 语义 |
|---|---|---|
| `true` | 40 | **硬关闭**（该形态确定不要这一行） |
| `!!js process.platform !== 'win32'` | 7 | **平台门控**：非 Windows 才启用 |
| `!!js process.platform === 'win32'` | 7 | **平台门控**：仅 Windows |
| `!!js "!ctx.get('profileContext')"` | 5 | **服务存在性门控**：没有 `profileContext` 服务就禁用 |
| `!!js "ctx.get('profileContext')?.name !== 'desktop'"` | 3 | **按 profile 名门控**：仅 `desktop` 形态启用 |
| `false` | 1 | 显式启用（覆盖更早的禁用） |

**统计命令**（在 `<repo>` 根目录，只读）：

```powershell
Select-String -Path packages\bundle\base\cordis.patch.yml,
  packages\bundle\web-app\cordis.patch.yml,
  packages\bundle\web-app\presets\*.patch.yml -Pattern 'disabled:\s*(.+)$' |
  ForEach-Object { $_.Matches[0].Groups[1].Value.Trim() } | Group-Object | Sort-Object Count -Descending
```

实测输出（原文照录）：

```
Count Name
----- ----
   40 true
    7 !!js process.platform !== 'win32'
    7 !!js process.platform === 'win32'
    5 !!js "!ctx.get('profileContext')"
    3 !!js "ctx.get('profileContext')?.name !== 'desktop'"
    1 false
```

> **一处早期记录（未复现）**：本笔记初版给的表是"`true` 38 / 平台门控各 6 / 服务存在性 5 / profile 名 3"，取自当时一次本机 `web` profile 的 dump 统计，并给出了 `!!js '!ctx.get(''profileContext'')'` 这种 YAML 重渲染后的写法（dump 会重新加引号、把内层单引号写两遍）。本节给出的是**当前提交下、直接从仓库文件数出来的**数字——两者只差几处，**共同说明的是"形态有这几类"这一点**，不要把某个数字当常量。

**价值**：同一个 bundle 能**复用到多种产品形态**，不必为每种形态复制一份 patch。这是"可组合"能真正落地的前提。

**求值时机：表达式在"相关服务就绪之后"才解析。** `packages\bundle\web-app\cordis.patch.yml` 第 8–11 行的注释原文：

> The web-startup plugin injects `cmdlineArgs` and provides `webStartup` as an ordinary Cordis service. **Rows configured from flags inject that service, so Loader resolves their expressions only after it exists.** The web runtime then provides bind-dependent `webRuntime` values to the trust fence.

机制上对得上：行上写 `inject: [...]`（§5.4 的实例）之后，这一行要等那个服务就绪才**激活**；而 `config` 的插值位置是"**在声明的注入激活后**、基于该插件上下文"（`docs\cordis-primer.zh.md` 第 45 行）。所以按 `inject`、`process.platform`、`ctx.get('profileContext')` 来门控一行，都是"此刻"的答案。
（`disabled` 与 `config` 的求值时机是否严格同步，本课**未逐分支实测**；依据是上面两处原文 + 源码 8 的 `disabledOf`。）

**而 `--dump-config` 里 `!!js` 原样打印、不求值**（所以 dump 出来仍是一份可加载的 YAML）——`1.2` 已确认，本课实测也印证：§6.2 输出里 `tools` 的 `config.mode` 仍是 `{ __jsExpr: … }` 节点。

### 8.2 源码 8：`!!js` 在哪两个字段被求值

`vendor\loader\src\config\entry.ts` 第 67–99 行

```ts
  get id() {
    let id = this.options.id
    if (this.parent.tree.ctx.fiber.entry) {
      id = this.parent.tree.ctx.fiber.entry.id + EntryTree.sep + id
    }
    return id
  }

  /** True when this entry or any owning parent entry is disabled. */
  get disabled() {
    // group is always enabled
    if (this.options.group) return false
    let entry: Entry | undefined = this
    do {
      if (this.disabledOf(entry.options)) return true
      entry = entry.parent.ctx.fiber.entry
    } while (entry)
    return false
  }

  /**
   * Effective disabled state: a `!!js` expression evaluates against the loader
   * context. The raw node stays in the options, so write-back keeps the form.
   */
  private disabledOf(options: EntryOptions): boolean {
    return isJsExpr(options.disabled)
      ? Boolean(this.evaluate(options.disabled.__jsExpr))
      : Boolean(options.disabled)
  }

  evaluate(expr: string) {
    return evaluate(this.ctx, expr)
  }
```

> 变量来源说明：`this.options` 是**这一行的原始数据**（`{ id, name, config, disabled, … }`）；`this.ctx` 是这一行自己的上下文（构造函数里由父上下文扩展而来）；`EntryTree.sep` 是 `':'`（`vendor\loader\src\config\tree.ts` 第 8 行）。

按块讲解：

- **做什么**：`disabled` 不是一个布尔字段，而是一个**读取时现算**的状态：先看这一行自己（`disabledOf`），再沿"父条目"链往上走（第 79–83 行），**任何一层禁用就禁用**；`group` 行本身永远算启用（第 78 行）。
- **与哪个知识点相关**：本课 **0.2 的第 4 条**与 §8.1 的五种写法；它也解释了为什么"禁用既有行"比"删除行"更可靠（§9）。
- **`!!js` 在哪里被求值**：`disabledOf` 第 92–94 行——是表达式节点就 `evaluate` 并取布尔，否则直接 `Boolean(...)`。**每次挂载决策都会重算**，所以门控能看到"此刻的" loader 上下文。
- **为什么"原始的表达式节点要留在 options 里"**：JSDoc 第 88–90 行——`The raw node stays in the options, so write-back keeps the form`。这与 §6.2 实测里 `tools` 的 `config.mode` 仍是 `{ __jsExpr: … }` 是同一件事：**patch 与 dump 都只搬运、不求值**。
- **顺带一个 `id` 的细节**：第 67–73 行说明**运行时**的 `id` 可能带前缀（父条目的 `id` + `':'` + 自己的 `id`）。这也是插件管理器要区分"Loader entry id"与"patch 寻址用的 tree-local id"（`patchId`）的原因。
- **`config` 侧的对应实现**：`vendor\loader\src\index.ts` 第 104–113 行的 `internal/config` 监听器里，最后一步是 `return interpolate(this.ctx, config)`；但它有意**跳过 tree carrier**（第 110–111 行：插件带 `EntryGroup.key` 标记就直接返回原值）——因为它们装的是**别的行的配置**，那些 `!!js` 属于别的行自己的上下文。

### 8.3 源码 9：求值就是"在上下文的 `with` 作用域里 `eval`"

`vendor\loader\src\config\utils.ts` 第 1–32 行（整文件）

```ts
import { valueMap } from '@deepseek-ai/cosmokit'

// eslint-disable-next-line no-new-func
/** Evaluate a JavaScript expression against a loader context scope. */
export const evaluate = new Function('ctx', 'expr', `
  with (ctx) {
    return eval(expr)
  }
`) as ((ctx: object, expr: string) => any)

/** Recursively replace YAML `!!js` expression nodes with evaluated values. */
export function interpolate(ctx: object, value: any) {
  if (isJsExpr(value)) {
    return evaluate(ctx, value.__jsExpr)
  } else if (!value || typeof value !== 'object') {
    return value
  } else if (Array.isArray(value)) {
    return value.map(item => interpolate(ctx, item))
  } else {
    return valueMap(value, item => interpolate(ctx, item))
  }
}

/** Return true when a value is a serialized loader JavaScript expression. */
export function isJsExpr(value: any): value is JsExpr {
  return value instanceof Object && '__jsExpr' in value
}

/** Serialized JavaScript expression produced by the include YAML tag. */
export interface JsExpr {
  __jsExpr: string
}
```

按块讲解：

- **做什么**：`evaluate` 用 `new Function` 造一个函数，函数体是 `with (ctx) { return eval(expr) }` —— 于是表达式里的 `ctx.get('profileContext')`、`process.platform` 都能直接写；`interpolate` 负责**递归**把整棵 `config` 里的表达式节点换掉；`isJsExpr` 是判定（`'__jsExpr' in value`）。
- **与哪个知识点相关**：§8.1 的写法表 + `1.3` 的语言点"配置里的表达式在运行时求值"。
- **为什么这么写**：`!!js` 的 YAML 标签在 `vendor\include\src\index.ts` 第 9–15 行被解析成一个**普通对象** `{ __jsExpr: '源码文本' }`（`construct: (data) => ({ __jsExpr: data })`），所以它能安全地穿过 YAML→JSON→patch 的搬运，直到真正需要值的时候才求值；这也让 `--dump-config` 能**原样打印**它（`1.2` 已验证）。
- **代价（标注为推断）**：`eval` + `with` 意味着表达式能摸到传给它的整个上下文对象，且**语法错误要到求值时才炸**。仓库因此加了一道静态门禁（源码 10），并且 `1.2` 提到的 `--dump-config` 不启动任何插件——**dump 只搬运，不触发这段求值**。

### 8.4 源码 10：仓库自己有一道门禁，只允许 `disabled` 带表达式

`scripts\verify-cordis-config.ts` 第 508–539 行

```ts
/**
 * Expression-node diagnostics for one entry. `disabled` is the single
 * interpolated metadata field: its own `!!js` expression node is allowed and
 * must parse, while expressions nested below it stay truthy data; every other
 * metadata field must stay fully static.
 * @param entry - one loader entry (or patch row).
 * @param path - the entry's diagnostic path prefix.
 * @returns one diagnostic per offending expression.
 */
export function metadataExpressionErrors(entry: Record<string, unknown>, path: string): string[] {
  const problems: string[] = []
  for (const field of metadataFields) {
    if (!(field in entry)) continue
    const expressionPaths: string[] = []
    collectExpressionPaths(entry[field], `${path}.${field}`, expressionPaths)
    for (const expressionPath of expressionPaths) problems.push(`${expressionPath}: !!js is not interpolated here`)
  }
  const disabled = entry.disabled
  if (disabled !== undefined) {
    if (isJsExpr(disabled)) {
      const detail = disabledExpressionProblem(disabled.__jsExpr)
      if (detail !== undefined) problems.push(`${path}.disabled${detail}`)
    } else {
      // A non-expression value gates on Boolean() at mount; an expression
      // nested anywhere below it never evaluates, so it must stay literal.
      const expressionPaths: string[] = []
      collectExpressionPaths(disabled, `${path}.disabled`, expressionPaths)
      for (const expressionPath of expressionPaths) problems.push(`${expressionPath}: !!js is not interpolated here`)
    }
  }
  return problems
}
```

> 变量来源说明：`metadataFields` 是本文件第 41 行定义的常量——`['id', 'name', 'group', 'inject', 'intercept', 'isolate']`；`isJsExpr` 与 `collectExpressionPaths` 也来自本文件（前者由 `scripts\cordis-yaml.ts` 复用）。

按块讲解：

- **做什么**：扫描仓库里的 Cordis YAML（含 include patch 与插入的行），**凡是 `id` / `name` / `group` / `inject` / `intercept` / `isolate` 里出现表达式节点就报错**（`!!js is not interpolated here`）；`disabled` 是**唯一**被允许带表达式的字段，但它必须是表达式节点本身、而且必须能被解析。
- **与哪个知识点相关**：§8.1/§8.2 —— 把"`!!js` 只能写在 `config` 与 `disabled` 上"从**约定**变成**可执行检查**。文档侧同样这么写：`docs\cordis-tutorial\05-config.zh.md` 第 107 行——"`!!js` 仅在 `config` 与条目 `disabled` 字段内有效……其余元数据（`name`、`id`、`inject` 等）保持静态"。
- **为什么这么写**：因为**写错位置的表达式不会报错，只会静默变成真值**。注释第 531–532 行说得最直白：非表达式的 `disabled` 值在挂载时按 `Boolean()` 判定，**嵌在它下面的表达式永远不会被求值**，所以必须保持字面量。
- **为什么必须有这道门禁（历史事故）**：`docs\postmortem\0002-js-expression-disabled-filesystem-tools.zh.md`（状态：已解决）。摘要第 9 行原文：

  > ACP（Agent Client Protocol）示例试图通过 `disabled: !!js ...` 有条件地启用文件系统插件，但 Cordis 仅在插件 `config` 内部对 JavaScript 表达式求值。**原始的表达式对象为 truthy，因此文件系统栈始终处于禁用状态。**

  复盘第 32 行给的是当时的根因：*"实际只有 `entry.options.config` 使用它……而 `Entry.disabled` 直接测试 `entry.options.disabled`，不经过插值。YAML 标签在语法上合法，因此加载过程不产生任何诊断信息。"*

  **文档口径 vs 源码口径（以源码为准）**：复盘描述的是**当时**的实现；**当前**提交里 `Entry.disabled` 已经会求值（源码 8 第 91–95 行的 `disabledOf`），所以 `disabled: !!js ...` 现在是**受支持且有门禁**的写法。复盘留下的教训仍然成立，也是本课最值钱的一句：**"语法上被接受的配置值，不一定在你以为的位置被求值。"**

## 9. 一处值得学的设计取舍：为什么"禁用"而不是"删除"

`packages\bundle\web-app\cordis.patch.yml` 第 455–457 行原文（源码摘录见 §6.1）：

> **Disabling rather than deleting is deliberate**: the base is shared, and a row absent from a surface overlay would silently reappear the day someone reorders the composition.

两层含义：

1. **base 是共享的**——别的形态还要用那些行，不能为 Web 形态把它们删掉。
2. **"删掉"是不可靠的**：缺失的行在将来组合顺序变化时会**悄悄回来**。而 `disabled: true` 是**显式的**、留在文件里、可审查、可被后面的层再改回去的。

两点补充（都来自本课的源码）：

- 第 1 点补充："缺失的行会回来"之所以成立，是因为**整棵树是叠出来的、没有原始内容**（`1.2` 的空根结论）；某层不写这一行，就意味着它对这一行**没有主张**。
- 第 2 点补充：能被"再改回去"也是真的——`1.3` 的覆盖规则允许后面的层写 `disabled: false`（§8.1 表里那一条 `false` 就是这种行）；而"删除"没有对应的反向操作。

（同一份文件里还有大量注释解释"哪一行为什么留在 host 平面、哪一行移进 preset"，那是第三编的内容。）

## 附录 A 关键问题与答案

> 用法：每题都给了**明确答案**，不留空。凡涉及**后续编**的题，题名后标了「⚠️ 第一次读请跳过」，理由写在答案里。

### Q1 `id` 与 `name` 的语义差别是什么？

**答案**：`id` 是**树内的逻辑身份**，用于一切寻址（patch 定位 / 插件管理器启停 / 热重载重放）；`name` 是**要加载什么**（包名，或包的子路径导出，如 `@deepseek-ai/dsh-web-app/startup`）。

- `insert` 的行：两者都必需。
- **覆盖行：只需 `id`，`name` 可选**；写了就作为**身份校验**——不一致时整条 patch 被跳过并告警（源码 5 第 115–118 行）。
- 出处：`vendor\include\src\index.ts` 第 76–127 行；实例 `packages\bundle\web-app\cordis.patch.yml` 第 465–472 行（覆盖行不写 `name`）。

### Q2 为什么 `id` 必须稳定？

**答案**：因为它是 patch、插件管理器、热重载**共用的寻址键**。

- 改 `id`（或把行搬到别的 bundle）→ 下游 patch 全部失配，但**只得到一条 `patch: entry xxx not found` 警告，不中断** ⇒ **静默失败**：树能起来，效果没了。真实事故见 `docs\upgrade-guide\v0.1.7-rc.2\schedule-optional-bundle\guide.zh.md` 第 16 行。
- 重复 `id` → 加载器**不拒绝**（`EntryTree.ensureId` 只在自动生成 id 时查撞车；`entryMap.set` 后写覆盖先写）。后果有三层：① 靠前那条**永远 patch 不到**（§7.5 实测）；② 插件管理器把它标成 `unaddressable`，拒绝通过界面改它（`packages\boot\plugin-manager\src\index.ts` 第 252–272 行）；③ 某些**服务自己的注册表会直接拒绝**重复 id（`packages\extensions\tool-cordis\src\host.ts` 第 9–18 行）。
- 把 `id` 当**稳定契约**对待，是这一切的结论。

### Q3 `disabled` 为什么允许写成表达式？

**答案**：为了让**同一个 bundle 复用到多种产品形态**：用平台条件、服务存在性、profile 名来决定某一行是否启用，避免为每种形态复制一份 patch。

- `disabled` 是**唯一**允许写 `!!js` 的元数据字段（`id` / `name` / `group` / `inject` / `intercept` / `isolate` 必须静态），仓库有一道门禁脚本在查这件事：`scripts\verify-cordis-config.ts` 第 41、508–539 行。
- 它在**每次挂载决策**时于 loader 上下文里求值（`vendor\loader\src\config\entry.ts` 第 91–95 行），所以表达式能看到"此刻"的服务；相关服务是靠 `inject` 就绪后才求值的（`docs\cordis-primer.zh.md` 第 45 行、《web-app》patch 第 8–11 行）。
- **副作用**：`--dump-config` **不求值**，原样打印（`1.2` 已验证）；因此 dump 出来仍是一份可加载的 YAML。
- 代价与历史教训：表达式写错位置**不会报错**，只会静默成为真值——见 `docs\postmortem\0002`（§8.4）。

### Q4 bundle 的 patch 只能是一个文件吗？

**答案**：不是。`dsh.bundle.patch` 可以是**有序文件列表**，那些文件按列表顺序拼成**该 bundle 的那一层**。

- 实例：`dsh-web-app` 声明了 **5 个**（主 patch + `presets/` 下 4 个 preset 声明），见 `packages\bundle\web-app\package.json` 第 42–52 行。
- 对照：`dsh-base` 用的是字符串形式，只贡献 1 层（`packages\bundle\base\package.json` 第 31–35 行）。
- 校验与解析：`bundlePatchFiles` / `bundlePatchPaths`（源码 1）。

### Q5 为什么用 `disabled: true` 而不是把行删掉？

**答案**：因为 **base 是共享的**，且"删除"会在组合顺序变化时让该行**悄悄复现**；禁用是**显式且可审查**的，还能被后面的层再改回来（写 `disabled: false`）。

- 出处：`packages\bundle\web-app\cordis.patch.yml` 第 455–457 行原文（§9）。

### Q6 同一个 `id` 被两层都写到，谁生效？

**答案**：**后出现的那一层**——因为所有层被**拍平成一份有序列表**、交给**同一次** `applyEntryPatches` 调用（`packages\boot\app-boot\src\profile.ts` 第 800–815 行），而循环是顺序处理的，每条覆盖都是 `target[key] = value`。

- 实测：`tool-bash` 在 base 里是 `disabled: !!js process.platform === 'win32'`，在 web-app 里是 `disabled: true`，最终结果是 `disabled: true`，**base 那句表达式整句消失**（§6.2）。
- 注意：覆盖是**整键替换**，不是深合并。

### Q7 一个 patch 打不到目标时会怎样？

**答案**：**警告 + 跳过那一条 + 继续处理后面的**，绝不中断启动。

- 三种情形的告警原文（`vendor\include\src\index.ts` 第 82–117 行）：
  - `patch insert: entry %C not found`（`insert` 带 `id`，目标不存在）
  - `patch insert: entry %C is not a group`（`insert` 带 `id`，目标不是 group）
  - `patch: entry %C not found`（普通覆盖，目标不存在）
  - `patch: id is required for non-insert patches`（普通覆盖漏写 `id`）
  - `patch: name mismatch for %C (expected %C, got %C), skipping`（`name` 不符）
- `%C` 由调用方替换成 JSON 引用后的值（`packages\boot\app-boot\src\profile.ts` 第 811–814 行）；实测输出见 §7.5。

### Q8 `!!js` 表达式能写在哪些字段上？ ⚠️ 第一次读请跳过

**跳过理由**：完整规则属 `2.6`（配置与组合）与 `2.2`（注入）。

**答案**：只有两处——条目（或 patch 行）的 **`config` 内部**，以及 **`disabled` 字段本身**。

- `disabled` 的表达式节点必须是**它本身**；嵌在 `disabled` 下面的表达式不会被求值（`scripts\verify-cordis-config.ts` 第 525–536 行）。
- 其余元数据（`id` / `name` / `group` / `inject` / `intercept` / `isolate`）必须保持静态；写在那里**不会报错**，只会留成真值数据（`docs\cordis-primer.zh.md` 第 45 行、`docs\cordis-tutorial\05-config.zh.md` 第 107 行）。需要"按环境选插件"时，文档的答案是**用 overlay**，不是写表达式。

### Q9 `config.plugins` 里的 `id` 也是条目吗？ ⚠️ 第一次读请跳过

**跳过理由**：agent preset 的语义属第三编。

**答案**：**不是。** 它们只是**配置数据**——preset 声明里那一行 `config.plugins` 数组的内容，**不能被 patch 按 `id` 寻址**。

- 判据在源码 3：只有 `entry.group && Array.isArray(entry.config)` 才会被递归登记进索引；`config.plugins` 既不是 `group`，`config` 也不是数组。
- 数字佐证：本课 §6.2 用到的 6 个 patch 文件里共 **323 次 `- id:` 写法**，而应用后树里只有 **185 个条目**（§6.3）。
- 例：`packages\bundle\web-app\presets\standard.patch.yml` 第 5–40 行 —— 条目是 `preset-standard`；它 `config.plugins` 里的 `persona`、`tool-bash` 等 `id` 是 preset 的内容。
