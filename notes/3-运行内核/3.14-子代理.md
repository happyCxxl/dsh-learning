## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：把「委派」这条链讲死——**谁提供能力、子级住在哪、上下文隔离到什么程度、结果从哪条路回来、父子关系记在哪些字段里**。
**不是**：agent loop 内部的轮次排序（那是 3.5 与 3.6）、工具注册表与 schema（3.9）、会话持久化格式（3.1 / 3.13）、scope / preset 的注册原语（第二编 2.5）。本课只用到它们的**对外表现**。

### 0.2 现在只要记住这 5 件事

1. **委派是一个可选的能力接缝（seam），不是一个工具。** 与 bash 一样它不属于 agent loop；但与 bash 不同：**同一上下文可以并存多个提供方实现**，按名字注册在 `ctx.subagents` 上，跟 LLM 适配器注册表同构，而 bash 只允许一个执行器。
2. **一个服务 + 六个后端 + 两个面向模型的 Consumer。** Service Definition 是 `dsh-subagent`；后端兄弟包为 `spawn`、`fork`、`acp`、`codex`、`claude-code`、`dsh-sdk`；Consumer 是 `dsh-tool-subagent`（按提供方委派）与 `dsh-tool-subagent-control`（`send_message` / `interrupt_agent` / `list_agents`）。
3. **子代理天生就有独立上下文，因为每个子代理就是一条独立 Session。** 进程内子代理是一个全新的 `Agent`，拥有自己的会话、自己的系统提示词和全新的扁平作用域；父级的工具限制与权限**绝不**被导入。
4. **回传有两条完全不同的路。** 一次性 run：父级 await `run.result`，只拿到子级最终输出。可继续子级：没有 run、没有 Task，运行时不问自答地向父级投递一条「结算通知」，模型自己写的消息走 `send_message()`。
5. **lineage 是数据，不是权限，也不是可见性。** 它由 `parentSession`（持久）、`delegationDepth`（持久）、`subagentDepth`（运行时）三个字段构成；**从不影响可见性**，带作用域的注册也不会向下继承给 subagent。

### 0.3 明确授权：这些现在不用管

- **进程外四个后端（`acp` / `codex` / `claude-code` / `dsh-sdk`）的内部协议**——本课只讲它们**对外广告的能力**与拒绝时机，传输细节属 4.7；
- **可继续子级的冷恢复、容量池（`maxActiveSubagents`）、所有权图**——本课提到它们存在的理由与关键结论，机制细节属 3.15 与本包的实现章节；
- **`subagentModelSelection`（子级 LLM 路由选择）**——本课只在工具 schema 一处顺带点到，它的设置投影属于配置类主题。

## 1. 最小词汇表（本课新增的 8 个词）

沿用 1.1 已定义的词：`ctx`（插件共享的登记处）、**service**（登记处里一项有名字的能力，用 `ctx.<键>` 取用）、`session`（一次完整对话的真源，只追加）、`turn`（轮次）、`step`（步骤）、**工具**（模型可调用的动作）。下面 8 个词是本课新增的。

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **subagent 子代理** | 被另一个 agent 叫去干活的**另一个 agent**；它不是「一次函数调用」，而是一整条自己的会话 | 一个新的 `Agent` + 一条新 `Session` |
| **委派（delegate）** | 父级把一件自足的任务交出去，只等结果、不等中间过程 | `subagent` 工具；`ctx.subagents.start(...)` |
| **提供方 / 后端（provider）** | 「子代理住在哪、怎么跑」的一种实现，按名字注册，可选多个 | `ctx.subagents.registerProvider(new SpawnInProcessProvider('spawn'))` |
| **一次性（one-shot）** | 跑一次、出一个结果、结束；**没有**可再对话的句柄 | `SubagentRun`（`result` + `dispose`） |
| **可继续（continuable）** | 子级**持久存在**，可以按顺序再收多条消息、跑多个轮次 | `prepareContinuable`；`startContinuable()` |
| **Activation（激活）** | 一个可继续子级**当前「活着」的那一段**；子级会话可以持久存在，而它只在该子级驻留时有对应的 Activation | `Activation`；由「继续执行管理器」持有 |
| **delegation depth 委派深度** | 递归预算：顶层为 0，子级 = 父级 + 1；用来防止无限层层下派 | `SessionHeader.delegationDepth`、`AgentOptions.subagentDepth` |
| **lineage 谱系** | 以数据形式携带的父子关系事实；**只描述关系，不授予权限、不改变可见性** | `parentSession` / `delegationDepth` / `subagentDepth` |

> ⚠️ `Activation` 的完整生命周期、`lineage` 与 scope 的边界属第三编后续课与第二编，本课只用到上表这个程度。

## 2. 先建立画面

### 2.1 谁是谁的一部分（静态结构）

```
插件树（每个条目 ⇒ 一个被加载的插件）
└─ ctx.subagents  ← Service Definition：dsh-subagent 的 SubagentRuntime
   │                （只挂服务不改变任何行为：没有提供方和工具时什么都不能委派）
   ├─ 提供方注册表：按名字注册，可并存多个
   │   ├─ spawn        进程内，全新子 Agent（继承父级对话：否）
   │   ├─ fork         进程内，以父级已完成轮次前缀为初始内容（继承父级对话：是）
   │   ├─ acp          进程外（继承父子对话：否）
   │   ├─ codex        进程外（继承父子对话：否）
   │   ├─ claude-code  进程外（继承父子对话：否）
   │   └─ dsh-sdk      进程外，另一 Harness 运行时（继承父子对话：否）
   │        └─ 共用库：subagent-in-process-driver（不是第七个后端，组合里没人配置它）
   └─ Consumer（面向模型的工具，注册到 ctx.tools）
       ├─ dsh-tool-subagent          subagent（按提供方委派）
       └─ dsh-tool-subagent-control  send_message / interrupt_agent / list_agents
```

**精确性说明**：图中「继承父级对话」是提供方的一个**描述性**字段，不是服务校验的启动能力；它只影响工具**对模型的措辞**，不说明工具注册、注入服务或权限继承（`packages/subagent/subagent/src/types.ts` 第 349–354 行）。

### 2.2 一次委派发生了什么（动态过程）

```
父 agent 的某个 step 里，模型调用工具 subagent

  ①工具层：校验入参 → 组装 SubagentStartRequest → `ctx.subagents.start(provideName, request)`
        │
  ②服务层：按名字取提供方 → 检查能力 flag（缺能力 = 当场抛 UNSUPPORTED_CAPABILITY）
        │        → 快照一个 descriptor（持久描述符）
        │
  ③提供方：进程内 = driver 造一条全新 Session + 新 Agent（必要时先注入 fork 种子）
        │       进程外 = 起子进程 / 另一个运行时
        │
  ④投递初始提示词 → 子级自己跑 turn/step（父级看不到中间过程）
        │
  ⑤结算：
        ├─ 一次性前台：run.result → 变成**工具结果**（父级下一个 step 就能看到）
        ├─ 一次性后台：注册一个归父级所有的 Task → await 用 job_output 取
        └─ 可继续：没有返回值；Activation 结束时**运行时**投递一条结算通知给父级
```

**精确性说明**：图里把「父级看到结果」画成一个点，实际上它总是**追加进父级自己的会话事件**（工具结果或用户消息）之后才被模型看到；可继续路径的结算通知是一条 **user 消息**，与工具结果不是同一类事实。

### 2.3 大白话版：委派一次，机器里发生了什么

**完全不用上面的术语**，先建立画面（来源：`docs/subsystems/subagent.zh.md` 第 5、136、202 行，以及 `packages/subagent/subagent-in-process-driver/src/index.ts` 第 104–152 行的执行顺序；这里只做白话转述）。

1. 模型说「我要委派一个任务」，并附上任务描述和一段完整指令。
2. 工具插件拿到这句话，先做一些把关：这个提供方能不能满足我要的深度限制 / 输出结构 / 工具集 / 人设？不能就**当场报错**，而不是接下了再忽略。
3. 工具插件把请求交给服务；服务按名字找到那个「子代理住在哪」的实现。
4. 如果是**同进程**的实现：造一条全新的会话记录，造一个全新的 agent，把父级的 cwd、谱系、深度、权限快照写进去。此刻父级**第一次**看到「有这么个孩子」这件事——它会往自己日志里追加一条目录事实。
5. 子级开始跑自己的轮次：自己的提示词、自己的工具表、自己的事件日志。父级的对话内容（除 fork 外）不进去。
6. 子级结束。**一次性**的情况下，它最后的输出变成父级那次工具调用的结果，父级继续跑。**可继续**的情况下，工具调用早就返回了（只给了个 id），子级结束时由运行时主动往父级邮箱投一条「它结束了」的通知。
7. 不管哪条路，父级的输入里最终只会多出「结果 + 一点记账」，子级的中间过程一步都不会进来。

## 3. 结论先行（每条都指得出源码）

1. **委派是一个可选能力 seam，不是一个工具。** 与 bash 一样，它不属于 agent loop，所以类型定义在 subagent 子系统里而不是 core 里；但它与 bash 不同：**同一上下文可以并存多个提供方实现**，按名称注册在 `ctx.subagents` 上，跟 LLM 适配器注册表同构，而 bash 只允许一个执行器（`docs/subsystems/subagent.zh.md` 第 5 行）。
2. **一个服务 + 六个后端 + 两个面向模型的 Consumer。** Service Definition 是 `dsh-subagent`；后端兄弟包为 `spawn`、`fork`、`acp`、`codex`、`claude-code`、`dsh-sdk`；Consumer 是 `dsh-tool-subagent`（按提供方委派）与 `dsh-tool-subagent-control`（`send_message`／`interrupt_agent`／`list_agents`）（`docs/subsystems/subagent.zh.md` 第 7 行；`packages/subagent/README.zh.md` 第 25-36 行）。
3. **子代理天生就有独立上下文，因为每个子代理就是一条独立 Session。** 进程内子代理是一个全新的 `Agent`，拥有自己的会话、自己的系统提示词和全新的扁平作用域；父级的工具限制与权限**绝不**被导入（`packages/subagent/subagent-spawn-in-process/README.zh.md` 第 12、82 行）。
4. **回传有两条完全不同的路。** 一次性 run：父级 await `run.result`，只拿到子级最终输出（`packages/subagent/tool-subagent/src/index.ts` 第 208-238 行）。可继续子级：没有 run、没有 Task，运行时不问自答地向父级投递一条「结算通知」，模型自己写的消息走 `send_message()`（`packages/subagent/subagent/src/continuation-activation.ts` 第 871-888 行）。
5. **lineage 是数据，不是权限，也不是可见性。** glossary 原文：lineage 是「以数据形式携带的父子关系事实（`parentSession`、持久的 `delegationDepth`、运行时 `subagentDepth`）；从不影响可见性」（`docs/glossary.zh.md` 第 21 行）。带作用域的注册不会向下继承给 subagent，子树行为一律通过 lineage 数据表达（`docs/glossary.zh.md` 第 13 行）。

**源码 A：`ctx.subagents` 这个键是怎么来的** —— `packages/subagent/subagent/src/index.ts` 第 197–224 行

```ts
/** Named provider registry with one-shot runs, durable discovery, and continuable-child operations. */
export class SubagentRuntime extends TypertRemoteService {           // ← class 头：它提供的正是 ctx.subagents
  static Config = z.object({
    maxDepth: z.number().step(1).min(0).max(Number.MAX_SAFE_INTEGER).default(1).volatile(),
    maxActiveSubagents: z.number().step(1).min(1).max(Number.MAX_SAFE_INTEGER).default(8).volatile(),
  })
  private providers = new Map<string, SubagentProvider>()            // ← 键 = 提供方名字，值 = 后端实例
  private continuations: SubagentContinuationManager | undefined
  /**
   * The contained lifecycle-edge publisher. Built here because scoped dispatch
   * keys its carrier by this exact service instance, whose own context filter
   * composes into the carrier.
   */
  private readonly emitLifecycle: LifecycleEmitter

  constructor(ctx: Context, private config: Config) {
    super(ctx, 'subagents')                                          // ← 这一句决定了它的 ctx 键叫 subagents
    this.emitLifecycle = createLifecycleEmitter(this.ctx, parent => scopeTarget(this, parent))
    ctx.inject(['agents'], (childCtx: Context) => {
      const manager = new SubagentContinuationManager(childCtx, {
        prepareContinuable: (name, request) => this.prepareContinuable(name, request),
        observeActivation: (provider, childId, parent) => this.observeActivation(provider, childId, parent),
      }, () => this.config.maxActiveSubagents.get())
      this.continuations = manager
      childCtx.effect(() => () => {
        /* v8 ignore else -- one injected binding owns the slot until its fiber disposes. */
        if (this.continuations === manager) this.continuations = undefined
      }, 'subagents.continuationBinding()')
      // …（第 225 行起：把服务自身的远程方法与后续注入登记完，与本知识点无关，此处省略）
    })
  }
}
// （第 183–191 行的 BrowserPromptSource 接口与第 189–195 行的 Config 接口已省略：后者的两个字段
//  已单独摘出如上，前者与本知识点无关。第 225–660 行是类体其余方法与私有助手，本块不需要，故省略。）
```

按块讲解：

- **`super(ctx, 'subagents')`**：`ctx.subagents` 这个名字**不是文档起的，是代码里写死的字符串**（与 1.1 §6 里 `ctx.sessions` 的来源完全同构）。想知道某个 `ctx.<键>` 谁提供，就搜这个字符串。
- **`providers = new Map<string, SubagentProvider>()`**：键是**提供方名字**、值是后端实例。这就是「同一上下文可并存多个实现、按名字注册」的落点——换成 bash 那种单执行器就写不出这个 `Map`。
- **两个 `Volatile` 配置的默认值**：`maxDepth` 默认 `1`（顶层默认只允许一层委派）、`maxActiveSubagents` 默认 `8`（同时驻留的可继续子级上限）。`Volatile` 表示这两个值可以**在运行中变**，下一次委派重新读取（`packages/subagent/subagent/README.zh.md` 第 47、51–53 行）。
- **`ctx.inject(['agents'], …)`**：可继续子级的编排需要 `ctx.agents`，所以管理器在**注入建立后**才被创建；`childCtx.effect(...)` 保证这条绑定随 fiber 一起撤销。属第二编的依赖注入，此处只记它解释了「服务为什么能顺手管住可继续子级」。
- **`extends TypertRemoteService`**：与 1.1 里 `SessionStore extends Service` 同类——一个包要贡献一项具名能力，就继承一个服务基类并 `super(ctx, '<键>')`。

### 4.2 启动时能力：缺能力就当场拒绝

```ts
/**
 * Which START-TIME features a provider supports. Checked by the service before delegating to
 * {@link SubagentProvider.start}: a request that needs a capability the chosen provider lacks
 * is rejected with a typed error rather than accepted-then-ignored (the "fail loud, no silent
 * degradation" rule). These flags describe the ONE-SHOT
 * {@link SubagentProvider.start} path, where the provider composes the child;
 * continuable children are composed by the continuation manager itself and are
 * gated by {@link SubagentProvider.prepareContinuable} instead. Each flag
 * corresponds one-to-one to a {@link SubagentStartRequest} option: `depthLimit`
 * to `maxDepth`; the other names match.
 */
export interface SubagentCapabilities {
  readonly agentOptions: boolean      // ← 对应 SubagentStartRequest.agentOptions
  readonly outputSchema: boolean      // ← 对应 SubagentStartRequest.outputSchema
  readonly depthLimit: boolean        // ← 对应 SubagentStartRequest.maxDepth（名字故意不同）
  readonly toolFilter: boolean        // ← 对应 SubagentStartRequest.toolFilter
  readonly persona: boolean           // ← 对应 SubagentStartRequest.persona
}
```

```ts
  private assertCapabilities(provider: SubagentProvider, request: SubagentStartRequest): void {
    const needs: { when: boolean; cap: keyof SubagentCapabilities }[] = [   // ← 请求里的字段 → 需要的 flag
```

- **反向证据（进程外后端为什么全 `false`）**：`packages/subagent/subagent/src/out-of-process.ts` 第 51–63 行定义的 `NO_START_CAPABILITIES` 五个 flag 全 `false`，注释原文是 *"A child in another process cannot honor parent-enforced start features (`agentOptions`/`outputSchema`/`maxDepth`/`toolFilter`/`persona`), so the service rejects a request needing any of them before `start` runs — never accepted-then-ignored."*

### 4.3 两类子级形态

- **一次性（one-shot）**：`SubagentRun` 是一次可 dispose 的前台委派，只有一个结果，**绝不是**持久化子 agent 句柄；发布后的提示词提交、轮次工作与基础设施故障都归 `result`。
- **可继续（continuable）**：一份持久化子会话，至多关联一个进程内 **Activation**（被重建的子 Agent 处于驻留状态的时段）；它可执行多个 FIFO 轮次，且在其创建的后代仍在运行期间保持驻留。

```text
persisted Session
  -> optional live Activation
       -> one retained AgentHandle
       -> Agent inbox as the only turn FIFO
       -> zero or more owned child Activations
```
（`docs/subsystems/subagent.zh.md` 第 126–134 行）

可继续路径**不会**创建 Task，也没有承载中间结果的包装层（`docs/subsystems/subagent.zh.md` 第 126 行）。

**源码 E：一次性 run 的接口本体（注意它没有的东西）** —— `packages/subagent/subagent/src/types.ts` 第 299–334 行

```ts
/**
 * ONE-SHOT child handle returned after publication. Prompt submission, turn
 * work, and infrastructure faults after that boundary belong to {@link result}.
 * Consumers await that result and must always {@link dispose} to cancel
 * remaining work and reach quiescence. A run is one disposable foreground
 * delegation with one result; continuable conversations have no run — the
 * continuation manager holds their `AgentHandle` directly and orders every
 * turn through the child's own inbox.
 */
export interface SubagentRun {
  /**
   * Parent-scoped run id. For a local run, this MUST equal the published child
   * session id, whose `parentSession` records `request.parent.session.id`; a
   * remote provider mints an id unique in the parent namespace.
   */
  readonly id: SessionId
  /**
   * The exact published in-process child, or `undefined` for a remote run.
   */
  readonly localAgent: Agent | undefined
  /**
   * Resolves with the child's terminal {@link SubagentResult} when the run
   * settles. Does NOT reject on a child-level failure — a model/transport
   * failure resolves with `stopReason: 'error'` so the consumer maps it to an
   * `isError` tool result. Rejects on an infrastructure fault the seam cannot
   * represent as a stop reason.
   */
  readonly result: Promise<SubagentResult>
  /**
   * Cancel remaining work, reach child quiescence, and release resources.
   * Idempotent.
   */
  dispose(): Promise<void>
}
// （第 315–319 行 JSDoc 的后半句 “When present, its id is {@link id}; the provider retains no
//   ownership implication beyond the run's ordinary {@link dispose} contract.” 被删；
//   第 329–333 行 dispose 的注释保留。成员一个都没删。）
```

按块讲解：

- **`result` 的行为是整个 seam 最容易被记错的一条**：**子级失败不 reject**——模型/传输失败会以 `stopReason: 'error'` **resolve**，好让 Consumer 把它映射成一条 `isError` 的工具结果；只有「seam 无法用 stop reason 表示的基础设施故障」才 reject。这条注释解释了为什么工具层要写 `stopStatusError` 那种映射函数（源码 L）。
- **`localAgent` 可为 `undefined`**：进程外运行没有本地子 Agent。工具层用它判断「这条 run 有没有本地子会话可以登记进目录」（服务调用点 `packages/subagent/subagent/src/index.ts` 第 569–570 行）。
- **`dispose()` 的注释末尾是 `Idempotent`**：重复 dispose 是安全的——这正是源码 K 里 `finally` 块能无条件回收的原因。
- **接口里没有 `steer` / `resume` / `sendMessage`**：这就是「一次性不是持久句柄」的类型级证据（`packages/subagent/subagent-spawn-in-process/tests/subagent-spawn-in-process.spec.ts` 第 221 行有一条测试专门断言这一点）。

### 4.4 进程内子级是怎么被造出来的

驱动器 `startInProcessRun` 的顺序（`packages/subagent/subagent-in-process-driver/src/index.ts` 第 104–152 行）：

1. 校验 `maxDepth`，父级已中止则直接抛「publication 之前中止」（第 108–109 行）；
2. `resolveChildDepth(parent, maxDepth)` 推导子级深度（第 111 行）；
3. 铸一个新 `SessionId`，`seed` 决定其长度即 **activation boundary**（第 113–115 行）；
4. **在首个 await 之前**捕获委派权限快照——「之后父级切换权限属于父级的未来」（第 117–119 行）；
5. `parent.ctx.agents.create({ sessionId, parentAgent, meta, seed, agentOptions, signal, setup })`，在未发布的 setup 窗口内追加密钥策略、组合 persona／工具过滤、安装结构化输出运行时、挂描述符（第 122–143 行）；
6. `drivePublishedRun` 提交提示词、等 `whenIdle()`、读结果、暴露 `dispose()`（第 158–209 行）。

`setup` 窗口里做的事由 `applyChildComposition` 统一负责：先 join 父级的 preset，再注册固定的委派范围声明，最后才是子级自己的 persona 与工具限制——「创建与冷恢复都经过这里」。同一函数里那条模型可见的声明就是本会话 system-reminder 里那条「You are a delegated subagent…」。

**源码 F：整段创建流程** —— `packages/subagent/subagent-in-process-driver/src/index.ts` 第 93–152 行

```ts
/**
 * Establish and drive one in-process one-shot child. Fulfillment means the agent
 * is already published in the registry and transfers its turn, cancellation,
 * and disposal work through the returned run. Rejection means the agent
 * factory's unpublished creation transaction reached quiescence without
 * publishing a child. Every start appends its resolved descriptor inside the
 * child's initial turn.
 * @param request - the trusted typed start request, including its required signal.
 * @param options - the optional fork seed.
 * @returns a published holder-owned run.
 */
export async function startInProcessRun(
  request: ResolvedSubagentStartRequest,
  options: InProcessRunOptions,
): Promise<SubagentRun> {
  assertSubagentMaxDepth(request.maxDepth)          // ① 先校验上限形状（非负安全整数）
  if (request.signal.aborted) throw prePublicationAbort()   // ② 守卫：已经中止就不开工
  const parent = request.parent
  const childDepth = resolveChildDepth(parent, request.maxDepth)   // ③ 深度 = 父级 + 1，并查上限

  const childId = brandString<SessionId>(randomUUID())   // ④ 铸新 SessionId（全新的会话身份）
  const seed = options.seed
  const activationBoundary = SessionLogOffset(seed?.length ?? 0)   // ⑤ seed 长度 = 子级自有事件的起点

  // Capture before the first await: a later parent switch belongs to the
  // parent's future.
  const inherited = captureDelegatedPolicyOverrides(parent)   // ⑥ 同步捕获权限快照，必须在任何 await 之前

  let structured: StructuredAttachment | undefined
  const setup = (childCtx: Context, child: Agent): void => {    // ⑦ 未发布窗口里的注册回调
    appendDelegatedPolicyOverrides(child.session, inherited)
    applyChildComposition(childCtx, parent, {
      persona: request.persona,
      toolFilter: request.toolFilter,
    })
    if (request.outputSchema !== undefined) {
      structured = attachStructuredRuntime(childCtx, request.outputSchema)
    }
    attachDescriptorAppend(childCtx, request.descriptor)       // ⑧ 在子级首个 step 前追加描述符
  }

  const handle = await parent.ctx.agents.create({               // ⑨ 真正造子 Agent：事务在这里提交
    sessionId: childId,
    parentAgent: parent,
    meta: childSessionMeta(parent, childDepth, seed !== undefined),
    ...seed !== undefined ? { seed } : {},
    ...seed === undefined ? {} : { inheritedEventCount: activationBoundary },
    agentOptions: resolveChildAgentOptions(parent, request.agentOptions, childDepth),
    signal: request.signal,
    setup,
  })
  return drivePublishedRun(                              // ⑩ 发布之后才进入「驱动 + 结算」
    handle,
    request.signal,
    request.prompt,
    childId,
    activationBoundary,
    structured,
  )
}
// （本块为 39 行，略超粒度上限：它把「校验 → 造 id → 捕获权限 → setup → create → 驱动」
//  六步连成一条不可分割的顺序，任何一刀都会让「inherited 为什么必须在 await 之前」失去上下文。
//  未删任何行；第 93–103 行的 JSDoc 完整保留。）
```

按块讲解：

- **`request` / `options` 从哪来**：`request` 是服务校验能力后交下来的 `ResolvedSubagentStartRequest`（多一个 `descriptor`）；`options` 只有 `seed` 一项——spawn 传 `{}`（源码 P 第 58 行），fork 传 `{ seed }`（源码 Q 第 77–82 行）。**两个后端在这里分叉，且分叉是数据而不是分支。**
- **①②③ 三道前置守卫**：`assertSubagentMaxDepth`（形状）、`signal.aborted`（时机）、`resolveChildDepth`（预算）。任何一个不通过都**没有**创建过一条会话——这是「拒绝 = 未发布资源已清理」的类型级基础。
- **⑤ `activationBoundary` 的用途**：把「fork 继承来的 seed」与「子级自己写下的事件」在日志上切开。源码块 N 读结果时就从这条边界之后读，所以 **fork 的 seed 不会被误当子级输出**。
- **⑥ 为什么必须同步捕获**：注释原文 *"Capture before the first await: a later parent switch belongs to the parent's future."*——父级在 `await` 期间改了权限，那是父级的未来，不属于这个孩子。这条注释的「为什么」还写在 `captureDelegatedPolicyOverrides` 的 JSDoc 里（`packages/subagent/subagent/src/child-agent.ts` 第 238–248 行）。
- **⑨ `meta` 里的三件事一次写清**：`childSessionMeta(parent, childDepth, seed !== undefined)` 写「父级 cwd、父级 preset、`parentSession`、`isSeeded`、`origin: 'subagent'`、`delegationDepth`」；`seed` 与 `inheritedEventCount` 只在 fork 时出现；`agentOptions` 走 `resolveChildAgentOptions` 把 `subagentDepth: childDepth` 盖上去。
- **⑩ 发布之后**：`drivePublishedRun` 才提交提示词并等 `whenIdle()`——也就是「创建事务」与「驱动一个轮次」被显式分成两段，因为前者的失败意味着**没有**孩子，后者的失败意味着**有**孩子但轮次出了问题。

**源码 G：子会话的持久元数据从哪几行写出来的** —— `packages/subagent/subagent/src/child-agent.ts` 第 122–157 行

```ts
/**
 * Build the child session's durable creation metadata: the parent's workspace,
 * its direct lineage, coarse product origin, the recursion budget that must
 * survive persistence, the seed boundary that separates inherited parent
 * history from child work, and the composition the child runs under.
 *
 * The preset is read from the parent's LIVE scope chain rather than from its
 * header, because a parent that switched preset while blank runs on the newer
 * composition and its header still names the older one. Recording it is what
 * makes a child's history reconstructable: without it a cold read of the child
 * resolves the deployment default and rebuilds turns under a tool set the
 * child never had.
 * @param parent - the delegating parent agent.
 * @param childDepth - the resolved delegation depth to persist.
 * @param isSeeded - whether this child inherits a parent-log prefix, including an explicitly empty one.
 * @returns the `meta` for `ctx.agents.create()`.
 */
export function childSessionMeta(
  parent: Agent,
  childDepth: number,
  isSeeded: boolean,
): NonNullable<CreateAgentOptions['meta']> {
  const parentHeader = parent.session.header               // ← 父级的持久 header：cwd / id 从这里来
  const agentPreset = parent.ctx.get('agentPresets')?.composedPreset(parent.ctx)   // ← 活作用域链，不是 header
  return {
    ...parentHeader.cwd !== undefined ? { cwd: parentHeader.cwd } : {},
    ...agentPreset === undefined ? {} : { agentPreset },
    parentSession: parentHeader.id,                        // ← headline：#1 的直接父子事实
    isSeeded,
    // Navigation classification only; the descriptor remains the authority
    // for mode and continuation capability.
    origin: 'subagent',
    // Durable: the recursion budget must survive persistence and resume.
    delegationDepth: childDepth,
  }
}
// （本块无省略：第 122–157 行整段照录，是一份完整函数。）
```

按块讲解：

- **`parent` / `childDepth` / `isSeeded` 从哪来**：`parent` 是请求里的父 Agent，`childDepth` 由 `resolveChildDepth` 算出（源码 F ③），`isSeeded` 由调用点写成 `seed !== undefined`（源码 F ⑨）——**注意「传了空 seed」和「没传 seed」在这是两种不同的事实**，所以判断用 `!== undefined` 而不是 `.length > 0`。
- **`origin: 'subagent'` 的注释是关键限定**：它只是「导航分类」，**可继续能力的权威是 descriptor 而不是它**。所以看到 `origin: 'subagent'` 不能推断这个孩子还能继续对话。
- **`delegationDepth: childDepth` 的注释给了持久化的理由**：`Durable: the recursion budget must survive persistence and resume`——纯运行时的深度会在冷恢复后把子级重置回顶层（与源码 I 的 `Math.max` 互为因果）。
- **`agentPreset` 为什么读活作用域而不读 header**：JSDoc 原文说明「父级可以在空转期间换 preset，此时 header 还记着旧的那个」；写下真实 preset 才能让子级历史在冷读时可重建。
- **`parentSession` 的一行就是 lineage 的主键**：它同时也是鉴权输入（见附录 A ④），所以它不能只被理解成「显示用的父子关系」。

**源码 H：setup 窗口里做的四件事** —— `packages/subagent/subagent/src/child-agent.ts` 第 167–219 行

```ts
/**
 * Model-facing delegation-scope statement for every in-process child. A
 * runtime-context contribution rather than a system-prompt section, so the
 * deployment's system prompt stays uniform across parents and children.
 */
export const SUBAGENT_DELEGATION_CONTEXT
  = 'You are a delegated subagent: your permission scope was fixed when you were started and cannot be '
    + 'widened from inside this session — operations that require approval are rejected automatically. '
    + 'When the task needs access beyond that scope, do not retry the denied operation; state the '
    + 'limitation in your reply so the delegating agent can handle it.'

/**
 * Compose one child inside its creation window: join its parent's preset,
 * register the fixed delegation-scope statement, then apply the child's own
 * shadowing persona section and tool restriction, all owned by the child's
 * scope and therefore invisible to its parent and siblings. Creation and cold
 * resume both pass through here.
 *
 * The join comes first and the child's own registrations second, which is the
 * order the layering already implies — the nearest scope wins a name, and a
 * per-child restriction intersects with everything its chain admits — but
 * stating it here keeps the two steps from being read as independent.
 */
export function applyChildComposition(
  childCtx: Context,
  parent: Agent,
  composition: ChildComposition,
): void {
  childCtx.get('agentPresets')?.composeFrom(childCtx, parent.ctx)   // ① 先 join 父级 preset
  childCtx.systemPrompt.context({                                   // ② 固定范围声明（模型可见）
    name: 'subagent:delegation',
    order: childCtx.systemPrompt.getContextOrder('SUBAGENT_DELEGATION'),
    text: SUBAGENT_DELEGATION_CONTEXT,
  })
  if (composition.persona !== undefined) {                          // ③ 子级 persona（遮蔽部署 persona）
    childCtx.systemPrompt.section({
      name: 'deployment:persona-prefix',
      order: childCtx.systemPrompt.getSectionOrder('DEPLOYMENT_PERSONA_PREFIX'),
      text: composition.persona,
    })
  }
  if (composition.toolFilter !== undefined) childCtx.tools.restrict(composition.toolFilter)   // ④ 工具过滤
}
// （第 190–195 行 JSDoc 的后半段 “The join and the per-child registrations live in ONE call because a
//  child composed without the join is exactly the defect this function exists to prevent: with every
//  model-facing row on the agent plane, a child that joins no preset sees an empty tool registry and none
//  of its parent's prompt sections. Taking the parent as a parameter is what makes that omission
//  unrepresentable at the call sites.” 被删，只保留到 “independent.”；两行 @param 也删。
//  函数体一行未删。）
```

按块讲解：

- **`childCtx` / `parent` / `composition` 从哪来**：`childCtx` 与 `child` 是 `setup(childCtx, child)` 回调给的**未发布**子作用域；`parent` 是驱动器闭包里的父 Agent；`composition` 由驱动器从请求里取值（`{ persona: request.persona, toolFilter: request.toolFilter }`，源码 F ⑦）。
- **顺序是硬约束**：`composeFrom`（join 父 preset）在前、子级自己的两处注册在后。JSDoc 原文给了理由——*"the nearest scope wins a name, and a per-child restriction intersects with everything its chain admits"*。换句话说：**先有一份可继承的组合，再在这份组合上做收窄**；反过来写会得到一个「先收窄、后又被父级组合放开」的结果。
- **② 这条声明是「运行时上下文贡献」而不是系统提示词片段**：JSDoc 原文 *"A runtime-context contribution rather than a system-prompt section, so the deployment's system prompt stays uniform across parents and children."* 它正是委派子代理在 system-reminder 里看到的那段话---「你的权限范围在启动时已经固定，无法在本会话内扩大」。
- **③ 是 shadowing（遮蔽）而不是新增**：`deployment:persona-prefix` 这个名字与部署级 persona 同名，子作用域注册后**只对这个孩子**生效。
- **④ `tools.restrict` 的语义**：被过滤掉的工具**既不出现在提示词里，也拒绝执行**——与「这个工具不存在」无法区分（`docs/glossary.zh.md` 第 19 行）。这条与 1.1 附录 A 的 R2 说明是同一个原语，区别只在这里是**子级**作用域。
- **为什么集成在一个函数里**：JSDoc 被删的后半段说的就是「拆开写会漏掉 join，而漏 join 的孩子会看到空工具表」——**把父级做成参数，使这种遗漏在调用点无法表达**。

```ts
  interface AgentOptions {
    /** Delegation depth: zero for a top-level agent and parent depth + 1 for a child. */
    subagentDepth?: number
  }
}

/**
 * Read an agent's delegation depth, treating absence as top-level depth zero.
 * The persisted session header is authoritative and monotone: runtime
 * `AgentOptions.subagentDepth` may DEEPEN the count but can never lower it —
 * a resumed child arrives with fresh options, and counting it from zero would
 * let it delegate as if it were top-level.
 * @param agent - the agent whose header and options carry the depth.
 * @returns its non-negative safe-integer depth.
 * @throws if the runtime `AgentOptions.subagentDepth` is not a non-negative safe integer.
 */
export function delegationDepthOf(agent: Agent): number {
  const runtime = agent.options.subagentDepth                    // ← 运行时来源（可缺失）
  if (runtime !== undefined && (!Number.isSafeInteger(runtime) || runtime < 0 || Object.is(runtime, -0))) {
    throw new TypeError('agent subagentDepth must be a non-negative safe integer')   // ← 守卫：非法运行时值
  }
  // The header value was validated at the session boundary (creation and
  // persistence load both construct through the store).
  return Math.max(agent.session.header.delegationDepth ?? 0, runtime ?? 0)   // ← 存在的较大值权威
}
```

```ts
/** Thrown when starting a child would exceed the requested depth cap. */
export class SubagentDepthError extends Error {                    // ← 专用错误类型：调用方按类型分派
  constructor(public readonly attemptedDepth: number, public readonly maxDepth: number) {
    super(`subagent depth ${attemptedDepth} exceeds maxDepth ${maxDepth}`)
    this.name = 'SubagentDepthError'
  }
}

/**
 * Resolve the child's delegation depth from its parent and enforce an optional
 * cap. The persisted parent header is the monotone floor, so a resumed parent
 * cannot delegate as if it were top-level.
 * @param parent - the delegating parent agent.
 * @param maxDepth - optional absolute cap the resolved depth must not exceed.
 * @returns the child's non-negative safe-integer depth.
 * @throws {SubagentDepthError} when the resolved depth exceeds `maxDepth`.
 * @throws {RangeError} when the resolved depth leaves the safe-integer range.
 */
export function resolveChildDepth(parent: Agent, maxDepth: number | undefined): number {
  const childDepth = delegationDepthOf(parent) + 1                 // ① 子级 = 父级 + 1（父级读法见源码 I）
  if (!Number.isSafeInteger(childDepth)) {                         // ② 守卫：数值域
    throw new RangeError('subagent child depth exceeds the safe-integer range')
  }
  if (maxDepth !== undefined && childDepth > maxDepth) {           // ③ 守卫：请求上限
    throw new SubagentDepthError(childDepth, maxDepth)
  }
  return childDepth
}
```

### 4.6 结果回传的三条通道

**① 一次性前台**：`tool-subagent` 里 `settleForegroundRun(run)` await `run.result`，把每个非 `completed` 的 stop reason 映射为错误标题；工具输出 schema 是三选一的 `oneOf`：`background`／`continuable`／`foreground`。

**② 一次性后台**：注册一个归父级所有的普通 Task，`done` 通道由 `settleRun` 结算，模型拿到的是 `started background subagent job <id>`；`run-settlement.ts` 的模块注释明确：**只有一次性后台路径用 Jobs**。

**③ 可继续**：`startContinuable()` 在 inbox 接受初始提示词时就 resolve，既不等待也不收集结果。Activation 结算后由运行时投递通知，模型自己写的消息走 `send_message()`。

```ts
/**
 * Collect and release one foreground run without letting disposal replace an
 * independent result failure.
 */
async function settleForegroundRun(run: SubagentRun): Promise<ForegroundToolResult> {
  const [execution] = await Promise.allSettled([          // ① 先只 await 结果，把失败「装进」settled
    run.result.then((result): ForegroundToolResult => {
      const error = stopReasonError(result)               // ② 非 completed → 拿到一句人类可读标题（源码 L）
      if (error !== undefined) {
        // The registry converts this throw to isError; partial output is not
        // success, but the preserved partial answer still reaches the parent.
        throw new Error(withDiagnosticAndPartialText(error, result))   // ③ 抛出 = 工具结果标为出错
      }
      return {
        kind: 'foreground',
        runId: run.id,
        // Content blocks already cross durable JSON boundaries elsewhere;
        // the registry performs the authoritative lossless snapshot here.
        output: result.output as unknown as JsonValue[],
      }
    }),
  ])
  const [disposal] = await Promise.allSettled([Promise.resolve().then(() => run.dispose())])   // ④ 无论成败都释放
  if (execution.status === 'rejected') {
    if (disposal.status === 'rejected') {                 // ⑤ 两条通道都失败：两项原因都保留
      throw new AggregateError(
        [execution.reason, disposal.reason],
        `subagent run failed: ${String(execution.reason)}; dispose failed: ${String(disposal.reason)}`,
      )
    }
    throw execution.reason
  }
  if (disposal.status === 'rejected') throw disposal.reason
  return execution.value                                 // ⑥ 成功路径：回传子级最终输出
}
// （本块无省略：第 204–238 行整段照录，是一份完整函数。）
```

- **`run` 从哪来**：调用点是同文件第 563–567 行的前台分支——`const run: SubagentRun = await runtimeCtx.subagents.start(config.provider, { ...request, signal: exec.signal })`，紧接着 `return settleForegroundRun(run)`。也就是说**只有前台路径进这个函数**。

- **③ `throw` 的语义**：工具注册表把抛出翻译成 `isError` 的工具结果。注释原文承认 *"partial output is not success"*，但同时把保留的部分输出（`withDiagnosticAndPartialText`，第 184–196 行）一起带给父级。

```ts
/**
 * Map a child result to the task outcome: completed carries final text, local
 * cancellation (`aborted` without a diagnostic) is killed, and provider-
 * diagnosed remote aborts plus every other reason are failed without partial
 * output.
 * @param result - child terminal result.
 * @returns outcome for the `ctx.jobs` registration.
 */
function runOutcome(result: SubagentResult): JobOutcome {
  switch (result.stopReason) {
    case 'completed':
      return { status: 'completed', result: finalText(result.output) }        // ① 成功：携带最终文本
    case 'aborted':
      return result.diagnostic === undefined
        ? { status: 'killed' }                                                // ② 本地取消（无诊断）
        : { status: 'failed', detail: failureDetail(result) }                 // ③ 远端/带诊断的中止算失败
    case 'error':
    case 'max-tokens':
    case 'refusal':
      return { status: 'failed', detail: failureDetail(result) }
    // Merge-extensible reasons remain failures with provider-authored detail.
    default:
      return { status: 'failed', detail: failureDetail(result) }
  }
}

/**
 * Await the child result, dispose the run, then return its task outcome. Result
 * and disposal failures become `failed`; when both fail, both details survive.
 * @param run - live run to settle and release.
 * @returns outcome after child resources are released.
 */
export async function settleRun(run: SubagentRun): Promise<JobOutcome> {
  let outcome: JobOutcome
  try {
    outcome = runOutcome(await run.result)          // ④ 结果通道：异常 → failed
  } catch (error: unknown) {
    outcome = { status: 'failed', detail: String(error) }
  }
  try {
    await run.dispose()                             // ⑤ 释放通道：异常 → 也变 failed
  } catch (error: unknown) {
    const prefix = outcome.detail === undefined ? '' : `${outcome.detail}; `
    return { status: 'failed', detail: `${prefix}dispose failed: ${String(error)}` }
  }
  return outcome
}
// （第 13–27 行的 finalText 与 failureDetail 两个辅助函数被省略：前者把 text block 拼成一条字符串，
//  后者把 diagnostic 拼在 stopReason 后面，属于纯格式化；第 1–7 行的模块注释保留在正文里引用。
//  下面两个函数体一行未删。）
```

- **⑦ catch 的取向**：投递失败**只警告**，不让结算本身失败——通知是记账，不是结算的前置条件。

```ts
/**
 * The balanced completed-turn prefix of `parent`'s log: every event up to and including the
 * last `turn/end`. The in-flight turn is excluded; before any completed turn the child starts
 * fresh. Because live sequence numbers equal array indexes, the result remains a valid seed
 * beginning at sequence zero.
 */
function completedTurnPrefix(parent: Agent): SessionEvent[] {
  const events = parent.session.snapshotEvents()
  const lastEnd = events.findLast(e => e.type === 'turn/end')     // ← 找最后一个 turn/end
  if (lastEnd === undefined) return []                            // ← 守卫：没有完成的轮次 → 空 seed
  // seq === array index (the append contract), so slice up to and including it.
  return events.slice(0, lastEnd.seq + 1)
}

class ForkInProcessProvider implements SubagentProvider {
  readonly capabilities: SubagentCapabilities = {
    agentOptions: true, outputSchema: true, depthLimit: true, toolFilter: true, persona: true,
  }
  // Context contract: a forked child IS seeded with the parent's completed-turn prefix.
  readonly inheritsParentContext = true      // ← 唯一与 spawn 相反的描述性字段
  constructor(readonly name: string) {}
  start(request: ResolvedSubagentStartRequest) {
    const seed = completedTurnPrefix(request.parent)
    return startInProcessRun(request, {
      // Only pass a seed when there's a completed turn to inherit; an empty seed
      // is equivalent to a fresh child, so omit it to keep the session unseeded.
      ...seed.length > 0 ? { seed } : {},     // ← 空 seed 不传，避免把会话标成 seeded
    })
  }
  prepareContinuable(request: ContinuableCreateRequest): Promise<ContinuableCreateSpec> {
    // The fork prefix is captured ONCE, at creation: it becomes part of the
    // child's own durable transcript, so a later cold resume replays that
    // prefix instead of re-forking the parent's newer history.
    const seed = completedTurnPrefix(request.parent)
    return Promise.resolve(seed.length > 0 ? { seed } : {})
  }
}
```

按块讲解：

- **两个类的差异只有三行**：`inheritsParentContext` 的取值、`start` 里传不传 `seed`、`prepareContinuable` 里传不传 `seed`。其余（五项能力、注册方式）完全对称。这正是「**差别以数据表达**」的字面证据。
- **`completedTurnPrefix` 的 `findLast` + `slice(0, seq + 1)`**：因为「活着的 `seq` 等于数组下标」是一条追加契约，所以「切到最后一个 `turn/end` 为止」得到的必然是从 0 连续、且轮次平衡的前缀——可以直接当 `CreateAgentOptions.seed`（`docs/subsystems/subagent.zh.md` 第 466 行）。
- **`seed.length > 0 ? { seed } : {}`**：空 seed **不传**。注释给了理由：空 seed 与「全新子级」等价，但传了它会把会话标成 `isSeeded: true`（与源码 G 里 `isSeeded` 的判断一致）。
- **fork 的可继续版本为什么在这里也算 seed**：注释原文 *"The fork prefix is captured ONCE, at creation: it becomes part of the child's own durable transcript, so a later cold resume replays that prefix instead of re-forking the parent's newer history."*——这解释了「fork 是一次性快照」在可继续路径上同样成立（`packages/subagent/subagent-fork-in-process/README.zh.md` 第 12、144 行）。

**还有两个按「形态」而不是按「传输」区分的维度**（容易被混在一起，所以单列）：

- **一次性 vs 可继续**由工具行的 `backgroundMode` 选择（默认 `one-shot`，或在支持的提供方上 `continuable`）；可继续要求提供方具备 `prepareContinuable`，否则插件在加载期就失败（`packages/subagent/tool-subagent/src/index.ts` 第 345-349 行；`packages/subagent/subagent/README.zh.md` 第 59 行）。
- **前台 vs 后台**由模型给的 `run_in_background` 决定；`one-shot` 策略下默认前台，`continuable` 策略下默认后台（`packages/subagent/tool-subagent/src/index.ts` 第 287-305 行）。

另外两个结构性限制值得记住：ACP 子级**仍然只能是可继续性之外的一次性**，因为父级会话语料里没有它的本地子会话，所以它无法被枚举发现（`packages/subagent/subagent/README.zh.md` 第 188 行）；`subagent-in-process-driver` 不是第七个后端，而是 spawn 与 fork 共用的库，组合里没有任何东西配置它（`packages/subagent/subagent-in-process-driver/README.zh.md` 第 12 行）。

### 4.8 发现：父级自有的目录

进程内子级创建成功后，父会话追加一条 `subagent/catalog` 事实（`parent.append('subagent/catalog', …)`），记录 `childId`、`childCreatedAt`、`mode` 与 label。服务在提供方返回后调用它，并约定：目录追加失败会 dispose 该 run，调用方拿到的是目录错误。`subagentCatalog` projection 在 apply 时**跳过 seq 小于 `inheritedEventCount` 的事件**，即排除 fork 继承的事实。

**源码 U：目录事实的写入与投影的过滤** —— `packages/subagent/subagent/src/catalog.ts` 第 124–135 行，与第 137–164 行

```ts
// ── 第一段：projection 定义（catalog.ts 第 124–135 行） ──────────────────────────
/** Parent-owned direct-child catalog projection; invalid own facts reject restoration. */
export const subagentCatalogProjectionDefinition = {
  key: 'subagentCatalog',
  stateSchema,
  init: (_header: SessionHeader, inheritedEventCount: SessionLogOffset) => ({ inheritedEventCount }),
  apply: (state, event: SessionEvent) => {
    if (event.type !== 'subagent/catalog' || event.seq < state.inheritedEventCount) return state
    return { ...state, head: appendChunkedList(state.head, eventDataSchema.parse(event.data)) }
  },
  stateVersion: 3,
  wire: { viewSchema, view: subagentCatalogEntries },
} satisfies ProjectionDefinition<'subagentCatalog', SubagentCatalogState>
// 本段无省略：第 124–135 行整段照录。

// ── 第二段：写入函数（catalog.ts 第 137–164 行） ────────────────────────────────
/**
 * Append a complete direct-child discovery fact to its parent Session.
 * @param parent - durable direct parent receiving the discovery fact.
 * @param child - established child's immutable Session metadata.
 * @param descriptor - mode-discriminated creation label frozen with the child.
 */
export function establishCatalogChild(
  parent: Session,
  child: SessionHeader,
  descriptor:
    | { readonly mode: 'one-shot'; readonly label?: string }
    | { readonly mode: 'continuable'; readonly label: string },
): void {
  parent.append('subagent/catalog', descriptor.mode === 'one-shot'      // ← 写进父会话的持久日志
    ? {
      version: SUBAGENT_CATALOG_VERSION,
      childId: child.id,
      childCreatedAt: child.createdAt,
      mode: descriptor.mode,
      ...descriptor.label === undefined ? {} : { label: descriptor.label },
    }
    : {
      version: SUBAGENT_CATALOG_VERSION,
      childId: child.id,
      childCreatedAt: child.createdAt,
      mode: descriptor.mode,
      label: descriptor.label,
    })
}
// 本段无省略：第 137–164 行整段照录。
```

按块讲解：

- **两段的参数从哪来**：`apply(state, event)` 的 `state` 由 `init(_header, inheritedEventCount)` 建立——注意 `init` **接住了 `inheritedEventCount`**，所以「跳过 fork 继承的事实」是投影初始化时就定下的边界，而不是每帧再算。`establishCatalogChild` 的调用点在服务里（`packages/subagent/subagent/src/index.ts` 第 572 行），`child` 用的是 `run.localAgent?.session.header`（第 569 行），所以进程外 run 不产生目录事实。
- **`event.seq < state.inheritedEventCount` 一行就是「排除 fork 继承事实」**：fork 子级继承的父级事件里可能包含父级自己的目录事实；如果不跳过，子级会「继承」父级的子代理清单。
- **`mode` 是 discriminated union 而不是可选字段**：`one-shot` 的 label 可缺、`continuable` 的 label 必填——这让「可继续子级一定有标签」成为类型事实。
- **目录写入失败为什么要 dispose run**：服务第 569–585 行的注释原文 *"No caller receives this run; the catalog error owns the failed start."*——此刻没有任何调用方拿到这个 run，所以只能就地释放，并把目录错误抛给调用方。

## 5. 三个「容易记错」的点

1. **独立上下文 ≠ 看不见对话**（本课最常被混的一句）。`fork` 后端会把父级**已配平、已完成轮次**的前缀作为子会话初始内容注入（`inheritsParentContext = true`），但那是 fork 时的一次性快照：「此后父级记录的任何内容都不会到达子 agent」，而且**进行中的轮次绝不包含**（`packages/subagent/subagent-fork-in-process/README.zh.md` 第 12、36、144 行）。所以工具措辞会随 `inheritsParentContext` 变化（源码 S）。
2. **`origin: 'subagent'` 不是「可继续」的证明**。它只是导航分类；mode 与可继续能力的权威是 **descriptor**（源码 G 的注释原文）。
3. **两个深度字段不能只读一个**。持久 header 是单调下界、运行时值只能加深；只读运行时值会让冷恢复后的子级以为自己仍在顶层（源码 I 的 JSDoc 原文）。

**明确不存在的通道**（避免误以为是漏洞）：可继续子级的输出**不通过本次工具调用返回**；后台运行不通过工具暴露结果；没有持久化 parent mailbox，child→parent 需要直接父级仍在线；也没有已接受消息的回放（`packages/subagent/tool-subagent/README.zh.md` 第 211 行；`packages/subagent/subagent/README.zh.md` 第 190、195 行）。

## 附录 A 关键问题与答案

> ✅ 五道题**全部给出明确答案**，不留空、不写「待补充」。逐段标注了「第一次读请跳过」的位置。

### ① 子代理为什么需要独立上下文？

**答：三条互相独立的理由，都能在源码里指名。**

1. **隔离即目的：不消耗父级上下文。** 工具描述本身就是这么写的——「Delegate a self-contained task to a subagent (a separate agent that works in its own context) to offload focused, independent work … so it does not consume this conversation's context. The subagent returns its result, not its intermediate steps.」（`packages/subagent/tool-subagent/src/index.ts` 第 267-271 行；原文见源码 Q 的 `promptDescription` 与 description 非 fork 分支）。子代理的中间工作从不进入父级，父级输入只为最终结果多付一份 token（`packages/subagent/subagent-spawn-in-process/README.zh.md` 第 120-126 行）。
2. **结构上必须独立：每个子代理就是一条自己的 Session。** 进程内后端通过 `parent.ctx.agents.create({ sessionId, parentAgent, meta, … })` 造一个全新子 Agent；新 Session id 由 `randomUUID()` 铸造（`packages/subagent/subagent-in-process-driver/src/index.ts` 第 113、134-143 行，见源码 F ④⑨）。所以子代理有自己的事件日志、自己的系统提示词、自己的请求前缀与 KV Cache（`packages/subagent/subagent-spawn-in-process/README.zh.md` 第 116 行）。
3. **隔离的严格边界：新建扁平作用域，不继承父级注册与权限。** 「子 agent 获得全新的扁平注册作用域：父级工具限制与权限绝不会被导入」（`packages/subagent/subagent-spawn-in-process/README.zh.md` 第 82 行）；glossary 把这条上升为通则——带作用域的注册不会向下继承给 subagent，子树行为通过 lineage 数据表达，从不通过 scope 结构（`docs/glossary.zh.md` 第 13 行）。

**重要限定：独立上下文 ≠ 看不见对话。** `fork` 后端会把父级**已配平、已完成轮次**的前缀作为子会话初始内容注入（`inheritsParentContext = true`，见源码 T），但那是 fork 时的一次性快照：「此后父级记录的任何内容都不会到达子 agent」，而且**进行中的轮次绝不包含**（`packages/subagent/subagent-fork-in-process/README.zh.md` 第 12、36、144 行）。所以工具措辞会随 `inheritsParentContext` 变化（源码 S）。

> **第一次读请跳过下面这段**（它涉及第二编的 scope 原语与 preset 组合）：隔离与「父级 preset 的继承」并不矛盾——子级会**join 父级 preset**（源码 H ①），但这一步拿到的是「一份可继承的组合」，之后子级自己的 persona 与工具过滤在其上**收窄**；父级的工具限制与权限仍然不会被导入。

### ② 有哪几种委派后端？它们的差别是什么？

**答：六个已注册后端（另有一个不是后端而是共享库的驱动器），差别集中在「子级住在哪个进程」和「按数据表达了什么」。**

后端对照表见 §4.7（含每个后端的默认 providerName、子级住哪、是否继承父级对话、启动时能力与出处行号）。

- **进程内两个后端的差别只有一处，且以数据表达**：spawn 传 `startInProcessRun(request, {})`；fork 传 `{ seed: completedTurnPrefix(parent) }`（源码 T）。
- **进程外四个后端的能力声明**：`acp`、`codex`、`claude-code` 全 `false`（`NO_START_CAPABILITIES`）；`dsh-sdk` 只支持 `agentOptions`，理由是「它能把 Agent 路由选项解析进子运行时的进程级握手，而输出结构、深度、工具过滤与人设的所有权不跨越这个进程边界」（`packages/subagent/subagent-dsh-sdk/src/index.ts` 第 109-113、129-138 行）。
- **两个按「形态」而不是按「传输」区分的维度**（容易被混在一起）：一次性 vs 可继续由工具行的 `backgroundMode` 选择；前台 vs 后台由模型的 `run_in_background` 决定（`packages/subagent/tool-subagent/src/index.ts` 第 287-305、345-349 行）。
- **两个结构性限制**：ACP 子级仍然只能是可继续性之外的一次性，因为父级会话语料里没有它的本地子会话，所以无法被枚举发现（`packages/subagent/subagent/README.zh.md` 第 188 行）；`subagent-in-process-driver` 不是第七个后端（`packages/subagent/subagent-in-process-driver/README.zh.md` 第 12 行）。

### ③ 结果如何回传给父 agent？

**答：按子级形态分三条路，互不替代。**

**路径 A：一次性前台（最常见）——工具结果。**
`tool-subagent` 在 `execute` 里 `await ctx.subagents.start(name, request)` 拿到 `SubagentRun`，然后 `settleForegroundRun(run)`：先 `await run.result`，再**无论成败都** `await run.dispose()`；两条通道都 reject 时抛 `AggregateError` 同时保留两项失败（源码 K）。父级看到的就是工具结果里的 `output`（子级最终输出）。

结果的选取规则是唯一真源 `finalAssistantOutput()`：取最后一条**非空** assistant 消息；若不存在，退化为累积的 assistant 文本流；两者都没有则为 `[]`（`packages/subagent/subagent/src/assistant-output.ts` 第 62-75 行；类内 `collect()` 第 55-59 行）。驱动器读结果时从 activation boundary 之后的事件里读，因此 **fork 的 seed 不会被误当子级输出**（`packages/subagent/subagent-in-process-driver/src/index.ts` 第 211-238 行，与源码 F ⑤ 的 `activationBoundary` 呼应）。

失败如何呈现：非 `completed` 的 stop reason 一律变成出错的工具结果（源码 L），并附上提供方诊断与保留的部分输出（`withDiagnosticAndPartialText`，`packages/subagent/tool-subagent/src/index.ts` 第 156-196 行）。注意 `run.result` **不会**因子级失败而 reject——模型／传输失败以 `stopReason: 'error'` resolve，只有 seam 无法表示的基础设施故障才 reject（源码 E 的 `result` 注释、`packages/subagent/subagent/src/types.ts` 第 321-328 行）。

**路径 B：一次性后台——Task 通道。**
`jobs.start({ kind: 'subagent', label, owner: parent.id, run: … })` 注册一个归父级所有的 Task（源码 M），`done` 由 `settleRun` 结算成 `JobOutcome`：`completed` 带最终文本，本地取消（无 diagnostic 的 `aborted`）映射为 `killed`，其余为 `failed`（源码 N；`packages/subagent/subagent/src/run-settlement.ts` 第 37-53 行）。模型拿到 `started background subagent job <id>`（源码 R 的 render），之后用 `job_output` 收集、`job_output`/`job_kill` 管理。

**路径 C：可继续子级——没有返回值，只有运行时结算通知 + 显式 `send_message()`。**
`startContinuable()` 在 inbox 接受初始提示词时就 resolve 成 `{ childId, messageId }`，「既不等待轮次开始，也不等待消息进入会话日志」（`docs/subsystems/subagent.zh.md` 第 136 行；源码 M 的第 530-536 行）。真正把结果送到父级的是 Activation 结算时的 `notifySettlement()`：解析持久 `parentSession` → 拿在线父 Agent → `createSettlementMessage()` → 父级正在拆卸则 `inject()`（不唤醒），否则空闲走 `queue`、繁忙走 `steer`（源码 O）。这条通知对「每个调用方拿到过 id 的 child」都是**无条件**的，且发生在会让 parent 被判定为已结算的所有权释放之前（`docs/subsystems/subagent.zh.md` 第 202 行；源码 O 的调用点在 `releaseOwnership` 之前）。

后半段同样重要：**子级也能主动推**。`sendMessage()` 是唯一由模型编写消息的操作，它接收确切在线 sender 与目标 id，只允许**直接 parent** 或**直接可继续 child**，并自行推导 sender 来源（`docs/subsystems/subagent.zh.md` 第 138、150 行）。为此 `startContinuable` 会在子级的初始用户任务后面附上一段返回指引（源码 Q 的 `withContinuableReturnGuidance`），明确告诉子级把结果发回父级 id，并强调「发消息不会结束你的轮次」。

**明确不存在的通道**（避免误以为是漏洞）：可继续子级的输出**不通过本次工具调用返回**；后台运行不通过工具暴露结果；没有持久化 parent mailbox，child→parent 需要直接父级仍在线；也没有已接受消息的回放（`packages/subagent/tool-subagent/README.zh.md` 第 211 行；`packages/subagent/subagent/README.zh.md` 第 190、195 行）。

### ④ lineage（parentSession / delegationDepth / subagentDepth）各自是什么意思？

**答：三者都是「以数据形式携带的父子关系事实」，合计构成谱系（lineage）；它们不影响可见性，也不是权限凭据。**

字段表见 §4.5。

**合并规则（本 seam 独有，别记错）**：`delegationDepthOf(agent)` 返回 `Math.max(header.delegationDepth ?? 0, options.subagentDepth ?? 0)`——**存在的较大值具有权威性**（源码 I）。写侧由 `childSessionMeta()` 把 `delegationDepth` 落进子会话 header（源码 G），由 `resolveChildAgentOptions()` 把 `subagentDepth` 落到子 Agent 的 options（`packages/subagent/subagent/src/child-agent.ts` 第 115 行）。**两个字段都归 subagent seam 所有：核心循环既不设置也不读取它们**（`docs/subsystems/subagent.zh.md` 第 465 行）。

**执行语义**：

- 子级深度 = `delegationDepthOf(parent) + 1`；超出安全整数域抛 `RangeError`，超过 `request.maxDepth` 抛 `SubagentDepthError`（message 形如 `subagent depth 1 exceeds maxDepth 0`）（源码 J；`packages/subagent/subagent/src/child-agent.ts` 第 50-59 行，第 33-38 行）。
- 运行时值本身也要校验：非安全整数、负数或 `-0` 一律 `TypeError('agent subagentDepth must be a non-negative safe integer')`（源码 I）。
- 工具层的 `maxDepth` 默认读宿主设置，初始值 `1`；`0` 禁止一切委派；数值深度要求提供方具备 `depthLimit` 能力，否则挂载期就失败（`packages/subagent/subagent/README.zh.md` 第 47 行；`packages/subagent/tool-subagent/src/index.ts` 第 328-334 行）。

> **第一次读请跳过下面这段**（它涉及 schedule 子系统与 preset 作用域）：**一个能说明「lineage 是数据不是权限」的第三方例子**：schedule 工具的 `subagentCallerRefusal` 在调用方的委派深度大于零时拒绝全部四个排程工具，其理由是「委派封顶本身执行的记账，由持久化 session header 承载并跨冷恢复保留」——即另一个子系统**读** lineage 数据做自己的策略，而不是继承任何父级权限（`.agents/notes/implemented/architecture/2026-09-24-preset-scoped-schedule-tools.zh.md` 第 29-30 行）。

### ⑤ `parentSession` 是权限凭据还是显示字段？

**答：两者都不是「纯粹的一种」——它是「鉴权输入」＋「谱系主键」，但既不表示父级仍在线，也不影响可见性。**

1. **是鉴权输入**：可继续路径上，「向直接 parent 发消息」这类操作的合法性来自持久 `parentSession` 关系，而不是来自 scope 继承（`.agents/notes/implemented/feature/2026-07-28-continuable-subagent-conversations.zh.md` 第 53 行；`docs/subsystems/subagent.zh.md` 第 138、150 行）。
2. **不是在线路由能力**：源码 O 第 874-875 行必须**真的去在线注册表里找父 Agent**，找不到就 `return`——这证明 `parentSession` 只记录「谁是父级」，不保证「父级还在」。`packages/subagent/subagent/README.zh.md` 第 190、195 行把这条写成限制：「没有持久 parent mailbox」。
3. **不影响可见性**：glossary 的定义句是「以数据形式携带的父子关系事实……从不影响可见性」（`docs/glossary.zh.md` 第 21 行）。可见性由 scope 结构决定，而带作用域的注册**不向下继承**（第 13 行）——所以「子级能不能看到某个工具」与「子级的父级是谁」是两件互不相干的事。
4. **和 `origin` 的分工**：`parentSession` 是 lineage；`origin: 'subagent'` 只是粗粒度产品分类，是展示元数据，**不是可继续性的证明**（`packages/core/session/src/types.ts` 第 113-117 行；源码 G 的注释）。
