## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：把"产品是怎么被叠出来的"这条规则讲死——**顺序是什么、每一层能做什么、冲突时谁赢**。
**不是**：patch 文件的完整语法（那是 `1.4`）、配置校验机制（那是 `2.6`）。

### 0.2 现在只要记住 3 件事

1. **顺序**：空根 → 各 bundle（按 profile 列出的顺序）→ profile 自己的 patch → home 级 patch → `--patch` 覆盖层；**后者覆盖前者**。
2. **一次 patch 只做三件事**：按 `id` 定位一个条目，然后 **覆盖它的 `config`** / **禁用它** / **插入新条目**。
3. **覆盖是"整体替换那个键"**，不是深合并——想只加一个字段，也得把该条目完整的 `config` 重述一遍。

### 0.3 明确授权：这些现在不用管

- `# ==` 注释的**渲染算法**（前缀快照 + 位置差分）——**第一次读不必弄懂**：知道它标的是"这一段谁贡献的、被谁改过"就够了。它的源码与逐块讲解在 §5.1 / §5.2，回查时再看；
- `group` 条目的子条目递归、`name` 身份校验的细节——属于 `1.3` / `2.6`（本课只在 §4.3 的对照表里点一下它们的存在）；
- `!!js` 表达式什么时候求值——属于 `2.6`。

### 0.4 本课依赖 1.1 的词汇

`profile` / `bundle` / `patch` / 条目 `entry` / 层 `layer` 这五个词已由 `notes\1-结构与装配\1.1-名词与分层.md` 定义，本课不重复。

## 1. 最小词汇表（本课新增的 5 个词）

| 词 | 大白话 | 在源码/输出里的样子 |
|---|---|---|
| **override 覆盖** | 按 `id` 找到**已有**的条目，改掉它的某个键 | patch 里写 `- id: xxx` + 要改的键 |
| **insert 插入** | 往树里**加新**条目 | patch 里写 `- insert:` 后跟条目数组 |
| **层边界** | dump 输出里那行 `# ==` 注释，标明"下面这一段是谁贡献的、被谁改过" | `# == @deepseek-ai/dsh-base, patched by @deepseek-ai/dsh-web-app` |
| **快照** | 把"只应用前 k 层"的树算一遍，得到一份中间结果 | 生成 dump 用的手段，不在输出里出现 |
| **位置差分** | 把相邻两份快照按**下标**逐行比对，看出哪一行被改动 | 同上 |
| （复用）**group** | 一种特殊条目，它的 `config` 本身是一串**子条目** | `- id: <组名>` + `config:` 数组 |

> ⚠️ `group` 的完整语义在 `2.6` 展开；本课只在"`insert` 带 `id` 要求目标是 group"这一处用到它。

## 2. 先建立画面

### 2.1 组装链（静态结构）

```
cordis.yml          内容就是一个空数组 []        ← 起点，永远不该手改
     │
     │  按下面的顺序依次"叠"（后者覆盖前者）
     ▼
 ① 各 bundle 的 patch       顺序 = profile 清单里 dsh.profile.bundles 的书写顺序
 ② profile 的 patch         $DSH_HOME\profiles\<名字>\cordis.patch.yml
 ③ home 级 patch            $DSH_HOME\cordis.patch.yml（不存在则跳过）
 ④ --patch 覆盖层           命令行上按出现顺序，可多个
     │
     ▼
 组装结果 = "有效条目列表" → 也就是运行时的插件树
```

### 2.2 一次 `--dump-config` 是怎么算出来的（大白话）

1. 读 `cordis.yml`，得到一个**空表**。
2. 把上面 ①→④ 的 patch **依次**应用上去（每次应用都是同一份算法）。
3. 每应用一层，就把当前的树**存一份快照**。
4. 比对相邻快照：哪一行是新出现的（→ 记下它的来源），哪一行被改了（→ 记下"谁改的"）。
5. 按"来源 + 改动者"把**连续的行**归成一段，每段前面打一行 `# ==` 注释，最后整份打印出来。

→ 所以 dump 不是"逐层罗列"，而是**带出处的最终结果**。这也是为什么同一层会被切成很多段（见 §5）。

## 3. 结论：权威的组合顺序

**出处（源码，权威）**：`apps\cli\src\dump-config.ts` 第 44–75 行的 `collectConfigDumpLayers`，其文档注释原文：

> Read dump layers in **bundle, profile, home, then argv order** without composing them.

| 序号 | 层 | 来源 | 不存在时 |
|---|---|---|---|
| 0 | **根** | profile 目录下的 `cordis.yml`，内容是**空数组** `[]` | 由启动器写入 |
| 1 | **bundle 层**（可多层） | 每个 bundle 的 patch 文件，按 `dsh.profile.bundles` **列出的顺序** | — |
| 2 | **profile 层** | profile 目录下的 `cordis.patch.yml`（用户自己那份） | 存在才加 |
| 3 | **home 层** | `$DSH_HOME\cordis.patch.yml` | 用 `loadOptionalPatches` 加载，缺失 → **不贡献层**（不报错） |
| 4 | **argv 层**（可多层） | 每个 `--patch <file>`，按命令行顺序 | — |

**根文件为什么是空的**：`apps\cli\src\profile-boot.ts` 第 80–88 行定义了 `PROFILE_ROOT_CONFIG`：

```yaml
# dsh profile root — an empty entry list. The tree is composed as patches:
# each bundle in package.json's dsh.profile.bundles, then cordis.patch.yml, then any
# --patch overlays. Edit cordis.patch.yml, not this file.
[]
```

→ **整棵树没有"原始内容"，全部由 patch 的 `insert` 推入。** 这是"产品是叠出来的"最字面的证据。

### 3.1 顺序就是在这一段里定下来的（源码）

`collectConfigDumpLayers` 是 dump 路径上"把层按顺序排好"的唯一地方，也是本课 §3 那张表的直接依据：

`apps\cli\src\dump-config.ts` 第 45–74 行

```ts
/**
 * Read dump layers in bundle, profile, home, then argv order without composing them.
 * @param loaded - prepared profile and parsed bundle and profile patches.
 * @param defaultOnly - omit profile, home, and argv layers without reading their files.
 * @param patches - overlay paths relative to the invoking directory, in argv order.
 * @returns the labeled layers shared by YAML and schema dumps.
 */
export function collectConfigDumpLayers(       // ← 函数头：一次 dump 的全部输入就是这三样
  loaded: Profile,
  defaultOnly: boolean,
  patches: readonly string[],
): ConfigDumpLayer[] {
  const layers: ConfigDumpLayer[] = loaded.layers.map(layer => ({   // ① bundle 层
    label: layer.packageName,
    patches: layer.patches,
  }))
  if (!defaultOnly) {
    if (existsSync(loaded.patchPath)) {                             // ② profile 自己的 patch
      layers.push({ label: loaded.patchPath, patches: loaded.patches })
    }
    const homePatchFile = homePatchPath()                           // ③ home 级 patch
    const homePatches = loadOptionalPatches(NAME, homePatchFile)
    if (homePatches !== undefined) {
      layers.push({ label: homePatchFile, patches: homePatches })
    }
    for (const file of patches) {                                   // ④ --patch 覆盖层
      const absolute = resolve(file)
      layers.push({ label: absolute, patches: loadOverlayPatches(NAME, absolute) })
    }
  }
  return layers
}
// （第 76 行的 /* v8 ignore stop */ 是覆盖率标记，与本知识点无关，此处省略）
```

按块讲解：

- **JSDoc 第一句**就是这个顺序的权威表述（原文 `bundle, profile, home, then argv order`）——§3 的结论直接来自它，不是从文档抄的。
- **`loaded` / `defaultOnly` / `patches` 从哪来**：调用方是同文件第 32–42 行的 `runDumpConfig`，它做的正是 `const loaded = prepareProfile(profile, !defaultOnly, …)`、`const layers = collectConfigDumpLayers(loaded, defaultOnly, patches)` —— 所以 `loaded.layers` 已经是**按 `dsh.profile.bundles` 顺序加载好的** bundle 层（见 §3.2），这里只做 `map`，不重排。
- **① `map` 而不是 `push`**：bundle 层是"底"，必须整段排在最前，所以先把它们变成数组的初始内容，后面的层才 `push` 上去。**数组顺序 = 应用顺序 = 覆盖顺序**。
- **② `existsSync` 先判一次**：文件不在就**不 push**（"存在才加"的落点）。这里判的是 profile 自己的 `cordis.patch.yml`。
- **③ 走 `loadOptionalPatches`**：它缺文件返回 `undefined`，于是 `if (homePatches !== undefined)` 不成立、这一层**根本不进数组**——这就是"home 层缺失时不贡献层、也不报错"。对照 §3.4：bundle / `--patch` 用的 `loadOverlayPatches` 缺文件会**抛错**。
- **④ `for` 按 argv 顺序**：`resolve(file)` 把相对路径按**当前工作目录**变成绝对路径（所以 `--patch` 的相对路径与 cwd 有关，其余层与 cwd 无关）；`loadOverlayPatches` 在循环里被调用，**任何一个 `--patch` 文件缺失都会立刻抛错**。
- **`if (!defaultOnly)` 包住 ②③④ 一整段**：这是 `--dump-default-config` 的实现——它不只是"不渲染"这三层，而是**连文件都不读**。所以 profile 的 patch 写坏了，它照样能出结果（"损坏配置的诊断手段"的机制来源）。

### 3.2 bundle 层为什么天生就是有序的（源码）

`loaded.layers` 的顺序不是 dump 排的，而是 `loadProfileDirectory` 按 `dsh.profile.bundles` 数组逐个读出来的：

`packages\boot\app-boot\src\profile.ts` 第 738–760 行

```ts
// （第 719–731 行的函数文档注释：说明本函数用于"已初始化的 profile 目录"，此处省略）
export function loadProfileDirectory(       // ← 函数头
  binName: string,
  dir: string,
  installAnchor: string,
  options: { userLayer?: boolean } = {},
): Profile {
  const manifest = dropRetiredBundles(dir, readProfileManifest(binName, dir))   // ① 读清单，并剔除已下线的 bundle
  const bundles = manifest.dsh?.profile?.bundles ?? []                          // ② 顺序的唯一来源
  const layers: ProfileLayer[] = []
  const skippedBundles: SkippedBundle[] = []
  const exemptions = bundles.length === 0 ? {} : readProfileVersionExemptions(dir)
  for (const packageName of bundles) {                                          // ③ 按书写顺序遍历
    try {
      const packageDir = resolveBundleDir(binName, packageName, installAnchor, dir)
      const bundleManifest = readProfileManifest(binName, packageDir)
      const bundle = bundleManifest.dsh?.bundle
      if (bundle === undefined) {
        throw new Error(`${binName}: profile bundle ${JSON.stringify(packageName)} declares no dsh.bundle in its package.json`)
      }
      const issue = evaluatePluginCompatibility(bundleManifest, exemptions)
      if (issue !== undefined && !issue.exempted) throw new Error(pluginCompatibilityWarning(issue))
      const patchPaths = bundlePatchPaths(packageDir, bundle)
      const patches = patchPaths.flatMap(patchPath => loadOverlayPatches(binName, patchPath))
      layers.push({ packageName, packageDir, patchPaths, patches })             // ④ 顺序 = 数组顺序
    } catch (error) {
      skippedBundles.push({ packageName, reason: String(error) })               // ⑤ 失败的 bundle 只记录、不中断
    }
  }
  // …（第 761–765 行：读 profile 自己的 cordis.patch.yml 并组装返回值，见 §3.3）
}
```

按块讲解：

- **② `bundles` 从哪来**：`manifest` 来自 profile 目录的 `package.json`，`dsh.profile.bundles` 是数组；`?? []` 让"没写 bundles"的 profile 得到一个空数组（于是只有用户层，不会抛错）。
- **③ `for … of` 直接遍历这个数组**：**没有任何排序、没有去重**。所以"bundle 层的顺序"字面上就是 `dsh.profile.bundles` 里**书写的先后**——这就是 §3 表里"按列出的顺序"的确切含义。
- **④ 一个 bundle 也可能贡献**多层：`patches` 是 `patchPaths.flatMap(...)`，把该 bundle 声明的**多个 patch 文件按声明顺序拼接**成一个列表。仓库里 `dsh-web-app` 就声明了 5 个文件（`packages\bundle\web-app\package.json` 第 44–50 行：`cordis.patch.yml` 加 4 个 `presets\*.patch.yml`）。
- **⑤ `try/catch` 只 `push` 到 `skippedBundles`**：这就是"兼容性预检失败的 bundle **不贡献层**、但启动继续"的落点；`reportSkippedBundles`（同文件第 118–122 行）之后把这些原因打到 **stderr**，所以 dump 的 stdout 可能干净而 stderr 有警告。
- **`dropRetiredBundles`（第 738 行）**会顺手把旧版本下线过的 bundle 从清单里删掉——这会**改写** profile 的 `package.json`，是本课唯一会动用户文件的路径（标注为推断：它只在下线的 bundle 真的出现在清单里时才改写）。

### 3.3 profile 自己的层与 home 层：一个常量、两条路径

`apps\cli\src\profile-boot.ts` 第 67–75 行

```ts
/**
 * The home-level user patch layer (`$DSH_HOME/cordis.patch.yml`), applied
 * over every profile's own layer. Resolved per call, not at module load:
 * `$DSH_HOME` may be set by the test or launcher after import.
 * @returns the absolute patch-file path.
 */
export function homePatchPath(): string {
  return join(resolveDshHome(), PROFILE_PATCH_FILENAME)
}
```

按块讲解：

- **路径从哪来**：`PROFILE_PATCH_FILENAME` 是 `packages\boot\app-boot\src\profile.ts` 第 40 行导出的常量，值就是字符串 `'cordis.patch.yml'`；`resolveDshHome()` 来自 `@deepseek-ai/dsh-home-paths`（默认 `~/.dsh`，可用环境变量覆盖）。所以 home 层的绝对路径＝`$DSH_HOME\cordis.patch.yml`。
- **"applied over every profile's own layer"**：作者原文直接说明 home 层叠在**每个** profile 之上（不是某个 profile 内部的一层）——这是 §附录 A Q6"home 层到底存不存在"的答案本体。
- **`Resolved per call, not at module load`**：路径在**每次调用**时算，不在模块加载时算——因为 `$DSH_HOME` 可能在 import 之后才被设置。这就是"在哪个目录跑都行"的机制底座（与 cwd 无关）。
- **与 §3.1 的衔接**：`collectConfigDumpLayers` 用 `loadOptionalPatches`（缺文件 → `undefined` → 不贡献层）；而 `packages\boot\app-boot\src\profile-context.ts` 第 63–74 行的 `readProfilePatches`（热重载路径）用**同样的顺序**取层：`profile.layers` → profile 的 patch → `home` 下的 `cordis.patch.yml` → `context.overlays`（`--patch`），最后还追加一条由 `DSH_TELEMETRY_DISABLED` 推导出的禁用 patch。→ **dump 与真实启动同序，所以 dump 不会漂移。**

> 热重载那段整块源码见 `1.1` §5.5；本课只记结论：**顺序相同是硬约束，两处实现互为证据。**

### 3.4 文件名写对了却不存在，会怎样（源码）

```ts
// packages\boot\app-boot\src\index.ts 第 305–344 行（两个函数的文档注释各保留首句）
/**
 * Load an optional patch-list file: … A missing
 * file means "no layer"; an unreadable, unparsable, or non-array file throws —
 * a present patch file that cannot apply is a misconfiguration and must fail
 * loud at boot, never be silently skipped.
 */
export function loadOptionalPatches(binName: string, file: string): PatchOptions[] | undefined {
  let content: string
  try {
    content = readFileSync(file, 'utf8')
  } catch (error) {
    if ((error as NodeJS.ErrnoException | null)?.code === 'ENOENT') return undefined   // ← 只放行"文件不存在"
    throw new Error(`${binName}: failed to read patches ${file}: ${String(error)}`)
  }
  return parsePatchList(binName, file, content, 'patches')
}

/**
 * Load a required overlay patch list: a bundle's `cordis.patch.yml` or a
 * `--patch <path>` overlay. … a missing file throws, because the caller named this file
 */
export function loadOverlayPatches(binName: string, file: string): PatchOptions[] {
  let content: string
  try {
    content = readFileSync(file, 'utf8')
  } catch (error) {
    throw new Error(`${binName}: failed to read overlay ${file}: ${String(error)}`)    // ← 任何读取失败都抛
  }
  return parsePatchList(binName, file, content, 'overlay')
}
// （第 305–315、327–335 行：两段 JSDoc 的完整文字与 @param 列表，与本知识点无关，此处省略，
//   只保留各自第一句判断依据）
```

按块讲解：

- **两个函数的唯一区别就是 catch 里的那一句**：`loadOptionalPatches` 只把 `ENOENT`（文件不存在）翻译成 `undefined`，其它错误（权限、目录、编码）照样抛；`loadOverlayPatches` 一律抛。
- **谁用哪个**：`home` 层与 profile 自己的层用 **optional**（用户可能没写）；**bundle 的 patch 与 `--patch` 文件**用 **overlay**（调用方点名了这个文件，缺了就是配置错误）。→ 所以"少写一个 `--patch` 路径参数"会**启动失败**，而"删掉 home 级 patch"只是少一层。
- **"文件存在但内容坏了"两种都抛**：`parsePatchList`（第 371 行）对非数组、非映射的条目逐个抛错，JSDoc 的原话是 *"a present patch file that cannot apply is a misconfiguration and must fail loud at boot, never be silently skipped"*。
- **注意区分"文件坏"与"patch 打不中"**：文件坏 → **抛错**；单个 patch 的目标行不存在 → 只是**警告并跳过**（见 §4）。作者在第 362–364 行写明了理由：*"a single patch whose target row is absent stays a per-entry Loader warning, so one overlay shared across surfaces does not have to match every tree."*

## 4. patch 的确切语义

**出处（源码，权威）**：`vendor\include\src\index.ts` 第 57–127 行的 `applyEntryPatches` —— 它是 `boot()` 与 `--dump-config` **共用的同一份算法**（所以 dump 与真实启动不会漂移）。作者在第 46–47 行的 JSDoc 里写明这层意图：*"THE patch semantics of this include, shared by mounting (`applyPatches`) and offline config tooling (`dsh --dump-config`) so a dump can never drift from what boots."*

### 4.1 整段算法（本课最重要的一段源码）

整段从第 43 行（JSDoc 开头）到第 127 行（函数收尾）共 85 行，超过"能自解释"的粒度上限，所以按**职责**切成两块：**第一半**回答"patch 能定位到谁"，**第二半**回答"打不中 / 打中了分别怎么办"。两块都带上函数头与依赖变量的来源，可独立阅读。

**第一半：入口 + `id` 索引**（这一段决定了"一次 patch 能定位到哪些条目"）

`vendor\include\src\index.ts` 第 43–78 行

```ts
// （第 43–51 行 JSDoc：主题是"这是本 include 的 patch 语义，挂载与离线 dump 共用"，
//   完整文字含 4 个 @param，此处只留第 52–56 行的参数说明）
/**
 * @param data - the parsed entry list (JSON-safe plain data).
 * @param patches - the patch list to apply, in order.
 * @param warn - sink for skipped-patch diagnostics (printf-style, `%C` = code).
 * @returns a detached entry list with every applicable patch applied.
 */
export function applyEntryPatches(                 // ← 函数头
  data: EntryOptions[],
  patches: PatchOptions[] | undefined,
  warn: (message: string, ...args: any[]) => void,
): EntryOptions[] {
  if (!patches?.length) return [...data]           // ① 没有 patch：原样返回
  data = structuredClone(data)                     // ② 先深拷贝：绝不改输入对象

  const entryMap = new Map<string, EntryOptions>() // ③ 索引：id → 条目
```

按块讲解：

- **⑧⑬⑫ 三种形态**：`insert` 不带 `id` → 顶层追加（bundle 就是靠它把自己那一堆条目推进**空根**）；`insert` 带 `id` → 目标必须**存在且是 group**，推进它的 `config`；非 `insert` → 必须带 `id` 的**原地覆盖**。三种之外没有第四种。

## 5. dump 输出怎么读：`# ==` 为什么重复

要点已在 §2.2 用大白话讲完，这一节补上"它是怎么算出来的"源码，以及三条精确说明。

**出处（源码）**：`packages\boot\app-boot\src\index.ts` 第 399–430 行（`renderConfigDump` 的文档注释）、第 431–494 行（`renderConfigDump` 实现）、第 496–525 行（`groupedDump`）。

### 5.1 快照与位置差分（`# ==` 重复的机制来源）

`packages\boot\app-boot\src\index.ts` 第 452–493 行

```ts
  const baseLabel = basename(absoluteConfigPath)     // ← 起点标签 = 根文件名（cordis.yml）
  const base = parsed as Parameters<typeof applyEntryPatches>[0]
  // snapshot_k = ONE application of layers 1..k flattened, using the exact
  // arguments boot passes for that prefix. snapshot_N is the mounted composition.
  const snapshot = (count: number, warnings: string[]): ReturnType<typeof applyEntryPatches> => {
    const flattened = structuredClone(layers.slice(0, count).flatMap(layer => layer.patches))
    return applyEntryPatches(base, flattened, (message: string, ...args: unknown[]) => {
      let index = 0
      warnings.push(message.replace(/%C/g, () => JSON.stringify(args[index++])))
    })
  }
  let previous = base
  let previousWarnings: string[] = []
  const entryOrigins: { origin: string; patchedBy: string[] }[] = base.map(() => ({ origin: baseLabel, patchedBy: [] }))
  let composed = base
  for (let count = 1; count <= layers.length; count += 1) {      // ← 逐层推进
    const layer = layers[count - 1]
    if (layer === undefined) continue
    const warnings: string[] = []
    composed = snapshot(count, warnings)                          // ① 只应用前 count 层
    for (const line of warnings.slice(previousWarnings.length)) {  // ② 新增的警告属于刚加的这一层
      warn(`${binName}: [${layer.label}] ${line}`)
    }
    const before = previous.map(entry => JSON.stringify(entry))   // ③ 上一份快照，按下标对齐
    for (let index = 0; index < composed.length; index += 1) {
      if (index >= before.length) entryOrigins.push({ origin: layer.label, patchedBy: [] })  // ④ 新出现的行
      else if (JSON.stringify(composed[index]) !== before[index]) entryOrigins[index]?.patchedBy.push(layer.label)  // ⑤ 被改动的行
    }
    previous = composed
    previousWarnings = warnings
  }
  return groupedDump(composed, entryOrigins)
}
// （函数头与整段 JSDoc 在第 431–451 行；上面从第 452 行开始，第 474–475 行的
//   entryOrigins 与 composed 初始化已合并进来。第 457–462 行的注释解释了为什么每次快照都要
//   structuredClone：applyEntryPatches 只深拷贝条目列表，insert 的行是"按引用"推入的，
//   共用 patch 对象会让后一次快照的改动漏进前一次的结果。）
```

按块讲解：

- **`snapshot(count, …)` 做什么**：把**前 `count` 层**的 patch 拍平成一份列表，喂给 §4 那个 `applyEntryPatches`（起点 `base` = 根文件里的空数组 `[]`），得到"只叠到第 k 层"的中间结果。**注意它用的就是 boot 用的同一个函数、同样的参数形状**——所以快照不是模拟。
- **③④⑤ 位置差分**：把上一份快照按行 `JSON.stringify` 后**按下标**比对。`index >= before.length` 说明这一行是**新出现的**（→ `origin` = 刚加的那一层）；下标相同但内容不同说明这一行**被这一层改了**（→ 往 `patchedBy` 里追加这一层的标签）。
- **为什么"按下标"能成立**：这正是 §4 算法的性质——patch **只在原地改写（`target[key] = value`）或尾部追加（`push`）**，不会把中间的行挪走或删掉。所以同一位置的下标可以跨快照追踪同一行。
- **② warnings 的差分**：上一层能看到的"打不中的 patch"这一层也看得到，所以只取**多出来的尾巴**，把新警告记在**刚加的那一层**名下——这就是 dump 里 `dsh: [<层标签>] patch: entry … not found` 的来源（打到 stderr，不在 YAML 里）。
- **每行最终拿到两个属性**：`origin`（哪一层推入的）+ `patchedBy`（哪些层改过它）。

### 5.2 谁的标签相同，就合成一段

`packages\boot\app-boot\src\index.ts` 第 496–525 行

```ts
/** Render the composed rows grouped under one source-and-patches comment per contiguous run. */
function groupedDump(                                  // ← 函数头
  composed: readonly unknown[],
  entryOrigins: readonly { origin: string; patchedBy: string[] }[],
): string {
  const lines: string[] = []
  let currentLabel: string | undefined
  let group: unknown[] = []
  const flush = (): void => {
    if (currentLabel === undefined || group.length === 0) return
    lines.push(`# == ${currentLabel}`)                 // ① 一段的注释头
    lines.push(yaml.dump(group, { schema: entryListSchema, noRefs: true }).trimEnd())
    group = []
  }
  for (let index = 0; index < composed.length; index += 1) {   // ② 顺序扫过最终结果
    const record = entryOrigins[index]
    if (record === undefined) continue
    const label = record.patchedBy.length === 0
      ? record.origin                                 // ③ 没人改过：只写来源
      : `${record.origin}, patched by ${record.patchedBy.join(', ')}`   // ④ 被改过：来源 + 改动者
    if (label !== currentLabel) {
      flush()                                          // ⑤ 标签一变，先把上一段 flush 掉
      currentLabel = label
    }
    group.push(composed[index])
  }
  flush()
  return lines.join('\n') + '\n'
}
```

> 本块是**完整未删节**（第 496–525 行），没有省略任何行——它是一个独立的小函数，整段拿来才自解释。

按块讲解：

- **③④ 标签怎么拼**：`patchedBy` 为空 → 只写来源包名；非空 → 追加 `, patched by …`（多个改动者按层顺序用逗号连起来）。这就是 §7 那行 `# == @deepseek-ai/dsh-base, patched by @deepseek-ai/dsh-web-app` 的生成规则。
- **⑤"连续段"语义**：只在标签**发生变化**时切段，所以**标签相同但被别的层隔开的两段会各写一次注释**。
- **→ 精确说明 3：`# ==` 的条数 ≠ 层的数量。** 任何一个"改动点"都会把原本连续的一段切成两段，所以条数通常远多于层数；同一层被写很多次是正常的，不是渲染 bug。
- **① `# ==` 是 YAML 注释**：所以输出的整份文档仍然**可被当作 YAML 加载**（这也解释了为什么它不破坏 `--dump-config > tree.yml` 的可用性）。

### 5.3 另外几个细节

- `!!js` 表达式**原样打印、不求值**（`renderConfigDump` 与 `applyEntryPatches` 共用 `entryListSchema`，见 `vendor\include\src\index.ts` 第 17–25 行；所以 dump 出来仍是一份可加载的 YAML）。
- **行准入是后续阶段**：被兼容策略拒绝的**插件行仍会出现在 dump 里**（函数的 JSDoc 原文：*"Row admission is a later stage: a plugin row the compatibility policy denies still appears here, while a denied bundle contributes no layer."*），但被拒的 **bundle 不贡献层**（见 §3.2 ⑤）。
- ⚠️ **dump 的行数不是常量**：它随 profile 里装了哪些 bundle、user patch 改了多少条目而变化，别把某个行数当成本课知识。

### 5.4 关于"打印出来的形状"：本笔记没有粘贴本机 dump

- dump 的**内容**由"你装了哪些 bundle + 你写了什么 patch"决定，**任何人的输出都不该被当作本课知识**；所以本笔记只讲生成规则，不粘"我的机器上长什么样"（R10）。
- 想让 `# ==` 出现，至少要有**两层**：单层（只有一个 bundle、没有 user patch、没有 home、没有 `--patch`）时所有行的 `patchedBy` 都为空，标签全等，于是整棵树只会有**一条** `# ==`（标注为推断：由 §5.2 的 `flush` 逻辑直接推得，我没有实跑单层与多层两种 dump 做对照）。
- **本笔记对 dump 的实测状态**：**未执行** `--dump-config`（原因见 §6 与 §8.4）；§5.1 / §5.2 的源码块逐行读过并核对过行号，§7 的 YAML 与注释是**仓库内公开文件**的摘录，任何人 clone 后都能看到同样的内容。

```yaml
# the criterion for host-plane ownership — injection resolves before any session
# exists, so there is no agent to key by. Behind a preset realm those variables
# would never reach the model's shell at all.
# （第 465–466 行：- id: tool-plugin-manager / disabled: true，与本例无关，此处省略）

- id: tool-bash
  disabled: true

- id: tool-pwsh
  disabled: true

# （第 474 行起：background-job REGISTRY 的一段长注释与后续行，与本例无关，此处省略）
```

按块讲解：

- **这是"层叠加"的最小可复现实例**：`- id: tool-bash` 只带一个 `disabled: true`，**没有 `name`、没有 `config`** —— 它既不新增条目，也不重述任何键，只把已有条目的**一个键**改掉（§4.1 ⑭ 的浅赋值）。patch 里"只写你要改的键"就是这套语义的直接用法。
- **`disabled: true` 覆盖掉的是一个表达式**：base 给 `tool-bash` 写的是 `disabled: !!js process.platform === 'win32'`（`packages\bundle\base\cordis.patch.yml` 第 267–269 行）。覆盖后该键的**值**变成常量 `true`，表达式连同它的求值时机一起被丢弃——**再次证明是整键替换**。
- **为什么 dump 里多出 `name` 字段**：patch 只改了 `disabled`，`name` 仍是 base 插入时那一行自带的（base 第 267–268 行写了 `name: '@deepseek-ai/dsh-tool-bash'`）；dump 打印的是**组装后的整行**，所以 `name` 出现在这里不代表 Web 层又写了一遍。
- **`# ==` 那一行怎么来的**：这两行的 `origin` 是 `@deepseek-ai/dsh-base`（它们由 base 的 `insert` 推进空根），`patchedBy` 是 `['@deepseek-ai/dsh-web-app']`（Web 层改了它们的 `disabled`），按 §5.2 ④ 拼成 `@deepseek-ai/dsh-base, patched by @deepseek-ai/dsh-web-app`。如果中间还有别的层也动过同一行，它会被逐个追加到这个逗号列表里。
- **注释里给出的"为什么用禁用而不是删除"是作者原文**（第 455–457 行）：
  > **Disabling rather than deleting is deliberate**: the base is shared, and a row absent from a surface overlay would silently reappear the day someone reorders the composition.

  → **理由的本质与本课的算法有关**：`patch` 只能"改已有行 / 追加新行"，**没有删除操作**；就算有，删除也只是"这一层看不见"，一旦有人调整了 `dsh.profile.bundles` 的顺序，被删的行会从更早的层里**重新长出来**。而 `disabled: true` 是一条**写在后面的显式覆盖**，顺序怎么调都还是它说了算——这正是"禁用"比"删除"稳的原因。
- **`shell-env` 那段注释为什么留着**：作者用"这个键留在 host plane"反衬"哪些行才该被表面层关掉"，属于同一层的判据说明；它本身不是本课知识点。

## 附录 A 关键问题与答案

> ✅ 九道题**全部给出明确答案**，不留空、不写"待补充"。Q1–Q5 是第一次读就该能答的；**Q6–Q9 涉及后续编才会展开的细节**（`!!js` 求值、兼容性预检、禁用与删除的取舍），**第一次读可以跳过**，回查时再看。

### Q1 组合顺序到底是什么？

→ 空数组 `[]`（根）→ 各 bundle 按 `dsh.profile.bundles` 顺序 → profile 的 `cordis.patch.yml` → `$DSH_HOME\cordis.patch.yml` → 各 `--patch`（按 argv 顺序）。**后出现的覆盖先出现的。**

### Q2 `--dump-config` 与 `--dump-default-config` 差哪一层？

→ 差 **profile + home + argv 三层**；而且 default 版本**根本不读这些文件**，所以它是 `cordis.patch.yml` 损坏时的诊断手段。

### Q3 patch 是替换整个 `config` 还是深合并？

→ **浅赋值覆盖**（`target[key] = value`）。`config` 作为整体被替换，**没有深合并**；只加一个字段也要重述完整 `config`。

### Q4 dump 里出现 `patch: entry ... not found` 是什么意思？

→ 该 patch 的 `id` 在**当前已组装的树里找不到对应条目**，于是被跳过并告警（**不中断**）。常见成因：目标条目所属的 bundle 被兼容策略拒绝（不贡献层），或 `id` 拼错。`insert` 带 `id` 时还会额外要求目标是 **group**。

### Q5 为什么 dump 里有几十条 `# ==`，明明只有两三个 bundle？

→ 因为它渲染的是**连续段**而不是层：逐层前缀快照 + 位置差分得到每行的 `origin` 与 `patchedBy`，只有两者都相同的**连续**行才会合并到同一条注释下。任何"改动点"都会把一段切成两段。

### Q6 home 层到底存不存在？

→ **存在**。定义在 `apps\cli\src\profile-boot.ts` 第 67–75 行（注释原文：*"applied **over every profile's own layer**"*），路径是 `join(resolveDshHome(), 'cordis.patch.yml')`；用 `loadOptionalPatches` 加载，**缺失时不贡献层、也不报错**（与 bundle / `--patch` 用的 `loadOverlayPatches` 不同——后者缺失会**抛错**）。

**为什么曾有"文档说有、注释里没有"的矛盾**——四处说法不一致：

| 位置 | 是否写了 home 层 |
|---|---|
| `docs\architecture.zh.md` 第 27 行 | ✅ 写了 |
| `apps\cli\src\dump-config.ts` 第 45 行 | ✅ 写了 |
| `packages\boot\app-boot\src\profile.ts` 头注释 | ❌ 只写到 "profile's own patches, then any launcher layers" |
| 生成的 `cordis.yml` 注释 | ❌ 只写到 "bundles, then cordis.patch.yml, then any --patch overlays" |

**判定依据（标注为判断）**：以**实际执行路径**为准——`dump-config.ts` 的 `collectConfigDumpLayers` 与 `profile-context.ts` 的 `readProfilePatches` 都明确包含 home 层。两处头注释是不完整的描述：它们描述的是"profile 内部能改的层"，而 home 层在 profile **之外**、叠加在**每个 profile 之上**。

### Q7 同一个 `id` 被多层改过，`disabled` 这种字段会"叠加"吗？

→ **不会。** 每次覆盖都是 `target[key] = value`（源码 `vendor\include\src\index.ts` 第 120–123 行），**整键替换**。实例：base 给 `tool-bash` 写的是 `disabled: !!js process.platform === 'win32'`（`packages\bundle\base\cordis.patch.yml` 第 267–269 行），Web 层写成常量 `disabled: true`（`packages\bundle\web-app\cordis.patch.yml` 第 468–470 行）——结果是 `true`，原来的平台表达式**不复存在**。`config` 同理：想让某个 `config` 多一个键，必须把该条目的 `config` **完整重写**。

### Q8 少写一个 `--patch` 的文件路径会怎样？home 级 patch 少写呢？

→ **`--patch` 的文件不存在 → 抛错、启动失败**（`loadOverlayPatches`，`packages\boot\app-boot\src\index.ts` 第 336–344 行，catch 里无条件 `throw`）。**home 级 patch 不存在 → 只是少一层，不报错**（`loadOptionalPatches`，同文件第 316–325 行，只有 `ENOENT` 返回 `undefined`）。判据是"这个文件是谁点名的"：调用方在命令行上点名了它 → 它必须存在；用户"可能没写"的那个 → 缺失就是正常状态。注意区分第三种情况：**文件存在但内容坏了 → 两种都抛错**。

### Q9 为什么作者用 `disabled: true` 而不是把行删掉？

→ 作者原文（`packages\bundle\web-app\cordis.patch.yml` 第 455–457 行）：

> **Disabling rather than deleting is deliberate**: the base is shared, and a row absent from a surface overlay would silently reappear the day someone reorders the composition.

机制上的理由（标注为推断，由 §4.1 的算法直接推得）：`applyEntryPatches` 只有"原地改写 / 尾部追加"两种动作，**没有删除操作**；即使有，也只是"这一层看不见"。一旦有人调整 `dsh.profile.bundles` 的顺序，被"删掉"的行会从更早的层里重新长出来；而 `disabled: true` 是一条写在后面的**显式覆盖**，顺序怎么调都由它说了算。
