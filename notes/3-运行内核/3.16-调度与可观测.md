## 0. 怎么读这一课（先看这段）

### 0.1 这一课是什么、不是什么

**是**：三条链路各自的**触发路径**与**数据归宿**——定时任务怎么"叫醒" agent、统计的 8 个数字从哪折叠出来、遥测记录怎么出站。

**不是**：

| 不做的事 | 属于哪一课 |
|---|---|
| cordis 的 `Service` 注册、`effect` 作用域、waterfall 的 `next()` 叠加规则 | `2.2` / `2.4` |
| 存储 domain / table 的持久化语义与配置校验 | `1.4` / `2.6` |
| 投影 seam 的 cell、快照、`asOfSeq` 的完整设计 | `3.3` |
| 收件箱、轮次与步骤的驱动 | `3.5` |
| OTLP 传输与 OTel SDK 内部实现 | 第四编 |

### 0.2 现在只要记住这 5 件事

1. **「调度」不执行模型**：到期后它只做三件事——解析原会话拿到 agent、`followup()` 一条普通 `user` 消息（来源标成 `schedule`）、`sessions.flush()` 确认落盘。消息进了收件箱，**模型由 agent loop 在下一轮自己领走**。
2. **触发条件是两条同时成立**：`status === 'active'` **且** `Date.parse(scheduledAt) <= now`。不是"有 timer 就一定会跑"。
3. **「统计」是一个投影单元**（`sessionStats`）：对**已提交**的会话事件做纯折叠，产出 8 个数字；它给**客户端**读，不给模型、也不给运维告警。
4. **「遥测」是日志的出站副本**：一条权威会话事件 → 一条 `ledger` 记录；**捕获**在 `session-telemetry`，批处理/重试/队列/丢失策略全在**后端**（随发行版是 `session-telemetry-otel`，走 OTLP/HTTP）。
5. **两者与会话日志的关系正好相反**：统计是日志的**派生读模型**（可丢弃、可重建，"持久的那份是缓存快捷方式，永不是权威"）；遥测是日志的**镜像副本**（单向出站、**从不回写**）。两者都**不是**第二份权威日志。

### 0.3 明确授权：下面这些现在**不用管**

- `ctx.storageDomain.open(...)`、`domainTable(...)`、任务行的 schema 细节（`1.4` / `2.6`）——**第一次读**只要记住"任务行是宿主的一份持久数据，和会话日志是两套存储"就够了；
- `ctx.effect(...)`、`Service` 重复注册即抛错、waterfall 的 `next()` 怎么叠加（`2.2` / `2.4`）——本课只在"注册即 effect""脱敏是一个 waterfall"两处点到它们；
- 投影注册表的 cell 懒建、`asOfSeq` 水位、变更流的 `Object.is` 门禁（`3.3`）——本课只看"事件进来 → 折叠 → 变没变"这三步；
- OTel SDK 的 `BatchLogRecordProcessorOptions` 每个字段、OTLP 协议本身的编码（第四编）。

**判断标准只有一条**：只要你能说清"这个细节属于'**塞消息** / **折叠** / **出站**'三条链路里的哪一条"，就够了。

## 1. 最小词汇表（本课新增的 6 个词）

这 6 个词是读后面三章的地基。**先用大白话建立直觉，不要追问它们的实现。**

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **schedule 定时任务** | 宿主记下的一条"到点要提醒某个会话"的**行**（不是"进程里的闹钟"） | 任务行 `ScheduleTask`，存在 `schedule` domain 的 `tasks` 表里 |
| **drive 驱动** | 宿主的一次"看看到点了没、该提醒就提醒"的**过程** | `ScheduleRuntime.drive()`；由 `requestDrive()` 请求 |

### 2.2 大白话版：一条提醒从建立到被领走

**完全不用上面的术语**（来源：`packages\schedule\schedule\src\runtime.ts` 第 85–164 行与 `docs\subsystems\schedule.zh.md` 第 432–438 行「宿主投递」一节；这里是白话转述，细节在 §3）。

1. 模型调用一个工具，说"1 小时后提醒我这个会话做某事"；宿主把这句话**存成一行**（含会话 id、要提醒的内容、计划时间、状态 `active`）。
2. 存完立刻"敲一下"宿主的定时器：重新算一遍最近的目标时刻。
3. 宿主只维护**一个**定时器，指向"所有 `active` 任务里最早的那个目标"。
4. 到点了，宿主把**当前已经到期**的任务挑出来（`active` 且计划时间 ≤ 现在）。
5. 它按会话把到期任务分组：同一会话的多个重复任务**合成一条消息**。
6. 它拿会话 id 去恢复/接管那个会话，拿到它的 agent。
7. 它拼出提醒文本（固定开头 + 动态字段的 JSON），**当作一条普通的用户消息**投进该 agent 的收件箱，来源标记为 `schedule`。
8. 这条消息进收件箱的同时，被记成一条**持久的会话事件**（"收件箱被拼接了"）。
9. 它调用一次"确认落盘"（flush）；**只有确认成功，才回头更新那行任务**：记一次投递、一次性任务转为 `inactive`、重复任务推进到下一次。
10. **到此为止，没有任何模型请求被发出。** agent 的循环在下一轮自己看到收件箱里有东西，才开始执行。
11. 如果第 6–9 步里任何一步失败，只记一条警告，那行任务保持原样，等下一次管理变更或宿主重启再试。

### 2.3 大白话版：统计条上的数字从哪来

**完全不用上面的术语**（来源：`packages\session\session-stats\src\projection.ts` 第 1–24 行模块注释、第 130–198 行折叠实现；`packages\session\session-stats\README.zh.md` 第 66–68、81–86 行）。

1. 会话每追加一条事件，都会被送进这台"折叠机"。
2. 看到"一个步开始了"，它记下起始时刻，开一个暂存格。
3. 看到"模型流里出现第一个非空片段"，它把首 token 时刻写进暂存格（步内重试后仍保留）。
4. 看到"这一轮的消息组装好了"，它结算：模型墙钟 = 现在 − 步开始；有首 token 就再记首 token 延迟；**同时有合法用量报告**才记解码时长与输出 token；然后**关掉暂存格**。
5. 看到"工具被调用"，它按调用 id 记下时刻；看到"工具结果回来"，配对结算工具墙钟（用"自有键"判断，避免把原型上的名字当成记录）。
6. 看到"一个步结束了"，它把步数 +1；如果这是**新轮次**的第一个已结束步，轮次数也 +1。
7. 看到"轮次结束"，它丢掉没配上的工具调用。
8. 它对外只暴露 **8 个数字**；这份数字由投影 seam 交给客户端（随发行版是 Web 聊天统计条）。
9. 这份数字**不给模型**：它不向提示词写任何东西。

### 2.4 大白话版：一条遥测记录的一生

**完全不用上面的术语**（来源：`packages\session\session-telemetry\src\index.ts` 第 1–15 行的模块注释与 `coordinator.ts` 第 179–213 行；`docs\subsystems\session-telemetry.zh.md` 第 60 行）。

1. 一条权威会话事件被提交了（比如 `assistant/message`）。
2. 捕获侧把它的"信封"（不含数据）和"数据"各深拷贝一份，包成一条**逻辑记录**：来源事件、通道（`ledger`）、时间、严重级、身份属性、载荷。
3. 这条记录先过一道**脱敏关卡**：部署挂了规则就按规则改，没挂就原样通过；规则抛错 → **扣下这一条**（fail-closed），但**只影响导出副本，权威日志永不改写**。
4. 通过后端接口 `emit()` 交给后端（契约要求：**必须是非阻塞入队**）。
5. 后端把它组装回"事件 + 严重级 + 属性"，交给传输层。
6. 传输层按**字节上限 / 条数上限 / 定时**批量，队列满了或单条超限就拒收并报告（**不截断内容**），同一时刻只允许一个请求在飞。
7. 通过 OTLP/HTTP 发出去；**只有显式用户反馈才授权捕获**，所以默认状态下第 1 步不会发生。

## 3. 调度（schedule）：模型建任务 → 收件箱多一条消息

### 3.1 结论与整条链路

**① 「调度」不是新机制，是"往收件箱塞一条消息"**：`ScheduleRuntime` 到期后只做三件事——解析原会话拿到 Agent、`followup()` 一条普通 `user` 消息（来源标成 `schedule`）、`sessions.flush()` 确认落盘。**它不触发模型执行**：消息被 append 成持久事件 `agent/inbox/spliced`，模型由 agent loop 在下一轮自己领走。

| 环节 | 做了什么 | 出处 |
|---|---|---|
| 模型建任务 | `schedule_create` / `list` / `update` / `delete` 四个工具，每次调用都作用于**调用方 Agent 的会话** | `packages\schedule\tool-schedule\src\index.ts` 第 435–437、445–481 行 |
| 工具落在哪个 Agent 上 | 工具在**挂载作用域**注册（preset 决定谁拿到），委派子代理调用一律拒绝 | 同文件第 227–230 行；`packages\bundle\web-app\presets\standard.patch.yml` 第 36–37 行 |
| 持久化任务 | `ScheduleService.create()` 写入 `schedule` domain 的 `tasks` 表：`{sessionId, record, status:'active', deliveryHistory}` | `packages\schedule\schedule\src\index.ts` 第 251–262 行；`storage.ts` 第 37–59 行 |
| 起 timer | `create` / `delete` / `update` 提交后都调 `runtime.requestDrive()`（**提交后、通知后**） | `index.ts` 第 260、336、371 行 |
| 选下一个到期点 | 扫全部任务，取 `active` 且 `scheduledAt <= now` 的；再把剩余 active 里最小目标设为 `setTimeout`（上限 `MAX_TIMER_DELAY_MS = 2_147_483_647`，`unref()`） | `runtime.ts` 第 90、155–164 行、第 16–17 行 |
| 解析原会话 | `ctx.sessionController.resolveAgent(task.sessionId)`——**冷会话在这里被恢复** | `runtime.ts` 第 101 行；`packages\api\session-controller\src\agent.ts` 第 170–172、183–204 行 |
| 投递 | `createUserMessage({content:[{type:'text',text}], source:{kind:'schedule'}})` → `resolved.agent.followup(message)` → `await ctx.sessions.flush(resolved.agent.session)`，flush 返回假就抛错 | `runtime.ts` 第 119–126 行 |
| 消息真的进了日志 | `followup` 走收件箱的 splice，**同步 append** 持久事件 `agent/inbox/spliced` | `packages\core\agent-loop\src\inbox.ts` 第 227–235 行；`packages\schedule\schedule\tests\delivery.spec.ts` 第 10–61 行 |
| 记账 | flush 成功后一次任务行 put：`lastDelivery` + 追加 `deliveryHistory.records`（含指令快照）+ 一次性任务转 `inactive` 或重复任务推进下一目标 | `runtime.ts` 第 127–142 行；`delivery-history.ts` 第 31–50 行 |

**模型看到什么**：一次性任务用 `renderReminderFraming`，重复任务用 `renderRecurringReminderBatchFraming`，两者共享固定来源行 `This is a scheduled message from the user`，动态字段一律走 `JSON.stringify`。**同一会话同一轮的多个重复任务合成一条消息**（`runtime.ts` 第 94–97、114–118 行）。

**串行与合并**：`ScheduleRuntime` 全程活在 `ctx.agents.withoutInitiator(...)` 里，即**不继承**任何创建者 Agent 的归因；`requested` / `running` 两个标志把并发唤醒合并成一次驱动。管理写入与投递写入**共用一条 FIFO**。

**时钟回拨是显式处理的**：选批次时会用解析后的**当前**时间重新过滤成员，未来成员不进本批、且保留定时义务（`runtime.ts` 第 104–108、143–152 行）。

### 3.2 源码：驱动入口——到期筛选、解析会话、回拨守卫

`packages\schedule\schedule\src\runtime.ts` 第 85–108 行

```ts
  private async drive(): Promise<void> {
    this.clearTimer()
    const failed = new Set<string>()
    const handled = new Set<string>()
    const scanNow = Date.now()
    const due = this.tasks().filter(task => task.status === 'active' && Date.parse(task.record.scheduledAt) <= scanNow)
    for (const task of due) {
      if (this.stopping) return
      if (handled.has(task.record.id)) continue
      const group = isRecurringScheduleRecord(task.record)
        ? due.filter(candidate => candidate.sessionId === task.sessionId && isRecurringScheduleRecord(candidate.record))
        : [task]
      for (const member of group) handled.add(member.record.id)
      let admitted = group
      const committed = new Set<ScheduleTask['record']['id']>()
      try {
        const resolved = await this.ctx.sessionController.resolveAgent(task.sessionId)
        if ('error' in resolved) throw resolved.error
        // oxlint-disable-next-line typescript/no-unnecessary-condition -- Disposal can run while Session restoration is awaited.
        if (this.stopping) return
        const now = Date.now()
        // Session restoration can span a wall-clock rollback; future members keep their timer obligation.
        admitted = group.filter(member => Date.parse(member.record.scheduledAt) <= now)
        if (admitted.length === 0) continue
```

按块讲解：

- **做什么**：这是宿主定时器每次被唤醒时的第一步——把"该提醒谁"挑出来，然后逐个会话解析出 Agent。
- **与哪个知识点相关**：§0.2 第 2 条（**触发条件是两条同时成立**）的落点就是第 90 行那个 `filter`：`status === 'active'` 且 `Date.parse(scheduledAt) <= scanNow`。它同时解释了 §3.1 的两处易错点——**`inactive` 任务不排程**（可查询、不再触发）、**没到期不解析会话**。

### 3.7 源码：`followup` 到底做了什么（两步：进队 + 记账）

第一步——`followup` 本身只是一次 `send`：

    // Waking input cannot join an aborted activity, so it starts the next turn.
    // Captured before the insertion so a reentrant cancel from a splice observer cannot reclassify it.
    const wakingAfterAbort = wakeup && this.phase.kind !== 'idle' && this.phase.abort.signal.aborted

    this.inbox.splice(resolvedTarget, Infinity, 0, [message])
    if (wakeup) this.wakeDriver(wakingAfterAbort)
  }

  followup(input: UserMessage): void {
    this.send(input, 'next-turn', true)
  }

  steer(input: UserMessage): void {

  }

## 4. 统计（session-stats）：一个单元、八个数字、一份可丢缓存

### 4.1 结论

**② 「统计」是纯折叠，不是埋点**：`session-stats` 只注册一个投影单元 `sessionStats`，对已提交的会话事件做 `apply`；视图是 **8 个数字**（`turns` / `steps` / `llmMs` / `toolMs` / `ttftMs` / `ttftSteps` / `decodeMs` / `decodeTokens`）。**给客户端用**：Web 聊天统计条 `useProjection('sessionStats')`。

| 事件 | 作用 |
|---|---|
| `step/start` | 开一个边界 `openStep{turn, step, startTime, firstTokenTime: null}` |
| `assistant/attempt` | 从流里取首个非空 delta 记 `firstTokenTime`（步内 `llm/retry` 后仍保留） |
| `assistant/message` | 记 `llmMs += time - startTime`；有首 token 则记 `ttftMs/ttftSteps`；有合法 usage 再记 `decodeMs/decodeTokens`，并**关掉边界** |
| `tool/call` | `pendingCalls[callId] = time` |
| `tool/result` | 按 callId 配对累加 `toolMs`（用 `Object.hasOwn`，避免原型名污染） |
| `step/end` | `steps += 1`；`turn` 与 `lastTurn` 不同才 `turns += 1` |
| `turn/end` | 丢掉未配对的 `pendingCalls` |
| 其它 | 返回**同一引用**（`Object.is` 门禁，变更流不动） |

**为什么以 `step/end` 为计数权威**：loop 对每个进入的步在 `finally` 里恰好追加一条，完成/失败/取消/max-tokens 全都落地一条。作者原文（`projection.ts` 第 6–11 行）：*"`step/end` — not `assistant/message` — is the counted step event because it is the step lifecycle authority … Counting assembled assistant messages instead would overcount max-tokens usage-host messages … and undercount cancelled steps."*

    for (const registration of this.registrations.values()) {
      let cell = registration.cells.get(session)
      if (cell !== undefined && cell.observedSeq >= event.seq) continue
      if (cell === undefined) {

        // index, so the prefix slice is exact), then take the normal gate.

          }

        }

## 5. 遥测（session-telemetry）：捕获侧与导出侧

### 5.1 结论

**③ 「遥测」捕获与导出分家**：`session-telemetry` 只负责**捕获**——把每条权威会话事件深拷贝成一条 `SessionTelemetryRecord`（外加两条没有日志归宿的 `ops` 记录），交给 `emit()`；**批处理、重试、队列、丢失策略全归后端**。随发行版交付的后端是 `session-telemetry-otel`，走 OTLP/HTTP 到 collector。

作者在模块注释里把这条边界写成了硬约束（`packages\session\session-telemetry\src\index.ts` 第 9–11 行）：

> *"Everything downstream of `SessionTelemetryBackend.emit` — batching, retry, queueing, and loss policy — is the backend's responsibility and is deliberately not modelled here."*

### 5.2 源码：出站词汇表只有一种记录

  /** Canonical envelope without data; body carries the separately redacted payload. Absent for operational records. */
  sourceEvent?: { sessionId: SessionId; envelope: Omit<SessionEvent, 'data'> }
  /** Ledger (session-log mirror) or ops (operational signal) channel; backends keep the two under separate instrumentation scopes. */
  channel: 'ledger' | 'ops'
  /** Unix epoch milliseconds — the source event's append time for ledger records, the emission time for ops records. */
  time: number
  /** Pre-mapped alerting severity; see {@link SessionTelemetrySeverity}. */
  severity: SessionTelemetrySeverity

   * Identity attributes, deliberately minimal: ledger records carry
   * `session.id`, `session.format_version`, `event.type`, `event.seq`, plus optional
   * `session.cwd` / `session.parent_id`; a seeded Session also carries
   * `session.seed_length` from its exact inherited event count;
   * ops records carry `telemetry.op`, `session.id`, and (for `agent-error`)
   * `agent.id`, `turn`, `step`, `error.name`. Anything recoverable from the
   * body is intentionally NOT duplicated here.
   */
  attributes: Record<string, string | number>
  /**
   * The complete payload: a deep copy of the session event's `data` for
   * ledger records (JSON-serializable by `Session.append`'s own
   * validation), or the op payload for ops records. Never mutated after
   * handoff.
   */

按块讲解：

- **做什么**：定义"抓取侧能交给后端的唯一一种东西"。
- **与哪个知识点相关**：§0.2 第 4 条（一条权威事件 → 一条 `ledger` 记录）。
- **字段怎么分工**（README 与文档的口径，源码注释即出处）：`sourceEvent` 是**不含 data 的信封**（`ledger` 独有；`ops` 刻意不带，免得被误认成日志行）；`channel` 区分两族；`time` 在 `ledger` 上是**源事件的 append 时间**、在 `ops` 上是**发出时间**；`severity` 是**捕获时就预映射好**的告警级别；`attributes` 刻意最小化——**能从 `body` 恢复的东西一概不重复**；`body` 是深拷贝，**交接后不再改动**。
- **为什么 `ops` 不带 seq 类标识**：接口注释（第 61–63 行）写明——`ops` 记录"deliberately omit `event.seq`-style identity so they can never be mistaken for ledger rows"，所以接收端可以对 `ledger` 按序去重，而**容忍 `ops` 重复**。

### 5.3 源码：一条事件 → 一条记录 → 脱敏 → 交接

  private captureEvent(session: Session, event: SessionEvent): void {
    const { data, ...envelope } = event
    this.deliver(session, {
      record: this.redact({
        sourceEvent: { sessionId: session.id, envelope: structuredClone(envelope) },
        channel: 'ledger',
        time: event.time,
        severity: severityOf(event),
        attributes: identityOf(session, event),
        // The canonical event object is mutable and the backend serializes
        // later; append-time validation guarantees this clone cannot throw.
        body: structuredClone(data),
      }),
      seq: event.seq,
    })
  }

  /**
   * Run the `session-telemetry/record` waterfall at capture time. The innermost `next`
   * passes the record through unchanged — this package ships no rules; exported
   * data is as clean as the listeners a deployment mounts. Callers run inside
   * {@link contain}, so a throwing rule withholds the record instead of
   * reaching the loop (fail-closed). On-demand capture invokes this waterfall
   * while reading the canonical session log, not when the event was appended.
   */
  private redact(record: SessionTelemetryRecord): SessionTelemetryRecord {
    return this.ctx.waterfall('session-telemetry/record', record, () => record)
  }

  /** Hand one redacted record to the backend, then advance its ledger cursor. */
  private deliver(session: Session, pending: PendingRecord): void {
    this.backend.emit(pending.record)
    if (pending.seq !== undefined) handoffCursor.set(session, pending.seq)
  }

按块讲解：

- **做什么**：把一条会话事件变成一条记录、过脱敏、交给后端，并推进交接游标。
- **与哪个知识点相关**：§0.2 第 4 条、§2.4 的第 2–4 步，以及"**脱敏只作用于导出副本，权威日志永不改写**"。
- **`envelope` 与 `data` 从哪来**：`const { data, ...envelope } = event` 一行把事件拆成两半——**信封不含 data**，`data` 单独深拷贝进 `body`。两次 `structuredClone` 的理由就写在注释里：**权威事件对象是可变的，而后端稍后才序列化它**；深拷贝把"稍后"这段窗口封住。
- **脱敏为什么是一个 waterfall，且本包不带规则**：`redact` 的实现只有一行 `ctx.waterfall('session-telemetry/record', record, () => record)`——**最内层的 `next()` 原样返回**，所以"导出的数据有多干净，取决于部署挂了多少规则"。规则抛错时，调用点外面的 `contain`（第 246–252 行）把它变成一条警告，**这一条记录被扣下**（fail-closed），且**绝不进 agent loop**。
- **游标为什么在 `deliver` 里推进**：`handoffCursor` 是**模块级** `WeakMap<Session, SessionSeqCursor>`（第 47–58 行），作者称它是"**注册即副作用**"纪律的一处**显式例外**——cordis 没有 HMR 状态交接 API，而用 `Session` 对象做键是唯一能让"重新收养的 fiber 从游标继续、而不是重发历史"的进程内生命周期。**游标标的是"已交接"，不是"已送达"**。

按块讲解：

- **做什么**：装配"按需捕获"的协调器，并把两条**授权入口**接上：权威的 `feedback/record` 事件，以及 `feedback/committed`。
- **与哪个知识点相关**：§0.2 第 4 条与 §5.6 的"默认不上传"——**没有反馈就没有授权，持续监听根本不存在**（协调器的 `capture: 'on-demand'` 表示不注册 firehose 监听）。
- **私有 sink 与公共服务分离**：`enqueue` 只挂在**私有** `backend` 上交给协调器；而类对外的 `emit(_record)` 是**空实现**（第 250 行）。作者在 Agent Note 里给的理由是结构性保证：*"私有后端能力使授权成为结构性保证，并确保公共服务在整个回放过程中保持关闭"*（`.agents\notes\archived\feature\2026-08-05-feedback-gated-session-telemetry.zh.md` 第 30 行）。
- **`record.sourceEvent === undefined` 的分支**：`ops` 记录没有 `sourceEvent`，**一律不上传**（`enqueue` 需要它来定位会话）；此外如果脱敏规则把 `sourceEvent` 删掉，也走这条路：**警告 + 丢**（第 203–206 行）。
- **`session.eventAt(event.seq) !== event` 这道守卫**：只有**权威日志里那一个对象**才能授权它之前的前缀出站；不是同一个对象（回放、伪造、非权威广播）就警告并丢弃（常量 `NON_CANONICAL_EVENT_WARNING` 在第 42 行）。
- **`isFeedback` 的判据**（第 45–53 行）：`feedback/record` 一律算，`feedback/message-put` / `feedback/message-delete` 要求 `event.data.sessionId === session.id`；并且**`event.seq < session.inheritedEventCount` 的继承前缀不算**——"fork 种子不授权"。
- **`emit` 的守卫与 `reportSessionLog` 的装配**：`SEVERITY` 映射把三档 `info/warn/error` 换成 OTel 严重级数字（第 131–135 行）。

### 5.5 源码：批处理、队列与字节上限

`packages\telemetry\otel\src\session-log.ts` 第 83–111 行

```ts
  onEmit(record: ReadableLogRecord): void {
    if (this.stopped) return
    if (this.queue.length >= this.config.maxQueueSize) {
      this.warn('Session log queue is full; record rejected')
      return
    }
    let bytes: number
    try {
      const serialized = JsonLogsSerializer.serializeRequest([record])
      if (serialized === undefined) throw new Error('Session log serialization produced no request')
      bytes = serialized.byteLength
    } catch (error) {
      this.warn('Session log serialization failed; record rejected', error instanceof Error ? error : new Error(String(error)))
      return
    }
    if (bytes > this.limit) {
      this.warn('Session log record rejected; content was not truncated', new Error(`Session log record exceeds maxRequestBytes: ${bytes} > ${this.limit}`))
      return
    }
    this.queue.push({ record, bytes })
    this.bytes += bytes
    if (this.active !== undefined) return
    if (this.queue.length >= this.config.maxExportBatchSize || this.bytes >= this.limit) {
      void this.forceFlush()
    } else if (this.timer === undefined) {
      this.timer = setTimeout(() => { void this.forceFlush() }, this.config.scheduledDelayMillis)
      this.timer.unref()
    }
  }
```

按块讲解：

- **做什么**：入队前做三重把关（停止 / 队列满 / 单条超限），然后决定"立刻发"还是"定时发"。
- **与哪个知识点相关**：§0.2 第 4 条的"批处理、队列、丢失策略在后端"，以及 §2.4 第 6 步。
- **"拒绝"而不是"截断"**：第 98–101 行的警告文案就是设计声明——*"content was not truncated"*。**超限的单条记录被丢弃，不会把内容切一半发出去**。
- **"同时只有一个请求在飞"**：第 104 行 `if (this.active !== undefined) return` —— 已有请求在跑时只入队、不再触发；`drain()`（第 122–141 行）一次只切出一批（按 `maxExportBatchSize` 与字节预算），发完 `await this.exporter.forceFlush()` 才继续。
- **`unref()`**：定时 drain 的 timer 同样不阻止进程退出。
- **队列上限与批量上限从哪来**：默认 `maxQueueSize: 2048` / `maxExportBatchSize: 512` / `scheduledDelayMillis: 1000` / `exportTimeoutMillis: 30000`（`SessionLogReporter` 构造函数第 188–193 行）；校验在 `resolveSessionLogLimits`（第 50–65 行，**批量不能大于队列**、单请求上限不超过 `4_000_000` 字节）。生产组合另外把 `scheduledDelayMillis` 调成 10000、`maxExportBatchSize` 调成 2048（§5.6）。

> ✅ 六道题**全部给出明确答案**，不留空、不写"待补充"。Q1–Q4 就是 `LEARNING-ROADMAP.md` 里 3.16 的验收问题与初版四问；**Q3 中"脱敏 waterfall 的叠加规则"与 Q6 中"历史设计为何变了"两处细节依赖第二编/归档记录，第一次读只看结论即可**（题内已标注）。

### Q1 定时/延迟任务如何触发 agent（走哪条路径）？

**答：不直接触发。路径是 `timer → drive() → sessionController.resolveAgent → agent.followup(普通 user 消息) → sessions.flush() → 任务行记账`，模型执行由 agent loop 在下一轮自行从收件箱领走。**

逐段依据：

1. **timer 从哪来**：初始化时 `runtime.requestDrive()` 起一次（`index.ts` 第 163 行），之后每次管理变更（`create` / `delete` / `update` / 归档停止）再请求一次（第 260、336、371、457 行）；`drive()` 结尾按剩余 `active` 任务的最小目标重设**唯一**一个 timer，并 `unref()`（`runtime.ts` 第 155–164 行）。
2. **哪些任务会被驱动**：`status === 'active'` 且 `Date.parse(scheduledAt) <= now`（`runtime.ts` 第 90 行）；`inactive` 任务可被查询但不再排程（`docs\subsystems\schedule.zh.md` 第 434 行）。
3. **冷会话怎么办**：`ctx.sessionController.resolveAgent(sessionId)` 会恢复/接管原会话；返回的 `{error}` 会被转成异常，进入失败分支（`runtime.ts` 第 101–102 行；`agent.ts` 第 170–172、183–204 行）。
4. **投递动作**：构造 `source:{kind:'schedule'}` 的 user 消息 → `followup()`；作者注释写明"followup 同步 splice 收件箱，早于 flush 观察会话"（`runtime.ts` 第 119–124 行）。
5. **为什么要 flush**：`ctx.sessions.flush()` 返回假就报 `Session persistence did not acknowledge the reminder`；`ScheduleService` 把 `sessionPersistence` 声明为**加载顺序要求**而不是直接调用的服务——只有注册了 `session/flush` 监听器的持久化后端才会让它返回真（`runtime.ts` 第 124–125 行；`index.ts` 第 91–100 行）。
6. **失败不自动重试**：解析/入队/flush 失败只 `logger.warn`，任务保持原样，等下一次管理变更或宿主重启再试；同一个 drive 里已成功提交的任务照常参与下一次定时计算（`runtime.ts` 第 143–152 行；作者 JSDoc 原文在第 40–43 行）。
7. **重复任务只补最近一次**：批内用 `resolveRecurringOccurrence(record, now)` 取最新发生时点并算出 `nextScheduledAt`；没有下一个目标就转 `inactive`（`runtime.ts` 第 109–142 行；算法本体在 `domain.ts`，本课未展开）。
8. **为什么不用 `withInitiator`**：驱动是"共享定时器"这类与某个 Agent 无关的进程本地工作，必须不继承创建者归因（`packages\core\agent\src\index.ts` 第 331–344 行；`packages\core\agent\README.zh.md` 第 113 行）。

**附带的两条边界**：① 委派子代理拥有的会话**从来收不到**投递，所以创建/改时间会以 `subagent_session` 拒绝，但**删除仍然允许**（`index.ts` 第 398–417 行；`tool-schedule\src\index.ts` 第 227–230 行）；② 收件箱已持久化但任务行尚未 put 时崩溃，会导致**重复投递**，跨存储没有原子性（`docs\subsystems\schedule.zh.md` 第 438 行）。

### Q2 统计（session-stats）记录了什么、给谁用？

**答：记录的是"整条持久日志口径"的 8 个数字——轮次数、已关闭步数、模型墙钟、工具墙钟、首 token 延迟与承载步数、解码墙钟与输出 token；给客户端读（随发行版的消费者是 Web 聊天统计条），不是给模型、也不是给运维告警。**

- 字段语义：`turns`（至少含一个已关闭步的不同轮次，被拒绝/空轮不计）、`steps`（`step/end` 条数，完成/失败/取消/max-tokens 全算）、`llmMs`（`step/start → assistant/message`）、`toolMs`（按 callId 配对的 `tool/call → tool/result`）、`ttftMs`/`ttftSteps`、`decodeMs`/`decodeTokens`（`packages\session\session-stats\src\types.ts` 第 22–39 行；README 字段表第 40–47 行）。
- **口径是"日志口径"不是"可见面口径"**：被压缩掉的消息所属的步仍然计入（`README.zh.md` 第 121 行）。
- **给谁**：客户端。读法是投影 seam 的快照 + 变更流：注册表订阅一次 `session/event`，每个已提交事件喂给每个单元的 `apply`，只有 `wire.view` 结果 `Object.is` 变化才推变更（`session-projection\src\index.ts` 第 220–222、657–703 行）。随发行版的界面消费者是聊天统计条，缺失该单元时整块回退到窗口折叠（`StatsPills.tsx` 第 53–84、156–164 行）。
- **给不给模型**：不给。README 的"模型体验"一节写明无面向模型内容、KV cache 无影响（第 104–110 行）。
- **持久吗**：数字本身来自内存折叠；投影缓存把单元**内部状态**节流写回 `session_projcache`，缓存行可因版本不符或越过日志末端被丢弃——它只是省一次重放的快捷方式（`session-projection\src\index.ts` 第 119–134 行；节流参数 `base\cordis.patch.yml` 第 182–186 行）。
- **能力可消失**：没有投影注册表时插件 fiber 挂起、不注册任何东西；卸载时键消失，调用方读作"能力缺失"（`session-stats\src\index.ts` 第 19–20 行；`README.zh.md` 第 53 行）。

### Q3 遥测记录什么、如何导出？

**答：记录"每条权威会话事件一条 `ledger` 记录"+"两条 `ops` 记录（`agent-error`、`shutdown`）"；导出由后端负责，随发行版后端把记录经 OTLP/HTTP 批量发到 collector，且只有显式用户反馈才授权捕获。**

| 字段 | `ledger` 记录 | `ops` 记录 |
|---|---|---|
| `sourceEvent` | 有：`{sessionId, envelope}`（envelope 不含 data） | 无（刻意，免得被误认成日志行） |
| `channel` | `'ledger'` | `'ops'` |
| `time` | 源事件的 append 时间 | 发出时间 |
| `severity` | `tool/result.isError`、`turn/end` 错误 → `error`，否则 `info` | `agent-error` 为 `error`；`shutdown` 为 `info` |
| `attributes` | `session.id` / `session.format_version` / `event.type` / `event.seq`（+可选 `session.cwd` / `parent_id` / `seed_length`） | `telemetry.op`、`session.id`（`agent-error` 另有 `agent.id` / `turn` / `step` / `error.name`） |
| `body` | 事件 `data` 的深拷贝 | 运维载荷 |

**如何捕获**：`live` 模式在捕获时刻深拷贝、脱敏、交接（`coordinator.ts` 第 92–124、180–195 行）；（随发行版的）OTel 后端选的是 `on-demand`——**不挂持续监听**，只有 `feedback/record` / `feedback/committed` 授权，并把它之前**尚未交接**的前缀整段读出来（`session-telemetry-otel\src\index.ts` 第 218–242 行；`coordinator.ts` 第 151–164 行）。交接位置由模块级 `handoffCursor` 记（`coordinator.ts` 第 47–58 行）。

> （第一次读可跳过这段细节）脱敏点是一个 **waterfall**，本包**不带任何规则**：`ctx.waterfall('session-telemetry/record', record, () => record)`；抛错的监听器会**扣下这一条**（fail-closed），且**只作用于导出副本**（`coordinator.ts` 第 197–207 行；`index.ts` 第 26–45 行）。waterfall 的叠加规则属第二编 2.4。

**如何导出**：记录先过脱敏 → `backend.emit()`（必须非阻塞）→ OTel 后端把它组装回 `{...envelope, data: body}` + `severityNumber` + `attributes` 交给 `reporter.reportSessionLog()` → `dsh-otel` 的处理器按字节/条数/定时批量、限制队列、单请求在飞 → OTLP/HTTP POST 到 `exporter.url`（`coordinator.ts` 第 197–213 行；`session-telemetry-otel\src\index.ts` 第 202–213 行；`session-log.ts` 第 83–141 行；`base\cordis.patch.yml` 第 204–218 行）。

**投递保证是尽力而为**：游标标"已交接"不标"已送达"，可能丢也可能重；去重键是 `(session.id, session.format_version, event.seq)`，`ops` 记录故意不去重（`docs\subsystems\session-telemetry.zh.md` 第 60 行）。**默认不上传**：模式默认 `FEEDBACK_ONLY`；`DISABLED` 不构造任何 SDK 状态、只对反馈事件发警告；`FULL` 在这个枚举里**不存在**，穿进配置会直接抛错（`session-telemetry-otel\src\index.ts` 第 32–39、56–65、155–162 行；`base\cordis.patch.yml` 第 191–207 行；`tests\otel.spec.ts` 第 727–736 行）。

### Q4 可观测性数据与会话日志是什么关系（派生还是独立）？

**答：两种不同关系，不能一句话概括——`sessionStats` 是会话日志的派生读模型（可以整块丢掉再算出来）；遥测是会话日志的出站镜像副本（一条对一条、单向、不回写）。二者都不是第二份权威日志。** 完整对照见 §6 那张表；依据是 `projection.ts` 第 130–198 行、`session-projection\src\index.ts` 第 119–134 行、`coordinator.ts` 第 180–213 行、`session-telemetry\src\index.ts` 第 36–44 行（"脱敏只作用于导出副本；权威会话日志永不改写"）、`docs\subsystems\session-telemetry.zh.md` 第 60 行。

**一句话判据**：问"这条数据丢了会怎样"——**能重放日志重建的**是派生（统计）；**丢了就只能容忍的**是镜像（遥测）。

### Q5 定时任务的触发条件到底是什么？哪些情况不会触发？

**答：两个条件同时成立才会被驱动——`status === 'active'` **且** `Date.parse(scheduledAt) <= now`**（`runtime.ts` 第 90 行）。下列情况**不会**触发或**不会**投递：

| 情况 | 结果 | 依据 |
|---|---|---|
| 任务已 `inactive`（一次性已投递、重复任务没有下一个目标） | 可查询，但不再排程 | `runtime.ts` 第 90、155 行；`docs\subsystems\schedule.zh.md` 第 434 行 |
| 目标时刻还没到 | 不解析会话、不投递；只把最近目标重设为 timer（超长会切段） | `runtime.ts` 第 155–164 行；`runtime.spec.ts` 第 66–72、299–308 行 |
| 会话恢复耗时跨越了墙钟回拨，成员又变回"未来" | 本批**不投递**，但成员**保留定时义务** | `runtime.ts` 第 104–108 行 |
| 会话属于委派子代理 | 投递**永远到不了**：创建/改时间直接以 `subagent_session` 拒绝 | `index.ts` 第 410–417 行；`tool-schedule\src\index.ts` 第 227–230 行 |
| 解析/入队/flush 失败 | 只记警告，**不自动重试**；等下一次管理变更或宿主重启 | `runtime.ts` 第 143–152 行 |
| 服务正在停止（`dispose`） | `drive()` 在几个检查点直接 `return`，不再投递 | `runtime.ts` 第 92、104、154 行 |

### Q6 遥测默认会上传吗？`FULL` 模式存在吗？

**答：默认不上传。** 发行版组合里的默认模式是 `FEEDBACK_ONLY`：**普通活动从不触发捕获**，只有显式用户反馈才释放该会话截至该反馈、且**尚未交接**的日志前缀（`base\cordis.patch.yml` 第 191–207 行；`session-telemetry-otel\src\index.ts` 第 218–242 行）。**`FULL` 在当前源码里不存在**：`SessionTelemetryMode` 只有 `FEEDBACK_ONLY` / `DISABLED` 两个值，未知值（含 `'FULL'`）在读取传输配置**之前**就被拒绝（第 33–39、56–65 行；`tests\otel.spec.ts` 第 727–736 行断言枚举恰为两项、`'FULL'` 不在其中）。

> （第一次读可跳过这段）**历史设计确实有过 `FULL`**：那份 Agent Note 描述了三个值、并把 `DISABLED` 当默认；它是 2026-09-04 **归档**的设计记录。**冲突时以源码为准**——完整对照见 §5.7。
