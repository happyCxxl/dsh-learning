## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：一个 step 内的一批 `tool-call` **怎么被分组、怎么被限流、结果怎么回到正确位置**这条完整链路，含 13 处就地源码与逐块讲解。
**不是**：工具注册表本身（`3.9`）、工具流水线内部的守卫与审批判定（`3.10`）、PTC 的编程模型（第四编）。这三样本课只在必要处点一下。

### 0.2 现在只要记住这 4 件事

1. **调度单位是一整个 step 的一批调用**，不是一次调用——`executeToolCalls()` 一次收下模型顺序的整批 `tool-call`，跑完才返回。
2. **先分组、后执行**：连续的「可并行」调用合成一组，每个「独占」调用**单独成一组**；**组间严格串行**，组内才并发。
3. **组内是"有界滚动池"**：上限是配置 `maxParallelToolCalls`（默认 `10`），**结算一个补一个**，不做固定分批。
4. **并发只发生在工具主体的派发上**：有序策略（pre-execute）、收尾（post-execute）、写进日志的结果，全部保持**模型顺序**。

### 0.3 明确授权：这些现在**不用管**

- `tools/pre-execute` / `tools/post-execute` / guard 内部的判定规则——属 `3.10`。本课只需要知道"它们是**有序**阶段，只有 `dispatch` 那一段会重叠"。
- `concludesTurn`、`additionalContexts`、`surfaceOp`、`sourceEventSeqs`、`deriveMessages()` 的完整语义——属 `3.3` / `3.8`。本课只按"提交点要做的四件事"讲它们**在调度器里的用法**。
- **PTC 模式下的并发**（`run_code` 内部自建的那套队列）——属第四编 `4.7`，已降级到**附录 B**，第一次读请跳过。
- 一元分类器为什么表达不了"资源相容"的完整论证——`3.9` 与本课 §5 Q1 各讲一半。

判断标准只有一条：**只要你能说清"这一步是在『分组 / 限流 / 提交 / 分类』里做哪一件事"，就够了。**

## 1. 最小词汇表（本课新增的 8 个词）

这 8 个词是理解后面一切的地基。**先用大白话建立直觉，不要追问实现。**

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **tool-call** | 模型在一条 assistant 消息里说"我要用某个工具"，一次请求算一个 | assistant 消息里 `type: 'tool-call'` 的 block |
| **`tool/call` / `tool/result`** | 日志里的一对事件：前者记"我开始跑它了"，后者记"它跑完了、结果是什么" | `session.append('tool/call', …)` / `session.append('tool/result', …)` |
| **execution mode（执行模式）** | 注册表给一条调用下的"能不能和兄弟一起跑"的判定 | `ctx.tools.executionMode(exec).kind` → `'parallel'` / `'exclusive'` |
| **exclusive（独占）** | 单独跑、绝不与任何兄弟重叠的那一类 | `{ kind: 'exclusive' }` |
| **barrier（屏障）** | 独占调用前后"必须等干净"的那道坎 | §4.2：它被切成「容量为 1 的组」 |
| **rolling pool（滚动池）** | 有上限、**结算一个补一个**的并发容器（不是固定分批的窗口） | §4.6 的 `fillPool` |
| **slot（槽位）** | 按下标定长的一个位置，一条调用占一个；结果先落这里，再统一提交 | `slots[index]` |
| **commit cursor（提交游标）** | 只跨越"连续的模型序槽位"的读指针 | §4.4 的 `committed` |

> ⚠️ `parallel` / `exclusive` 属于**工具注册表**的词汇体系（`3.9` 定义），`slot` / `commit cursor` 属于**本课才引入的调度器内部实现**。本课只用上面这个程度——注册表如何解析出定义、流水线内部各阶段的细节，**这里不答**。

## 2. 先建立画面

### 2.1 静态结构：一次 step 的调度形状

```
一个 step 里，模型按顺序要了 N 条 tool-call
        │
        │  executeToolCalls()：按模型顺序扫描，边扫边问注册表
        ▼
┌───────────────────────────────────────────────────────────┐
│ 组 1（parallel） 连续的"可并行"调用                          │
│   └─ 有界滚动池：最多 maxParallelToolCalls 个在途            │
│      启动 = 模型顺序 · 结算 = 先到先得 · 提交 = 模型顺序      │
├───────────────────────────────────────────────────────────┤
│ 组 2（exclusive）一条独占调用 = 容量为 1 的池 = 屏障          │
│      它开始前：组 1 必须整组提交完（含 post-execute）         │
│      它结束前：组 3 绝不会启动                              │
├───────────────────────────────────────────────────────────┤
│ 组 3（parallel）  ……                                        │
└───────────────────────────────────────────────────────────┘
        │
        ▼  每提交一条：追加 tool/result、交出 additionalContexts、聚合 concludesTurn
    返回 { concluded } 给 step
```

> 精确性说明（两处）：① 图里的"组"是**调度器临时切出来的**，不是持久数据结构——`runGroup` 返回后就没了；② `tool/call`、`tool/result` 画在组外，是因为它们**不是组的成员**，而是"提交"这个动作的副作用。

### 2.2 动态过程：三条并列调用各自什么时候跑

```
时间 →

组 1 [读A, 读B]                组 2 [写A]            组 3 [读C]
├─ 读A 启动                                    （写A 必须等组 1 整组提交完）
├─ 读B 启动                                     ├─ 写A 启动
├─ 读B 结算（先到先得）                          ├─ 写A 结算
├─ 读A 结算                                     ├─ 写A 提交（含 post-execute）
├─ 读A 提交 → tool/result                       └─→ 读C 才被允许启动
└─ 读B 提交 → tool/result
（提交顺序恒为 读A→读B，与谁先结算无关）
```

### 2.3 大白话版：模型同时要了 3 个工具，机器里发生了什么

**完全不用上面的术语**（来源：设计笔记 `第 33–41 行` 的例子与 `第 43–47 行` 的说明；这里只做白话转述，细节留到 §4）：

1. 模型这一轮一口气说了三件事："读 A""写 A""再读 A"。
2. 循环收下这三件事，**一件都还没动**，先问登记处："这条调用你能和别人一起跑吗？"
3. 从头往下走：第一件答"能"，第二件答"不能"，第三件答"能"。
4. 切法有两种：
   - 遇到答"能"的，就把它**并进当前这一堆**，继续往下；
   - 遇到答"不能"的，就让它**自己单独一堆**，作为一道坎。
5. 于是切成三堆：`[读A]`、`[写A]`、`[读A]`。**一堆一堆地跑，前一堆没结束，后一堆不会开工。**
6. 跑一堆时可以同时开工，上限是配置里的那个数字；**每跑完一个，就再补进来一个**，不做"一批跑完再开下一批"。
7. 但结果**不能按跑完的先后写进日志**——必须按模型原来的顺序摆回去。先跑完的只是先占住自己的位置。
8. 第二堆那道坎，要等第一堆**彻底**结束：不只是"工具跑完了"，还包括**收尾检查跑完、结果写进日志**。
9. 如果中途被取消，正在跑的会先结算并写进日志，**还没开工的会拿到一条合成的"取消前未派发"错误结果**——日志里每条调用都有配对结果，不会留下悬空的调用。

## 3. 结论先行

一句话：**一个 assistant step 里的一批 `tool-call`，先被切成「连续的 parallel 组」和「单个 exclusive 组」，组间严格串行，组内才用有界滚动池并行**（`packages/core/agent-loop/src/tool-calls.ts` 第 85–101 行、第 122–247 行）。

| 结论 | 要点 | 出处 |
|---|---|---|
| 调度单位 | 不是"一次调用"，而是 **一个 step 的整批调用**；`executeToolCalls()` 收下模型顺序的 `ToolCallBlock[]`，一次跑完 | tool-calls.ts 第 60–67 行；`packages/core/agent-loop/src/agent.ts` 第 532–537 行 |
| 分组依据 | 每条调用现问注册表 `ctx.tools.executionMode(exec).kind`；`parallel` → 尽可能长的连续组，`exclusive` → 单独一组 | tool-calls.ts 第 89–90 行；`packages/core/tools/src/index.ts` 第 1303–1312 行 |
| 独占屏障 | 独占调用**单独跑**，且它前面的调用必须全部提交完（含 post-execute 与 `tool/result` 追加）才轮到它；它完全结束后才启动后面的调用。解决的是**安全**问题，不是性能问题：一元分类器没法证明两个并列调用资源相容，所以"变更类"调用只能独占 | tool-calls.ts 第 90–93 行、第 147–161 行；设计笔记第 19–21、29 行 |
| 并行度 | `maxParallelToolCalls`：volatile 正整数，默认 `10`，**每个工具组开始时读一次**；池条件 `inFlight.size < maxParallelToolCalls` | `packages/core/agent-loop/src/constants.ts` 第 5–6 行；`packages/core/agent-loop/src/index.ts` 第 334–335 行；tool-calls.ts 第 132、200 行；README.zh.md 第 48、57 行 |
| 乱序回填 | 结果先落进**按下标定长的槽位数组** `slots[index]`，提交游标 `committed` 只跨越"连续的模型序槽位"；乱序完成不会插队 | tool-calls.ts 第 133–135、147–161、176 行 |
| 顺序归位到日志 | `tool/call` 按**启动顺序**追加（可能交错），`tool/result` 按**模型顺序**追加，并用 `sourceEventSeqs: [callSeq]` 指回各自那次 `tool/call` | tool-calls.ts 第 168、263–266、282–289 行 |
| 只有 body 重叠 | `tools/pre-execute` / `tools/post-execute` 保持模型顺序串行；只有 dispatch/工具主体并发 | 设计笔记（同上）第 45 行；tool-calls.ts 第 216–218 行注释 |
| fail-closed | 只有分类器**显式返回 `true`** 才并行；未声明、未知工具、参数非法、抛错、非布尔真值全部独占 | `packages/core/tools/src/index.ts` 第 1296–1312 行；`packages/core/tools/src/schema.ts` 第 625–630 行 |

**一处文档与源码的冲突（以源码为准）**：设计笔记第 51 行写"`run_code` 及其内部派发队列仍按**串行**方式执行"；但源码里 `run_code` 内部有一套**按 `maxParallelSubCalls`（默认 10）限制的并发队列**，其注释明确说它"遵循与原生循环相同的并发规则"（`packages/core/tools/src/ptc.ts` 第 418–432 行；旋钮定义在 `packages/core/tools/src/index.ts` 第 686–693、794–801、810–813 行）。判定依据：**源码是实际执行路径**，设计笔记那句写在 2026-07-10，早于该旋钮出现。细节见**附录 B**（第一次读请跳过）。

## 4. 机制与源码对照

本节 13 块源码，全部就地给出。每块上方标 `文件路径 第 A–B 行`，每块下方按"做什么 / 与哪个知识点相关 / 为什么这么写"讲解。

### 4.1 模块契约与三个中间类型

模块头注释把整个行为压缩成六句：独占调用形成屏障、并行调用走有界滚动池、启动前会**重新分类**；派发可以重叠，但策略、结果与结果上下文保持模型顺序；abort 或调度器内部故障会停止补充并排空已启动的调用；abort 为被跳过的调用记录**合成错误结果**以保证回放有效；**终态调度器故障**在排空后 reject，由属主 step 在收尾前记录保守的恢复结果（tool-calls.ts 第 1–12 行）。

三个中间类型是读实现的钥匙：

`packages/core/agent-loop/src/tool-calls.ts` 第 20–39 行

```ts
/** One tool call after argument parsing, ready to schedule. */
interface PlannedCall {
  block: ToolCallBlock
  exec: ToolExecutionInput
}

/** Settled dispatch awaiting model-order finalization. */
interface Slot {
  exec: ToolRunContext
  result: ToolExecutionResult
  needsPost: boolean
}

/** One scheduler group outcome, including a drained cancellation. */
interface GroupOutcome {
  consumed: number
  aborted: boolean
  /** Whether any committed result carried {@link ToolExecutionResult.concludesTurn}. */
  concluded: boolean
}
```

按块讲解：

- **`PlannedCall`**：一条**已解析参数、可以调度**的调用。`block` 是模型原始的那一块（提交日志时要用它的 `id` / `name` / `arguments` 原样文本）；`exec` 是注册表要的 `ToolExecutionInput`。**这一对分工很重要**：日志写的是 `block`，注册表跑的是 `exec`。
- **`Slot`**：**已结算但尚未按模型顺序定稿**的一次派发。`needsPost` 是后面 `commitReady` 走哪条路的分岔口——`true` → `finalize`（含 post-execute），`false` → `finish`（不含）。
- **`GroupOutcome`**：一个组的结局。`consumed` 告诉外层"这一轮吃掉了多少条下标"（正常是 `started`，abort 时是整组长度）；`aborted` 让外层立刻给更后面的调用补合成结果；`concluded` 表示本组有结果带 `concludesTurn`，最终作为 `executeToolCalls` 的返回值交给 step。
- 这三块都没被省略——它们加起来 20 行，正是本课后面每一块源码都要用到的词汇。

### 4.2 外层：分组循环（屏障就是"容量为 1 的组"）

`packages/core/agent-loop/src/tool-calls.ts` 第 83–102 行

```ts
  let next = 0
  let concluded = false
  while (next < planned.length) {
    // Commit before classifying again so registry changes affect unstarted calls.
    // oxlint-disable-next-line typescript/no-non-null-assertion -- bounded by the loop condition
    const first = planned[next]!
    const mode = ctx.tools.executionMode(first.exec).kind
    const group = mode === 'parallel' ? planned.slice(next) : [first]
    const outcome = await runGroup(
      ctx, turn, step, group, mode, signal, acceptContext,
    )
    next += outcome.consumed
    concluded ||= outcome.concluded
    if (outcome.aborted) {
      for (const call of planned.slice(next)) appendSkippedToolCall(session, turn, step, call.block)
      return { concluded }
    }
  }
  return { concluded }
}
```

按块讲解：

- **`planned` 从哪来**：同文件第 72–81 行 `const planned: PlannedCall[] = toolCalls.map(block => ({ block, exec: { callId, name, arguments: parseArguments(block.arguments), agent, signal } }))`。所以**参数只解析一次**、`exec` 只构造一次；`agent` 来自第 68 行 `ctx.agents.requireInitiator()`，`signal` 是这个 step 共用的取消信号。`next` 是本块自己声明的游标，起点 0。
- **第 86 行的注释就是"惰性分类"的理由**（作者原文）：*"Commit before classifying again so registry changes affect unstarted calls."* —— 每轮**先让上一组提交完**，再问下一条的模式，所以注册表在组中途被改动，会立刻影响**还没启动**的调用。
- **第 89–90 行是本课的"一句话机制"**：`parallel` 时**乐观地**把"剩下的全部"当一组（`planned.slice(next)`），真正的截断发生在池内部的重分类（§4.6）；`exclusive` 时组就是它自己（`[first]`）。
- **→ 屏障的实现方式就在这里**：屏障**不是一把锁**，而是"切出来的一个容量为 1 的组"。加上第 91–93 行的 `await`，独占组的前后调用都不可能与它重叠。
- **`await runGroup(...)` 返回才前进**（第 94 行 `next += outcome.consumed`）：正常路径下 `consumed === started === group.length`，所以游标正好跨过整组。
- **第 96–99 行是 abort 的收口**：本组已经 `aborted`，就为**外层还没轮到的**剩余调用逐条 `appendSkippedToolCall`，然后立刻返回，**不再启动任何新组**。守卫是 `if (outcome.aborted)`。
- **`concluded` 用 `||=` 逐组累积**（第 95 行）：只要任何一组提交过带 `concludesTurn` 的结果，返回给 step 的 `{ concluded }` 就是 `true`（第 101 行）。

### 4.3 内层：`runGroup` 的入参、状态与三个游标

`packages/core/agent-loop/src/tool-calls.ts` 第 122–144 行

```ts
async function runGroup(
  ctx: Context,
  turn: number,
  step: number,
  group: PlannedCall[],
  mode: ToolExecutionMode['kind'],
  signal: AbortSignal,
  acceptContext: (context: UserMessage) => void,
): Promise<GroupOutcome> {
  const { session } = ctx.agents.requireInitiator()
  const maxParallelToolCalls = ctx.agentLoop.config.maxParallelToolCalls.get()
  const slots: (Slot | undefined)[] = group.map(() => undefined)
  // Started slots retain their `tool/call` seq so the result can cite it.
  const callSeqs: Array<SessionSeq | undefined> = group.map(() => undefined)
  let nextToStart = 0
  let committed = 0
  let started = 0
  let aborted: boolean = signal.aborted
  let concluded = false
  let schedulerFailure: { error: unknown } | undefined
  const throwSchedulerFailure = (): void => {
    if (schedulerFailure !== undefined) throw schedulerFailure.error
  }
```

按块讲解：

- **函数契约（同文件第 113–121 行 JSDoc 原文，节选）**：*"Run one exclusive barrier or parallel pool. Later calls are reclassified before start; an exclusive reclassification waits for the current pool to drain and remains for the caller's next barrier."* —— 这三句就是本课的分组、重分类、屏障三件事。
- **`group` / `mode` 从哪来**：外层的第 90 行与第 89 行（§4.2）。`mode` 是**切组时**的模式，后面第 204–205 行的重分类会再问一次注册表。
- **`maxParallelToolCalls` 的读法**：`ctx.agentLoop.config.maxParallelToolCalls.get()` **在每次进入 `runGroup` 时读一次**（第 132 行）。这就是 README 第 57 行说的"在下一个工具组开始时读取的 volatile Config 字段"——**改配置不影响正在跑的组，只影响下一个组**。
- **`slots` 与 `callSeqs` 都是按下标定长**：`group.map(() => undefined)` 让"下标即身份"从天而降，不需要额外查表。`callSeqs` 的注释说明它的用途：*"Started slots retain their `tool/call` seq so the result can cite it."*
- **三个游标各自是什么**：`nextToStart`＝下一个要启动的；`committed`＝下一个可提交的；`started`＝已启动总数。**`nextToStart >= committed >= started` 不成立**——正确的不变关系是 `nextToStart >= started >= committed`（启动跑在提交前面）。
- **`aborted` 的初值是 `signal.aborted`**（第 139 行）：进组前就已经取消的组，一条都不会启动（§4.6 的 `while (!aborted …)` 直接不成立）。
- **`schedulerFailure` 是"一个格子"而不是"一个异常"**：`{ error }` 只会被 `??=` 赋第一次；`throwSchedulerFailure()` 是唯一的抛出点，被刻意放在每个 `await` 之后调用——**调度器故障是终态**，不会伪装成普通的 `ABORTED` 结果（设计笔记第 87 行）。

## 附录 A 关键问题与答案

> ✅ 四道题**全部给出明确答案**，不留空、不写"待补充"。Q1–Q3 第一次读就该能答；**Q4 的第 4 小点提到 PTC 与 Cordis 变更工具，属第四编，第一次读可跳过那一条**。

### Q1 工具调用的调度策略是什么？独占屏障解决什么问题？

**策略（三步）：**

1. **先分组、后执行。** 拿到一个 step 的全部 `tool-call` 后，按模型顺序扫描：从当前下标开始的**连续 `parallel`** 合成一组；遇到 `exclusive` 就把它单独成组。组之间严格串行，前一组 `await` 返回（含 post-execute 与结果提交）才进入下一组（tool-calls.ts 第 85–101 行）。
2. **组内用有界滚动池。** 并行组先按模型顺序启动到上限，之后"结算一个补一个"，不做固定窗口分批（tool-calls.ts 第 199–214、221–231 行；设计笔记第 43、91 行）。
3. **顺序只在两个地方强制**：启动是模型顺序（第 203–206 行），提交也是模型顺序（第 147–161 行）。中间的结果返回顺序随意——这就是"派发可重叠、策略与结果保持模型顺序"（第 3–5 行模块注释）。

**屏障解决什么：**

- **安全**：分类器是**一元**的——返回 `true` 只承诺"可以和任何同样返回 `true` 的弟兄重叠"，调度器**不做**成对比较、不证明资源相容（设计笔记第 19 行）。因此"安全性取决于并列调用之间关系"的调用（典型：同一路径的写入、依赖有序中间件状态的调用）无法用这个接口表达，只能独占（设计笔记第 21 行）。独占组容量为 1，天然排除了它与任何兄弟的重叠。
- **顺序**：独占调用必须看到它之前所有调用的**完整效果**，包括 post-execute 与 `tool/result` 落盘。因为它被单独成组并被 `await`（第 91–93 行），前置组不提交完就不会启动它；它不结束（含 post-execute）后面的组也不会启动。
- **它在消除的是"时序不确定性"，不是延迟**：把变更调用串进一个确定的位置，读类调用才敢在外围重叠。

### Q2 并行度如何限制？

- **配置**：`maxParallelToolCalls`，默认 `10`（`packages/core/agent-loop/src/constants.ts` 第 5–6 行），schema 为 `z.number().step(1).min(1).default(10).volatile()`——正整数，`0` 和 `1.5` 在插件加载期就被拒（`packages/core/agent-loop/src/index.ts` 第 334–335 行；拒绝行为见 `packages/core/agent-loop/tests/tool-calls.spec.ts` 第 274–277 行）。README 的字段表也写明"`1` 为串行"（README.zh.md 第 48 行）。
- **读取时机**：`runGroup` 每次进入时 `ctx.agentLoop.config.maxParallelToolCalls.get()` **读一次**（tool-calls.ts 第 132 行）。这正是 README 说的"在下一个工具组开始时读取的 volatile Config 字段"（README.zh.md 第 57 行）——改配置不影响正在跑的组，只影响下一个组。
- **限制点**：唯一的闸门是池条件 `inFlight.size < maxParallelToolCalls`（第 200 行）。
- **独占组 = 容量 1 的池**（第 90 行 `[first]`）。
- **范围**：上限约束的是**一个 agent、一个 step、一个组内的在途数量**；不同 agent 各有自己的批次、不共享计数，但共享同一个配置值（README.zh.md 第 48 行；设计笔记第 61 行）。同一 step 内不同组之间天然串行，所以不存在跨组的并发叠加。
- **另一个独立旋钮**：`run_code` 内部子派发的 `maxParallelSubCalls`（默认 10，`packages/core/tools/src/index.ts` 第 686–693、794–801、810–813 行），与 agent-loop 的上限**无关**，别混用。

### Q3 乱序完成的结果如何回填到对应位置？

三段式，全部在 `runGroup` 内：

1. **落槽位，位移即身份。** 每条调用启动时就占一个模型下标；`dispatch` 结算的 `.then` 把结果写进 `slots[index]`（tool-calls.ts 第 176 行；`post-result`/`final-result` 同样按下标写，第 188、191 行）。先完成只是**先写自己的槽位**，不影响别人。
2. **连续头游标才提交。** `commitReady()` 从 `committed` 开始，只在下标连续有值时才推进；`slots[committed] === undefined` 就 `break`（第 147–150 行）。所以"c2 已完成、c1 未完成"时一个 `tool/result` 都不会追加——测试第 230–251 行正是断言 `release('2')` 之后结果数组仍为空。
3. **归位靠 seq 引用，不靠日志相邻。** 启动时存下该调用的 `tool/call` seq（第 135、168 行），提交时 `appendToolResult(..., callSeqs[committed]!)`（第 156 行），最终写进 `sourceEventSeqs: [callSeq]`（第 289 行）。因此日志里 `tool/call` 事件可能交错出现，但每条 `tool/result` 都精确指向自己那次调用，`deriveMessages()` 的配对不受影响（测试第 253–270 行）。

顺带两条同源的"按模型顺序回填"：工具执行后的 `additionalContexts` 在同一个提交点交给 `acceptContext`（第 157 行），agent 把它 append 到 next-step 收件箱（`packages/core/agent-loop/src/agent.ts` 第 534–537 行），所以上下文顺序是 c1、c2 而非完成顺序（测试第 383–409 行）；`concludesTurn` 也在提交时聚合（第 158 行），且最终作为 `executeToolCalls` 的返回值交给 step（第 101 行）。

### Q4 什么情况下必须独占（不并行）？

分两类，都真实存在于代码里：

**A. 框架层的 fail-closed（只要不是显式 `true` 就独占）**（`packages/core/tools/src/index.ts` 第 1296–1312 行）：

1. **未声明分类器**——`if (!tool?.isConcurrencySafe) return { kind: 'exclusive' }`（第 1305 行）。这是绝大多数工具的实际状态，参考 §4.11 的声明面。
2. **解析不到定义**：未知工具名，或对当前 scope 不可见（第 1304–1305 行）。
3. **参数非法**：`defineTool` 包装层先校验，失败直接 `return false`，不把脏参数喂给用户分类器（`packages/core/tools/src/schema.ts` 第 625–630 行）。
4. **分类器抛错**（`catch { return { kind: 'exclusive' } }`，第 1309–1311 行）。
5. **返回非严格 `true`**：`'yes'`、`1`、truthy 对象都不算（第 1308 行；测试第 95–107 行）。

**B. 设计上必须独占的语义**（一元分类器表达不了的关系规则）：

1. **会变更父会话或父级拥有状态的调用**——工具返回 `true` 即承诺不这么干（设计笔记第 55 行）；做不到就只能独占。
2. **安全性取决于"与其他并列调用的关系"的调用**，例如"两个写同一路径的调用不能重叠"。该接口无法表达"仅当路径不同才安全"，故这类调用一律独占（设计笔记第 21、81 行）。
3. **依赖有序中间件状态的调用**：pre/post-execute 之所以被强制串行，正是因为中间件可能持有顺序敏感状态（设计笔记第 45、83 行）。因此"必须与其他调用保持严格先后"的工具，纵向也依赖独占屏障。
4. **本仓的具体取舍**：bash 独占（无已证明的输入敏感分类器）、文件写入与编辑独占、`session_search` 独占、todo 变更、用户交互、workflow、PTC 变更工具与 Cordis 变更工具都独占（设计笔记第 63 行；写入/编辑的独占断言见 `packages/fs/tool-fs/tests/tools.spec.ts` 第 183–191 行）。⚠️ **这一条里的 PTC / Cordis 部分属第四编，第一次读可跳过。**

另外两个"等于必须串行"的配置事实：把 `maxParallelToolCalls` 设为 `1` 会退化成全程串行（tool-calls.ts 第 200 行；测试第 311–328 行）；`run_code` 本身也是独占的（未声明分类器 → fail-closed），其内部队列另有上限（设计笔记第 63 行；`packages/core/tools/src/ptc.ts` 第 418–432 行）。

## 附录 B 跨编内容：PTC 下的并发（第一次读请跳过）

> ⚠️ **第一次读请跳过本节。** PTC 的编程模型属**第四编 `4.7`**；留在这里是为了回查与保全既有结论。

**结论：** PTC mode 下模型只发一个原生 `run_code`，agent-loop 的调度器**看不见** run_code 内部的子派发（设计笔记第 51 行）。但工具注册表内部为 `run_code` **自建了一套同样规则的队列**：

- 分类在**每次驱动轮次**重读：`classify: () => registry.executionMode(input).kind`（`packages/core/tools/src/ptc.ts` 第 603–608 行，注释原文："Re-read per driver pass against the same agent view the SDK declared; fail-closed exclusive when undeclared/invalid."）。

按块讲解：

- **这段注释本身就是最权威的对照表**：它逐条列出了 PTC 队列与原生调度器**一致的四件事**——有序阶段（dispatch-start 追加、prepare、finalize/finish、上下文延迟、settle 追加）都在**同一条 driver lane** 内、只有 around-dispatch/body 并发；启动严格按提交顺序；结果按提交顺序经 head-of-line 游标提交；连续 `parallel` 调用最多重叠到上限，`exclusive` 调用等池排空后单独跑、**并把屏障保持到它的提交（含 post-execute）完成**。

- **`dispatches` 计数与 `PendingDispatch`** 是块内变量：前者统计本轮的派发数，后者是队列条目（`start` / `classify` / `abandon` / `commit` / `flight` / `settled` / `mode`）。**省略说明**：本块只摘注释与接口头（第 417–433 行）；`PendingDispatch` 的七个成员从第 433 行开始、其实现体与驱动循环在第 447 行之后——那些属第四编 `4.7` 的正文，此处不摘。
