## 0. 怎么读这一课

### 0.1 这一课是什么、不是什么

**是**：把"上下文被压缩时机器里发生了什么"讲到底——谁触发、按什么数字触发、落地时改了什么东西、原始内容还在不在。

**不是**：agent 循环本身（那是 `3.5`／`3.7`）、会话表层与投影的完整语义（`3.3`）、spill 与恢复（`3.13`）。本课只用到它们的最小面。

### 0.2 现在只要记住这 5 件事

1. **压缩不是删除，是"表层替换"**：把一段较早的历史节点从**派生对话**里移走，换成一个承载摘要的 `user/message` 节点；被换掉的事件**仍然逐字节躺在会话日志里**。
2. **压缩是一个能力 seam（接缝），不是一个函数**：契约是 `ctx.compaction`，提供方是 `dsh-compaction-basic`，面向用户的消费方是 `/compact` 命令。
3. **触发一共四个入口**：自动压力（每个步骤前测一次）、提供方确认的上下文溢出恢复、用户按需 `/compact`、程序化显式范围。
4. **阈值是算出来的，不是拍出来的**：`thresholdTokens = floor(min(W × thresholdRatio, W − O − headroomTokens))`，默认 `thresholdRatio = 0.8`、`headroomTokens = 65536`、`retainRatio = 0.16`。
5. **决定"何时该压缩"的那个测量不属于压缩包**：它是独立的单例服务 `ctx.tokenMeter`；压缩只是读它。

### 0.3 明确授权：这些现在不用管

- `SurfaceManager` 的增量折叠、`contentGeneration` 的缓冲重建细节——**第一次读不必弄懂**，知道"表层是从日志折叠出来的位置序列"就够了（§4.4 有落点，展开在 `3.3`）；

## 1. 最小词汇表（6 个词）

| 词 | 大白话 | 源码里的写法 |
|---|---|---|
| **surface 表层** | 会话日志**折叠出来的"模型能看到的位置序列"**。它不存内容，只存"哪些事件、按什么顺序" | `session.surface.nodes`（一串 `SessionSeq`） |
| **shadow 遮蔽** | 把一段表层节点**从位置序列里拼掉**，换成一条新节点。原事件不动 | `surfaceOp: { op: 'replace', startSeq, endSeq }` |
| **checkpoint 检查点** | 压缩后放进表层的那条**承载摘要的 `user/message`** | `compactCheckpointSource(compactionId)` 产出的消息来源 |
| **compaction seam 压缩接缝** | 一项可替换能力的三段式：契约（Service Definition）+ 提供方（Provider）+ 消费方（Consumer） | `ctx.compaction` / `dsh-compaction-basic` / `dsh-command-compact` |
| **meter 计量** | 独立服务，按当前路由给**每个表层节点**报一个 token 价 | `ctx.tokenMeter.measure(session)` |
| **log-only 仅写日志** | 这类事件只进日志、**绝不上表层**（所以它不能带 `surfaceOp`） | `compaction/start`、`compaction/summary`、`compaction/end`、`compaction/prune` |

> ⚠️ 这 6 个词里的 `surface`／投影属于**上一课（3.3）**的体系；这里只用到"它是一串位置"这个程度。为什么替换要靠代数计数、折叠怎么保证幂等，回 `3.3` 看。

**术语统一说明**：本笔记只用英文正名 `surface` / `compaction` / `seam` / `checkpoint` / `shadow`。中文文档里的"表层""压缩""能力 seam"只在引用原文时各出现一次。

## 2. 先建立画面

### 2.1 静态结构：谁是谁的一部分

```
会话日志 log（只追加、真源）
   ├─ 原始事件：user/message · assistant/message · tool/result · system/message …
   └─ 压缩自己的记账事件（仅写日志，不上表层）
        compaction/start ──► 锁
        compaction/summary ─► 摘要正文 + 被遮蔽范围 + 模型调用事实
        compaction/end ─────► 释放锁
                     │
                     │  按日志顺序折叠
                     ▼
表层 surface.nodes = [ seq₀, seq₁, … ]      ← 只是"哪些事件可见"的位置序列
                     │
                     │  replace 落地后：splice 掉被遮蔽的那一段，
                     │  在同一位置插入承载摘要的 checkpoint 节点
                     ▼
派生消息 deriveMessages() = [ 系统头, …, 检查点, 保留的尾部 ]  ← 真正进请求的东西
```

**精确性说明**：压缩事件本身**不在**表层上。文件 `packages\compaction\compaction\src\types.ts` 第 25–33 行的文档注释原文写着这类事件是 "log-only"，第 68–72 行同理；摘要正文是通过**紧随其后的另一条** `user/message` 才到达模型的。

### 2.2 动态过程：一次压缩的先后顺序

```
① 触发判定（四个入口之一）
     自动压力：agent/pre-step 里 measure() → 与 thresholdTokens 比
     溢出恢复：agent/request-error 里 failure.code === CONTEXT_WINDOW_EXCEEDED
     手动：/compact → compactNow()（要求 agent 空闲）
     程序化：compactRegion(start, end)（调用方给范围）
        │
② 选范围 selectCompactableRange()：从第一个"非系统头"节点起，尾部按 retainTokens 留字
        │
③ 校验选区 + 断言没有未闭合的 start（拿锁前先看锁）
        │
④ 同步追加 compaction/start   ← 从这一行起持锁
        │
⑤ 异步摘要：复用会话前缀 + 最后一条固定指令 → 一次 ctx.llm.stream()
        │        （失败可走 compaction/summary-error waterfall 恢复后重试）
        │
⑥ 「摘要必须更小」比较：checkpoint 的路由价 < 被遮蔽段的路由价，否则抛错回滚
        │
⑦ 提交（同步、不 yield）：追加 compaction/summary → 立刻追加带 surfaceOp 的 user/message
        │
⑧ 追加 compaction/end 释放锁（失败路径也恰好尝试一次闭合）
```

## 3. 大白话版：模型"忘了"一半对话时，机器里发生了什么

**完全不用上面的术语**，先建立画面（来源：`docs\subsystems\compaction.zh.md` 第 19–21 行对锁括住整个操作的描述，以及 `packages\compaction\compaction-basic\README.zh.md` 第 82 行的运行时说明；这里只做白话转述）。

1. 每要问模型一次之前，机器先把"这次请求大概多重"算一遍。
2. 如果重到某个线以上，机器决定"该给对话减负了"。
3. 它挑一段**较早**的历史：从头开始，但**绝不动最前面那段系统提示词**，也**绝不动最近的尾巴**。
4. 它在日志里记一句"我要开始压缩了"——这一句就是锁：别人看到它没配对的"结束"，就不许再开一次。
5. 它把这段历史、加上原来的系统提示词和工具说明书、再补一句"请把上面这段总结成检查点"的指令，**一起**发给模型。因为前缀和上一次真实请求一模一样，模型侧的前缀缓存还能用。
6. 模型回一段结构化摘要。机器检查："这条摘要比它要替换掉的那段**更短吗**？"不够短就放弃。
7. 够短，就在日志里记下摘要本身、记下被替换掉的是哪一段，然后追加**一条新的用户消息**（内容是那段摘要），并注明"这条消息取代了刚才那一段"。
8. 记一句"压缩结束了"，锁释放。
9. 之后每次组装请求，"那一段"因为已经被取代，**不再出现在给模型的消息里**；但它们**还在日志里**，谁想看都还看得到。

**这就是全篇的骨架。** 剩下的是：每一步用哪个数字、哪句代码。

## 4. 正文：机制与源码对照

### 4.1 契约层：`ctx.compaction` 与它的事件词汇

压缩的契约是抽象类 `CompactionEngine`，它把"何时压缩"和"怎么压缩"全部交给后端；契约本身只固定三个动词与一条消息来源约定。

`packages\compaction\compaction\src\index.ts` 第 31–32 行、第 119–123 行（类头与 `ctx` 键）、第 136–140 行、第 162–166 行、第 187–193 行（三个抽象签名与类尾）

```ts
/** Why automatic policy is asking a backend to consider compaction. */
export type CompactionTrigger = 'pressure' | 'context-overflow'   // ← 自动策略只有这两个原因

/**
 * Abstract compaction service. Implementations own trigger policy, retention,
 * and summarization, and may consume a separate measurement service. … Load
 * one implementation per context as `ctx.compaction`.
 */
export abstract class CompactionEngine extends Service {          // ← 块开头：抽象类
  constructor(ctx: Context) {
    super(ctx, 'compaction')                                     // ← ctx 键就是这里写死的
  }

  // …（第 124–135 行：compactIfNeeded 的 JSDoc，说明 pressure 用最新"已路由请求"、
  //    overflow 可以低于常规阈值强制执行，此处省略）
  abstract compactIfNeeded(                                      // ← 动词①：自动策略入口
    agent: CompactionAgentContext,
    trigger: CompactionTrigger,
    signal: AbortSignal,
  ): Promise<CompactionResult | null>

  // …（第 142–161 行：compactNow 的 JSDoc，说明它同步起一个 idle 任务、
  //    选不到范围就不写任何东西，此处省略）
  abstract compactNow(                                          // ← 动词②：绕过阈值的显式缩减
    agent: ManualCompactAgentContext,
    signal: AbortSignal,
    sourceCommandId?: CommandId,
  ): Promise<CompactionResult | null>

  // …（第 168–175 行：compactRegion 的 JSDoc，说明 start/end 是"表层位置"而非数值区间、
  //    两端都必须工具配对平衡，此处省略）
  abstract compactRegion(                                       // ← 动词③：调用方指定范围
    start: SessionSeq,
    end: SessionSeq,
    agent: CompactionAgentContext,
    signal?: AbortSignal,
  ): Promise<CompactionResult>
}
```

> 源码第 124–135、142–161、168–186 行是三段 JSDoc 的剩余部分（例如"模型后端必须转发取消信号""替换消息必须用 `compactCheckpointSource`"），与本课这一块无关，故上面的摘录跳到第 193 行的 `}` 为止。

按块讲解：

- **做什么**：定义 `ctx.compaction` 这一项能力的三个动词。`CompactionEngine extends Service` + `super(ctx, 'compaction')` 就是"它在共享登记处占用的名字"的来源（对照 `1.1` 第 6 节读 `ctx.sessions` 的同一手法）。
- **与哪个知识点相关**：§0.2 第 2 条"压缩是一个能力 seam"。seam 的三段式在这里只出现第一段——契约。
- **为什么这么写**：`compactIfNeeded` 的参数里**没有"范围"**，只有 `trigger`：范围策略属于后端（顺序、保留比例、是否先修剪都是可替换策略）。而 `compactRegion` 反过来——它**只接受范围**，因为调用方已经做了决定。这个分工就是"后端拥有保留策略、契约拥有动词"。
- **`CompactionTrigger` 只有两个取值**：`'pressure'`（常规压力）与 `'context-overflow'`（提供方已经确认溢出）。手动入口不在这两个值里，因为 `compactNow` 是独立的动词而不是一个 trigger 值。

**契约的另一半：事件词汇。** 三类压缩事件都是"仅写日志"，这段注释是全篇"事件不上表层"的权威出处：

`packages\compaction\compaction\src\types.ts` 第 17–33 行、第 68–72 行

```ts
declare module '@deepseek-ai/dsh-session/types' {                 // ← 块开头：声明合并进会话事件表

    /**

     * shadows the compacted range. …

      sourceCommandId?: CommandId

      shadowedRange: { start: SessionSeq; end: SessionSeq }

    } & ( /* …（第 54–67 行：rawOutput / llmStreamCall 的两个变体，
```

按块讲解：

- **做什么**：用声明合并往 `SessionEventMap` 里加三个事件类型。`compaction/start` 携带 `compactionId` 与 `turn`，`compaction/end` 携带同样的身份再带一个可选 `error`。
- **与哪个知识点相关**：§1 的 **log-only** 词条；以及 §4.5 的"锁就是一对日志标记"。
- **为什么这么写**：
  - 注释里那句 `holds the lock until compaction/end` 说明**锁不是内存对象**，而是"有 start 没 end"这个可回放的事实。所以进程崩溃留下的不是"虚假完成"，而是"可检测的遗留锁"（`docs\subsystems\compaction.zh.md` 第 19 行）。
  - `turn: number | null` 区分两种压缩：数字 = 自动压缩，必须严格装在某个已打开的轮次里；`null` = 轮次之间的独立手动尝试。
  - **`shadowedTokenCount` 与真正的"是否更小"比较不是同一个数**。这个字段是**固定启发式的影子价**（§4.6 讲）；真正决定成败的是路由价比较（§4.5 第 418–422 行）。
  - `provider` / `model` / `maxTokens?` / `usage?` 写进日志，是为了让"这次一次性摘要请求"能从**日志 + 代码**重建——注释原文的理由是 *the reconstructability Agent Note*。

### 4.2 触发条件①：自动压力（`agent/pre-step`）

自动压缩的监听器只在 `auto !== false` 时注册（`packages\compaction\compaction-basic\src\index.ts` 第 140 行，`auto` 默认 `true` 见 `config.ts` 第 108 行）。

**第一个机制知识点：监听器把"抛错"降级成"警告并继续这一轮"。**

`packages\compaction\compaction-basic\src\index.ts` 第 137–176 行

```ts
constructor(ctx: Context, config: BasicCompactionConfig = {}) {
  super(ctx)
  this.config = resolveConfig(config)
  if (this.config.auto) this._registerAutomaticCompaction()       // ← 守卫：auto 为 false 就一个监听器都不装
}

private _registerAutomaticCompaction(): void {
  const { ctx } = this                                            // ← 后面闭包里用的 ctx 从这里来
  const logResult = (result: CompactionResult, trigger: string): void => {
    ctx.logger.info(
      `compaction (${trigger}): shadowed ${result.shadowedSeqs.length} surface nodes `
      + `(seqs ${result.shadowedRange.start}-${result.shadowedRange.end}, `
      + `~${result.shadowedTokenCount} tokens)`,
    )
  }

  ctx.on('agent/pre-step', async (
    { agent, signal },                                            // ← payload 解构：agent 与本次轮次的取消信号
    next,
  ): Promise<PreStepDecision> => {
    if (!signal.aborted) {                                        // ← 守卫①：轮次已取消就什么都不做
      try {
        const result = await this.compactIfNeeded(agent, 'pressure', signal)
        if (result !== null) logResult(result, 'step pressure')
      } catch (error: unknown) {
        if (error instanceof TargetPressureConfigError) {
          if (this.warnedPressureConfigTargets.has(error.targetKey)) return next()   // ← 同一目标只警告一次
          this.warnedPressureConfigTargets.add(error.targetKey)
        }
        const message = error instanceof Error ? error.message : String(error)
        ctx.logger.warn(`step compaction failed: ${message}; continuing the turn`)
      }
    }
    return next()                                                 // ← 无论成败都放行这一步
  })
```

**机制：范围从"第一个非系统节点"起，尾部按 token 预算逐字保留，且不许切开工具调用/结果对。**

```ts
export function selectCompactableRange(
  session: Session,
  measurement: TokenMeasurement,
  retainTokens: number,
): { start: SessionSeq; end: SessionSeq } | null {
  const pricedNodes = measurement.nodes                            // ← 价格清单来自 meter 的测量结果
  if (pricedNodes.length === 0) return null

  const surfaceNodes = session.surface.nodes                       // ← 位置清单来自 session 表层
  if (surfaceNodes.length !== pricedNodes.length
    || surfaceNodes.some((seq, index) => seq !== pricedNodes[index]?.seq)) {
    throw new Error('compaction: token-meter surface does not match the current session surface')  // ← 守卫：两份清单必须逐位相等
  }
  const firstIdx = systemHead(session, surfaceNodes[0]!) === undefined ? 0 : 1   // ← 节点 0 是系统头就从 1 开始

  let accumulated = 0
  let keepFromIdx = pricedNodes.length                             // ← 默认"全留"（即没有可压的）
  for (let index = pricedNodes.length - 1; index >= 0; index -= 1) {   // ← 块开头：从尾部向前累加
    accumulated += pricedNodes[index]!.tokens
    keepFromIdx = index
    if (accumulated >= retainTokens) break                         // ← 攒够保留预算就停
  }
  if (keepFromIdx <= firstIdx) return null                         // ← 守卫：没有可安全压缩的部分

  while (keepFromIdx > firstIdx) {                                 // ← 块开头：边界回退循环
    if (toolPairingBalancedBefore(session, surfaceNodes[keepFromIdx]!)) break
    keepFromIdx -= 1                                               // ← 会切开工具对就再往前挪一格
  }
  if (keepFromIdx <= firstIdx) return null

  const first = surfaceNodes[firstIdx]!
  const cutoff = surfaceNodes[keepFromIdx - 1]!
  return { start: first, end: cutoff }                             // ← 闭区间：位置 [firstIdx, keepFromIdx-1]
}
```

按块讲解：

- **做什么**：给定"要保留多少 token"，算出"从头到哪一格可以压"。
- **与哪个知识点相关**：§4.2 里 `retainTokens` 的消费点；以及"系统提示词永不被压缩"。
- **为什么这么写**：
  - **第一件事是交叉校验两份清单**：meter 的节点序列必须与 `session.surface.nodes` **逐位相等**，否则直接抛错。原因很实际——价格是算在"当时的表层"上的，如果表层变了，价格就作废了。宁可失败也不按过期价格下刀。
  - **`systemHead` 判断只作用于位置 0**：函数返回 `undefined`（节点 0 不是 `system/message`）才允许从 0 开始。第 92–105 行的 `systemHead` 实现注释写着它包括一个 `eventAt` 历史读取，并带一处迁移期豁免标记。
  - **保留循环从尾部倒着走**：阈值是"至少留 `retainTokens`"，从最近的消息往回数最贴近"保留最近的对话"这个语义。循环结束时的 `keepFromIdx` 就是**第一个要保留的位置**。
  - **边界回退用的是 `toolPairingBalancedBefore`**：它问的是"这一格**之前**的那个切点是否平衡"。若不平衡，说明有一个助手的工具调用还没等到结果——把这一格也留给尾部，再试前一格。第 141、148 行的两次 `return null` 覆盖"范围退化成空"的两种情形。
- **`toolPairingBalancedBefore/After` 是什么**：`packages\compaction\compaction\src\tool-pairing.ts` 第 112–126 行，两个函数都只是 `cutBalance(cache, seq, 0|1)`；平衡信息按 `replaceGeneration` 缓存，位置 `i` 的切点表示"第 i 个节点之前是否平衡"（第 14–24 行的 `BalanceCache` 注释）。
- **实测锚点**（测试名，可直接搜到）：`counts the durable routed request envelope without putting it on the surface`、`rounds a retention cut head-ward to preserve tool-call/result pairing`、`declines when rounding a cut would consume the only tool pair`（`packages\compaction\compaction-basic\tests\compaction-basic.spec.ts` 第 793、879、909 行）。

- **与哪个知识点相关**：§2.1 图的最下面一层；也是"压缩后模型看到的内容如何变化"的答案。
- **为什么这么写**：
  - **"遮蔽=从派生中消失"就是这一行 `for (const seq of nodes…)` 的全部原因**：被 `splice` 掉的 seq 不在 `nodes` 里，循环自然看不见它们。**没有"跳过被压缩内容"的特殊分支**——这正是"表层是唯一真源"的价值。
  - **`contentGeneration` 触发整份重建**：替换会把该代数加一（§4.5），所以缓存不会留下过期的消息；普通追加只走增量，成本 O(新节点)。
  - **派生消息共享并深冻结**：注释原文强调返回的是新数组但 `Message` 对象是共享且冻结的，消费方无法通过它改写日志。
- **压缩不改变的东西**（都要记住，都是限定条件）：
  - **系统提示词**：选区从不以节点 0 开始，且 session 层硬拒绝兜底（§4.5）。
  - **工具定义与会话前缀**：`packages\compaction\compaction\README.zh.md` 第 161 行原文——"压缩缩减派生历史，绝不缩减系统提示词、工具或会话前缀"。
  - **近期尾部逐字不变**：范围选择的保留逻辑保证（§4.4）。
- **请求前缀缓存失效点**：`packages\compaction\compaction\README.zh.md` 第 150 行原文——替换使"从第一个被遮蔽的历史 token 起"的复用失效；之前未变的前缀仍可复用。
- **摘要模型与对话模型看到的不是同一套东西**：摘要模型看到系统头 + 工具 schema + 被遮蔽区消息 + 最后一条压缩指令；**对话模型永远看不到那次私有请求**，只有返回的文本进入检查点（推理与工具调用被排除，见 §4.7 的 `summaryText`）。

### 4.9 可选配套：工具结果修剪

**机制：不改摘要语义，只把超长工具结果的中间段换成标记；同样是"替换"。**

`packages\compaction\compaction-tool-result-pruner\src\index.ts` 第 136–171 行（`pruneSession` 的候选扫描与替换落地；第 172–181 行是统计汇总，未摘）

```ts
  pruneSession(session: Session): PruneResult {
    const candidates: SnapshotCandidate[] = []
    for (const seq of [...session.surface.nodes]) {                 // ← 块开头：对当前表层做一次快照再遍历
      const event = session.eventAt(seq)
      if (event?.type === 'tool/result') candidates.push({ seq, event })   // ← 只挑工具结果
    }

    const pruned: PrunedEntry[] = []
    let charsRemoved = 0
    for (const { seq, event } of candidates) {                      // ← 块开头：逐个改写
      const original = session.deriveEventMessage(event) as ToolResultMessage
      const content = this.pruneContent(original.content)           // ← 保留头 + 标记 + 保留尾
      if (content === null) continue                                // ← 守卫：不需要修剪就跳过
      const charsBefore = this.measureContent(original.content)
      const charsAfter = this.measureContent(content)
      const message = freezeMessage<ToolResultMessage>({ ...original, content })
      // Shadow-price protocol: the metering event and its replacement are
      // appended synchronously adjacent, so pure consumers subtract the
      // shadowed node's heuristic price without retaining per-node state.
      session.append('compaction/prune', {                          // ← ① 仅写日志的影子价事件
        shadowedRange: { start: seq, end: seq },
        shadowedSeqs: [seq],
        shadowedTokenCount: this.ctx.tokenMeter.estimateMessage(original),
      })
      const replacement = session.append('tool/result', {           // ← ② 紧接着的同步替换
        ...event.data,
        message,
      }, {
        surfaceOp: { op: 'replace', startSeq: seq, endSeq: seq },
        sourceEventSeqs: [seq],
      })
      // …（第 172–179 行：把 originalSeq / replacementSeq / callId / 前后字符数推进 pruned
      //   并累加 charsRemoved，与"影子价协议"无关，此处省略）
    }
    return { pruned, charsRemoved }
  }
```

按块讲解：

- **做什么**：扫描当前表层所有 `tool/result`，对超过字符预算的结果做"保留头 + 标记 + 保留尾"重写。
- **与哪个知识点相关**：§4.2 里 `this.ctx.get('toolResultPruner')` 那个可选依赖；`compaction/prune` 事件；"修剪可能完全免掉摘要"。
- **为什么这么写**：
  - **影子价协议（作者注释原文）**：计量事件与它的替换**同步相邻**，所以纯消费方**不必逐节点存价**就能减掉被遮蔽节点的启发式价。这与 `compaction/summary` + `user/message` 的配对是同一套协议。
  - **`sourceEventSeqs: [seq]`**：只遮蔽一个节点，所以只引一个 seq——session 层的 `assertToolResultRewrite`（§4.5）还会要求替换事件**只有 `content` 不同**，其余字段逐一深比相等。
  - **默认预算**：`thresholdChars: 8192`、`headChars: 4096`、`tailChars: 1024`（`packages\compaction\compaction-tool-result-pruner\src\config.ts` 第 9–14 行的 `DEFAULTS`）。仓库的默认装配把这三个值显式写了出来（`packages\bundle\base\cordis.patch.yml` 第 418–423 行）——**这是仓库公开文件里的默认值，不是任何人的本机配置**。
  - **修剪只在压缩触发条件满足后才跑**：低于压力的对话绝不会被触碰（`packages\compaction\compaction-basic\README.zh.md` 第 90 行）。
- **同一族的第三个成员（本课只点名）**：`compaction-image-offload` 用**纯消息投影**替换图片出现位置，**不替换节点、也不需要影子价**（`docs\subsystems\compaction.zh.md` 第 28 行；注册点见 `packages\compaction\compaction-image-offload\src\index.ts` 第 18–33 行）。

### 4.10 四个入口的手动那一条：`/compact`

`packages\compaction\command-compact\src\index.ts` 第 11–12、58–79 行

```ts
export const name = 'command-compact'
export const inject = ['commands', 'compaction']                  // ← 块开头：注入命令注册表与压缩契约

/** Execute one argument-free manual compaction request. */
async function executeCompact(
  ctx: Context,
  invocation: CommandInvocation,
): Promise<CommandResult> {
  if (invocation.rawInput.trim().length > 0) {                     // ← 守卫：不接受参数
    return { kind: 'error', text: USAGE }
  }
  try {
    const result = await ctx.compaction.compactNow(invocation.agent, invocation.signal, invocation.commandId)
    if (result === null) return { kind: 'success', text: 'No compactable history yet.' }   // ← 没有可压范围
    return {
      kind: 'success',
      text: `Compacted ${result.shadowedSeqs.length} history items (~${result.shadowedTokenCount} tokens).`,
      sourceEventSeq: result.summarySeq,
    }
  } catch (error: unknown) {
    if (invocation.signal.aborted) return { kind: 'error', text: 'Compaction cancelled.' }
    if (error instanceof ManualCompactionError) return expectedFailure(error)   // ← 六种失败码各自一句人话
    throw error                                                    // ← 非预期错误继续抛
  }
}
// …（第 24–56 行：expectedFailure，把 busy / cancelled / changed / summary / commit / persistence
//   六种失败码翻成人话；第 80–83 行：USAGE 之后、executeCompact 之前的模块级空行与分段注释；
//   第 85–107 行：apply() 的命令注册与生命周期。三者本课都不展开，此处省略）
```

按块讲解：

- **做什么**：把 `/compact` 命令接到 `compactNow`，并把失败翻译成人能读的话。
- **与哪个知识点相关**：§0.2 第 3 条的入口③；`ManualCompactionErrorCode` 六个值的消费方。
- **为什么这么写**：
  - **`ctx.compaction` 而不是具体后端**：命令插件依赖的是**契约**，所以换后端（例如未来基于模板的后端）命令不用改。这就是 seam 的第三段——Consumer。
  - **显示的是 `shadowedTokenCount`**，即启发式影子价（§4.6），所以那个 `~` 号是诚实的：它是估算。
  - **`busy` 的来源有两处**：agent 不空闲（`runMaintenance` 拿不到接纳，`compaction-basic` 第 428–434 行包成 `ManualCompactionError('busy', …)`）与日志里已有未配对的 `compaction/start`（`region.ts` 第 316–319 行）。两者的文案被合并成同一句。
- **手动路径与自动路径的两个差别**（都在 `compactSurfaceRegion` 的选项里，见 §4.5）：
  - `owner: null` → 独立标记对（`turn: null`），且**必须有** `entryState.openTurn === null`，否则报 `busy`；自动路径反过来要求**必须**有打开的轮次。
  - `stability: 'selected-span'` → 只要求**选区本身**稳定，摘要期间别处新增的上下文（例如空闲注入）不会让这次压缩作废；自动路径用 `'whole-surface'`，整份表层必须一字不变（`region.ts` 第 430–468 行）。
  - 手动路径成功闭合后还会 `flush` 一次持久化（第 410–413 行提供的 `flush` 回调），失败则报 `persistence`。

## 7. 实测命令的可执行性说明（R9）

本课用到两类只读命令（§5.1 的测试、本节第 6 条的检索），五件事逐一交代：

1. **在哪个目录跑**：必须先在 `<repo>` 根目录（vitest 的配置与 `packages/**` 路径都相对它解析）。**这一点与 cwd 相关**。
2. **可执行文件怎么找到**：`<repo>\node_modules\.bin\vitest.CMD`。**它不在 PATH 上**，要么写相对路径 `node_modules/.bin/vitest.CMD`，要么写全路径并加 `&`。前置条件是仓库依赖已装（`node_modules` 存在）；若不存在先跑包管理器安装。
3. **输出落在哪**：默认只写到 stdout/stderr，**不需要重定向**。要截断就先重定向到文件再读前 N 行——**不要**把原生命令输出用管道喂给 `Select-Object -First N`（见第 4 条）。
4. **副作用**：不修改任何已跟踪文件、不建目录、不写业务数据；vitest 会在临时目录放缓存。**它不会** 打模型、不会起服务。
5. **典型报错与含义**：
   - 测试表格显示全绿但退出码是 `1` —— 通常是 PowerShell 因 stderr 上的插件提示而额外报的原生命令错误，或管道提前关闭掐死了子进程。以表格里的 `Test Files / Tests` 为准，或先重定向再读。
   - `No test files found` —— 路径写错或漏了 `run` 子命令（不加 `run` 会进 watch 模式，交互式挂住）。
   - 报找不到 `vite-tsconfig-paths` 之类插件 —— 依赖没装全，先装依赖。
6. **附录 A ② 那条"未找到"是怎么查的**：在 `<repo>` 根目录用 PowerShell 原生检索（只读、无副作用、无输出落盘；本机 **`rg` 不在 PATH 上**，所以用 `Select-String`）：

   ```powershell
   # cwd：<repo> 根目录
   Get-ChildItem -Recurse -File -Path 'packages/compaction' |
     Select-String -Pattern 'recall|Recall|readBack|unshadow'
   ```

## 10. 本课的三句话总结

1. **压缩改动的是"位置序列"，不是"内容"**：一条 `splice`，两代计数，日志一字不改。
2. **一切可控性都来自"先记日志、后生效"**：锁是一对标记，替换是可回放的决策，摘要是否更小是一次可复算的比较。
3. **压缩不属于主干**：它挂事件、读计量、被后端替换。想换一种压缩策略，装另一个 Provider 即可。

## 附录 A 四题解答

> ⚠️ **第一次读请跳过本节。** 它要求先读过 §4 的全部机制。内容留着供回查，不要挡在读路径上。

### ① 何时触发压缩？触发条件是什么？

**四个入口，条件各不相同。**

**1. 自动压力（默认开启）**：每个步骤在请求派生前于 `agent/pre-step` waterfall 里测一次（`packages\compaction\compaction-basic\src\index.ts` 第 158–176 行）。条件是 `measurement.totalTokens >= spec.thresholdTokens`（第 319 行），其中

`thresholdTokens = floor(min(W × thresholdRatio, W − O − headroomTokens))`（`packages\compaction\compaction-basic\src\config.ts` 第 191–194 行）

- `W` = 适配器声明的 `contextWindow`；`O` = 本次路由请求预留的输出 token（信封 `maxTokens`，否则适配器默认值，否则 0 —— `index.ts` 第 65–68 行）；`headroomTokens` 默认 `65536`；`thresholdRatio` 默认 `0.8`（`config.ts` 第 20–23、75–79 行）。
- **实测锚点**：窗口 1,048,576 / 输出 256,000 → 阈值 727,040、保留 126,812；窗口 1,000,000 / 输出 0 → 阈值 800,000、保留 160,000（`packages\compaction\compaction-basic\tests\compaction-basic.spec.ts` 第 430–435 行的用例表，断言见第 439–443 行）。
- `retainTokens = floor((W − O) × retainRatio)`（默认比例 `0.16`）或显式 `retainTokens`，且**必须严格小于阈值**，否则加载期或首次使用期抛错（`config.ts` 第 195–204、229–241 行）。
- 触发前还有两个前置守卫：没有"已路由请求"→ 直接返回 `null`（`index.ts` 第 274–275 行）；适配器没声明容量 → 抛 `TargetPressureConfigError`，且**同一目标只警告一次**（第 166–173、307–313 行）。

**2. 溢出恢复（被动）**：仅在提供方把失败规范化为 `CONTEXT_WINDOW_EXCEEDED` 时介入，且 `maxOverflowRetries`（默认 1）未耗尽（`index.ts` 第 194–200 行）。这一路径**不看阈值**，直接做一次最大平衡头部缩减（第 294–302 行，`selectCompactableRange(..., 0)`）。

**3. 手动 `/compact`**：任何时候都绕过阈值，但要求 agent 空闲——`runMaintenance` 拿不到空闲接纳就抛 `ManualCompactionError('busy', …)`（`index.ts` 第 383–435 行；命令处理器 `packages\compaction\command-compact\src\index.ts` 第 59–79 行）。

**4. 程序化 `compactRegion(start, end, …)`**：调用方指定范围，要求存在未结束的轮次（`region.ts` 第 197–202 行）。

**统一的额外前提**：任何入口都要求没有未匹配的 `compaction/start` 锁（`region.ts` 第 184–189、308–320 行）；摘要还需要一个模型目标，否则报错（`packages\compaction\compaction-basic\src\summarizer.ts` 第 137–142 行）。

### ② 「遮蔽而非删除」在实现上如何落地？原始事件还在吗？

**还在。** 落地方式是三步：

1. 摘要替换事件带 `surfaceOp: { op: 'replace', startSeq, endSeq }` 与完整覆盖被遮蔽节点的 `sourceEventSeqs`（`packages\compaction\compaction-basic\src\region.ts` 第 506–509 行；语义定义 `packages\core\session\src\types.ts` 第 449–464 行）。
2. session 折叠把这一段从位置序列里 `splice` 掉，只留下替换节点自己的 seq，并把 `replaceGeneration`、`contentGeneration` 各加一（`packages\core\session\src\surface.ts` 第 569–572 行）。
3. 原始 `SessionEvent` 从未被改动。§5.3 的探针记录显示：替换后表层是 `[2]`，但 `snapshotEvents()` 长度是 3，seq 0/1 的 `user/message`、`assistant/message` 仍可按 seq 取回完整 `data`（含原文）。同一条事实由仓库测试独立覆盖：`packages\core\session\tests\surface.spec.ts` 第 690–703 行。

**配套证据**：`compaction/start`、`compaction/summary`、`compaction/end`、`compaction/prune` 四类事件都是"仅写入日志、不得携带 `surfaceOp`"——`SurfaceOp` 只对五类产消息事件合法（`packages\core\session\src\types.ts` 第 433–444 行；`packages\compaction\compaction\src\types.ts` 第 19–24、68–72、73–89 行的注释原文 "log-only"）。如果一条非产消息事件硬要带 `surfaceOp`，session 层会抛 `… is not surface-eligible and cannot carry surfaceOp`（`surface.ts` 第 304–313 行）。

**代价也说清楚**：**模型侧的原始内容确实不可读了**。摘要文本里没有指回被遮蔽区段的引用；`shadowedRange` 只存在于模型不可见的 `compaction/summary` 事件上。**在 `packages\compaction\` 全文检索「recall / readBack / unshadow（回读被遮蔽区段）」：未找到任何实现或导出**（检索命令见 §7；`shadowedRange` 的全部出现处只有事件载荷定义与日志打印，见 `packages\compaction\compaction\src\types.ts` 第 38、84、115 行与 `packages\compaction\compaction-basic\src\index.ts` 第 153 行）。也就是说：**日志里能取回原文，但没有任何面向模型或面向用户的"取回"路径**。

### ③ 压缩后模型看到的内容如何变化？

- **少了一整段，多了一个节点。** `deriveMessages()` 只遍历 `surface.nodes`（`packages\core\session\src\index.ts` 第 856–877 行），被替换的节点不在其中；摘要节点取而代之，并且**占在被替换段原来的位置**上。
- **摘要节点的形状**：一条 `user` 角色消息，内容是 `CHECKPOINT_PREAMBLE` + `\n\n` + `<compacted-summary>` + 模型正文 + `</compacted-summary>`（`packages\compaction\compaction-basic\src\summarizer.ts` 第 188–194 行）。开场白明确要求模型"把捕获的上下文当作既定背景，不要复述，不要承认这个检查点"（第 70–71 行）。
- **近期历史逐字不变**：范围选择的保留尾逻辑（§4.4）保证尾部节点不进入选区。
- **系统提示词不变**：选区从不以节点 0 开始（`region.ts` 第 131 行），session 层还有硬拒绝兜底（`surface.ts` 第 487–507 行）。压缩也**不缩减**系统提示词、工具定义或会话前缀（`packages\compaction\compaction\README.zh.md` 第 161 行）。
- **请求前缀缓存失效点**：从第一个被替换的历史 token 起失效，之前的未变前缀仍可复用（`packages\compaction\compaction\README.zh.md` 第 150 行）。
- **摘要模型看到的是另一套东西**：系统头 + 工具 schema + 被遮蔽区域消息 + 最后一条固定压缩指令（`region.ts` 第 544–563 行；`summarizer.ts` 第 32–67、144–162 行）。会话模型永远看不到这次私有请求或其推理；只有返回的文本进入检查点，推理与工具调用被排除（`summarizer.ts` 第 213–221 行的 `summaryText`）。

### ④ 压缩与 token 计量的关系？

- **计量决定触发，但不属于压缩包。** 决定何时压缩的测量是独立服务 `ctx.tokenMeter`（`packages\compaction\compaction\README.zh.md` 第 78 行；`packages\llm\token-meter\src\index.ts` 第 100–111、146–191 行）。`compaction-basic` 声明注入 `['llm', 'tokenMeter', 'sessions']`（`packages\compaction\compaction-basic\src\index.ts` 第 114 行）。
- **压力值有明确口径**：`measurement.totalTokens` 是请求 + 响应压力（= `baseline + surfaceDeltaTokens`，下界 0），比较对象是 `thresholdTokens`（`index.ts` 第 319、340 行；口径出处 `token-meter\src\index.ts` 第 187 行）。所以"余量"不是 `W − 当前历史` 这么简单——输出预留与 `headroomTokens` 都先被扣掉。
- **保留预算是另一个数字**：`retainTokens = floor((W − O) × retainRatio)` 或显式 `retainTokens`，且必须小于阈值（`config.ts` 第 195–204 行）。它喂给 `selectCompactableRange` 决定尾巴留多长（`region.ts` 第 117–155 行）。
- **一次压缩报两类 token 数**：`CompactionResult.shadowedTokenCount` 是**固定启发式**的影子价（`region.ts` 第 376–381 行），`/compact` 把它显示给用户（`packages\compaction\command-compact\src\index.ts` 第 68–72 行）；而"摘要是否真的更小"用的是**路由定价**的 `shadowedRouteTokenCount` 与 `estimateMessage(checkpointMessage)` 相对比较（`region.ts` 第 414–422 行）。
- **修剪也会被重新计价**：一旦压力成立，先 `prune.pruneSession(...)`，再 `meter.measure(...)` 重新测量，然后再选摘要范围（`index.ts` 第 321–327 行）；修剪自身用 `estimateMessage(original)` 记录被替换节点的影子价（`packages\compaction\compaction-tool-result-pruner\src\index.ts` 第 160–164 行）。
- **只用计量下界，不做乐观假设**：压力判据读取的是**已记录的最新区块请求信封**（`session.requestHeader()?.config`，`index.ts` 第 48–57 行）；压缩不改写系统提示词、工具或前缀，因此这些部分不因压缩而变小。
- **准确度是近似的**：`tokenMeter` 的固定启发式约每 token 四字符加结构开销，对 CJK 与 JSON Schema 明显低估；只有适配器声明了图片定价的路由上，图片才带提供方精确视觉 token（`packages\llm\token-meter\README.zh.md` 第 68 行）。UI 占用显示与压缩读取的不是同一个数（同文件第 68 行）。
